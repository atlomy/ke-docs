Federation and Marketplace

Audience: Super admin / platform operator Last aligned with platform state: 2026-05-25 Platform version: V2 (pre-1.0)

Purpose​

KE uses a unified federation / marketplace pattern across three slots: Ingest (raw sources entering the platform), Alignment (standards the platform projects, federates, or exports to), and Workspace (pickers, widgets, viewers researchers see). Each slot has its own scope-distinct registry; all three share the same contract shape (capability URI binding). Domain Bundles compose capabilities across all three slots as the marketplace unit. Read this when curating the Tier-1 anchor bundle catalog, when reviewing a pilot-tenant Tier-2 bundle, or when onboarding a new connector under Spec 0023.

Features​

  • Three slots, one contract — Ingest / Alignment / Workspace are three faces of one registry pattern; capability URIs are the binding interface. Substrate: ADR-043 (PR #375) · Maturity: Built · Limit: cross-slot hard dependencies must be declared per the ADR-043 amendment mandate.
  • Domain Bundle — the marketplace unit; bundles compose capabilities from one or more slots into a coherent package a tenant can subscribe to. Substrate: ADR-043 · Maturity: Built · Limit: bundles obey the provisional URI namespace prefix convention per the ADR-043 same-day amendment.
  • Tier-1 anchor bundles — platform-canonical, curated by platform staff. Substrate: ADR-043 · Maturity: Built · Limit: Tier-1 entries are platform-published; not editable by tenants.
  • Tier-2 pilot-tenant bundles — pilot-cohort-specific, conditional on platform review. Substrate: ADR-043 · Maturity: Built · Limit: Tier-2 entries require platform-staff acceptance before any tenant subscription path goes live.
  • Platform-team-only publish (MVP) — community / tenant publish flow is designed-for but deferred until a production cohort proves the contract. Substrate: ADR-043 · Maturity: Deferred (publish flow) · Limit: the marketplace MVP is platform-staff-only.
  • Spec 0023 connector registry — multi-source tenant onboarding connectors register alongside ingest-slot federations as a marketplace-from-start design. Substrate: Spec 0023 (PR #369) · Maturity: Built · Limit: connector entries follow the ADR-043 contract shape; no flat vendor-list path.
  • ADR-006 binding preserved — archetypes remain platform-fixed canonical structure; researchers create entities, declare slot configs, and subscribe to bundles within archetypes; they never create new archetypes. Substrate: ADR-006 (unchanged by ADR-043) · Maturity: Built · Limit: this is a hard invariant — no bundle can introduce a new archetype as a side effect.

Usability — how you use it​

Curating the Tier-1 anchor catalog​

  1. Open the federation registry surface under the platform admin. The first-party capability URIs and any Domain Bundles that compose them are listed per slot.
  2. To add a Tier-1 anchor bundle, declare the capability URIs the bundle composes (across Ingest / Alignment / Workspace as needed) and the bundle metadata (no tenant payload). Confirm the URI namespace prefix matches the ADR-043 provisional convention.
  3. If the bundle declares a cross-slot hard dependency, the ADR-043 amendment requires the dependency be declared explicitly. The registry will reject undeclared cross-slot dependencies.
  4. Tier-1 publish is platform-staff-only; no tenant approval is required, but the bundle should be cross-referenced from the relevant ADR or spec.

Reviewing a Tier-2 pilot-tenant bundle​

  1. The submitting tenant proposes the bundle through the platform program path (not via the admin UI). The platform-staff review verifies the bundle composes only capabilities the tenant is entitled to under their archetype subscriptions.
  2. Confirm the bundle does not require introducing a new archetype — that is a hard invariant per ADR-006.
  3. Accept the bundle into Tier-2 if the review passes; the bundle becomes available to other pilot tenants on the same cohort.

Onboarding a new connector under Spec 0023​

  1. The connector registers under the Ingest slot as a federation entry, not as a flat vendor-list row. The Spec 0023 reframing makes this the canonical path.
  2. Provide the connector's capability URI and the slot binding. No tenant payload appears in the registry entry.
  3. Confirm the connector's secrets are managed via secrets-management.md — never inline in the registry.

Red lines​

  • Marketplace curation does not expose tenant payload; bundle metadata and capability URIs carry no tenant content.
  • Per-tenant bundle subscriptions are tenant-administered; the platform tier sees aggregate subscription counts only.
  • Connector registry entries must not embed credentials, URLs with userinfo, or payload-adjacent detail. See secrets-management.md.
  • Canonical red-lines block: see platform_monitoring.md.

Troubleshooting​

  • Symptom: Bundle declaration rejected with a cross-slot dependency error. Likely cause: The bundle composes capabilities across two or more slots but did not declare the cross-slot dependency explicitly. Fix: Add the dependency declaration per the ADR-043 same-day amendment. Escalate: ADR-043 owner if the dependency is novel and the contract needs clarification.

  • Symptom: A Tier-2 bundle proposal includes what looks like a new archetype. Likely cause: The submitting tenant misunderstood ADR-006; archetypes are platform-fixed canonical structure. Fix: Reject the proposal. The tenant should instead declare a slot config or subscribe to an existing bundle within an existing archetype. Escalate: ADR-006 owner if the proposed structure represents a genuine gap in the canonical archetype set; that path is platform-driven, not tenant-driven.

  • Symptom: Connector registry entry rendered with a credential or URL userinfo. Likely cause: Severe red-line violation — credentials must be referenced via the ExternalServiceCredential substrate, not inlined. Fix: Capture the entry reference, do not screenshot. Escalate: security on-call — see secrets-management.md for the correct path.

  • Symptom: Bundle composes a capability URI that resolves to a different slot than its namespace prefix suggests. Likely cause: The provisional URI namespace prefix convention was not followed when the capability was registered. Fix: Re-register the capability with a correct namespace prefix; bundles referencing the old URI need to be updated. Escalate: ADR-043 amendment owner.

  • Symptom: Tenant attempts to publish a community / Tier-3 bundle through the admin UI. Likely cause: Misunderstanding of the MVP scope — community / tenant publish is deferred. Fix: Reject the publish; the contract is designed-for but the publish flow is not live. Escalate: not required; this is by design.
