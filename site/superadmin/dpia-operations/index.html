DPIA Operations

Audience: Super admin / platform operator Last aligned with platform state: 2026-05-25 Platform version: V2 (pre-1.0)

Purpose​

When a tenant enables DecisionEvent capture, the platform records a DPIA refresh trigger so the data-protection officer can refresh the tenant's DPIA before the captured stream is treated as DPA-covered. Read this when verifying that a DPIA refresh trigger landed, when investigating a missing audit row, or when running the routine shift sweep covered in platform_monitoring.md. This is a compliance audit surface, not a capture-control surface — capture remains opt-in per tenant via Django admin (Spec 0018 H.8); the log records that the opt-in happened.

Features​

  • DPIA refresh trigger log — audit rows for DecisionEvent capture enablement on the Operations tab at /admin/monitoring/platform/?tab=operations. Substrate: Spec 0018 PR #315 (US-C.7.1) · Maturity: Built · Limit: read-only; gated by require_platform_staff(...).
  • H.8 audit source — trigger entries sourced from the H.8 audit log on per-tenant TELEMETRY_CAPTURE override changes. Substrate: Spec 0018 H.8 · Maturity: Built · Limit: toggle is Django-admin-only — there is no API for tenant self-enablement, so every entry has a known acting admin user id.
  • LIA framework alignment — DecisionEvent inherits ADR-016 §A10's legitimate-interest assessment under GDPR Art. 6(1)(f); the recommender-calibration purpose is named explicitly. Substrate: ADR-016 §A10 amendment · Maturity: Built · Limit: LIA scope is bounded to recommender-calibration; new purposes require an LIA amendment.
  • Capture vs logging distinction — the DPIA log records enablement events, not captured DecisionEvent payload. Substrate: Spec 0018 design §4.7 · Maturity: Built · Limit: payload lives in tenant-local telemetry and is inaccessible from the platform tab.

Usability — how you use it​

Verifying a DPIA refresh trigger landed​

  1. Open /admin/monitoring/platform/?tab=operations. The DPIA log is one of three operator views on the tab (the other two — Bedrock invocation logging health and the operator incident timeline — are documented in incident-operations.md and platform_monitoring.md).
  2. For each new-enablement row, confirm: opaque tenant ref, timestamp, acting admin user id (Django auth), DPIA refresh status (required / in-progress / completed with refresh date), and source audit row reference.
  3. If the DPIA refresh status is required, alert the DPO so the tenant's DPIA can be refreshed before the capture stream is treated as DPA-covered. Capture remains opt-in regardless; the DPIA refresh is a compliance obligation, not a capture gate.
  4. After the DPO completes the refresh, the row updates to completed with the refresh date.

Pre-flight before changing per-tenant capture posture​

  • Do not toggle a per-tenant TELEMETRY_CAPTURE override outside the Django admin path. The H.8 audit row is the legal record of the toggle event.
  • Confirm the PaPostureModal intercept is reachable (see incident-operations.md).
  • Confirm a recent DPIA refresh has been completed for the tenant before treating the captured stream as DPA-covered. The log is the operator's confirmation surface.

Red lines​

  • The DPIA log displays only the enablement metadata above. It does not display DecisionEvent payload, recorded reasons, or per-event detail.
  • Tenant identification is via opaque ref only.
  • The log is the compliance trail for the toggle event; it is not a back-channel into the tenant's captured data. If DPIA review needs payload-adjacent detail, the DPO enters the tenant boundary under the existing access-control regime.
  • Canonical red-lines block: see platform_monitoring.md.

Troubleshooting​

  • Symptom: DPIA log shows a new-enablement row with no acting admin user id. Likely cause: Audit row was written from a background management command rather than the admin UI — should not happen in normal flow because the per-tenant override is Django-admin-only (Spec 0018 H.8). Fix: Verify by reading the per-tenant TELEMETRY_CAPTURE override audit directly; if that audit also lacks the acting admin, treat as an integrity event. Escalate: security on-call — possible direct DB mutation or contract violation.

  • Symptom: DPIA refresh status remains required past the agreed refresh window. Likely cause: DPO has not completed the refresh, or the completion update failed to write. Fix: Contact the DPO with the row reference; if the DPO confirms the refresh was completed, verify the completion row landed in the H.8 audit. Escalate: program ops if the refresh is genuinely outstanding past the agreed SLA.

  • Symptom: DecisionEvent capture is enabled for a tenant but no DPIA log row exists. Likely cause: Either the enablement happened before Spec 0018 PR #315 shipped (the trigger is forward-only), or the audit write failed. Fix: Check the per-tenant TELEMETRY_CAPTURE override audit history; if the override is recent and post-PR #315, treat as an integrity event. Escalate: security on-call if the timing rules out the pre-PR backfill explanation.

  • Symptom: DPIA log row references a captured DecisionEvent payload field. Likely cause: Severe red-line violation — the log is enablement-metadata-only by contract. Fix: Capture the row reference. Do not screenshot or quote the payload field in any escalation artifact. Escalate: security on-call immediately; file under Spec 0018 §4.7.

  • Symptom: Tab loads but DPIA log section is empty across all known recent toggles. Likely cause: Either the capability gate is blocking the read (unlikely — same gate as the surrounding tab), or the GraphQL filter is excluding all rows due to a query regression. Fix: Refresh the tab; confirm require_platform_staff(...) is satisfied; check the H.8 audit directly to confirm rows exist. Escalate: Spec 0018 US-C.7.1 owner.
