LLM Providers Guide

Audience: Super admin / platform operator Last aligned with platform state: 2026-05-25 Platform version: V2 (pre-1.0)

Purpose​

The platform's in-product AI surfaces (ambient import-wizard chat, AI-assisted manual grounding, future AI assists) issue single LLM calls through a thin provider abstraction. This page is the operator runbook for that substrate: which providers are wired today, how to switch them per environment, where credentials live, and how to diagnose a degraded provider call. Read this when an AI-assist surface returns provider_unavailable, when rotating provider credentials, or when standing up the AI runtime in a new environment. The contract that bounds what these providers may do is ADR-014-α (single-call assist; bounded agency; never autonomous mutation of platform state).

Features​

  • Provider abstraction — data_import.llm_providers.get_llm_provider() returns a BaseLLMProvider selected by the LLM_PROVIDER setting; current concrete providers are MockProvider (default in development) and BedrockProvider (live cloud provider). Substrate: data_import/llm_providers.py · Maturity: Built · Limit: the abstraction surfaces a single-call interface; multi-step agent loops are out of scope per ADR-014-α.
  • AWS Bedrock as the live provider — configured via AWS_BEDROCK_REGION and BEDROCK_MODEL_ID; credentials via BEDROCK_AWS_ACCESS_KEY_ID / BEDROCK_AWS_SECRET_ACCESS_KEY / BEDROCK_AWS_SESSION_TOKEN, an IAM role via BEDROCK_AWS_PROFILE, or via the ExternalServiceCredential substrate with auth_scheme = aws_iam_role. Substrate: atlomy/settings.py + data_import/llm_providers.py · Maturity: Built · Limit: aws_iam_role is preferred; token-backed fallbacks should only be used where IAM roles are not yet provisioned.
  • Mock provider as the default — LLM_PROVIDER = mock is the default; the mock provider returns deterministic stub responses for development and CI. Substrate: MockProvider in data_import/llm_providers.py · Maturity: Built · Limit: mock is not acceptable in any environment that serves researchers.
  • AI assist call wrapper — atlomyapp/slot_taxonomy/ai_assist.py issues single calls through the provider abstraction; failure paths set intent = "provider_unavailable" and log to tenant-local telemetry. Substrate: ADR-014-α + Spec 0026 + ai_assist.py · Maturity: Built · Limit: a failed provider call falls back to documented degraded behavior; no silent mutation of platform state.
  • Tenant-local AI-call telemetry — every call records task, model + version, tokens, latency, refusal / escalation flag, injection-classifier verdict, and one-way hashes of prompt + response. Substrate: telemetry/services/llm_call.py + telemetry/models.py · Maturity: Built · Limit: raw prompt and raw response text are never recorded; tenant pseudonym only — never end-user identity.
  • ADR-014-α single-call assist contract — bounds what these providers may do across all in-product AI surfaces. Substrate: ADR-014-α (Proposed, α-activated 2026-05-21) · Maturity: Built (codified from Spec 0017 C.3 ambient chat + Spec 0020 v1.2 §10.2 Wave 2) · Limit: multi-step agent loops, agent-to-agent coordination, autonomous state mutation — all out of scope; β remains deferred.

Usability — how you use it​

Configuring the AI runtime in a new environment​

  1. Choose a provider. LLM_PROVIDER = bedrock is the live cloud path; LLM_PROVIDER = mock is dev-only. Set in the environment's .env.
  2. For Bedrock, provide AWS_BEDROCK_REGION and BEDROCK_MODEL_ID. Prefer IAM role credentials over static keys; provision via the ExternalServiceCredential substrate (see secrets-management.md) with auth_scheme = aws_iam_role.
  3. Restart the Django app inside the django_app container. The provider abstraction picks up the new settings on next process start.
  4. Verify by triggering a known AI-assist surface (e.g., ambient import-wizard chat or Spec 0020 v1.2 §10.2 Wave 2 manual-grounding assist) and confirming the call lands in tenant-local AI-call telemetry with the expected model id.

Rotating Bedrock credentials​

  1. Rotate at AWS. If using the ExternalServiceCredential substrate, the secret_ref does not change; re-run admin Validate per secrets-management.md to confirm ok.
  2. If using static BEDROCK_AWS_* env vars, update the environment's .env and restart the django_app container.
  3. Trigger one assist call to confirm the rotation propagated; check tenant-local AI-call telemetry for a fresh call with no intent = "provider_unavailable".

Pre-flight before changing providers​

  • Do not switch from bedrock to mock in any environment that serves researchers — the mock provider returns stubs and will silently degrade AI-assist surfaces.
  • Confirm the target provider is wired (currently only mock and bedrock are concrete providers); other settings will fall back to mock per get_llm_provider.
  • Confirm tenant-local AI-call telemetry capture is enabled if you want the rotation to be observable. Tenant-local telemetry follows the per-tenant TELEMETRY_CAPTURE posture (see dpia-operations.md).

Red lines​

  • No raw prompt text and no raw response text in any persisted row — only one-way hashes.
  • No end-user identity in telemetry — only platform pseudonym.
  • No provider error payload in operator-facing surfaces — validation reports ok / not_allowed / unavailable plus exception class name only.
  • Provider credentials never inline in code or in registry entries — always via the ExternalServiceCredential substrate or environment variables. See secrets-management.md.
  • Canonical red-lines block: see platform_monitoring.md.

Troubleshooting​

  • Symptom: AI-assist surface returns provider_unavailable. Likely cause: The Bedrock provider call failed — either an IAM permission issue, a region or model id mismatch, or a transient AWS service issue. The wrapper sets intent = "provider_unavailable" and logs to tenant-local telemetry. Fix: Check tenant-local AI-call telemetry for the call's exception class. Confirm AWS_BEDROCK_REGION and BEDROCK_MODEL_ID are set correctly; confirm the IAM principal has Bedrock invoke access for the requested model. Escalate: AWS account owner if IAM scope is the cause; ADR-014-α owner if the wrapper itself is misbehaving.

  • Symptom: Provider abstraction silently falls back to MockProvider in production. Likely cause: LLM_PROVIDER is unset or set to a value other than the currently wired providers (mock, bedrock); get_llm_provider defaults to mock. Fix: Set LLM_PROVIDER = bedrock in the environment's .env and restart the django_app container. Escalate: not required; this is a configuration issue.

  • Symptom: AI-call telemetry rows are missing the model id. Likely cause: The provider returned a malformed response and the telemetry wrapper recorded the call with a degraded shape. Fix: Check BEDROCK_MODEL_ID for typos; confirm the model id is one the IAM principal has access to. Escalate: ADR-014-α owner if the model id is correct and the malformed shape persists.

  • Symptom: Bedrock IAM permission denied on bedrock:InvokeModel. Likely cause: The IAM principal has not been granted invoke access for the requested model, or model access has not been enabled in the Bedrock console for the account. Fix: Grant bedrock:InvokeModel scoped to the specific model ARN; enable model access in the Bedrock console. Scope IAM to specific ARNs, never *. Escalate: AWS account owner.

  • Symptom: AI-call telemetry shows a raw prompt or raw response value. Likely cause: Severe red-line violation — telemetry should record one-way hashes only. Fix: Capture the row reference. Do not screenshot or quote the raw content. Escalate: security on-call immediately.

  • Symptom: Same call retried multiple times in the same window. Likely cause: An AI-assist surface is missing idempotency or the caller is not honoring the single-call contract from ADR-014-α. Fix: Identify the calling surface via tenant-local telemetry; confirm it issues one call per user action. Escalate: ADR-014-α owner if a new surface is violating the single-call invariant.
