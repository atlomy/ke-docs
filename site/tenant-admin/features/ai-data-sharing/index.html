What AI Features Send

Purpose​

Turning on an AI feature means some of your project's information is sent to an AI provider outside the platform. This page states, for each feature listed here, exactly what that is — so the decision is made with the facts rather than an assumption.

Do not read this page as a complete list of what is active. It documents the features described below and no others, and the defaults are not uniform: reader names and AI grounding both start switched off and wait for an administrator, while the import assistant starts switched ON for a newly provisioned project. If you are compiling a record of what leaves your project, treat this page as covering the features it names, and ask your platform operator about any AI surface not documented here.

Read it before enabling any AI feature, and again if your institution asks you what leaves the platform on your project's behalf.

The two features on this page differ on the question that matters most, so there is no single rule to carry between them.

Reader names for collections sends only the shape of your data: the names you gave your tables and columns, and one word chosen for readers. No value from inside a record is sent.

Vocabulary grounding suggestions is the exception, and it is the reason this page cannot state one rule for both. Grounding exists to ask what a particular value in your records means, so the value itself is what is sent — a word or phrase a researcher typed into a field. If your reason for reading this page is to know whether record content leaves the platform, the answer is yes for this one feature, under the limits its section sets out.

The data-protection consequence​

Enabling an AI feature makes the configured AI provider a sub-processor of whatever that feature sends. If your institution keeps a record of sub-processors, or your project works under a data-protection agreement, the enabling decision belongs in that record, and this page is the description of what the sub-processor receives.

Which provider is configured, and whether it is your own account or the platform's, is an environment decision — see Environment settings. Turning a feature on does not change the provider; it changes what the provider is given.

Reader names for collections​

What it does. During the import wizard, this feature asks the AI provider what one record of a collection should be called for readers — "Specimen" rather than specimens_tbl. It proposes; nothing is written until a researcher accepts. See Voice and vocabulary for how an accepted name is used.

What is sent. For each collection in one import session, and nothing else:

WhatWhere it comes from
Source table namesThe names of the tables you imported
Source column namesThe column names in those tables, capped per collection
Structural typeThe archetype the platform assigned to the collection
Role identifierThe platform's own internal name for the collection's role
A per-request handleGenerated for the request; means nothing outside it
The reader name in use todaySee below — this one can be text a person wrote

Why the last row matters. The name readers currently see is sent so the model can leave a collection alone when its name is already right — it cannot make that judgement without knowing the current name. Usually that name was derived by the platform. But it can also be a name your project set by hand, or one a researcher accepted and edited on an earlier import. In those cases the text a person typed is part of what is sent.

A disclosure that said only "table and column names" would understate this, so it is stated plainly instead: the current reader name is sent, and it may be your own wording.

What is not sent. No rows. No field values. No record content of any kind. Nothing about who is in your project or who ran the import.

How often. Once per collection when a suggestion reaches you, and re-opening the wizard does not send again, because the first answer is reused.

Three is the limit on suggestions you SEE, not on collections sent. A session shows at most three reader-name suggestions. But when the AI answers for a collection and the platform then withholds the suggestion — because it matches the name already in use, or is not confident enough — that collection's place is released rather than counted, so further collections can still be sent. This is deliberate: a withheld suggestion should not use up one of your three. It does mean the number of collections described to the provider in one session can exceed three.

What actually bounds it is the session's token budget, which your administrator sets and which refuses a request before the provider is contacted. If you need a hard ceiling on what leaves the project, that budget is the control — not the count of suggestions on screen.

A request that fails is the exception, and it matters for this page. When the provider does not answer, or answers unusably, nothing is remembered — so the collection becomes eligible again and each use of Try again sends the same table names, column names and current reader name once more. What bounds that is the session's token budget, not a count of attempts: once the budget cannot cover another request, the platform refuses it before contacting the provider. So the honest ceiling on a failing session is the budget your administrator set, not "once".

Turning it off. A project administrator can disable it at any time, and the switch takes effect immediately: a suggestion already on screen can no longer be accepted after the feature is switched off.

Vocabulary grounding suggestions​

What it does. Some values in your records have no grounded reading — a term the platform cannot match to any vocabulary it knows. This feature asks what such a value might mean: first a public authority service, then the AI provider. It proposes; nothing is written until a researcher accepts.

What is sent — including record content. The ungrounded value itself, which is text from inside a record:

WhatWhere it goes
The ungrounded valueThe public authority service, as the search query
The ungrounded value, or a stand-in for itThe AI provider, in the prompt — see below
The kind of value it isThe AI provider, as the platform's own category name
Candidate matches the authority returnedThe AI provider, to be judged

What the model receives depends on a gate. Before the value reaches the prompt it is checked, and only a value that passes is sent as written. A value that does not pass is replaced by a keyed one-way hash of itself, or by [redacted] when it is classified as unsafe to send. The gate refuses a value when its kind is not on the allowlist, when it is empty or longer than the permitted length, when it carries a signal associated with personal data, or when it is an internal platform key rather than something a person wrote.

The authority lookup is gated too, inside the connector that performs it, and a refused lookup is not attempted. But treat the plain reading as the operative one for a consent decision: when the gate allows a value, that value leaves your project verbatim, to a public service and to the AI provider.

What is not sent. Whole rows. Other fields of the record the value came from. Your schema's identity — the platform's internal name for your project is used only as the key for the hash and does not itself reach the prompt.

How often. Once per suggestion request. What bounds it is a rolling 24-hour token budget your administrator sets; when the budget cannot cover another request the platform refuses it before the provider is contacted.

Turning it off. A project administrator can disable it at any time.
