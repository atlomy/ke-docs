Making fields searchable: search, facets, and autocomplete

Purpose​

Every field in your environment carries its own search settings: whether the field's text is matched by search, whether the field can become a filter ("facet") control, and whether its values feed suggest-as-you-type. The settings live on each field's configuration record, are filled automatically when the field is created, and are exactly the configuration the Entry Surface readiness review reads. Read this page when a field matches (or fails to match) in search unexpectedly, when you are deciding which fields should become public filter controls, or when preparing your environment for a public launch.

Features​

  • Per-field search settings — each field carries three eligibility settings: searchable (text matching), filter ("facet") eligibility, and autocomplete eligibility. Maturity: Active. Limit: the admin screens do not currently include a control for editing a stored value — changing one is done with your platform operator.
  • Automatic defaults from the field's type — when a field is created during an import, the platform fills the three settings from a fixed per-type table, the same for every environment. The platform never infers them from the content of your data. Maturity: Active. Limit: the automatic value fills a blank only; an explicitly chosen value is never overwritten, including by re-imports.
  • Searchable fields define the search index — when a record is written to your environment's search index, only its searchable-marked fields contribute text. The search your team uses inside the environment reads this index. Maturity: Active. Limit: fields created before automatic defaults existed fall back to built-in platform rules until explicit values are stored for them.
  • Filter ("facet") eligibility — a facet-eligible field can produce filter buckets, and the readiness review lists it as a reviewed filter field. Maturity: Active. Limit: a public filter control additionally requires a simple single-value field, your review, and promotion into the public configuration — eligibility alone does not create a public control.
  • Autocomplete eligibility — an autocomplete-eligible field feeds suggest-as-you-type. Maturity: Active. Limit: a public suggestion source has the same additional requirements as a public filter: a simple single-value field and review.
  • Search boost (reserved) — a field's configuration can record a weighting value for ranking its matches. Maturity: Built. Limit: the value is stored and preserved as yours, but no search engine consults it — it has no effect on results today. Leave it unset.

Usability — how you use it​

Where the settings live, and what fills them​

The settings sit on the field's configuration record, next to its label, type, and ordering. You do not set them by hand at creation time: the moment a field is created, the platform writes all three eligibility values from the field's type.

Field typeSearchableFilter-eligibleSuggestions
Short textYesNoYes
Long-form (rich) textYesNoNo
Single-choice listYesYesYes
Multiple-choice listYesYesNo
Link to another recordYesYesNo
Looked-up valueYesNoNo
Number, date, yes/noNoNoNo
MediaNoNoNo

Three rows deserve a note. A link field is matched through the linked record's display text, which is why it is searchable even though it stores no text of its own. Number, date, and yes/no fields start with everything off — an opt-in you record explicitly is preserved and never reverted by the platform. A media field itself carries no searchable text; the descriptive fields on a media record (title, creator, and so on) are ordinary text and choice fields and follow their own rows in this table.

Changing a setting — what is self-serve and what runs through your operator​

You can do yourself: read each field's stored eligibility values and sampled evidence in the Entry Surface readiness report, and record review decisions there — including deferring a filter or suggestion candidate with a reason. A recorded deferral is read by the public surface: the deferred control is reported unavailable, with a reason citing your review.

Performed with your platform operator: editing a stored searchable, filter, or autocomplete value on a field (the admin screens have no control for this today); refreshing the search index after a change so existing records reflect it; promoting reviewed fields into the public Entry configuration; and enabling your environment's search engine in the first place.

Whichever path sets a value, the same protection applies: an explicit value is yours. Re-importing your source data fills blanks with automatic defaults but never overwrites a value that was chosen deliberately.

Hiding a field from search​

Hiding works the same way in reverse. A field whose searchable setting is off contributes no text to the search index, so its values stop matching once the index is refreshed. A field explicitly marked not filter-eligible also leaves the readiness review's candidate list — the review stops proposing it.

How the settings feed the readiness review​

The readiness report classifies every field of the public role's record type by its stored settings:

  • A field marked filter-eligible appears as a reviewed filter field — listed with the reviewed single-value filter fields when its values are simple single values, or flagged separately when its shape is complex (multi-value, linked, looked-up, media).
  • A field marked autocomplete-eligible with simple single values appears as a reviewed autocomplete field.
  • A simple single-value field with no explicit eligibility appears as a candidate, with the review actions the panel offers (review before promotion, choose a shorter label, defer with reason).

Each row carries evidence sampled from your records: how many records carry a value, how many distinct values exist, and warnings where values are too long for a compact public control. The report is the place to confirm a setting change landed — see Entry Surface Readiness for the panel itself.

What researchers and public readers see​

Inside your environment, the workspace search matches against the search index, so only searchable-marked fields produce hits. If your environment's search engine has not yet been enabled, a search request is refused with a plain message that search is not enabled for the workspace yet — enablement is an operator step.

On the public Entry surface, a filter or suggestion control reaches readers only when the field is explicitly eligible, holds simple single values, has passed your review, and was promoted into the public configuration. A control that does not meet all of these is reported with an unavailable status and a short reason, one of four kinds:

  • the field is not part of that public role's configuration;
  • the control was deferred by a review decision you recorded;
  • the field has not yet been reviewed and promoted;
  • the field's value shape (multi-value, linked, looked-up, or media) has no public control of this kind.

An automatic default alone never creates a public control: a field the platform seeded but nobody reviewed stays review evidence, not a public promise.

Verifying a change after saving​

  1. Open the Entry Surface readiness panel and refresh the report.
  2. Find the field's row and confirm its stored eligibility values and classification moved as expected — into the reviewed lists, into the candidates, or out of the candidates entirely.
  3. For a searchable change, ask your operator to confirm the index refresh ran, then search for a value that occurs only in that field and confirm it now matches (or no longer matches).
