Citation Style Administration

Purpose​

This page is the operating reference for the citation-style service behind the three-step style workflow. It names the administrative endpoints that drive that workflow, explains what the detail view tells you, and explains the pinned test corpus and the blast-radius measurement that decides how risky a proposed style change is. Read it when you are about to refine a citation style and want to know exactly what each step does, what numbers the platform reports back, and why a proposal lands in one risk class rather than another.

This is the companion to Standards and Citations, which describes the citation framework and the propose → scholar review → apply workflow as a working procedure. That page is where to start; this one goes deeper into the service the workflow runs through. It does not replace it — the workflow narrative lives there and is not repeated here.

A dedicated configuration screen for citation styles is not yet available. Today the service is operated through the platform's administrative citation endpoints, one set per entry type. Each endpoint requires the environment administrator role. The steps below are administrator-operated, but because there is no UI yet, your platform operator will typically run them with you the first few times.

Features​

The service exposes a small set of administrative endpoints, each scoped to one entry type. The two read paths report state; the write paths drive the workflow and the test corpus.

Reading the active style and pending work​

  • Style detail — the read view for one entry type. It reports the entry type's active style (its identifier, version, when it was applied, and by whom), the number of active citation test cases pinned for that entry type, and how many style proposals are currently pending review. Call this first: it tells you what is live, how much test coverage exists, and whether anyone has a refinement waiting · Maturity: Built.
  • Catalog browse — lists the citation styles that ship with the platform, so you can adopt one directly instead of refining. A catalog of more than seventy standard styles ships with the platform · Maturity: Built.

The three workflow endpoints​

These three carry the propose → scholar review → apply path. The full procedure, including who does each step and why no single person can silently change every citation, is in Standards and Citations.

  • Propose — you submit a list of sample citations you want the rendered output to match. The platform generates a proposed style, measures it against the entry type's pinned test corpus, and returns a risk class, a blast-radius percentage, the specific test cases that would change, and a plain-language explanation of what the proposal does. The proposal is recorded as pending; nothing is applied · Maturity: Built.
  • Scholar approval — a scholar reviews the pending proposal, its differences from the active style, and its risk class, then approves it. Approval only moves the proposal forward; it does not change any published citation · Maturity: Built.
  • Apply — once a proposal is scholar-approved, an administrator applies it. The approved style is stored in your environment as the new active style, recorded with the applying administrator and a version stamp. From then on, citations render against the new active style; existing published pages pick it up the next time they are rebuilt. A proposal cannot be applied unless it has been scholar-approved first; applying without that step is refused · Maturity: Built.

Adopting a catalog style directly (through the catalog browse endpoint) skips the propose-and-review path: the chosen style is stored as the active style straight away, stamped with a checksum of the style file and the administrator who selected it. Use the review path when you are refining how citations read for your own material; use direct adoption when an off-the-shelf venue or institution style already fits.

Pinned citation test cases​

The risk numbers a proposal reports are only as meaningful as the test corpus they are measured against. A pinned citation test case is one published citation, frozen as the expected rendered text plus the structured citation data behind it, kept as a regression check for one entry type.

  • What pinning does — the platform reads citations off your already-published entries and records each one as an expected result. After pinning, any future style proposal is rendered against these frozen citations; if the proposal would change one of them, that change is counted as a regression · Maturity: Built.
  • How pinning is scoped — pinning draws only from published entries for the entry type. You can pin a single citation (by naming the published entry and the citation's position on it) or let the platform sweep your published entries and pin a representative sample automatically. The automatic sweep is deliberately bounded so the corpus stays a representative regression check rather than an exhaustive copy: it pins at most three citations of any one structural shape and at most forty in total, and it skips citations that are not well-formed enough to pin reliably. The response reports how many candidates it saw, how many it skipped, the shape breakdown, and every case it pinned · Maturity: Built.
  • Turning a case on or off — a pinned case can be deactivated and reactivated. Only active cases count toward the blast-radius measurement, so deactivating a case removes it from the regression baseline without deleting it · Maturity: Built.

Blast radius and risk classes​

When you propose a style, the platform renders it against every active pinned test case for that entry type and counts how many would change. From that it computes two things:

  • Blast-radius percentage — the share of pinned test cases the proposal would change. It is the count of changed cases divided by the total active cases, as a percentage. With no pinned cases the blast radius is zero, which is why the test corpus matters: a proposal measured against an empty corpus carries no evidence about its real reach.
  • Risk class — a plain label derived from the blast-radius percentage, used to route the proposal:
    • Low — at or below five percent of pinned cases change. A small, contained refinement.
    • Medium — between five and twenty-five percent change. The scholar reviews the differences before approving.
    • High — more than twenty-five percent change. A wide-reaching change that warrants careful second-eyes review; nothing is applied automatically.

The proposal also returns the specific test cases that would change — each with its expected text and what the proposed style would render instead — so a reviewer is looking at concrete before-and-after citations, not just a number.

Usability — how you use it​

The typical sequence, all operated through the administrative citation endpoints for one entry type:

  1. Check the current state — read the style detail to see the active style, how many test cases are pinned, and whether a proposal is already pending.
  2. Build a baseline, if you have not — pin citations from your published entries so a proposal can be measured against real output. Without pinned cases, every proposal reports a zero blast radius and tells you nothing about its reach.
  3. Propose a refinement — submit the sample citations you want the output to match. Read the returned risk class, blast-radius percentage, and the list of cases that would change.
  4. Have a scholar review and approve — the scholar weighs the differences and the risk class.
  5. Apply — once approved, an administrator applies the style; it becomes the active style, and citations render against it from then on.

If an off-the-shelf style already fits, skip steps 3 to 5 and adopt a catalog style directly through the catalog browse path.

Which actions are administrator-self-serve and which involve your platform operator:

  • Self-serve (environment administrator role): every endpoint here is gated to the environment administrator role. From a permissions standpoint, reading the detail, browsing the catalog, pinning and unpinning test cases, proposing, recording scholar approval, and applying are all administrator-operated.
  • Operator-mediated in practice: because there is no dedicated screen yet, these endpoints are usually run by your platform operator alongside you — especially the first time. Installing a citation style that is not in the shipped catalog is also an operator task: provide the style file or a published style URL.
