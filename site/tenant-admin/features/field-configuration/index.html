Field configuration: kinds, scopes, resolvers, and language behavior

Purpose​

Every field in every table of your environment is described by one field definition: what kind of value the field holds, what it is called, where its data is read from, who can see it on published pages, how a connecting field finds the record it points to (its resolution rule — internally, a "resolver"), and how searches treat its script and accents. This page is the reference for those definitions. Read it when adding a field, choosing between a link and a lookup, restricting a field from published pages, or tuning accent behavior for a multilingual corpus.

A field definition is configuration, not code. Renaming a field, reordering the field list, or restricting a field's visibility is an edit you make in the workspace, and it takes effect without platform changes.

Features​

What one field definition controls​

A single definition drives the same field everywhere it appears · Maturity: Active.

  • In the workspace — the definition is the column and the form field. Adding a definition adds a column to the table grid and a field to the editing form. The displayed name, the field description (the tooltip researchers see), and the field's position in the list all come from the definition.
  • In editing — the field kind decides which editor control researchers get, and fields marked required gate the completion of a new row. Date fields use native date inputs in workspace editing surfaces and date-aware filtering in the table.
  • In search matching — the definition's language settings (script, accent folding, language, multilingual) shape how searches match the field's values. Whether the field is searched, faceted, or suggested at all is a separate set of controls — see Making fields searchable.
  • On published pages — the field's visibility level decides whether it appears on published pages; its display name and position carry over when it does.

The ten field kinds​

Every field has exactly one kind · Maturity: Active.

KindHolds
Plain textA text value
Rich textFormatted text with a full text editor
NumberA numeric value, displayed per its numeric format
DateA calendar date, edited with a native date input and filtered by calendar date
BooleanYes / no
Select (single)One value from the field's option list
Select (multi)Several values from the field's option list
RelationA live link to one or more records in another table
LookupA read-only value pulled through a link field
MediaA reference to a media item

The kind decides which detail settings apply (formats, roles, options — see below). Definitions are validated when saved: settings that do not fit the field's kind are rejected with a validation message rather than silently ignored.

Changing a text-shaped timestamp column to Date does not bulk-convert every stored value. Existing text values remain raw until an explicit conversion or cleanup flow handles them. This avoids silently corrupting scholarly date forms that look parseable but carry project-specific meaning.

Where a field's data comes from​

  • Source path — each ordinary field names the place its values are read from in your environment's record store (a path such as data.title). Fields added in the workspace default to a path derived from the field key. The source path belongs to your source: every re-import refreshes it, so a hand-edit to the path does not survive the next re-import. Maturity: Active.
  • Field key and label — the field key is the field's stable identity. It survives source renames and label changes; renaming a field's displayed name never touches the key. Labels for imported fields default to your source's own column names, verbatim — your renames are then preserved. Maturity: Active.
  • Imported or workspace-added — fields arrive through import or are added directly in the workspace. Field keys beginning with x_ mark a field as an environment extension. The table's Details view badges each field: capability badges (multilingual, linkable, script, lookup, rich text) and a scope badge distinguishing environment-wide fields, extension fields, and personal note fields. Maturity: Active.
  • What a re-import can and cannot change — every setting on a definition falls into one of three behaviors · Maturity: Active:
    • Refreshed from source — source path, storage layer (which internal store holds the field's values), and connection rules. The source is the truth; re-imports overwrite these.
    • Filled once if empty — field kind, script, language, multilingual, position, and choice options. Detection and import fill blanks; they never overwrite a value that is already set.
    • Yours after creation — display name, field description, required, accent folding, formats and roles, formula templates, link and lookup configuration, and standards declarations. No automatic process overwrites these; they survive every re-import.

Connection rules​

When a field points at records in another table, its definition records how the connection is resolved — the rule the platform follows, each time a record is read, to turn the stored value into the connected record · Maturity: Active.

  • Direct — no connection; the value is read as-is. The default for ordinary fields.
  • Foreign-key walk — follows a true foreign-key relationship carried over from your source database.
  • String match — for a soft foreign key: no declared relationship exists in the source, but a value in this field equals a value in a named column of the target table. The rule names the two columns.
  • Composed — multi-step or computed matching, performed by a named function from the platform's function library with parameters — for example, matching the part of a value before a comma against a bibliography table.

Choosing one for a soft foreign key: when two tables relate only by matching values, the rule is string match. When the match needs computation first — splitting, prefixes, normalization — it is a composed rule.

Connection rules are established during import analysis. The analyzer detects candidate connections from your data's structure and from value overlap between tables; an AI assistant proposes a rule only where the analysis is uncertain; a person approves before anything is written. From then on the rule runs identically on every read — no AI is involved when records are read. Re-imports refresh these rules from the source's structure; correcting one by hand outside an import is operator-mediated.

Per-field visibility on published pages​

Each field carries one of three visibility levels · Maturity: Active.

  • Public — the field appears on published pages. This is the default for every field, so published pages are unchanged until you restrict something.
  • Workspace — the field stays inside your environment's workspace and never reaches published pages.
  • Private — the field is visible to its owner only.

You set visibility per field on the workspace Publish view, with a three-way control next to each field. The choice saves per field as you set it; publishing changes then rebuilds every entry in the table, applying the current visibility. Because the filter is applied when entries are built for publication, a newly restricted field disappears from already-published pages when those entries are next published. The researcher-tier walkthrough is The Publish view.

Language behavior​

Per-field language settings control how searches match the field's text · Maturity: Active.

  • Script — the field's dominant writing system (for example latin, greek, arabic), detected automatically from content. Empty until detection has run; you can override it per field.
  • Accent folding — on by default: searches match the field accent-insensitively, on both the stored text and what is typed. Turn it off for fields where a diacritic is part of the letter's identity — Scandinavian å versus a, Vietnamese tone marks, Turkish dotted and dotless i, or a critical edition whose polytonic accents distinguish words. Applies to text fields, plain and rich. Once you set it, the choice is yours; no automatic process overwrites it.
  • Language — the field's language code (for example el, grc, ar), detected automatically. You can override it; while it is empty, the script setting stands in for language-based defaults.

A field that holds several values​

A text field can be set to hold more than one value per record — one for each language, register, script, edition, or calendar (or a custom kind of your own) · Maturity: Built. All the values land in one searchable entry, so a search matches the record no matter which value carries the match.

Two parts of the field definition govern this, and they are independent:

 Field definition (the schema window)
 ├─ This column's language & script   ← ONE language + script for the whole column
 │     Language code:  [ grc      ]      (a single-value modifier on the column)
 │     Script:         [ greek    ]
 │
 └─ Multiple values                   ← the column keeps a SEPARATE value per entry
       [✓] This column holds more than one value
       A separate value for each:  [ Language ▾ ]   (Language / Register / Script /
                                                      Edition / Calendar / Custom)
       Allowed languages:
          [ GK ✕ ] [ LA ✕ ] [ AR ✕ ]      ← chips: the allowed values
          Add a language: [________] (Add) ← type a new one; normalized to a chip

There is one control for this. When you turn on This column holds more than one value, two settings appear:

  • A separate value for each — what the values are distinguished by: Language, Register, Script, Edition, Calendar, or Custom. This choice drives the wording of the next setting and of the per-record editor (Allowed registers, + Add register, and so on).
  • Allowed languages (the label follows the choice above) — the set of values the field accepts, shown as chips. This is a controlled, extensible picker, not a free-text list: type a value and it is added as a chip; the × on a chip removes it.
    • Drift normalization — a typed value is normalized to a canonical short form before it joins the set, so variant spellings of the same value fold together: typing greek yields a GK chip, and GREEK and GK collapse to one entry rather than splitting the data across two headings. Researchers entering per-record values pick from this same normalized set, with a + new affordance for a value the set does not yet offer.

Researchers fill the per-record values in the table cell or the record's form — see the researcher walkthrough Working in multiple scripts and languages. Right-to-left values (Arabic, Hebrew, Persian, Urdu, Aramaic) render right-aligned in those editors.

The researcher-facing wording avoids platform terms: the editor reads "Multiple values", "A separate value for each", and "Allowed languages", never "multikey", "key", or "kind". The kind labels (Language, Register, …) are the only domain terms shown.

Formats, roles, and the link / lookup / formula distinction​

Detail settings per kind · Maturity: Active:

  • Number fields take a numeric format — integer, decimal, year, currency, percent, or duration — plus an optional decimal precision. The currency format requires an ISO currency code.
  • Plain-text fields take a role: plain, URL, email, phone, or embed.
  • Choice fields (single and multi select) carry their option list.
  • Media fields declare which media kinds they accept: image, audio, video, file, or embed.
  • Relation fields declare whether they hold one connection or many.

Three field shapes derive their value rather than storing it directly:

  • A link field (relation) holds live connections to records in other tables. The connections are stored as relationship records, not inside the record's own data. Its definition names which tables it may point to and which field of the connected record is shown as the link's display value.
  • A lookup shows a value from the record on the other end of an existing link field. It is read-only: its definition names the link field it follows and which field on the connected record to show; nested paths and lists are supported. A lookup must always name its target field, and a field is either a link or a lookup, never both — both rules are enforced when the definition is saved.
  • A formula field computes its value each time the record is read, from a template combining other fields of the same record. Empty components are dropped by default, so a missing part leaves no stray separators. Computed values are never stored, and a formula field cannot also be a link or a lookup.

Lookup and formula columns are read-only in the grid. To change what they show, edit the fields or linked records they derive from.

Usability — how you use it​

Field definitions are edited in the workspace; the edits require the administrator role in your environment.

  • Add a field: use the add-column control at the end of the table grid, or the table Details view's add-field action. The dialog asks for the field key (required, the stable identity), the kind, and the kind's detail settings.
  • Edit a field: open the column header menu on the field's column, or use the Details view's edit action. Changing the kind of a column that already holds data is a deliberate act — review the field's values first.
  • Delete a field: from the same column header menu. Deleting removes the definition — the column and the form field — but not the stored values underneath. Re-adding a field with the same field key brings the values back.
  • Set per-field visibility: open the Publish view, set each field's level (Public / Workspace / Private), then publish changes to rebuild the table's entries with the current visibility.
  • Declare standards: a field definition can declare which standards its content conforms to, chosen from the platform's approved list — see Standards and Citations.

Which edits are self-serve, and which go through your operator​

Admin-self-serve, in the workspace:

  • Adding, editing, and deleting field definitions — kind, key, display name, field description, position, source path, language behavior, formats and roles, choice options, links, lookups, formulas, and standards declarations.
  • Per-field visibility on the Publish view.

Operator-mediated — contact your platform operator:

  • Marking a field required or optional. There is no workspace control for this today.
  • Correcting a connection rule by hand outside an import.
  • Changing a field's storage layer.

Troubleshooting​

SymptomLikely causeFix
You edited a field's source path and a re-import reverted itThe source path is refreshed from source on every re-import — the source is the truth for itMake the change in your source data or the import mapping; workspace edits to the source path do not survive re-import.
A lookup or formula column cannot be edited row by rowLookup and formula values are derived, not storedEdit the linked record (for a lookup) or the fields the formula combines.
You set a field to Workspace or Private, but it still shows on a published pageVisibility is applied when entries are rebuilt for publicationOpen the Publish view and publish changes for the table; the rebuild applies the current visibility.
You deleted a field and need its data backDeleting removes the definition only — the stored values remain in the record storeRe-add a field with the same field key; the default source path matches and the values reappear.
Searches ignore accent distinctions that matter in your materialAccent folding is on by defaultTurn accent folding off for that field; its diacritics then count as letter identity in matching.
A definition will not saveA detail setting does not fit the field's kind — for example the currency format without a currency code, or a lookup without a target fieldRead the validation message; it names the setting to fix.
