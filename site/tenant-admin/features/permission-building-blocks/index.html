Permission building blocks: the named set

Purpose​

The standard roles in your environment — and any custom role you compose — are built from one fixed set of permission building blocks. There are nine. Each block is a single capability: it is either granted or not. A role is a chosen combination of these blocks.

This page names every block, says exactly what each one lets a contributor do, gives the default combination a new contributor starts from, and shows how the blocks combine into a reviewer, a supervisor, and an exporter. Read it when you are composing a custom role on the Permissions Panel and want to know precisely what each checkbox controls.

The building blocks are fixed by the platform: you combine them, you cannot invent new ones. Composing roles and assigning them is yours to do as an administrator. Adding the contributor accounts those roles attach to is handled by your platform operator — see Onboarding a collaborator.

The nine building blocks​

Each block below lists its name, what it gates, and its impact tier — low, medium, or high. The impact tier tells you how cautious to be when granting it; the three high-impact blocks are called out again in the next section.

Review suggestions​

Gates: reading and commenting on suggested changes before they are saved. A contributor with only this block can examine every proposed change and leave comments, but cannot save anything. Impact tier: medium.

Save additive changes​

Gates: saving additive changes — new records or new fields — that do not alter existing work. This is the lowest-impact save permission. Impact tier: low.

Save normal changes​

Gates: saving edits that change existing records. These are the everyday changes a working contributor makes, and they remain reviewable. Impact tier: medium.

Run high-impact changes​

Gates: running broad merges, deletes, and reorganizations — the changes that touch the most records at once. Impact tier: high.

Use the undo window​

Gates: reversing a just-saved change while the short undo window is still open. Without this block, a contributor can save but cannot self-reverse. Impact tier: low.

Manage import templates​

Gates: creating and updating the saved import setups the project reuses. Impact tier: medium.

Change field setup​

Gates: changing the fields contributors use when they edit — which fields exist and how they behave. This reshapes the editing surface for everyone, which is why it sits in the high tier. Impact tier: high. See Field Configuration for what this controls.

Manage roles​

Gates: inviting contributors into roles and deciding what each person can do — in other words, composing roles and assigning the other eight blocks. A contributor needs this block to open the role-management surfaces at all. Impact tier: high.

Export suggestion metrics​

Gates: downloading aggregate metrics about suggestion quality and review patterns. The numbers are aggregate, never individual review text. Impact tier: medium.

Defaults for new contributors​

When a contributor account first appears in your environment, it starts from a fixed default combination — the set the platform treats as a safe working baseline for a project team member. The five blocks below are on by default; the other four are off.

Building blockDefault
Review suggestionsOn
Save additive changesOn
Save normal changesOn
Use the undo windowOn
Manage import templatesOn
Run high-impact changesOff
Change field setupOff
Manage rolesOff
Export suggestion metricsOff

The default is a starting point, not a fixed role: from the Permissions Panel you assign a standard role or compose a custom one over it. The three high-impact blocks — run high-impact changes, change field setup, and manage roles — are off by default, and so is exporting metrics.

The high-impact blocks and the project rules​

Three blocks are high-impact: run high-impact changes, change field setup, and manage roles. Granting one of these gives a contributor a capability that can affect a large share of the project's work, or affect what other contributors can do.

These blocks decide who is allowed to make a high-impact change. They are separate from your environment's project rules, which decide how such a change is confirmed when it happens. The two work together: a block grants the capability; a project rule can require a second pair of hands before the change goes through. For example, your environment can require that a high-impact save is confirmed by a contributor who did not author it, and can require that destructive changes are confirmed either by two contributors or by a single contributor through an elevated confirmation step.

So even a contributor who holds run high-impact changes is still subject to the project rules at the moment they apply a change. Granting the block does not bypass the rules; it only makes the contributor eligible to start the change. You set these rules on the Project rules tab — see the project rules described in the Permissions Panel.

Manage roles is the one block that controls access to permission management itself. A contributor cannot open the role-management surfaces, or change anyone's permissions, without it.

Composition examples by capability shape​

These three shapes show how the blocks combine. They are illustrations, not extra preset roles — compose the equivalent as a custom role, or start from the matching standard role and adjust.

A reviewer — someone who reads and comments but never saves. One block:

  • Review suggestions

Everything else is off. This shape can examine and annotate proposed changes and nothing more.

A supervisor — a senior contributor who does the full editing job and can reorganize, but does not manage people or reshape the field setup. The save and undo blocks plus high-impact changes:

  • Review suggestions
  • Save additive changes
  • Save normal changes
  • Run high-impact changes
  • Use the undo window
  • Manage import templates

Change field setup, manage roles, and export metrics stay off. This contributor can do every kind of save — including high-impact reorganizations — but reshaping the editing surface and managing other people's access remain with an administrator.

An exporter — someone whose job is to pull aggregate metrics, with read access to the review stream but no save authority. Two blocks:

  • Review suggestions
  • Export suggestion metrics

All save and management blocks stay off. This shape can read suggestions and download the aggregate quality and review-pattern metrics, without the ability to save changes or alter anyone's access.

Who does what​

ActionWho
Compose a custom role from the building blocksAdministrator (self-serve, on the Permissions Panel)
Assign a standard or custom role to a contributorAdministrator (self-serve)
Adjust a single contributor's blocksAdministrator (self-serve)
Add a new contributor account for a role to attach toPlatform operator
Add new building blocks beyond the nineNot available — the set is fixed by the platform
