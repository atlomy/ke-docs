Workspace configuration: tables, labels, and shared views

Purpose​

This page is the reference for the collection settings that shape what researchers see in the workspace: the name, icon and order behind every sidebar entry; the field that names each record; the default field set; and the identity that keeps one collection distinct from its siblings. Administrators manage these settings on the workspace's Tables & visibility page. This reference also explains the related ontology entries and environment-wide saved views. Read it after an import has landed a new collection, when labels or ordering look wrong, or when curating the defaults your whole team shares.

What you change yourself, and what the platform maintains​

  • Admin-self-serve. Renaming a collection, changing its icon, hiding it from the workspace, reordering the sidebar, choosing its row-title field, and choosing its default fields are all available from Tables & visibility. Saved views remain curated in the workspace itself. Re-importing source data never reverts a collection's label, icon, or order once you have edited them.
  • Import-maintained. Workspace table records and ontology entries are created automatically when imported data is applied — you do not create them by hand for imported sources. The import also maintains a read-only record of which display column the source itself declared, and refreshes the ontology entries (including the anchor) each time an import is applied.
  • Operator-mediated. Environments configured from a declaration file rather than through the import wizard receive their initial tables, labels, and anchor from a seeding run performed by your platform operator. Re-running that seeding converges on the declared file — if you change those values by hand, tell your operator so the declaration is updated to match.

Features​

  • Workspace collection records — one record per collection in the researcher workspace. Each record carries the collection's label, an icon name from the Material icon set, an active flag, and a sidebar position (lower numbers appear first). Switching Shown in workspace off hides the collection from the workspace without deleting anything or changing its public publication state. Maturity: Active. Limit: unregistering a collection deletes its saved views with it — hide rather than remove unless you mean to discard those views too.
  • Record labels from the display field — the display field is the data column shown as each record's name in Details, Relations, Publish, search results, linked-record chips, and an Edition-kind keyed column's key picker (which offers each linked edition record labelled by its own collection's display field). It is written as a data path to one of the table's columns, in the form data.<column name>. It is set from the source's declared display column at import and refreshed on re-import only while you have not edited it — your edit always wins. A second, read-only field records what the source declared at the most recent import, so the platform can tell your edit apart from an import-written value. When the display field is blank or a row has no value there, records show a visible unnamed placeholder rather than a generic record type or a guessed column; in the edition key picker specifically, that same blank-value case falls back to the collection's own generic name instead (so several such rows can appear to share one key) — the platform never borrows a different column to fill the gap. Maturity: Active.
  • Default visible columns — an optional list of field names that render as the table's columns by default; leaving it empty shows all fields. This is the environment's default for the table; researchers' own column arrangements and saved views sit on top of it. A re-import can add newly declared source fields to an explicit default list, but it does not remove the administrator's existing selections. Maturity: Active. Limit: the underlying field definitions can still be shared across a concept family, so two source tables that share one concept family may expose a broader shared field set until their views hide irrelevant columns.
  • Table scoping — each table shows the records of one concept family (the configuration forms call this an archetype), optionally narrowed to a single record type and a single source table. Two source tables that share a record type stay two distinct tables rather than merging. When a source renames a table while keeping its stable identity, the platform reuses the existing record so saved views survive, leaves your label untouched, and adds a warning suggesting you review it. Maturity: Active. Limit: table records are scoped per source table, but field-definition scoping is not yet as narrow as table identity in every import shape; curate the default view after large cold imports.
  • Advanced filter setting — a reserved setting on each table record for filtering a table beyond its record type. The workspace does not yet apply it to the rows researchers see; the import writes its own source-table scope into it, and that is the only shape in use. Maturity: Deferred. Limit: entering a custom value today makes the table's scope ambiguous, which switches off in-table record creation, relation editing, and table publishing for that table — leave it as the import wrote it.
  • Ontology entries and collection relationships — each ontology entry pairs a platform concept family with the label your environment uses for it, an optional record type that narrows it, and an anchor flag. The anchor marks the concept family your environment is organized around; the platform allows at most one. The same read-only page lists the collection-to-collection relationships available in the environment's schema view and opens the full Schema Visualizer when you need a map. Maturity: Active. Limit: ontology entries are import-maintained — applying an import refreshes the labels and recomputes the anchor from the approved import decisions, so treat this list as something you read and verify; raise a lasting change with your platform operator.
  • Environment-wide saved views — named views attached to a table, each storing filter conditions, sort order, column arrangement (order, visibility, pinning, sizing), row density (compact, cozy, or comfortable), and row color rules, plus the view mode it opens: Table, Details, Relations, or Publish. A view can be pinned to the primary tab row, and one view per table can be the default. Every saved view is shared with everyone working in the environment. Maturity: Active. Limit: the database allows at most one default view per table.

Usability — how you use it​

Open the workspace account menu and choose Workspace settings → Tables & visibility. The page shows one card for each registered collection, with its record count and a direct Open in workspace link. Create collection opens the workspace's existing creation flow, and Bring in data opens the import wizard; the page does not create a second lifecycle path. A data-derived collection that has not been registered stays read-only here and points you back to the workspace to register it first.

  • Rename a collection, change its icon, or reorder the sidebar. Edit Collection label, Icon, or Default order, then choose Save name and order. Researchers see the saved label and order in their workspace sidebar. A later re-import does not undo these edits.
  • Hide a collection without deleting it. Switch Shown in workspace off and save the collection settings. The collection, its records, configuration, and saved views remain, and it returns intact when you switch the setting back on. This switch does not publish or unpublish anything.
  • Set which field names each record. Choose Row title field and save. The choice is shared by Details, Relations, Publish, search results, and linked-record chips. Source-declared label field shows what the latest import declared and is read-only; it remains visible as provenance rather than becoming another editable label. Clearing the row-title choice makes records show a placeholder instead of a name. Use in this view is different: it changes only a saved view's identifying column.
  • Choose the default workspace fields. Select Show all configured fields, or Choose workspace fields and tick at least one field, then save. Researchers can still arrange their own columns, and saved views carry their own column arrangement. When a later import declares new source fields, the platform can add them to this default set without removing your existing choices.
  • Curate first views after import. After a cold import with several source tables under one concept family, open each workspace table before researchers begin using it. If a table shows fields that belong to a neighboring source table, hide those fields in the default saved view and keep the table label source-specific so researchers can tell the tables apart.
  • Review identity and filtering cautiously. Advanced identity and filter exposes the collection's canonical structure, canonical type, source table, and advanced filter. These values determine which records belong to the collection. Changing canonical structure resets the row-title field and default workspace fields because the old field names belong to the previous structure; choose the new presentation fields before saving if the defaults are not suitable. A save is refused while a public view or relationship depends on the identity being changed; do not treat that refusal as a reason to recreate the collection.
  • Read the ontology and relationship map. Choose Schema & definitions → Relationships & ontology from the workspace account menu. The page shows each concept family's label, its optional record type, and whether it is the anchor or a supporting concept. Below it, the collection-relationships list names the source collection, relationship, and target collection; choose Open schema visualizer for the full interactive map. This page has no create, rename, retire, or delete controls. Verify it after an import; a label that needs to change durably should go through your import decisions or your platform operator, because the next import apply refreshes this list.
  • Curate saved views. Saved views and the views researchers create in the workspace are the same records — there is no separate admin-only kind, and every view is visible to the whole environment. Shape a view in the workspace itself, where its filters, sort, column arrangement, color rules, density, pinning, and default status are stored as you work.
  • Set the default view. Mark one view per table as the default; it is what the table opens with, for everyone. The database enforces at most one default per table, so clear the current default before assigning a new one.

Troubleshooting​

SymptomLikely causeFix
An import created two similar-looking tablesTwo source tables share one record type; each source table becomes its own workspace table by designRename the labels so researchers can tell them apart, or hide the one not in use.
A table shows columns from a related source tableThe table record is scoped per source table, but the field definitions can still be shared at the concept-family levelHide the irrelevant columns in the table's default saved view. Escalate if the field set itself must be separated by source table.
Records show a placeholder instead of a nameThe table's display field is blank — the source declared no display column — or it points at a column many records leave emptySet the display field to a data.<column name> path for a column every record fills.
A re-import did not pick up the source's new display columnYou edited the display field, and your edit always wins over the importCompare with the read-only companion field showing what the source declared, and copy that value in if you want the source's choice.
Creating records or editing relations is unavailable in one table, or the table cannot be publishedThe table record carries a custom advanced-filter value, which makes its scope ambiguousRemove the custom additions from the advanced filter, keeping only what the import wrote.
Marking a second view as the default failsA table can have at most one default view; the database enforces itClear the default flag on the current default and save, then mark the new view.
Saved views disappeared after a table was removedDeleting a table record deletes its saved views with itRestore from your environment's backup if available. Going forward, hide tables with the active flag instead of deleting them.
Your ontology label edits were revertedApplying an import refreshes ontology entries, including labels and the anchorMake the label change part of your import decisions, or ask your platform operator to update the environment's declaration.
