Data Import Wizard

Audience: Tenant administrator with admin role on an environment's schema. Last aligned with platform state: 2026-06-10 Platform version: V2 (pre-1.0)

Purpose​

The Data Import Wizard is how source data lands in your environment without bypassing review. It parses an uploaded source (xlsx workbook, MySQL dump or live connection, CSV bundle, Coda document), generates parser-first / LLM-second proposals, routes them through a two-step approval flow, and materialises approved configuration plus retained rows. Read this when bringing in a new corpus, when revising the mapping for a known source shape, or when a researcher reports that an import did the wrong thing.

The wizard is the curated onboarding path; the older CLI importers remain available as an engineer-grade override for diagnostic and repair work. Direct database tools (Directus) are not the wizard.

Features​

Ordered roughly by what an operator touches first.

  • Mapping Projects entry surface — Unfold SIDEBAR → Imports & AI → Mapping Projects. Lands you at /admin/data_import/mappingproject/. Substrate: Spec 0011 + ADR-018 (retired NoCoDB / Data Wizard) · Maturity: Active · Limit: the stock Django "Add MappingProject" form does not parse a source; use the upload buttons.
  • Upload data — Import Wizard (xlsx) — top-right object-tools button on the changelist; project name + description + file picker; sync request cap 5 MB. Oversize sync requests return HTTP 413 before Django parses the body; larger uploads go through the background route (cap 100 MB). Substrate: Spec 0011 Task F0a · Maturity: Active · Limit: sync request boundary; larger files queue async.
  • Upload MySQL data — Import Wizard — two source modes: dump file (sync cap 50 MB; async cap 500 MB) or live DSN (mysql://host:port/dbname + optional credentials, session-only). Substrate: Spec 0011 Task F0b-ii · Maturity: Active · Limit: live DSN credentials never persisted; stripped from durable logging. Saved MySQL live connections via ExternalServiceCredential reference resolved server-side.
  • Upload CSV bundle — Import Wizard — multi-file form; each filename (without .csv) becomes a table name; per-file cap 10 MB; sync bundle cap 30 MB; async cap 50 MB per file / 250 MB total. Substrate: Spec 0011 Task F0b-iv · Maturity: Active · Limit: parser detects soft-FK relations by value-overlap across files (confidence capped lower than xlsx).
  • Upload Coda document — Import Wizard — project name + Coda document name + session-only API key + optional table subset. Substrate: Spec 0011 Task F0b-iii · Maturity: Active · Limit: API key is used once and never persisted; existing committed Coda configs appear only as comparison-oracle evidence.
  • Async worker ledger — ImportWizardJob stores tenant-local job state for staged-file and credential-reference imports; skip-locked claim, stale-claim requeue, dedup, no-op smoke, staged xlsx / CSV bundle / MySQL dump / Coda execution. Substrate: Spec 0011 F0b-async + data_import/services/import_job_scheduler.py · Maturity: Active (worker baseline + enqueue/status/retention/health) · Limit: production load envelope, session-only raw live-DSN UX, and future-provider row replay remain operational gaps. Two ops commands: cleanup_import_wizard_artifacts (retention, refuses out-of-root paths) and inspect_import_wizard_jobs (read-only queue health, --fail-on-stale for cron/ops probes).
  • Wizard review path (six-stage v4 frame) — /admin/data_import/mappingproject/<id>/wizard/. Stage 1 bring in your data; Stage 2 here's what we found; Stage 3 here's what we'd do; Stage 4 a few things to confirm; Stage 5 a practice run; Stage 6 ready when you are. Substrate: Spec 0017 rev 2 · Maturity: Active (Django bridge); the full React PublicPreview, ambient chat handle, Stage 6 bulk post-commit undo, and localization/a11y polish remain follow-up · Limit: the v4 frame is progressive enhancement on the Django admin templates; the native React port is deferred.
  • Comfort dial / autonomy setting — Stage 3 stores a per-project comfort level: Hands off / Stay informed / Ask if unsure / Confirm everything. Influences which parser-fast-track findings stay fast-track. Substrate: Spec 0017 Sprint B + ADR-033 (comfort-dial apply pipeline) · Maturity: Active · Limit: high-risk rows always require explicit review regardless of comfort.
  • Reason chips on Stage 3 proposal cards — affected-row counts, confidence pills, reviewer-friendly reason chips ("column-name fit", "value-type fit", "language match"), inline feedback (looks good / change this →). Substrate: Spec 0017 Sprint B · Maturity: Active · Limit: mutating proposal and subtree actions are CSRF-protected POST forms only; GET attempts redirect without changing proposals.
  • Change a table meaning (reclassify, approve-with-change) — when a proposed table meaning is wrong, pick the correct one in the Stage-3 "change this" disclosure: the proposal retargets atomically (both payload layers; subtype cleared), risk is recomputed against the NEW meaning, and the row applies through the normal single-actor chain — every card, group header, preview, and the materializer immediately speak the corrected meaning. Rows carrying an older unapplied request show an explicit "Old → New requested" banner with Apply change / Keep actions, and Stage 4 refuses plain confirmation of a stale meaning. Substrate: spec 2026-06-10-wizard-archetype-reclassify-path.md + reclassify_proposal_target (PR #557) · Maturity: Active · Limit: pre-materialize wizard action; closed (MATERIALIZED) imports don't reclassify.
  • Stage 3 per-mapping undo (auto-applied proposals) — stacked undo queue capped to three visible items; timer per auto-decision pauses while hovered/focused (the paused time honestly extends the window); emits DecisionEvent(source_signal=UNDO, reason_code=REJECTED_BY_RESEARCHER). Toasts carry the proposal's identity ("Approved: . → "); "applied for you" is reserved for auto-applies and names its cause ("comfort dial: Stay informed"); a comfort-dial change that auto-applies several rows emits ONE aggregate toast with "Undo all". Substrate: Spec 0017 Sprint C C.2 + Spec 0018 B.3 + PR #552/#556 · Maturity: Active · Limit: reverses only the pre-materialization proposal transition; does not undo Stage 6 post-commit writes.
  • Stage 4 "show me the cell" — saved per-proposal answers in MappingProject.wizard_answers; mini-grid around the source value when retained source rows are available. Substrate: Spec 0017 Sprint B · Maturity: Active · Limit: answers persist with the project; future imports of the same shape reuse them via saved-setup recall.
  • Stage 5 grouped practice-run issues — issues grouped by category (not by row), good/warn/error breakdown bar, affected-summary CSV export. Substrate: Spec 0017 Sprint B · Maturity: Active · Limit: a practice run; nothing is materialised at this stage.
  • Stage 1 saved-setup recall + Stage 2 recognition banner — ImportTemplate stores tenant-local saved setups with structural fingerprints, Stage 4 answer memory, and column profiles for diff rendering. Stage 1 cards have hover/focus diff popovers; Stage 2 shows a cautious recognition banner for repeated shapes without storing source rows. Substrate: Spec 0017 Sprint C C.1 + ADR-034 (wizard staged commit + ImportTemplate) · Maturity: Active · Limit: successful structural imports create or update the saved setup at the materialization boundary.
  • Ambient chat handle with action-guard — floating chat handle with stage-aware context; proposed actions are held back from execution until the researcher confirms (action-guard contract). Substrate: Spec 0017 Sprint C.3.8 · Maturity: Active · Limit: chat does not silently mutate review state.
  • Draft reader preview — Stage 5/6 surface that shows what a researcher will see post-materialization, backed by the real renderer and the same field-plan resolver the materializer writes. Restructured fields are marked in the practice-run preview, including keep-both companion fields. Substrate: Spec 0017 + Spec 0021 + Spec 0034 + data_import/services/draft_reader_preview.py · Maturity: Active.
  • Truthful materialize progress + completion-first receipt — the final import run shows per-table progress as tables commit ("…done (3) · …in progress (2 of 9)"), an honest indeterminate beat for the relationship pass, and a "Finalizing import" page identity (it no longer looks like a fresh source read). After completion the receipt LEADS with what happened — live record/connection counts, "N references not linked yet" with a per-link breakdown, and an Open-your-workspace action — while the pre-Start receipt folds detail behind count-bearing disclosures. Substrate: materialize_project(progress_callback=…) + work-kind-aware progress context (PR #556) · Maturity: Active · Limit: per-link sub-progress inside the single-transaction edge pass is structurally impossible; the beat is honest, not granular.
  • Per-table outcome honesty (zero-record predictions) — every source table in the plan produces exactly one outcome row (created N / will create 0 records, with the reason); the practice run and pre-Start receipt PREDICT these outcomes and the post-import receipt + completion message report the actuals. An approved table silently producing nothing is no longer possible. Substrate: MaterializationReport.table_outcomes (PR #555; root cause = the declared-lookup join convention synthesizing unsatisfiable identity columns — fixed with an intrinsic-row-id fallback for Coda sources) · Maturity: Active.
  • Wizard messages + busy states + kept scroll position — the wizard frame renders all platform messages (successes AND validation errors — previously silently swallowed); every submit shows a disabled busy state with an inline label (no more dead clicks against the browser spinner); review-list actions keep your scroll position on every stage. Substrate: PRs #551/#552 · Maturity: Active.
  • Flow B risk_class routing (two-step approval) — MappingProposal.risk_class (low / medium / high) stamped at persistence by a pure classifier. Scholar approve (PROPOSED → SCHOLAR_APPROVED) then tenant admin apply (SCHOLAR_APPROVED → APPROVED). Tenant admin apply recomputes risk against current environment state; if the class shifted while the row sat in review, the wizard blocks apply, records risk_class_at_apply, and requires explicit acknowledgement. Substrate: Spec 0011 Task F2 + ADR-010 + ADR-017 · Maturity: Active (data + transitions + Django queue lanes); Native React lanes and delegation controls remain F4 scope · Limit: AI never directly mutates production; every proposal needs scholar approval AND tenant admin apply.
  • NEEDS_REVISION status — scholars mark a proposal NEEDS_REVISION with a required structured note; non-terminal — blocks materialization but preserves the proposal and audit trail. Substrate: Spec 0011 Task F2 · Maturity: Active · Limit: requires reset/edit before re-approval; the note is structured.
  • Proposal kinds emitted today — ARCHETYPE, COLUMN, RELATION, LABEL, and review-only RESTRUCTURE proposals for lookup-as-picker, supporting-table disposition, and denormalized multilingual pairs. WIDGET_CHOICE and MULTILINGUAL_RULE are declared sockets, not generated. Substrate: Spec 0011 Task F1 + F1.1 + F0b-stub-future-kinds + Spec 0034 + data_import/models.py MappingProposal.Kind · Maturity: Active · Limit: one proposal per parser finding (ADR-010 §A.1 / §A.4); pre-push lint scripts/atlas/check_proposal_builder_one_per_finding.py enforces structurally.
  • RESTRUCTURE materialization — approved restructure proposals now materialize rather than stopping at preview: lookup columns can become linkable picker fields, supporting tables can become reference-option entities for inbound pickers, and multilingual sibling columns can merge into one multilingual field. Keep both saves the original field plus a typed companion field, such as _select or _ml; Replace keeps only the restructured field. Substrate: ADR-048 + Spec 0034 · Maturity: Active · Limit: bidirectional missed lookup detection, out-of-scope target auto-include, and export/search filtering of reference-option rows remain deferred.
  • Heuristic enrichment bridge — separate enrichment pass after deterministic parsing and before proposal building; adds reviewable table-name, column-name, junction-shape, and linkable-override hints. Substrate: Spec 0011 F0b-cli-bridge · Maturity: Active · Limit: heuristic findings cannot fast-track to SCHOLAR_APPROVED solely because confidence is high.
  • Parser evidence capability matrix — records source fidelity tier and whether each table/candidate/relation was declared by source metadata, inferred by deterministic parser signals, or produced by heuristic enrichment. Substrate: Spec 0011 F0b-source-evidence-capability-matrix · Maturity: Active · Limit: reviewer/debugging evidence; does not bypass Flow B approval.
  • LLM proposer (provider-gated) — backend supports AWS Bedrock via epistemic/services/proposals/providers/bedrock.py. Substrate: ADR-014-α + Spec 0011 Task F2 · Maturity: Active (provider-gated) · Limit: without Bedrock credentials, the proposal carries parser-only candidates and status_reason="llm_unavailable".
  • External service credentials with AWS Secrets Manager references — Coda and live-DSN MySQL paths resolve credentials through ExternalServiceCredential records that can reference AWS Secrets Manager rather than carry raw secret material. Substrate: Spec 0011 + customers/services/external_credentials.py · Maturity: Active · Limit: reference resolved server-side at job execution time.
  • Identity-aware re-import (--merge-replace) — matches new-payload rows to existing entities via identity_key (Coda) or id_column (MySQL/XLSX); refreshes source-managed fields; preserves researcher edits to non-source fields. Substrate: ADR-017 Phase 2.A · Maturity: Active · Limit: prefer over --replace/--clear unless intentionally wiping researcher edits.
  • Tip surfacing at Stage 3 — efficiency-tip cards alongside proposal cards; respects Client.tips_enabled. Substrate: Spec 0030 Phase 6.B (PR 5cb9a3d8, 2026-05-25) · Maturity: Active · Limit: tips never block researcher action; see Efficiency Tips.
  • Import Wizard metrics — when telemetry capture is explicitly enabled, upload outcomes, Coda credential validation, parse/propose jobs, proposal transitions, scheduler rounds, load probes, artifact-retention cleanup, queue-health inspection, and materialization / source-row replay emit tenant-local, payload-free metrics. Substrate: Spec 0011 F0b-telemetry · Maturity: Active (backend); the rich drilldown UI is follow-up · Limit: UI must not display raw source rows, filenames, staged paths, document/table names, credential references, tokens, or job ids.

    • Usability — how you use it​

    The default operator flow:

    1. Land at the Mapping Projects changelist: /admin/data_import/mappingproject/. Use one of the upload buttons in the top-right object-tools row — never the stock Django "Add MappingProject" form.
    2. Submit the source: pick the upload route matching your source shape (xlsx / MySQL / CSV bundle / Coda). Within the sync cap, the parser runs synchronously, generates proposals, creates the MappingProject, and redirects you to the wizard. Above the sync cap, use Run in background; the wizard opens its status page which refreshes while the job runs and links to the project when complete.
    3. Walk the six-stage wizard: Stage 1 (saved-setup recall) → Stage 2 (what we found) → Stage 3 (proposal cards + reason chips + comfort dial) → Stage 4 (ambiguous-question cards) → Stage 5 (practice-run issues by category) → Stage 6 (ready when you are).
    4. Two-step approval per proposal: scholar approve first, then tenant admin apply. Tenant admin apply recomputes risk; if the class shifted, acknowledge explicitly before mutation.
    5. Materialize: once every proposal is APPROVED or REJECTED, the wizard footer shows "Materialize mapping config". This seeds TenantOntology + TenantArchetypeFormConfig and can replay retained xlsx / CSV / MySQL-dump rows while their staged artifacts remain under tenant upload storage. Completed Coda background jobs and saved MySQL live-connection references replay rows by resolving the stored ExternalServiceCredential reference server-side.

    Risk-class routing summary:

    RiskWhat it meansRouting
    lowAdditive change, blast radius ≤ 5%, no test-corpus regression.Scholar approves → tenant admin applies. Express lane in the Django wizard.
    mediumModifies an existing mapping, or 5–25% blast radius.Scholar reviews diff → tenant admin applies after approval.
    highDestructive, > 25% blast radius, test-corpus regression, or change to a field referenced by ≥ 3 active artifacts.Tenant-admin gate even after scholar approval. Second pair of eyes expected.

    Re-importing source data​

    ModeCLI flagBehaviour
    Preserve edits--merge-replaceMatches by identity_key; refreshes source-managed fields; preserves researcher edits to non-source fields. Default for routine re-runs.
    Full refresh--replace or --clearWipes existing rows and re-imports verbatim. Destructive.

    Engineer CLI override​

    For controlled engineering workflows or data repair, with container shell access:

    docker compose exec django_app python manage.py import_coda_epistemic \
        --schema <tenant_schema> \
        --default-document "<coda-document-name>" \
        --archetypes TERM,PASSAGE,DOCUMENT \
        --merge-replace

    docker compose exec django_app python manage.py import_mysql \
        --schema <tenant_schema> \
        --config atlomyapp/import_configs/<tenant>_v1_compat.json

    docker compose exec django_app python manage.py import_xlsx \
        --schema <tenant_schema> \
        --config atlomyapp/import_configs/<tenant>_xlsx.json \
        --xlsx /path/to/workbook.xlsx

    Prefer the browser upload flow for reviewable MappingProjects; the CLI commands remain for engineering workflows, direct materialization, and repair tasks.

    Per-environment DB inspection (Directus, separate from the wizard)​

    Directus is integrated as a per-environment DB introspection / admin tool — distinct from the wizard. Use it for power-admin tasks (raw-row edits, SQL inspection, ad-hoc views) once data is materialised.

    • Compose files: docker-compose.directus-tenant.yml (generic), with per-environment compose variants.
    • Provision: python manage.py setup_directus_fdw && python manage.py sync_directus_metadata (per-environment context).
    • Allow-list / deny-list: DB_EXCLUDE_TABLES per-environment.

    Directus does not replace the wizard. The wizard is the curated onboarding path; Directus is the optional raw-DB tool for power users once data is materialised.

    Troubleshooting​

    SymptomLikely causeFix
    Mapping Projects list is emptyNo imports have been started yet; the list only fills as MappingProject rows are createdUse one of the upload buttons in the top-right object-tools row. If you do not see the Upload button, hard-refresh the page (Ctrl+Shift+R) to bypass a cached changelist template.
    Clicked "Add MappingProject" and got a bare formThat is the stock Django admin "Add" form; it does not parse a sourceThe wizard is at /admin/data_import/mappingproject/<id>/wizard/ and only renders meaningfully when a MappingProject row already exists, normally created through one of the upload buttons. The Django "Add" form is effectively unusable for tenant-admin work.
    The wizard says the AI proposer did not runThe proposal carries status_reason="llm_unavailable"; LLM_PROVIDER=bedrock plus AWS Bedrock credentials are not setThe parser still runs and the proposal carries parser-only candidates; review them. To enable Bedrock, set BEDROCK_AWS_ACCESS_KEY_ID, BEDROCK_AWS_SECRET_ACCESS_KEY, AWS_BEDROCK_REGION, AWS_BEDROCK_MODEL_ID.
    A re-import overwrote a researcher's manual editsYou ran --replace or --clear instead of --merge-replaceRestore from your environment's backup; re-run with --merge-replace. See ADR-017 Phase 2.A.
    Multiple proposals for the same tableThe one-finding-one-proposal invariant should prevent thisFile an issue. The invariant is enforced by scripts/atlas/check_proposal_builder_one_per_finding.py as a pre-push hook; if it fires, the substrate has regressed.
    Sync upload returned HTTP 413The file exceeds the sync cap; middleware enforces the boundary before Django parses the bodyRe-submit through Run in background. Async caps: xlsx 100 MB, MySQL dump 500 MB, CSV bundle 50 MB per file / 250 MB total.
    Tenant admin apply blocked with a risk-class acknowledgementThe proposal's risk_class recomputed differently than at scholar approval time; the wizard records risk_class_at_apply and requires explicit acknowledgementRead the recomputed class and the reason. Acknowledge if you accept the new class, or reject and start over.
    ExternalCredentialUnavailable on a Coda or saved-MySQL re-importThe ExternalServiceCredential reference resolves to an unavailable secretCheck the ExternalServiceCredential row and the AWS Secrets Manager reference. Credentials are resolved server-side at job execution time.
    cleanup_import_wizard_artifacts refuses to remove a terminal artifactThe artifact is still referenced by a pending or running job, or the path is outside tenant upload storageWait for the dependent job to terminate; for out-of-root paths, the refusal is structural — the path was malformed.
