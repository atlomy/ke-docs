Voice and Vocabulary

Audience: Tenant administrator. Last aligned with platform state: 2026-05-25 Platform version: V2 (pre-1.0)

Purpose​

You configure the words the platform uses when it talks to your researchers — labels, button text, archetype names, confirmation phrases, tip wording. Researchers see your wording on every platform-emitted surface. Read this when onboarding a new environment, when a researcher asks "why does it say X?", or when the substrate emits a fallback that needs to be replaced with your wording.

The substrate is purely a tenant-admin concern; researchers do not edit voice or vocabulary directly.

Features​

  • TenantVocabularyEntry rows — one per term; map a platform-canonical key to the surface form your researchers see. Substrate: ADR-044 + customers/models/vocabulary.py (migration 0014) · Maturity: Active · Limit: you cannot create entries for keys the platform does not declare canonically.
  • {% voice %} template tag — the rendering primitive every platform-emitted string passes through; resolves to your entry, then _fallback_bundle_voice, then a labelled platform default. Substrate: ADR-044 + atlomyapp/templatetags/ke_voice.py · Maturity: Active · Limit: applies only to platform-emitted strings, not researcher-authored content.
  • Tenant ontology voice keys — environment-wide tone toggles and fallback phrasings carried on the TenantOntology row; read first when the {% voice %} tag resolves. Substrate: ADR-044 D.3.7 + D.3.9 · Maturity: Active · Limit: a small fixed set of voice keys; richer per-key overrides go on the vocabulary entry.
  • Safety-floor gate — onboarding gate that blocks authoring until enough vocabulary entries are grounded, derived, or AI-reviewed. Substrate: ADR-044 §3 + R3 absorption (tiered Levenshtein, softened observational mode) · Maturity: Active (observational by default) · Limit: enforcement mode is configurable per environment; default observational mode surfaces unlock state without hard-blocking.
  • Wizard-stage chrome wiring — all five wizard stage chrome pages plus workspace TableToolbar labels resolve through the substrate. Substrate: ADR-044 D.3.7 + D.3.9 (wired 2026-05-25, PR #419) · Maturity: Active · Limit: applies to chrome and toolbar text; per-row data is not voice-substituted.
  • HMAC-validated AI suggestion provenance — every ai_reviewed vocabulary entry carries an HMAC ai_suggestion_id referencing its originating proposal. Substrate: ADR-044 D.3.13 · Maturity: Active · Limit: tamper-evident, not encrypted.

Usability — how you use it​

The vocabulary surface lives inside the Django admin. The common operator paths:

  • Map a canonical key to your wording: open the vocabulary admin, find the canonical key your researchers see surfaced, edit the matching TenantVocabularyEntry row to set the preferred surface form, save. The change propagates through the {% voice %} tag across every platform-emitted surface.
  • Test what a researcher would see: the fallback-bundle view shows the resolved string for any canonical key — your entry first, the bundle fallback next, then the labelled platform default. Use this before deciding whether you need a new entry.
  • Unlock the safety-floor gate: any of grounded, derived, or ai_reviewed status satisfies the gate. See AI-Assisted Bootstrap for the one-pass onboarding path and Vocabulary Grounding for the external-authority path. The derivation lane writes entries from imported source data.
  • Audit a wording change: every vocabulary edit emits an audit row. Open the Audit tab in Permissions Panel to see actor, timestamp, target, and reason code.

When the platform's underlying canonical key changes (a rename in a future release), the audit tab surfaces a notification. Your existing entry remains in place until you decide what to do.

Troubleshooting​

SymptomLikely causeFix
A platform-emitted string still shows the platform default in your environmentNo matching TenantVocabularyEntry exists for the canonical key, and the fallback bundle has no entry eitherOpen the vocabulary admin, locate the canonical key, add a row with your preferred surface form. Verify the rendered output via the fallback-bundle view.
The safety-floor gate stays closed even after you added a vocabulary entryThe added entry's status is proposed; the gate accepts only grounded / derived / ai_reviewedPromote the entry through grounding (Wikidata or PeriodO lookup) or AI bootstrap acceptance, or trigger the derivation lane by importing source data.
A wizard stage shows a raw canonical key like archetype.term.display_label instead of your wordingThe surface bypassed {% voice %} or the canonical key is new and not in the fallback bundleThis is a platform bug — file an issue. Surfaces are required to go through {% voice %} per ADR-044 D.3.9 and the structural allowlist (D.3.11).
You see "vocabulary substrate" lint findings in the Permissions Panel bannerThe startup linter detected missing entries, broken grounding references, or duplicate keysClick into the surfaced rows. The lint is read-only; you decide whether to add, ground, or remove entries.
The tenant-vocabulary pre-commit lint blocked a code changeA platform module hardcoded tenant-specific wording instead of going through the voice substrateRefactor the code so the wording resolves through {% voice %} or a TenantArchetypeFormConfig entry. Suppression markers are documented in AGENTS.md.
