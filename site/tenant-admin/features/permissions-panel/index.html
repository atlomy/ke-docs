Permissions Panel

Purpose​

The Permissions Panel at /admin/permissions/ is the single surface for who-can-do-what in your environment. Contributor roles, custom role composition, project safety rules, wording overrides, ownership hand-off, and the project-history lookup all live here. Read this when changing a contributor's role, composing a custom role, handing off project ownership, or answering "who reviewed that import, and when?".

Features​

  • Contributors tab — every contributor in your environment, with their assigned role and last activity. Change a contributor's role, adjust individual permissions, or narrow the scope of their assignment. Maturity: Active. Limit: the panel manages roles and permissions for existing contributors; contributor accounts are created by your platform operator — see User and Access Management.
  • Roles tab with custom role composition — the standard roles come preloaded; custom roles are composed from a fixed set of permission building blocks. A standard role can be renamed inline; the new name is a display label only. Maturity: Active. Limit: the building blocks themselves are fixed by the platform.
  • Role scoping — a role assignment (or a custom role) can be limited to specific record types or fields. Maturity: Active. Limit: a scope only narrows where the role applies; it cannot add permissions the role does not grant.
  • Project rules tab — set your environment-wide review policy: whether high-impact saves need a reviewer who did not author the change, and how destructive changes are confirmed — by two contributors, or by a single contributor through an elevated confirmation step. Maturity: Active. Limit: the panel saves and displays these choices as your environment's declared policy; how each applied change was actually confirmed, and by whom, is shown on the Project history tab.
  • Review learning setting — on the Project rules tab: opt in to record privacy-safe signals from your team's review decisions so future suggestions improve. Maturity: Active. Limit: off by default; switching it on requires acknowledging the privacy notice, and the change is recorded along with which admin made it.
  • Wording tab — rename the permission-related labels shown in your environment, starting with role names. Maturity: Active. Limit: changes compose with your environment's voice and vocabulary settings; there is no separate translation table to maintain.
  • Vocabulary review prompt — when the panel loads, it checks permission-related wording and flags entries that need review, with the reason and a link to edit each one. Maturity: Active. Limit: the check is read-only — it never changes anything; you act on a finding or dismiss it.
  • Project history tab — look up the recorded history of an applied import proposal: its status, how it was confirmed, who reviewed it and when, the recorded reason, and the permissions that were in force at the moment it was applied. A record carries an "Edited after apply" marker when the applied content was changed afterwards. Maturity: Active. Limit: lookup is per proposal — you supply the proposal's ID from the import screens; records are read-only.
  • Ownership hand-off — the current project owner can hand ownership to another contributor. The hand-off asks for explicit confirmation for both sides, completes as a single change, and is recorded. Maturity: Active. Limit: only the current owner can start a hand-off, and the new owner must be an active contributor holding the administrator role with permission management.
  • Display density control — switch the panel between compact, cozy, and comfortable layouts. Maturity: Active. Limit: cosmetic only — it affects rendering, not permissions; the choice is remembered in the browser where you set it.

Usability — how you use it​

The panel's address is /admin/permissions/. It opens on the Contributors tab; the other tabs are Roles, Project rules, Wording, and Project history. The active tab is kept in the page address, so a bookmark or a shared link opens the panel on that tab.

  • Change a contributor's role: Contributors tab, open the contributor's row, pick the role. To limit where the role applies, set a scope on the same row.
  • Compose a custom role: Roles tab, combine the permission building blocks, name the role. Rename any role's display label inline with the edit control; the underlying building blocks stay fixed.
  • Set project rules: Project rules tab. Switch the separate-reviewer requirement on or off, choose the destructive-change policy, and save.
  • Enable review learning: Project rules tab. Switch the setting on, acknowledge the privacy notice, and save. The decision is recorded along with who made it.
  • Hand off ownership: as the current project owner, use the "Hand off ownership" control, choose the new owner, and confirm for both sides.
  • Look up an import's history: Project history tab, enter the proposal's ID, and load the history. The record shows the review decision and the permission snapshot from the moment of apply.
  • Review flagged wording: when the vocabulary check finds entries needing review, a notice appears. Open the Wording tab, follow each flagged entry's edit link, or dismiss the finding.

Troubleshooting​

SymptomLikely causeFix
A notice says permission wording needs reviewThe load-time vocabulary check flagged entriesOpen the Wording tab. The check is read-only; follow the edit link on each flagged entry, or dismiss the finding. See Voice and Vocabulary.
Renaming a standard role did not change what it allowsA rename sets a display label only; the role's permission building blocks are fixedThis is the intended behavior. Compose a custom role if you need a different set of building blocks.
A contributor cannot act on content their role should allowTheir role assignment carries a scope that excludes that contentOpen the contributor's row and check the scope. Widen it or remove it.
The ownership hand-off will not completeOnly the current owner can hand off, and the new owner must be an active contributor holding the administrator role with permission managementGive the intended new owner the administrator role with permission management first, then run the hand-off again.
Review learning is on, but suggestions do not seem to improveSignals accumulate gradually and stay within your environmentThis is expected early on. The setting records your team's review decisions over time; it does not change behavior immediately.
