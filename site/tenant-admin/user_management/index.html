User and Access Management

Audience: Tenant administrator. Last aligned with platform state: 2026-05-25 Platform version: V2 (pre-1.0)

Purpose​

This page covers team membership and the standard role set. It is the lightweight overview; the live source of truth for contributors, role composition, project rules, ownership transfers, and the audit trail is the Permissions Panel. Read this if you want a one-page summary of the role model; jump to the Permissions Panel if you are about to make a change.

Features​

  • Standard role catalog — the four pre-loaded roles every environment ships with. Substrate: ADR-007 + ADR-035 + customers/services/permission_bundles.py · Maturity: Built · Limit: the underlying permission primitives of standard roles are fixed; renaming is surface-label-only.
  • Custom role composition — build a role from a fixed set of permission primitives. Substrate: Spec 0018 Sprint C + customers/services/permission_admin.py · Maturity: Active · Limit: primitives are platform-defined; you compose them, you do not invent new ones.
  • Project rules — per-project policy that further scopes a role's effective permissions within that project. Substrate: Spec 0018 Sprint C · Maturity: Active · Limit: effective permission on a project is the intersection of role and project rule.
  • Ownership transfer — reassigns authored content from one contributor to another with explicit confirmation. Substrate: Spec 0018 Sprint C ownership-transfer modal · Maturity: Active · Limit: non-destructive at the row level; the original author's history remains visible in the audit tab.

Usability — how you use it​

The Permissions Panel at /admin/permissions/ is where you do this day-to-day. From the panel:

  • Add a contributor: Contributors tab, then the standard add form. The contributor must be assigned a role before they can do anything; an unrolelled contributor sees nothing.
  • Assign a standard role: pick from the catalog. The standard roles are pre-loaded.
  • Compose a custom role: Roles tab, then compose from the permission primitives. Custom roles can be renamed inline; the rename is a tenant-local surface label, not a primitive change.
  • Apply a project rule: Project rules tab. Rules intersect with role permissions, never expand them.
  • Transfer ownership: open the contributor's row and use the ownership-transfer modal. The modal records a transfer event in the audit tab.

Standard role summary:

RoleDescriptionTypical user
ViewerView content; no edits.External reviewers, students.
EditorCreate and edit content (lemmas / entries / events / bibliography).Senior researchers, content contributors.
EngineerRun data imports through the wizard and manage schema mappings.Technical coordinators, data specialists.
AdminFull environment control, including managing other contributors.Project directors, principal investigators.

Troubleshooting​

SymptomLikely causeFix
A contributor cannot see the System tab or platform-settings sectionTheir role does not carry the admin primitiveOpen the Permissions Panel, move them to the admin role or compose a custom role that includes the admin primitives.
You need a permission shape no standard role providesThe standard catalog is fixedCompose a custom role from the available primitives. If the primitive itself does not exist, that is a platform-team conversation; do not work around it.
Renaming a standard role did not change the permissionsRenaming is a tenant-local surface label onlyThe rename is correct; the underlying permission primitives are fixed by the platform. Compose a custom role if you need different primitives.
A contributor's permissions changed without an apparent editA project rule narrowed their effective permission for that projectCheck the Project rules tab. Effective permission is the intersection of role and project rule.
