Planning a safe re-import

Purpose​

A re-import brings a refreshed copy of source data you have imported before into your environment. Most re-imports are routine: the source gained a few rows, corrected some values, or grew a new column, and you want the environment to reflect that. This page is for the planning that happens before you press start — checking what would change, choosing how records are refreshed, and reading the practice run — so a refresh updates your data without quietly overwriting work your researchers have done.

Read this before re-running a source you have imported once already, especially if researchers have been editing those records in the workspace since the first import.

This page covers the planning and the choices. For the wizard's screens, size limits, and step-by-step controls, see Data Import Wizard. For what your researchers see afterwards, see the cross-links at the end.

When a re-import is routine, and when it is risky​

A re-import is routine when:

  • The source gained rows, or corrected values in fields the source manages.
  • The source grew a new column you want as a new field.
  • Nobody has hand-edited the affected records inside the workspace, so there are no researcher edits to protect.

A re-import deserves a careful plan when:

  • Researchers have edited records in the workspace since the last import — added notes, set field labels, marked fields required, or filled in fields the source does not manage.
  • The source dropped or renamed columns that your researchers rely on.
  • You are not certain which refresh behaviour a planned run will use.

The wizard itself never publishes anything and writes nothing to your environment until you press Start import in the final step. The risk is not in opening the wizard. It is in choosing the wrong refresh behaviour for a source whose records carry researcher edits.

Before you run: check for researcher edits​

Researcher edits are the thing a re-import can put at risk, so locate them before you plan the run.

  • Open the affected tables in the workspace and look for records that have been worked on since the last import — filled-in fields the source does not provide, renamed field labels, required flags, or notes.
  • Field configuration you set — labels, required flags, field-level settings — is preserved across a re-import regardless of refresh behaviour. It is the record values that researchers entered into fields the source does not manage that depend on which behaviour you choose.
  • If researchers have been working in these tables and you cannot tell what they changed, treat the run as risky and plan for the edit-preserving behaviour described below.

Choosing how records are refreshed​

The platform supports two behaviours for refreshing the records themselves. The difference is what happens to anything a researcher added that the source does not manage.

BehaviourWhat it keepsWhat it replacesWhen to use
Edit-preserving refreshResearcher edits to fields the source does not manage, on records it can matchOnly the values the source manages, refreshed from the new dataThe right default for routine re-runs
Full refreshNothing from the prior recordsEverything — the existing rows are removed and reloaded from scratchOnly a genuine "start over", when you intend to discard prior records and their researcher edits

Edit-preserving refresh matches each incoming row to an existing record by the record's source identity — the stable identifier carried from the first import — then refreshes the source-managed values and leaves everything else alone. Where there is no match, it creates a new record. Full refresh does not match at all: it removes the existing rows and reloads, which discards any researcher edit those rows held.

This choice is made by your platform operator, not in the wizard. Edit-preserving refresh and full refresh are run as platform commands, not as buttons inside the wizard. If you are unsure which behaviour a planned re-import will use, confirm it with your platform operator before the run — this is the single most important step in planning a safe re-import. State plainly which one you want and why.

What the wizard does on a re-import​

When you re-import a source you have brought in before, the wizard works for you rather than starting over:

  • It recognizes the saved setup from the earlier import.
  • It carries your unchanged decisions forward instead of re-asking them, so you review only what is new, changed, or ambiguous.
  • Anything new, changed, or genuinely uncertain goes back to review. Uncertainty always routes to review — it is never carried forward silently.

This carry-forward is about the structural decisions you made (how a table is read, what a column becomes). It is separate from the record-refresh behaviour above, which governs the record values themselves.

Reading the practice run before you commit​

The wizard's practice run is a full dry run that happens before anything is written. It is your last and best check on a re-import plan.

  • It reports how many records will be created, updated, or skipped, and how many are blocked by unresolved review items.
  • Issues are grouped by cause rather than scattered by row, with a good / warning / error breakdown, and each group links back to the review queue.
  • For a re-import of mostly unchanged data, the practice run should show nearly all records ready rather than blocked, because carried-forward decisions are already accounted for.

Read the practice run as a forecast of the real run. If the numbers do not match what you expect — far more records updated than rows changed, or a table predicted to create nothing — stop and find out why before pressing start. The practice run is also where the wizard predicts each table's outcome, so the final receipt should confirm what the practice run forecast.

What researchers will see afterwards​

A re-import surfaces to researchers as a delta — a summary of only what is new, changed, carried forward, removed, or restored since their last import. It does not ask them to re-review decisions already made. Point researchers at these entries so they can read their side of a re-import:

  • Understand what changed after a re-import — how the delta reads, and the reassurance that their own edits and labels are not overwritten by an edit-preserving refresh.
  • What happens to saved views after a re-import — how a saved view adapts when a field it referenced is removed in the new source, and how it is restored if that field returns.

If something went wrong​

The safe direction is to plan so that nothing needs undoing. But if a re-import has already written records you wish it had not:

  • Records written by an import cannot be undone from inside the wizard. The wizard's undo applies to review decisions before the final run; it does not reverse records written when you press start.
  • The verified recovery path is to restore the affected records from your environment's backup, then re-run as an edit-preserving refresh. If your platform operator runs imports for you, ask them to restore from backup and use the edit-preserving behaviour. This is operator-mediated work, not something you reverse yourself.
  • A re-import that was interrupted mid-run — rather than completed wrongly — is a different case: the setup, approvals, and practice run are kept, and starting again resumes from the stopped table without writing completed tables twice. A run that did not finish cleanly is reconciled by your platform operator before the next attempt; it is not something to force past.

The honest statement is that a full refresh over records with researcher edits is destructive and the records themselves are recovered only from backup, not from within the platform. Plan the behaviour choice carefully and you avoid needing recovery at all.
