What the workspace remembers — and what you can undo

Purpose​

The workspace keeps several kinds of memory working for you at once: a history for edits to a table's records and fields, a separate history for changes to how a saved view is displayed, browser-side memory of where you left off, and account-level memory of how you organized your sidebar. They behave differently. This page explains which is which, so you know what Undo can bring back, why it sometimes refuses, and why your screen may not match a colleague's.

Features​

  • Undo and redo for workspace edits (Active) — Table, Details, and Relations share one chronological history for the active table. It holds up to 50 value, paste, manual row-order, reversible field-definition, and relationship changes while this browser tab keeps the workspace page open. A type conversion that rewrites stored cells starts this history over because configuration snapshots cannot restore those cells.
  • Undo and redo for view changes (Active) — the separate view history steps through filters, sort order, column layout, row color rules, and row density. It holds up to 20 presentation changes.
  • Confirmation for destructive structure changes (Active) — deleting a saved view asks you to confirm and does not enter either history. Creating or deleting a row or field is also outside workspace edit history. Removing a relationship is different: it is an edit to the connection and can be undone.
  • Shared default view wins for first entry (Active) — each table has one shared default saved view, including its view kind: Table, Details, Relations, Publish, or Media where available.
  • Last concrete view remembered per table (Active) — the browser you are using can remember a specific non-default view tab you last opened in a table. That memory does not replace the table's shared default view kind.
  • Sidebar size remembered per browser (Active) — how wide you made the sidebar, and whether you collapsed it to the icon rail.
  • Sidebar organization saved with your account (Active) — pinned tables, named groups, your table order, which groups you collapsed, and your recently opened tables are stored with your sign-in, not in the browser.

Usability — how you use it​

What workspace Undo covers​

The workspace-history Undo and Redo controls appear in Table, Details, and Relations. Their labels name both the surface and the next operation, such as a value edit made in Details or a link removed in Relations. They follow one chronological history for the active table:

  • editing one value in Table or Details
  • pasting values into existing rows, including a batch
  • changing the hand-arranged row order
  • changing a field type or another field definition when the save rewrites no stored cell
  • adding or removing a relationship from Table, Details, or Relations

Each press of Undo steps back one saved operation, up to 50 entries; Redo reapplies what you undid. Ctrl/Cmd+Z runs Undo. Redo accepts Ctrl/Cmd+Y and Shift+Ctrl/Cmd+Z. These shortcuts are ignored while you are typing in an editor or while a dialog is open. If a paste review is still waiting for confirmation, Undo cancels that pending paste before it touches saved data.

Undo is careful around newer work. Before it replays a value or field-definition change, the workspace checks that the current value or definition still matches the history entry. If another edit has landed since then, Undo refuses, keeps the history entry in place, and explains the conflict instead of overwriting the newer edit. A refused direct save also keeps your draft visible with Retry save and Discard retained edit choices.

Some type changes convert stored cells to the new type. The workspace reports the converted and quarantined counts; quarantined values remain as they were and are marked for correction. If at least one cell was converted, the receipt says the conversion cannot be undone and clears this table's Undo and Redo history. Schema-only changes that convert no cell remain ordinary history entries.

Undoing an unlink restores the same connection, including its recorded status, provenance, detail, anchor, and attribution. The restore is accepted only for the same signed-in person and environment, within 90 days of the unlink, and only while the current relationship field still permits that connection. A restore that is stale, already used, duplicated, or no longer allowed is refused without consuming the history entry.

An import run does not enter this browser history. If an import created an approved connection through a declared relationship field and you later unlink it in the workspace, that later unlink is a workspace edit and can be undone. Imported connections that have no editable relationship field remain read-only.

What workspace Undo deliberately leaves alone​

Workspace Undo does not create or delete rows or fields, reverse an import run, upload or remove a media file, change Appearance, alter citation rules, change field visibility, publish or unpublish records, or change privacy/public scope. Appearance, Publish, and Media do not expose or intercept the workspace-history shortcuts, so pressing Ctrl/Cmd+Z there cannot replay an edit from another panel or change publication state.

Creating a new row, duplicating a row, and adding or deleting a field therefore require their own explicit action and confirmation where appropriate. Pasting into existing rows is reversible; extra clipboard lines never create new rows automatically.

View Undo is separate​

The view-history controls cover how the active saved view is displayed:

  • filters — adding a condition, changing one, or removing it
  • sort order
  • column layout — order, visibility, pinning, widths, and the view display column
  • row color rules
  • row density

That history holds up to 20 changes. Its command-palette actions are named Undo view change and Redo view change, keeping it distinct from the labelled workspace-operation entries. A restored arrangement is saved back to the shared view, so collaborators see the arrangement you restored.

Why saved-view deletion is confirmed, not undone​

Saved-view deletion does not enter either history. Deleting a saved view shows a confirmation step on the view's tab itself, and a deleted view is gone for everyone who works in the environment. When you want to experiment with a shared view, Duplicate it first and work on the copy.

When the undo history starts over​

Workspace-operation history is short-lived on purpose. Each table has its own 50-entry bucket while this browser tab keeps the workspace page mounted. Switching among Table, Details, and Relations keeps the bucket. Visiting another table switches to that table's bucket, and returning restores the first table's bucket. Appearance, Publish, and Media leave the bucket in place but cannot apply it.

Reloading the page, closing the tab, opening the workspace in a new tab, or completing a type conversion that rewrites stored cells starts workspace-operation history fresh. A new edit after Undo clears the redo path, as in other editors. The separate view history also starts fresh when you move to another saved view or table or reload, while the saved view itself keeps the arrangement durably.

What the browser you are using remembers​

Open a table without naming a view in the address, and the table's shared default view is the starting point. That default includes its view kind — for example, a table can open directly in Table or Details if that is the default view's mode.

The browser you are using can also remember a concrete non-default view you opened in that table. That memory is kept per table, in that browser — a different computer, a different browser, or a private window starts fresh. It does not turn the default view into a private personal default.

Two things always win over this memory:

  • An explicit link. A view link a colleague sends you opens exactly the view in the link, not your remembered one.
  • The shared default. If no concrete saved-view link or remembered concrete view applies, the workspace uses the table's default view and its view kind.
  • A removed view. If the view you last used no longer exists, the workspace falls back to the table's default view.

The sidebar's size is browser-side memory too: its width, and whether you collapsed it to the icon rail, are restored the next time you open the workspace in the same browser.

Some things are deliberately not remembered: the toolbar's quick filter text and your row selection clear when you move to another table or view, so you never land on yesterday's narrowing without noticing.

What follows your account​

How you organized the sidebar — pinned tables, named groups, the order of your tables, which groups you collapsed, and your recently opened tables — is stored with your sign-in for this environment rather than in the browser. Resizing the sidebar stays with the browser; organizing it stays with you.

Why you and a colleague may not see the same view​

Saved views are shared — everyone in your environment sees the same view tabs. Which tab you land on can still differ when one browser follows a concrete view link or remembers a concrete non-default view, while another browser starts from the table's default. You are both looking at the same shared set of views, opened at different tabs.

To get back to the shared starting point, select the default view — the first tab in the view tab row. Each table has exactly one default view; Set as default in a view tab's menu changes which view that is, for everyone.

Troubleshooting​

SymptomLikely causeFix
Workspace Undo is grayed out.The active table has no reversible edit in this browser tab, or an undo/redo is still applying.Finish the current editor or wait for replay to finish. If you reloaded or opened a new tab, reapply the change by hand.
Undo refused instead of changing a value or field.The current value or field definition no longer matches the recorded operation, so replay would overwrite newer work.Review the current state and decide which edit should win; then make that edit deliberately.
A removed relationship was not restored.The restore was already used, is older than 90 days, would duplicate an existing link, belongs to another person or environment, or the relationship field no longer permits it.Refresh Relations and review the current rule and links. Add the link again only if the current configuration allows it.
Ctrl/Cmd+Z did nothing in Appearance, Publish, or Media.Workspace-history shortcuts are intentionally inactive on non-editing surfaces.Return to Table, Details, or Relations to undo a record, field, paste, row-order, or relationship edit.
Undo did not reverse a publish, visibility, privacy, citation, media, import, row-create, or field-create action.Those operations are outside workspace edit history.Use that surface's explicit controls or correction process. Workspace Undo never changes publication or privacy state.
The workspace opened on a different view than your colleague sees.One of you followed a concrete view link or had a remembered concrete view; the other started from the shared default.Select the same view tab, or open the same view link.
The workspace did not return you to your last view.You opened a link that names a view, you are in a different browser or a private window, the remembered view was removed, or the shared default view is taking precedence.Open the view's tab again, or ask your team which view should be the default.
The sidebar looks different on another computer.Sidebar width and collapse are remembered per browser; only its organization follows your account.Resize or collapse the sidebar once on the new computer — your groups, pins, and table order are already with your account.
