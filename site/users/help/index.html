Help Entry Format — Authoring Guide

Audience: Authors contributing to the researcher help substrate (docs team, engineers shipping researcher-visible behavior changes, AI agents authoring help content). Last aligned with platform state: 2026-06-11 Platform version: V2 (pre-1.0)

See docs/superpowers/specs/0050-researcher-help-substrate/ for the full spec.

What a help entry is​

One entry = one researcher intent. A help entry answers a specific task-shaped question ("how do I make a field required?", "what changed since my last import?") in the researcher's own language. It is not a feature overview, a release note, or an engineering description.

Help entries are authored once and rendered to three surfaces:

  1. The workspace Help page (FAQ + guides list).
  2. In-product "?" affordances on the matching surface (via help_keys — see docs/developer/architecture/help-key-contract.md).
  3. The AI helper's knowledge pack (consumed as structured, retrieval-ready units).

Frontmatter schema​

Every entry file MUST include all required fields.

---
id: kebab-case-unique-id               # required — matches filename (without .md)
title: "Short task-shaped title"       # required — one sentence, action-first
summary: "One plain sentence."         # required — card subtitle on the Help page
group: data                            # required — data | find | import (Help page grouping)
intents:                               # required — minimum 3 retrieval phrases
  - "natural-language question or phrase a researcher would type"
  - "alternate phrasing"
  - "another variant"
help_keys:                             # required — dotted namespace IDs per helpKey contract
  - workspace.surface.concept          # see help-key-contract.md for namespace rules
audience: researcher                   # required — always "researcher" for this tree
related:                               # optional — sibling entry IDs (not filenames)
  - other-entry-id
---

Field rules​

FieldRule
idKebab-case slug; must match the filename without .md; globally unique across docs/users/help/. Never reuse a retired ID.
titleOne concise sentence, action-first ("Make a field required", "Share a search"). Use researcher vocabulary — never "slot", "tenant" (for a person), or engineering terms.
summaryOne plain sentence shown under the title on Help page cards and at the top of the reading pane / drawer. Same vocabulary rules as the title.
groupOne of data (working with your data), find (finding and sharing), import (importing and updating). Drives the Help page's collapsible groups — declared here, never inferred.
intentsTask-shaped phrases a researcher would type or speak. At least 3. They are the retrieval surface for FAQ search and the AI helper. Include common misspellings / alternate vocabulary. Do NOT duplicate the title verbatim as the first intent.
help_keysDotted namespace IDs per the helpKey contract (<surface>.<sub-surface>.<concept>). The entries here become rows in help-manifest.json at docs-site build. Use platform-canonical IDs — never tenant-specific names. If the entry describes a cross-surface concept, list all relevant anchors.
audienceAlways researcher for entries in docs/users/help/. Entries for tenant-admin-only features live in docs/tenant_admin/help/ (future).
relatedSibling entry IDs (not filenames, not URLs). Keep to entries the researcher would naturally reach next.

Body authoring rules​

Task-shaped, not feature-shaped​

Write from the researcher's goal, not from the platform's internals.

  • Good: "When a field is required, a record cannot be saved while it is empty."
  • Avoid: "The required column in TenantArchetypeFormConfig is RESEARCHER_OWNED."

Researcher vocabulary​

Do not saySay instead
slotfield (or the field's name, or "this column")
tenant (for a person)researcher, your team, your project
retired / deactivatedremoved
restore (a retired column)restored
comfort dialautonomy setting
staged commitreview before write
archetype (as a code concept)concept family (acceptable once with a plain definition)
MappingProjectimport project
substrate, infra layerthe platform, the system

Do not use pilot codenames (e.g. the names of specific research projects or universities using the platform) anywhere in this tree. Use generic examples instead: "a field called 'Author'", "a collection called 'Manuscripts'", and so on.

Verbatim-label examples​

When an example needs a field or collection name, use a plausible generic label — one the reader could substitute for their own ("Author", "Date of publication", "Manuscripts"). The real display label renders as the researcher's own vocabulary at runtime via the voice substrate (ADR-044).

Steps must be checkable​

Each numbered step must correspond to a real UI action on a real surface (/app/workspace/..., Field Definitions, Search & Read, the import wizard, etc.). If a step is not yet in the product, either omit it or mark it explicitly as "coming soon" — do not describe aspirational behavior as shipped.

Deep-links​

Where a step lands the researcher on a specific page, include the URL path as a parenthetical note: "(Go to Field Definitions at /app/workspace/ <your-collection>/field-definitions.)" Omit the domain and any IDs.

Notes and caveats​

Use a blockquote (>) for a single important caveat:

> Your import never sets this for you — requiredness is always your choice.

Do not use blockquotes for normal body text.

Same-PR gate​

Every PR that ships a researcher-visible behavior change MUST include the matching help entry update in the same PR. This is the Amendment 1 culture gate from the 2026-05-25 docs strategy. The PR reviewer checklist includes one line: "Help entry added or updated for every researcher-visible change in this PR."

If no researcher-visible behavior changed, no help entry is needed. If the change is purely behind-the-scenes or affects only engineering surfaces, mark the PR description accordingly so reviewers know the check was considered.

Build and validation​

The help entries are compiled by scripts/build_help_entries.py:

# Validate all entries (CI-safe):
python3 scripts/build_help_entries.py --check

# Build help-entries.json:
python3 scripts/build_help_entries.py

In --check mode the script exits non-zero and lists ALL invalid files if any frontmatter field is missing, mistyped, or violates the rules above.

The build compiles each body into a small block model (body in the JSON: paragraphs, sub-headings, numbered steps, bullet lists, note callouts, and tables) so the app renders entries without parsing markdown at runtime (Spec 0050 design §2). Two structural rules: the leading # Title heading is dropped (frontmatter title is canonical), and a ## Related section is dropped (frontmatter related: is canonical — the surfaces render it as chips). The raw markdown is kept alongside as body_markdown for the AI helper's knowledge pack.

The emitted help-entries.json lives at the repo root (or wherever the docs build pipeline picks it up) and is the single source consumed by:

  • The workspace Help page (SPA route /app/workspace/help, served by the help_entries view at /app/help/entries.json).
  • The contextual "?" affordances (<HelpRef helpKey="…" /> resolves against the same compiled corpus in v1; help-manifest.json at docs-site build takes over when the publication pipeline lands).
  • The AI helper's knowledge pack.
