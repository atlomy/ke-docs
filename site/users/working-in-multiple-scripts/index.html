Working in multiple scripts and languages

Purpose​

Many projects keep their material in more than one form: a native-script form, a transliteration, a translation — sometimes all three on the same record. This page covers how those forms relate to each other, how to enter text in any script, how one search reaches every form at once, and how multi-script records appear to readers. Read it when you start work in a multilingual environment, or when a search behaves differently across scripts than you expect.

What is available depends on how your environment is configured. The sections below describe what the platform supports; your project may use all of it or a subset.

Features​

  • Text in any script — every text field stores what you write, in the script you write it. The platform never rewrites your text into another script. Maturity: Active.
  • Side-by-side language forms — a record can carry a native-script field, a transliteration field, and a translation field next to each other; a search term in any of them finds the record, provided those fields are searchable and filled. Maturity: Active.
  • A field that holds several values — a single field can keep more than one value per record — one for each language, register, script, edition, or calendar. All the values are searchable together, and you edit them in the table cell or the record's form. Maturity: Active.
  • Forgiving matching across accents and marks — search sets aside most marks (Greek breathings and iota subscripts, Arabic vowel marks, Hebrew vowel points) while keeping the acute accent and the diaeresis, so a term typed in a modern keyboard layout finds historic spellings. Maturity: Active.
  • Exact matching where a mark makes a different letter — a field can be set to match every mark exactly, for languages where marks are part of a letter's identity. Your environment administrator sets this per field. Maturity: Active.
  • Script-aware browsing for readers — a project can publish more than one index of its entries (by transliteration and by original script, for example), and Greek and Latin index lists group accented entries under their base letter while still displaying the full form. Maturity: Active.

Usability — how you use it​

One entry, several forms — which to fill and why​

Multilingual records take two shapes, and a project may use either or both:

  • Separate fields side by side. The native-script form, the transliteration, and the translation are each their own field — each with its own column in the table, and each searchable in its own right.
  • One field holding several values. A single field keeps more than one value per record — most often one per language, but a field can instead separate by register, script, edition, or calendar. The Details panel marks these fields with a multilingual badge.

Every form you fill is one more way the record can be found: the native script for colleagues who search in it, the transliteration for those who search in Latin script, the translation for finding by meaning. Search reaches a form only when it has a value and its field is searchable — and the platform never invents a transliteration or a translation from another field. What you write is all there is.

Setting a field up to hold several values​

A field that holds several values is set up once, on the field. Its setup has two independent parts:

 Field setup
 ├─ This column's language & script   ← one language + script for the whole column
 │     Language code:  [ grc      ]      (use when every value is in one language)
 │     Script:         [ greek    ]
 │
 └─ Multiple values                   ← the column keeps a separate value per entry
       [✓] This column holds more than one value
       A separate value for each:  [ Language ▾ ]   (or Register / Script /
                                                      Edition / Calendar / Custom)
       Allowed languages:
          [ GK ✕ ] [ LA ✕ ] [ AR ✕ ]      ← chips: each allowed value
          Add a language: [________] (Add) ← type a new one; it's tidied to a chip

The two parts are independent. This column's language & script stamps a single language on the whole column; Multiple values instead lets the column keep a separate value for each allowed language. Allowed languages is a set of chips, not free text — and the label follows your choice (Allowed registers, Allowed scripts, and so on). For the full walkthrough, see Let a column hold several values. Setting fields up is an administrator task — see Field configuration.

Entering text in any script​

Type or paste in any script. Keyboard layouts and input methods come from your operating system, not the platform; whatever they produce, the field stores.

  • Ordinary text fields work the same in every script — write as you would anywhere.
  • A field holding several values shows them together in the table cell. Edit the cell and an editor opens: one row per value, each pairing the value with the language (or register, script, edition, or calendar) it belongs to. Choose the language for a row from the dropdown beside it — it lists the languages the field allows, and + new lets you add one the list does not yet offer. + Add language (the wording follows the field's setup — + Add register, + Add script, and so on) adds a row, the × beside a row removes it, Save commits, and Cancel or Esc closes without saving. Rows left empty are dropped when you save. When a row's language is Arabic, Hebrew, Persian, Urdu, or Aramaic, its value box writes from right to left.
  • In the record's form, the same field edits the same way: one row per value, the language chosen from the dropdown, + new for one not yet listed, and + Add language for another row. The cell and the form edit the same values — fill them wherever suits you.

You pick each row's language from a list rather than typing it freely. That keeps every record's values lining up under the same set of languages, so they group and display consistently across the collection. Which languages a field allows is part of the field's setup — see Field configuration. For the step-by-step, see Add a value in another language.

How one search covers all the forms​

Quick search and Search & Read match against every searchable field of a record at once — the native form, the transliteration, the translation, and every value of a field that holds several. One query, all forms; there is no language switch to set first.

Matching is forgiving about most accents and marks. When text is prepared for search, and again when your typed term is read, these are set aside:

  • breathings and iota subscripts in polytonic Greek, and the circumflex and grave accents;
  • Arabic vowel marks;
  • Hebrew vowel points.

Two marks still count: the acute accent and the diaeresis, in Greek and in Latin script alike. A term typed with no accents at all can miss a record whose stored form carries one of these. It does not matter how your keyboard produces an accented letter — as one key or as letter plus accent — search treats both the same.

Some languages use marks as part of a letter's identity rather than as accents — the Scandinavian å, the Turkish dotted and dotless i, Vietnamese tone marks. For fields in such languages, your environment can keep every mark significant: search then finds that field's content only when your term carries the same marks as the stored form. This is set per field — the platform suggests a setting from the language it detects in each field, and your environment administrator confirms or changes it.

One nearby tool is stricter than search: the table's Filter visible rows… box matches text as it appears in the rows, so marks count there. Type the form exactly as written, or use quick search instead.

Why a search matched — or missed​

Each quick search result shows which fields your term matched. Read that line: it tells you whether the native form, the transliteration, or the translation caught your term — and, when a result surprises you, which form is responsible.

When a record you expect does not come back, work through the likely causes in order: an acute accent or diaeresis the stored form carries and your term omits; a form that is empty on that record; a field outside your environment's search configuration; a field set to exact matching. Find a record when search returns nothing walks each case with its fix.

When one form is empty​

Search matches what is written. If a record's transliteration field is empty, no transliterated term will find it — the native form still works, and the rest of the record is unaffected. The same holds inside a field that holds several values: each value is searchable when it has text, and an empty one is not there to match. Filling the missing form is the whole fix; the record becomes findable that way as soon as the value is saved.

What readers see on published pages​

Published pages show your text as you stored it, in its original script — the reader's layout and typography render it; nothing transliterates it for display.

A field that holds several values shows them all together on the published page, joined into one line — for example, several translations read as "Genitals, Penis, Sexual organ" and a transliteration alongside its native form as "aidoion · A'da' Al-tnasul". A project can instead set such a field to show one chosen value per record on its published pages — the Greek value on a Greek record, say — but showing them all is the default.

A project can publish more than one browsable index of its entries — by transliteration and by original script, for example — and readers switch between them. Index rows can show the transliterated form, the original-script form, and a short gloss together. In Greek and Latin index lists, an entry beginning with an accented letter is grouped under its base letter — an entry starting with an accented alpha lists under Α — while the row still displays the full accented form. Fields set to exact matching keep their marks in browse lists, and other scripts are listed as written. See Public reader and Browse entries by index.

Which form serves as an entry's heading, and where translation and transliteration sets sit on the page, is part of your project's publication setup — if the arrangement does not suit your corpus, contact your environment administrator.

Troubleshooting​

SymptomLikely causeFix
A Greek term typed without breathings finds the record, but the same term without its acute accent does not.Breathings are set aside in matching; the acute accent still counts.Retype the term with its acute accent.
A transliterated search misses a record you can see in the table.The transliteration field is empty on that record, or it is not searchable.Open the record and check the transliteration field. Find a record when search returns nothing covers each case.
Arabic or Hebrew text in a multi-value editor writes left-to-right.The row's language is not set to a right-to-left language.Pick Arabic, Hebrew, Persian, Urdu, or Aramaic from the row's dropdown; the value box switches direction.
