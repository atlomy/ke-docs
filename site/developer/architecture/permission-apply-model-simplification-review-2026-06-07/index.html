Permission / Apply-Model Simplification Review — 2026-06-07

Status: RATIFIED by owner 2026-06-07. Applied as ADR-035 Amendment 4 (the clause + loud inline "SPECIFIED — NOT ENFORCED" deferral markers) and ADR-057 marked Superseded. It is an amendment + a collapse, not a new ADR — the smell that triggered it ("a new ADR to undo friction an earlier one created") argues against adding more architecture, not less. See [[feedback_new_adr_to_undo_complexity_is_a_smell]]. The bug-fix code remains gated behind the two live caveat checks below ("no code lands until they are answered").

Evidence base: a file:line-cited audit of ADR-035 vs the merged v2 code (the apply/permission stack), run 2026-06-07. The hypothesis under test — the model is heavier than current single-researcher-pilot requirements — is now largely confirmed by code, with two runtime caveats flagged below.

The real finding: spec/code drift, not just over-engineering​

The framing that matters is not "the model is over-built" (a judgment call). It is spec/code drift: a large part of ADR-035's apply governance is specified on paper but enforced nowhere in code. That reframes the work — and the near-miss — sharply:

ADR-057 would have implemented the wizard's conformance to a policy that nothing enforces. We nearly wrote a new ADR to make the wizard obey an ADR that only exists on paper.

So the fix is not merely "remove complexity." It is doc-honesty: align the documented policy with what the code actually runs and actually needs, and mark the remainder as honestly deferred. That is harder to argue against than "let's simplify" — it is correcting a documentation defect, not trading away design.

ADR-035 specifies an elaborate stack — capability flags, named bundles, a Flow B two-step, three risk tiers, a §4/§4.1 sensitivity floor (sandboxed draft → blanket-deny prefilter → dynamic phrase + 30s delay), require_separate_review_authority, high_risk_apply_policy, comfort dials, permission snapshots. The audit found that most of the apply-governance surface is specified but not enforced:

Requirements reality: ADR-035's own ratification note states all three pilots "start as single-contributor at import time" and that §4.1 is therefore the primary path. Typical fresh-import proposals (ARCHETYPE/COLUMN/RELATION on a tenant with no prior entities) classify LOW — i.e. the demoralizing "155 still need a person" wall was overwhelmingly additive work that needs no second human. The genuinely-destructive operations (the real safety target) are a minority: archetype reassignment over populated data, slot overwrite, and RESTRUCTURE drop/hoist (epistemic/services/proposals/risk.py:125,175,206,243-251).

The decision (proposed): the simplest model​

For the actual actor — a single researcher who is also the tenant admin (the bootstrap user holding the tenant-admin bundle) — the apply model collapses to:

  1. Manual "Looks good" on a LOW/MEDIUM proposal is terminal (→ APPROVED, with the undo bar), exactly mirroring what the comfort-dial path (stage3_auto_apply_proposals) already does. No second human, no parked SCHOLAR_APPROVED step, no capability-flag gate — because none of those are enforced today and none add safety for a sole actor. This removes the F41 wall.
  2. Risk is still recomputed at apply (recompute_proposal_risk / RiskClassDivergence) — kept, because it is actor-count-independent and catches tenant-state drift. The legacy one-step approve_proposal (persistence.py:310-353) must not be the vehicle, since it skips the recompute; route through the recompute path.
  3. HIGH-tier (genuinely destructive) still requires the dynamic phrase (§4.1 Layer 3) — the one realized destructive-op protection. This is the must-keep safety floor; it stays regardless of contributor count.
  4. "Continue to choices" batches step 1 across all confirmed low/medium proposals (the F30 group-coded UX), routing each through the same recompute + tier check — a batched invocation of the per-proposal path, not a status-flip shortcut.

That is the entire model the current pilots need. Everything below is deferred, not deleted.

Explicit decision: does the common path read capability flags at all? — No.​

This is the decision that shrinks the model rather than just simplifying it. Once manual low/medium apply is terminal-with-undo unconditionally (matching comfort-dial), the apply decision for the common path is risk tier, full stop — low/medium applies; HIGH routes to the phrase gate. The path does not read can_apply_*. Justification, not assertion:

  • The comfort-dial automatic path already applies low/medium with undo gated on comfort level + risk + auto_approved, never on can_apply_* (epistemic/services/proposals/persistence.py:526-549). Mirroring it means the manual path needn't read those flags either — and they aren't read on any apply path today regardless.
  • For a single-contributor tenant there is no lower-privileged actor to gate against: Django staff/admin access already gates who can reach the wizard at all. A per-proposal capability check adds nothing.

Consequence — F51 stops mattering for the apply decision. The permission snapshot becomes pure audit (record who applied, for the trail), not a gate. So the "does the snapshot populate?" question (caveat 1) no longer blocks the common apply path — it only affects audit completeness. Capability-flag enforcement on apply is part of the deferred multi-contributor work, built when a reviewer-only contributor who must be prevented from applying actually exists.

Drop / defer (speculative for single-researcher pilots) — keep the columns, defer the logic​

  • require_separate_review_authority + high_risk_apply_policy enforcement — keep the persisted fields (cheap future-proofing); defer building the apply branch ADR-057 would add. They encode a multi-contributor policy no current tenant uses.
  • §4.1 Layer 1 (sandboxed draft) + Layer 2 (blanket-deny prefilter) — defer (zero code today). The shipped substitutes — risk-recompute + dynamic phrase + undo — cover the realized safety. One caveat to keep on the table: if any live import flow can emit a HIGH RESTRUCTURE drop/hoist proposal, a minimal deterministic guard there has genuine single-user value and should not be blanket-deferred. (Runtime question — see caveats.)
  • can_apply_* as a live terminal-vs-parked gate — simplify away; keep the flags as audit-snapshot data (forensic value). Do not lump in can_review_proposals, which is load-bearing.
  • The capability × recomputed-tier gate and the "researcher==admin" special-case proposed in ADR-057 — unneeded once step 1 makes low/medium manual apply terminal for the sole actor. (ADR-057's Alternatives reasoning — don't gate on the role-name; don't use the recompute-skipping one-step path — is preserved here as the rationale for clauses 2–3.)

Recommended disposition of the ADRs​

  • ADR-057 → collapse / supersede. It is mostly conformance; its genuinely-new content is absorbed as: (a) a bug-fix (make manual low/medium apply terminal for a sole capable actor, mirroring comfort-dial), (b) an ADR-035 amendment (below), (c) a small UX spec for the batched "Continue to choices". No standalone ADR. Mark ADR-057 Superseded by this review's outcome once the amendment lands.
  • ADR-035 → amend (Accepted ADRs are amended in place in this repo): add a clause stating that for a single-contributor tenant, low/medium manual apply is terminal with undo (the §4 floor already blesses this for the automatic path; this makes the manual path consistent), and that the common apply path does not read capability flags (the decision above). Mark the deferred machinery loudly, inline, per element — annotate §4.1 Layers 1–2, require_separate_review_authority / high_risk_apply_policy enforcement, and the can_apply_* apply-gate each with a visible "SPECIFIED — NOT ENFORCED — deferred until a multi-contributor tenant exists" marker, right where each is described. This is not optional polish: the drift re-accumulates the moment a future contributor reads the spec as enforced policy — which is exactly how we got here. If the deferral is not legible in the document, this same audit gets re-run in six months. The marker is the immune response.

Caveats (runtime questions the static audit could not settle)​

  1. F51 / snapshot population. PR #495's request-helper path is dead in production (request.user.membership is never set; data_import/admin.py:2719-2732). Population depends entirely on the DB-lookup fallback (persistence.py:52-81), which needs the acting wizard user to have an active non-public-schema TenantMembership. The "feature exists, never populates" symptom is most consistent with the wizard actor lacking a provisioned membership — which is itself evidence the capability machinery isn't wired to the real actor. Given the explicit decision above (the common path does not read capability flags), F51 no longer gates the apply decision — the snapshot is now pure audit. So this drops from a build-blocker to an audit-completeness concern: confirm the snapshot populates if/when you want a complete who-applied trail, but it does not block shipping the simplified apply path.
  2. Destructive HIGH-tier reachability. Whether a live import can actually emit a HIGH drop/hoist (or other genuinely-destructive HIGH) proposal determines how much the deferred Layer-2 blanket-deny is worth — and whether the HIGH-tier phrase gate itself is worth building right now. If those destructive ops cannot occur in the current wizard, the phrase guard is protecting something that can't happen, so even it is defer-not-build until the destructive op becomes reachable. A data/runtime question, not a code-shape one.

These caveats gate the build, hard. Do not write the high-tier path on the unverified assumption that a destructive op exists — verify reachability live first. Both are checkable in a short live session, and no code lands until they are answered.

Caveat-check results (2026-06-07, post-ratification) — build UNBLOCKED, scoped​

Caveat 2 — destructive HIGH reachability: partially reachable; the phrase guard stays, and it does NOT gate the bug-fix.

  • HIGH RESTRUCTURE patterns = {SUPPORTING_TABLE_DISPOSITION, BIDIRECTIONAL_LOOKUP_MISSED} (epistemic/services/proposals/risk.py:206-209). BIDIRECTIONAL_LOOKUP_MISSED is emitted by the live detector (restructure_detector.py, builder.py:724); the only literal DROP is in a fixture, not the live path.
  • But all RESTRUCTURE proposals never auto-apply regardless of risk class (risk.py:230-231, the two-track gate) — so the simplified low/medium terminal path never touches them.
  • HIGH ARCHETYPE/COLUMN ops (reassignment over populated data, slot overwrite — risk.py:125,175) are unreachable on a fresh import (nothing populated) and only arise on a re-import over existing data.
  • The HIGH-tier dynamic phrase guard already exists (data_import/admin.py:3197, enforced :9642) and has reachable inputs → keep it, not defer-not-build; no new high-tier code needed.
  • ⚠ Non-blocking follow-up: confirm whether BIDIRECTIONAL_LOOKUP_MISSED / SUPPORTING_TABLE_DISPOSITION are genuinely data-destructive or merely reinterpretation — the names suggest the latter; if so their HIGH class is conservative (safe direction).

Caveat 1 — F51 snapshot population: downgraded to audit-completeness, NON-blocking by the ratified decision (the common path reads no flags → snapshot is pure audit). Confirm membership provisioning when wiring the who-applied trail; it does not gate the bug-fix.

Net: the bug-fix is unblocked and tightly scoped — make the manual low/medium non-RESTRUCTURE "Looks good" terminal-with-undo via the recompute path (mirroring the comfort-dial path). RESTRUCTURE keeps its two-track review; HIGH keeps the existing phrase guard; no new safety code is written.

Evidence packet — Spec 0047 R7: read sits behind a REVIEW capability (2026-06-11)​

Fed in from the Workspace Search & Read build + live walk (Spec 0047 T5.3):

  • The read path is gated by can_review_proposals. Both workspaceSearch (atlomyapp/graphql/schema.py, require_capability_from_info(capability= "can_review_proposals")) and the new workspaceSearchFacets facet-metadata endpoint reuse the same gate. Searching/reading working data — a pure READ — requires proposal-review authority. A researcher who can read but not review cannot use the section at all. That is the R7 category mismatch in one line: there is no read capability; review authority is the de-facto read grant.
  • Archetype scope piggybacks on the same flag. _workspace_search_allowed_ archetypes narrows results by permissions_jsonb.scope.archetypes — scope semantics again attached to a review capability rather than a read one.
  • The UI now surfaces the gate honestly (capability banner: hidden collection count = configured searchable tables − returned groups), so whatever this review decides, the section will show the boundary rather than silently drop rows — i.e. the surface is ready for either resolution.
  • Implication for the simplest model: if the ratified direction is "the common path reads no capability flags" (§ above), the search/read gate is the largest remaining read-side consumer of capability flags. Options when this review lands: (a) keep one coarse "workspace member" gate for the whole working-data read surface (matches the single-researcher pilot reality), or (b) introduce a real read capability and stop overloading can_review_proposals. Either way, the current state — review authority as the implicit read grant — is the kind of accidental layer this review exists to simplify.

Next steps (if ratified)​

  1. Owner ratifies the simplest-model decision (steps 1–4) + the defer list.
  2. ADR-035 amendment (clause + deferred-layer markers); ADR-057 marked superseded.
  3. Bug-fix PR: manual low/medium apply terminal for the sole capable actor via the recompute path; batched "Continue to choices" (F30 UX). Verify the F41 wall is gone on a live single-researcher import.
  4. Confirm caveat 1 (provision/verify the wizard actor's membership) and caveat 2 (RESTRUCTURE reachability) live.
