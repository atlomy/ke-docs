New Engineer Architectural Onboarding

Audience: Engineers joining KE (Knowledge Environments)

Goal: In ~30 minutes, understand how KE thinks, not just how it’s built.

Note on naming: The platform is KE — Knowledge Environments. Atlomy Atlas is the original software the platform grew out of, now one tenant alongside others (visionis, jpp, …). "Atlomy" remains the brand of the founding tenant; "KE" is the platform name. Older prose below may still say "Atlomy" when referring to the platform — read in that historical context.

This is not a framework tour. It is a mental model.

0. Why This Document Exists (5 minutes)​

Most platforms fail not because of bad code, but because good engineers make locally reasonable decisions that violate global structure.

KE is different. It has a strong architectural spine. Your job is not to memorize it — it’s to internalize how decisions are made.

If you remember only one thing, remember this:

Canonical structure is shared. Interpretation is tenant-specific.

Everything else follows.

1. The Two Worlds You Are Working In (5 minutes)​

Atlomy deliberately separates two kinds of truth:

1.1 Operational Truth (Stable, Controlled)​

Purpose: Keep the platform running safely.

Lives in:

  • Django Admin (admin.atlomy.org)
  • Canonical PostgreSQL schemas

Includes:

  • Tenants
  • Users
  • Permissions
  • Canonical schema
  • Infrastructure settings

Characteristics:

  • Changes are rare
  • Governance is strict
  • AI does not act here

Think of this as the laws of physics.

1.2 Epistemic Interpretation (Fluid, Human-Governed)​

Purpose: Help humans model, curate, and evolve knowledge.

Lives in:

  • React SPA (app.atlomy.org)
  • Epistemic database layer

Includes:

  • Knowledge entities
  • Ontologies
  • AI suggestions
  • Researcher workflows

Characteristics:

  • Changes are frequent
  • AI assists but never decides
  • Humans approve transitions

Think of this as how different cultures describe reality using the same physics.

2. The Epistemic–Canonical Lifecycle (7 minutes)​

Knowledge in Atlomy does not start canonical.

It flows.

2.1 Lifecycle States​

All epistemic entities have a database-enforced state machine:

DRAFT → AI_PROPOSED → HUMAN_REVIEW → APPROVED
   → APPLYING → APPLIED_TO_CANONICAL
   → (or) REJECTED / DEPRECATED

Key rules:

  • AI may propose
  • Humans approve
  • The system executes

No shortcuts.

2.2 What Crosses the Boundary?​

Only when all of these are true:

  • Human approval
  • Known blast radius
  • Migration path exists
  • Provenance is recorded

If any are missing → it stays epistemic.

Guideline: When in doubt, keep it epistemic.

3. Ontology Is Explicit (Not a Frontend Hack) (5 minutes)​

Tenants do not share vocabulary.

They share structure.

3.1 Archetypes vs Labels​

  • Archetype: TERM, BLOG_POST, MODEL
  • Label: "Lemma", "Concept", "Article"

These mappings live in the database:

tenant_ontologies
  tenant_id
  archetype
  label
  label_plural

Never hardcode labels.

Ever.

3.2 Why This Matters​

Because ontology drift:

  • Is real
  • Is inevitable
  • Must be queryable

If you put it in JSON or React config, you’ve hidden it.

Hidden ontology becomes technical debt.

4. Hybrid Ontology: Relational + JSON (5 minutes)​

Atlomy does not believe in:

  • Rigid schemas everywhere
  • JSON chaos everywhere

Instead:

4.1 The Rule​

Tables define what can exist. JSON defines how it is expressed.

4.2 What Goes Where​

Relational:

  • Status
  • Confidence
  • Approval
  • Relationships
  • Anything governance touches

JSON:

  • Tenant-specific fields
  • Experimental structure
  • AI-proposed extensions

If you put governance in JSON, you are bypassing governance.

5. APIs Are Contracts, Not Internals (4 minutes)​

5.1 GraphQL​

Used for:

  • Epistemic reads
  • Graph-shaped data
  • UI-driven queries

GraphQL is the epistemic contract.

Frontend types come from it.

5.2 REST​

Used for:

  • Mutations
  • Approvals
  • File uploads
  • Side effects

Never use REST because it’s "simpler".

Use it because the operation changes state.

6. What This Architecture Prevents (3 minutes)​

The system is designed to make certain mistakes structurally impossible:

❌ Letting AI approve changes ❌ Hardcoding tenant labels ❌ Skipping governance for speed ❌ Treating epistemic structure as SQL schema ❌ Using frontend config as source of truth

If you feel friction, that’s intentional.

7. How to Make Decisions Here (3 minutes)​

Before proposing a change, ask:

  1. Does this affect canonical structure or epistemic interpretation?
  2. Does it change what exists or how it’s viewed?
  3. Does this need a new ADR, or extend an existing one?
  4. Is this reversible?

If it touches principles → ADR. If it touches behavior → code.

8. Final Mental Model (2 minutes)​

Atlomy is not a CRUD app.

It is:

  • A governed knowledge system
  • With AI as an assistant
  • Serving multiple epistemic worldviews

Your job is not just to ship features.

It is to preserve the separation that makes this possible.

Welcome aboard.
