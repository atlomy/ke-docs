ADR-018: Retire NocoDB integration + V1 data_wizard import surface

Date: 2026-05-07 Status: Approved Deciders: Atlomy Account (user authorization 2026-05-07), assistant Related: ADR-002 (Hybrid Ontology), ADR-010 (Parser-First / LLM-Second), ADR-012 (Tenant Config via Runtime Pipeline), ADR-015 (Native React Tenant Admin), ADR-017 (Slot Config as Tenant-Authoritative Manifest) Supersedes: docs/developer/architecture/NOCODB_INTEGRATION_ADR.md (the "Atlomy-NocoDB Integration Journey" memo) and docs/developer/architecture/data_wizard_nocodb_refactor.md (the V1 data_wizard refactor plan).

Context​

NocoDB was introduced in late 2025 (Sprints 5–12) as the Working layer of a Working → Canonical → Published architecture. It carried two concerns:

  1. External source-of-truth surface for scholar-facing edits, with FDW + webhook + sync wiring back into Django.
  2. Schema-suggestion AI workflow (SchemaSuggestion rows + ChartDB/DrawDB visualizers) for proposing tenant-data → archetype mappings.

In parallel, the V1 data_wizard third-party app provided a CSV upload + ETL surface for the Atlomy Atlas dictionary, mapped onto V1 Lemma/Reference models through data_wizard.register(...) + nocodb-backed import jobs (data_import.ImportJob, data_import.ImportTemplate, data_import.api.DataImportViewSet).

By 2026-05-07 the v2 architecture had moved past both:

  • Canonical onboarding pipeline is now MappingProject + MappingProposal (ADR-010), driven by the parser-first / LLM-second wizard (templates/admin/ke/import_wizard.html).
  • Importers (atlomyapp.management.commands.import_coda_epistemic, epistemic.management.commands.import_xlsx, epistemic.management.commands.import_mysql) are CLI-driven and write directly to EpistemicEntity with identity-aware re-import (--merge-replace, ADR-017 Phase 2.A).
  • Tenant editing surface is the KE Admin Overlay (Phase 0–12, May 2026) on top of TenantArchetypeFormConfig (ADR-017), not a NocoDB base.
  • Schema visualization is the React schema visualizer at /dbvisualizer/schema/ introspecting the live database.

The NocoDB sync logs, schema suggestions, and data_wizard runs were empty across all tenants. The integration's only remaining role was placeholders: sidebar navigation, dashboard tiles, dead URL routes, and stale ADR references.

Decision​

Retire the NocoDB integration and the data_wizard third-party app entirely.

Removed code:

  • nocodb/ Django app (admin, models, services, signals, tasks, urls, views, templates, migrations).
  • Root-level NocoDB scripts: reset_nocodb.py, fix_nocodb_fdw.py.
  • docker-compose.nocodb.yml and the nocodb service block in docker-compose.yml.
  • data_wizard + data_wizard.sources from INSTALLED_APPS; the DATA_WIZARD config block; the /data-wizard/ URL.
  • V1 NocoDB upload pipeline in data_import/: views.py, tasks.py, serializers.py, widgets.py, validators.py, api/views.py, api_serializers.py, wizard.py, services/nocodb_importer.py, the V1 React import-wizard bundle under data_import/static/, and the V1 admin templates under data_import/templates/.
  • data_import.ImportJob and data_import.ImportTemplate models. data_import.MappingProject / MappingProposal survive — those are the canonical wizard models.
  • atlomyapp/management/commands/restore_atlomy_tenant.py (V1 atlas restoration via NocoDB working DB).
  • atlomyapp/management/commands/seed_schema_review.py and atlomyapp/tests/test_schema_review.py (NocoDB SchemaSuggestion seeding/tests).
  • NocoDB-only tests under tests/ and tests/verification/: schema-adaptation, webhook flow, archetype detection, conflict resolution, idempotency, relationship detection, working-db tenant-constant pin, sprint-12 verifications, AI-schema verification, onboarding verification, sprint5-6 verification, backend-final verification.
  • SPA legacy import-wizard page (spa/src/pages/import-wizard/) and the legacy NocoDB schema-review entry (spa/src/apps/schema_review/App.tsx); the active mapping-project review (spa/src/apps/schema_review/{index.tsx,MappingProjectReview.tsx,ProposalRow.tsx,components/}) survives — that's the canonical wizard's review UI.
  • atlomyapp/data_wizard_enhancements.py (orphaned data_wizard admin enhancement shim).
  • populate_db.py and index.py root-level V1 sample-data + Elasticsearch fixture scripts.
  • The LLMMappingService class from data_import/mapping_services.py (only consumed by the deleted DataImportViewSet); LanguageProcessor is preserved.

Surgical edits — NocoDB references stripped from: settings (INSTALLED_APPS, beat schedule, sidebar, env vars), urls.py + urls_public.py (registrations + admin index), atlomyapp/views.py (TenantCreateView no longer provisions a NocoDB workspace), atlomyapp/dashboard.py (sidebar tiles + KPIs), atlomyapp/graphql/schema.py (NocoDBTableMappingType, SchemaSuggestionType, schema_suggestions resolver), atlomyapp/management/commands/provision_roles.py, the tenant-create template, monitoring/{collectors,dashboard}.py (sync-health + AI-suggestion sections), dbvisualizer/services/optimizer.py (LLM client → rule-based fallback), the introspector's exclusion list, the docker-compose Directus configs (DB_EXCLUDE_TABLES), epistemic/services/* comment trail, tests/conftest.py (NocoDB fixtures + signal disconnect + initial migrate), the lint scripts, and .pre-commit-config.yaml.

Consequences​

Positive:

  • ~25 fewer Python modules + ~5MB of data_import/static/ JS bundle gone.
  • Three docker services retired (nocodb, nc_data volume, docker-compose.nocodb.yml orchestration file).
  • Sidebar/navigation aligned with the canonical workflow (Mapping Projects + Proposal Queue, no more dead NocoDB tiles).
  • Lint surface shrunk: data_wizard_ table-prefix rule retired from the dbvisualizer introspector; NocoDB allow-list paths retired from scripts/lint_no_tenant_vocabulary.py + scripts/atlas/check_no_tenant_hardcode.py + scripts/atlas/check_three_layer.py.
  • Dev-environment-setup simplified: no more NocoDB JWT secret, no more port 8080 contention.

Trade-offs:

  • Tenants who previously edited via NocoDB lose that surface. The KE Admin Overlay is the replacement; it's slot-driven and tenant-config-aware. No tenant currently relied on NocoDB for production workflows.
  • The Working layer of the original three-layer architecture (Working → Canonical → Published) no longer has an external authoring surface — EpistemicEntity is the canonical layer and is now also where authoring happens (via the slot-config-aware admin overlay). If a future requirement reintroduces an external Working layer (e.g., a new no-code-DB partner), the three-layer contract guard at scripts/atlas/check_three_layer.py can be re-extended.
  • monitoring/ lost its sync-success and DLQ metric collectors; both files are stubbed and ready for v2 substrate metrics (MappingProject throughput, telemetry rollups).
  • atlomyapp.Job + JobAdmin + atlomyapp/management/commands/add_data.py are preserved — V1 SPA lemma pages still read from Elasticsearch, and add_data is the canonical Coda → ES ingestion command that Job rows track. The NocoDB-specific --working-db-name branch (and read_working_table_dataframe import) was stripped from add_data.py; the Coda + local-CSV ingestion paths remain. Rewiring the V1 SPA to read from EpistemicEntity directly is a separate v2 milestone (tracked in roadmap, not in this ADR).

Database:

The user authorized cleaning our db and reimporting if needed the data. Migrations were rewritten (data_import/migrations/0001_initial.py no longer references data_wizard or nocodb); the legacy tables (nocodb_*, data_wizard_*, data_import_importjob, data_import_templates, atlomyapp_job) will be dropped at the final-stage DB reset. Directus tenant configs (docker-compose.directus-{jpp,tenant}.yml) had their DB_EXCLUDE_TABLES lists trimmed accordingly.

Alternatives considered​

Considered: Keep NocoDB as a no-op shim with empty migrations, in case a future tenant needs it. Rejected: Adds permanent maintenance cost (lint allowlists, docker config, migration graph) for a surface no tenant uses. ADR-018 explicitly closes the door; if the use-case returns, a fresh integration ADR is the right entry point.

Considered: Retire data_wizard but keep nocodb for the schema-suggestion / DrawDB visualizer. Rejected: The schema visualizer's NocoDB tie-in (SchemaSuggestion-driven prompts) was never wired to the active wizard. The canonical visualizer is the React schema-graph (/dbvisualizer/schema/), introspecting the live DB; NocoDB added no value.

Considered: Stage the removal across multiple sprints to absorb tenant-side surprise. Rejected: All NocoDB tables were empty across all tenants. Two-stage commit ordering (Stage 1 = data_import legacy + data_wizard; Stage 2 = nocodb + Job + SPA + monitoring + tests + docs) keeps the diff reviewable without dragging out the calendar.

Implementation​

Two commits on branch experiment/v2-anchor-and-seamless-edit:

  • Stage 1 (76d36f7b): data_wizard + V1 NocoDB upload pipeline (41 files, 5930 deletions).
  • Stage 2 (this commit): nocodb Django app, atlomyapp.Job, SPA legacy pages, monitoring/dbvisualizer/scripts surgical edits, ADR-018 + retirement notices on superseded docs.

Stage 3 (DrawDB removal + React schema visualizer rewire to live DB) tracks separately under user-driven scope expansion 2026-05-07.
