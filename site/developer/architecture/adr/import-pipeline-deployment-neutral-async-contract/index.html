ADR 054: Import Pipeline — Deployment-Neutral Async Contract

  • Status: Accepted (ratified 2026-06-03 after a dual-prong adversarial stress-test — see § "Stress-test absorption")
  • Date: 2026-06-03
  • Deciders: Premshay (platform owner, ratifying), assistant
  • Context source: Spec 0040 async/materialize work; an external (Codex) architecture consult; a 2026-06-03 dual-prong stress-test (a code-grounded adversarial-research workflow — 44 findings/33 confirmed across 53 agents — plus a NotebookLM round: prescriptive + open critique + debate + explainer). Relates to Spec 0010 (Cloud Deployment Framework), the 2026-05-26 Event-Substrate design (Drafted, awaiting ratification), ADR-037, ADR-047, ADR-048.

Ratification note (2026-06-03). The Proposed body was stress-tested by two independent prongs before acceptance. Both recommended ratify-with-amendments; the amendments are folded into the Decision / Implementation / Consequences below and the raw dispositions are recorded in § "Stress-test absorption". The core decision (a deployment-neutral seam contract; monolith-or-split by config) survived; the amendments sharpened the storage seam (it was under-specified and would have re-introduced the very bug it targets), demoted the event-emission seam out of the committed set, and made several optimistic claims honest. Five priority/numeric calls are left open for the owner (see § "Open questions").

Context​

The import wizard is a multi-stage human-in-the-loop pipeline: upload → parse → AI/heuristic mapping proposals → human review → materialize (bulk-write entities + relationship edges) → downstream readers. Spec 0040 made materialize always-background to escape a ~120s gunicorn timeout (a 385k-edge import blew it). Tracing the pipeline surfaced that "async" today rests on implicit single-host couplings that only work because web, worker, and an in-process drain thread share one process/host:

  • Artifacts are staged to container-local /tmp (upload_storage.py → tempfile.gettempdir()) and materialize replays them from that local path (epistemic/services/materialization/source_rows.py, via resolve_staged_upload_path). There is no object-storage client in the staging/replay path. The replay consumers are path-native: csv_bundle_parser.load_csv_bundle_table_data(directory: Path) requires a real directory (directory.is_dir() + glob); mysql_parser.SqlDumpIntrospector._open() suffix-sniffs .gz on a path string and opens a local named file; xlsx_parser calls openpyxl.load_workbook(path, read_only=True) (needs a seekable file).
  • Dispatch is a DB job ledger drained by a Celery beat every 2 minutes, 1 job/tenant/tick (run_import_wizard_scheduler_round → execute_next, which claims due PENDING jobs) — plus an in-process daemon thread spawned in the web request for immediate drain. Under ATOMIC_REQUESTS=True (settings.py:425) the daemon is spawned inside the still-open request transaction and claims on a separate connection where the just-enqueued PENDING row is not yet committed — a latent race the dispatch decision below fixes.
  • The external LLM proposal call runs inside the parse step, synchronously in the HTTP request for small uploads (routing is by file size); behind the ProposalLLM abstraction (get_proposal_llm()), Bedrock today, swappable.
  • The BYOK Coda credential is re-prompted at approval and stashed in a short-TTL (600s) encrypted Redis key (ADR-037).

Two forces make this a rare opportunity rather than a patch job: (1) the deployment layer is greenfield and uncommitted — cloud provider unsettled (uncertain academic→spinout trajectory; provider-neutral is the binding requirement), IaC tool OpenTofu-first but not locked (prod main.tf is a ~35-line module invocation against a platform_stack module whose body lists resources-to-add but defines none yet; S3 is "intended in IaC, unwired in code"), Spec 0010 explicitly "modular monolith first, split only where operational evidence justifies." (2) The LLM is swappable (a convenience, not a commitment). Because deployment follows software here, the import pipeline must not assume a deployment shape, cloud, IaC tool, or LLM vendor — it must emit the requirements a deployment then satisfies.

Decision​

The import pipeline commits to a deployment-neutral async contract: it must run correctly both as a single-process modular monolith and with a split worker tier, on any cloud, under any IaC tool, with any LLM vendor — switchable by configuration, not code. We place the right seams now (cheap in greenfield, expensive to retrofit) and defer scale machinery (adoptable later behind the same seams). The pipeline guarantees:

  1. Artifacts via a storage abstraction — write + read + replay + DELETE (not just write/read). The replay consumers are path-native, so the store must expose a localize affordance (open(key) stream or fetch_to_local(key) → Path) and replay must localize an object-backed artifact into a per-job ephemeral temp before handing the local path to the existing parsers (or refactor parsers to streams). A worker buffering a shared-store artifact into its own ephemeral temp is deployment-neutral — the bug being killed is cross-process implicit /tmp sharing, not all local temp use. Artifacts resolve through a distinct named storage alias (STORAGES['import_artifacts']), never default_storage (which is platform-pinned to S3Boto3Storage('atlomy-dev-files'), the media surface). Keys are tenant-schema-prefixed so isolation is a property of the store (today it is incidental to /tmp path-containment). Lifecycle/retention (import_job_retention.py, today shutil.rmtree/Path.unlink/stat/rglob + a resolve(strict=True)+.parents traversal guard) routes deletion/existence/size/listing through the abstraction too — else an object-backed artifact orphans (object storage never self-reaps). The seam may stay the Django Storage API (open/listdir/delete/exists/size cover it); a narrow domain ImportArtifactStore interface is an optional expression, not a required replacement. The local-FS backend keeps current monolith/dev behavior (additive: path OR stream).
  2. Task execution via an explicit, swappable executor (IMPORT_TASK_EXECUTOR = immediate | broker) — monolith-vs-split is config, not a hidden assumption.
  3. Dispatch on DB commit (transaction.on_commit → enqueue a per-job task — which does not exist yet; only the beat scanner does), ledger as the source of truth for state/progress/retries. Beat is re-labelled to a sweeper but must retain a full due-PENDING re-dispatch scan (today execute_next provides this — recovering orphaned-PENDING jobs whose on_commit publish was lost), in addition to requeuing stale RUNNING. The on_commit dispatch also fixes the daemon-races-commit race (it can only fire after the row commits).
  4. LLM as a background stage behind ProposalLLM — off the request path, provider-swappable. (Today only the Bedrock provider is implemented; a second vendor is a small code-add behind the existing factory, not pure config.)
  5. Worker enters tenant schema_context from a payload tenant id. This is a TODO, not yet satisfied: the job carries no tenant field today and the daemon reads the request-local connection. Making it explicit is part of the contract.
  6. Job state + progress are explicit and durable in the ledger (the ledger-derived status half is real — SourceRowReplayPlan/classify_project_source_row_replay, consumed by the SPA). Honest scope: the existing materialization_in_progress: bool cannot represent FAILED vs never-ran vs COMPLETED — a richer terminal-status surface is still owed. OpenTelemetry is aspirational (absent from code/requirements) — it is an evidence-gated adoption, not a placed seam.

The earlier seventh "event-emission seam" is demoted from the committed Decision — see Consequences/Neutral and the absorption note. Materialize already writes the ledger/audit; we do not couple import code to the unbuilt Approach-B substrate taxonomy now.

Alternatives considered​

  • Status quo (beat-poll + in-process daemon + local /tmp). Rejected: confirmed latent multi-process artifact bug; couples interactive work to a 2-min scheduler; runs heavy work in the web process; blocks the worker-tier split Spec 0010 wants.
  • Full distributed redesign now (Temporal/Hatchet, microservice split, transactional outbox, object-storage ops, versioned-snapshot publication). Rejected as pre-paying — no operational evidence yet; each is adoptable later behind the seams. (The stress-test's devil's-advocate argument that only the storage seam should be committed and the rest dropped was rejected on verification: the executor switch, on_commit dispatch, and LLM seam are all cheap-now/expensive-later and confirmed.)
  • Commit to a cloud/IaC now and wire to it (e.g. "wire materialize to the S3 bucket"). Rejected as wrong-layer: bakes a deployment choice into import code while deployment is uncommitted; the storage abstraction preserves the capability provider-neutrally.

Consequences​

Positive​

  • Fixes the latent multi-process artifact bug and unblocks Spec 0010's worker-tier split (the materialize timeout becomes the operational evidence, once the couplings are gone).
  • Preserves deployment optionality: monolith ↔ split, OCI ↔ GCP ↔ AWS ↔ Azure, OpenTofu ↔ Terraform, Bedrock ↔ Vertex ↔ direct-API — config/infra choices, no import-code change.
  • Moves the external LLM call off the request path regardless of upload size.

Negative​

  • Adds indirection now (storage interface + localize, explicit executor, per-job task) — real upfront cost, justified by the greenfield-retrofit asymmetry.
  • A storage abstraction backed by local FS in dev and object storage in prod introduces a behavioral-divergence surface (object stores lack POSIX seek/byte-range semantics; the localize step is what bridges it) — must be tested in both modes.
  • Two residual dual-write gaps, both deferred-but-now-documented: (a) on_commit dispatch vs broker publish (covered by the beat's full-PENDING re-dispatch scan, not a transactional outbox); (b) the inline-Coda credential path is itself a non-transactional dual-write — the DB job row (Postgres) + the inline key (store_inline_materialize_key, Redis /2) — so a rollback after the Redis write orphans a secret-at-rest for up to the TTL (a residual not enumerated in ADR-037).
  • Acknowledged residual couplings to honesty-check the "provider-neutral" claim: the cross-worker inline-credential transport (ADR-037) hard-pins to Redis specifically (CACHES default RedisCache, LOCATION via the Celery broker URL); the LLM seam currently has only the Bedrock provider implemented.

Neutral​

  • The in-process daemon is retained as the explicit immediate executor for the monolith/dev profile; its only sin was being implicit (and racing the request commit, which on_commit fixes).
  • This ADR sets a software contract; concrete backend/topology/IaC choices remain Spec 0010's, informed by it. IMPORT_TASK_EXECUTOR=immediate|broker maps cleanly onto Spec 0010's monolith-first/split-on-evidence stance.
  • The seventh event-emission seam is tracked as future alignment, not a committed property: materialize already writes the ledger/audit; if/when the Approach-B substrate is ratified, the emission points are where they should be, but we do not author substrate-shaped payloads now.
  • BYOK handling (ADR-037) is unchanged in mechanism; faster dispatch only shortens the window between approval re-prompt and materialize start (it does not tighten the worst-case TTL). The retry-after-TTL-expiry hole is closed today only by an undocumented coupling — every Coda inline-load failure (incl. transient HTTP blips) is wrapped as SourceRowLoadError/non-retryable — a forward-constraint to preserve, not lean on.

Implementation notes​

Phased, each step independently shippable and provider-neutral:

(b) Distinct named alias STORAGES['import_artifacts'], never default_storage. (c) Tenant-schema-prefixed keys, non-colliding with media/static. (d) Retention via the abstraction (delete/exists/size/listdir; traversal guard → key-prefix containment). (e) Local-FS default for monolith/dev parity. Falsification AC (preserve from the original): the same import materializes identically with IMPORT_TASK_EXECUTOR=immediate (one process) and =broker (separate worker) with the storage backend pointed at a non-shared location — a worker with no access to the web process's local FS still replays correctly via the abstraction.

The default immediate is behaviour-preserving for the monolith; broker is a config flip once a worker tier + P0 increment-B land. A deferral is not complete until its trigger is observable.

Finding W — materialize hot-path profiling evidence (2026-06-09)​

Records evidence under the existing chunked materialize / worker-tier split deferral above (this does NOT re-open the Decision; it is the ADR-055 trigger evidence arriving). Finding W: a live materialize ran ~15 min, the DB connection sat idle-in-transaction 11+ min while django_app held ~59% CPU — i.e. a CPU-bound Python hot path, not DB-bound. py-spy was blocked (no SYS_PTRACE), so the hot path was pinned with cProfile on a synthetic materialize: a MappingProject over ~5000 PASSAGE rows + ~1000 TERM rows + an approved RELATION (TEXTS→VOCAB) generating 5000 typed edges, profiling only materialize_project (proposal-build/persist excluded). Harness: tests/integration/test_materialize_perf_probe.py (skipped by default; KE_RUN_PERF_PROBE=1 to run). cProfile inflates absolute wall time — rank by relative cost, not the raw seconds.

There are two structurally different hot paths; the live run could be either (no record settles first-import vs re-apply, and the diagnosis is consistent with both — a first import hashes one EntityRelationship per edge on the bulk_create path while the DB waits; a re-apply rewrites every row via bulk_update):

  1. Re-apply path (existing rows → versioned_bulk_update → Django bulk_update). This was the catastrophic one in the profile: the idempotent re-apply of identical data took 31.9s vs 7.4s for the initial materialize (4.3× slower to change nothing). Top cumulative cost was versioned_bulk_update = 27.0s, all inside Django bulk_update's CASE/WHEN expression machinery:

    • expressions.resolve_expression — 468,908 calls for 6000 rows (~78 calls/row), 19.1s cumulative — the O(rows × fields) fingerprint.
    • copy.copy — 468,910 calls, 5.2s; query.build_filter — 135,047 calls, 7.0s; _add_q — 133,040 calls, 10.0s. Django builds a giant CASE WHEN pk=… THEN <Value(jsonb)> per field per row and resolves/copies each JSONB Value — pure Python, DB idle. This is the single worst function observed: bulk_update of unchanged JSONB rows.

  2. First-import path (new rows → bulk_create + per-edge hash). RUN 1 (7.4s) was dominated by edges, not entities: _materialize_relationship_edges = 5.05s vs _materialize_entities = 2.28s. Within it: _stale_linkable_edge_consequences (relationship_materializer.py:325) is an N+1 — 1000 calls / 1000 source entities, 2.25s, one EntityRelationship query per source entity (→ ~385k queries at the documented 385k-edge incident scale); plus _entity_relationship_from_edge → compute_record_content_hash once per edge (5000 calls, ~0.79s, un-skippable, scales with edge count). The documented "385k-edge import blew it" lives here.

Scale extrapolation (honest): the 7.4s/31.9s figures are cProfile-inflated at 6k rows and do NOT reproduce 15 min. Django bulk_update cost is ~linear in rows at fixed batch_size, so the re-apply path extrapolates to the incident order-of-magnitude (~10²× rows ≈ tens of minutes). The first-import N+1 is linear in entities but its query count (385k) is the more direct match to the documented edge-count incident.

Phased plan​

  • Phase 1 — re-apply skip-unchanged (SHIPPED 2026-06-09, this branch). In versioned_bulk_update, write only the rows whose semantic content hash changed; the common idempotent re-apply (changed == 0) issues zero UPDATEs. Safe because every field in the caller's update list is covered by semantic_field_names (the hash inputs), so an unchanged hash proves the persisted row already matches — skipping its write is correct, not just an optimisation. Measured: RUN 2 31.9s → 6.28s (5.1×); versioned_bulk_update 27.0s → 0.57s (47×). Scope limits (explicit): this does not chunk, does not touch the single transaction.atomic envelope (service.py:129), and does not address the first-import edge path — it removes the re-apply rewrite cost only. Guards: test_source_versioning.py:: test_versioned_bulk_update_skips_db_write_when_nothing_changed + …_writes_only_changed_rows.
  • Phase 2 — first-import edge materialization (DEFERRED; the likely incident target, needs review). Batch the _stale_linkable_edge_consequences N+1 into a single grouped query over the rule's existing edges; the per-edge compute_record_content_hash is intrinsic but can stream. The chunked-commit seam lives here too: the per-table loop already batches bulk_create (batch_size=500), so the seam is moving transaction.atomic inside the per-batch loop — which must compose with a staged/pending projection + atomic publish flip (ADR-054 above) so partial graph state never leaks to readers, the status→MATERIALIZED flip + template-record stay last, and a mid-run failure leaves the project APPROVED. That coupling is why Phase 2 is review- gated, not a drive-by.
    • Phase 2a — stale-edge N+1 batched (SHIPPED 2026-06-09, branch perf/materialize-edge-n1-phase2). The _stale_linkable_edge_consequences per-source-entity query is replaced by ONE EntityRelationship query per linkable slot (_existing_linkable_edge_rows_by_source, subquery-scoped to the slot's entity set, grouped in Python; the per-entity function is kept as the correctness oracle). Synthetic 6k-row probe (cProfile-inflated): RUN 1 wall 7.79s → 5.23s, SQL statements 2145 → 147 (stale-edge SELECTs 1001 → 2; each per-entity query also carried a per-cursor SET search_path, hence the ~2×N statement removal); RUN 2 6.02s → 3.57s (2091 → 93). Guards: tests/integration/services/materialization/test_linkable_stale_edge_batch.py (O(1)-per-slot query bound + batched==per-entity full-dict equivalence + project-scope honor). Scope limits: transaction envelope untouched — Phase 2b (chunked commits) stays review-gated and Phase 3 (worker tier) stays deferred.
    • Phase 2b — chunked per-batch commits (SHIPPED 2026-06-10, branch perf/materialize-chunked-commits-2b; approved 2026-06-09 decision-log "Owner-delegated ratification batch"). materialize_project is no longer one atomic envelope. Commit seam: config seed in its own transaction → the synthetic-support pass as its own batch → one committed transaction per source table for entity writes (ENTITY_BULK_BATCH_SIZE=500 still bounds statement size within a table) → relationship pass + archetype-table seed keep their pre-existing own-transaction degrade contracts → the status→MATERIALIZED flip + import-template record stay LAST in their own final transaction, only after every batch succeeded. Semantics change, stated not hidden: workspace-ADMIN visibility is progressive — entities appear table-by-table while a run is in flight (accepted in the approval). The PUBLIC reader still sees nothing partial: projections stay DRAFT until the explicit publish path (ADR-047 two-axis gate; materialize never creates or publishes projections — guarded by a published_public_projection_qs assertion on a mid-run-failed run). Failure/resume contract: a mid-run failure leaves the project APPROVED (never MATERIALIZED); committed batches stand; the failed batch rolls back whole; downstream passes + the flip are skipped; the report returns completed=False (new MaterializationReport field, also in to_dict) with a loud MATERIALIZATION INCOMPLETE warning naming the failed table, its position (N of M), and the committed tables. Resume = simply re-run materialize_project: provenance.source_id identity matching + update_or_create config seeding + edge idempotency refresh committed rows in place and create the missing ones — no duplicates. Guards: tests/integration/services/materialization/test_chunked_commits.py (mid-run failure leaves APPROVED with table 1 committed; re-run completes without duplicates; public-gate assertion; success-path counts identical; transaction-wall probe asserting no single service transaction wraps two tables and the flip is last in its own block).
  • Phase 3 — worker-tier split (DEFERRED). Materialize runs today as a background thread in a gunicorn web worker. The ADR-054 dispatch substrate (per-job task + IMPORT_TASK_EXECUTOR=immediate|broker + sweeper) is already the seam; Phase 3 = dispatch materialize as a scheduled job on a worker tier, config-flipped, no import-code change. ADR-055 materialize_wall_ms / edge_count / entity_count are the un-defer triggers.

  • Storage seam was under-specified (HIGH, both prongs): "route through Storage" is not a drop-in (django-storages S3 has no path()); the 3 replay parsers are path-native; retention is FS-native; default_storage is S3-pinned to the media bucket with no tenant prefix. → seam #1 expanded to write+read+replay+DELETE + localize + named-alias + tenant-prefix (above). The workflow refuted the audio's "temp-download re-introduces the local-FS dependency" framing (worker-local ephemeral temp is fine) and the audio's "Django Storage must be replaced by a narrow interface" (it may stay Storage; narrow interface optional).
  • Event-emission seam is premature (both prongs, strong convergence): fixes no bug, removes no coupling, couples to an unbuilt substrate → demoted out of the committed Decision.
  • Beat-demotion would silently lose orphaned-PENDING recovery (HIGH, workflow): the sweeper must keep the full due-PENDING re-dispatch scan, not narrow to stale-RUNNING. → folded into seam #3.
  • Daemon races the request commit under ATOMIC_REQUESTS (HIGH, workflow): the on_commit dispatch fixes it; the current daemon is buggy. → Context + seam #3.
  • Honesty amendments (medium): OTel aspirational + terminal-status gap (seam #6); Redis binding + inline-credential second dual-write leg (Consequences); seam #5 tenant-locator is a TODO not satisfied; LLM-only-Bedrock; "13-line stub" → ~35-line module invocation.
  • Newly-named deferred seams: cancellation; scoped artifact-integrity checksum; per-project claim-lock as the real concurrency-idempotency gap.

Rejected over-claims (verified NOT to hold, recorded so they are not re-raised): "reject the per-tenant fairness deferral / noisy-neighbor starvation" — the deferral is correct (the cheap part is tenant-routing metadata, the machinery is rightly deferred); "only the storage seam fixes a defect, don't commit the other seams"; "IMPORT_TASK_EXECUTOR is premature scaffolding"; "the credential window tightened" (functionally unchanged).
