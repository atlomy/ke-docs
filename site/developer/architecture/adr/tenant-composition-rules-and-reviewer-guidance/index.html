ADR-008: Migration-Time Composition Rules + Reviewer-Authored Proposal Guidance

Date: 2026-04-26 Status: Proposed — time-bounded scope; sunsets when migration completes Deciders: Architecture team Related:

  • ADR-002 (Hybrid Ontology Relational+JSON) — provides the substrate
  • ADR-004 (Tenant Ontology Mapping) — adjacent concern; this ADR extends the mapping pipeline
  • ADR-009 (Platform-Native Entity Conventions and Relationship UX) — the post-migration concern
  • data_import/services/mapping_proposal_service.py — current AI proposal pipeline
  • data_import/services/tenant_hints/ — current per-tenant hints registry (aliases + heuristic boosts only)
  • epistemic/services/indexers/ — per-tenant indexer registry
  • docs/devlogs/2026_w17/2026-04-26_2030_universal-hybrid-materialization.md — slice-2 session
  • docs/context/partner_model.md 2026-04-26 entries — generalization-guard rule + scaffolding-not-architecture rule
  • atlomyapp/management/commands/add_data.py — v1 Atlas import showing the composition challenge concretely

Scope clarification (added after initial draft)​

This ADR is migration scaffolding, not platform architecture. It addresses a one-time concern: bringing legacy CSV/SQL-bundle data into epistemic_entities with reasonable archetype mappings. Once a tenant's data is materialized and ongoing edits flow through platform forms (per ADR-009), the composition_rules / reviewer_notes / convention-library machinery should be deprecated for that tenant — not grown.

The user's correction (2026-04-26): "this is important for migrating a csv db, but it isn't something that necessarily needs to stay forever … more wise would be to propose how to create the correct and simpler fields … or, more obvious — we should probably have the conventions inside the now smarter and better db."

ADR-009 is where the lasting architecture lives. This ADR exists because Atlas's first tenant has CSV/Coda.io lineage we have to ingest before we can offer rich entity forms — but every feature added here should ask: would this still matter post-migration? If no, keep it minimal.

Context​

The slice-2 AI mapping experiment (2026-04-26) materialized 6,321 EpistemicEntity rows from Atlas CSVs and produced 71 proposals from JPP's MySQL schema. End-to-end the universal hybrid (epistemic_entities) works.

But the experiment surfaced a third class of tenant-specific knowledge that the current proposal pipeline cannot handle: composition rules. These are conventions where a target field is synthesized from multiple source columns following a domain-specific grammar, not 1:1 mapped from a single source column.

Concrete examples (Atlas, classical philology)​

  • lemma_full: a citation form synthesized from Author + Treatise + Chapter + Page columns, e.g. "Aristotle, History of Animals, 17, 83". No lemma_full column exists in the source CSV.

  • Abbreviated reference rendering: in v1 the lemma page renders citations like:

    1. Arist., HA I, 17, p. 83 Balme (496a26)
    : the great vessel
    κατὰ μὲν τὴν μεγίστην κοιλίαν ἐξήρτηται τῇ μεγάλῃ φλεβί …

    This is built from (a) author-specific abbreviation rules (author_formats["Aristotle"]), (b) a separate abbreviation lookup table (abbreviated_references keyed by editor name), (c) the modern bibliography (Balme), and (d) the passage text. The rendered citation is a synthesis across four data sources.

  • Hyperlinks on hover: the abbreviated reference hyperlinks to author and treatise pages — those pages exist as separate v1 entities, which means the citation needs structured back-references to the entities it composes from, not just a plain string.

What the AI proposal currently does​

Today's MappingProposalService treats each source as a flat list of headers and asks: "which target field does each header map to?" The answer is a 1:1 alias mapping (Author → entity.name, Treatise → document.title, etc.). The AI cannot infer that (Author, Treatise, Chapter, Page) together synthesize a lemma_full field per a citation convention. It is not a mind reader.

Why this is universal, not Atlas-specific​

JPP has its own conventions:

  • Person naming with NAME_TYPE variants (birth name vs. throne name vs. alias) and Mongol-period transliteration rules
  • Project-scoped editorial visibility (per ADR-007)
  • Source citation conventions that differ from classical philology

Medieval-manuscript tenants have shelfmark conventions ([city] [library] [collection] [number]). Social-science tenants have field-coding conventions. Each is a standard within its field but not universal across fields.

Atlas's value is that these conventions are reusable. Without architectural support for composition + reviewer guidance + convention libraries, every new tenant onboarding rediscovers the same problem and the AI proposals stay flat.

Decision (proposed)​

Adopt three layers, building on the existing tenant_hints/ and indexers/ registry patterns:

Layer 1 — Composition rules in tenant_hints/​

Extend TenantHints with composition_rules:

@dataclass(frozen=True)
class CompositionRule:
    name: str
    target_field: str
    source_columns: tuple[str, ...]
    template: str          # "{Author}, {Treatise}, {Chapter}, {Page}"
    requires_lookup: str = ""   # optional secondary table key
    convention: str = ""        # name of an entry in the convention library
    applies_to_archetype: str = ""  # narrows when the rule fires (e.g., "PASSAGE")

Hooked into the proposal pipeline after AI mapping, before materialization. Rules synthesize the target field per row and add it to data (or a back-reference structure). The reviewer sees both the AI's per-column proposal AND the synthesized composite, and can edit either.

Layer 2 — Reviewer-authored guidance on proposals​

Extend MappingProposal with reviewer_notes: JSONField(default=list) storing structured directives from tenant admins:

[
  {"kind": "composition_hint", "fields": ["Author", "Treatise", "Chapter", "Page"],
   "target": "lemma_full", "convention": "classical_humanities_v1"},
  {"kind": "lookup_hint", "field": "Reference Abbreviated",
   "lookup_in": "abbreviated_references"},
  {"kind": "join_hint", "from_source": "ancient_words", "to_source": "lemma",
   "via": "lemma_word"},
  {"kind": "free_text", "text": "These three columns are usage examples, not separate fields."}
]

Reviewers add notes via the admin (and later the visualizer SPA). On next proposal regeneration, the LLM prompt incorporates the notes as additional context — turning the tenant's domain expertise into structured directives the AI can act on.

Layer 3 — Convention library​

A registry of named conventions tenants can opt into:

  • classical_humanities_v1 — Greek/Latin lemma + Liddell-Scott citation grammar + Aristotle/Plato author abbreviations + abbreviated_references lookup
  • prosopography_v1 — Person + name_type variants + project scoping (JPP's pattern from ADR-007)
  • medieval_manuscripts_v1 — shelfmark conventions
  • cohort_studies_v1 — clinical-cohort field coding

Tenants pick from the library AND/OR define their own composition rules in tenant_hints/. New tenants in classical philology don't have to re-discover what we already learned from Atlas.

Rationale​

  • Three patterns one architecture. This ADR mirrors the registry-with-tenant-implementations pattern already approved for tenant_hints/ (slice-2) and indexers/ (this session). The architectural cost is low because the pattern is proven.
  • Reviewer notes are a feedback channel, not a free-form chat. Structured directives let the same prompt work across regenerations and let composition rules be promoted to convention libraries when reused.
  • Convention libraries amortize discovery. Atlas's classical citation grammar is research; the next classics tenant uses it for free.
  • The generalization-guard rule still holds. Universal layer (mapping_proposal_service.py, archetype_contracts.py) stays tenant-neutral. All composition rules / conventions / hints live in tenant-specific modules.

Consequences​

Positive​

  • Closes the composition gap. v1 Atlas's lemma_full and abbreviated-reference HTML can be reproduced from epistemic_entities without hardcoding into universal code.
  • Tenants get a way to nudge AI proposals toward correctness without engineering changes.
  • Convention libraries become the canonical home for domain knowledge — discoverable, versionable, attributable.
  • The pattern extends cleanly to non-classical conventions (prosopography, manuscripts, social science, cohort studies).

Risks​

  • Convention library can become a dumping ground. Mitigation: a curation policy and ADR sign-off for library additions; per-tenant hints stay tenant-private until promoted.
  • Reviewer note schema can drift. Mitigation: a small reviewer_note_kinds enum + JSON-schema validation per kind.
  • Prompt context bloat. Reviewer notes increase prompt size. Mitigation: scope notes to the proposal's archetype + filter by relevance.
  • Composition rules can mask AI errors. A bad composition rule could hide an AI miss. Mitigation: surface both the per-column AI proposal AND the synthesized composite in the reviewer UI; never silently override AI decisions.

Out of scope​

  • ML-driven inference of composition rules (the AI proposing its own composition rules). Phase 2 candidate after the manual rule pattern proves out.
  • Cross-tenant convention sharing as a federated marketplace. Phase 3+.
  • A composition-rule DSL beyond Python templates. Start with Python; introduce a constrained DSL only if/when a non-engineer reviewer needs to author rules.

Open questions​

  1. Where does the abbreviated_references lookup live? A separate auxiliary_table row in the proposal pipeline? An EpistemicEntity rendering with archetype=REFERENCE_ABBREVIATION? A pure tenant-hints lookup dict?
  2. Re-prompting cadence. When a reviewer adds a note, do we re-run the LLM proposal automatically or wait for explicit "regenerate"?
  3. Convention versioning. classical_humanities_v1 vs. _v2 — semver? Date-stamped? Tenant locks the version?
  4. Reviewer-note approval. Can any tenant admin add notes, or only an "ontology lead" role (per ADR-007 sub-tenant workspace)?

Status & next step​

Status: Proposed (stub).

Next step: Full architectural evaluation in next session. Implementation in slice-3 alongside ADR-007's WORKSPACE archetype and the SQL-row materialization path.

This ADR was triggered by the user surfacing the v1 lemma_full / abbreviated_references composition challenge after seeing the slice-2 indexer require a tenant-specific join deviation (source_reference → source_work_name instead of the row_id join my prompt suggested) — and recognizing the same class of problem will recur for every classical-philology-style and prosopography-style tenant.
