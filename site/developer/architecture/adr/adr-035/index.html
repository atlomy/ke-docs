ADR-035: Tenant Contributor Permission Model

Operational confirmation: all 3 current tenants — Atlas / Visionis / JPP — start as single-contributor at import time, so §4.1 layered safety floor is the primary apply-pipeline path for the wizard, not the multi-contributor fallback. Jointly ratified with ADR-033.) Deciders: Atlomy Account, assistant, Codex (review pending) Context source: Spec 0017 architecture pass 2026-05-16 (comfort-dial role-model decision); user directive to dismantle strict scholar/admin separation in favor of a contributor-centric model Related: ADR-001 (epistemic/operational separation), ADR-010 (Flow B state machine — relaxes implicit "different humans" assumption), ADR-012 (config as data, not code), ADR-015 (tenant admin shell), ADR-016 (telemetry substrate — actor labeling), ADR-017 (slot config authority), ADR-033 (comfort dial — Sprint B gate), ADR-034 (staged commit + ImportTemplate), ADR-057 (import-wizard apply flow realizes §1 capability-gating + §4 floor as capability-gated terminal apply + batched review — 2026-06-07)

⚠ Amendment 4 — Apply-path reality + honest deferral (owner-ratified 2026-06-07)​

A file:line audit of this ADR against the merged v2 code (2026-06-07) found that much of the apply-governance surface specified below is enforced nowhere in code — capability flags provisioned but never checked at apply, require_separate_review_authority / high_risk_apply_policy write/display-only, §4.1 Layers 1–2 with zero code. This is spec/code drift, and it nearly caused a downstream ADR to make the wizard "conform" to a policy that does not run. The owner has ratified the following correction. Full analysis + rationale: docs/developer/architecture/permission-apply-model-simplification-review-2026-06-07.md.

Ratified decision (the model the current single-contributor pilots actually need):

  1. For a single-contributor tenant, manual low/medium "Looks good" is terminal-with-undo — consistent with the automatic comfort-dial path (ADR-033), which already applies low/medium gated on risk tier, not on capability flags. This is the §4 low/medium floor applied to the manual path.
  2. The common apply path does NOT read capability flags. There is no lower-privileged actor to gate against in a single-contributor tenant (Django staff access already gates wizard entry), and no apply path reads can_apply_* today regardless. The permission snapshot (applied_by_permission_level) is therefore pure audit, not a gate.
  3. The two enforced protections are kept: risk-recompute-at-apply (Spec 0011 F0b) and the §4.1 Layer-3 dynamic phrase on genuinely-destructive HIGH-tier ops — the latter only once those ops are confirmed reachable (build gate).

⚠ SPECIFIED — NOT ENFORCED — DEFERRED UNTIL A MULTI-CONTRIBUTOR TENANT EXISTS. The following are design record for the multi-person future, not current policy. Do not read the prose below as enforced; it is honestly deferred and must be built (with tests) only when a second apply-capable contributor is onboarded:

  • the can_apply_low/medium/high_risk flags as an apply gate (they remain valid as audit-snapshot data; can_review_proposals IS enforced and is not deferred);
  • require_separate_review_authority and high_risk_apply_policy enforcement (the fields persist; nothing branches on them);
  • §4.1 Primary layer (sandboxed draft / consolidated diff) and Second layer (blanket-deny prefilter) — zero code today.

Build gate (2 live checks before any apply-path code lands): (a) does the wizard apply-actor actually carry a provisioned TenantMembership (else the snapshot never populates); (b) can a genuinely-destructive HIGH op (e.g. RESTRUCTURE drop/hoist) even be emitted by the current wizard — if not, even the Layer-3 phrase guard is defer-not-build. ADR-057 is superseded by this amendment (it becomes a small bug-fix + this clause + a UX note, not a standalone ADR). The rest of this ADR is preserved as the design record; read it through the lens of this amendment.

Context​

V1 of KE (Atlomy Atlas) used Django Groups + Permissions for role management. User calibration: "very unrefined and hard to operate even with 7–10 users." V2 abandoned that model outright. The current v2 state is:

  • TenantMembership (customers/models.py:303-322) holds three operational-tier roles: ADMIN / EDITOR / VIEWER. No capability flags.
  • Flow B state machine (data_import/models.py:245-250): PROPOSED → SCHOLAR_APPROVED → APPROVED. State-driven, not role-driven. No DB-level constraint enforces "different humans" — the requirement was a UI convention in the Django admin templates.
  • Audit fields (scholar_reviewed_by, admin_applied_by, created_by, approved_by) are CharField traces, not FK gates.
  • ADR-010's "reviewer approves the proposal" framing is silent on whether reviewer and applier must be different humans.

The v4 import wizard (Spec 0017 rev 2) introduces a comfort dial whose authority boundary depends on the role model. The strawman ADR-033 v1 assumed strict scholar/admin separation; Builder correction reframes this:

"Who knows the research and the logic behind the database better than the researchers themselves? Teams like these usually work in collaboration. Each person could be a contributor, and the permissions may be wide for many of the team members."

Lived reality of research tenants:

  • Multi-contributor academic teams: PI + post-doc + lab/project manager + grad student.
  • Single-contributor tenants where the researcher is the admin.
  • Cross-institution collaboration: an external scholar from another KE who wants to contribute knowledge to a host KE (future scope).

The strict scholar/admin gate the strawman invoked was never actually enforced in the model — only in the UI flow. So this ADR is not relaxing a hard invariant; it is making the existing reality explicit, configurable, and safe.

Decision​

1. Capability-flag permissions; named roles are bundles (Builder 2026-05-17 amendment — Amendment 3.b)​

Permissions in v2 are capability flags on TenantMembership.permissions_jsonb (per ADR-012 config-as-data discipline). Capability flags ARE the foundation. Named "roles" — contributor, editor, external collaborator, reviewer, tenant admin — are user-facing bundles of capability flags, not discrete role tiers in their own right. A tenant may use the platform's default bundles, edit them, or compose custom bundles (per §2.1).

A single TenantMembership row carries two orthogonal axes:

  • Operational role (ADR-001 — existing field): ADMIN / EDITOR / VIEWER. Governs tenant settings, billing, user management, and infrastructure-level operations.
  • permissions_jsonb (new in this ADR): capability flags for epistemic work — proposal review, applying, undoing, slot config, permission management, recommender access. See §2 for the canonical flag list, §2.1 for the default bundle library, §3.1 for the bootstrap pattern.

The two axes are orthogonal: a single user can hold both. Operational roles do NOT inherit capability flags by default; capabilities must be explicitly granted (with the single-contributor bootstrap exception in §3.1).

'Contributor' is one named bundle among several, not a discrete role tier. The earlier framing of contributor as "primary epistemic-tier role" was a header drift that conflated bundle of capability flags with discrete role tier. Capability flags are the foundation; bundle names (including "contributor") are convenience presets.

Example bundles a tenant may use or customize (full default bundle library in §2.1):

  • Researcher-contributor (default for primary research staff): can review, apply low/medium-risk, manage templates, undo within window. Cannot apply high-risk, configure slots, or manage permissions without explicit tenant-admin opt-in.
  • External collaborator (scoped add/edit/remove without DB authorship): can review proposals, can apply low-risk additive changes only within scoped archetypes/slots (see §2 scope dimension), cannot apply medium/high-risk, cannot configure slots or templates, cannot manage permissions. Suitable for guest collaborators on a specific dataset or cross-institution scope (§6).
  • Reviewer-only (audit / external review): can review proposals (read + comment), cannot apply at any risk level. Suitable for advisory board members, external auditors, or pre-publication readers.
  • Tenant admin (bootstrap user + designated managers): full epistemic capabilities including high-risk apply, slot config, permission management. Typically pairs with operational ADMIN role for tenant-creating users (§3.1 bootstrap pattern).

A contributor with broad capabilities may drive a proposal from PROPOSED → APPROVED end-to-end as a single human, except for sensitivity-tiered safety floors (§4) which are mandatory regardless of permission set. [⚠ As enforced today (see Amendment 4): the apply path does not read can_apply_* at all — the common low/medium path is terminal-with-undo unconditionally; capability-flag gating is deferred until a multi-contributor tenant exists.]

User-facing copy discipline (per Amendment 3.a / Spec 0017 US-D.3 voice-override framework): bundle names, capability-flag labels, and help tips render in researcher-natural language, not platform vocabulary. Capability flags themselves are platform-canonical (can_apply_low_risk etc.) but their user-facing labels and help-text go through TenantArchetypeFormConfig.voice_overrides. Plain-language help tips per flag are required (e.g., can_apply_low_risk → label "Save additive changes" → help text: "Save additive changes like new entries or transcriptions immediately. Doesn't affect existing records.") The Sprint D permissions UI (Spec 0017 tasks.md US-D.5) implements this discipline.

2.1 Default bundle library + scope dimension (Builder 2026-05-17 amendment — Amendment 3.c)​

The platform ships four default bundles. Tenant admins may use them as-is, edit them, or compose custom bundles via the Sprint D permissions UI (Spec 0017 tasks.md US-D.5). Default bundle JSON lives in platform-canonical code; tenant overrides + custom bundles live in Tenant.permission_bundles (new JSONField, per ADR-012).

Scope dimension on capability flags: the optional scope field restricts capability flags to specific archetypes or slot combinations. Examples:

// External collaborator restricted to a single archetype:
{
  "can_review_proposals": true,
  "can_apply_low_risk": true,
  "scope": {
    "archetypes": ["TERM"]
  }
}
// Contributor restricted to two specific slots (e.g., visiting linguist
// adding translations and alt spellings to a specific lemma collection):
{
  "can_review_proposals": true,
  "can_apply_low_risk": true,
  "scope": {
    "slots": ["TERM.translations", "TERM.alt_spellings"]
  }
}

Absence of scope = unrestricted (capability applies tenant-wide). Scope composes with capability flags multiplicatively: a contributor with can_apply_low_risk=true AND scope.archetypes=["TERM"] cannot apply low-risk to non-TERM archetypes, regardless of risk_class.

Custom-bundle composition (Sprint D US-D.5): tenant admins compose custom bundles by (a) picking a default bundle as a starting point, (b) toggling individual capability flags, (c) optionally setting scope restrictions, (d) naming the bundle in researcher-natural language (via tenant's voice_overrides). Custom bundles are persisted on Tenant.permission_bundles and become selectable when adding new contributors.

User-facing copy for bundles: bundle names use researcher-natural language per Amendment 3.a / voice_overrides. The platform-canonical name researcher-contributor might surface to an Atlas user as "Lemma editor", to a Visionis user as "Finds cataloguer", to a JPP user as "Lexicon contributor". Capability-flag labels and help-tips are similarly tenant-customizable.

3. Tenant policy fields on Tenant​

  • [⚠ SPECIFIED — NOT ENFORCED — deferred until multi-contributor; see Amendment 4. The field persists but no apply-path code reads it.] Tenant.require_separate_review_authority (BooleanField, default false). When true, the same contributor cannot drive both SCHOLAR_APPROVED and APPROVED transitions on the same proposal regardless of permission flags. Default false matches collaborative reality.
  • [⚠ SPECIFIED — NOT ENFORCED — deferred until multi-contributor; see Amendment 4. Read/display only; no apply-path branches on it.] Tenant.high_risk_apply_policy (CharField, enum: dual_contributor_required | elevated_confirmation_allowed).   • Tenant.permission_bundles (JSONField, new in Amendment 3.c). Holds tenant-custom permission bundles composed via Sprint D UI. Platform-default bundles (§2.1) are inherited if permission_bundles is null or missing the default-bundle keys.

3.1 Bootstrap permission grant for tenant-creating user (Builder 2026-05-17 amendment — Amendment 3.d)​

The Q6 (operational/epistemic interaction) disposition flagged that the platform needs a bootstrap mechanism for the first epistemic-permission manager in a fresh tenant, so single-contributor tenants are not locked out of high-tier work by the default new-contributor permission set. This subsection specifies the mechanism.

The first-user-special pattern, similar to Django's createsuperuser: when a Tenant row is created, the user creating the tenant receives a TenantMembership row with full capabilities by default — the tenant-admin bundle (§2.1) overrides the default-new-contributor set's four false flags.

The mechanism:

  1. Tenant-creation flow: when a new Tenant row is created, the platform creates the first TenantMembership row for the creating user with:

    • role = ADMIN (operational tier)
    • is_bootstrap = True (new BooleanField on TenantMembership, default false)
    • permissions_jsonb set to the tenant-admin bundle (all can_* flags true)
    • No scope restriction

  2. First-user check: a Tenant has at most one TenantMembership row with is_bootstrap = True. Database constraint enforces uniqueness.

  3. Subsequent users: TenantMembership rows created via the tenant-admin UI default to whichever bundle the inviting admin selects (typically researcher-contributor for primary research staff, external-collaborator for guests, etc.) with is_bootstrap = False.

  4. Bootstrap role transfer: a bootstrap user can transfer the is_bootstrap flag to another contributor via the tenant-admin UI (e.g., if the original tenant-creator leaves the project). The transfer-target contributor must already have can_manage_permissions = true to receive the flag. The transfer is atomic — bootstrap moves in one operation; never duplicated.

  5. Bootstrap tenant-lockout prevention: a bootstrap user cannot remove their own can_manage_permissions flag without first transferring is_bootstrap to another contributor. A bootstrap user also cannot have their TenantMembership row deleted without prior transfer. This prevents the tenant becoming an orphan with no contributor able to manage permissions.

  6. Audit trail: every bootstrap transfer records transferred_by (previous bootstrap user), transferred_to (new bootstrap user), transferred_at, and the consolidated permission state before/after on MappingProposal.applied_by_permission_level snapshot mechanism.

Why this matters for v1 single-contributor tenants (Builder 2026-05-17 operational confirmation): all three current tenants — Atlas, Visionis, JPP — begin as single-contributor at import time. The bootstrap user IS the researcher AND the tenant admin. They need full capability flags (including can_apply_high_risk, can_configure_slots, can_manage_permissions) to drive the v4 wizard end-to-end. Without this mechanism, the default new-contributor permission set would lock them out of exactly the workflows the wizard is designed to enable.

For the bootstrap user specifically, the §4.1 layered safety floor (sandboxed draft → blanket-deny prefilter → dynamic phrase) IS their compensating safety mechanism for high-tier applies — they have can_apply_high_risk = true but no second contributor for dual review, so the layered floor provides structural protection per ADR-035 §4.

Multi-contributor transition: once a second contributor is invited and granted can_apply_high_risk = true, the Tenant.high_risk_apply_policy field (§3) automatically derives to dual_contributor_required (since ≥ 2 contributors with that flag now exist). High-tier applies switch from the §4.1 layered floor to dual-contributor review. The bootstrap user retains is_bootstrap = True but their high-tier path is now the dual-review path, not the layered floor. The layered floor remains available as a fallback if the second contributor is unavailable.

4. Sensitivity-tiered safety floor (mandatory regardless of permission set)​

The proposal-class taxonomy from Spec 0017 + the risk_class recompute from Spec 0011 (F0b-risk-recompute-at-apply guard) jointly determine the tier:

High-tier classification is the floor, not a ceiling. A tenant may also enforce dual review for medium-tier via require_separate_review_authority=true.

4.1 Layered safety floor for single-contributor high-tier applies (Codex 2026-05-16 amendment)​

Dynamic phrase typing + 30s delay + audit emphasis alone is not sufficient as the primary gate for single-contributor high-tier applies. Addressing approval-fatigue concerns surfaced in R3 critique: any active-cognition gate that runs at every high-tier apply eventually shifts the habituation surface rather than eliminating it — the researcher learns to skim the phrase, complete it, and proceed. The gate needs structural compensation, not only behavioral compensation.

The safety floor is three layers in order:

[⚠ SPECIFIED — NOT ENFORCED — zero code today; deferred until multi-contributor / until destructive HIGH ops are confirmed reachable; see Amendment 4.] Primary layer — Sandboxed draft schema / draft apply plan. High-tier AI / canonical / efficiency proposals first produce a draft schema or draft apply plan in a sandboxed staging area. The researcher reviews one consolidated diff (the cumulative effect of all queued high-tier proposals — schema changes, slot-config edits, destructive merges) before promotion to canonical tables. This collapses N individual habituation surfaces into one deliberative review surface; researchers see what the cumulative effect looks like, not a per-proposal phrase-typing exercise. The sandboxed draft is durable (persists across sessions) and reviewable by any contributor with can_review_proposals, so multi-contributor tenants can use the same primary surface for dual-review.

[⚠ SPECIFIED — NOT ENFORCED — zero code today; deferred; see Amendment 4.] Second layer — Blanket-deny prefilter for mathematically destructive or policy-forbidden changes. Before the sandboxed draft reaches the researcher, a deterministic prefilter rejects changes that are (a) mathematically destructive in ways the policy has decided are never reversible (e.g., destructive migration of canonical PII columns; mass-delete operations exceeding configured row-count thresholds; schema operations that destroy provenance lineage); or (b) policy-forbidden for the tenant's Tenant.high_risk_apply_policy configuration. These never reach the researcher's review surface — they fail upstream with an audit-trail entry explaining why. The researcher cannot approve what the policy already denied.

Third layer — Dynamic phrase typing + 30s reflection delay + audit-trail emphasis. For surviving high-tier actions that clear the prefilter and ride in the consolidated draft diff, the elevated-confirmation gate applies as the final commit-press step. The phrase remains context-specific and dynamic per the original §4 rationale (a static "I confirm" string would habituate at the typing level). The 30s reflection delay remains as backup throttle. The audit-trail entry records the phrase typed verbatim, the consolidated diff, and the policy decisions taken by the prefilter.

Dynamic phrase language discipline (Builder 2026-05-17 amendment — Amendment 3.a): the phrase must (a) reflect the destructive action being authorized, not a routine structural-fact recognition, AND (b) use researcher-natural language, not platform vocabulary. Researchers confirming a destructive action should read a phrase that names the consequence in their domain terms — not "rows", "archetype", "committed", "foreign key", or other platform-internal naming that triggers disengagement.

The platform provides default researcher-natural phrase templates per high-tier proposal class in plain English. Tenants override per their domain via TenantArchetypeFormConfig.voice_overrides (Spec 0017 US-D.3 / Sprint D) so each tenant sees terminology that matches how their researchers actually talk about their data.

Language rules (apply to default templates AND tenant voice_overrides):

  • Use researcher domain vocabulary: "entries", "records", "finds", "lemma entries", "catalog entries", "fragments" — NOT "rows", "table cells", "JSONB columns", "documents in the index"
  • Name the consequence in research terms: "I'm permanently removing data I worked on" — NOT "I'm executing a DELETE statement"
  • Avoid platform-internal type names: never use EpistemicEntity, TenantArchetypeFormConfig, archetype, slot, MappingProposal in the phrase
  • Avoid DB-engineer framing: "already saved" or "I've already entered" — NOT "already-committed"; "data I've already entered" — NOT "committed rows"
  • Quantity in researcher-meaningful units: entries / records / cards / fragments / finds — NOT rows / objects / serialized payloads
  • The previous illustrative phrase change patient_id to foreign key was withdrawn because FK detection on patient_id is parser-surface-structural (low-tier) per ADR-033 §1.1 — it is not itself a destructive operation. Only the destructive migration of already-saved patient_id values would surface in the layered safety floor. The corrected phrase shape names the work the researcher could lose ("12,433 records I've already saved"), not the structural mechanism ("rows", "FK", "migration").

Together, the three layers compose: the prefilter prevents the worst classes of destructive operation from ever needing researcher attention; the sandboxed draft converts per-proposal habituation into one consolidated deliberative review; the dynamic phrase + delay + audit emphasis remain as the final intentional act. Multi-contributor tenants continue to enforce dual contributor confirmation; single-contributor tenants get the three layers as compensation for absence of a second human.

5. Audit-trail extensions on MappingProposal​

Existing fields retained for backward compatibility, augmented with:

  • confirmation_method (enum): single_contributor_typed | dual_review | elevated_confirmation | auto_applied_low_risk | auto_applied_medium_risk | comfort_dial_level_N (where N ∈ {0,1,2}). Indicates how the APPROVED transition was reached.
  • applied_by_permission_level (JSONField): forensic snapshot of the applying contributor's permissions_jsonb at apply time.

6. Cross-institution contributor scope (v1 boundary)​

V1 of this ADR is internal-team only: contributors are TenantMembership rows of the host tenant. Cross-institution collaboration (an external scholar contributing to a host KE) is deferred to a future ADR (likely co-filed with ADR-034's deferred cross-tenant template federation).

The schema anticipates external identity without locking it in:

  • permissions_jsonb carries no FK to local-tenant User — external identity claims could be added without migration.
  • Audit fields are CharField (external-identity-friendly).
  • A future ContributorOrigin field on TenantMembership can distinguish home_tenant vs external_federated contributors.

External contributor data sovereignty (when v2 lands): an external contributor's signals attribute to their home tenant, not the host. Host data does not pool back to the external's home tenant automatically.

7. React tenant-admin shell wiring (ADR-015)​

A new Contributors & Permissions panel in the React tenant-admin shell exposes:

  • TenantMembership row CRUD with a permissions_jsonb editor (per-flag toggles + tenant-policy editor).
  • Read-only audit-trail viewer over confirmation_method + applied_by_permission_level columns on Flow B history.
  • Visible distinction between operational-tier role (ADMIN/EDITOR/VIEWER) and epistemic-tier permissions.

Panel access gated by can_manage_permissions.

Alternatives considered​

  1. Keep strict scholar/admin separation (ADR-033 v1 strawman). Rejected: imposes ceremony with no safety gain in single-contributor / small-team tenants. V1 calibration shows 7–10 users was already too painful to operate.
  2. Revive Django Groups + Permissions. Rejected: per ADR-012 config-as-data, permissions are tenant runtime data, not hardcoded code. Also conflicts with ADR-001 operational/epistemic separation.
  3. Three-role enum on TenantMembership (contributor / reviewer / viewer). Considered. Loses per-capability granularity. JSONB permission set composes roles arbitrarily without schema migration.
  4. Parallel ContributorPermission table FK'd to TenantMembership. Considered. Cleaner per ADR-001 but requires JOIN on every authorization check. JSONB on TenantMembership chosen for simplicity.
  5. No sensitivity-tier safety floor — let permissions alone govern. Rejected: high-tier proposals (cross-row structure changes, mass deletes) need a uniform safety guarantee even when a single user has every permission. The elevated-confirmation gate preserves safety without requiring a second human.

Consequences​

Positive​

  • Single-contributor tenants get a usable flow without imposed ceremony.
  • Multi-contributor academic teams (PI + post-doc + grad student) work collaboratively without arbitrary scholar/admin gatekeeping.
  • High-tier proposals retain a safety floor regardless of team size.
  • Schema anticipates cross-institution collaboration without locking it in.
  • Permissions are runtime tenant data (per ADR-012), not hardcoded Django Groups.
  • ADR-033's "authority boundary" question (Open Q2) collapses naturally onto contributor permissions + sensitivity tier.

Negative​

  • Migration adds permissions_jsonb to TenantMembership + two fields to Tenant + new audit fields on MappingProposal. Backfill required.
  • Django admin templates that currently render "scholar approve" / "admin apply" as separate gated screens need to be updated to render the contributor permission view.
  • Tenants that have been operationally enforcing the "different humans" UI convention need to be migrated thoughtfully (default require_separate_review_authority=true on migration if their history suggests it).
  • JSONB auditability cost: permissions buried in TenantMembership.permissions_jsonb are harder to audit than a normalized permission table. A compliance officer asking "who held can_apply_high_risk between dates X and Y" must parse JSONB across many rows rather than join a single ledger table. Compensating mechanism: the applied_by_permission_level JSONField on MappingProposal (§5) records a forensic snapshot of the applying contributor's permission state at apply time. Audit tooling queries the snapshot — not the live state — so the historical record of "what permissions did the actor hold when they pressed apply" is preserved at write time. This trades live-state auditability for apply-time forensic durability; the latter is the question compliance actually asks ("was this destructive change authorized?"), not the former ("what permissions are active right now?").

Risk​

  • Backfill default for require_separate_review_authority matters. Default false matches the new contributor model but may surprise tenants whose workflow assumed two-human separation. Mitigation: per-tenant opt-in during migration; notify current admins.
  • Sensitivity-tier classification of proposal classes is partly subjective. Coordination required between Spec 0017 proposal taxonomy (this ADR) and Spec 0011 risk_class recompute (Codex's lane).

Open questions (resolved 2026-05-16 per Codex review — architecture-pass amendment pass)​

  1. Migration default for require_separate_review_authority — preserve current UI convention (true) or match new contributor-centric default (false)? Resolved 2026-05-16 (Codex review): New tenants default false. Existing tenants default true when history or current UI convention suggests two-human separation; otherwise require tenant-admin acknowledgement during migration.
  2. Sensitivity-tier classification location — platform-canonical default in code (per Spec 0017 proposal taxonomy) or per-tenant override allowed? Resolved 2026-05-16 (Codex review): Platform-canonical default from proposal class + risk_class_at_apply. Tenants may raise strictness, not lower below the platform floor.
  3. Elevated-confirmation gate specification — Resolved 2026-05-16 (Codex review): Per Codex review, not fully resolved by the original §4 dynamic-phrase-as-primary framing. The resolution is the layered safety floor added in §4.1: dynamic phrase typing is the third layer (final intentional act), not the primary gate. Primary is sandboxed draft schema / consolidated diff review; second is blanket-deny prefilter for mathematically destructive or policy-forbidden changes; third is dynamic phrase + 30s delay + audit emphasis. See §4.1 for the full layered model. The previous illustrative phrase change patient_id to foreign key was withdrawn — FK detection is parser-surface-structural per ADR-033 §1.1, not itself destructive. Acceptable phrases reflect genuinely destructive actions (e.g., migrate patient_id values across 12,433 already-committed rows).
  4. External contributor identity claim shape — when cross-institution federation lands, what's the identity payload? OAuth claim with verified email + institutional affiliation? ORCID-backed? Resolved 2026-05-16 (Codex review): Defer to federation ADR. Likely OIDC + verified email + institutional affiliation, with ORCID optional where scholarly identity matters.
  5. can_manage_permissions granularity — single flag or split into can_invite, can_modify_existing, can_remove? Resolved 2026-05-16 (Codex review): Single flag for v1, with audit trail. Split into invite/modify/remove only when a tenant needs that distinction.
  6. Operational/epistemic role interaction — Resolved 2026-05-16 (Codex review): Independent by default. Migration default: a TenantMembership with operational role ADMIN inherits no epistemic capability flags. Each can_* flag must be explicitly toggled with audit trail. An IT admin who reboots servers should not by default inherit can_apply_high_risk — that would let server-rebooters rewrite the research data model. A tenant may opt in via the Tenant.high_risk_apply_policy field (or a future Tenant.admin_implies_epistemic boolean) to couple the two roles as a convenience, but the platform default keeps them decoupled. Bootstrap note: the first epistemic-permission manager is seeded explicitly at tenant creation (the tenant-creating user is granted can_manage_permissions and proceeds to designate other contributors) without implying that all operational admins inherit epistemic powers.
