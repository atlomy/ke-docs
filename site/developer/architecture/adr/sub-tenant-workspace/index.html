ADR-007: Sub-Tenant WorkSpace (editor-scoped data ownership)

Date: 2026-04-25 Status: Proposed Deciders: Architecture Team, JPP migration evaluation (/root/Projects/Atlomy/git/JPP/) Related:

  • ADR-001 (Epistemic-Operational Separation)
  • ADR-002 (Hybrid Ontology Relational+JSON)
  • ADR-004 (Tenant Ontology Mapping)
  • ADR-006 (Archetype Capability Contracts — in flight)
  • customers/models.py:15 (current TenantMembership)
  • docs/developer/architecture/rbac.md (current 4-role tenant-isolated RBAC)
  • JPP audit: /root/Projects/Atlomy/git/JPP/docs/validation/atlas-workspace-brief-2026-04-25.md (full proposal)

Context​

The platform's current RBAC model is tenant-scoped: a tenant has 4 roles (Viewer, Editor, Engineer, Admin) provisioned via provision_roles; an Editor can edit any record in their tenant's schema. There is no sub-tenant scope.

Several plausible tenant patterns require sub-tenant editor scoping:

  • Multi-team prosopographies (a tenant has multiple research teams; each team owns a subset of records)
  • Multi-cohort medical studies (cohort-X editors edit cohort-X records, not cohort-Y)
  • Multi-region historical projects (Project A team works on the Persian region; Project B on Central Asia; cross-edit is by exception)

The Jerusalem Prosopography Project (JPP), evaluated as candidate tenant #3 after Atlomy Atlas and VISIONIS, surfaces this pattern concretely:

  • 33 sub-projects in the legacy JPP MySQL schema
  • 73 explicit tblProject_permission entries
  • 18,694 persons_projects and 20,212 reports_projects scoping links
  • Day-to-day operational fact: JPP editors work within their own project's scope; Project A editors don't typically edit Project B's persons/reports.

Promotion threshold (per docs/research/archetypes/PROMOTION_RULES.md): a feature reaches the platform when ≥3 tenants need it. JPP is one. The argument here is that the pattern is plausibly relevant to multiple future tenants and that addressing it now (with JPP as design partner) is cheaper than retrofitting later.

A related but distinct concept exists in atlomy_chat: ResearchProject (app/services/project_management_service.py:28) is a single-user research notebook with LLM memory continuity. AMTA's Project is "Itay's private analytical workspace"; KE WorkSpace would be "the editorial team's shared data ownership scope." These are complementary, not competing — see §6 Open Decisions.

Decision​

Adopt a sub-tenant WorkSpace primitive in the platform. Native to KE Platform; not federated to AMTA.

Schema design​

# customers/models.py (new additions)
class WorkSpace(models.Model):
    id = models.UUIDField(primary_key=True, default=uuid.uuid4)
    tenant = models.ForeignKey(Client, on_delete=models.CASCADE, related_name='workspaces')
    name = models.CharField(max_length=200)
    description = models.TextField(blank=True)
    status = models.CharField(
        max_length=20,
        choices=[('active', 'Active'), ('archived', 'Archived'), ('suspended', 'Suspended')],
        default='active',
    )
    created_at = models.DateTimeField(auto_now_add=True)
    created_by = models.ForeignKey('auth.User', on_delete=models.SET_NULL, null=True, related_name='workspaces_created')
    archived_at = models.DateTimeField(null=True, blank=True)

    class Meta:
        unique_together = [('tenant', 'name')]


class WorkSpaceMembership(models.Model):
    workspace = models.ForeignKey(WorkSpace, on_delete=models.CASCADE, related_name='memberships')
    user = models.ForeignKey('auth.User', on_delete=models.CASCADE, related_name='workspace_memberships')
    role = models.CharField(
        max_length=20,
        choices=[('admin', 'WorkSpace Admin'), ('editor', 'WorkSpace Editor'), ('viewer', 'WorkSpace Viewer')],
    )
    created_at = models.DateTimeField(auto_now_add=True)

    class Meta:
        unique_together = [('workspace', 'user')]

JSONB convention on epistemic_entities.data​

Add workspace_ids as a conventional_jsonb_keys entry on the relevant ArchetypeContracts (ENTITY, DOCUMENT, EVENT, PASSAGE, ANNOTATION). Per ADR-006 (in-flight) the contract framework supports this.

# Example: ENTITY_CONTRACT additions
conventional_jsonb_keys = (
    # ... existing keys ...
    "workspace_ids",  # array<UUID>: sub-tenant scoping; empty/absent = tenant-wide visibility
)

A record with empty/absent data.workspace_ids is tenant-wide — visible to all tenant editors. This preserves backward compatibility for tenants without sub-tenant needs (Atlomy Atlas + VISIONIS today).

Tenant setting​

Add Tenant.enforce_workspace_scope: bool (default false). When true, users without a workspace membership lose general-tenant edit ability — they can only edit records whose data.workspace_ids includes a workspace they're a member of. When false, the tenant operates with tenant-wide editor permissions as today (no behavior change).

Permission middleware​

# atlomyapp/middleware/workspace_scope.py
class WorkSpaceScopeMiddleware:
    """Filter epistemic_entities querysets by user's accessible workspaces.

    If tenant.enforce_workspace_scope is False, no-op.
    If True, restrict queryset to records where:
      - data.workspace_ids is empty/absent (tenant-wide), OR
      - data.workspace_ids contains a workspace_id the user has membership in.

    Bypassed for users with the bypass_workspace_scope permission (platform admins).
    """

Frontend placement​

WorkSpace UX lives in the SPA (spa/src/apps/workspaces/), accessible from the user's account context. Not in Django Unfold admin for daily-use screens. Unfold admin gets a minimal WorkSpaceAdmin for platform-superadmin operations (suspend, hard-delete).

The SPA components borrow ~6 from atlomy_chat's next-app/src/components/projects/ after adapting user_id → members:

  • EnhancedProjectsPanel → workspace list sidebar
  • ProjectContextIndicator → header workspace badge
  • ProjectContextMenu → workspace switcher
  • ProjectOnboarding → guided creation
  • ProjectCollaboration → member-management UI
  • ContextAwareProjectCard → workspace card

Components attribute their AMTA origin in source comments; this is a one-time fork, not an ongoing dependency.

Rationale for not adopting AMTA's pattern wholesale​

AMTA's ResearchProject is single-user-owned (user_id: str field) with Claude-memory-tool storage. The single-owner model leaks into both API and UI in ways that resist multi-user adaptation. Lifting the frontend pattern is high-leverage; lifting the backend storage and ownership model is not.

Rationale for not federating to AMTA​

Authorization-via-external-service is an anti-pattern when both services are under our control. AMTA outage shouldn't break tenant edit-permissions checks. Hard runtime coupling to AMTA's API for a security-critical decision is rejected.

Consequences​

Positive​

  • Plausibly serves future tenants with multi-team / multi-cohort / multi-region patterns.
  • Default-permissive (tenants without enforce_workspace_scope=true see no change). Atlomy Atlas and VISIONIS continue to operate exactly as today.
  • Clean schema: WorkSpace is a sub-resource of Tenant; WorkSpaceMembership is a join. JSONB scoping reuses existing data field — no new column on epistemic_entities.
  • Frontend reuse from AMTA saves ~1–2 weeks of UI invention.
  • JPP becomes design partner, validating the abstraction against real workflow before locking the API.

Negative / risks​

  • Permission middleware adds query complexity — every queryset now filters by accessible workspaces (when enforce_workspace_scope=true). GIN index on epistemic_entities.data makes JSONB-array containment fast; should be benchmarked at JPP scale.
  • Component lift from AMTA creates a fork — AMTA components evolve; KE workspace components diverge over time. Acceptable as a one-time copy with attribution.
  • Naming risk: AMTA uses "Project," JPP uses "Project," Atlas docs sometimes use "Collection." Settling on "WorkSpace" requires a glossary update. Mitigation: this ADR fixes the platform term as WorkSpace; tenant-display labels remain free per TenantOntology.
  • Promotion-rule risk: only one tenant (JPP) currently demands this. The argument for promotion rests on plausibility of future tenants needing the same pattern. If wrong, the platform absorbs ~3–4 weeks of work that benefits one tenant. The mitigation is the default-false flag — Atlomy Atlas and VISIONIS pay zero cost.

Sprint placement​

  • Sprint 17 (proposed): Story 17.1 (data model + middleware, 8 pts), Story 17.2 (SPA UI lift, 8 pts), Story 17.3 (migration tooling + JPP validation, 5 pts). Total 21 pts. Fits one normal sprint.

Out of scope (explicitly)​

  • Per-record permissions finer than workspace-level. A record either is or is not in a workspace; an editor either is or is not a workspace member. "Editor X can edit Person 123 but not Person 456 in the same workspace" is not supported. If a tenant needs this, separate records into separate workspaces.
  • Cross-tenant workspace sharing. WorkSpaces belong to one tenant. Cross-tenant collaboration uses the federated discovery layer (docs/architecture/federated_discovery_spec.md), not workspace membership.
  • AMTA's ResearchProject stays single-user. KE WorkSpace and AMTA Project are complementary concepts; no convergence required.

Alternatives considered​

Alt 1 — JPP-specific workaround (Django Groups + JSONB filter, no platform change)​

Map JPP's 33 Projects to Django Groups; use data.workspace_id JSONB; per-tenant custom permission decorator. ~1 week JPP-side cost. Rejected because each future tenant would rebuild the same workaround; the cost compounds.

Alt 2 — Lift AMTA's ResearchProject wholesale (storage + ownership + UI)​

AMTA's pattern uses Claude-memory-tool storage and single-user ownership. Rejected because the single-user model is structurally incompatible with multi-editor scoping; the lift produces a half-converted shape with awkward edges.

Alt 3 — Federate to AMTA's /api/projects/* API​

JPP records carry data.amta_workspace_id; KE Platform queries AMTA at runtime for permission decisions. Rejected because authorization-via-external-service is an anti-pattern when both services are under our control. AMTA outage shouldn't break editor permissions.

Alt 4 — Defer until 3rd-tenant evidence​

Wait for a second non-Atlomy non-VISIONIS tenant to surface the same pattern before promoting. Considered. The tradeoff: JPP onboarding becomes slower (Alt 1's workaround) or blocked (no editor-scoping enforcement). Atlas team should confirm whether JPP's evidence + plausible-future-tenant argument is sufficient for promotion, or whether stricter promotion threshold applies.

Open decisions for the architecture team​

  1. Promotion judgment: does JPP's evidence alone satisfy the promotion threshold, or wait for a third tenant to surface the need?
  2. Default scoping behavior: enforce_workspace_scope defaults to false — agreed?
  3. Frontend split: SPA primary + Unfold for platform-superadmin only — agreed?
  4. AMTA component lift: lift the 6 components (with attribution) or build native? Recommendation: lift — saves ~2 weeks.
  5. Naming: "WorkSpace" vs "Project" vs "Collection" — recommendation: WorkSpace (avoids AMTA-Project collision; signals multi-editor-ownership semantics).
  6. AMTA relationship: AMTA's ResearchProject stays single-user — agreed? (No convergence required.)
