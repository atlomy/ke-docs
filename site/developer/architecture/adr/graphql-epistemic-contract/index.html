ADR-003: GraphQL as Epistemic Interface Contract

Date: 2025-12-28
Status: Approved
Deciders: Architecture Team, External Consultant

Context​

Epistemic queries in Atlomy are:

  • Deep: Fetch table + fields + relationships + archetypes + AI suggestions
  • Graph-shaped: Relationships are central to epistemic reasoning
  • UI-driven: Frontend needs vary (dashboard vs detail view)
  • Irregular: Each view needs different data shapes

REST APIs lead to:

  • Over-fetching (get whole object, use 20% of fields)
  • Under-fetching (N+1 queries to assemble view)
  • Tight coupling (client depends on server's data shape)

Decision​

We will use GraphQL as the primary interface contract for epistemic reads.

2026-05-11 Amendment: GraphQL Is An Application Contract, Not The Only Publication Format​

ADR-003 remains valid: GraphQL is the primary contract for live epistemic reads from React, AI, admin, and research tooling.

ADR-029 adds a publication boundary. Public Entry pages, institutional exports, federation resources, citation payloads, and archive packages may be rendered or serialized from EntryProjection / EntryPublishService without requiring a GraphQL request at public read time. GraphQL can still expose the same Entry contract for application clients; it is not the only durable publication format.

This distinction keeps GraphQL central for interactive KE tools while allowing minimal-computing and institutional requirements such as static HTML, versioned JSON, JSON-LD, CSL, IIIF manifests, RO-Crate, and federation harvest feeds.

Technology Stack​

  • Server: Strawberry GraphQL (Python, Django integration)
  • Client: Apollo Client (React, caching, optimistic updates)
  • Type Generation: graphql-codegen (GraphQL schema → TypeScript types)

Scope​

GraphQL for:

  • ✅ Epistemic entity reads (tables, schemas, relationships, archetypes)
  • ✅ Complex graph queries (table → fields → relationships → suggestions)
  • ✅ AI suggestion previews with provenance
  • ✅ Knowledge exploration (search, filter, facets)

REST for:

  • ✅ Mutations (approve, reject, apply schema changes)
  • ✅ File uploads (CSV import, error export)
  • ✅ Webhooks and background callbacks (source sync, indexing, projection rebuilds)
  • ✅ Governance actions (state transitions)

Rationale​

Why GraphQL Wins for Epistemic:

  1. Single query for complex views: Eliminate N+1 queries
  2. Client-driven: React decides what data it needs
  3. Self-documenting: Introspection for API discovery
  4. Type safety: TypeScript types auto-generated from schema
  5. Versioning: Add fields without breaking clients

Why REST for Mutations:

  1. Governance: State transitions are operations, not queries
  2. Simplicity: File uploads easier with multipart/form-data
  3. Caching: POST requests shouldn't be cached
  4. Webhooks: REST is standard for callbacks

Schema Design​

Example GraphQL Schema​

type Query {
  table(id: ID!): EpistemicTable
  tables(tenantId: ID!, archetypes: [Archetype]): [EpistemicTable!]!
  schemaSuggestion(id: ID!): SchemaSuggestion
}

type EpistemicTable {
  id: ID!
  name: String!
  archetype: Archetype!
  status: EpistemicStatus!
  confidence: Float
  
  fields: [Field!]!
  relationships: [Relationship!]!
  suggestions(status: [SuggestionStatus]): [SchemaSuggestion!]!
  
  metadata: TableMetadata
}

type SchemaSuggestion {
  id: ID!
  status: SuggestionStatus!
  aiModel: String!
  reasoning: String!
  confidence: Float!
  
  blastRadius: BlastRadius!
  provenance: Provenance!
  
  proposedChanges: [SchemaChange!]!
}

type BlastRadius {
  affectedRecords: Int!
  breakingChanges: [String!]!
  impactedRelationships: Int!
}

enum EpistemicStatus {
  DRAFT
  AI_PROPOSED
  HUMAN_REVIEW
  APPROVED
  APPLYING
  APPLIED_TO_CANONICAL
  DEPRECATED
  REJECTED
}

Example Query​

query SchemaReviewContext($tableId: ID!) {
  table(id: $tableId) {
    id
    name
    archetype {
      name
      color
      suggestedFields
    }
    fields {
      name
      type
      isRequired
    }
    relationships {
      type
      targetTable {
        name
        archetype { name }
      }
    }
    suggestions(status: [AI_PROPOSED, HUMAN_REVIEW]) {
      id
      status
      confidence
      aiModel
      reasoning
      blastRadius {
        affectedRecords
        breakingChanges
      }
      proposedChanges {
        type
        fieldName
        oldValue
        newValue
      }
    }
  }
}

This replaces ~7 REST calls with a single GraphQL query.

Knowledge Exploration Queries (Sprint 17+)​

The schema above covers schema management (Sprint 11–12). As the platform evolves toward knowledge exploration, the GraphQL schema will extend to include archetype-polymorphic entity queries — the kind researchers use to browse and explore tenant knowledge:

type EpistemicEntity {
  id: ID!
  archetype: Archetype!
  tenantLabel: String!             # Resolved via TenantOntology (ADR-004)
  tenantLabelPlural: String!
  status: EpistemicStatus!
  confidence: Float

  # Universal relational fields (from archetype contract)
  canonicalForm: String
  title: String

  # Tenant-specific flexible data (JSONB)
  data: JSON!

  # Relationships (archetype-governed)
  relatedEntities(kind: RelationshipKind): [EntityEdge!]!
  attestingDocuments: [EpistemicEntity!]!
  media: [EpistemicEntity!]!

  provenance: Provenance
}

type EntityEdge {
  kind: RelationshipKind!          # ATTESTS, ILLUSTRATES, AUTHORED_BY, etc.
  target: EpistemicEntity!
  confidence: Float
}

type Query {
  # Schema management (Sprint 12)
  table(id: ID!): EpistemicTable
  schemaSuggestion(id: ID!): SchemaSuggestion

  # Knowledge exploration (Sprint 17+)
  entities(
    archetype: Archetype
    status: [EpistemicStatus]
    search: String
    facets: [FacetFilter]
    first: Int
    after: String
  ): EntityConnection!

  entity(id: ID!): EpistemicEntity
}

Key design principle: The GraphQL schema is shared across tenants. The same entities(archetype: TERM) query returns anatomical lemmas for ATLOMY and Arabic lexical roots for VISIONIS. The tenantLabel field (resolved via TenantOntology) tells the frontend what to call them; the data JSON carries tenant-specific fields. The frontend renders different page modules per tenant, but the query shape is identical.

This means:

  • No per-tenant GraphQL schemas
  • No per-tenant resolver code
  • Tenant variation is data-driven, not code-driven
  • The same React component can render a TERM detail page for any tenant by reading tenantLabel and iterating over data keys

Consequences​

Positive​

  • ✅ Eliminate over-fetching: Client gets exactly what it needs
  • ✅ Eliminate N+1: Server batches/caches resolvers
  • ✅ Type safety: TypeScript types auto-generated
  • ✅ API discovery: Introspection powers GraphiQL playground
  • ✅ Versioning: Add fields without breaking changes

Negative​

  • ⚠️ Complexity: More moving parts than REST
  • ⚠️ Learning curve: Team needs GraphQL training
  • ⚠️ Caching: More complex than REST (Apollo cache)
  • ⚠️ Performance: N+1 at resolver level if not careful (use DataLoader)

Mitigations​

  • Training: 2-week GraphQL workshop before Sprint 11
  • Tooling: GraphiQL for API exploration, graphql-codegen for types
  • Performance: DataLoader for batching, Redis for caching
  • Monitoring: Apollo Studio for query analysis

Implementation Timeline​

Sprint 11 (Schema Review UI)​

  • Define initial GraphQL schema for tables, suggestions
  • Implement resolvers with DataLoader
  • Set up Apollo Client in React
  • Generate TypeScript types

Sprint 13 (Knowledge Explorer)​

  • Extend schema for search, facets
  • Add pagination (cursor-based)
  • Implement filters, sorting

Sprint 14+ (Optimization)​

  • Add persisted queries (security + performance)
  • Implement Redis caching for expensive resolvers
  • Set up Apollo Studio monitoring

API Contract Governance​

GraphQL schema is the source of truth:

  • Schema changes reviewed like code (PRs)
  • Breaking changes require deprecation warnings
  • Versioning via @deprecated directive, not /v2/ URLs

Type Generation:

# codegen.yml
schema: http://localhost:8000/graphql
documents: 'src/**/*.graphql'
generates:
  src/generated/graphql.ts:
    plugins:
      - typescript
      - typescript-operations
      - typescript-react-apollo

Run on CI: npm run codegen generates types from schema.

Alternatives Considered​

  1. REST Only: Rejected. Too many round-trips, over-fetching.
  2. GraphQL for Everything: Rejected. Mutations/uploads better in REST.
  3. gRPC: Rejected. Overkill, less frontend-friendly than GraphQL.

Anti-Patterns to Avoid​

❌ Don't: Use GraphQL for file uploads
✅ Do: Use REST multipart/form-data

❌ Don't: Put mutations in Query type
✅ Do: Use REST POST/PATCH for state changes

❌ Don't: Skip DataLoader (causes N+1)
✅ Do: Batch database calls with DataLoader

❌ Don't: Expose internal Django models directly
✅ Do: Design GraphQL schema for frontend needs

Compliance​

This decision supports:

  • API-First Architecture: GraphQL schema is the contract
  • Epistemic Complexity: Graph queries match epistemic structure
  • Frontend Independence: React decides data needs, not backend
