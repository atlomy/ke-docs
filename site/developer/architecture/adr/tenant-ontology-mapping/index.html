ADR-004: Tenant Ontology Mapping

Date: 2025-12-28
Status: Approved
Deciders: Architecture Team, External Consultant

Context​

The platform supports multi-ontology tenants where the same archetype has different domain vocabulary:

  • ATLOMY calls a TERM a "Lemma" (anatomical term from ancient Greek/Latin corpus)
  • VISIONIS calls a TERM a "Lexical Root" (Arabic root for seeing/perception, e.g. n-ẓ-r)
  • ATLOMY calls a DOCUMENT a "Reference" (corpus edition citation)
  • VISIONIS calls a DOCUMENT a "Reader Text" (curated primary source passage) — and also has sub-typed DOCUMENTs: "Edition" (bibliographic source) and "Translation" (translation record)

These are semantically equivalent archetypes with different labels, and in some cases different sub-type vocabularies.

Beyond archetype labels, tenants also maintain classification vocabularies — controlled term sets used to categorize entities. ATLOMY uses simple field-level classifications (body region, anatomical system). VISIONIS uses rich, researcher-managed faceted vocabularies (Perspectives, Subjects, Genre, Location, Time periods).

Problem: Where do these mappings and vocabularies live?

Decision​

Tenant-specific ontology mappings live in a dedicated TenantOntology table, not in JSON fields or frontend config.

Schema Design​

CREATE TABLE tenant_ontologies (
  id UUID PRIMARY KEY,
  tenant_id UUID NOT NULL REFERENCES tenants(id),
  
  -- Canonical archetype (system-wide, one of the 7 frozen in ADR-006)
  archetype VARCHAR(50) NOT NULL,  -- 'DOCUMENT', 'TERM', 'ENTITY', 'EVENT', 'MEDIA', 'RELATIONSHIP', 'ANNOTATION'
  
  -- Sub-type variant (optional — allows multiple labels per archetype per tenant)
  variant VARCHAR(100),            -- NULL for the primary label, e.g. 'edition', 'translation' for DOCUMENT sub-types
  
  -- Tenant-specific label
  label VARCHAR(100) NOT NULL,     -- 'Lemma', 'Reader Text', 'Edition', etc.
  label_plural VARCHAR(100),       -- 'Lemmas', 'Reader Texts', 'Editions'
  
  -- UI customization
  icon_name VARCHAR(50),           -- 'book', 'brain', 'tag'
  color_hex VARCHAR(7),            -- '#3B82F6'
  
  -- Field label mappings: maps canonical/JSONB field names to tenant-visible labels
  field_mappings JSONB,            -- {"ancient_words": "Ancient Words", "root_letters": "Root Letters"}
  
  -- Classification vocabularies (for taxonomy facets, not epistemic entities)
  vocabulary JSONB,                -- See "Vocabulary Management" section below
  
  created_at TIMESTAMPTZ NOT NULL,
  updated_at TIMESTAMPTZ NOT NULL,
  
  UNIQUE(tenant_id, archetype, variant)
);

Note on the variant column and unique constraint: The original schema used UNIQUE(tenant_id, archetype), which limited each tenant to one label per archetype. In practice, VISIONIS has three kinds of DOCUMENT (Reader Text, Edition, Translation). The variant column allows sub-typing within an archetype. NULL variant means the primary/default label. Named variants (e.g. 'edition', 'translation') are sub-types. The unique constraint is now UNIQUE(tenant_id, archetype, variant).

GraphQL Schema​

type TenantOntology {
  archetype: Archetype!
  variant: String               # NULL = primary label, "edition" / "translation" = sub-type
  label: String!
  labelPlural: String!
  icon: String
  color: String
  fieldMappings: JSON
  vocabularies: [Vocabulary!]!  # Classification facets for this archetype
}

type Vocabulary {
  name: String!                 # "perspective", "subject", "genre"
  entries: [VocabularyEntry!]!
}

type VocabularyEntry {
  code: String!                 # "P1", "S18", "G6"
  label: String!                # "Scriptural Perspective", "Seeing God"
  description: String
}

type Query {
  tenantOntology: [TenantOntology!]!
}

React Usage​

// Fetch tenant ontology on app load
const { data } = useQuery(GET_TENANT_ONTOLOGY);

// Primary label for an archetype
const termLabel = data.tenantOntology.find(
  o => o.archetype === 'TERM' && !o.variant
).label;
// "Lemma" for ATLOMY, "Lexical Root" for VISIONIS

// Sub-typed labels
const docVariants = data.tenantOntology.filter(o => o.archetype === 'DOCUMENT');
// ATLOMY: [{label: "Reference", variant: null}]
// VISIONIS: [{label: "Reader Text", variant: null}, {label: "Edition", variant: "edition"}, ...]

<h1>Add New {termLabel}</h1>
<Button>Create {termLabel}</Button>

Rationale​

Why Dedicated Table?​

NOT in JSON fields:

  • ❌ Hard to query ("show all tenants using 'Lemma' label")
  • ❌ Not validated
  • ❌ Breaks referential integrity

NOT in frontend config:

  • ❌ Requires frontend deployment to change labels
  • ❌ Can't be used by backend (reports, emails)
  • ❌ Not accessible to AI reasoning

YES in relational table:

  • ✅ Queryable: "Which tenants use archetype X?"
  • ✅ Validated: Foreign key to tenant
  • ✅ Backend accessible: Use in emails, reports, AI reasoning
  • ✅ Auditable: Track when labels changed
  • ✅ Scalable: Future cross-tenant analytics

Use Cases​

1. Dynamic UI Labels​

// Instead of hardcoded "Lemma"
<PageTitle>Manage {ontology.label_plural}</PageTitle>

2. AI Mapping Pipeline (Sprint 16)​

TenantOntology is both read and written by the AI mapping workflow:

Read: When the AI mapper detects a CSV upload as archetype TERM, it checks whether this tenant already has a label for TERM. If VISIONIS already established "Lexical Root," the AI pre-fills that label in the mapping proposal.

Write: When a researcher approves a mapping proposal, the system atomically creates or updates the TenantOntology row. This is the moment the tenant's vocabulary becomes official.

# AI reads existing tenant vocabulary
ontology = TenantOntology.objects.filter(tenant=tenant, archetype='TERM', variant=None).first()
if ontology:
    proposed_label = ontology.label  # Pre-fill with established vocabulary
else:
    proposed_label = ai_suggest_label(table_name, sample_data, tenant)

# On approval, system writes
TenantOntology.objects.update_or_create(
    tenant=tenant, archetype='TERM', variant=None,
    defaults={'label': approved_label, 'label_plural': approved_label_plural}
)

3. Cross-Tenant Analytics​

-- "How many tenants use the TERM archetype?"
SELECT label, COUNT(*) 
FROM tenant_ontologies 
WHERE archetype = 'TERM' AND variant IS NULL
GROUP BY label;

4. Email Templates​

# Instead of hardcoded "Lemma"
email_body = f"You have 5 new {ontology.label_plural} to review"

Vocabulary Management​

Beyond archetype labels, tenants maintain classification vocabularies — controlled term sets used to categorize entities via facets. These are not epistemic entities (they don't go through draft → review → approve). They are admin-configured vocabularies that researchers use to tag and filter.

Why vocabularies belong in TenantOntology​

VISIONIS has four explicit classification dimensions from its research database:

VocabularyEntriesExample
Perspectives7P1: Scriptural, P2: Literary, P3: Philosophical
Subjects22S1: Seeing God, S3: The Sense of Sight, S7: Images and Imagination
Genre12G1: Qurʾan, G2: Hadith, G4: Poetry
Location9C1: Arabian Peninsula, C2: Levant, C6: Iraq

ATLOMY's equivalent is simpler — body region and anatomical system as field values on the Lemma model.

These vocabularies are:

  • Tenant-specific: ATLOMY doesn't have "Perspectives"; VISIONIS doesn't have "body regions."
  • Admin-managed: An admin configures them; researchers select from them.
  • Not epistemic entities: They don't need AI proposal, confidence scores, or approval workflows.
  • Many-to-many: One reader text can reference "S18, S13" (two subjects).

Schema for vocabularies​

The vocabulary JSONB column on tenant_ontologies stores the controlled vocabulary sets relevant to that archetype in that tenant:

{
  "perspectives": {
    "label": "Perspective",
    "label_plural": "Perspectives",
    "entries": [
      {"code": "P1", "label": "Scriptural Perspective", "subcategories": "Qurʾan, Tafsīr, Hadith"},
      {"code": "P2", "label": "Literary Perspective", "subcategories": "Prose, Poetry, Rhetoric"}
    ]
  },
  "subjects": {
    "label": "Subject",
    "label_plural": "Subjects",
    "entries": [
      {"code": "S1", "label": "Seeing God", "description": "The desire to see God, the vision of God", "material_relation": "Objects that display or represent the divine"},
      {"code": "S3", "label": "The Sense of Sight", "description": "Sight as one of the senses"}
    ]
  }
}

This is JSONB because:

  • Vocabulary structure varies per tenant (VISIONIS Subjects have a material_relation field; ATLOMY body regions don't).
  • Vocabularies are read-heavy and rarely change.
  • No need for relational joins — they're loaded into the React context once per session and used for facet filtering.

If a future tenant needs vocabularies with full audit trails and complex relationships, they can be promoted to a relational table. For now, JSONB is sufficient.

Field Mappings Specification​

The field_mappings JSONB column maps JSONB data field keys to human-readable labels in the tenant's language:

{
  "ancient_words": {"label": "Ancient Words", "display_order": 1},
  "body_region": {"label": "Body Region", "display_order": 2, "facet": true},
  "transliteration": {"label": "Transliteration", "display_order": 3}
}

For VISIONIS TERM:

{
  "root_letters": {"label": "Root Letters", "display_order": 1},
  "transcription": {"label": "Transcription", "display_order": 2},
  "sense_category": {"label": "Sense Category", "display_order": 3, "facet": true}
}

The frontend iterates over field_mappings to render tenant-specific fields from the data JSONB in the correct order with the correct labels. Fields not in field_mappings are not rendered (they may exist in JSONB for internal use but are not user-facing).

Implementation​

Migration Plan​

Sprint 11 (Immediate):

  • Create tenant_ontologies table
  • Seed with default mappings (TERM → "Term", BLOG_POST → "Article")
  • Add GraphQL query

Sprint 12:

  • Update React to fetch ontology on load
  • Replace hardcoded labels with ontology lookups

Sprint 13:

  • Add admin UI for tenant customization
  • Allow tenants to override default labels

Sprint 14+:

  • Field-level mappings (optional)
  • Icon/color customization UI

Consequences​

Positive​

  • ✅ Tenant flexibility: Easy to customize labels
  • ✅ AI-friendly: AI uses tenant's vocabulary
  • ✅ Analytics: Query ontology usage
  • ✅ Maintainability: Change labels without deployment

Negative​

  • ⚠️ Extra table: More schema complexity
  • ⚠️ Loading overhead: Fetch ontology on app load

Mitigations​

  • Cache ontology in React Context (load once per session)
  • Backend cache in Redis (rarely changes)

Anti-Patterns to Avoid​

❌ Don't: Hardcode labels in React components
✅ Do: Load from tenantOntology context

❌ Don't: Store in frontend .env files
✅ Do: Store in database, fetch via GraphQL

❌ Don't: Use JSON for everything
✅ Do: Relational table for queries, JSON for complex field mappings only

Compliance​

This decision supports:

  • Multi-Ontology Principle: Tenants express differently, structure remains
  • AI Governance: AI proposes in tenant's vocabulary
  • Tenant Autonomy: Control their own labels
