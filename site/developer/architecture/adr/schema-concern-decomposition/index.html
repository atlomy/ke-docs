ADR 060: Schema Concern Decomposition — Field Identity, Tenant Label, Storage, Roles, Baseline, and Search-Linguistic Config

  • Status: Accepted (2026-06-11) — owner rulings folded in (§"Owner rulings"); gen-1 column retirement executes behind the pre-launch audit gate (D5.4)
  • Date: 2026-06-11
  • Deciders: drafted by Claude (schema first-principles research lane); platform owner ratifies
  • Context source: docs/research/2026-06-11_slot-frame-archaeology.md (slot-frame archaeology, owner-ratified finding) + docs/research/2026-06-11_schema-architecture-first-principles.md (full-layer interrogation, this ADR's evidence body); the 2026-06-10/11 escorted live walk (display-field A/B/C conflation, unseeded search metadata); Spec 0047 owner pivot
  • Related: ADR-004 (tenant ontology mapping), ADR-006 (capability contracts), ADR-012 (config via runtime pipeline), ADR-017 (slot config as tenant-authoritative manifest + §B identity ledger), ADR-019 (Lemma retirement), ADR-029 (projection-first published entries), ADR-031 (source-model versioning), ADR-033 (comfort-dial apply), ADR-037 (slot-type taxonomy), ADR-042 (substrate naming/rename arc), ADR-044 (vocabulary substrate), Spec 0009 Task 2 (search metadata), Spec 0046 (stream field bindings), Spec 0047 (workspace search/read), Spec 0049 (re-import-as-delta), decision log 2026-05-22 ("slot" dissolves from user-facing vocabulary), decision log 2026-06-02 (relationship rule_name derivation)

Context​

TenantArchetypeFormConfig was born on a single afternoon (2026-04-30, commit 2ffca228) with help text declaring slot_name a "Canonical slot in the archetype's presentation contract (e.g., 'title', 'subtitle', 'body', 'attestations')" and label "defaults to slot_name humanised". The archaeology research established that this frame was written, not decided: no ADR ratified it, the platform inverted it within ~36 hours (the slot-config materializer made slot_name a slugified mirror of every tenant column), and every subsequent load-bearing decision moved away from it — ADR-017 reframed the table as the tenant-authoritative manifest, ADR-029/Spec 0022 relocated the real presentation contract into publication rules, ADR-037 ruled the curated canonical layer is the type taxonomy, never slot names.

The owner then widened the question to the entire early schema layer. The first-principles research (companion doc) inventoried every model frozen by atlomyapp/migrations/0001_initial.py plus the epistemic substrate and found:

  1. The physical shape is right and already survived adversarial review: ADR-017's v1 framing ("slot configs become a projection of typed schema") was rejected in the 2026-05-07 three-source synthesis because the wide config-row manifest is the industry-canonical metadata-as-source primitive (Directus directus_fields, Salesforce metadata virtualization).
  2. The semantic layer drifted: five architectural generations appended columns without retiring the prior generation's words. Beyond the four slot names, the research identified eight further conflations/defects (C1–C8): one column with two unrelated semantics (display_field); a default pointing at a retired storage layer (source_layer=MODEL); the type-taxonomy column named after a presentation concern (widget); three coexisting relationship-modeling generations; detection output and tenant policy sharing linguistic columns unprovenanced; search-metadata columns seeded on one import path and left null on the newer one; tenant vocabulary spread across four homes; and dual encodings of source-path roles inside the entry-surface config.
  3. External standards and SOTA tools (TEI ODD, CIDOC-CRM E41/E42, Wikibase Q/P-ids vs labels, Dublin Core, Omeka S resource templates, Directus, Airtable) converge on: field identity ≠ display label, everywhere; presentation roles never live on field identity; wide field-metadata rows decomposed by column ownership, not by table explosion.
  4. The live consequences are real, today: researchers see humanized platform slugs instead of their own column names (Spec 0047 facet labels); a tenant's label fix is clobbered by the next re-import; the same archetype's display field resolves first-wins-wrong across source tables.

The PoC clock (generalisation milestone late August 2026; greenfield-but- time-boxed deployment) makes this the cheapest moment these fixes will ever have.

Decision​

The platform ratifies a six-concern decomposition of the tenant schema layer, applied to the existing tables as named column semantics, defaults, and update disciplines — explicitly not as a physical re-architecture.

D1 — The six concerns and their carriers​

D2 — Label-default rule​

The tenant-facing label of an imported field defaults to the verbatim source column name — the tenant's vocabulary exactly as authored, however ugly — and is tenant-overridable thereafter. Humanization (slug.replace("_"," ").title() and its ~10 duplicates) is permitted only as a last-resort fallback for genuinely empty/absent headers, via one shared helper. This supersedes "defaults to slot_name humanised". (The platform already preserves the verbatim header in ColumnHeaderSeed "as found" — this rule aligns the label with evidence the schema already keeps.)

No backfill mechanism exists or is needed (owner ruling, 2026-06-11): the platform is greenfield — every real tenant, including the original one, first imports at production launch, after this rule is in code, so every label is born verbatim. Pre-launch test environments are scrub-phase data and may be healed by hand or wiped.

D3 — Per-column ownership matrix (the re-run contract)​

Every TenantArchetypeFormConfig column is classified into exactly one of three ownership classes, encoded as a module-level constant that the slot-config materializer, the wizard field-plan resolver, and the re-import delta engine (Spec 0049) all read:

Class names are behavior-first (owner ruling 2026-06-11: names must be self-explanatory to humans and AI agents, and consistent; "researcher", not "tenant", where a person is meant — "tenant" is infrastructure vocabulary):

  • REFRESHED_FROM_SOURCE — every re-import overwrites; the source is the truth: source_field, source_layer.
  • SET_ONCE_IF_EMPTY — the machine may fill a blank/default; it may never overwrite a real value: widget, script, language, multilingual, searchable, facet, autocomplete_eligible, display_order, enum_options.
  • RESEARCHER_OWNED — never machine-written after creation: label, help_text, required, accent_fold, search_boost, composition_template, composition_skip_empty, complies_with, multikey_kind, multikey_keys, numeric_format, currency_code, precision, text_role, media_kinds, relation_cardinality, lookup_for, target_field, target_archetypes, linkable, display_field.

Ratified per-column rulings (2026-06-11):

  • display_order = SET_ONCE_IF_EMPTY. The initial value mirrors the source's own column order; re-imports may append positions for newly arrived fields but never reshuffle the researcher's layout. Known defect folded in as an implementation task: the Coda import does not currently preserve the Coda table's column order — fix the initial ordering.
  • required = RESEARCHER_OWNED, no inference. The platform writes False at creation, full stop — a column being historically always-filled does not mean future records must fill it, and a wrong guess blocks data entry. Follow-up (owner): the required control must be properly surfaced to researchers — docs, tutorials, and the UI itself.
  • Kind-change proposals: when a re-imported source's typing changes (text→date after cleanup; single→list; values matching another table's identities), the platform may propose a kind change through the existing restructure/review proposal queue — never auto-apply.

D3a — Row lifecycle (not just column updates)​

The matrix governs updates to a living row; dispositions govern the row itself:

  • Column set aside at first import → no config row is created.
  • Column set aside on a re-import (the row exists; the researcher may have curated it) → the row is removed, never hard-deleted — curation is preserved, and the Spec 0049 delta view reports it loudly ("1 field removed"). A later re-import that restores the column revives the same identity with its curation intact. Researcher-facing language is "removed" / "restored" — never "retired"/"deactivated" (tech/business speak; owner ruling 2026-06-11).
  • Column restructured into a picker → the picker is a new identity (x_select); the original column's row follows its own disposition. Curation never silently teleports between identities — the delta view reports the change next to the new picker.
  • Source column renamed → new identity through re-import review (Spec 0049); the old identity is removed loudly, as above.
  • Saved views are a third layout layer (researcher-owned per view, above display_order): a view's own column order/visibility is never touched by imports. When a field a view references is removed, the view degrades gracefully (the missing column is dropped from render, the view keeps working) and the re-import delta notes which saved views were affected. A removed-then-restored field reappears in views that referenced it.

D3b — Two birth paths, one rulebook​

Import is one way data enters a KE; the other is starting an empty KE and building it table by table (researcher-driven schema editing is a first-class platform requirement, decision log 2026-05-22). The same identity/label/ownership rules serve both:

  • Researcher-created fields have no source: every column is RESEARCHER_OWNED from birth; slot_name is minted from the typed label by the same single slugifier; the label IS what they typed (verbatim by construction).
  • Researcher-created relations are born as materialized EntityRelationship edges via the workspace pickers — they never need read-time resolver mechanics (which strengthens D5.4's retirement gate: hand-built KEs cannot produce gen-1 dependencies).
  • Relation creation UX must demand the minimum from the researcher and speak non-developer language end to end — archetype/field/display-field maintenance for hand-built KEs is a surfaced, supported workflow, not an admin back door.

This generalizes the archaeology doc's R3 (the materializer's defaults clobber contradicting its own docstring), ports Spec 0046's managed=seeded|manual discipline to the slot layer, and implements the ADR-017 --merge-replace philosophy per-column ("keys in source schema: source wins; keys outside it: existing wins").

Implementation clarifications (folded in from the D3 build, 2026-06-11):

  • Gen-1 relationship columns (is_relationship, resolver_kind, resolver_args, target_archetype) were absent from the three lists above. Classified REFRESHED_FROM_SOURCE — they are machine-derived resolution mechanics (consistent with their D5.4 demotion) until the audit-gated retirement removes them.
  • Identity and versioning sit outside the matrix by design: archetype + slot_name are the immutable row identity (D1), and the ADR-031 versioning bookkeeping columns are maintained by save(), not by import paths. Both are documented exclusions covered by the same CI guard.
  • Approval-carried relation wiring: linkable, target_archetypes, display_field, lookup_for, target_field are RESEARCHER_OWNED, but the field-plan path writes them from researcher-approved proposal content — that is the review-queue lane acting, not a machine overwrite. Documented as the _APPROVAL_CARRIED_RELATION_WIRING set so the flat-column→linkable re-import heal keeps working. Extended 2026-06-12 (D4-lane consumer sweep caught the gap): the multilingual/ multikey modifiers (multikey_kind, multikey_keys, multilingual) join the same lane — they are written from approved multilingual-reshape proposals, and freezing them at creation broke the field-plan modifier refresh.
  • Strictness delta, accepted: previously some RESEARCHER_OWNED fields (help_text, search_boost, …) were machine-fillable while still at default; they are now never machine-written after creation. If a future source wiring (e.g. source column descriptions → help_text) wants fill-after-creation, it goes through the review lane or re-opens this classification with evidence.

D4 — Seeding honesty for search metadata (deterministic floor, learning lane)​

The wizard/field-plan materialization path seeds explicit searchable/facet/autocomplete_eligible/search_boost values (today it writes None, leaving the columns vestigial). After this lands, null means exactly "row predates seeding" and the help text says so.

The seed is deterministic and kind-derived — a fixed table from slot kind to flags, identical for every tenant domain (owner ruling 2026-06-11: content heuristics are dangerous given the diversity of tenant domains; deterministic-first). Text kinds → searchable; select kinds → facet + their declared options; relation kinds → searched through their target's display projection. Media is not a flat "not searchable" row: per ADR-022, a media object is a multilayered artifact whose anchors bind to terms, passages, and any archetype (e.g. a 3D-model body-part mesh bound to terms/ events/entities in the public reader) — media kinds are searchable through their binding graph, and their seeding rows are defined with ADR-022 as input, per media kind, not guessed.

Content-derived enrichment is not banned — it is channeled. Content sniffing (value distributions, enum candidates, cross-table identity matches) may enrich the DB or search, but only as proposals through the review queue and the platform's learning/telemetry mechanisms (decision- event telemetry, vocabulary learning around tenants) — never as silently written values. A dedicated case-mapping pass (follow-up) enumerates which enrichments are worth proposing and what evidence each requires.

D5 — Column-level dispositions​

  1. display_field (FormConfig) is constrained to its documented meaning — the projected field of a linkable slot. Archetype/collection display- label resolution reads TenantArchetypeTable.display_field (per-collection) exclusively; the first-wins archetype-level fallback read-path is removed after a per-collection backfill, with all consumers (public reader, admin, workspace GraphQL) verified before the gate flips.
  2. source_layer default → EPISTEMIC (D1 row 3).
  3. widget keeps its column name for now; the rename to slot_kind is assigned to the ADR-042 rename arc. New code and docs must say "slot kind", never "widget", for concern #5.
  4. Relationship-mechanism authority (three coexisting generations): the ADR-037-era mechanism (widget=RELATION/LOOKUP, linkable, target_archetypes, lookup_for/target_field, relation_cardinality) is authoritative for tenant-facing modeling. The gen-1 columns (is_relationship, resolver_kind, resolver_args, singular target_archetype) are demoted to documented read-time resolution mechanics — they exist to resolve relations for imports that never materialized real EntityRelationship edges (live consumers: relationship_resolver.py, entry_surface.py, workspace_rows.py, publication.py; fk_walk in the MySQL parser). Retirement executes behind a concrete pre-launch audit gate (owner-amended 2026-06-11), not an open-ended "post-wizard-parity": during the remaining test window, audit read-path hits on gen-1 resolution across wizard-imported environments; if zero — as expected, since every launch import goes through the wizard and hand-built KEs are born with materialized edges (D3b) — retire the columns in the cleanup arc before launch. (No column drops in this ADR itself.)
  5. Linguistic provenance follows the detected-seed rule (D3): detection writes only into empty/default values — ratifying and extending the materializer's existing if created: discipline to re-runs.

D6 — Supersession of the 0001-era "presentation contract" frame​

The 2026-04-30 help-text frame — slot_name as a canonical presentation slot; label as humanized slug; the model docstring's "drives BOTH form rendering and display projection" — is formally superseded. Help texts and docstrings are rewritten to the D1 table's language (identity, not presentation; projection is EntryProjection's job under ADR-029). This ADR also folds in the 2026-05-22 ruling (ALREADY DECIDED — this ADR cites, it does not re-open): "slot" remains engineering-internal vocabulary and is dissolved from researcher-facing surfaces. Known failure mode: AI agents keep regressing to "slot" in new copy — reviewers and lints should treat it as a vocabulary violation on researcher-facing surfaces. The replacement noun stays with the product-language pass, and the pass must handle the "field" collision (owner caution 2026-06-11): "field" is overloaded — a table's field, a research field (domain), the literal field an archaeologist or botanist works in — and KE's slots are a specific kind of field. Candidate nouns are evaluated there, not here.

D7 — What is explicitly NOT changed​

  • No physical decomposition of TenantArchetypeFormConfig — the wide manifest is the ratified primitive (ADR-017 alternatives D/E).
  • No renaming of existing slot_name values — they are identity.
  • No weakening of the out-of-the-box scholarly page — the default role wiring is a platform guarantee.
  • No relocation of per-slot search flags — placement reaffirmed.
  • No changes to ADR-037's taxonomy, ADR-006's contracts, the EntryProjection family, Spec 0046's binding model, or EntityIdentityLedger.
  • v1-residue models (Configuration with its tenant-vocabulary enum, ElasticSearchModel, 3D-viewer-era operational models) are acknowledged as out of scope here and routed to the ke-rename/code-cleanup arc.

Consequences​

Positive​

  • Researchers see their own vocabulary by default on every tenant-facing surface (fixes the live Spec 0047 facet/matched-field label defect), and their corrections survive re-imports (D3 ends the clobber).
  • One named home per concern ends the display-field A/B/C class of bug at its schema root and gives agents/engineers a true mental model instead of the December-2025 page model the help text taught.
  • The re-import contract becomes a single auditable constant — Spec 0049's delta engine, the materializer, and the wizard share one source of truth.
  • Standards alignment (TEI/CIDOC/Wikibase identity≠label; Directus column ownership) without new infrastructure; complies_with is positioned for Clause-1 promotions and federation identity.
  • Everything lands as help-text/default migrations + code-level discipline inside the wipeable window — no mass row rewrites, no flag days.

Negative​

  • Verbatim labels can be ugly (fld_017, trailing whitespace) — accepted: provenance over prettiness; the wizard may suggest prettified labels in review UI without storing them as defaults (ruling 3 — accepted).
  • The ownership matrix adds a constant every import-path author must honor; a path that bypasses it re-introduces clobber silently. Mitigation: the matrix lives beside the model, and the materializer/field-plan tests assert classification coverage of every concrete column (a new column without a classification fails CI).
  • Demoting-but-keeping gen-1 relationship columns prolongs the ~9-column relationship surface; accepted to avoid breaking live fk_walk consumers.
  • Tests asserting humanized labels need updating (bounded; known sites).

Mitigations​

  • Step-ordered rollout (companion doc §6): words/defaults → label default → ownership matrix → slugifier+backfill → display_field gate → search seeding; each step independently shippable and reversible.
  • The display_field fallback removal (highest blast radius) ships only after per-collection backfill verification across all consumer surfaces (public reader + admin + workspace — the verify-all-consumers rule).

Alternatives considered​

  1. Physical decomposition into per-concern tables (slot_identity / slot_search_config / slot_linguistics…). Rejected: re-litigates ADR-017's settled alternative D/E; multiplies joins for every consumer; weeks of work under the PoC clock for zero researcher-visible gain; no surveyed SOTA system does it.
  2. Status quo + spot-fix the label default only. Rejected: leaves the clobber, the dual-semantics column, the dead default, and the false help text in place; the next agent re-learns the wrong model and the next import path re-introduces the bug (the trigger incident pattern).
  3. Typed-schema source of truth replacing the manifest. Already rejected by ADR-017 (2026-05-07 synthesis); re-rejected here for the record.
  4. Move search flags to TenantSearchProfile / a dedicated search table. Rejected: Spec 0009 Task 2 deliberately put structural flags at slot grain (they are per-field facts, tenant-overridable per slot); engine choice already lives at the profile. Fix seeding, not placement.
  5. Adopt Spec 0046-style managed + seed_strategy columns on FormConfig instead of a code-level matrix. Deferred, not rejected: per-row ownership provenance is richer but costs a migration + admin surface now; the code-level matrix delivers the same re-run semantics today and can be upgraded to per-row provenance if override telemetry shows drift (evidence-gated per ADR-055 — trigger: count of machine-overwritten tenant edits detected by the delta engine, surfaced on the ops digest).

Implementation​

Companion doc §6 carries the full ordered/risk-ranked path. Summary: Step 1 words+defaults (hours, metadata-only migration; slot_name/label help text SHIPPED 2026-06-11, migration 0008); Step 2 label default — SHIPPED 2026-06-11 (commit a04f8af0: all seven derivation sites verbatim, override-recognizer taught both machine forms, mangle-revealing regression test); Step 3 ownership matrix + row lifecycle (D3/D3a/D3b) — SHIPPED 2026-06-11 (merge acf03306: matrix + CI coverage guard + clobber ended + ruling-1 column order); Step 4 single slugifier + collision report — SHIPPED 2026-06-12 (merge d46f243f: normalize_slot_name canonical, Unicode-preserving — non-Latin column names no longer collapse to empty slugs; collect-all SlotNameCollisionError in both write paths); Step 5 display_field gate — SHIPPED 2026-06-12 (merge of c6adfddd+1c0142d4: first-wins fallback removed from anchor_projection/epistemic-admin/wizard panels; full consumer matrix verified; capture refresh with source_display_field override stamp + backfill command; live-verified — all five dev-tenant collections show human labels post-gate); Step 6 wizard-path deterministic search seeding (D4) — SHIPPED 2026-06-12 (same merge: SLOT_KIND_SEARCH_SEED at every create path; search_boost marked RESERVED). Steps 1–4 target → delivered inside the pre-August window.
