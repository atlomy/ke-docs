ADR-041: Spatial substrate — PostGIS + GeoSPARQL + MapLibre GL JS

Status: Proposed (v1.1 — amended 2026-05-20 per R1d targeted stress-test absorption; ratification paired with ADR-039 Place preset per ADR-038 v1.2 §D8 staggering rationale) Date: 2026-05-20 Deciders: User; architecture team Related: ADR-022 (Anchor + ClaimCluster substrate), ADR-037 (Slot-Type Taxonomy; GEOMETRY SlotKind in Threshold-C amendment queue per v1.1), ADR-038 (Federated Preset Registry), ADR-039 (Place preset; first consumer), ADR-029 (Projection-First Published Entry Layer), ADR-030 (CIDOC + Linked Art Export Profile Choice; SHACL prerequisite), ADR-002 (Hybrid Ontology) Companion:

  • ADR-039 — Place preset (the data contract this substrate underlies)
  • Spec 0019 — MapView design.md (consumer of the MapLibre GL JS substrate)
  • docs/superpowers/plans/2026-05-19-mapview-spatial-anchored-surface-brainstorm.md — resolves §Open Questions §1 + §2 + §4
  • docs/superpowers/plans/2026-05-20-period-place-spatial-architectural-pass.md — post-307 absorption provenance

TL;DR​

ADR-041 commits the platform to a spatial substrate spanning storage (PostGIS), query (GeoSPARQL→PostGIS function mapping), CRS handling (PROJ), client rendering (MapLibre GL JS), tile architecture (tenant-provided + external WMS at v1), and performance contracts (render <500ms; vector N=10k interactive).

The substrate is the engineering precondition for ADR-039 Place preset ratification + Spec 0019 MapView design.md upgrade. ADR-041 itself does NOT ship a preset; it ships the substrate that ADR-039 (and future spatial-consuming ADRs) ride on. The substrate is what makes the GEOMETRY SlotKind (queued in ADR-037 v1.1 Threshold-C amendment queue) implementable.

Substrate-readiness staggering per ADR-038 v1.2 §D8: ADR-040 Period landed first (text-centric, no substrate gate); ADR-039 Place + ADR-041 substrate land paired (the substrate IS the gate for Place); subsequent D8 presets ratify behind the substrate as separate ADRs.

Context​

What this ADR resolves​

ADR-039 declares the Place preset's data contract: required slots (prefLabel + geometry + placeType), complies_with declarations (GeoSPARQL + CIDOC E53 + schema.org/Place + GeoJSON + Pleiades + GeoNames + Wikidata + dcterms:Location + EPSG), capability URIs. What ADR-039 does NOT specify is HOW the platform stores geometry, indexes spatial data, executes geospatial queries, handles CRS transformations, renders maps, serves raster tiles, or guarantees performance. ADR-041 resolves those substrate questions.

The Spec 0019 MapView brainstorm anticipated five substrate questions in its §Open Questions (§1 substrate library; §2 tile server architecture; §4 coordinate-system surface; §5 time-axis controls; §6 permission scoping). ADR-041 resolves §1 + §2 + §4 directly; §5 + §6 land in Spec 0019 design.md upgrade per Phase 7.

Why now​

Three drivers:

  1. ADR-039 ratification dependency. Place preset is geometry-bound and cannot ship text-centric per ADR-039 §"Why Place can't move text-centric like Period did." The substrate IS the gate.
  2. GEOMETRY SlotKind Threshold-C amendment dependency. ADR-037 v1.1 queues GEOMETRY in §Evolution Threshold-C amendment queue. The amendment requires G1 impact + G3 fixture commitments. ADR-041 provides the substrate that makes the SlotKind implementable.
  3. Integrative-tenant readiness. The integrative tenant (multi-disciplinary humanities + archaeology + ecology + GIS) cannot onboard without a spatial substrate; ADR-041 is the architectural commitment that makes this onboarding viable.

What this ADR does NOT decide​

  • Specific MapView UI design (timeline scrubber UX; cell-editor integration): Spec 0019 design.md upgrade.
  • Place preset data contract: ADR-039.
  • 3D viewer integration: handled by existing spa/src/pages/three_d_model/ viewer.
  • Per-tenant tile hosting cost model: operational, not architectural.
  • Public GeoSPARQL endpoint exposure: ADR-041 D4 internalizes GeoSPARQL as a query-translation layer; public endpoint deferred to Phase C.

Decision​

The spatial substrate for KE is PostGIS + GeoSPARQL→PostGIS function mapping + MapLibre GL JS + tenant-provided / external WMS tile architecture. Eight binding points:

D1 — Geometry storage shape​

Geometry stored as a PostGIS geometry column type. The Anchor model (per ADR-022) gains a geometry column of type geometry(Geometry, 4326) where the type parameter accepts any GeoJSON geometry subtype (Point, LineString, Polygon, MultiPolygon, GeometryCollection) and SRID 4326 is WGS84 default — overridable per row via the srid modifier per ADR-037.

Per-slot SRID declaration: slots configured with geometry_kind=* + srid=<epsg_code> carry geometry in the declared CRS. The platform stores ALL geometry under the declared SRID; reprojection at query time (D5).

JSONB representation at the application layer: GraphQL + REST API surface exposes geometry as RFC 7946 GeoJSON Geometry objects ({type, coordinates, srid}). PostGIS storage + GeoJSON application-layer shape converge via ST_AsGeoJSON() on read + ST_GeomFromGeoJSON() on write.

Validation: writes through validate_geometry_value_shape (per Spec 0020 v1.1 §6 pattern) check RFC 7946 conformance + EPSG-list membership.

D2 — PostGIS extension version + install​

Minimum version: PostGIS 3.4. Tested-supported: 3.4 + 3.5. Recommended for new deployments: 3.5.

v1.1 verification per R1d N8 (PostGIS 3.5 vs 3.4 minimum question): the documented major new features in PostGIS 3.5 (per https://postgis.net/docs/manual-3.5/release_notes.html) are: SFCGAL function renaming with CG_ prefix + new computational geometry capabilities (intersection, union, triangulation); topology performance improvements (faster load of big lines; accelerated ST_CreateTopoGeo); new ST_RemoveIrrelevantPointsForView + ST_RemoveSmallParts simplification functions; ST_GeneratePoints performance enhancement; enhanced ST_AsGeoJson with column-id promotion. None of these features are load-bearing for the v1 spatial substrate — Place preset doesn't depend on SFCGAL topology, doesn't use ST_GeneratePoints, and emits GeoJSON via ST_AsGeoJSON (not record-based). PostGIS 3.4 minimum is defensible; 3.5 is recommended for new deployments because of operational improvements (topology load performance) that benefit large-tenant onboarding.

Required features (validated against PostGIS docs): ST_AsMVT for vector tile aggregation (added in PostGIS 2.4; long-stable); the 9 GeoSPARQL spatial-relation predicates per §D4 (all long-stable in PostGIS 3.x); ST_Transform for CRS reprojection (long-stable); GIST index support (long-stable). v1 doesn't depend on 3.5-specific features.

Install discipline: CREATE EXTENSION IF NOT EXISTS postgis; in schema migration. Reversible (DROP EXTENSION postgis CASCADE) — but CASCADE removes all dependent objects, so rollback discipline is "rebuild from earlier migration."

Dev environment: docker-compose.yml Postgres image swap to postgis/postgis:15-3.4 or postgis/postgis:15-3.5. Developers running docker-compose down -v && docker-compose up recreate database with PostGIS available from the start.

D3 — Spatial indexing (GIST)​

Each geometry column gets a GIST (Generalized Search Tree) index per PostGIS standard practice. GIST accelerates bbox queries (ST_Intersects), containment (ST_Contains, ST_Within), proximity (ST_DWithin), and nearest-neighbor (KNN operator <->).

Index maintenance: writes auto-update. Bulk loads should DROP INDEX + bulk-insert + CREATE INDEX for ~10x throughput.

No additional spatial indexes at v1: BRIN evaluation deferred to first multi-million-row spatial table.

D4 — GeoSPARQL query support via PostGIS function mapping​

ADR-041 does NOT ship a public SPARQL endpoint at v1. GeoSPARQL semantics are translated to PostGIS function calls at the federation-query layer (v1.1 — table extended per R1d N9 missing-predicates finding):

Output emission: projection layer (ADR-029) emits GeoSPARQL-conformant JSON-LD (geo:hasSerialization with geo:wktLiteral + geo:geoJSONLiteral). External SPARQL endpoints consuming the JSON-LD see standards-conformant data.

Why not a full GeoSPARQL endpoint at v1: implementing a SPARQL endpoint requires a separate query engine (Apache Jena Fuseki, Virtuoso, custom) that ingests platform RDF + maintains parallel indexes. Triple-store sync is fragile; query optimization differs. PostGIS translation delivers the same functional capability without parallel-storage overhead. Deferred to Phase C.

D5 — CRS handling via PROJ​

PROJ library (integrated into PostGIS 3.x) handles all CRS reprojection. Tenants declare per-slot CRS via the srid modifier; platform reprojects at query time when federation queries cross CRS boundaries.

Pattern: query bbox in WGS84 (EPSG:4326) + target geometries in British National Grid (EPSG:27700):

  1. Federation query translator extracts query bbox + target tenant's per-slot SRID
  2. ST_Transform(target_geometry, 4326) reprojects at execution time
  3. PostGIS GIST index works against the reprojected geometry's bbox

Performance impact: per-row ST_Transform when SRIDs differ. Magnitude not documented in PostGIS docs (v1.1 speculation-flag correction per R1d N18 — the "~10-20% overhead" claim in v1.0 was unverified author-knowledge; the actual PostGIS docs at https://postgis.net/docs/ST_Transform.html document no benchmark numbers). Documented mitigation: PostGIS docs explicitly recommend functional indexes — CREATE INDEX idx_geom_<srid>_<table> ON <table> USING gist (ST_Transform(geom, <target_srid>)) WHERE geom IS NOT NULL; — for tables where multiple transformations are common. Phase B.4 benchmark commitment (per D8) establishes the actual reprojection overhead for the integrative-tenant scale; the optimization path (functional indexes + materialized views for high-traffic CRS pairs) is well-known.

Default CRS: WGS84 (EPSG:4326). v1.1 amendment per R1d N6 (CRS choice burden): the tenant-onboarding flow MUST NOT silently default tenants with non-WGS84 source data to WGS84. When tenants import GIS data carrying CRS metadata (GeoTIFF + projection file; shapefile + .prj; declared SRID in source database), the platform's import wizard surfaces the source CRS + asks for confirmation BEFORE storage. When source data has no CRS metadata, the wizard prompts for tenant-admin declaration with WGS84 as suggested default but with the explicit warning: "WGS84 is the international standard. If your data is in a local archaeological grid (e.g., site-specific Cartesian coordinates), entering WGS84 here will silently corrupt the spatial relationships. Confirm WGS84 only if your coordinates are in lat/lon decimal degrees." Wave 1 (Phase B.5) ships this as a manual confirmation flow; Wave 2 (gated on AI orchestration) auto-detects CRS from sample geometries (e.g., values outside [-180, 180] × [-90, 90] range signal non-WGS84).

3D coordinate support: PROJ + PostGIS support 3D transformations. GEOMETRY SlotKind accepts 2D + 3D coordinate arrays per RFC 7946 Position spec. 3D rendering deferred to existing spa/src/pages/three_d_model/ viewer via ke:supportsThreeDDrillIn capability URI (linked from MapView per Spec 0019).

D6 — MapLibre GL JS substrate library​

Decision: MapLibre GL JS is the client-side rendering substrate. Resolves Spec 0019 brainstorm §Open Question §1.

Why MapLibre:

  • vs Leaflet: MapLibre is vector-tile-native + WebGL-accelerated; Leaflet is raster-tile + DOM-based. Integrative-tenant scale (raster-heavy orthophotos; vector-heavy N=10k+ archaeological finds) needs WebGL throughput.
  • vs Mapbox GL JS: MapLibre is the BSD-3 open-source fork of Mapbox GL JS v1 (Mapbox v2+ went proprietary). Feature parity; no vendor lock-in.
  • vs OpenLayers: OpenLayers is comprehensive but heavier; MapLibre is leaner + WebGL-first.

License: BSD-3-Clause. Bundle cost: not stated in official MapLibre GL JS docs as of v5.24.0 (the "~600KB" estimate in v1.0 of this ADR was unverified author-knowledge per R1d N18 speculation-creep watch). Phase B.3 ratification gate: actual bundle cost MUST be measured at build time + reported in the Spec 0019 MapView design.md KeMapSurface.tsx Phase B.3 deliverable; the measurement gates the lazy-load-on-mount strategy (if the bundle is materially larger than expected, the main app bundle's TTI budget needs revisiting).

Plugin ecosystem: maplibre-gl-draw (vector-feature editing), maplibre-gl-geocoder (gazetteer integration via ADR-039's ke:supportsGazetteerLookup capability URI).

D7 — Tile server architecture v1​

Vector tiles: served from PostGIS via ST_AsMVT() aggregation function. Platform exposes /api/vt/{z}/{x}/{y}.pbf (Mapbox Vector Tile format; consumed natively by MapLibre). Each request hits PostGIS once via parameterized SQL selecting features within the tile bbox + applying tenant's spatial-permission filter (ADR-035) + serializing via ST_AsMVT. No separate tile-generation pipeline; tiles computed on-demand with HTTP caching headers.

Raster tiles: NOT generated by the platform at v1. Tenants provide raster basemap data via:

  1. Pre-tiled raster upload: tenant uploads GeoTIFF + TileJSON + pre-tiled raster directory ({z}/{x}/{y}.png). Platform serves statically. Tenant generates tiles via gdal2tiles.py, rio-cogeo, tippecanoe.
  2. External WMS URL: tenant declares WMS URL in tenant config; MapView consumes directly via MapLibre's raster-dem + raster source types.

Why no platform-generated raster tiles at v1: raster tile generation from GeoTIFF inputs is computationally expensive + storage-intensive. The integrative-tenant pattern (terabyte-scale orthophotos) would require dedicated infrastructure (object storage + tile-rendering pipeline) not justified for the three-pilot reality. v1 ships consumption; production-grade tile generation deferred to first integrative-tenant onboarding + commercial evaluation.

Honest framing of onboarding cost (v1.1 — explicit re R1d N12 critique): requiring tenants to self-manage tile generation IS a real onboarding cost. For tenants with archaeological-fieldwork workflows generating fresh quarterly orthophotos, the gdal2tiles.py + COG + TileJSON pipeline is non-trivial GIS-tooling expertise. The v1 platform doesn't paper over this: tenants either (a) bring GIS expertise OR (b) outsource tile hosting to an external WMS provider OR (c) wait for v2/cloud-native tiling. When the first integrative tenant signals onboarding intent without GIS tooling capability, the platform's response is to evaluate building the utility script (or the cloud-native pipeline) at that point — driven by actual tenant evidence, not pre-built for hypothetical demand. The architectural commitment at v1 is "the consumption path works; tile generation is tenant-side"; the operational commitment is "when a tenant needs more, we evaluate then."

v2 / future paths: cloud-native raster tiling via TiTiler + s3-backed COG (Cloud Optimized GeoTIFF). Pre-evaluated as next iteration target; not committed at v1.

Alternatives Considered​

Avoid PostGIS; store geometry as JSONB​

Why not chosen: spatial queries via application-layer code are 100-1000x slower than PostGIS. PostGIS's GIST index + native spatial functions are the unambiguous standard.

Standalone triple-store (Apache Jena Fuseki + GeoSPARQL endpoint)​

Why not chosen: requires synchronizing two storage systems; triple-store sync is fragile; query optimization differs. PostGIS translation (D4) delivers the same functional capability without parallel-storage overhead. Deferred to Phase C.

Mapbox GL JS instead of MapLibre​

Why not chosen: Mapbox GL JS v3 requires Mapbox account + paid tile-server subscription. Vendor lock-in. MapLibre delivers feature parity without commercial constraints.

Defer the spatial substrate to a future ADR​

Why not chosen: covered in ADR-039 §"Why Place can't move text-centric like Period did." Place is geometry-bound; the substrate + preset ratify together.

Consequences​

Positive​

  • Standards-conformant spatial queries. GeoSPARQL + GeoJSON RFC 7946 + EPSG codes + WKT serializations native via PostGIS function mapping + PROJ.
  • PostGIS performance + ecosystem. Battle-tested across two decades of GIS deployments.
  • MapLibre WebGL throughput. Integrative-tenant scale (10k+ features, raster basemaps) at 60fps on commodity hardware.
  • CRS pluralism. Tenants with local-grid coordinate systems accommodated via per-slot SRID declarations; PROJ handles transformations at federation-query time.
  • Vector tile server is part of the platform. ST_AsMVT() aggregation means no separate tile-generation pipeline.
  • GEOMETRY SlotKind Threshold-C amendment unblocked.

Negative​

  • PostGIS install adds dev-environment complexity. Mitigation: docker-compose image change is one-line config update.
  • Vector tile endpoint is a new performance-critical path. Mitigation: D8 performance commitments + benchmark coverage; HTTP caching headers.
  • Raster basemap responsibility shifts to tenants. Mitigation: Phase B.5 onboarding doc.
  • Cross-CRS reprojection adds query latency (~10-20% overhead). Mitigation: materialized views for high-traffic CRS pairs deferred to Phase B.4.
  • No public GeoSPARQL endpoint at v1. Mitigation: projection layer emits GeoSPARQL-conformant JSON-LD; deferred to Phase C.
  • 3D-coordinate support is shallow at v1. MapLibre is fundamentally 2.5D; true 3D rendering lives in existing three_d_model/ viewer.

Mitigations​

  • Phase the implementation. B.1 ships PostGIS + GEOMETRY SlotKind; B.2 ships GeoSPARQL→PostGIS translator; B.3 ships MapLibre + vector tile endpoint; B.4 ships performance tuning + benchmark.
  • Reuse ADR-022 Anchor substrate. Anchor.source_type=GIS_GEOMETRY rows already exist as a contract; ADR-041 adds storage substrate.
  • Bound vector-tile endpoint performance via materialized views when benchmark identifies slow patterns.
  • Document tenant raster-tile generation. Phase B.5 onboarding doc walking through gdal2tiles.py + rio-cogeo + TileJSON.

  • Vector-tile cache strategy (HTTP headers + Nginx-level cache for /api/vt/).

Phase B.5 — Production-grade tenant raster-tile workflow​

  • Tenant-facing doc: raster-tile generation walkthrough.
  • Pre-tiled raster upload + static serve (or external WMS URL declaration).
  • Tenant migration playbook: integrative-tenant onboarding includes raster basemap setup.

What this ADR does NOT specify​

  • Cloud-native tile generation (TiTiler + s3-backed COG) — deferred to Phase C.
  • Public GeoSPARQL endpoint — deferred to Phase C.
  • 3D point-cloud + mesh rendering — existing three_d_model/ viewer; cross-surface integration is Spec 0019.
  • Per-tenant tile-hosting commercial model — operational; separate decision.

Compliance​

Foundational principle​

Canonical Structure Is Shared; Interpretation Is Tenant-Specific. The substrate (PostGIS + GeoSPARQL semantics + MapLibre + tile endpoint) is platform-canonical; the CRS choice + raster basemap content + tile-server hosting are tenant-supplied. Boundary preserved.

Open Questions​

  1. PostGIS minor-version pinning: pin to 3.4 or allow 3.4 + 3.5? Recommend: support 3.4 + 3.5; pin 3.4 minimum. Resolved in Phase B.1.
  2. Vector tile cache strategy: HTTP cache headers, Nginx-level cache, or CDN-fronted? Recommend: HTTP headers + Nginx cache at v1; CDN deferred. Resolved in Phase B.4.
  3. Materialized view triggers for high-traffic CRS pairs: when does the platform pre-compute reprojected geometry? Recommend: tenant-admin-declared OR auto-triggered at 1k queries/day. Resolved in Phase B.4.
  4. 3D rendering integration depth: embed inline vs link out? Recommend: link out for v1. Resolved in Spec 0019 design.md.
  5. Public GeoSPARQL endpoint via Apache Jena Fuseki: when does the platform commit? Recommend: Phase C when use-case evidence justifies.
  6. Tile-generation cost model for raster basemaps: who pays for cloud-native generation infrastructure (Phase C+)? Operational; deferred.
  7. GIST vs SP-GIST vs BRIN index choice: any spatial table crossing 1M rows re-evaluated. Recommend: GIST at v1; BRIN gate at 1M rows; SP-GIST gate at k-NN patterns. Resolved per-table in Phase B.4.
  8. <platform-domain> placeholder resolution: same as ADR-039 §Open Question §0. File alongside §O0 as single platform-naming + infrastructure decision.
