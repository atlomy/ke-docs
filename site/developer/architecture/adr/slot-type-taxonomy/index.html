ADR-037: Slot-Type Taxonomy and Tenant Vocabulary Layer

Status: Accepted (2026-05-20 — ratified per Option D.2 binding-shape ratification with decision-log deferrals; see docs/developer/architecture/adr-037-ratification-brief.md. Five amendments folded in below; operational details deferred to docs/decisions/log.md. Federation-contract layer commitments deferred to ADR-038 — Federated Preset Registry as Federation Contract.) Date: 2026-05-19 (drafted) / 2026-05-20 (ratified) Deciders: User; architecture team Related: ADR-002 (Hybrid Ontology — Relational + JSON), ADR-004 (Tenant Ontology Mapping), ADR-028 (Plate Editor for v2), ADR-035 (Tenant Contributor Permission Model), ADR-036 (Workspace/Operations Surface Split), docs/developer/architecture/platform_principles.md Supersedes: nothing Scope-extends: ADR-002 (codifies the slot-level expression of the hybrid ontology), ADR-004 (extends tenant-label mapping from archetype to slot) Companion: docs/design/2026-05-19_slot-type-taxonomy-rework-brief.md (Claude Design brief for the workspace surface)

TL;DR​

KE has been conflating three orthogonal concerns under a single "widget" / "field type" label:

  1. What can exist — the canonical primitive: text, number, date, relation, etc. (platform-owned, shared)
  2. How it is parameterised — multikey discriminator, composition template, numeric format, target archetype, etc. (platform-owned vocabulary, tenant-supplied values)
  3. What the tenant calls it — "Lemma", "Transliteration", "Editorial register", "Vocalised form" (tenant-owned)

The pass-2 workspace design proposes a 22-tile field-type vocabulary that mixes all three layers, baking tenant specialisations (e.g. "Transliteration" — an Atlas-only Greek→Latin slug-derivation pattern) into platform code. This regresses against the foundational principle (platform_principles.md): Canonical Structure Is Shared; Interpretation Is Tenant-Specific.

This ADR codifies the three layers and binds the workspace UI to the canonical layer, with tenant naming and presentation handled in a separate vocabulary layer.

Layer 1 — SlotKind        ← platform canonical (currently ~10 values; open set, see "Evolution")
Layer 2 — SlotModifiers   ← platform-defined parametric vocabulary; field set grows as tenants reveal new primitives
Layer 3 — TenantPreset    ← per-tenant catalog of named (SlotKind, Modifiers) recipes
            ↓
          UX picker       ← the "22 icons" become tenant-curated presets, not schema entries

This is a snapshot, not a closure. The current SlotKind list and SlotModifiers vocabulary reflect what three pilot tenants (Atlas, JPP, Visionis) have shown us so far — and not even the full scope of what those three pilots need. The three-layer model is what we believe is durable; the contents of Layers 1 and 2 will grow as real tenants and real use cases reveal primitives we haven't seen yet. The "Evolution of the taxonomy" section below names the promotion path so that growth happens deliberately, not by accident.

Context​

The accidental tenant leak​

The workspace pass-2 design's 22-type field vocabulary (docs/design/handoff/workspace/01-prototype/atoms.jsx) lists tiles including text, richtext, lang (Multilingual), translit (Transliteration), number, year, currency, date, select, multiselect, bool, user, lookup, relation, media, audio, video, file, link, embed, email, color.

Three of these tiles are tenant-extrapolation rather than canonical platform vocabulary:

Design tileWhat it actually isTenant evidence
translit (Transliteration)TEXT + multikey + (often) composition_templateAtlas only — Greek→Latin slug derivation for URLs. JPP would call the analogous mechanism "vocalised form"; Visionis would name it differently or not at all.
lang (Multilingual)TEXT + multikey, key set = languagesAtlas has language variants; JPP needs editorial register variants (original / translation / notes); Visionis may need edition variants
year (Year)NUMBER + numeric_format=yearAtlas uses 4-digit lifespan years for AUTHOR; JPP works with regnal years; Visionis may use radiocarbon (BP)

All three collapse into the same underlying schema move: canonical primitive + parametric modifier + tenant-supplied label. The icon is a UX shortcut, not an ontology entry; atoms.jsx names the Multilingual and Year tiles lang and year, while their icon IDs are tlang and tyear.

This pattern crossed the line that platform_principles.md draws: "Tables define what can exist. JSON defines how it is expressed." Once "Transliteration" is a platform-level type, future tenants either inherit Atlas-specific semantics they don't need or are forced to fork the platform vocabulary — both failure modes of the canonical/interpretation boundary.

The backend is already more general than the proposed design​

The current TenantArchetypeFormConfig model (atlomyapp/models.py:329–644) defines an 11-value Widget enum (text, richtext, number, date, boolean, select, multiselect, linked_record, lookup, array, media) plus a rich set of parametric modifier fields:

  • multilingual: bool — turns the slot into a key-value list
  • script: str — Unicode script (greek/arabic/latin)
  • language: str — ISO 639 code
  • accent_fold: bool — diacritic normalisation
  • composition_template: str — str.format pattern (e.g. '{lemma}, {morph_1}, {morph_2}') ✱
  • composition_skip_empty: bool
  • target_archetype: str + target_archetypes: [str] — for RELATION/LOOKUP
  • target_field, display_field, lookup_for — for LOOKUP projections
  • resolver_kind, resolver_args — direct | fk_walk | string_match | composed

✱ composition_template already exists and is in production use. Atlas's lemma_full field is computed via this mechanism today. The workspace design's 22-tile vocabulary, however, has no "Composed" tile — composition is invisible at the researcher UX layer despite being a load-bearing feature.

So the backend is already closer to the right model than the proposed design surface. This ADR codifies what the backend implicitly knows and binds the UI to it.

Three-layer write authority (extends ADR-004)​

ADR-004 established that archetype labels vary by tenant (TERM → "Lemma" in Atlas, "Lexical Root" in Visionis). The same pattern applies to slot labels and slot presets: the canonical kind is shared, the tenant-facing name and curated configuration is tenant-owned. ADR-037 extends ADR-004's label mapping from archetype-level to slot-level and adds a tenant-preset catalog.

Decision​

Layer 1 — SlotKind (canonical, current snapshot: 10 values, open set)​

Rename the inner enum TenantArchetypeFormConfig.Widget → TenantArchetypeFormConfig.SlotKind. The field name widget remains for backward compatibility but is documented as "the SlotKind primitive — see ADR-037".

Current snapshot (derived from three pilot tenants, expected to grow):

KindBackend storageSemantics
TEXTCharField / TextFieldSingle-line or multi-line string. Multi-key variants (language / register / script / edition) live in modifiers, not here.
RICHTEXTTextField storing Plate JSONBlock-structured rich content per ADR-028.
NUMBERDecimalFieldInteger or decimal. Format (year / currency / percent / duration) lives in modifiers.
DATEDateField / DateTimeFieldDate or datetime.
BOOLEANBooleanFieldTrue / false.
SELECTCharField storing enum valueSingle choice. Options live in modifiers, not in the model.
MULTISELECTJSONField (list of enum values)Multi-choice. Replaces today's ARRAY enum value (collapsed).
RELATIONvia EntityRelationshipEdge to another row. Target archetype lives in modifiers.
LOOKUPderived (read-only)Read-only projection through a relation. Target field lives in modifiers.
MEDIAFK to MediaBinary attachment. Image / audio / video / file kinds live in modifiers, not as separate SlotKinds.

Dropped from existing enum: ARRAY (collapsed into MULTISELECT via modifier semantics).

Currently expressed via modifiers, not as separate SlotKinds: image, audio, video, file (MEDIA + media_kinds); link, email, embed (TEXT + text_role or MEDIA + media_kinds: [embed]); year, currency, percent, duration (NUMBER + numeric_format); multilingual, transliteration (TEXT + multikey:true).

Why open set, not closed: Three pilot tenants do not cover the full space of scholarly data. Likely future candidates include GEOMETRY (spatial / GIS-bound data for tenants with map archetypes), TIME_RANGE (fuzzy historical date intervals where DATE is too precise), EMBEDDING (vector content for AI-assisted retrieval), COORDINATE (3D-mesh anchors, IIIF regions). None of these are added today — but the model must allow them to land without a UX redesign. The "Evolution of the taxonomy" section below names the promotion path.

Layer 2 — SlotModifiers vocabulary (current snapshot, open set)​

The modifier set is platform-defined (the schema of which modifiers exist and what their values mean is canonical); the values per slot are tenant-supplied. The current modifier list is what three pilot tenants have revealed so far; it is expected to grow as new tenants and use cases land. See "Evolution of the taxonomy" for the promotion path.

Already on TenantArchetypeFormConfig (keep):

  • multilingual: bool
  • script: str
  • language: str
  • accent_fold: bool
  • composition_template: str
  • composition_skip_empty: bool
  • target_archetype: str
  • target_archetypes: list<str>
  • target_field: str
  • display_field: str
  • lookup_for: str
  • resolver_kind: enum
  • resolver_args: jsonb

Added by this ADR (all nullable, default-falsy):

  • multikey_kind: enum(language, register, script, edition, calendar, custom) — discriminates the multi-key role. Default for existing multilingual=True rows backfilled to language. Defining JPP's original_greek + modern_hebrew + editorial_note becomes multilingual=True + multikey_kind=register + (tenant-declared key set in modifiers). calendar value added 2026-05-20 (R2 absorption B3): empirical evidence from Visionis AUTHOR dual-calendar authoring (TIME OF LIVING HIJRI + TIME OF LIVING GREGOR columns side-by-side) + the integrative-tenant multi-calendar pattern (Gregorian / Hijri / Hebrew AM / Yuan / BP / radiocarbon-calibrated). Slots with kind=TIME_RANGE + multikey_kind=calendar carry multiple calendar-system values per row.
  • multikey_keys: list<str> — optional tenant-declared key set when the runtime is not free-form (e.g., JPP's three editorial registers).
  • numeric_format: enum(integer, decimal, year, currency, percent, duration) — for NUMBER.
  • currency_code: str (ISO-4217) — for NUMBER + numeric_format=currency.
  • precision: int — for NUMBER decimals.
  • text_role: enum(plain, url, email, phone, embed) — semantic role for TEXT.
  • enum_options: jsonb (list of {value, label, color, order}) — for SELECT and MULTISELECT. Replaces today's lean on import-config JSON for the option list, so tenants without an import config can still curate options.
  • media_kinds: list<enum(image, audio, video, file, embed)> — restricts MEDIA to specific binary types.
  • relation_cardinality: enum(one, many) — for RELATION.

Migration discipline: every new field is nullable, default-falsy. Existing rows continue to work. A one-shot data migration backfills multikey_kind='language' for rows where multilingual=True. No widget value loses data.

Layer 3 — TenantPreset catalog​

The "22 icons" in the workspace design become a starter preset library shipped by the platform. Each preset binds a (SlotKind, Modifiers) recipe to a friendly label and an icon. Tenants can override labels, add their own presets, and remove starter presets they don't use.

TenantSlotPreset (new model):
  tenant: FK to Tenant
  preset_id: str (slug, unique per tenant)        e.g. "text-single", "atlas-transliteration"
  label: str (tenant-facing display)              e.g. "Text", "Transliteration"
  icon: enum (one of the 22 ke-icon names)        e.g. "ttext", "ttranslit"
  description: str (tenant-facing hint)
  slot_kind: enum (one of Layer 1 SlotKinds)
  modifiers: jsonb (Layer 2 values)
  is_platform_default: bool (true for starter presets, false for tenant-added)
  display_order: int

Atlas can add atlas-transliteration as a tenant preset (TEXT + multikey:true + multikey_kind=script + composition_template="{lemma}-{roman}") without that pattern leaking into platform code. JPP can add jpp-editorial-register (TEXT + multikey:true + multikey_kind=register + multikey_keys=["original","translation","notes"]).

Platform starter library (16 presets, intentionally fewer than 22 to avoid encoding Atlas specialisations or non-archetype operational directories as defaults): Text · Rich text · Multilingual text · Composed text · Number · Year · Currency · Date · Select · Multi-select · Checkbox · Linked record · Lookup · Media · URL · Email — covering the canonical primitives + the genuinely-cross-tenant variants. Image / audio / video / file presets are filed under Media; embed is filed under URL or Media depending on context.

Widget enum rename​

Rename TenantArchetypeFormConfig.Widget → TenantArchetypeFormConfig.SlotKind (inner Django class). The field name stays widget to avoid a churny migration on every callsite. A docstring on the model field points to this ADR.

If a cleaner rename is wanted later, file a separate decision-log entry — this ADR does not require the field rename.

GraphQL surface​

Extend TenantArchetypeFormConfigType (atlomyapp/graphql/schema.py:76) to expose the new modifier fields (multikey_kind, multikey_keys, numeric_format, text_role, enum_options, media_kinds, relation_cardinality, currency_code, precision). Add a new GraphQL type TenantSlotPresetType and a query tenantSlotPresets(archetype) returning the merged platform-default + tenant catalog.

The frontend resolves (SlotKind, modifiers) → preset at read time; the preset drives icon, label, and cell-editor routing.

Frontend taxonomy​

Frontend introduces a slotTypeRegistry.ts module (spa/src/apps/tenant_admin/workspace/slotTypeRegistry.ts) that mirrors Layer 1 + Layer 2 as TS types and exposes the platform starter library as a constant. KeIcon.tsx ports the 22 icons from atoms.jsx as a presentation library — pure UX, no schema coupling.

The workspace ColumnHeaderPolish, SchemaEditModal, FieldEditor, and MultilingualCellEditor route on (kind, modifiers) — not on the legacy widget string alone — and consume tenant presets via the new GraphQL query.

Evolution of the taxonomy​

This ADR pins the three-layer model as durable: canonical primitive (Layer 1) / parametric vocabulary (Layer 2) / tenant-curated recipes (Layer 3). The contents of Layers 1 and 2 are explicitly open. The three pilot tenants (Atlas, JPP, Visionis) do not cover the full space of scholarly data — they are early observations, not the reference. Real tenants (and even further work inside the three pilots) will likely reveal:

  • New SlotKinds the platform doesn't have yet (e.g. GEOMETRY, TIME_RANGE, EMBEDDING, COORDINATE).
  • New modifier fields (e.g. calendar_system for non-Gregorian years, confidence_tier for AI-assisted slots, geometry_kind for points vs polygons).
  • New modifier values inside existing modifier fields (e.g. additional multikey_kind values beyond language/register/script/edition).
  • New tenant presets that recur across enough tenants to deserve promotion to platform-default.

The promotion path defines how additions happen, modelled on platform_principles.md §"When Do We Add a New Archetype?":

When to extend ADR-037 vs supersede it​

  • Extend (amend this ADR) when: adding a new modifier field, adding a new modifier value, promoting a preset, adding a new SlotKind that fits the three-layer model.
  • Supersede (file ADR-037 successor) when: the three-layer model itself is wrong for a tenant's data, the canonical/interpretation boundary needs redrawing, or a new architectural concept (e.g., slot composition across archetypes) demands its own ADR.

Evolution anti-patterns​

  • ❌ Adding tenant-specific names to the platform starter library because "everyone is asking" (they aren't — re-check the count; usually it's one loud tenant).
  • ❌ Adding a new SlotKind when a modifier would suffice ("Year" is not a SlotKind; "GEOMETRY" might be).
  • ❌ Locking the SlotKind enum on the assumption that the three pilot tenants are the reference (they are not; they are early observations).
  • ❌ Letting a tenant preset turn into a platform-required preset by stealth (every promotion is an explicit decision).
  • ❌ Treating the "currently 10 SlotKinds" line as a closure of the platform's data vocabulary.

What this is NOT​

  • A frozen vocabulary. The platform's data primitive set will grow as we learn from real tenants.
  • An exhaustive enumeration of every modifier we will ever need. The modifier set is a snapshot tied to today's observed needs.
  • A claim that the three pilot tenants are representative of all future tenants. They are not. Treat their needs as anchoring evidence, not as bounds.

Consequences​

Enabled by this decision​

  • Cross-tenant onboarding without platform forks. A new tenant declares their presets in their own catalog; platform vocabulary is untouched. JPP onboarding becomes a configuration exercise, not a platform change.
  • Composition surfaces in the researcher UX. Atlas's lemma_full becomes a researcher-visible "Composed text" preset (already-existing composition_template lit up in the workspace), not an invisible backend feature.
  • Multikey generalisation. Multilingual text, transliteration, editorial registers, and edition variants all share one primitive (TEXT + multikey:true) with multikey_kind discriminator. The frontend MultilingualCellEditor becomes a generic MultiKeyTabs component.
  • Tenant-vocabulary lint coverage. scripts/lint_no_tenant_vocabulary.py already gates platform code against tenant-specific strings; this ADR moves "Transliteration" / "Editorial register" / similar tenant-specific presets into tenant config where the lint correctly ignores them.
  • Backward compatibility. Existing rows keep working. The migration is additive (nullable fields, one data backfill for multikey_kind).

Costs​

  • One migration cycle. Adding 8 nullable fields + creating TenantSlotPreset. Pre-production rebuild keeps this cheap; in-production this would be more careful.
  • Frontend rework. The workspace design's 22-tile picker becomes the preset-library picker. Implementation cost is on the workspace pass-2 branch; the work was already in scope (the design's ColumnHeaderMenu has the nested-search structure; this ADR sharpens what populates it).
  • GraphQL schema additions. Backwards-compatible (new optional fields + new query).

Risks​

  • Tenant-preset CRUD UI. The workspace SchemaEditModal needs a path for tenant admins to author presets. If we defer this past v1, tenants will lean on platform defaults and we re-create the "platform tile is too specific" pressure from the other direction. Mitigation: ship the starter library wide-but-shallow in v1, build preset-CRUD in a follow-up sprint, accept the constraint that v1 tenants pick from the starter library + can override per-slot via the existing modifier fields.
  • Per-key provenance is deferred. Tracking which DecisionEvent approved which language / register value (Problem B in the framing discussion) is real but not blocking. Filed in docs/decisions/log.md with trigger condition: when JPP onboarding makes register-level audit trails a real concern.
  • Lookup vs. Relation conflation. Today's lookup and linked_record widgets stay distinct. Some tenants may discover they want richer lookups (multi-hop, filtered, aggregated). Out of scope for this ADR; ADR-002 + ADR-004 already constrain how that work would happen.

What this prevents​

  • Encoding "Transliteration" as a platform field type, which would force every future tenant to either inherit Atlas semantics or fork.
  • Encoding "Year" as a platform field type, which would constrain non-Gregorian-calendar tenants.
  • Encoding the 22-tile picker as the canonical schema, which would conflate UX presentation with platform structure.

Post-R1 corrections (2026-05-19)​

After the Round-1 critique audios + user review surfaced knowledge layers the round had missed, this ADR is amended below to reflect the actual platform architecture. Four corrections.

Correction 1 — accent_fold is universal capability, not Atlas bias​

The Round-1 absorption devlog (concern A3) flagged accent_fold and script as possibly Atlas-extrapolated modifiers. This is wrong. Both are part of the Linguistic Autonomy architectural strand from Phase 2a/2b (devlog docs/devlogs/2026_w18/2026-05-02_1014_phase-2-linguistic-autonomy.md).

  • script lives in epistemic/services/language_detection/detection.py. Unicode-script-aware (cjk → han normalisation, modifier-letter Lm exclusion for the §3a.2 Apostrophe Exception across Greek elision + the four apostrophe conventions). Tenant-overridable.
  • accent_fold carries Policy A (broader recall via diacritic stripping; default for index-time) vs Policy B (precise letter-identity for Scandinavian å, Vietnamese tonal precision, Turkish dotted/dotless I). Per-slot, per-tenant override. Phase-2e Subfield Hybrid Precision (.folded + .raw subfields) is the future cleanup for query-time mixed-policy handling.
  • Both fields are documented in docs/decisions/2026-05-03_slot-config-capability-flags.md § "Already shipped".
  • Long-tail empirical audit at docs/research/2026-05-03_long-tail-fold-audit/findings.md.

Disposition: Phase A "modifier audit" obligation is withdrawn for accent_fold and script. They are universal capabilities; no audit needed. The AUDIT: comments in spa/src/lib/slot-taxonomy/modifiers.ts are corrected to point at the Linguistic Autonomy devlog.

Correction 2 — Don't invent a "Discipline / community" tier​

A naive reframe proposed adding a "Tier 3 — Discipline / community conventions" layer (classics shares transliteration; medicine shares anatomical-classification; …). This conflicts with an existing architectural decision.

docs/superpowers/specs/0017-import-wizard-ux-overhaul/design.md records (2026-05-17 Builder ratification walk): the domain-archetype dropdown was proposed and explicitly WITHDRAWN on three grounds:

"(1) the dropdown adds onboarding friction that conflicts with the make-or-break first-import design constraint; (2) any fixed enum mis-categorizes researchers from non-registered fields; (3) within-domain heterogeneity is severe — within 'humanities' alone, Classics is epistemically very different from music theory or media studies, and the claims/evidence trails differ across those subfields more than they differ across some humanities/STEM pairings."

The platform's chosen approach (ADR-033 §4.2): keep domain_archetype as an optional stratification axis, populated via tenant-admin configuration (not import-time researcher input). Synthetic out-of-distribution probes (biomedical-longitudinal, geospatial-appendonly, social-survey) validate cross-domain at calibration time per ADR-033 §5 Step 2.

Translating to ADR-037: the existing three-layer model is correct. Cross-tenant convention sharing happens via:

  • Promotion thresholds (ADR-037 §Evolution) — when ≥2 tenants independently author the same preset, consider promoting to platform-default. This is the architectural mechanism for "classics convention emergence" without baking a fixed enum.
  • Institutional standards declarations (see Correction 3) — TEI, CSL, CIDOC/Linked Art are the durable cross-tenant standardisation vector. A slot can declare TEI-XML compliance as a modifier; downstream interoperability flows from the standards declaration, not from a discipline label.
  • Cross-tenant preset import/export (deferred to Phase B / future ADR) — once tenants can author presets, they can share via opt-in export. This handles "Atlas's transliteration preset shared to a future Byzantine Greek tenant" without the platform owning a "classics library."

Disposition: the naive Tier 3 proposal is withdrawn. The three-layer model stays. What changes is the vocabulary used to describe how presets propagate (promotion thresholds + standards declarations + tenant-to-tenant import/export), not the number of layers.

Correction 3 — Institutional-standards layer ALREADY EXISTS​

The reframe proposed adding "standards compliance" as a new architectural concern. This work is already in flight:

  • ADR-030 — CIDOC + Linked Art Export Profile (Accepted 2026-05-11). Exposes shape-level fixtures that prove EntryProjection retains identifiers, relationships, citations, media refs, and provenance sufficient to support CIDOC-family export.
  • Spec 0008 — Citation Framework + CSL (Implementation landed 2026-05-09 per docs/devlogs/2026_w19/2026-05-09_1432_sprint-0008-phase2-backend.md). TenantCSLStyle model stores CSL XML per tenant. Citation framework operational. See epistemic/services/csl_projector.py + epistemic/services/citation_renderer.py.
  • docs/internal/program/07-standards-sustainability-and-business-model.md — internal/gitignored strategic positioning: minimum-viable accepted (DOI, RO-Crate + BagIt, IIIF + Web Annotation, CSL); richer integrations (Zotero, Crossref, ORCID, CIDOC, Linked Art) layer on per-pilot. This is private program context, not a repo-resolvable dependency.
  • docs/research/standards/CROSSWALK.md — standards crosswalk matrix maintained.
  • docs/research/2026-05-11_spec0009-deep-review/02_standards_and_interop.md — standards integration strategy.

Phase A addition (small): add a complies_with: list[str] modifier to the SlotModifiers vocabulary. Values are standard ids drawn from a platform-canonical list (TEI, CIDOC-CRM, IIIF-Presentation, IIIF-3D, LinkedArt, MARC, RO-Crate, BagIt, CSL, GeoJSON, …). Declaration-only in Phase A — a tenant admin marks "this slot's data complies with TEI" but no Phase A code validates that compliance. Downstream export tooling (ADR-030 CIDOC export, future TEI/IIIF export) consumes the declaration to decide which slots to project.

This is a modifier addition, not a new tier. The three-layer model holds.

Correction 4 — JPP framing in Round-1 sources is wrong​

The Round-1 tenant-needs primer described JPP as "medieval Hebrew + Latin biographical records." The actual JPP, per the 2026-04-26 platform-learnings devlog (docs/devlogs/2026_w17/2026-04-26_session-conclusions-and-platform-learnings.md):

  • Mongol-era prosopography (Yuan dynasty + earlier). Sample person: Temüjin (Genghis Khan).
  • 47,727 EpistemicEntity rows capped at 2,000 per source table, across Person / Name / Place / Tribe / Period / Report / Keyword archetypes.
  • Denormalised relational model: a person record intertwines names + keywords + places + reports + tribes + periods. Temüjin example: 77 keywords, 39 places, 82 reports (passages/documents), 11 tribes, 18 periods, 4 alternate names.
  • Han characters are the dominant script for the source material; Hebrew may be present but is not the main concern. The search-engine work flagged "Han+Latin dominant (Yuan-era prosopography names matched earlier n=200 finding)."
  • Key search challenge: word segmentation for CJK content, not character normalisation (Han ideographs have no Latin transliteration that preserves searchability across word-boundary norms).

The Round-1 primer's "Hebrew + Latin" framing fed into every R1 audio + the absorption devlog. Implications:

  • The "Editorial register" use case (original_hebrew / modern_hebrew / english / notes) attributed to JPP needs reconsideration — JPP's actual editorial registers (Han source / scholarly transliteration / English translation / period notes / tribe-genealogy notes?) need cross-checking with JPP team.
  • The multikey_kind=register discussion is still useful in principle; the example presets should be drawn from the actual JPP shape.
  • The Person ↔ Name ↔ Place ↔ Tribe ↔ Period ↔ Report ↔ Keyword denormalisation is the most complex relational shape currently in the platform — richer than Atlas's TERM ↔ TREATISE ↔ AUTHOR linkage. The slot-taxonomy work must accommodate this density. The RELATION SlotKind + target_archetypes (multi-target) + relation_cardinality=many already handle it structurally; the question is whether the picker UX makes it easy to author 6-way denormalised relations on a Person archetype without overwhelming the researcher.

The Round-1 sources at docs/internal/research/2026-05-19_slot-type-taxonomy-round1/ are local-only (gitignored); they are amended in-place to correct JPP framing.

Post-R1 Addendum (2026-05-19, after audio debate v2 convergence + integrative-tenant evidence)​

A second debate audio (fired with sources + a "look at other sources when conceptual/architectural topics surface" directive) converged on every disposition in the corrections above. The audio independently surfaced the per-register-undo / per-mapping-undo compatibility concern (matches B2) and the governance-softness-under-commercial-pressure concern (matches A5). It added one devastating concrete example that strengthens the 22→15 starter-library prune:

"Imagine an archaeologist logging a radiocarbon date of 12,000 before present. They see a convenient tile labeled year. So they click it... It expects a four-digit integer. It silently truncates 12,000 to 1200. We didn't just give them a bad user experience. We literally erased 10,000 years of human history from their data set because we were too hesitant to separate our foundational schema from our UI buttons."

The "silent data corruption from a false default" framing is the production rationale for the prune — it's not architectural purity, it's research integrity. Applies cross-discipline: BP dates (archaeology), regnal years (medieval studies), Hijri calendar (Islamic studies), Hebrew anno mundi (rabbinic studies), Yuan/Tang/Song dynasties (Asian studies), radiocarbon ranges (geosciences), MYA (paleontology). Any tenant whose dating convention is not 4-digit Gregorian would be silently corrupted by a platform-default year tile.

The three-surface publication contract (binding for Phase A)​

KE's data must render coherently on three surfaces simultaneously. Phase A's complies_with modifier is read by each surface differently:

The three surfaces are the same data rendered through different projections. The platform_principles.md foundational rule applies — canonical structure is shared; interpretation is tenant-specific — extended to the publication layer: canonical claims are shared; surface rendering is audience-specific.

Implications for Phase A:

  • Every Phase A SlotKind + modifier addition must answer "how does this render on each of the three surfaces?" If a slot type has no clear public-reader rendering, that's a design problem; if it has no clear compliance-export view, that's a standards-architecture gap; if it has no clear research-surface picker preset, that's a UX problem.
  • The complies_with modifier is the architectural hook that ties all three surfaces together. A slot declared complies_with: [TEI, CIDOC-CRM] will: (research) render with a compliance chip, (public) emit conformsTo triples, (compliance) project into TEI XML + CIDOC export views.
  • domain_archetype (ADR-033 §4.2 optional stratification) plays NO role in the publication surfaces — surface rendering is driven by the slot Kind + modifiers, not by tenant-discipline labels. This re-confirms the rejection of the naive Tier 3 discipline layer.

Reified-arguments framing (added 2026-05-20 from R2 absorption Standards-notebook nuance)​

CIDOC-CRM frames every assertion as "the opinion of someone" — every property is intrinsically reified to its actor + activity. ADR-037 + ADR-022 substrate already handles this via DecisionEvent (ADR-035 stratum / actor / capability provenance) + ClaimCluster (ADR-022 cross-source attestation chain) + the planned complies_with modifier (Phase A.1; carries standards-conformance provenance). The reification is implicit in the substrate; this paragraph makes it explicit for ratification reviewers and for downstream ADRs (ADR-038, ADR-030 SHACL shapes): slot-level assertions are reified arguments, not bare facts, and the substrate is designed so that any slot value can be traced to its DecisionEvent + ClaimCluster + complies_with declarations. No code change required; framing.

G3 — Three-Surface Demonstration Gate (added 2026-05-20 from R2 absorption B1)​

Any new Layer-1 SlotKind landing via Threshold-C amendment (per §Evolution) must demonstrate all three rendering paths via test fixtures committed alongside the amendment PR. Demonstration is required, not promised in the §Decision narrative.

  1. Public reader surface: JSON-LD output via projection-first (ADR-029) with dcterms:conformsTo triples derived from the slot's complies_with modifier values.
  2. Research workspace surface: cell editor + column header preset render the slot in the active workspace view-kind (table / details / relations / map / publish).
  3. Compliance export surface: at least one of the slot's declared complies_with targets has a concrete export view (RO-Crate / BagIt / TEI / CIDOC / IIIF / CSL / GeoSPARQL / GeoJSON / PeriodO / etc.) that emits a non-empty, non-corrupted payload.

Programmatic governance gates (added 2026-05-20 from R1 absorption A5 + R2 sharpening)​

Architectural promotion thresholds must not rely solely on subjective human sign-off under commercial pressure ("the sales team is screaming that they'll lose an enterprise contract if a module isn't shipped by Friday"). Two programmatic gates:

  • G1 — JPP+Visionis impact analysis on Layer-1 amendment: any amendment to this ADR that adds a Layer-1 SlotKind MUST attach a documented impact analysis showing the new primitive works natively for JPP + Visionis (or post-promotion equivalents) without modifier abuse. Amendment cannot land without the analysis. Enforced at PR review time.
  • G2 — Build-time CI two-stage gate on multikey_kind=custom density threshold (v1.1 refined per post-D.2 R1 finding B3): the platform measures multikey_kind=custom density per tenant slot config. Two thresholds with distinct response:
    • Hard gate (>0.2 / 20% density): build-time CI lint step (scripts/lint_no_tenant_vocabulary.py extension OR a sibling lint) fails the pipeline. Deployment "fails the compile" until architectural review unblocks. This is the previous single-threshold behavior, now raised from 0.1 to 0.2.
    • Soft gate (0.1-0.2 / 10-20% density): build-time CI emits a structured warning + routes the slot config to architectural review without failing the pipeline. Routing target uses the existing three suppression mechanisms (sidecar override file / JSON _lint_skip marker / Python # noqa: multikey-custom-density decorator) for known-acceptable configs; un-suppressed soft-gate hits surface in a PR review checklist + a daily cron alert.
    • Below 0.1: no action.
    • Why two-stage: the previous single-threshold-at-0.1 produced too many false-positive CI failures on legitimate tenant configurations during early-stage onboarding (e.g., a new tenant in active vocabulary-development inevitably crosses 0.1 before settling). Raising the hard fail to 0.2 (the genuine "this design is broken" signal) + adding a soft-warning band at 0.1-0.2 (the "worth a look before merging" signal) recovers PR-merge throughput without losing the safety gate. R2 absorption sharpened the original G2 from runtime "Slack alert + write-block" to build-time CI failure; B3 sharpens further to two-stage with explicit review routing for the middle band. Daily cron retained as a secondary alert path for non-CI-routed changes (direct database writes, etc.).
