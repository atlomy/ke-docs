ADR 046: Workspace Operation Ledger For Authoring Undo/Redo

  • Status: Superseded by docs/superpowers/specs/2026-05-26-event-substrate-collab-federation-design.md (2026-05-27). Concerns absorbed into §3 substrate; redo-as-new-row + operation_kind discriminator + retention policy + lint chokepoint carry forward. ADR-046's "WorkspaceOperation ledger" framing evolves into the broader event substrate; this ADR retained as historical context.
  • Date: 2026-05-26
  • Deciders: Atlomy Account, Codex, Claude
  • Context source: Workspace UI parity continuation, table undo/versioning audit, external product/open-source research sidecar
  • Related: ADR-028, ADR-029, ADR-031, ADR-034, ADR-036, ADR-044 (TipEvent two-row precedent), Spec 0027 (DRAFT-row mutations), Spec 0028, Spec 0031 (repurposed as Workspace Event Substrate)

Context​

Workspace table parity exposed a real product gap: users expect Cmd/Ctrl+Z to recover from cell edits, paste, row movement, row/column operations, and delete flows. Current v2 has pieces of the substrate but not the durable workspace contract:

  • ADR-031 source rows expose record_version and record_content_hash, but workspace updateEntity does not yet accept baseVersion or return conflict envelopes.
  • ADR-029 EntrySnapshot supports public projection latest-good/named-release rollback, but that is a publication layer, not authoring undo.
  • ADR-034 import-wizard undo covers an 8-second pre-materialization proposal reversal, not table content recovery.
  • Spec 0028 / PR #428 adds frontend-local workspace undo/redo for immediate table UX, but not cross-session or multi-user recovery.

Product and open-source review converged on a layered pattern:

  • immediate local undo/redo for short-term interaction;
  • durable row/page activity for accountability and recovery context;
  • coarse snapshots/version restore for larger recovery.

Coda, Airtable, Notion, Google Docs/Sheets, Baserow, Directus, NocoDB, and Grist do not collapse these into one mechanism. Baserow is the closest open-source precedent: it records explicit actions with do, undo, and redo behavior, while row history remains a separate audit/read surface.

Decision​

KE SHALL implement a tenant-local WorkspaceOperation ledger for workspace authoring operations, layered on top of ADR-031 record_version / record_content_hash concurrency tokens. The ledger records user-visible operations, their before/after payloads, and the source-row versions they consumed and produced. Undo and redo are backend mutations that apply inverse operations only when target rows still match the expected versions.

All workspace mutations that write to EpistemicEntity, EntityRelationship, or other source-versioned content fields MUST route through the WorkspaceOperationService chokepoint. Direct .save() calls on these models from GraphQL resolvers, ad-hoc services, or admin paths are prohibited and enforced by lint (see Spec 0031 Task 4.5). This is what makes "successful backend undo/redo is the source of truth" load-bearing across future write paths instead of degrading the first time a new mutation forgets to call the service.

The workspace table keeps frontend-local history for fast interaction, but the backend ledger is the source of truth for durable recoverability. Full event sourcing, CRDT-backed table storage, and managed multiplayer state are deferred until offline-first or simultaneous same-cell collaboration becomes a proven requirement.

Alternatives Considered​

Frontend-only history​

Keep PR #428-style local undo stacks and rely on React Query optimistic rollback for failed mutations.

Not chosen as the durable solution. It gives fast UX but does not survive reload, another browser, another collaborator, or backend-side changes. It also cannot produce row activity or audit history.

Reuse ADR-031 source row versions only​

Treat record_version as "version history."

Not chosen. ADR-031 deliberately separates concurrency tokens from version history. It can reject stale writes but cannot answer what changed, who changed it, or how to invert a batch operation.

Use publication snapshots for authoring recovery​

Leverage EntrySnapshot latest-good/named-release/tombstone mechanics.

Not chosen. ADR-029 snapshots are public projection/export artifacts. They are too coarse and too late in the pipeline for live workspace editing.

Full event sourcing​

Store every source change as the primary system of record and rebuild current state from events.

Deferred. It would solve replay but adds migration, query, projection, and operator complexity that is disproportionate to the current need.

CRDT / Yjs / Liveblocks-style table collaboration​

Use collaborative shared types for table cells and row order.

Deferred for tables. CRDTs are appropriate for true live simultaneous editing, offline-first behavior, or rich-text collaboration. Plate may use Yjs for document editing later, but the workspace table can reach the required product bar with version-checked operations.

Consequences​

Positive​

  • Cell edits, paste, row movement, and later delete/schema actions can be undone through a durable backend path.
  • Multi-user conflict semantics become explicit: undo does not overwrite a row that has moved past the operation's expected version.
  • Row activity and "what changed" UI can be built from the same ledger.
  • ADR-031 remains useful as the concurrency proof instead of being overloaded as history.
  • The implementation is incremental: first cell/batch updates, then row order, row lifecycle, and schema/presentation operations.

Negative​

  • Operations that touch multiple rows need careful atomicity and conflict rules.
  • The ledger stores tenant-local before/after values, which increases retention and privacy responsibility.
  • Existing direct write paths must be audited so workspace edits do not bypass the ledger.
  • GraphQL callers need a new conflict/result shape rather than assuming every edit either returns a row or throws.

Neutral​

  • The ledger is tenant-local operational history, not cross-tenant telemetry.
  • It does not replace publication snapshots, media artifact revisions, or import wizard staged undo.
  • It does not require replacing AG Grid, TanStack Query, or Plate.

Implementation Notes​

Spec 0031 owns implementation. The initial backend shape should be small:

  • WorkspaceOperation
    • id
    • actor
    • client_session_id
    • client_operation_id
    • scope / table_ref / view_ref
    • operation_type
    • status
    • undo_status
    • redo_of
    • timestamps: created/applied/undone/redone
    • bounded metadata
  • WorkspaceOperationItem
    • operation FK
    • source model / source id
    • slot or field ref
    • before value
    • after value
    • base record version/hash
    • result record version/hash
    • per-item conflict/error state

Phase 1 implements cell_update and batch_cell_update only, including TSV/CSV paste-over-existing-cells. Phase 1 covers BOTH approved-row edits (today's update_entity path) AND DRAFT-row edits (Spec 0027's update_workspace_draft_record path) — both currently bypass each other and both must route through the ledger. Row activation (activate_workspace_draft_record) is declared un-undoable in Phase 1: the inverse — demotion of a now-APPROVED row plus its promoted edges back to DRAFT — is non-trivial and waits for a separate ADR amendment if researcher workflows demand it. Row create/delete, row ordering, column schema, and saved-view presentation operations should follow once the first contract is proven.

Row-order undo is explicitly deferred out of Phase 1. The frontend-local history layer in gridOperationHistory.ts already covers it for the in-session UX, but durable row-order undo requires either (a) a canonical row-order field on the source row or (b) a sub-key version token on TenantWorkspaceSavedView.column_state.manualRowOrder. Neither exists today and re-using the saved-view row's whole-row record_version is wrong granularity. Resolve in a follow-up amendment.

Undo of a multi-row operation should be atomic by default. If any target row is stale, return needs_rebase with conflict details and do not partially undo. Partial-undo trigger condition is named explicitly: revisit only if paste-undo conflict rate exceeds an agreed threshold (e.g., 5%) across a 30-day window of real workflows. Record any such revision in docs/decisions/log.md.

Triggers for event-sourcing migration​

The layered ledger is a stepping stone, not a permanent end state. Per WOL R1 absorption (2026-05-26), the following concrete triggers force the eventual migration from the operation ledger to full event sourcing:

  • Real-time multiplayer same-cell editing requirement (where two users edit the same field simultaneously and need CRDT-style merge semantics).
  • Offline-first authoring requirement (where the SPA must accept edits without backend connectivity and reconcile on reconnect).
  • Cross-tenant operation replay requirement (e.g., for federation marketplace per ADR-043, where a federation peer needs to replay another tenant's authoring history into its own substrate).
  • Authoring-audit retention beyond 5 years (where storage cost of full-payload retention crosses break-even with event-stream replay reconstruction).

When any of these triggers becomes a committed product requirement, a new ADR amendment supersedes this one with the event-sourcing migration plan. Until then, the ledger is the canonical authoring-history mechanism.

Review Questions And Resolutions​

Claude review 2026-05-26 resolved the six review questions raised by the preparatory Codex draft + Claude review brief. The resolutions below are load-bearing for Spec 0031 Phase 1 and any deviation requires an ADR amendment.

  1. Boundary (operation ledger now, full event sourcing / CRDT deferred)? Accepted. Plate rich-text document body undo stays editor-local (via Plate's UndoManager and any future Yjs decision) and is NOT a ledger operation type.
  2. Two tables (WorkspaceOperation + WorkspaceOperationItem) or one operation table with JSONB item payloads? Two tables. Row-activity queries by indexed source_id are the discriminator; JSONB GIN lookups are materially slower and harder to reason about. Shape precedent: TipEvent two-row pattern shipped in PR #419 (tip_surfaced + tip_action linked by parent_tip_event_id).
  3. Extend updateEntity with optional baseVersion, or add a new applyWorkspaceOperation mutation? Add applyWorkspaceOperation. Extending updateEntity creates a permanent fork between callers that pass baseVersion (ledger-tracked) and callers that do not (bypass). Keep updateEntity as a thin compatibility wrapper that internally builds a single-item operation envelope; deprecate the wrapper across one sprint once SPA call sites migrate.
  4. Phase 1 scope: cell + paste only, or include row-order undo because PR #428 already touched it locally? Cell + paste only, for BOTH approved-row and DRAFT-row write paths. Row-order durable undo is deferred — the PR #428 frontend layer keeps working in the meantime; it is local-only and not lying about it. See Implementation Notes above for why.
  5. Retention default for tenant-local before/after values? Two-tier with hard delete: full payload retained 90 days (the inverse-undo window); operation-row + per-item field_ref + before/after content hash retained 1 year (row activity stays readable after the value-undo window closes); hard delete at 1 year + 30 days, swept by tenant-local cron analogous to TipEvent retention. Tenant-overridable via the existing Client model settings pattern.
  6. Atomic all-or-nothing batch undo as the first policy? Accepted. Partial-undo trigger condition is named in Implementation Notes above.
