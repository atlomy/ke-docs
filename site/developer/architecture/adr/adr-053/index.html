ADR 053: Structure-Aware Archetype Classification with Conflict Surfacing

  • Status: Proposed
  • Date: 2026-06-01
  • Deciders: Platform owner/architect + Claude (surfaced live during the ADR-037 Phase A.1 fresh-import gate)
  • Context source: ADR-037 Phase A.1 fresh cold-start import gate, 2026-06-01 (docs/devlogs/2026_w23/2026-06-01_1003_adr037-phase-a1-fresh-import-gate-fb-resume-fix.md); Round-7 NotebookLM absorption, 2026-06-01 (docs/devlogs/2026_w23/2026-06-01_1952_adr037-r7-notebooklm-absorption.md); related ADR-033 (Comfort-Dial Apply Pipeline + Stratified-Prior Recommender), ADR-048 (RESTRUCTURE Materialization), archetype_strategic_planning.md, and the platform deterministic-first principle.

Context​

During the import gate, the Stage 3 matching-review surface classified source tables into archetypes and stated its own method on the card — a table-name heuristic matched a table to a primary archetype (e.g., a reference table mapped to DOCUMENT at ~0.75 confidence; another lookup table mapped to TERM). The domain owner disagreed on structural grounds: the tables in question are lookup/reference tables that other tables point at to enrich them — structurally an annotation/reference layer, not primary entities (TERM / PASSAGE / DOCUMENT). (Concrete per-tenant instances are recorded in the audience-restricted gate devlog, not here.)

The decisive observation: the importer already computes the relational structure. It is precisely that relational detection which generates the lookup→picker RESTRUCTURE proposals (ADR-048) for these same tables. So the system knows a table is a lookup target / heavily-referenced reference table — and then ignores that deterministic signal and classifies the archetype from the table's name instead. The result is confident, name-based archetype guesses that contradict structural facts the user can see, which:

  1. Erodes researcher trust — the surface asserted "DOCUMENT @0.75" and made the domain expert doubt knowledge they actually held ("I didn't think it was a document and now it made me not sure").
  2. Violates the platform's deterministic-first principle — use structural/declared signals before heuristic pattern-matching; minimize inference. The classifier inverts that order.

Round-7 review amended the first draft of this ADR. The original phrasing ("deterministic relational role primes; table-name breaks the tie") was still too blunt: a heavily referenced table can be a mechanical lookup table, but it can also be the researcher's core entity list, a public controlled vocabulary, or a primary scholarly text that many other tables cite. Naively applying "lookup target = annotation/reference" would reproduce the same trust failure in the opposite direction by auto-demoting core scholarly objects.

Decision​

Archetype classification MUST be structure-aware, not structure-dominant. The importer should convert deterministic relation evidence into an explicit structural-role feature / reason-code contract (for example: lookup_target_weight, hub_like, dictionary_like, leaf_like, and structure_name_conflict) and pass that contract to the classifier. The classifier MUST NOT read raw relation-graph internals directly.

When structural-role evidence and naming evidence agree, the classifier may raise confidence. When they disagree, the classifier MUST lower confidence and surface a concrete conflict reason to the user instead of auto-deciding. A plain-English prompt should name the conflict in domain-facing terms: this table is named like a primary entity, but its shape looks like a reference dictionary; should it become a public entity set, a controlled vocabulary, or private support data?

The table-name heuristic remains a real human-intent signal. It is no longer the primary classifier, but it is also not merely decorative: it is the signal that can prevent structural overcorrection when a heavily referenced table is epistemically central.

Classification and publication consequence are separate. A reference-like structural role MUST NOT automatically decide whether a table is public, private support data, excluded, or represented as a controlled vocabulary. The wizard explains structure; the researcher decides consequence.

Alternatives considered​

  • Keep name-heuristic primary (status quo). Rejected: it inverts deterministic-first, produces confident wrong guesses, and erodes trust at the exact moment the user is asked to decide.
  • Pure structural, ignore names entirely. Rejected: table/column names carry real signal for genuinely primary entities; discarding them loses information and would mis-handle well-named primary tables that aren't lookup targets.
  • Structure always wins; names only break ties. Rejected after Round-7: this overcorrects. Heavily referenced tables may be epistemically central; auto-demoting them would invert the original trust failure rather than fix it.
  • Thread the raw relation graph directly into the classifier. Rejected: it creates tight coupling between relation detection and archetype classification. D4/D5 graph improvements would silently skew classifier behavior and make imports less reproducible.
  • Always require manual archetype assignment. Rejected: defeats the assistive purpose and worsens the 190-decision review load the gate already flagged as unworkable.

Consequences​

Positive​

  • Fewer confident-but-wrong archetype guesses; the system stops contradicting structure it already computed.
  • Reuses an already-computed signal (the lookup/relation graph behind RESTRUCTURE proposals) — low marginal cost.
  • Restores the deterministic-first contract and researcher trust in the surface.
  • Prevents the opposite failure mode: structural overcorrection that demotes a core scholarly table because it is heavily referenced.

Negative​

  • Requires a structural-role contract between relation detection and archetype classification.
  • Needs clear role features and conflict semantics; genuinely ambiguous tables remain.
  • Changes confidence semantics — structure↔name disagreement must lower confidence, which means more honest "we're unsure" states (a behavior change in the Stratified-Prior Recommender, ADR-033).

Neutral​

  • Surfacing more "we're unsure, here's the structural vs name conflict" is honest but increases the share of items that ask for a human. ADR-033's comfort dial may help route low-risk cases, but this ADR does not assign new classification/conflict-resolution responsibilities to the dial without a later scope decision.

Implementation notes​

  • The lookup/reference detection already exists — it is the source of the RESTRUCTURE lookup→picker proposals (ADR-048). Start with the lightest structural-role contract that can express the conflict: derived features and reason codes on proposals, not a new graph service unless implementation pressure earns it.
  • Confidence shown to the user should reflect structural agreement, not name-match strength alone.
  • Test that proves it works: a lookup-target table whose name resembles a primary entity must not produce a confident primary-archetype guess solely from name evidence. If structure and name disagree, the result must be a low-confidence conflict card or a classification whose consequence still requires explicit user choice.
  • This is a platform-canonical classifier change, not a tenant fix; no tenant-specific table names belong in the classifier (per-tenant aliases stay in tenant config).
