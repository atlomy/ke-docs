ADR-012 — Tenant configuration flows through a runtime pipeline, never code

Status: Accepted (ratified 2026-05-30) Date: 2026-05-01 Branch: experiment/v2-anchor-and-seamless-edit Related: ADR-001 (Epistemic/Operational Separation), ADR-002 (Hybrid Ontology), ADR-004 (Tenant Ontology Mapping), ADR-010 (Parser-First Relationship Resolution), ADR-017 (Slot Config as Tenant-Authoritative Manifest), ADR-018 (Retired External Authoring Surface) Supersedes: nothing (codifies a constraint that several existing ADRs implicitly assume)

Context​

The platform's core principle is canonical structure is shared; interpretation is tenant-specific. Implementing this faithfully demands that anything interpretation-shaped — slot mappings, widget choices, resolver wiring, relationship strategies, archetype assignments, search facets — live as data that tenants edit, never as code maintained by platform engineers.

In practice we kept slipping. ATLOMY's attestations and literature slots got their string_match resolver wiring through a handwritten Django migration (0051). When the resolver gained an enrich_via capability, an instinct to write 0053_attestations_enrich_via_document.py followed — naming early_edition, source_work_name, editor_abbreviated, jones_chapter_number directly in version-controlled Python.

That's wrong for three reasons:

  1. Per-tenant migrations don't scale. Every new tenant onboarded needs another 0053_<tenant>_<feature>.py; every column rename needs one too. Engineers become bottlenecks for changes that aren't engineering-shaped.
  2. Researchers can't self-serve. A tenant scholar who renames a source column or adds a "Becker abbreviation" field has to file a ticket against the platform team. The point of the runtime-config pipeline is to remove that ticket queue.
  3. Code review is the wrong gate. Whether a slot should call early_edition or early_pub is not a code-correctness question. It's a domain-knowledge question that the tenant — not the platform team — owns.

The platform already has the parts of an alternative pipeline. They were not previously connected end-to-end:

  • Supported source evidence is the input surface. Importers and tenant-admin tools produce source-schema evidence; researchers see only their own data; schema changes (rename, new column, new linked-record relation) become proposal evidence, not platform code.
  • MappingProposal carries any mapping or resolver wiring as parser_payload / llm_payload JSONB — completely free-form. Each proposal has a status (PROPOSED / APPROVED / REJECTED). (data_import/models.py)
  • Parser + LLM proposal layer (ADR-010) inspects schemas and produces proposals deterministically (parser) then refines (LLM gated by parser evidence).
  • Reviewer UI (Session 02) lets researchers approve/reject proposals individually, in admin and SPA.
  • Materialization service (Session 03) walks approved proposals and writes TenantOntology + TenantArchetypeFormConfig rows.
  • Resolver dispatcher (Session 04) reads TenantArchetypeFormConfig.resolver_kind and resolver_args at request time. No tenant fields hardcoded in resolver code.

What was missing: the materialization step only applied basic resolver_args = {source_field, target_field} from the proposal. Richer keys (filter_kwargs, serialize_data_fields, enrich_via, custom widget hint, custom slot name, custom label) were not propagated. So even when the parser/LLM proposed them, they fell on the floor — and we reached for migrations.

Decision​

Tenant-specific configuration must travel exclusively through the runtime pipeline:

source-schema event (or import-time parser run)
       │
       ▼
parser/AI inspects evidence, produces MappingProposal rows
       │      parser_payload  = deterministic findings
       │      llm_payload     = AI-refined findings (bounded by parser evidence)
       ▼
researcher reviews, approves/rejects in admin/SPA
       │
       ▼
materialization service applies APPROVED proposals
       │      → TenantOntology
       │      → TenantArchetypeFormConfig (resolver_kind, resolver_args, widget,
       │                                   label, help_text, slot_name)
       │      → optionally re-materializes EpistemicEntity rows
       ▼
anchor projection + resolver dispatcher pick up the new config at next request

This pipeline replaces any path that ends in a per-tenant Python migration for slot/resolver wiring. Migrations are reserved for canonical structure changes — new model fields, new resolver kinds, new archetypes, new platform-shared rules — and never for tenant interpretation.

Concretely​

  1. MappingProposal.parser_payload and MappingProposal.llm_payload are the canonical carrier for slot / resolver / widget / label proposals. Every key the materialization service writes to TenantArchetypeFormConfig must be derivable from one of these payloads.

  2. The materialization service must apply the full payload verbatim, not a curated subset. Any new resolver-args key added to the resolver dispatcher (e.g. enrich_via) becomes available to tenants the moment a proposal supplies it — no additional code change required.

  3. Source-schema change events (column add, rename, link create) trigger proposal generation through the supported importer or tenant-admin path. Each event produces a proposal with the appropriate proposal_kind and a fresh parser_payload describing the change.

  4. Per-tenant Django migrations for slot/resolver wiring are an antipattern. When you find yourself writing one, the correct response is: extend the proposal pipeline so the same configuration lands as data. If a one-time emergency seed is unavoidable (existing tenant, no proposal pipeline yet for that surface), document it as transitional in the migration's docstring with a removal date.

  5. Django admin UI on TenantArchetypeFormConfig remains an authorized escape hatch. A tenant researcher with admin permissions can edit resolver_args directly when a proposal pipeline doesn't exist for their use case yet. Edits made there are equally legitimate config; they just bypass the review-trail. The path to "publishable" config (versioning, draft/live separation, audit) is a future work item building on this foundation.

What this constrains​

  • No new file in <app>/migrations/ may seed resolver_args, widget, slot_name, label, or any tenant-interpretation field with a tenant-specific literal. Migrations may add columns, indexes, default ResolverKind enum values, or platform-shared seed rows (e.g. an "anchor archetype" exists for every tenant). They may not name a tenant's columns.
  • Code-reviewer subagents must reject migrations that violate this. The check: does the migration body contain string literals that look like a tenant's domain vocabulary (early_edition, Becker, phleps, …)? If yes, kick back with "route through MappingProposal".
  • Resolver code must accept all configuration through resolver_args. A new resolver kind that requires hardcoded knowledge of a tenant's field names is not eligible for merge.

What this doesn't constrain​

  • One-time data-fix migrations (e.g. correcting corrupted JSONB, backfilling from a deprecated column) are fine; they're operational repairs, not interpretation.
  • Platform-canonical structural rows (a single default ROOT entity per tenant, an installation-default ResolverKind) are fine in migrations; they describe shared structure.
  • Test-fixture seeds are fine; they're not production tenants.

Clarification (2026-05-30) — platform-canonical data catalogs are not "structure". The "platform-canonical structural rows" allowance covers a genuinely one-per-tenant structural anchor (a default ROOT entity, an installation-default ResolverKind). It does not extend to platform-canonical data catalogs that already have a code source-of-truth and are identical across every tenant — the slot-preset starter library (PLATFORM_STARTER_LIBRARY) and the canonical vocabulary baselines. Those resolve from code at read time, or are applied by idempotent tenant provisioning (the django-tenants post_schema_sync signal is the pattern — it fires after the schema is created + migrated), never materialized per-tenant via a migration RunPython. A canonical-data change must be one code edit, not a re-seed of every schema.

Migrations stay reserved for schema/DDL — including integrity triggers such as the decision_event append-only and monitoring hash-chain RunSQL, which have no code-resolvable representation. The provisioning code's home follows ADR-042 (platform/epistemic app placement, not atlomyapp).

Alternatives considered​

A. Keep ad-hoc migrations alongside the proposal pipeline​

Reject. Two ways to write the same configuration produce two ways to drift apart. Reviewers can't tell which is authoritative. Tenants who edit their config via admin discover that the "next migration deploy" overwrites their edits. This is worse than picking one path and committing.

B. Build a separate "tenant config DSL" and load it from disk​

Reject. We'd reinvent JSON inside YAML inside Python. The proposal pipeline already serializes through JSONB columns and is observable, queryable, and audit-traceable. A DSL adds parsing layers without solving the per-tenant-edit-distribution problem.

C. Generate migrations programmatically from approved proposals​

Reject. Migrations are forward-only and live in version control. If a tenant rejects an approved proposal a week later, we'd write a reversal migration. The current TenantArchetypeFormConfig table can absorb the same state changes via update_or_create, with no version-control churn.

Consequences​

Positive​

  • Tenant researchers can self-serve. Adding a new source column, approving the resulting proposal, and seeing the new slot render at /term/<id>/ becomes a flow that doesn't touch any Python code.
  • Engineers focus on capability, not configuration. A new resolver kind ships once; tenants configure it through proposals; no per-tenant migration follows the merge.
  • Multi-tenant cost is bounded. Onboarding a new tenant doesn't multiply the migration count.
  • AI proposals get end-to-end value. The work in ADR-010 (parser-first, LLM-second) only pays off if the LLM-refined resolver_args actually reach TenantArchetypeFormConfig. This ADR closes that loop.

Negative / cost​

  • Tenants need a working proposal pipeline to configure non-trivial slots. For ATLOMY on experiment/v2-anchor-and-seamless-edit, the pipeline exists for ARCHETYPE/COLUMN/RELATION proposals but not yet for "extend an existing slot's resolver_args" (e.g., adding enrich_via to a slot that was first proposed without it). Filed as follow-up: a "RESOLVER_ARGS_PATCH" proposal kind, or a generic "CONFIG_PATCH" kind, so existing slots can be enriched through the same review trail.
  • Admin UI escape hatch creates an audit gap when used. We accept this — the alternative (forbidding the escape hatch) blocks researchers when proposals are absent. The audit trail can be added later via Django auditlog on TenantArchetypeFormConfig.
  • Existing per-tenant migrations (0050, 0051, 0052 on this branch) are technical debt. They should be deprecated as the proposal pipeline grows to cover their cases. We don't revert them now (the slot config they seed is in production); we mark them as transitional and remove on the next major migration squash.

Implementation status (2026-05-01)​

  • ✅ MappingProposal model accepts arbitrary parser_payload / llm_payload (since Session 01)
  • ✅ Reviewer UI (admin + SPA) for proposal approval (Session 02)
  • ✅ Materialization service writes TenantArchetypeFormConfig from approved proposals (Session 03)
  • ✅ Resolver dispatcher reads resolver_kind + resolver_args at request time, no tenant fields in code (Session 04)
  • ✅ Materialization service propagates full payload-supplied resolver_args, widget, slot_name, label, help_text (this commit)
  • ✅ Test coverage: rich-payload pass-through verified end-to-end (test_payload_resolver_args_flow_to_config)
  • ✅ Migration audit complete: all atlomyapp/migrations/ files reviewed.
    • Removed (this branch's debt): 0050_seed_atlomy_models_slot, 0051_activate_atlomy_attestations_slot, 0052_update_widget_values_for_passage_bibliography, the proposed-and-deleted 0053_attestations_enrich_via_document.
    • Emptied to no-op marker: 0047_seed_atlomy_term_anchor (kept the file for chain ordering only — 0048 depends on the migration name; the body that defined 16 ATLOMY-specific slots is gone). Existing tenant schemas where it already ran retain their seeded rows.
    • Already untracked: 0049_seed_visionis_term_anchor (per state.md transitional artifacts list).
  • ⏳ Source-schema change events → MappingProposal generation: supported importers and tenant-admin flows need to emit proposal evidence for schema diffs.
  • ⏳ AI-assisted enrich_via proposal: source-schema analysis needs extension to propose join-style relationships.
  • ⏳ "Publishable" config (draft → live, versioning, audit): future work
  • ⏳ Fresh-deploy onboarding flow for the pilot tenants: now that the tenant-seed migrations are no-ops, a fresh tenant schema starts with no slot config. Bootstrap path needs to go through MappingProposal pipeline (or a one-time admin command that itself reads from a tenant-owned config file outside migrations/).

Out of scope (acknowledged debt, separate decision)​

  • atlomyapp/models.py ATLOMY-specific Django models (Lemma, Model, ModelLemma, Configuration) — these exist because the v1 ATLOMY application has its own ORM. Their migrations (e.g. 0011, 0032, 0033, 0037 adding lemma_full, morph_1, transliteration columns) name ATLOMY vocabulary because they're ATLOMY's own data model, not platform config. The platform v2 path migrates this into EpistemicEntity rows, but that's a multi-session refactor, not a migration cleanup. ADR-012 governs only platform-canonical config (TenantOntology, TenantArchetypeFormConfig).
  • Configuration.config_name enum carries ATLOMY domain values (ancient_words, early_editions_bibliography, …). Same category — it's a v1 application concern.
