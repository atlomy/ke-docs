ADR-043: Unified federation/marketplace pattern (Ingest + Alignment + Workspace)

Status: Proposed (v1.1) Date: 2026-05-22 (v1.0 draft; ratified per user direction "Ratify" on PR #372 federation vision devlog 2026-05-22); amended same-day 2026-05-22 (v1.1 — R2-A43-A cross-slot hard-dependency mandate + archetype-axis protection language; R2-A43-C provisional URI namespace prefix convention; both per user authorization for autonomous-session implementation tonight) Deciders: User; architecture team Related: ADR-006 (platform-fixed archetype enum), ADR-030 (CIDOC + Linked Art export profile), ADR-037 (Slot-Type Taxonomy + Tenant Vocabulary Layer), ADR-038 (Federated Preset Registry as Federation Contract), ADR-039 (Platform Place preset), ADR-040 (Platform Period preset), ADR-041 (Spatial substrate), ADR-042 (Layered substrate naming), Spec 0023 (Multi-source tenant onboarding), skills/ui-development/SKILL.md

TL;DR​

The capability-URI binding pattern has emerged in three separate KE artifacts — ADR-038 (Federated Preset Registry, for standards alignment), Spec 0023 Item 2 (connector registry, for raw-source ingest), and the ui-development skill (data-derived workspace selectors) — without ever being named as one pattern.

This ADR names it: KE has a unified federation registry pattern across three slots — Ingest (raw sources entering the platform), Alignment (standards the platform projects / federates / exports to), and Workspace (pickers, widgets, viewers researchers see). Each slot has its own registry (scope-distinct; do not conflate); all three share the same contract shape (capability URI binding); and Domain Bundles compose capabilities across all three slots as the marketplace unit.

The marketplace MVP is platform-team-only ("eat our own dog food") — community / tenant publish-flow is designed-for but explicitly deferred until a production cohort proves the contract. ADR-006's binding is preserved: archetypes are platform-fixed canonical structure; researchers create entities, declare slot configs, and subscribe to bundles WITHIN archetypes — they never create new archetypes.

This ADR records the pattern, the 5 ratified decisions D1-D5 from the federation vision devlog, the Tier-1 anchor bundle catalog, the conditional Tier-2 pilot-tenant bundles, and the open questions Q1-Q5 that need follow-up design work. It does NOT alter ADR-038's scope — ADR-038 stays focused on the alignment slot; this ADR generalizes the pattern over all three slots.

Context​

Three artifacts; one unnamed pattern​

The pattern has been emerging without being named:

ArtifactSlotWhat it federates
ADR-038 Federated Preset RegistryAlignmentStandards activations: CIDOC, Linked Art, PROV-O, SKOS, GeoSPARQL, …
Spec 0023 Item 2 Connector registry (proposed)IngestRaw sources: Coda, MySQL, XLSX, filesystem-upload, csv-of-urls, plus v1.1 Tenant-4 set
skills/ui-development/SKILL.md Data-derived selectorsWorkspacePickers, multi-language/multi-script/multi-calendar tabs, viewers populated from tenant data + tenant-preset recommendations

The user (2026-05-22) surfaced the unification:

"Ingestion should be evolved to a registry of sources which we can contribute to or tenants can. Maybe a small marketplace/add on/extensions with protocols. For example, importing an excel is different than importing access files, which conceptually sit between our current mysql and csv import levels. Same with work in workspace — a user should have the pickers and options relevant to the chosen field or data they have, whether it is their pick of tables or a certain discipline or package that bundles fields together (like we have multi key for languages or accent fold, to the latest insights about presets for archeological c14 and place and gis data or agro or agisoft or ortophoto and other surprises)."

The three artifacts are three faces of one pattern. The user proposes recognizing them as such and designing the next iteration as a federation/marketplace model.

The structural-shape gradient​

The user named a key insight: "importing an excel is different than importing access files, which conceptually sit between our current mysql and csv import levels." This is a structural-shape gradient:

CSV → Excel → Access → MySQL → Coda
 flat   tabbed   relational-with-files   full-relational   structured-doc

Each step adds structural complexity. A naive "5 connectors for 5 vendor names" framing misses this gradient — treats Excel and Access as arbitrary and forgets that they share a "tabbed + partial-relational" middle ground that could compose. A federation registry that's aware of the gradient can reuse parsers across structural-shape neighbors and suggest the right capability URI subscription based on a tenant's data shape.

The same structural-shape gradient applies to other slots: 3D (GLB → glTF → PLY → OBJ → FBX), GIS raw (GeoJSON → KML → shapefile → GeoPackage), imaging (TIFF → DICOM → NetCDF → COG → IIIF).

What this is NOT​

  • Not a re-litigation of ADR-038. ADR-038 stays focused on the alignment slot; this ADR generalizes the pattern over all three.
  • Not a community-publish flow design. D5 RESOLVED 2026-05-22 to platform-team-only at MVP; community publish-flow waits for a trigger.
  • Not a new archetype-creation surface. ADR-006 keeps archetypes platform-fixed at 6 values (TERM / DOCUMENT / PASSAGE / EVENT / ENTITY / ANNOTATION); researchers compose WITHIN archetypes via slot configs + bundle subscriptions.
  • Not a change to the alignment-slot capability URIs that ADR-038 already defines.

Why now​

Three converging forces:

  1. Tenant-4 trigger event (2026-05-22): Tenant 4 (integrative humanities-archaeology-ecology-GIS) is close to signing. The Spec 0023 v1.0 connector list (Coda + MySQL + XLSX + filesystem-upload + csv-of-urls) does NOT cover Tenant-4's raw sources (Access DB files, GDrive folders, raw GIS, raw imaging, 3D assets, scientific report composites). Spec 0023 needs a federation/marketplace framing rather than a flat vendor list.
  2. ADR-038's contract precedent: ADR-038 already proves the capability-URI binding pattern works for the alignment slot. Generalizing to ingest + workspace at the same time avoids drift between slot-specific contracts.
  3. The ui-development skill's data-derived discipline: workspace pickers already derive from data + tenant-preset recommendations, not from platform-fixed enums. Naming this as the third slot of the federation pattern makes the discipline explicit.

The longer the unification is deferred, the more likely the three slots ship contract-incompatible registries.

Decision​

D1 — Unified federation framing (RATIFIED 2026-05-22)​

KE adopts a unified federation registry pattern across three slots:

The capability URI lists are illustrative-initial; the registries are extensible per slot. Slot scopes stay distinct (do NOT conflate ingest with alignment per the 2026-05-22 layer-correction in 2026-05-22_0640_r2-reconciliation-first-principles.md §"R2-NEW-4"). What the slots share is contract shape, not contents.

Cross-cutting principle (preserved from ADR-006): archetypes are platform-fixed at 6 canonical values (TERM / DOCUMENT / PASSAGE / EVENT / ENTITY / ANNOTATION). Researchers create entities, declare slot configs, and subscribe to bundles WITHIN those archetypes. They never create new archetypes. The federation marketplace serves the four researcher-facing needs — documented, presented, searched, published — without expanding the archetype axis.

D2 — Separate ADR (RATIFIED 2026-05-22)​

This pattern lives in its own ADR (this document, ADR-043), not as an in-place amendment to ADR-038. Rationale:

  • ADR-038 stays focused on its current scope (standards alignment slot; federated preset registry semantics; capability activations across pilots).
  • This ADR is meta-architectural: it generalizes the pattern over three slots. Folding it into ADR-038 would either bloat ADR-038 or imply ADR-038 dictates ingest + workspace behavior, which it does not.
  • Future amendments to either ADR-038 or this ADR can cross-reference without forcing a re-read of the other.

D3 — Spec 0023 Item 2 reframing authorized (RATIFIED 2026-05-22)​

Spec 0023 Item 2 (connector registry) is authorized to redraft as a marketplace-from-start design. The reframed scope:

  • Registry contract = capability URI binding shape: each ingest extension declares its K.supports.* URIs, security boundary, parser-shape contract, and required tenant config.
  • First-party extension catalog = the v1.0 connectors covering pilots + v1.1 Tenant-4 set (10 capability URIs enumerated in D1 above).
  • Marketplace discovery UI = catalog browseable from tenant-admin surfaces; researchers don't normally browse it (per D1's smart-defaults principle).
  • Community-publish flow infrastructure = OUT OF SCOPE at MVP per D5; the registry shape is designed to admit it later.

The Spec 0023 design.md R2-NEW-4 amendment lands the v1.1 connector roster + marketplace framing without authoring the publish-flow surface.

D4 — Bundle catalog priority (RATIFIED 2026-05-22; framing precision 2026-05-22 morning per R2-A43-B)​

Empirical driver — documentary honesty note (R2-A43-B applied 2026-05-22 morning, anonymized per partner_model 2026-05-19 tenant-naming rule): the Tier-1 anchor catalog below is empirically driven by an incoming integrative humanities-archaeology-ecology-GIS tenant whose onboarding pipeline first surfaced the need for this bundle composition (Access DB + Google Drive folder ingest + raw GIS + 3D photogrammetry + radiocarbon dating). The Tier-1 anchors serve as the first production stress-test of the unified federation pattern against that tenant's data shape; they are NOT a generic broad-pattern speculation. Future engineers reading this ADR should understand that the bundle composition is a real-world stress-test answer to a real tenant's needs, not an architect's abstract catalog. (Per the partner_model 2026-05-19 tenant-naming rule, the tenant is described by architectural-pattern signature rather than by name; once the tenant signs and publicly identifies the project, the framing can be updated to name them explicitly — or stay anonymized as the longer-term pattern for tenant references in checked-in artifacts.)

D5 — Platform-team-only MVP scope (RATIFIED 2026-05-22)​

Marketplace MVP scope is platform-team-contributed extensions ONLY with a versioned manifest. User direction 2026-05-22: "I think that platform team only for now is the right way. We eat our own dog food."

What ships at MVP:

  • Registry contract (capability URI binding shape, per-slot).
  • First-party extension catalog (12 ingest URIs + 6 alignment URIs + 6 workspace URIs enumerated in D1).
  • Marketplace discovery UI (catalog browseable from tenant-admin surfaces).
  • 3 Tier-1 anchor bundles.

What does NOT ship at MVP (deferred-with-trigger):

  • Community / tenant publish-flow surface (the "Publish your extension" path).
  • Vetting / audit / signing / revoke pipeline for community contributions.
  • Per-tenant private extension publishing (tenants can't publish extensions visible only to themselves at MVP).

Trigger for community-publish flow: ≥1 production cohort of 3+ tenants using the marketplace through a meaningful slice of work (e.g., one onboarding + one schema evolution cycle each) AND observation that the platform-team contribution velocity is the bottleneck (not the contract design). Until that trigger fires, the platform team owns all extension contributions.

Security boundary discipline: even platform-team-contributed extensions declare a parser-shape contract; the platform interprets the parser shape; arbitrary Python execution is restricted to webhook_external_payload (which runs on the tenant's server, not platform-side) and to reviewed-and-merged platform-team code paths.

D6 — Domain Bundles are the composition unit​

A Domain Bundle is the marketplace unit. Each Bundle declares contributions to one or more slots:

# Conceptual shape (final schema is implementation detail for the Spec 0023 sibling spec)
bundle:
  id: bundle:archaeological-c14
  version: 1.0.0
  ingest:
    - capability: radiocarbon_lab_report_compose
      parser_shape: { ... }
  alignment:
    - capability: chronontology_publish
    - capability: periodo_period_resolve
  workspace:
    - capability: c14_calibration_curve_picker
      data_source: tenant
    - capability: uncertainty_distribution_viewer

Bundles compose across slots. The "composition unit" framing is what makes the marketplace navigable — a researcher onboarding a c14 dataset subscribes to bundle:archaeological-c14 once and inherits ingest + alignment + workspace contributions together, rather than wiring three separate capability subscriptions.

D6.1 — Cross-slot hard-dependency mandate (v1.1, R2-A43-A ratified 2026-05-22)​

Domain Bundles MUST explicitly declare cross-slot hard dependencies in their manifest. Implicit dependencies (e.g., "alignment iiif_manifest_publish only functions when ingest image_collection_ingest is also subscribed") would surface as runtime-stall scenarios where a researcher subscribes to an alignment-only bundle and the pipeline silently fails because the prerequisite ingest capability was never provisioned.

Concrete shape (extends the §D6 manifest schema):

bundle:
  id: bundle:place-gis
  version: 1.0.0
  ingest:
    - capability: raw_gis_ingest
  alignment:
    - capability: geosparql_query
      requires:                       # cross-slot hard dependency
        - ingest:raw_gis_ingest       # this alignment capability needs that ingest capability
  workspace:
    - capability: gis_coord_system_picker
      requires:
        - ingest:raw_gis_ingest

Installation-time enforcement: when a tenant subscribes to a bundle, the registry validates that all requires: declarations resolve to capabilities the tenant already subscribes to (via other bundles or per-capability subscriptions). Failures fire at install time, not at first-use time — preventing the "buy a car without an engine" failure mode.

D6.2 — Archetype-axis protection (v1.1, R2-A43-A ratified 2026-05-22)​

To preserve ADR-006 binding (archetypes platform-fixed at 6 values: TERM / DOCUMENT / PASSAGE / EVENT / ENTITY / ANNOTATION; researchers compose WITHIN them via slot configs + bundle subscriptions; researchers never create new archetypes), this ADR is explicit:

Workspace pickers act strictly as data-driven views within the existing six fixed archetypes — they do NOT create new pseudo-archetypes via the back door. Concretely:

  • c14_calibration_curve_picker is a data-driven view on the slot data of EVENT-archetype entities whose tenant config declares c14-shape slots (carbon-date slot + uncertainty-distribution slot). It does not introduce a RadiocarbonSample archetype, nor a hidden table.
  • gis_coord_system_picker is a data-driven view on the slot data of any archetype carrying place-shape slots. It does not introduce a Place or Locale archetype.
  • Future bundle workspace pickers MUST follow the same pattern: data-driven views over slot configs within the platform-fixed archetypes. If a future bundle author finds they "need a new archetype", that's the signal that ADR-006 needs to be re-litigated — NOT that the bundle should silently work around it.

This protection language is load-bearing: without it, the marketplace pattern's velocity would tempt bundle authors to generate custom base tables for domain-specific data ("just for archaeological samples, just for visual attestations"), shattering the unified data model that ADR-006 establishes. The audio-rendered explanation: bundles are specialized adapters plugged into the universal power grid that is the archetype substrate — they do NOT generate their own electricity.

D6.3 — Composite / orchestrator connector classification (v1.1, R2-S23-C applied 2026-05-22 morning)​

Some ingest capabilities don't parse files themselves — they traverse a remote container and dispatch arbitrary file types to other parsers. gdrive_folder_sync is the immediate example (Google Drive folder traversal; per-file dispatch to whatever parser matches the file extension/MIME); dropbox_folder_sync, onedrive_folder_sync, s3_bucket_sync, etc. follow the same pattern. The "every connector declares parser_shape" contract from §4 of Spec 0023 breaks for these because they can't honestly declare what shape they produce — that depends on what's in the folder, which changes between syncs.

Composite/orchestrator classification addresses this:

  • Parser classification (existing default): connector declares parser_shape (what files it produces). Validated against tenant slot configs at install time.
  • Composite/orchestrator classification (new): connector declares downstream_allow_list — the list of capability URIs it's permitted to dispatch to (chain-of-trust contract, not static parser_shape). At install time, every URI in the allow-list must resolve to a parser-capability the tenant also subscribes to (per §D6.1 cross-slot requires: hard-dependency mandate). At runtime, the orchestrator iterates files; for each file, looks up the dispatch target in downstream_allow_list based on extension/MIME; calls the downstream parser. If no allow-list entry matches a file, surface that file in the Import Wizard Stage 3 review queue (genuine-ambiguity escape hatch per the deterministic-first discipline in Spec 0023 §3.3.1 + §5.1).

Conceptual manifest shape (parallels §D6 + §D6.1):

bundle:
  id: bundle:drive-staging
  version: 1.0.0
  ingest:
    - capability: gdrive_folder_sync
      classification: composite                # NEW — distinguishes from parser
      downstream_allow_list:                   # NEW — capability URIs this can dispatch to
        - K.ingest.image_collection_ingest     # for .tif / .jpg / .png / .dcm files
        - K.ingest.3d_asset_ingest             # for .glb / .obj / .ply files
        - K.ingest.scientific_report_compose   # for .pdf composite reports
      requires:                                # per §D6.1 cross-slot hard dependency
        - ingest:K.ingest.image_collection_ingest
        - ingest:K.ingest.3d_asset_ingest
        - ingest:K.ingest.scientific_report_compose

The composite/orchestrator pattern lets KE add new orchestrators (Dropbox, OneDrive, Box, S3, network shares) without changing the contract — each declares its own downstream_allow_list against the parser catalog. The user-direction reasoning (2026-05-22 morning) confirms: this is the right shape for KE's backend-ETL use case, NOT MCP — MCP is for LLM-induced work (user-initiated, conversation-scoped); KE's orchestrators are scheduled / webhook-triggered / headless / deterministic. MCP integration patterns are reserved for in-product AI assistance per ADR-014-α single-call LLM-assist contract, a separate concern.

Audio-rendered analogy from the R2 critique (R2-S23-C): we're not treating the mail-delivery truck (orchestrator) like the letters it carries (parsers) — the truck declares its allow-list of letter-types it's licensed to carry; we validate the license at install time + sort each letter to the right downstream sorter at runtime. The truck has no parser_shape; the letters do.

Aggregator landscape (Nylas / Pipedream / n8n / Composio) explicitly ruled out for KE's pre-launch + small-team + tenant-isolated + academic-platform context — wrong abstraction shape (n8n loses tenant-isolation; Nylas is email/calendar-only; Composio is agent-toolkit-shaped; Pipedream is cloud-only credit pricing). Each connector is ~50-200 lines of vendor-SDK glue + standard OAuth 2.0; cardinality is small enough that build-per-vendor stays well below aggregator total cost of ownership. Subagent's full evaluation preserved at /tmp/r2-overnight-2026-05-22/external-integrations-and-manifest-contract-research.md.

D7 — Smart-defaults discipline preserved​

The marketplace gives options (extensions, bundles) BUT the smart-defaults discipline applies to the discovery layer:

  • Tenant admin uploads sample data → wizard recognizes structural shape → auto-suggests the right capability URI subscription → tenant admin confirms with one click.
  • Researcher creates a new entity within an existing archetype → workspace auto-shows fields + pickers + viewers derived from the bundles their tenant subscribes to → researcher doesn't browse the catalog.
  • Standards alignment activates automatically when researcher data matches an alignment capability's contract (e.g., place data with coordinates auto-publishes via GeoSPARQL when the tenant has subscribed to bundle:place-gis).

The catalog UI exists for the rare "I want to see what's available" tenant-admin moment; smart defaults handle 95% of day-to-day researcher interactions without them reaching for the catalog. This honors the user's R2 first-principles directive: "give them the options, but try to make the system smart enough to not have them needing to reach out to those options unless truly extraordinary conditions apply."

D8 — Provisional capability URI namespace convention (v1.1, R2-A43-C ratified 2026-05-22)​

Capability URI namespace governance was listed as an open question in v1.0. Without a provisional convention, capability URI collisions could silently corrupt routing — if two communities ever publish a tool claiming the same URI (e.g., both register image_ingest), the registry contract treats it as a unique binding identifier and silently overwrites the routing pointer. The failure mode is active silent data corruption across multiple tenants: half the platform's data pipelines start routing raw images to the wrong software tool. This is a Day-1 risk even at platform-team-only MVP scope (D5) because parallel agent / parallel-author authoring can introduce same-URI commits across feature branches.

This ADR adopts a provisional prefix-based namespace convention NOW, sufficient for the MVP scope and extensible without breakage when the registry contract opens to community publishing:

  • K.* — official platform-team-contributed capabilities (e.g., K.ingest.raw_gis_ingest, K.alignment.geosparql_query, K.workspace.gis_coord_system_picker). All v1.0 + v1.1 capabilities enumerated in §D1 carry the K.* prefix at registration.
  • K.community.* — reserved namespace for future community / tenant-published capabilities. Empty at MVP per §D5; structurally available so that when the D5 community-publish trigger fires, the namespace shape is already settled.
  • Bundle IDs follow the same convention (bundle:K.place-gis, bundle:K.community.<author>.<bundle-name>).

The provisional convention is a cheap stop-gap that prevents the silent-corruption disaster on day one. A full registry-authority design (collision detection, version pinning across K.community.* namespace, deprecation lifecycle) is queued in §"Open questions" (Q2 / Q3) for the community-publish-flow sprint when D5 trigger fires.

D9 — Workspace surface stays simple; reconciliation lives in Import Wizard (v1.1, ratified 2026-05-22)​

Cross-references Spec 0023 design.md §3.3.1 + §5.1 (R2-S23-A REFRAMED 2026-05-22):

The workspace surface (/app/workspace/... per ADR-036) stays as simple as Coda / Linear / Notion / Monday for daily researcher work. Bundle subscriptions show up as new fields + pickers + viewers (data-derived per ui-development skill), not as new admin curation moments inline. When a bundle's underlying capability requires reconciliation (e.g., column rename ambiguity in an XLSX-shape source, or a deprecated bundle version), that reconciliation lives in the Import Wizard Stage 3 review surface — not inline in the daily-work workspace.

This is an architectural boundary, not a UX preference: the workspace surface is the data-derived substrate established by the ui-development skill and elaborated by the workspace UI sprint series (PR #370 / #374 / and the field-definition modal + linked-record authoring work that follows). The federation marketplace pattern composes with the data-derived workspace; it does not introduce its own inline admin affordances.

Alternatives Considered​

Option B — Extend ADR-038 in place​

Amend ADR-038 to cover all three slots (ingest + alignment + workspace) under one federated registry. Largest blast radius but cleanest architectural story.

Why not chosen: ADR-038's scope is the alignment slot specifically (standards activations, federated preset registry semantics). Extending it would either bloat ADR-038 with off-topic ingest + workspace material or imply ADR-038 dictates the other slots' behavior, which it does not. A separate ADR (this one) lets ADR-038 stay focused and lets future amendments to either ADR not force re-reading the other.

Option C — Decision-log + design.md amendments only; defer ADR until implementation-ready​

Capture the direction in docs/decisions/log.md; amend Spec 0023 design.md Item 2 to reflect the marketplace evolution; defer a full ADR until the federation contract is implementation-ready.

Why not chosen: the unified pattern is a meta-architectural decision that constrains future work across all three slots. Future contributors authoring slot-specific specs (Spec 0023 Item 2 redraft; an ADR-038 alignment-slot extension; a Workspace-slot capability addition) need a single artifact to cite as the federation contract — otherwise the pattern fragments into per-spec re-interpretation. The decision log + design.md path leaves no anchor.

Consequences​

Positive​

  • One pattern, three slots. Future contributors author slot-specific specs with a single federation contract to cite. Prevents pattern fragmentation.
  • Tenant-4 onboarding path is concrete. The 10 v1.1 ingest capability URIs cover Tenant-4's raw sources; bundle subscription model gives Tenant-4 one place to express "I want place-gis + archaeological-c14 + photogrammetry-agisoft" without separately wiring 9 ingest connectors + 6 standards activations + 9 workspace pickers.
  • Bundle composition matches researcher mental model. Researchers think in disciplines (archaeology / GIS / anatomy / philology), not in capability URIs. Bundle-as-unit lets researchers subscribe in their own vocabulary while the platform's contract layer remains capability-URI-precise.
  • Eat-own-dog-food validates the contract before community exposure. Platform team contributes the first wave; the contract proves itself through real platform-team-contributed examples; community publish-flow lands safely later.
  • ADR-006 binding preserved. Archetypes stay platform-fixed; researchers compose WITHIN them via slot configs + bundle subscriptions.
  • Aligns the three artifacts (ADR-038 / Spec 0023 / ui-development) under one pattern. No future drift between slot-specific contracts.

Negative​

  • Five open questions remain unresolved (Q1-Q5 below) — the ADR records the framing but defers concrete UX / versioning / discovery / security details to follow-up specs.
  • Bundle composition adds an indirection. A researcher subscribing to bundle:archaeological-c14 doesn't directly see the underlying capability URIs. Debugging "why did this picker show up?" requires walking the bundle → capability URI → workspace-slot chain. The marketplace catalog UI mitigates this by surfacing bundle contents clearly.
  • MVP scope intentionally narrow. Community-publish flow is deferred; tenants can't publish extensions yet. This is by design (D5) but may be raised as a limitation by external observers who expect a full marketplace at v1.
  • Capability URI namespace governance is undefined at v1. Q3 calls out version pinning; collisions across bundles aren't yet addressed.

Migration plan (out of scope here — pointers only)​

This ADR records the pattern; implementation lives in the Spec 0023 sibling spec and a future workspace-slot spec. Pointers:

  • Spec 0023 Item 2 redraft (per D3) lands the ingest-slot first-party catalog + registry contract + marketplace discovery UI.
  • ADR-038 stays as-is; alignment-slot first-party catalog is already substantively defined there.
  • Workspace-slot first-party catalog lives in the ui-development skill + future spec; this ADR doesn't add a new model field, only names the pattern.
  • 3 Tier-1 anchor bundles declared platform-team-side during the Tenant-4 onboarding sprint or before; Tier-2 pilot bundles materialize conditionally per D4 trigger criteria.
  • No data migration required by this ADR alone; downstream Spec 0023 redraft will own any model + migration changes.

Open questions (queued for follow-up specs)​

These are recorded for follow-up design work; this ADR does NOT resolve them:

  • Q1 — Marketplace UX: where does the catalog live (workspace settings? import wizard Stage 0? both?).
  • Q2 — Bundle versioning + dependency graph: how do bundle compositions handle capability URI version pins? When bundle:place-gis@2.0.0 deprecates epsg_local_crs_picker@1.x in favor of @2.x, what happens to tenants pinned to the older version?
  • Q3 — Tenant-side contribution security (post-community-publish trigger): can a tenant publish an extension to themselves only (private extension), or must all extensions go through platform-team review?
  • Q4 — Extension discovery: how do researchers find applicable extensions for their data without reaching for options ("smart enough" principle from D7)?
  • Q5 — Platform domain naming (carried from ADR-039 / ADR-040 / ADR-041 Open Question §0): <platform-domain> placeholder pending platform-naming + infrastructure decision. Resolution gates capability-URI canonical naming + Tenant-4 GIS endpoint URIs.
