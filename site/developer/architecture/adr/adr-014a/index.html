ADR-014-α: In-Product AI Runtime — Single-Call LLM Assist Contract

Status: Accepted (α activation 2026-05-21; was Deferred — placeholder 2026-05-06). α v1.1 amendments ratified 2026-05-27 (event-substrate integration + BYOK + Phase-2F gate enforcement; see §"α v1.1 Amendments" below). Activation driver: Spec 0020 v1.2 §10.2 Wave 2 (AI-assisted manual grounding for ungrounded vocabulary values) requires a ratified AI-runtime contract before it can ship as a sibling spec. Other near-term consumers: future researcher-side AI assistants, future admin-side AI suggestions, post-Spec 0017 ambient-chat extensions. Date α-activated: 2026-05-21 Deciders: User (Premshay) + claude (drafter) Related: ADR-006 (Archetype Capability Contracts), ADR-010 (Parser-First / LLM-Second Relationship Resolution — α extends this discipline to AI-assist patterns generally), ADR-016 (Telemetry Substrate — α's load-bearing prerequisite, Approved), ADR-033 (Comfort Dial Apply Pipeline — α's bounded-agency principle echoes the dial's advisory-vs-applied distinction), ADR-035 (Tenant Contributor Permission Model — α inherits capability-gate discipline).

What α activates (and what β still defers)​

ADR-014 has existed as a placeholder since 2026-05-06, deferring an "in-app AI orchestration architecture" until prerequisites landed. The α activation does NOT open the full multi-step agent-loop ambition the placeholder reserves. Instead α scopes tight to the slice of in-product AI behavior that is already shipped (Spec 0017 C.3 ambient chat) and the slice that needs the contract to ship next (Spec 0020 v1.2 §10.2 Wave 2). Specifically:

Patternα scopeβ scope
Single LLM call per user action (Q&A, suggestion, summary)YES — covered by α—
Stateless single-call assist with optional retrieval from public authorities (Wikidata, PeriodO, GeoNames) for grounding suggestionsYES — covered by α—
Conversational session bounded to a single workflow surface (import wizard ambient chat)YES — codified from Spec 0017 C.3—
Multi-step agent loop (plan → act → observe → re-plan)NOβ
Agent-to-agent coordinationNOβ
RAG over the v2 epistemic substrate at scaleNO (single-document retrieval OK in α)β
Agent-authored mapping proposals at scaleNO (single proposal-per-action OK in α)β
Autonomous mutation of platform stateNEVER — α floor; β does not relax this without a new ADR—

α activates because the dependent work is real and immediate (Spec 0020 §10.2 Wave 2 is gated on it; ambient chat is already in production). β remains deferred pending an "AI Agent Resolver α" implementation that does not yet have a sponsor.

Context​

KE has shipped one in-product AI surface (Spec 0017 C.3 ambient import-wizard chat) and is about to ship a second (Spec 0020 v1.2 §10.2 Wave 2 admin-assisted vocabulary grounding). Both fit a common pattern — single LLM call, bounded context, advisory output, never mutates platform state directly — but the discipline lives only in the individual specs. Future AI-assist features (researcher search assist, document summarizer, recommender explainer, etc.) will face the same design questions over and over without a ratified contract.

α codifies the discipline that has already been ratified in spec form so future AI-assist features pick up the contract by reference instead of re-litigating each constraint. The contract is intentionally tighter than the eventual β contract β will need; α favors caution because the platform is pre-production single-tenant. β may add constraints for multi-step agent loops, but relaxing any α invariant requires an explicit ADR-014 amendment or successor ADR.

The five questions the original placeholder reserved for activation (Boundary, Telemetry contract, Multi-tenancy at orchestration tier, Retreat behavior, Agent identity in commits) are answered for α single-call patterns below. β reopens them for multi-step agent loops when their use case lands.

Decision​

The α contract specifies seven constraint families that every in-product single-call LLM-assist feature MUST satisfy. Each is a binding invariant; an AI-assist feature that violates any constraint requires either an ADR-014-α amendment (if the constraint should be relaxed platform-wide) or an explicit ADR-014-β proposal (if it crosses into the deferred multi-step territory).

1. Bounded agency (the floor — never relaxed without a new ADR)​

The AI surface MAY: explain, suggest, summarize, retrieve, score, classify, propose for review.

The AI surface MUST NOT, without an explicit user action gated by ADR-035 capability checks:

  • approve, apply, publish, index, delete, mutate any tenant data
  • mutate platform-canonical state (vocabulary registry, slot taxonomy, schema config)
  • enqueue background work that would later mutate state
  • emit signals into telemetry that downstream systems consume as user-equivalent input
  • bypass any reviewer-gate that exists for the non-AI path

Reference implementation (already shipped): Spec 0017 C.3 ambient chat — "The assistant may explain and suggest what to inspect next. It cannot approve, apply, publish, index, delete, or otherwise mutate import state" (per existing ADR-014 placeholder note 2026-05-20).

Rationale: this is the load-bearing safety floor. The LLM is helpful precisely because it can be wrong; wrong-with-mutation-power is unacceptable in α. Any future narrow auto-mutation pattern (for example, an AI-proposed mapping with multi-reviewer approval) needs a new ADR or explicit ADR-014 amendment before implementation.

2. Tenant data isolation​

Tenant data flows into the prompt MUST be:

  • Scoped to request.tenant (the active tenant schema); no cross-tenant blending in any prompt.
  • Bounded by a documented context envelope (e.g., "current wizard project + current mapping proposal + last 5 chat turns" for ambient chat). Document the envelope in the feature spec; no implicit "all tenant data" prompt assembly.
  • Stripped of platform-staff-only data (audit trail rows, telemetry rows, cross-tenant K-anonymized aggregates) before prompt assembly.

Public authority lookups (Wikidata, PeriodO, GeoNames, etc.) MAY happen as part of an AI-assist pipeline, but:

  • The lookup query MUST NOT carry tenant-private data verbatim (e.g., a tenant's slot value goes through a redaction pass + a fingerprint hash before any external API call carries it).
  • The lookup response is treated as public information; merging it back into a tenant-scoped prompt is allowed.

Reference implementation (already shipped): Spec 0017 C.3 ambient chat scoped to MappingProject.source_summary + visible MappingProposal review state; PR #326 added URL-userinfo redaction before truncation.

3. Token budget + graceful degradation​

Every AI-assist feature MUST have:

  • A tenant-local per-session token budget (e.g., Client.ai_session_token_budget for ambient chat; analogous per-feature field for new features). Default budgets are conservative; tenant-admin can raise via ADR-035 capability.
  • A per-call token estimate before sending to the LLM. Calls that would push the session past budget are rejected at the wrapper layer.
  • A graceful degradation path when budget is exhausted: the AI surface degrades to a non-AI mode (static help text, manual entry, FAQ links) — the underlying workflow MUST NOT block on AI exhaustion.

Reference implementation (already shipped): Spec 0017 C.3 ambient chat exhausts → chat disables; import wizard navigation continues. PR #326 zeroed budget-exhausted remaining tokens.

4. Telemetry markers (ADR-016 substrate)​

Every AI-assist call site MUST wrap the provider attempt with capture_llm_call(...) (per ADR-016). A telemetry row is emitted when ADR-016's telemetry_capture_enabled("llm_call") posture is active for the tenant/surface; production AI features must document whether llm_call capture is required, tenant-overridable, or dark by default. The wrapper metadata includes:

  • agent_role (e.g., wizard_ambient_chat, vocabulary_grounding_suggest) — feature-identifying
  • invocation_trigger (e.g., import_wizard_chat, admin_grounding_review) — surface-identifying
  • tenant_schema (for isolation auditing; ADR-016 hash-chained)
  • purpose taxonomy value (per ADR-016 purpose registry)
  • prompt_token_estimate, response_token_estimate, cost_estimate
  • outcome enum: success, budget_exhausted, validation_failed, external_api_failed, model_error
  • For feedback-bearing features: accept_rate_signal, edit_rate_signal, reject_rate_signal (post-user-action)

Raw answer bodies are NEVER captured by default. Features that need answer-body inspection for product reasons must declare it explicitly in their spec and route through an explicit opt-in answer-body capture path with redact-before-log discipline per ADR-016 §3; no feature may call a concrete helper for that path until the helper exists and the feature spec names it.

Reference implementation (already shipped): Spec 0017 C.3 ambient chat — agent_role="wizard_ambient_chat", invocation_trigger="import_wizard_chat", raw answer text NOT in telemetry.

5. Per-tenant control surface​

Every AI-assist feature MUST be controllable per-tenant via a Client-level boolean (e.g., ai_ambient_chat_enabled, ai_grounding_suggest_enabled). Default values:

  • Defaults to enabled ONLY if the feature has shipped at least one prior tenant successfully without complaint.
  • Defaults to disabled for new features; tenant-admin opts in.
  • Platform-staff override exists for emergency disable across all tenants (e.g., LLM provider outage; cost overrun).

The control surface lives in tenant-admin UI per ADR-036 (workspace/operations split). Disable acts immediately (graceful degradation per constraint 3).

Rationale: experimental AI features may simplify some tenants' work and complicate others'. The per-tenant kill switch is how we learn from telemetry without forcing every tenant to live with each experiment.

6. Trust posture per audience​

AI-assist output is presented differently based on the audience:

AudienceUI framingAuto-apply allowed?
Researcher (epistemic editor)"Suggested" / "Possible match" / "AI proposal" — always taggedNever (always reviewer-gated per ADR-010 + ADR-033 comfort dial)
Tenant admin (admin surfaces)"Suggested" / "AI recommends" — always taggedNever in α (per Bounded Agency floor)
Platform staff (cross-tenant analytics)Aggregated AI signal as one input among many; no per-tenant action without reviewNever

The tag MUST be visually consistent across features (proposal: a small "✨ AI" icon with hover-tooltip explaining provenance). Researcher MUST be able to distinguish AI-derived content from parser-derived content from human-authored content (per the deterministic-first calibration preserved in docs/context/partner_model-archive-2026Q2.md, 2026-05-05 Phase-2K.23.3).

7. Failure modes (retreat behavior)​

When the LLM call fails (timeout, model error, validation rejection, external API down), the feature MUST:

  • Surface a user-facing message naming the failure mode in plain language ("Preview unavailable" / "AI suggestion service is down — please proceed manually").
  • Fall back to the non-AI path (manual entry, static FAQ, parser-only output).
  • Log the failure to ADR-016 telemetry (outcome enum above).
  • NOT silently retry past the budget envelope; NOT silently substitute a fallback that the user can't tell from a real answer.

Reference implementation (newly added): Spec 0021's committed spa/src/components/PublicPreview/index.jsx wrapper error state — "Preview unavailable" alert with the underlying error message; same discipline applies to AI-assist.

Specific contract for Spec 0020 §10.2 Wave 2 (manual-grounding AI assist)​

The §10.2 Wave 2 sibling spec post-ADR-014-α MUST satisfy the seven constraints above. Specific application:

  • Bounded agency: AI proposes fork-declare candidates (e.g., "this value looks like Wikidata Q28934 = Hijri calendar"); admin accepts / edits / rejects. AI never declares forks autonomously.
  • Tenant isolation: AI sees the ungrounded value + its kind (e.g., ('calendar', 'hijri-shamsi')) + the tenant's existing fork chain for that kind. AI does NOT see other tenants' fork chains or any cross-tenant aggregate.
  • External lookups: AI may query public authorities (Wikidata, PeriodO) for the unknown value only after the feature classifies the lookup term as public-safe or the admin explicitly confirms that it may be sent externally. Values that are not public-safe use a redacted/normalized public label or skip external lookup. No tenant-private context (other slot values, project name) flows to the external API.
  • Token budget: per-tenant ai_grounding_suggest_token_budget field on Client (default ~10k tokens per session, calibrate later). Per-suggestion cost cap (~500 tokens). Exhausted budget → admin sees "Manual grounding only — AI quota for this session is exhausted."
  • Telemetry: agent_role="vocabulary_grounding_suggest", invocation_trigger="admin_grounding_review". Outcome enum tracks accept / edit / reject per cluster.
  • Per-tenant control: Client.ai_grounding_suggest_enabled boolean, defaults DISABLED for v1 (per "defaults to disabled for new features").
  • Trust posture: admin-facing UI tags AI suggestions with the ✨ AI icon; admin's choice is the authoritative action.
  • Failure mode: external authority API down → AI suggestion field shows "Lookup unavailable — please research manually"; declare/reject mutations stay available.

Open questions for α follow-up amendments (not blocking activation)​

These are α-scoped questions that don't gate the activation but should be resolved as the second or third α feature ships:

  1. Provider abstraction: ambient chat (Spec 0017 C.3) currently uses a single LLM provider. Should α specify a provider-abstraction interface so features can route to different providers (Anthropic, Bedrock, on-tenant open model) per tenant config? Likely yes for B.6 production telemetry posture; not blocking for §10.2 Wave 2. RESOLVED in α v1.1 amendment (2026-05-26) — see §"α v1.1 Amendments" below.
  2. Confidence threshold per feature: should α specify a minimum confidence threshold below which AI suggestions don't surface at all (vs surface with a low-confidence badge)? Probably feature-specific; α just requires the threshold be documented in the feature spec.
  3. Cross-tenant convergent-pattern feedback: when N tenants accept the same AI-suggested fork-declare for a vocabulary value, does that signal feed back into Threshold-A promotion? This crosses into β territory (cross-tenant pattern recognition) and should be deferred. Sharpened in α v1.1 amendment (2026-05-26) — the cross-tenant feedback mechanism is described as an event-substrate consumer; activation still β-deferred.

α v1.1 Amendments (2026-05-26) — Event-substrate integration + BYOK + Phase-2F gate enforcement​

This amendment extends ADR-014-α to compose cleanly with the workspace event substrate (ADR-046 successor + Spec 0031 successor under design per docs/research/2026-05-26_wol-event-substrate-research-compendium.md §7) and resolves α Open Question #1 (provider abstraction) via BYOK activation.

Triggering corrections (from 2026-05-26 brainstorming session): KE is greenfield-enough to redo the substrate; realtime collab is in Phase-1 scope; multi-workspace + project view is in Phase-1 scope; federation is near-term (~3 months); BYOK for LLMs is a new architectural item the user surfaced at session-end. All amendments below stay within α's bounded-agency floor — they do NOT relax the seven constraints; they sharpen and extend them for the event-sourced substrate.

The amendment does NOT promote AI to first-class actor with event-log authority. That remains β territory per the original ADR-014 §"When ADR-014-β activates."

Constraint 8 (NEW) — AI events carry forensic provenance metadata​

Every AI-emitted event (ai_proposal, ai_chat_message, ai_vocab_match_accepted, ai_citation_proposal, ai_metadata_proposal, et al.) MUST carry a forensic_provenance payload field with:

  • input_source_bytes_hash — SHA-256 of canonical normalized agent input (per Phase-2F gate 5 + LLM-telemetry §7)
  • fetch_timestamp — when the input was captured upstream of the agent
  • agent_role + agent_version (already in α constraint 4; lifted into event payload directly)
  • prompt_template_hash — SHA-256 of the full prompt template (versioned, reproducible)
  • output_hash — SHA-256 of the agent's raw output
  • confidence_score (per α Open Question #2; surfaced as event metadata)
  • refusal_flag + refusal_category_enum (if the agent refused; never the raw refused payload — per LLM-telemetry §6.3 prompt-injection-capture-without-leakage pattern)

These fields are MANDATORY for every AI event. Materialiser refuses to commit AI events that lack any forensic field.

Why — Phase-2F gate 5 (forensic provenance map) requires every agent output traceable to (input source bytes, fetch timestamp, agent version, prompt hash, output hash). The event substrate is the natural home; this constraint formalises the integration.

Constraint 9 (NEW) — Phase-2F gates enforced at event-emission boundary​

The seven Phase-2F gates (confusables, prompt-injection corpus, jailbreak corpus, sandbox-escape, forensic provenance, adversarial wreckage report, recommender-prior poisoning per ADR-033 §4.1.1.1) MUST execute BEFORE the AI event commits. Failed gates emit ai_proposal_blocked events with the failure reason instead of committing the proposal.

Blocked events stay in the event stream — Phase-2F gate 6 (adversarial wreckage report) aggregates them over rounds. Blocked events MUST NOT carry the raw blocked content; only the forensic hashes + classifier verdict + gate-failure enum.

Why — ADR-014-α §"Bounded agency" + AI Agent Resolver Epic §"Phase-2F red-team perimeter (binding)" already declare these gates as α-blocking. This constraint locates the enforcement at the event emission point so blocked-but-attempted AI work is visible in the event substrate for cross-round analysis.

Constraint 10 (NEW) — Signed audit trail via hash-chain integration​

AI events join the workspace event substrate's append-only hash chain by including the prior event's hash in the current event's prior_event_hash field. Tamper-evident under linear inspection (per LLM-telemetry §3.2 minimum-viable-shape).

Higher-stakes AI operations escalate to full per-tenant signing per LLM-telemetry §3.3:

  • AI proposals against PII-bearing slots (pii_classification IN {subject_identifier, narrative_pii, quasi_identifier})
  • AI proposals with federation_eligible=true (cross-tenant leakage class)
  • β-activated autonomous-mutation operations (if/when β fires)

Full signing uses per-tenant signing keys held in the same KMS substrate as Forgettable Payloads crypto-shred keys. Same custody discipline.

Why — preserves the audit chain across substrate boundaries; aligns the AI-call audit shape with the broader event-store audit shape; no separate AI-audit-substrate to maintain.

Constraint 11 (NEW) — Provider abstraction interface (resolves Open Question #1)​

KE SHALL provide a LLMProvider abstraction at epistemic/services/llm_provider.py (or equivalent) with:

  • provider_name enum: anthropic_api, bedrock_anthropic, openai_api, gemini_api, local_ollama, future additions registered via capability-URI binding (ADR-043 Workspace slot pattern)
  • provider_version (model + API version; for forensic provenance hash)
  • call(prompt, max_tokens, system, ...) -> {text, token_usage, finish_reason}
  • estimate_tokens(prompt) -> int (for α constraint 3 budget pre-check)

Each provider implementation is a small class. New providers register via the existing federated preset registry pattern (ADR-038); per-tenant subscription works the same way as standards / connector capabilities.

Why — BYOK forces this question's answer. The interface is the structural prerequisite for tenant-supplied keys; resolving the question now (vs deferring further) unblocks BYOK + tenant-specific model preferences (legal AI / classical-Greek-tuned / specific provider relationship).

Constraint 12 (NEW) — BYOK (Bring Your Own Key) for LLM providers​

Every AI-assist feature MUST support per-tenant provider configuration with two modes:

  • platform_covered (default): KE's platform-managed provider account; KE bears the LLM cost; subject to per-tenant token budgets per α constraint 3.
  • byok: tenant supplies their own LLM provider API key; tenant bears the cost; per-tenant budget caps still apply (in tenant-local units) for graceful degradation, but the budget source-of-truth is the tenant's configured cap.

New Client model fields:

ai_provider = CharField(choices=PROVIDER_REGISTRY, default='anthropic_api')
ai_provider_mode = CharField(choices=['platform_covered', 'byok'], default='platform_covered')
ai_provider_key_ref = UUIDField(null=True)  # FK to encrypted key in tenant_secrets
ai_provider_budget_tokens = IntegerField(null=True)  # tenant-defined cap when byok

Key custody pattern (composes with Forgettable Payloads / crypto-shred discipline):

  • BYOK API keys live in a tenant_secrets table (separate from pii_payloads; same encryption pattern); encrypted with per-tenant master key
  • Master key lives in the chosen hyperscaler's KMS (OCI Vault for pilot; portable to GCP Cloud KMS for spinout)
  • Tenant-admin UI: explicit consent flow — "Use platform AI (covered by KE platform) / Use your own provider (paste API key); your usage will be billed to your provider account"

Telemetry attribution (extends α constraint 4):

  • Event metadata includes ai_provider + ai_provider_mode + ai_provider_account_id_hash (hashed tenant account identifier for audit without leaking the key)
  • Token count + estimated cost still captured platform-side
  • Actual cost lives with tenant — platform never sees the bill
  • Tenant gets a per-tenant "AI usage" dashboard from the captured token counts

Compliance attribution shift:

  • Under platform_covered: KE's DPA with Anthropic/Bedrock covers the data-processing chain
  • Under byok: tenant's own DPA with their provider covers the data-processing chain; KE is intermediary handling prompt assembly + redaction (per LLM-telemetry §6.2 pattern)
  • GDPR sub-processor list per tenant changes; tenant-admin UI surfaces "this AI feature, when enabled, sends [classified slot values] to your configured provider"

Failure modes (extends α constraint 7):

  • Tenant key invalid / suspended → degrade to non-AI path per constraint 7; telemetry outcome=tenant_provider_failed
  • Tenant exceeded own provider's quota → same path
  • Platform-covered provider outage with tenant having BYOK configured for the feature: escalate to tenant-admin "platform AI is down; switch this feature to your own key temporarily?"

Why — academic-incubator-then-spinout trajectory makes platform-borne LLM cost a real concern at scale; tenants increasingly have their own research-grant AI credits (Anthropic for Research, OpenAI Academic, etc.); BYOK de-risks LLM cost growth while preserving the bounded-agency floor.

Constraint 13 (NEW) — Federation × AI orchestration discipline​

When AI proposals federate cross-tenant (per the federation event substrate; ADR-043 capability URI K.event_stream_federate):

  • Federation events for AI-emitted artifacts carry ai_provider + ai_provider_mode attribution as event metadata (tenant B can see "this came from Anthropic Claude 3.5" vs "local Mixtral")
  • Receiving tenant's recommender-prior poisoning controls (ADR-033 §4.1.1.1) stratify by provider — provider-specific bias detection becomes possible
  • Threshold-A promotion can require multi-provider convergence (e.g., accept proposal only if same proposal converged from N tenants AND M distinct providers) — sharpens the cross-tenant feedback signal beyond pure count
  • Receiving tenant's Phase-2F gates re-validate AI events; origin gate verdicts don't transfer

Default federation_eligible=false posture (per the sketches §B) applies to AI events identically to human events. AI proposals federate only when the source tenant + the human-reviewer accept and mark the event as federation-eligible.

Why — sharpens the cross-tenant feedback question (α Open Question #3) without promoting AI to direct-federation-actor authority; preserves the Phase-2F re-validation discipline; lets receiving tenants stratify trust by provider.

Constraint 14 (NEW) — AI presence in Hocuspocus rooms (collab substrate composition)​

When an AI agent is processing a row (proposing a citation, suggesting a relationship, drafting biographical text), researchers see an "✨ AI is working" presence chip in the Hocuspocus presence layer. The AI proposal materialises as an inline card adjacent to the Yjs CRDT region — NOT inside the Y.Doc.

Strict discipline: AI cannot write to the Y.Doc directly. That would be auto-mutation and violates α constraint 1. AI emits proposal events; the workspace UI renders proposals as adjacent inline cards that the human researcher can accept (commits an ai_proposal_accepted event) or dismiss.

Why — composes the Yjs/Hocuspocus realtime collab substrate with α's bounded-agency floor; gives researchers visibility into AI activity without ceding the collab-channel write authority.

α v1.1 does NOT change​

  • The seven α constraints stay verbatim (constraints 1-7); v1.1 adds constraints 8-14 as event-substrate operational extensions.
  • The "bounded agency" floor (constraint 1) — AI never approves/applies/publishes/mutates without explicit human action.
  • The β activation triggers (4 conditions) — multi-step loops, agent-to-agent coordination, RAG at scale, autonomous mutation. β remains deferred.
  • The Spec 0020 §10.2 Wave 2 contract (still satisfies α; now also satisfies v1.1 by inheritance).

Consequences​

Positive​

  • Spec 0020 §10.2 Wave 2 unblocked; sibling spec can open immediately post-ratification.
  • Future AI-assist features pick up the contract by reference rather than re-deriving constraints.
  • The discipline that's already implicit in Spec 0017 C.3 is now explicit and citable.
  • Telemetry (ADR-016) becomes the load-bearing signal for whether AI-assist features help or annoy.
  • Per-tenant kill switches let us A/B without forcing every tenant to live with each experiment.

Negative​

  • α deliberately leaves multi-step agent loops + autonomous mutation off the table. Features needing those capabilities have to either fit within the α envelope or wait for β.
  • The seven-constraint discipline adds spec-authoring overhead for every new AI-assist feature. Mitigation: the contract is short enough that satisfying each constraint is straightforward boilerplate.
  • The "defaults to disabled for new features" rule means every new AI feature ships dark and waits for tenant opt-in. Tenants who don't know to opt in won't see the value. Mitigation: tenant-admin onboarding doc should surface new AI features as they ship.

Mitigations​

  • ADR-016 telemetry substrate is already shipped (Approved 2026-05-05); the seven constraints map directly onto already-established telemetry fields.
  • Spec 0017 C.3 ambient chat is the concrete reference implementation any new feature can pattern off.
  • Per-tenant kill switches use Client model boolean fields — same pattern as other tenant-config flags already in production.

When ADR-014-β (or successor) activates​

α stays in force until at least one of:

  1. A feature genuinely needs multi-step agent loops (plan → act → observe → re-plan). Spec 0020 §10.2 Wave 2 doesn't; it's single-call.
  2. A feature genuinely needs agent-to-agent coordination. None currently in flight.
  3. A feature genuinely needs RAG at scale (retrieval over the full v2 epistemic substrate, not per-document lookup). Future researcher-side "ask Atlas" might.
  4. A feature genuinely needs autonomous mutation (within reviewer-gate envelope). This would require both β + an explicit Bounded-Agency relaxation amendment to α.

The β activation has to satisfy ADR-014-α as a floor (β can ADD constraints but not REMOVE the seven α invariants) plus add its own decisions for the multi-step territory.

Pre-activation history (preserved from 2026-05-06 placeholder)​

Why the original placeholder existed​

Multiple documents referenced ADR-014 as the locus for In-App AI orchestration architecture (LLM proposal layer, agent loop wiring, telemetry feedback into prompts, multi-step reasoning around Atlas's epistemic substrate):

  • docs/devlogs/2026_w18/2026-05-03_*.md and docs/devlogs/2026_w19/2026-05-05_1153_round-8-absorption.md reference ADR-014 as the deferred orchestration architecture.
  • docs/research/2026-05-01_search-engine-comparison/process-and-findings.md cites it as the consumer of the search retreat target.

Until the placeholder existed, those references were dangling. The doc-staleness lint (scripts/atlas/check_doc_staleness.py, F7) surfaced them on 2026-05-06. The placeholder resolved the references and documented the deferral honestly.

Original deferral rationale (2026-05-03 ambition right-sizing)​

In-app AI orchestration was deliberately scoped out of the immediate-term roadmap in favour of:

  1. The telemetry substrate (ADR-016) as a pre-condition. AI orchestration without structured tracing of LLM-call inputs / outputs / decisions / outcomes is debug-blind. ADR-016 was Approved 2026-05-05.
  2. The mapping-proposal substrate (data_import.MappingProposal, data_import.MappingProject, the parser-first/LLM-second resolver chain per ADR-010, the AI proposal layer commits 2-4 from 2026-04-30) as the first-iteration AI surface. Atlas has shipped this. It is not what ADR-014 was reserved for.
  3. The runtime config pipeline (ADR-012) as the integration contract for orchestrated agents. Until tenant config flows entirely through the runtime pipeline (mostly true post-Phase-2K.6), agent-driven changes had no clean place to land.

The placeholder reserved scope for: multi-step agent loops, agent-to-agent coordination, context-budget management, retrieval-augmented agent prompts running over the v2 epistemic substrate, agent-driven mapping-proposal generation at scale. α activation does NOT cover these. They remain β scope.

2026-05-20 Ambient Chat α Note (now codified above as Reference implementation)​

Spec 0017 Sprint C shipped a bounded Import Wizard ambient-chat slice — the first user-visible AI assistance surface that touches the orchestration boundary. The placeholder noted this was "not ADR-014 activation" by the placeholder's own definition (multi-step agent loop), but called it a "reference boundary for future in-app AI work." α activation codifies this exact pattern as the contract rather than treating it as a one-off. The seven-constraint contract above generalizes Spec 0017 C.3's discipline so future single-call AI-assist features inherit it by reference.

  • It performs one bounded LLM call per researcher question, not a multi-step agent loop.
  • Context is stage-scoped and compiled from the current MappingProject source summary + visible MappingProposal review state.
  • Conversations are browser-session only and keyed by tenant schema + mapping project.
  • customers.Client.ai_session_token_budget caps the per-session token spend; exhaustion disables chat only, never the import workflow.
  • The call site wraps provider attempts with capture_llm_call metadata via agent_role="wizard_ambient_chat" and invocation_trigger="import_wizard_chat" without storing raw answer text in telemetry.
  • The assistant may explain and suggest what to inspect next. It cannot approve, apply, publish, index, delete, or otherwise mutate import state.
  • A deterministic local action-intent guard blocks direct mutation requests before any provider call or token spend, while still allowing how-to and explanation questions about the same actions.

Original "What ADR-014-α (the first activation) must decide" (now answered above)​

The placeholder listed five decisions. α activation resolves each:

  1. Boundary: resolved by constraint 1 (Bounded Agency). AI is advisory; never mutates state.
  2. Telemetry contract: resolved by constraint 4 (Telemetry markers). Raw answer bodies NOT captured by default; per-call metadata is passed through the ADR-016 wrapper, with row emission controlled by the active capture posture.
  3. Multi-tenancy at the orchestration tier: α uses shared infrastructure with request.tenant scoping per constraint 2 (Tenant isolation). β may revisit if a tenant requires isolated pool.
  4. Retreat behaviour: resolved by constraint 7 (Failure modes). Graceful degradation to non-AI path; never silent.
  5. Agent identity in commits / proposals: out of α scope (α is single-call advisory; nothing is committed by the AI). β must address when agent-authored mutations land.

Alternatives previously in play (still relevant at the meta level)​

  • Status quo (single-call LLM proposals without a contract): is what α replaces. Worked until two features (ambient chat + grounding) needed shared discipline.
  • Off-platform agent infra (Anthropic Agent SDK, LangGraph, custom): trades integration depth for time-to-value. α uses native infrastructure for single-call patterns; β may re-evaluate for multi-step.
  • Defer further (skip ADR-014 entirely): rejected at α because Spec 0020 §10.2 Wave 2 has a concrete dependency. β remains deferred per its own activation trigger.
