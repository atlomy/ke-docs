ADR-038: Federated Preset Registry as Federation Contract

Status: Proposed (v1.2 — amended 2026-05-20 per R1c targeted stress-test refinements layered on v1.1 absorption; see docs/superpowers/plans/2026-05-20-period-place-spatial-architectural-pass.md for absorption provenance) Date: 2026-05-20 Deciders: User; architecture team Related: ADR-002 (Hybrid Ontology), ADR-004 (Tenant Ontology Mapping), ADR-006 (Archetype Capability Contracts), ADR-022 (Anchor + ClaimCluster + ArtifactVersion + extractor framework), ADR-023 (Publication & Persistent Identifiers), ADR-029 (Projection-First Published Entry Layer), ADR-030 (CIDOC + Linked Art Export Profile Choice), ADR-035 (Tenant Contributor Permission Model), ADR-037 (Slot-Type Taxonomy and Tenant Vocabulary Layer) Scope-extends: ADR-037 — formalizes the Phase B "tenant-curated preset library" framing into a federation-contract layer with versioning, subscription, conformance, forking, and lineage Supersedes: nothing Companion:

  • docs/superpowers/specs/2026-05-20-phase-b-federation-contract-worked-examples.md — worked examples + the original stub
  • docs/superpowers/specs/2026-05-20-place-period-federation-contract-paths.md — comparative-paths brainstorm (Path A archetype-promotion vs Path B preset-as-contract; Path B chosen)
  • docs/decisions/log.md 2026-05-20 — autonomous-variation-handling principle (binding constraint on §Decision)
  • docs/decisions/log.md 2026-05-20 — ADR-030 SHACL shape validation prerequisite

TL;DR​

ADR-037 names a TenantSlotPreset row that catalogs (SlotKind, Modifiers) recipes. The Phase B follow-up sprint, as originally written, framed presets as a tenant-local curation feature. The R2 NotebookLM round + the CROSSWALK Phase 1.5 extension + the integrative-tenant pattern + the four-tenant PLACE / TIME_PERIOD evidence recount surfaced that presets are the right architectural location for the canonical commitment the comparative-paths brainstorm was looking for — a place to declare Layer-3 platform-canonical recipes (Place, Period, Person, Document, Event, ClaimCluster) that tenants subscribe to or fork without polluting the platform-default shape.

This ADR formalizes ADR-037 Phase B as the federated preset registry: an open set of PlatformPreset and TenantPreset entries, each carrying a contract (required slots, projection rules, capability activations, complies_with declarations, lineage). Subscription is the tenant's federation contract. Forking with prov:specializationOf lineage preserves tenant pluralism without losing federation queryability. Layered on top is the autonomous-variation-handling principle — the wizard, registry, and complies_with mapping pipeline should reduce human triangulation as the tenant base grows, not require platform-staff intervention per new discipline.

Context​

What this ADR resolves​

Three threads converged into one decision over the 2026-05-19 / 2026-05-20 architectural arc:

  1. R2 NotebookLM round B3 finding (open-critique transcript) — the corrected ADR-037 plus the four-tenant PLACE+TIME_PERIOD schema evidence recount made PLACE and TIME_PERIOD pass Clause 1 PROMOTE under TERM-precedent reasoning, but the integrative-tenant pattern + Visionis's CIDOC-E4 thematic shape made archetype-level promotion architecturally costly (forces uniformity at the cost of long-tail discipline accommodation).
  2. CROSSWALK Phase 1.5 extension — adds PeriodO, GeoSPARQL, GeoJSON, CRMarchaeo, CRMsci, Darwin Core, Pleiades/GeoNames/Wikidata Q-IDs, PROV-O, and RO-Crate to the matrix. Under the extended standards set, PLACE and TIME_PERIOD pass Clause 1 formally — independent of the TERM-precedent path. Output at docs/research/standards/CROSSWALK_extensions_2026-05-20.md.
  3. Comparative-paths brainstorm — Path A (archetype promotion via ADR-006 capability contracts) vs Path B (federated preset registry as federation contract via ADR-037 Phase B extension). Re-weighted toward search-engine / library / data-aggregator / AI-agent discoverability (the user's vision: every team / every discipline / standard core delivering knowledge to public + research community). Net verdict: slight edge to Path B on long-tail accommodation, no data migration, AI-agent provenance, and future evolution. The 35% case for Path A is mental-model familiarity + strictest cross-tenant KE↔KE contract — both lower-weighted under the re-weighting.

Path B was chosen at ~65/35 confidence. This ADR carries the choice.

Why presets, not archetypes, carry the federation contract​

ADR-006 archetype contracts attach at the archetype enum level — a finite, slow-changing set of platform-shipped archetypes (DOCUMENT, TERM, ENTITY, EVENT, MEDIA, ANNOTATION, PASSAGE), each with platform-enforced contracts that every tenant inherits when the archetype is in use. Adding a new archetype is rare and expensive: every tenant carries the new contract, every storage migration touches every tenant, every standards-mapping has to land before the archetype can be used.

ADR-037 Phase B preset contracts attach at the preset registry level — an open, fast-evolving set of PlatformPreset and TenantPreset entries, each carrying subscription-enforced contracts that tenants opt into. Forking is first-class: a tenant authoring yuan-prosopography-place derives from platform-place/v1 with prov:specializationOf lineage; the fork participates in federation queries via prov:specializationOf* transitive closure; the platform's default Place shape stays clean.

The two mechanisms layer:

  • ADR-006 archetype contract governs the storage shape — what tables, what columns, what relationships, what canonical_type enum values exist.
  • ADR-038 preset contract governs the semantic shape — what slot vocabulary, what conformance, what federation participation, what standards a slot complies with.

An entity may simultaneously be archetype=ENTITY (ADR-006 contract) AND ke:preset=platform-place/v1 (ADR-038 contract). Both contracts compose. Tenant config implements both.

Why this is not "another archetype promotion ADR"​

ADR-006 §C5 explicitly defers PLACE, TIME_PERIOD, and SAMPLE with documented promotion conditions. The four-tenant evidence + the CROSSWALK extension verdicts mean those conditions are now met. But the choice of where to land that empirical evidence is not forced — ADR-006 says "if PLACE deserves promotion, add it." It does not say "PLACE must be an archetype rather than a preset." This ADR chooses preset, not archetype, on the architectural grounds in §Alternatives.

What's already shipped that supports this​

  • ADR-037 TenantSlotPreset scaffold — Phase A.1 adds the Django model + 16-preset starter library fixture + GraphQL extension.
  • complies_with: list[str] modifier — Phase A.1 carries the per-slot standards declaration. ADR-038 uses it as the hook for preset-level dcterms:conformsTo.
  • ADR-029 projection-first published Entry layer — the public-reader surface that consumes preset declarations.
  • ADR-022 Anchor + ClaimCluster — every preset's claim-evidence chain composes onto ADR-022 substrate.
  • Spec 0017 import wizard — the natural delivery surface for preset discovery + subscription + forking; the wizard's mapping stage becomes preset-aware.
  • ADR-035 permission model — preset publishing + subscription are operations governed by tenant-admin capabilities.

Autonomous-variation-handling principle (binding constraint)​

Per docs/decisions/log.md 2026-05-20 entry, the user directive "we are striving for an operational model that needs less and less triangulation by us and more autonomous system that handles all variations" is a binding constraint on this ADR. As KE grows from 4 tenants to 40 to 400, manual triangulation per new discipline does not scale. The platform's preset registry + import wizard + standards-mapping pipeline must learn to absorb variation without requiring platform-staff intervention for every new arrival. This shapes the §Decision (auto-detection over manual curation), §Acceptance (registry-measured Threshold-A promotion), and §Phasing priorities (wizard preset-discovery before lineage-UI).

Decision​

The federation-contract layer for KE is the federated preset registry. The eight binding points:

D1 — Preset taxonomy​

Presets are formalized into two types:

  • PlatformPreset (RDF type ke:PlatformPreset): authored by the platform, immutable per version, federation-visible across all tenants. Initial library at ratification time includes (at minimum) Place, Period, Person, Document, Event, and ClaimCluster.
  • TenantPreset (RDF type ke:TenantPreset): authored by a tenant, tenant-scoped by default, optionally federation-visible. Forks of any preset (Platform or Tenant) are TenantPresets that point at their parent via prov:specializationOf.

The taxonomy is two-typed, not N-typed: there is no "DisciplinePreset" or "CommunityPreset" tier. Discipline and community concerns surface via lineage chains (prov:specializationOf* from a tenant fork to a platform parent) and via tenant grouping, not via a fixed enum. This honors the foundational principle (canonical structure is shared; interpretation is tenant-specific) and matches the Spec 0017 withdrawal of the domain-archetype dropdown for the same reasons.

D2 — Preset contract​

Every preset carries an explicit contract:

Contract elementDescription
Required slotsSlots every subscribing entity MUST populate. Enforced at subscription time (back-check) and at entity create/update (write block).
Recommended slotsSurfaced in the wizard + workspace as defaults; not enforced.
Forbidden patternsAnti-patterns explicitly ruled out (e.g., "Place preset cannot use canonical_type=Person").
Projection contractHow the preset's slot vocabulary maps to JSON-LD types + standards-export views. Includes dcterms:conformsTo declarations derived from the preset's slots' complies_with modifiers (ADR-037).
Capability flag activationsAbstract capability URIs (per v1.1 D6) declaring what the subscribing consumer surface needs to support (e.g., subscribing to Place declares ke:supportsSpatialRendering; subscribing to Document declares ke:supportsCitationWidget; subscribing to ClaimCluster declares ke:supportsAttestationWalk). Each consumer (default React frontend, headless aggregator, Python pipeline) maps URIs to native rendering via its own local registry.
Lineageprov:specializationOf chain back to a parent preset (for TenantPreset forks). PlatformPresets may also chain back to a prior platform version.
VersionPresets are immutable per version. Evolution is via a new version with prov:specializationOf from the prior version. Migration paths between versions are tenant-side opt-in.
complies_with (preset-level)Aggregation of slot-level complies_with declarations into preset-level standards-conformance metadata. Drives the public-reader dcterms:conformsTo triples in the projection-layer JSON-LD output.

Contract enforcement happens at three boundaries:

  1. Subscription time: when a tenant declares subscribes_to: [<preset IRI>] in its config, the platform back-checks existing entities against the preset's required slots and surfaces conformance gaps. Tenant admin closes the gaps before subscription completes.
  2. Entity create/update time: writes that violate the contract (missing required slot, forbidden pattern) are blocked at the resolver layer.
  3. Wizard preview time: per Spec 0017, the wizard's preview stage surfaces conformance violations BEFORE materialization, so the researcher sees the problem before any data lands.

D3 — Subscription mechanism​

Tenants subscribe to presets via tenant config (subscribes_to: [<preset IRI>]). Subscription is per-tenant, not per-archetype-row — multiple canonical_type values within a single archetype can subscribe to different presets (an ENTITY with canonical_type=Site subscribes to platform-place/v1; an ENTITY with canonical_type=Person subscribes to platform-person/v1).

Subscription is a binding act: the tenant accepts the preset's required-slot contract and projection contract. Non-subscribers escape — entities without preset subscription are not federation-visible under preset queries, but they remain queryable per archetype + canonical_type.

Subscription is reversible: a tenant can unsubscribe (with appropriate platform warning about federation visibility loss), but unsubscription does not destroy entity data.

D4 — Forking mechanism​

Tenants publish a derived TenantPreset by declaring prov:specializationOf <parent-preset-IRI> plus a free-text ke:forkRationale describing the divergence and (optionally) new required slots. The platform validates monotonicity:

  • A fork can ADD required slots (the fork is strictly more constrained than the parent).
  • A fork cannot REMOVE the parent's required slots (the fork must still satisfy the parent's contract).
  • A fork can ADD dcterms:conformsTo declarations.
  • A fork cannot REMOVE the parent's dcterms:conformsTo declarations.

The monotonicity rule preserves transitivity: an entity subscribed to yuan-prosopography-place (which forks platform-place/v1) is queryable under platform-place/v1 via lineage closure, because the fork can only have tightened the contract, never loosened it.

ke:forkRationale is free-text; the platform does not enforce content discipline on the rationale. Tenant admin and workspace UI render the rationale + a slot diff (fork vs parent) for transparency.

D5 — Federation queryability​

The federated preset registry is exposed at a stable URL (canonical form: https://ke.atlomy.org/presets/.well-known/registry.ttl) as RDF / Turtle. SPARQL endpoint queries support:

  • Strict match — entities subscribed directly to a given preset IRI.
  • Include forks — entities subscribed to a preset OR any preset whose prov:specializationOf* (transitive closure) reaches the given preset.
  • Strict fork — entities subscribed to a specific TenantPreset IRI only.

Each preset's IRI is content-stable per version (https://ke.atlomy.org/presets/<presetId>/v<n>). Subscriber count and federation-query metadata are platform-tracked and exposed in the registry as ke:subscriberCount and ke:federationQueryCount30d (or equivalent). These metrics drive Threshold-A auto-promotion candidate detection (see D7).

The JSON-LD projection of an entity (ADR-029 published Entry surface) embeds the entity's preset IRI plus the preset's prov:specializationOf chain so that a structured-retrieval consumer (federation SPARQL endpoint, GraphRAG system, search-engine crawler, scholarly-infrastructure aggregator) can query the federation without needing the registry endpoint as a separate fetch. NOT a vanilla-RAG enabler — vanilla RAG embeds text content and is agnostic to JSON-LD typing per partner_model 2026-05-20 calibration; the lineage chain serves consumers that parse the structure. Worked example in the companion spec §2.

D6 — Capability activation (v1.1 — abstract capability URIs replace widget names per A3 / Q8)​

Subscribing to a preset activates platform-shipped widgets, projection rules, and standards-export surfaces declared in the preset's complies_with aggregation. v1.1 architectural correction (per post-D.2 R1 finding A3 / Q8 in plan v2): capability activations are declared via abstract capability URIs, NOT specific React widget names. v1.0 declared activations like "MapWidget" — this smuggled UI implementation into the federation data contract. Headless CMS / Python ML pipeline / GIS aggregator consumers cannot use React widget names; when the platform upgrades its UI framework, every preset subscription contract breaks.

The v1.1 capability URI vocabulary (in the ke: namespace):

Capability URIWhat it declares the surface needs to support
ke:supportsTemporalRenderingRender multikey-by-calendar interval data with per-calendar tab disambiguation. Default React frontend mounts the TimeRangeWidget component (extracted from MultilingualCellEditor's data-derived multikey pattern per plan v2 Q12).
ke:supportsSpatialRenderingRender geometry data with CRS-aware visualization. Default frontend mounts MapWidget (per ADR-041 spatial substrate); headless consumers route to their own renderer.
ke:requiresCalendarConversionBridge between subscribed calendars (Hijri ↔ Gregorian, BP ↔ Gregorian via standard conversion tables).
ke:supportsGazetteerLookupAuthority lookup against external gazetteers (PeriodO for period preset; Pleiades/GeoNames/Wikidata for place preset). Standards hint declares which gazetteer; Wave 1 = manual click + lookup affordance; Wave 2 (gated on AI orchestration) = auto-suggest from source-data shape.
ke:supportsCitationWidgetRender CSL citation per Spec 0008.
ke:supportsAttestationWalkRender ClaimCluster attestation chains (ADR-022 substrate).
ke:supportsStandardsExport (+ hint per standard)Activate compliance-export surfaces (GeoSPARQL, GeoJSON, CIDOC-XML, TEI taxonomy/category, PeriodO JSON, RO-Crate, Linked Art, BibTeX, DataCite, Crossref Unixref). The standard hint declares which export view.

Concrete examples (v1.1 — using capability URIs):

  • Subscribe to platform-place/v1 → activates ke:supportsSpatialRendering + ke:supportsGazetteerLookup (hint: pleiades, geonames, wikidata) + ke:supportsStandardsExport (hints: GeoSPARQL, GeoJSON, CIDOC-XML, KML, Linked Art Place); emits dcterms:conformsTo schema:Place, cidoc:E53_Place, geo:Feature, dcterms:Location triples.
  • Subscribe to platform-period/v1 → activates ke:supportsTemporalRendering + ke:requiresCalendarConversion + ke:supportsGazetteerLookup (hint: periodo) + ke:supportsStandardsExport (hints: TEI taxonomy/category + @period attribute, CIDOC-XML E4, PeriodO JSON, EDTF strings); emits dcterms:conformsTo dcterms:PeriodOfTime, cidoc:E4_Period, schema:HistoricalEvent, skos:Concept, time:ProperInterval, edtf:... triples.
  • Subscribe to platform-document/v1 → activates ke:supportsCitationWidget (hint: CSL) + ke:supportsStandardsExport (hints: BibTeX, DataCite, Crossref Unixref).

Client-side mapping: each platform / agent / consumer maintains its own local registry mapping ke: capability URIs to native rendering. The default React frontend ships the mapping (ke:supportsSpatialRendering → MapWidget); a Python aggregator ships its own (ke:supportsSpatialRendering → geopandas.plot()); a headless CMS routes the URIs to its own templates. When the platform upgrades from React to a future UI framework, the federation data contract stays stable; only the local-registry mapping changes.

Capability URI deprecation policy (v1.2 NEW per R1c N9 — version-coupling debt management): when a capability URI's semantics change in v2 of the platform, the URI is versioned, not silently replaced. Versioned form: ke:supportsTemporalRendering/v1 and ke:supportsTemporalRendering/v2. The unversioned form (ke:supportsTemporalRendering) always refers to the LATEST version. Existing tenant presets continue to declare the unversioned form; their effective semantics shift when the platform releases v2 of the capability — this is the documented contract. Consumers that need to pin to a specific URI version declare the versioned form explicitly in their local-registry mapping. Deprecation window: when v2 ships, v1 remains valid + supported in the local-registry mapping for ≥18 months (the "deprecation window"); after the window closes, v1 declarations resolve to v2 semantics OR fall back to a no-op + warning. The deprecation window is announced in docs/decisions/log.md at v2 release with the planned closure date. This bounds version-coupling debt to a known window rather than indefinite legacy support.

The mapping from preset declarations → capability URI activations is canonical platform code (not per-tenant), and the same activation table drives all three surfaces of the three-surface publication contract (ADR-037 §G3) — public reader JSON-LD, research workspace cell editor, compliance export.

D7 — Threshold-A auto-promotion (autonomous variation handling) — v1.1 hardened per A1 / Q9​

The registry MUST automate Threshold-A candidate detection (per ADR-037 §Evolution): when ≥2 tenants independently author equivalent forks (measured by shape similarity — required slot set + complies_with declarations + monotonic refinement of the same parent), the registry surfaces a promotion candidate to platform-staff review. Promotion converts a TenantPreset into a PlatformPreset; subscribers' configs do not need to migrate because the IRI namespace separation makes the promotion a registry-level act, not a per-tenant config edit.

v1.1 hardening (per post-D.2 R1 finding A1 — Threshold-A is gameable + scales poorly without these guards):

Three guardrails MUST land before Phase B.4 auto-detection ships:

  1. Mandatory semantic-divergence declaration. When a tenant publishes a fork, the ke:forkRationale field requires a constrained-vocabulary category declaration: "why does the parent preset fail my use case?" Initial constrained vocabulary (extensible via decision-log addition): discipline-specific-authoring-shape / calendar-or-script-system-extension / regulatory-compliance-requirement / research-protocol-divergence / tenant-naming-only (no functional divergence) / other (free-text required). Threshold-A promotion candidates fire ONLY when ≥2 tenants converge on equivalent shape AND declared the SAME divergence-category reason. This prevents one tenant from spamming identical forks across sub-tenants to artificially trigger promotion (game-theoretic capture risk per A1).
  2. Cross-disciplinary family dimension (v1.2 refined per R1c N4 — "Classics Lock-In bug"). Two paths to promotion exist; they apply to different evidence shapes:
    • Path 2a — Cross-disciplinary convergence (default after Phase A.1 + first non-Classics tenant onboards): Converging tenants MUST span distinct disciplinary contexts (declared via tenant primary domain per ADR-004 amendment Q13). A 2-tenant convergence within ONE discipline doesn't promote via this path; a 2-tenant convergence ACROSS disciplines does. This prevents within-discipline echo effects from triggering platform-canonical commitment.
    • Path 2b — Single-discipline carve-out (Phase A.1 reality + early-stage bundles): Until a non-General + non-Classics tenant onboards, the cross-disciplinary requirement creates chicken-and-egg paralysis (current evidence is single-discipline; Threshold-A can never fire; emergent promotion is blocked indefinitely). The carve-out: within a single bundle's discipline, a higher threshold (N≥3 convergent tenants + 0.95+ confidence + extended observation window 180 days) substitutes for the cross-discipline requirement. The Path 2b promotion is explicitly marked as "single-discipline evidence" in the candidate report; platform staff review with this signal in hand. Once non-Classics tenants onboard, Path 2a becomes the default; Path 2b remains available for genuinely-single-discipline patterns. Critical distinction: the D8 initial-library presets (Place, Period, Person, Document, Event, ClaimCluster) DO NOT go through Threshold-A promotion — they ratify via the deliberate ADR + G3 fixture path. Threshold-A applies only to EMERGENT presets beyond D8. The Classics Lock-In concern only blocks emergent promotion, not the D8 ratification commitments.
  3. Precision-conservative default. Initial threshold tuning errs heavily toward false-negative (miss real candidates rather than surface spurious ones). The auto-detection confidence threshold defaults to 0.85+; registry metrics adjust the threshold downward as candidate-acceptance-rate stabilizes over the first 90 days post Phase B.4. Per the autonomous-variation-handling decision-log entry, "minimize triangulation" does NOT mean "eliminate human review." Initial bias: spurious promotion candidates are more costly than missed real ones (because platform-canonical promotion is a one-way door per ADR-038 D4 monotonicity).

Auto-detection runs continuously (e.g., daily registry pass). Auto-detection produces candidates with a confidence score; platform staff review the candidate, accept or reject, and the decision is recorded in docs/decisions/log.md. Auto-detection does NOT auto-promote — humans still gate the platform-canonical commitment — but the platform pre-computes the candidates rather than requiring platform staff to discover them manually.

Per the autonomous-variation-handling decision-log entry (2026-05-20), this principle extends to:

  • Wizard preset-discovery: auto-detect the closest-match presets from source-data shape during Spec 0017 mapping stage. Wave 1 (Phase B.5 ships): shape-based heuristics (slot-name semantic matching + slot-vocabulary overlap; no external lookup). Wave 2 (gated on AI orchestration sprint per ADR-014-alpha): AI-driven semantic-type agreement at write time + external authority lookup (Wikidata, gazetteers).
  • Fork-suggestion: auto-suggest fork shapes when source-data slot vocabulary exceeds the closest preset's required-slot set. Wave 1: surface candidates with manual gate. Wave 2: AI-driven semantic-type agreement.
  • complies_with inference: Wave 1 ships exact-match + canonical-alias matching only (per B4 — advisory, not binding; manual triangulation for confidence <95%). Wave 2 (gated on AI orchestration) adds semantic-type agreement at write time. Per-slot complies_with declarations become a side effect of preset subscription + slot-name semantic matching at Wave 2; at Wave 1 they remain tenant-admin authored with platform suggestions.

Threshold-A auto-detection is the load-bearing mechanism for the registry's scale guarantee. Without it, the registry health degrades as tenants accumulate forks; with it, platform-canonical convergence is a registry-measured fact rather than a platform-staff observation. The three v1.1 guardrails make the mechanism robust against game-theoretic capture + within-discipline echo + over-eager promotion.

D10 — Three-tier vocabulary extensibility (v1.1 NEW per Bundle D Finding 3 / Q10)​

Vocabulary values across the platform — calendars, place types, period types, event types, script systems, edition variants, register variants, canonical_types, languages, and any future multikey_kind value — live in three tiers:

  1. Platform-canonical (Tier 1) — versioned, ratified per D2-D5, full bindings (conversion functions / Wikidata Q-IDs / standards declarations). Live in PlatformPreset registry. Example: the calendar enum (gregorian, hijri, hebrew, BP) declared in platform-period/v1 is Tier 1.
  2. Tenant-fork (Tier 2) — extends a parent preset's vocabulary monotonically (cannot remove parent values; can add). Partial bindings tenant-provided where they exist. Lives in TenantPreset forks. Example: an archaeological tenant fork adds "BP-calibrated" calendar with their own conversion functions.
  3. Inline ad-hoc (Tier 3) — first appearance in tenant data without prior preset declaration. Auto-promotes to fork-local with grounding_status: ungrounded. Federation queries handle ungrounded values with best-effort honesty (excluded-with-reason in cross-calendar Gregorian filter queries; no silent drop; the federation query result returns "N matches + M ungrounded matches that couldn't be cross-calendared"). Example: a tenant ingests a CSV with a "Sasanian" calendar identifier the platform has never seen; this surfaces as Tier 3 with an admin nudge to declare a grounding (Tier 2 fork) or wait for Threshold-A surfacing if another tenant introduces the same value.

v1.2 refinements per R1c stress-test (N5 + N6):

  • Tier 3 federation-query privacy guard (N5): count-based "ungrounded matches" exposure leaks tenant-private identifier counts to federation queriers (an attacker observing "5 grounded + 12 ungrounded" can infer the existence of 12 private categorical values on the queried tenant). Privacy rules:

    • Per-tenant ungrounded counts are NOT exposed in federation queries. Aggregate-only: federation queries return "N total ungrounded matches across federation" without per-tenant breakdown.
    • k-anonymity floor: ungrounded aggregate counts below k=11 (per ADR-016 anonymity floor) are suppressed entirely; the query reports "fewer than 11 ungrounded matches" instead of an exact count.
    • Tenant opt-out: tenant admin can opt their Tier 3 ungrounded values OUT of federation-query exposure entirely; queries treat that tenant's ungrounded values as "not participating" rather than as zero matches (avoiding the inferential gap).
    • Grounded values are unaffected by these rules — Tier 1/2 vocabulary values participate in federation queries with full visibility per ADR-038 D5 federation queryability rules.

  • Tier 3 canonical_type restriction (N6): canonical_type field is NOT permitted to carry Tier 3 (inline ad-hoc) values. Archetype contracts per ADR-006 are platform-canonical and bound to platform-shipped canonical_type enum values + tenant-declared tenant_relationship_rules per ADR-006 Rev 2.1. Allowing Tier 3 values on canonical_type would break the archetype capability-to-canonical-type mapping stability + the ADR-006 §D5 capability-flag activations + the Spec 0017 wizard's canonical-type validation. The Three-Tier model applies to vocabulary fields (calendar, place type, period type, script, etc.) and slot vocabulary, NOT to canonical_type. Tenant-fork (Tier 2) extension is the mechanism for tenant-specific canonical_type semantics (already supported via tenant_relationship_rules).

Why this pattern matters:

  • Platform-canonical convergence is evidence-driven, not pre-declared. Per the autonomous-variation-handling principle, the platform discovers new platform-canonical vocabulary values via Threshold-A surfacing across ungrounded inline values, not via pre-imagined enums.
  • Tenant pluralism is preserved at every layer. Tenants don't have to commit to platform-canonical vocabulary on day one; they can drop in ad-hoc values, then formalize via tenant fork once they're stable.
  • Federation queries stay honest about partial coverage. Ungrounded values aren't silently dropped from cross-tenant aggregations; they surface as "this many results we can't cross-calendar because their calendar isn't grounded."

This pattern applies UNIFORMLY across multikey dimensions (calendars + languages + scripts + editions + registers + ...) and across categorical fields (place types + period types + event types + canonical_types + ...). The same Three-Tier mechanism that drives the calendar enum drives every other vocabulary in the platform. Bundle D Finding 3 (the source for this section) made this generalization explicit; v1.1 codifies it.

Wave 1 / Wave 2 framing:

  • Wave 1 (Phase A.1 / Phase B.1 ships): manual tenant-admin workflow — tenant admin declares Tier 2 forks via the workspace UI; Tier 3 inline values surface as admin nudges; Threshold-A auto-detection runs on registry-internal signals only.
  • Wave 2 (gated on AI orchestration sprint per ADR-014-alpha): AI-driven semantic-type agreement for Tier 3 → Tier 2 grounding; external authority lookup (Wikidata, gazetteers) at write time; auto-suggestion of Tier 2 fork shapes from source-data analysis.

Alternatives Considered​

Path A — Archetype promotion (ADR-006 capability contracts)​

Add PLACE and TIME_PERIOD (and follow-up archetypes as evidence accumulates) as new entries in ADR-006's archetype list. Each gets a capability contract; existing ENTITY rows with Place-equivalent canonical_type migrate to PLACE archetype rows. Visionis's E4 thematic shape becomes either platform-default (forces uniformity on tenants without thematic needs) or tenant-config subset (architectural tension because ADR-006 contracts are platform-enforced, not tenant-opted).

Why not chosen:

  • Forces uniformity at the cost of long-tail discipline accommodation. The integrative-tenant pattern + Visionis E4-period + JPP Yuan-period evidence shows real tenant-shape divergence inside what would be one platform archetype. Path A handles this by either polluting the platform-default shape (bad — leaks one tenant's vocabulary into every tenant's required surface) or by absorbing the divergence into tenant config layered on top of the archetype contract (awkward — duplicates the role of ADR-037 Layer 3 presets at a coarser grain). Path B's preset-variant approach is structurally cleaner.
  • Requires data migration in JPP + Visionis. ENTITY rows with Place-equivalent canonical_type migrate to a new PLACE table or to PLACE archetype rows. Path B keeps existing rows; tenant config subscribes them to presets, with conformance back-check at subscription time.
  • Mental model is familiar but the apparent simplicity is illusory at the read layer. Path A's "fewer canonical vocabularies for the agent to learn" advantage is offset by ADR-004 tenant-label drift (every tenant labels PLACE differently). Path B's preset IRIs are canonical and stable across tenants.
  • New tenants in tail disciplines either conform to PLACE shape (lossy) or escape via custom canonical_type (no federation). Path B's fork-with-lineage gives a third option: subscribe to the preset, fork with rationale, retain federation visibility via prov:specializationOf.

Path A remains a defensible alternative if the platform's stakeholder priorities shift toward strict cross-tenant KE↔KE federation OR if Threshold-A auto-promotion fails to produce reliable candidates at scale. The 35% confidence reserved for Path A in the comparative-paths brainstorm tracks both of those open conditions.

Augmenting tenant config without a registry​

A lighter alternative: skip the federated registry and let presets remain tenant-local curation entries (the ADR-037 Phase B original framing — "tenant-curated preset library + social-proof recommender"). Subscription is implicit in tenant config; no platform-canonical preset library; no federation queryability via SPARQL.

Why not chosen: this is the framing the worked-examples doc and the comparative-paths brainstorm explicitly rejected. Without a registry layer, no AI-agent or data-aggregator can discover what presets exist across the federation, federation queries lose the prov:specializationOf* transitive closure, and the autonomous-variation-handling principle has nowhere to surface auto-promotion candidates. The registry is the architectural location that converts presets from a local-curation feature into a federation contract.

Per-archetype + per-slot ad-hoc complies_with only (no preset layer)​

A still lighter alternative: rely on per-slot complies_with declarations (ADR-037 Phase A.1) and per-archetype contracts (ADR-006) to carry federation semantics, without a named-recipe preset layer. The aggregation of slot declarations would substitute for preset-level conformance.

Why not chosen: this loses the discoverability + naming layer. AI-agents and aggregators querying "show me all Places in the federation" need a single IRI to match against, not a slot-by-slot reconstruction of the Place concept. Naming the preset is the discoverability act; the preset IRI is the federation handle.

Postponing Path B until R3 round​

Hold the architectural decision until a third NotebookLM round (post-Phase-A.1 + post-G2-build-time-CI + post-G3-three-surface-fixtures) can stress-test the implementation in code, per the R2 absorption's stated R3-trigger condition.

Why not chosen: the R2 audio debate v2 + open-critique transcript already converged on every disposition the corrected ADR-037 carries, and the comparative-paths brainstorm + CROSSWALK extension + integrative-tenant evidence converged on Path B independently. Postponing the choice imports option cost (Place + Period preset ADRs cannot land; the wizard cannot light up preset-discovery; tenant onboarding flows have nothing to subscribe to) for hypothetical critique against the same source base. R3's stronger role is post-Phase-B.1 implementation review, not pre-Phase-B authorial review.

Consequences​

Positive​

  • Long-tail discipline accommodation without per-tenant platform changes. New disciplines fork existing presets with rationale; lineage preserves federation visibility; no archetype migration.
  • No data migration in JPP + Visionis. Existing ENTITY rows stay in place; tenant config subscribes them to platform-canonical presets with conformance back-check surfacing gaps to tenant admin.
  • Stronger structured-retrieval provenance. The ke:preset + prov:specializationOf chain in JSON-LD output is queryable by GraphRAG systems + federation SPARQL clients + scholarly-infrastructure aggregators that consume PROV-O grounding. Strict-match, include-forks, and follow-lineage become first-class query axes. NOT a vanilla-RAG benefit — vanilla RAG (text-chunk embedding) doesn't parse the lineage triples; this serves structured consumers only.
  • Federation discovery via a single SPARQL query rather than N tenant-by-tenant API calls. The registry endpoint exposes the full preset graph + subscriber metadata + standards-conformance declarations.
  • Autonomous variation handling at registry scale. Threshold-A candidates surface continuously; per-slot complies_with inference removes manual standards-binding from the wizard's critical path; tenant-staff triangulation per new discipline drops as the registry learns the platform's variation patterns.
  • Capability activation is preset-driven via abstract URIs. Subscribing to Place declares ke:supportsSpatialRendering + ke:supportsStandardsExport (hint: GeoSPARQL, GeoJSON, KML); each consumer (React frontend mounts MapWidget; headless / Python aggregators route to their own renderers) maps URIs to native surfaces. No tenant code, no Django config flag, no per-tenant migration, no React-coupling. Three-surface publication contract (ADR-037 §G3) wires straight onto preset declarations.
  • Future evolution is cheaper. New presets are registry entries with their own small ADRs. New archetypes remain expensive (ADR-006 amendment + every-tenant migration), which is the correct cost gradient: archetypes are slow, presets are fast.

Negative​

  • Federated preset registry implementation is non-trivial. Versioning, conformance, lineage, RDF endpoint, SPARQL support, Threshold-A auto-detection — each is a load-bearing engineering surface. Phase B.1 alone ships a real new platform subsystem.
  • Per-preset documentation overhead. Each PlatformPreset gets its own small ADR + a wizard-facing description + a workspace-facing description + standards-conformance fixtures. Six initial presets means six ADRs + six fixture sets at ratification time.
  • Preset library curation is ongoing platform work, with no clean end state. As tenants fork, candidates surface, and the platform-canonical library grows, the curation cadence is permanent. This is the price of accommodating the long tail.
  • Novel mental model. ADR-006 archetype contracts and ADR-037 Layer 3 presets together form a two-layer contract surface that requires explanation to new engineers + new tenants. The companion worked-examples spec + the per-preset ADRs carry the explanatory weight.
  • Preset proliferation risk. If forking is too easy and Threshold-A auto-promotion is too lax, the registry accumulates redundant variants. Mitigation in §Implementation: require ke:forkRationale on every fork; surface fork lineage in the workspace + wizard; show federation-cost of forking in the wizard; tune Threshold-A precision/recall by registry metrics. Reasoned conservatism on the platform-canonical library is also a mitigation — the platform admits new PlatformPresets only on Threshold-A evidence + standards-conformance fixtures.
  • Dependent on ADR-030 ratification for full external interop. The dcterms:conformsTo declarations in preset projections need a concrete profile (Linked Art JSON-LD vs full CIDOC CRM JSON-LD vs SPARQL view vs constrained KE application profile) and SHACL shape validation against frozen fixtures (per the 2026-05-20 ADR-030 decision-log entry) before external repositories ingest cleanly. Phase B.1 ships the registry without external-interop guarantees; Phase B.5 + ADR-030 ratification close the loop.

Mitigations​

  • Phase the registry build. Phase B.1 (storage + RDF endpoint + SPARQL) is the smallest viable kernel. Phase B.2 (subscription + conformance) layers on. Phase B.3 (forking + lineage) layers on. Each phase has a stand-alone benefit even if later phases delay.
  • Reuse ADR-037 Phase A scaffolding. TenantSlotPreset is the storage substrate; the registry exposes its rows + lineage as RDF. The 16-preset Phase A.1 starter library becomes the seed for Phase B.5 platform-canonical curation (with the six D8 presets either ALREADY in the Phase A.1 starter or ADDED on Phase B.5 fixture authorship).
  • Bound Threshold-A auto-detection precision. Initial threshold tuning errs toward false-negative (miss real candidates rather than surface spurious ones); registry metrics adjust the threshold as candidate-acceptance-rate stabilizes. Per the decision-log entry, the "minimize triangulation" principle does not mean "eliminate human review."
  • Defer external interop until ADR-030 ratification. Phase B.1 RDF endpoint emits dcterms:conformsTo declarations; ADR-030 + SHACL validation makes those declarations enforceable. The decision-log entry on ADR-030 SHACL prerequisite is the gate.
  • Cross-link forward-references. ADR-037 §"Post-ratification architecture queue" already names ADR-038; ADR-006 §C5 PLACE / TIME_PERIOD deferral notes are updated to point at ADR-039 / ADR-040 once those land.

Compliance​

Foundational principle​

Canonical Structure Is Shared; Interpretation Is Tenant-Specific. This ADR honors the principle at the preset layer: PlatformPresets carry the shared canonical structure (required slots, projection contract, capability activations); TenantPresets carry the tenant-specific interpretation (forks with rationale, additional required slots, refined standards-conformance). The structure layer is platform-canonical and federation-queryable; the interpretation layer is tenant-owned and federation-visible only by tenant choice.

  • ADR-023 (Publication & Persistent Identifiers): preset IRIs use the platform-stable URL scheme; DOI minting on top is an optional ADR-023 amendment, not a requirement.
  • ADR-029 (Projection-First Published Entry Layer): the projection layer consumes preset declarations to emit the public-reader JSON-LD output. Three-surface contract fires through the projection layer.
  • ADR-030 (CIDOC + Linked Art Export Profile Choice): preset complies_with declarations + projection-layer dcterms:conformsTo triples + SHACL validation shapes connect at ADR-030 ratification. Until ADR-030 ratifies, Phase B.1 emits declarations without external-interop guarantees (per the 2026-05-20 SHACL decision-log entry).
  • ADR-035 (Tenant Contributor Permission Model): preset publishing + subscription + forking are operations governed by tenant-admin capabilities. Platform super-admin governs PlatformPreset library curation. ADR-035's stratum / actor / capability provenance applies to every preset write.
  • ADR-037 (Slot-Type Taxonomy and Tenant Vocabulary Layer): this ADR formalizes ADR-037 Phase B. The TenantSlotPreset Phase A.1 scaffold becomes the registry substrate. The complies_with modifier (Phase A.1) is the per-slot hook that aggregates into preset-level declarations.

Autonomous-variation-handling principle (decision-log 2026-05-20)​

Binding constraint on §Decision D7 (Threshold-A auto-promotion) and §Implementation (wizard preset-discovery, complies_with inference). The platform's preset registry MUST reduce manual triangulation as the tenant base grows. Auto-detection produces candidates; humans gate promotion. The principle is "minimize triangulation," not "eliminate human review."

ADR-030 SHACL shape prerequisite (decision-log 2026-05-20)​

Binding constraint on §Implementation Phase B.5 + cross-cutting external-interop work. ADR-030's promotion to Accepted requires (a) a chosen profile, (b) frozen test fixtures, (c) SHACL validation shapes in CI, and (d) external-repository ingestion demonstration. Until ADR-030 ratifies, Phase B.1 — B.4 ship without external-interop SHACL guarantees; Phase B.5 + ADR-030 ratification close the loop.

Open Questions​

These resolve in the formal Phase B.1 backend spec or in companion ADRs:

  1. Preset IRI scheme: https://ke.atlomy.org/presets/<presetId>/v<n> canonical, with optional DOI-minted preset identifiers via ADR-023 layered on top, OR DOI-minted as the canonical form? Recommend canonical platform URL scheme + optional DOI minting for highly-curated PlatformPresets only. Resolved in Phase B.1 spec.
  2. Fork monotonicity on dcterms:conformsTo: can a fork loosen the parent's standards-conformance declarations? Recommend no — forks can only add dcterms:conformsTo, never remove. This preserves the transitivity guarantee for federation queries. Resolved in this ADR via D4; flagged here for visibility.
  3. Preset deprecation: how do presets retire? Lineage chain remains visible; subscribers receive migration prompts; deprecated presets remain queryable for historical-data federation. Resolved in Phase B.3 spec.
  4. Cross-tenant preset publishing: can a tenant publish a TenantPreset that other tenants subscribe to (federation-wide visibility)? Recommend yes, via registry curation gate — tenant-published presets start as TenantPreset with optional federation-visibility flag; Threshold-A promotion to PlatformPreset follows the documented threshold. Resolved in Phase B.4 spec.
  5. Preset visibility scope: public vs tenant-internal vs federation-wide? Recommend: PlatformPresets always public; TenantPresets default federation-wide with tenant-internal opt-in flag. Resolved in Phase B.2 spec.
  6. Capability activation conflicts: what if two subscribed presets activate the same widget with different config? Recommend: explicit preset ordering in tenant config; later subscription wins; surface conflict in tenant admin. Resolved in Phase B.2 spec.
  7. Preset vs TenantSlotPreset collapse: extend ADR-037 Phase A.1's TenantSlotPreset model, or replace it with a unified Preset model carrying a type discriminator? Recommend: unified Preset model — fewer tables, cleaner queryability, single migration path. Resolved in Phase B.1 backend spec.
  8. Threshold-A auto-detection precision threshold: initial value, tuning mechanism, false-positive-rate target. Resolved in Phase B.4 spec; reviewed against registry metrics 90 days after Phase B.4 ships.
