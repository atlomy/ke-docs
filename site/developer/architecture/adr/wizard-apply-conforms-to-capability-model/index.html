ADR-057: Import-Wizard Apply Flow Conforms to the ADR-035 Capability Model — Capability-Gated Terminal Apply + Batched Review

Date: 2026-06-07 Status: Superseded by ADR-035 Amendment 4 (owner-ratified 2026-06-07) — see the model-review outcome below. Do not implement as written; the durable value is the Alternatives section. Deciders: Builder + spec owner (the batched-review redesign direction was endorsed by the owner in-session during the 2026-06-07 escorted import retest; the capability-gating contract and fail-safe semantics here are the engineering realization of that direction)

Parked 2026-06-07 — do not Accept until the model review concludes. On re-examination this ADR is mostly conformance: "the wizard should follow ADR-035" is a bug-fix, not a new architectural decision. Only two things here are genuinely new — (a) the capability × recomputed-tier terminal-apply gate, and (b) the batched "Continue to choices" review UX — and both may collapse if the upcoming review simplifies the permission/apply model. The right structure is likely bug-fix + an ADR-035 amendment (clause a) + a UX spec (clause b), not a standalone ADR. This ADR also has an unresolved dependency (F51 — see Mitigations) and is safety-adjacent (it decides when an apply becomes terminal), so it should not be Accepted on in-session endorsement alone. The durable value to preserve regardless of how it is restructured is the Alternatives section — specifically why not special-case "researcher==admin" (capability flags, not role names) and why not the legacy one-step approve_proposal (it silently drops the risk-recompute-at-apply guard). See the queued "permission/apply model simplification review" arc in roadmap/board.md. Update 2026-06-07: that review's analysis phase is done — docs/developer/architecture/permission-apply-model-simplification-review-2026-06-07.md recommends superseding this ADR: its conformance core becomes a bug-fix (manual low/medium apply terminal for a sole capable actor, mirroring the comfort-dial path) + an ADR-035 amendment + a small UX spec. Pending owner ratification.

Context​

The import wizard applies a reviewer's proposal decisions through Flow B's two-step path (Spec 0011 F2): scholar_approve_proposal moves PROPOSED → SCHOLAR_APPROVED ("Ready for final apply"), then admin_apply_proposal moves SCHOLAR_APPROVED → APPROVED with a risk-recompute gate. Only status=APPROVED proposals materialize (materialization/service.py), so a proposal that is merely scholar-approved does not import.

The wizard hardcodes this two-step as unconditional and per-item: every "Looks good" produces a SCHOLAR_APPROVED row that then needs a separate per-item admin "Final apply." During the first end-to-end retest, a reviewer made 129 "Looks good" decisions and hit a practice-run wall reading "155 choices still need a person / 0 of 10035 rows would import" — because those 129 were parked at SCHOLAR_APPROVED awaiting the second click, and there is no batch-apply affordance (only per-group stage3_restructure_group_apply_view). The reviewer's reaction: "after all the work I did?"

This contradicts the permission model already ratified in ADR-035:

  • §1 — permissions are capability flags on TenantMembership.permissions_jsonb (can_apply_low_risk, can_apply_medium_risk, can_apply_high_risk, …); named roles are bundles. "A contributor with broad capabilities may drive a proposal from PROPOSED → APPROVED end-to-end as a single human, except for sensitivity-tiered safety floors (§4)."
  • §4 — the sensitivity-tiered safety floor is a minimum bar, not a ceiling. For low/medium tier, a single contributor may "auto-apply with undo-bar" — the same as a multi-contributor tenant; no second human is required. High tier requires either a second contributor holding can_apply_high_risk (multi-contributor tenant) or the §4.1 layered floor (single-contributor tenant: sandboxed draft + consolidated diff + blanket-deny prefilter + dynamic phrase + 30s delay). §4 also exposes require_separate_review_authority=true for tenants that deliberately opt medium-tier into dual review.

So the wizard's unconditional per-item two-step is over-confirmation: it imposes dual-review friction that ADR-035 makes conditional on the tenant's contributor population and capability flags — with no compensating safety benefit when the acting reviewer already holds the apply capability for the proposal's risk tier (e.g. a sole researcher who is also the tenant admin gains zero separation-of-duties from confirming their own approval twice). The risk-recompute-at-apply guard (Spec 0011 F0b, in admin_apply_proposal) is genuinely valuable and independent of actor count; the separation-of-duties second click is the part that is vacuous for a single capable actor.

Decision​

The import wizard's apply flow conforms to ADR-035 §1 + §4 rather than hardcoding an unconditional two-actor step. Three clauses:

  1. Capability-gated terminal apply. Whether a reviewer's "Looks good" is terminal (→ APPROVED, with undo) or parked (→ SCHOLAR_APPROVED, awaiting a second human) is decided by the acting user's capability flags measured against the proposal's recomputed risk tier, not by a fixed two-step:

    • The reviewer holds the apply capability for the recomputed tier (can_apply_low_risk / can_apply_medium_risk) and the tenant does not set require_separate_review_authority for that tier → "Looks good" is terminal apply, with the undo bar as the §4 low/medium floor. The apply still runs the Spec 0011 F0b risk-recompute (and RiskClassDivergence acknowledgement) — governance is preserved, only the redundant second human is removed.
    • The proposal recomputes to high tier → it does not terminal-apply on a single click. It routes to the §4 high-tier floor: dual review if the tenant has ≥2 contributors with can_apply_high_risk, otherwise the §4.1 layered floor (sandboxed draft + consolidated diff + blanket-deny prefilter + dynamic phrase). This floor is never bypassed by batch apply.
    • The reviewer lacks the tier's apply capability, or the tenant opts into separate review authority → the two-step is retained (scholar-approve now, a capable second actor applies later).

  2. Batched review at "Continue to choices" (F30 UX). Per-item double-clicking is replaced by group-coded review: confirmed → green collapsed group, skipped → grey, changed → orange; each group stays expandable and individually re-decidable. "Continue to choices" performs the batch apply across all confirmed proposals — routing each through the same capability gate + risk-recompute + tier floor as clause 1. Batching the apply must not drop the governance: it is a batched invocation of the per-proposal apply path, not a status-flip shortcut.

  3. Fail-safe on indeterminate capability. Capability is read from TenantMembership.permissions_jsonb (via _permission_snapshot_for_actor). If that read is empty or indeterminate (no active membership, public schema, missing flags), the flow falls back to the conservative two-step — it never defaults an unknown actor to terminal apply.

This is the import-wizard realization of ADR-035's already-ratified model; it does not change the permission policy. It is distinct from the automatic comfort-dial apply path (stage3_auto_apply_proposals, ADR-033) — that governs unattended low/medium application keyed on the comfort dial; ADR-057 governs the manual "Looks good" review path and the "Continue to choices" batch.

Consequences​

Positive​

  • A single capable reviewer reaches materialize without a second redundant pass — the F41 "you did all that and nothing's ready" wall disappears for the common single-researcher case.
  • Governance that actually matters is preserved: risk-recompute-at-apply, audit trail (admin_applied_by, confirmation_method, permission snapshot), and the high-tier §4 / §4.1 floor all still fire.
  • The wizard now honors require_separate_review_authority and genuine multi-contributor separation instead of forcing dual review on everyone — dual review becomes a deliberate tenant choice, as ADR-035 intended.
  • Batched, group-coded review scales to hundreds of proposals; the per-item grind that produced the wall is gone.

Negative​

  • Collapsing low/medium to a single terminal click widens the blast radius of a mis-click. Mitigated by the undo bar (the §4-blessed low/medium control) and the preserved risk-recompute.
  • Correct behavior now depends on reading capability flags at apply time. If that read is wrong (see F51 below) the gate mis-fires; the fail-safe (clause 3) bounds this to over-conservatism (two-step retained), never to an unauthorized terminal apply.
  • More branching in the apply path (tier × capability × tenant-contributor-count) than a fixed two-step — more states to test.

Mitigations​

  • F51 (permission-snapshot capture) is a sequencing prerequisite. The capability read is the same _permission_snapshot_for_actor mechanism F51 reports as not populating ("No permission snapshot recorded"). Before terminal-apply can gate on it, Codex must confirm whether F51 is a read failure (the function returns {} → genuine prerequisite, fix first) or a persist failure (computed but not stored to the proposal → live gating can read membership independently and the snapshot is audit-only). One of those resolves whether ADR-057 strictly blocks on F51.
  • High-tier §4.1 layered floor must be visibly intact in the batch path — a regression test should prove "Continue to choices" cannot terminal-apply a high-tier proposal.
  • The undo window and group re-decidability must remain reachable after batch apply, so a batched mistake is recoverable.

Alternatives Considered​

  • Route the sole actor through the legacy one-step approve_proposal. Rejected: that path (line 306) flips PROPOSED → APPROVED but never calls recompute_proposal_risk — it would drop the risk-recompute-at-apply guard along with the redundant second human. We want to waive only separation-of-duties, not risk recompute.
  • Keep the unconditional two-step; just add an "apply all approved" button. Rejected as half-measure: it still misclassifies a single capable actor's first decision as non-terminal, still parks everything at SCHOLAR_APPROVED, and still ignores the capability model. It treats the symptom (no batch) not the cause (wrong gate).
  • Auto-apply everything on scholar-approve regardless of capability. Rejected: bypasses the high-tier §4 floor and the require_separate_review_authority opt-in; unsafe for genuinely multi-contributor or high-tier cases.
  • Detect "combined researcher+admin" as a special case. Rejected: ADR-035 §1 is explicit that roles are bundles of capability flags, not tiers; gating on a named role-combination is both less correct (misses custom bundles) and a generalization-guard slip. Gate on capability flags × recomputed tier instead.

Implementation​

  • Decide terminal-vs-parked at the wizard apply boundary from permissions_jsonb capability flags × the proposal's recomputed risk tier × tenant require_separate_review_authority × (for high tier) contributor count.
  • "Continue to choices" iterates confirmed proposals through the per-proposal apply path (capability gate → risk recompute → tier floor), not a bulk status update.
  • Empty/indeterminate capability snapshot → conservative two-step.
  • Sequence after (or jointly with) F51 once Codex determines read-vs-persist failure.
  • What proves it works: a single reviewer holding can_apply_low_risk + can_apply_medium_risk confirms N low/medium proposals and the practice run immediately reports them import-ready (no second pass); a high-tier proposal in the same batch is held at the §4 floor, never terminal-applied by "Continue to choices"; an actor with an empty capability snapshot still gets the two-step.

Compliance​

  • ADR-035 (tenant contributor permission model) — this ADR realizes §1 (capability flags) and §4/§4.1 (sensitivity-tiered floor; single-contributor compensation) in the import-wizard apply surface. Does not change the policy. See the forward-pointer added to ADR-035.
  • ADR-033 (comfort-dial apply pipeline) — distinct surface: ADR-033 governs the automatic comfort-dial path; ADR-057 governs the manual review path and batch. No overlap in trigger.
  • Spec 0011 F0b (risk-recompute-at-apply) — preserved on the collapsed terminal-apply path; the second human is removed, the risk gate is not.
  • Generalization guard — gating is on platform-canonical capability flags and recomputed tier, never on tenant-specific role names or a "researcher==admin" shorthand.
