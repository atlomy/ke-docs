ADR 059: Tenant Lifecycle — Cross-Schema FK Discipline, Schema-First Delete, and Username as the Membership Identity Key

  • Status: Accepted (ratified 2026-06-10 under explicit owner delegation — "Apply and ratify and merge" — after the four-lens adversarial-archaeology review + Round-12 NotebookLM critique round; absorption devlog docs/devlogs/2026_w24/2026-06-11_0030_round12-adr059-ratification-absorption.md)
  • Date: 2026-06-10
  • Deciders: drafted by Claude (Wave-3 A2 lane); platform owner ratifies
  • Context source: 2026-06-10 from-scratch tenant scrub + escorted live-walk findings W47/W48/W50; roadmap/board.md Active item "Tenant lifecycle robustness"
  • Related: ADR-035 (contributor permission model, §3.1 bootstrap member; §4.1 structural compensation for destructive ops), ADR-042 (search_path is the isolation primitive; cross-layer FK warning), ADR-047 (publication-state gate, tombstoned — what delete owes published artifacts), ADR-049 (onboarding initial admin), ADR-051 (tenant-scoped capability membership — Approach A ratified, implementation pending), ADR-052 (per-tenant identity load-bearing), ADR-055 (evidence-gated deferrals must instrument their trigger), ADR-017 §B (platform identity posture — mutable values excluded from identity keys), spec 0020 design §5.1 (TenantSlotPreset.tenant FK rationale)
  • Amended: 2026-06-10 — adversarial-archaeology review (D1 scoped layer-relative; D3 protected-tenant guard implemented, deferral superseded; D4 priced ADR-017 §B exception; Alternatives + falsifiers added); 2026-06-10 evening — dependency-evolution + survivability re-weighing (D1 upstream evidence + un-freeze trigger + substrate-evaluation rubric pointer; D2 upstream confirmation-bug evidence + A7 published-surface survivability guard; D4 fossil-FK lineage clause + attribution coordination pointer; D5 A6 seeded role vocabulary declared); 2026-06-10 night — Round-12 NotebookLM critique absorption (D2 per-schema advisory-lock serialization + backup/restore runbook pointer; acknowledgment-surface audit coverage named + stage-2 capability requirement; D5 provisioning-failure recovery gap declared; A7 erasure-precedence clause + scrub-flow note)

Context​

A 2026-06-10 from-scratch tenant scrub surfaced that the platform has no working operator path to delete a tenant, and that re-creating one requires a manual schema/raw-SQL dance:

  1. Cross-schema CASCADE FK breaks every ORM delete path. TenantSlotPreset (and UngroundedVocabularyValue) are tenant-app models — their tables exist only inside tenant schemas — yet they declare on_delete=CASCADE FKs to the shared customers.Client (atlomyapp/slot_taxonomy/models.py). Deleting a Client from the public schema makes Django's cascade collector query atlomyapp_tenantslotpreset / atlomyapp_ungroundedvocabularyvalue in the public search-path, where those tables do not exist → ProgrammingError: relation … does not exist. This crashes the superadmin admin delete button AND django-tenants' manage.py delete_tenant. The FK itself is deliberate (spec 0020 design §5.1: ADR-035 tenant discipline; platform defaults seeded per tenant; request.tenant-scoped queries; live consumers include the tenantSlotPresets GraphQL resolver, vocabulary-fork tracking, and provisioning get_or_create). Only the never-exercised deletion path is defective: the Python-side CASCADE is redundant by construction — the preset rows live in the schema being dropped, so the schema drop IS the cascade — yet it forces the collector to run a cross-schema query.
  2. auto_drop_schema=False orphans the Postgres schema even where an ORM delete would succeed, with no operator-visible warning.
  3. W47: the scrub re-created the tenant schema + users but never reseeded the public-schema TenantMembership rows — capability gates then denied every tenant user. There was no seeding surface to re-run.
  4. W50: membership identity correlates the tenant-schema request.user against the membership's public-schema auth.User FK by raw integer pk (filter(user=request.user) → user_id = <tenant-schema pk>). It works only when the two auth_user tables happen to assign the same pk — a coincidence that the scrub broke. Other pilot tenants had ZERO membership rows, so the coincidence was never even tested there.
  5. W48 (rider): the dbvisualizer surfaces must tolerate tenants whose schema is missing/half-deleted without crashing.

ADR-051 already ratified the end-state for membership identity (Approach A: relocate TenantMembership into a tenant-local app keyed to the tenant-schema user), but its implementation is pending. This ADR decides the interim, load-bearing contract that the lifecycle tooling builds on today.

Decisions​

D1 — Cross-layer FK discipline: existing FKs become DO_NOTHING; new ones SHOULD NOT be added​

(Amended 2026-06-10: the rule is stated layer-relative — TENANT_APPS → SHARED_APPS — so it survives the ADR-042 rename arc; module paths below are the current/interim housing of the two applied instances, not the rule's terms.)

TENANT_APPS models SHOULD NOT add new FKs to SHARED_APPS models: under ADR-042 the schema is the tenant (search_path is the isolation primitive; django-tenants itself warns against cross-layer FKs), and ADR-051 Approach A drops exactly such an FK as redundant ("the row's schema is the tenant"). The two existing instances keep theirs — TenantSlotPreset.tenant and UngroundedVocabularyValue.client, currently housed in atlomyapp/slot_taxonomy/models.py (interim; their ADR-042 destinations are epistemic.SlotPreset / epistemic.UngroundedVocabularyValue) — and any future cross-layer FK requires a recorded justification. The justification recorded for these two: (a) spec 0020 §5.1 scoping consumers (request.tenant-scoped queries, the tenantSlotPresets GraphQL resolver, vocabulary-fork tracking, provisioning get_or_create), and (b) the DB-level constraint serving as the schema-first ordering guard for D2.

Where a cross-layer FK exists, it MUST declare on_delete=models.DO_NOTHING:

  • Django's cascade collector then skips the relation — no cross-schema query, no ProgrammingError. Cross-layer CASCADE/PROTECT/SET_NULL are wrong by construction: the collector cannot see across schemas.
  • The DB-level FK constraint remains and is useful: it blocks deleting a Client row while its schema (and referencing rows) still exists, forcing the schema-first ordering in D2 — it is what makes the un-shadowable stock delete_tenant and any raw ORM delete fail loudly instead of silently orphaning a schema. Dropping the schema removes the referencing tables, after which the public rows delete cleanly.
  • DO_NOTHING + schema-drop-as-cascade is the only coherent semantics under ADR-042.

Upstream evidence (added 2026-06-10, dependency-evolution re-weighing): the cross-schema-FK/collector defect class is a long-standing, structurally unaddressed django-tenants limitation — on record upstream since 2016 (django-tenants #68: auth in both app lists → cascade ProgrammingError, closed unfixed, with DO_NOTHING already on the reporter's own option list; #149: queryset delete never drops schemas — Context defect 2) — with DO_NOTHING / drop-the-FK as the community's stable answers. This decision was taken against a frontier pin set, not a stale one: as of 2026-06 the platform pins django-tenants 3.10.1 (the latest release, 2026-03-17; nothing in 3.7.0→3.10.1 touches the collector, cross-schema FKs, or auto_drop_schema) and Django 6.0.5 (current stable; the 6.0 deletion collector is unchanged). D1 is alignment with upstream's decade-stable recommended posture, not a local heterodoxy.

Un-freeze trigger: re-evaluate D1 on any django-tenants release whose changelog touches cross-schema FK / collector behavior, or on a schema-library migration (the substrate-evaluation ADR below).

Alternative considered and rejected for now — drop the FK entirely (the lineage's own direction: ADR-051A's "the row's schema is the tenant" argument applies here too): rejected because the DB constraint is the loud refusal that keeps stock/raw deletes from orphaning schemas (Context defect 2). The FK-existence question is owned by whichever lands first: ADR-051 Approach A, or the ADR-042 rename sprint that re-homes slot_taxonomy — revisit there, not here.

A future substrate-evaluation ADR (the schema-library-migration arm of the un-freeze trigger; landscape signal: the django-pgschemas fork) does not invent its rubric: it inherits the preliminary-research five-criteria rubric recorded in cline_docs/techContext.md ("Why Schema-per-Tenant": data isolation, cross-tenant leakage, per-tenant query optimization, backup granularity, compliance/data residency), extended with the needs that have emerged since — path-based routing, the static/dynamic site mix, and schema management under worker-tier concurrency. The comparison covers the authoring/operational side only: the public reader surface is excluded per the published-surface survivability posture (D2 as amended) — its criterion is how cleanly projections leave the substrate entirely (ADR-029's direction), not which tenancy package serves it.

Falsifier: a tenant-app reference that must remain valid after its schema is dropped would invalidate schema-drop-as-cascade and reopen this decision.

D2 — Schema-first, idempotent delete_tenant service is the only delete path​

customers.services.tenant_lifecycle.delete_tenant(schema_name):

  1. Drop the Postgres schema FIRST (DROP SCHEMA IF EXISTS … CASCADE; DDL auto-commits; the drop is the tenant-data cascade).
  2. Then delete the public rows (Client + ORM cascade over shared models: Domain, TenantMembership, audit logs, search profile, credentials, snapshots), atomically.
  3. Idempotent / half-state recovering: schema-already-gone + rows present → deletes rows; rows-already-gone + schema present → drops schema; both gone → no-op success. Each call returns a report of what it found and did.
  4. Refuses the public schema and validates the schema name shape before any DDL.

Error blast radius: the public-row phase is one atomic transaction — abort-on-first-error, nothing half-deleted at the row layer; the schema drop is idempotent and re-runnable. Exposed from all three surfaces: service API, manage.py ke_delete_tenant (requires explicit confirmation; the stock django-tenants command cannot be name-shadowed — INSTALLED_APPS order gives it precedence — but after D1 it fails safely: the DB-level FK refuses while the schema exists; the stock command additionally carries an open upstream confirmation bug — django-tenants #1058, open since 2024-06, the interactive prompt mis-reads the first "yes" — independent support for ruling it non-canonical), and a confirmed superadmin admin action ("Delete tenant — drops schema") that replaces the default ORM delete on ClientAdmin (the default button/action now routes through the service too, so there is no surviving broken path).

The admin bulk action's blast radius is per-tenant continue-on-error: each tenant's delete is independently atomic and independently reported (success or refusal message per tenant); one tenant's failure does not abort the batch.

Published-surface survivability (amended 2026-06-10 — A7): KE commits to public reader surfaces remaining available per minimal-computing standards (ADR-003 "static HTML, versioned" outputs; ADR-029's EntryProjection decoupling) independent of platform operation. Tenant deletion therefore treats published artifacts as a separate protection axis from the pilot relationship (D3's is_protected): when the tenant schema holds PUBLISHED, CURRENT EntryProjection rows, delete_tenant REFUSES with a loud TenantLifecycleError — the same service-level refusal shape as is_protected, checked before any DDL, inherited by all three surfaces — unless the operator explicitly acknowledges unpublish-and-destroy: acknowledge_published_destruction=True on the service, --destroy-published on ke_delete_tenant, the acknowledgment checkbox on the admin confirmation page. The runbooks document export-then-delete as the standard path. Falsifier: if the export-package profile (ADR-029's deferred Datasette/SQLite/DuckDB alternative) ships as the canonical survivability vehicle, the refusal can relax to "exported package exists" (ADR-047/ADR-023 tombstone interplay, now instrumented rather than implied).

Round-12 additions (2026-06-10 night, NotebookLM critique absorption):

  • Concurrency: delete_tenant serializes per schema via a Postgres advisory lock (pg_try_advisory_lock on ke_delete_tenant:<schema>); a concurrent invocation refuses loudly. No schema change (activation-clock cost test: none). Backup/restore of half-deleted tenants is a runbook procedure, not a service concern — see the tenant operations runbook.
  • Acknowledgment-surface audit + authorization: Client (and Domain) are registered with django-auditlog (customers/apps.py), so every is_protected flip and Client deletion already lands in the audit log — the Round-12 critique's "no audit" claim was verified false; this clause NAMES the coverage so it is load-bearing rather than incidental. Authorization differentiation (a dedicated capability for unprotect / destroy-published rather than blanket superadmin) is REQUIRED at the production-simulation milestone (stage 2) — it rides the ADR-051A permission machinery; activating it earlier would build capability-gating ADR-035 Amendment 4 deliberately deferred.
  • Erasure precedence (A7 clarification): the published-surface refusal is an acknowledgment gate, never a denial of a tenant's erasure right. When a tenant requests deletion/erasure, the survivability commitment yields for personal data: the documented path is export-then-delete with the explicit acknowledgment, and the full erasure-vs-persistent-citation reconciliation (forgettable-payload / PII-externalization design) is owned by the WOL/GDPR arc (ADR-046 scope), not this ADR.
  • Automated flows: no import/materialize code path calls delete_tenant (verified) — the A7 refusal cannot deadlock ADR-054 jobs. The operator scrub-reimport procedure documents --destroy-published for scrubbing a tenant with published surfaces.

D3 — auto_drop_schema stays False; schema drops are explicit-surface-only​

Client.auto_drop_schema remains False (django-tenants default). Rationale: auto_drop_schema=True makes ANY ORM delete — including a bulk queryset delete, a cascade from some future shared-model FK, or an admin mishap — drop a pilot tenant's entire schema as a side effect. Dev/throwaway convenience does not justify that on a platform hosting protected pilot data. Instead:

  • All schema drops go through the explicit lifecycle surfaces (D2), which are confirmed (admin action / --yes flag) and logged.
  • Dev/throwaway flows use the same surfaces — manage.py ke_delete_tenant <schema> --yes is one command; there is no residual need for implicit drops.
  • Protected-tenant guard (amended 2026-06-10, adversarial-archaeology review): a Client.is_protected flag (BooleanField, default False) causes delete_tenant to refuse with a loud TenantLifecycleError naming the flag, before any DDL. Clearing the flag is a deliberate superadmin act on the Client record, separate in time and surface from the delete itself — structural compensation per ADR-035 §4.1 (typed/clicked confirmation is a behavioral gate that habituates; genuinely destructive ops need a structural guard), not a second confirmation. The refusal is enforced in the service, so all three surfaces (admin action, ke_delete_tenant, direct API) inherit it; the admin surfaces it as an error message, the command as a CommandError. Operators set the flag on pilot tenants at onboarding (tenant names are per-tenant operational data, not platform code — see the tenant operations runbook). An earlier draft of this clause deferred the guard "until pilot promotion criteria exist"; that deferral is superseded by this guard — it named no observable un-defer trigger, which ADR-055 rules a silent permanent deferral.
  • Activation clock (owner-refined, 2026-06-10 evening): the platform is on a deliberate deployment trajectory — (1) greenfield local dev (wipe/ rebuild by design) → (2) a near-term local production-simulation milestone (local DBs stop being wipeable BY POLICY so all code is exercised as production code) → (3) deployed design partners (stable, continuous, non-wipeable DBs). The activation default along that trajectory is activate-now-by-default: any guard or posture that can be live now WITHOUT blocking local wipe/rebuild or growing the pre-production migration chain activates immediately — deferral is the exception, reserved for exactly those two costs. Concretely: the D3 and D2/A7 refusal CODE is live from this PR (it costs nothing while no tenant is flagged or published); is_protected=True lands on pilot tenants at the production-simulation milestone or deployment onboarding, whichever comes first (the observable trigger ADR-055 requires); the A7 refusal self-activates the moment any tenant publishes. Wiping locally remains one explicit acknowledged step away throughout stage 1.

D4 — Membership↔tenant-user correlation is BY USERNAME (interim until ADR-051 Approach A)​

Decision: match-by-username, not raw pk and not a new identity column.

  • TenantMembership.user keeps its FK to the public-schema auth.User (it is a SHARED model; the FK is schema-local and sound). That public user is an identity anchor only: created with an unusable password, never a login account (logins authenticate tenant-schema users, ADR-049/052). Lineage honesty (added 2026-06-10, early-era staleness re-weighing): the user FK is a NocoDB-era fossil — the TenantMembership chassis was born 2025-12-27 in the FDW commit, under that same commit's explicit "no per-tenant users" assumption, when FK-to-public-user meant FK-to-the-login-human; ADR-049/052 inverted the login model without touching the FK. The dual-auth structure's deliberateness rests on ADR-052's retro-ratification, not on its origin, and the identity-anchor reading here is a priced re-purposing of a dead birth semantics — retired by ADR-051 Approach A, whose implementation priority this raises: the interim stands on a retro-ratification plus a fossil FK. Coordination pointer for ADR-051A: public-surface attribution (created-by lines on published pages) must survive the identity migration.
  • The correlation contract between a tenant-schema request.user and a membership row is username equality, resolved inside the public schema context (membership.user.username == request.user.username). A canonical resolver (customers.services.membership_identity.resolve_membership) replaces every filter(user=request.user) membership lookup; raw-pk matching is retired.
  • Why username over a stable identity key (e.g. a member_username column or UUID): usernames are already unique per auth_user table in both schemas; the proposal-persistence layer already correlates by username (epistemic/services/proposals/persistence.py), so this ratifies existing practice rather than inventing a second mechanism; and ADR-051 Approach A will delete this correlation entirely (membership keyed directly to the tenant-schema user), so adding a new column/key now is schema churn for a structure already scheduled for replacement. A rename collision (renaming a tenant user to capture another's membership) requires tenant-admin authority that already implies full membership control — not a new privilege escalation.
  • Why not pk: pk alignment between two independent sequences is a coincidence (W50); any reseed/scrub order change silently re-points capability grants at the wrong human.
  • Priced exception to the platform identity posture (amended 2026-06-10): username is a mutable key, and ADR-017 §B excludes mutable values from identity keys ("the platform owns identity"; DSN/path were demoted to provenance for exactly this reason). This interim deliberately accepts the divergence, because (a) the failure mode is fail-closed: an orphaned membership denies capabilities — loud to the user — rather than false-matching another human's grants, which is what raw-pk did (silent wrong-authority, ADR-051 Context); and (b) the contract is scheduled for deletion by ADR-051 Approach A. Blast radius of a tenant-user rename: the membership orphans; capability checks deny; the heal is re-running seed_tenant_users, which creates a fresh default-bundle membership — tuned permissions on the orphaned row are not carried over, and the orphaned row must be retired manually. Until ADR-051A lands, tenant-user renames are operationally discouraged; the seeded admin cannot perform them (auth permissions are withheld precisely to protect load-bearing attributes), and de-superusering legacy tenant accounts (ADR-049 invariant) closes the remaining surface. A future reader holding the ADR-017 §B ledger posture should read D4 as a priced, expiring exception — not a violation.

D5 — Seeding is a first-class, idempotent lifecycle surface​

create_tenant + seed_initial_admin service APIs (and the matching management commands / the ADR-049 onboarding wizard, which now delegates to them) cover BOTH halves of tenant identity:

  • the tenant-schema login user (is_staff=True, is_superuser=False LOAD-BEARING, deterministic SHARED_APPS − TENANT_APPS permission scoping — ADR-049 unchanged, relocated into the service);
  • the public-schema membership for that admin's identity-anchor user, with a named capability bundle (DEFAULT_BUNDLES), honoring the bootstrap guards: bootstrap requires can_manage_permissions=True (model guard), at most one bootstrap per tenant (DB constraint — the seeder grants bootstrap only if the tenant has none), and no clear-without-transfer (an existing bootstrap is never cleared or reassigned by seeding; transfers go through transfer_bootstrap_membership only).
  • Per ADR-051 ("the onboarding initial admin becomes the bootstrap member"), the onboarding wizard now grants bootstrap to the initial tenant admin's identity anchor — not to the platform superuser performing the creation. The tenant_creation_user signal path remains for direct Client.objects.create callers that opt into it.
  • Seeding is heal-safe: re-running never clobbers existing membership permissions a researcher/admin has since tuned (create-if-missing semantics) — this is the W47 reseed surface.
  • Rebuildable reader views are part of the heal surface (amended 2026-06-11 — Spec 0046): lifecycle seeding triggers an idempotent rebuild of per-archetype SQL reader views + the tenant compose function when the tenant already has entities. New empty tenants are no-op safe. Operators can run the same repair directly via materialize_per_archetype_views --schema <schema>.
  • Known operator-error surface (documented, not guarded): reseeding with a typo'd username silently creates a second admin membership + identity anchor (create-if-missing keys on the new name — the seeder cannot distinguish a typo from a deliberate second admin). The mis-seeded row is visible in the superadmin membership list and is removed manually; the one-bootstrap-per-tenant DB constraint caps the damage (the typo'd row is never bootstrap when one exists). Likewise, two bootstrap-granting paths coexist (this seeder and the tenant_creation_user signal opt-in) — safe under the same DB uniqueness constraint.
  • Seeded role vocabulary (amended 2026-06-10 — A6): the seeder writes role=TenantMembership.Role.ADMIN alongside the capability bundle. role is a Dec-2025-era second permission vocabulary on the same row, and it is still live-gating: atlomyapp/security.py ranks it through ROLE_ORDER, and the bootstrap-transfer guard (customers/services/bootstrap.py) refuses transfer unless role == ADMIN. It is part of the seeded contract and is declared here; collapsing the two vocabularies (role enum vs permissions_jsonb) is owned by ADR-051 Approach A's relocation, not by this ADR.

Known gap (Round-12, declared): create_tenant mid-provisioning failure (migration crash -> half-provisioned schema) has no automated rollback-or-resume path yet; recovery is the manual scrub via ke_delete_tenant (idempotent, recovers half-states). An automated provisioning-status / resume mechanism is a named follow-up for the lifecycle hardening arc — not a ratification blocker because the manual path is loud, tested, and documented.

Alternatives considered​

  • Drop the cross-layer FKs entirely (D1) — the lineage's own direction (ADR-051A: "the row's schema is the tenant"; ADR-042's cross-layer FK warning). Why not now: the DB-level constraint is the only thing that makes the un-shadowable stock delete_tenant and raw ORM/queryset deletes fail loudly instead of silently orphaning a schema (Context defect 2) — dropping it removes the structural guard that forces D2's ordering. The question is owned by the ADR-042 rename sprint / ADR-051 Approach A, whichever lands first (see D1).
  • Rows-first delete (D2 inverse) — impossible by D1's own design: the DB FK refuses the Client row delete while the schema exists. Of the two reachable half-states, schema-first leaves the loud, recoverable one (registered-but-empty Client row, visible in admin, healed by re-run) rather than the silent one (orphaned schema invisible to every surface).
  • auto_drop_schema=True (D3 inverse) — rejected: it makes ANY ORM delete (bulk queryset, future shared-FK cascade, admin mishap) drop a pilot schema as a side effect; dev convenience is one --yes flag.
  • Raw-pk correlation (D4) — the W50 defect itself: pk alignment between two independent sequences is a coincidence; breaking it silently re-points capability grants at the wrong human (false-match, ADR-051 Context).
  • Store a stable identity key now (D4) — a member_username column or platform-minted UUID per ADR-017 §B — the posture-conformant option. Why not now: ADR-051 Approach A deletes this correlation contract wholesale (memberships keyed directly to the tenant-schema user; "superseded, not migrated"), so a new column/key is schema churn on a structure scheduled for replacement; username adds zero schema and is precisely the correlation data the A-cutover will need. The mutability cost is priced in D4 (fail-closed, rename blast radius declared).

Consequences​

  • Tenant delete/create/seed work from superadmin UI, service API, and CLI; the interim manual procedure in docs/internal/tenants/operations.md is superseded by the canonical commands.
  • delete_tenant refuses tenants whose schema holds CURRENT EntryProjection rows unless published destruction is explicitly acknowledged (D2 as amended, A7); export-then-delete is the documented standard path.
  • New TENANT_APPS → SHARED_APPS FKs SHOULD NOT be added (D1 as amended); reviewers should ask for the recorded justification, and treat any cross-layer on_delete other than DO_NOTHING as a defect.
  • Capability lookups no longer depend on pk coincidence; tenants seeded in any order resolve memberships correctly. ADR-051 Approach A, when built, supersedes D4's correlation contract and removes the identity-anchor users.
  • The platform lifecycle commands are ke_create_tenant / ke_delete_tenant / seed_tenant_users (in customers/). The stock django-tenants create_tenant/delete_tenant remain reachable (command-name precedence follows INSTALLED_APPS order, so they cannot be shadowed) but are non-canonical: stock delete fails safely at the DB FK; stock create seeds no users/membership.
  • Client.delete() (ORM) on a tenant whose schema still exists now fails at the DB layer (FK constraint) instead of crashing in the collector — a loud, correct refusal pointing at the lifecycle service.
