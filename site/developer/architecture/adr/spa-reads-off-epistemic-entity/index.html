ADR-019: V1 SPA reads from EpistemicEntity via per-archetype views

Date: 2026-05-07 Status: Accepted; Phase 1-3 operational, Phase 4 deferred Deciders: Atlomy Account, assistant Related: ADR-002 (Hybrid Ontology), ADR-005 (React Integration Pattern), ADR-006 (Archetype Capability Contracts), ADR-010 (Parser-First / LLM-Second), ADR-011 (Search Engine), ADR-012 (Tenant Config via Runtime Pipeline), ADR-017 (Slot Config as Tenant-Authoritative Manifest), ADR-018 (Retired External Authoring Surface + data_wizard), ADR-029 (Projection-First Published Entry Layer). Supersedes: nothing — closes the gap left open by ADR-018.

Context​

ADR-018 (2026-05-07) retired the external no-code integration and the V1 data_wizard import surface. It explicitly preserved atlomyapp.Job, atlomyapp/management/commands/add_data.py, and the atlomyapp.Lemma / Reference / Model / Page models because the V1 SPA (spa/src/pages/*) still consumes:

SPA endpointView handlerBacking store
/lemma/<slug>/atlomyapp.views.get_LemmaLemma (Postgres) + Elasticsearch detail
/lemmas/get_lemmas_apiLemma (Postgres) + ES facets
/search/search_apiElasticsearch
/auto_fill/autofill_apiElasticsearch
/filters/, /lemmas_filters/filters_api, lemmas_filters_apiES aggregations
/get_show_home_models/, /model/<id>/, /get_details/, /get_model/, /get_model_by_id/views.get_*Model (Postgres)
/get_page_by_id/get_page_by_idPage (Postgres)
/save_feedback/save_feedback_apiFeedback (Postgres)

add_data ingests the atlas Coda CSV bundle into V1 Postgres tables + Elasticsearch indexes; the SPA surfaces depend on both substrates being current.

In parallel, the v2 architecture writes tenant data into EpistemicEntity (one universal hybrid table per tenant; ADR-002) via import_coda_epistemic, import_xlsx, and import_mysql. This is the canonical ingestion path for v2 — but its output is invisible to the V1 SPA today, because the SPA reads the V1 tables that add_data populates from a parallel Coda pull.

The duplication has three cost axes:

  1. Data drift — atlas Coda is fetched twice (once into EpistemicEntity via import_coda_epistemic, once into V1 Lemma via add_data). A field renamed in Coda has to land in both pipelines or one surface goes stale.
  2. Slot-config blindness — V1 Lemma is a fixed-column table. ADR-017 (slot config as tenant-authoritative manifest) doesn't drive what the SPA shows; the SPA renders from V1 columns hardcoded into its component tree.
  3. Tenant-onboarding cost — every new tenant must invent both a v2 archetype shape AND a V1 column-table shape if it wants its lemma-page-equivalent surface to render. Non-atlas validation tenants have v2 substrate; they don't have V1 columnar tables. The V1 SPA is currently effectively atlas-only.

The retirement of the external no-code path closed the duplicate-substrate question on the write side. ADR-019 closes it on the read side: the V1 SPA should consume EpistemicEntity data, projected through the same slot-config / archetype-capability-contract machinery the v2 admin uses.

Decision​

Rewire the V1 SPA's read path to source from EpistemicEntity through a per-archetype Postgres view layer, then retire the V1 Lemma and Job tables. Reference, Model, Page, Feedback retirement is out of scope for ADR-019 — those decisions belong in a separate follow-up ADR after Phase 4 ships.

The mechanism is the existing per-archetype-views machinery (epistemic/services/per_archetype_views.py, Phase-2K.25.3, 2026-05-06): the materializer already generates terms_view, documents_view, entities_view, etc. by reading TenantArchetypeFormConfig and emitting CREATE VIEW … AS SELECT … SQL that projects EpistemicEntity.data JSONB into typed columns. ADR-019 extends that machinery so the views also expose the columns the V1 SPA reads.

Five substrate-level changes:

Principle carried into implementation review (2026-05-10 user correction; resolved by 2026-05-11 ADR-029 amendment below): one non-atlas acceptance case wants public-reader top-level rows to be persons. The principled model is that persons remain ENTITY(Person) and "Entry anchor" is an orthogonal role. They should not be projected/reclassified as TERM merely because a legacy public route treats them as term-like index entries. The person-anchor regression in spec 0004 / Spec 0009 is the acceptance case that forces this decision against ADR-006 archetype semantics.

  1. Extend per-archetype views to include V1-compatible columns. The current materializer projects the slot-config-declared columns. For tenants that need V1-SPA compatibility, a per-tenant manifest declares which V1 columns each view must expose (terms_view.lemma, terms_view.translation, terms_view.short_description, terms_view.long_description, terms_view.transliteration, terms_view.author, terms_view.treatise, terms_view.is_active, terms_view.elastic_id, terms_view.slug). Each V1 column resolves either from a slot-config source_field path (so a Coda source-field rename propagates automatically — see M2), a direct data.… JSONB path, or a deterministic derivation. The view reads slug and elastic_id from EpistemicEntity.provenance (see point 4 below); both are persisted, not reconstructed.

  2. Centralize V1 reads through a LemmaReadService. Today V1 Lemma is read from atlomyapp/views.py, atlomyapp/api/views.py, atlomyapp/mixins/search_api_mixin.py, and atlomyapp/mixins/get_model_api_mixin.py. ADR-019 introduces atlomyapp/services/v1_read_service.py as the only allowed read entry point. Every existing Lemma.objects.… call site is refactored to LemmaReadService.fetch_…(…); the service internally branches on the per-tenant feature flag and reads from either Lemma.objects (legacy) or LemmaView.objects (the unmanaged ORM facade over terms_view). Phase 4's drop is gated on a CI grep that verifies no Lemma.objects reads remain anywhere in the runtime tree.

  3. Preserve V1's stable-pk-prefix URL contract via provenance.legacy_lemma_id + provenance.v1_slug. V1 slugs are generated by add_lemmas as slugify(f"{integer_pk}-{transliteration}") and atlomyapp/views.py:160 splits the slug, extracts the leading integer pk, and looks up Lemma.objects.get(id=lemma_id) — the transliteration suffix is decorative; any <pk>-anything URL resolves to the lemma whose id == <pk>. This is the durable-citation contract that academic papers and external sites rely on. Renaming a transliteration changes the slug stored in the row but does NOT break old citations because the pk prefix still parses out and matches. ADR-019 must preserve this contract verbatim.

    Phase 1 ships a one-shot migration that reads each existing Lemma.{id, slug, elastic_id} and writes them to the corresponding EpistemicEntity.provenance.{legacy_lemma_id, v1_slug, v1_elastic_id} (matched via Lemma.elastic_id ↔ EpistemicEntity provenance pointer or via provenance.legacy_lemma_id if the importer already wrote it). The per-archetype view exposes both slug (from provenance.v1_slug) and legacy_lemma_id (from provenance.legacy_lemma_id) as columns. LemmaReadService.fetch_by_slug(slug) does:

    1. exact-match on the view's slug column
    2. fall back: parse leading integer from slug; lookup by legacy_lemma_id
    3. 404 only if both fail

    For new EpistemicEntity rows created post-migration, the importer generates a clean lemma-derived slug (no integer prefix) and writes legacy_lemma_id = NULL. New rows have no V1 citation history; their slugs are stable as long as lemma_full doesn't change. If lemma_full does change for a new row, a SlugRedirect row records the old → new mapping (separate, much smaller surface than the legacy capture).

    The "split slug to extract integer pk" logic in atlomyapp/views.py:160 moves into LemmaReadService.fetch_by_slug — same behavior, single chokepoint.

  4. Tenant-scope all Elasticsearch indexes. Today atlomyapp.documents.get_legacy_lemma_index_name() returns the shared string lemma_index for reads, while only the document updater switches to f"{tenant}_lemma_index". This was harmless when atlas was the only tenant with V1 ES, but ADR-019 promises tenant generality — any non-atlas tenant enabling the V1 chrome would silently read atlas's index. Phase 3 changes get_legacy_lemma_index_name() to return tenant-scoped names for both reads and writes, and adds a CI guard that fails if any caller resolves an unscoped lemma_index literal. This is the security-critical prerequisite for tenant generality, not an optional cleanup.

  5. Replace add_data's Coda-pull-to-ES with a tenant-scoped V1 ES assembler over EpistemicEntity. Crucially, this is not an extraction of _create_elastic_objects from add_data. The current _create_elastic_objects consumes a "legacy consolidated source object" (Coda CSV bundles consolidated into nested per-lemma dicts with V1-only fields like ancient_words, lemma_full references, etc.); import_coda_epistemic deliberately strips those V1-only fields when projecting to EpistemicEntity. The reindex command therefore needs a fresh epistemic_to_v1_es_assembler.py that walks EpistemicEntity rows for TERM + PASSAGE + DOCUMENT + their EntityRelationship edges and assembles V1-shape ES documents tenant-side. Goal is functional equivalence of search behavior, not byte-equivalence of the document JSON. A reference contract — the actual JSON shape the SPA's search UI consumes today — is dumped from production atlas as the assembler's golden fixture in Phase 3.

After repointing reads (Phase 2) and rebuilding ES (Phase 3), Phase 4 drops atlomyapp_lemma + atlomyapp_job only. The V1 SPA components are unchanged — same JSON shapes out — but the substrate behind every URL changes.

Amendment — 2026-05-10 Operational Status​

Phase 1-3 are now operational for the configured development tenants:

  • public_reader_anchor in the tenant V1-compat manifest is the authoritative row set for public reader/search indexing. reindex_search_from_epistemic ignores the deprecated --archetypes argument and walks that manifest anchor.
  • Tenant-scoped ES indexes are active. Full reindex completed on 2026-05-10:
    • atlomy_atlas: 1185 docs emitted, 2 blank-anchor rows skipped.
    • spreadsheet-import validation tenant: 83 docs emitted, 0 blank-anchor rows skipped.
    • database-import validation tenant: 7608 docs emitted, 8 blank-anchor rows skipped.
  • Existing ES indexes may already have nested mappings. The reindex command now reads existing mappings and only adds missing compatible nested properties; it does not attempt a nested-to-object mapping change.
  • The public reader UI after the React 19 / MUI-reduction work must preserve the V1 reader contract visually as well as structurally: search-result filters, sort tabs, result counts, and index filters remain V1-compatible while using native/custom controls instead of MUI widgets.
  • /search/, /filters/, /lemmas/, /lemmas_filters/, /auto_fill/, lemma pages, and index pages were smoke-tested across the configured development tenants after full reindex and SPA collectstatic.

The principal question remains open and is intentionally not answered by code branching: if a tenant wants public-reader top-level rows to be persons, decide whether public_reader_anchor may point at a non-TERM archetype as a reader role, or whether those person rows should be projected into the term-like public-reader contract. Either path must be expressed through tenant configuration and shared platform projection primitives, not tenant-specific platform code.

Amendment — 2026-05-11 Scope Boundary After ADR-029​

ADR-019 is now understood as a transition-substrate ADR. It proved that legacy reader/search routes could read from EpistemicEntity and preserve the known legacy tenant's URL behavior while V1 surfaces remained in place.

ADR-019 does not define the final public KE architecture. ADR-029 and Spec 0009 move the public runtime contract to versioned Entry projections, GraphQL Entry queries, publish/export snapshots, and transition-oracle tests. V1 REST payloads and V1 Elasticsearch documents may still be sampled to prove migration parity; they must not become the durable public or institutional export contract.

The open person-anchor question is resolved by Spec 0009 / ADR-029 vocabulary: Entry is an orthogonal public role over canonical entities. A person-centric tenant may expose ENTITY(Person) rows as Entries without reclassifying them as TERM, and /lemma/ can remain a route alias for the migrated legacy tenant.

Consequences​

Positive:

  • Single source of truth. A field renamed in Coda lands in one pipeline (import_coda_epistemic → EpistemicEntity) and surfaces immediately on the SPA via the view + ES rebuild.
  • Tenant generality. Non-atlas and future tenants can use the V1 SPA chrome simply by declaring which V1 columns their per-archetype view exposes. No more atlas-only assumption.
  • ADR-017 alignment. Slot config becomes the read-time projection authority. The SPA can be retrofitted to drive its component tree from slot config too — but that's a v2 SPA goal, separate from this ADR.
  • add_data retirement. The legacy Coda-direct ingestion command goes away. Job model can also retire once the new reindex_search_from_epistemic command settles.
  • Ingestion-flow simplification. New tenant onboarding stops needing a parallel V1 Coda pipeline + V1 column-table seeding.

Trade-offs:

  • View vs materialized view performance. Per-archetype views are live (CREATE VIEW, not MATERIALIZED VIEW) — every query re-extracts JSONB. For low-cardinality detail pages (/lemma/<slug>/) this is fine; for high-cardinality list/search endpoints (/lemmas/, /search/) it may add 50–500 ms latency at atlas's TERM cardinality. Mitigations: per-archetype indexes on EpistemicEntity.data JSONB keys (already partially in place), or moving the high-cardinality views to MATERIALIZED with a refresh trigger on import. Decision deferred until benchmarks (see spec 0004 §Tasks).
  • Slug + elastic_id derivation must be deterministic. V1 SPA URLs include /lemma/<slug>/; existing bookmarks must keep resolving. The view's slug column has to derive from the same hash inputs as the V1 Lemma.save() slugify path. Mitigation: a shared helper in atlomyapp/services/v1_compat.py that both the view-SQL emitter and the V1 Lemma.save() (during the bridge period) consume.
  • Elasticsearch index rebuild cost. A full reindex of TERM (~1.2K rows) takes seconds; OK. PASSAGE (~5.9K rows) takes longer but still acceptable in a Celery beat schedule. For larger tenants, incremental reindex per-EpistemicEntity.modified_at is the obvious follow-up.
  • Reference / Model / Page / Feedback are NOT all archetype-shaped. Page and Feedback are tenant-platform models (page content, user feedback), not tenant-data archetypes. They stay in V1 form. The ADR scope is tenant-data surfaces (Lemma, Reference, Model (3D), and the search/autofill/filters that hang off them).
  • Window of dual-substrate. Phase 1 (extend views) and Phase 2 (repoint reads) ship before Phase 3 (retire V1 tables). During that window, a developer might assume Lemma.objects.create(…) is still the way to add a lemma — and the SPA still renders something, because the V1 table is still queryable. Mitigation: deprecation warnings on Lemma.objects.create after Phase 2; explicit retirement-notice docstring on the model; and the LemmaReadService (point 2 above) is the only allowed read entry point so Lemma.objects.… reads can be grep-banned in CI.

Review history​

This ADR was reviewed by Codex on 2026-05-07 (post-initial-draft, pre-implementation). Six findings were absorbed in revision v2:

  • H1 (under-scoped V1 reads) → introduced point 2 of the Decision (LemmaReadService) + Phase 4 grep gate.
  • H2 (ES tenant-shared) → made point 4 of the Decision (tenant-scope all ES) explicit and security-critical.
  • H3 (reindex_search_from_epistemic not a simple extraction) → reframed point 5; the assembler is new code over EpistemicEntity, not a reach-into add_data. Goal is functional, not byte, equivalence.
  • H4 (slug strategy inconsistent) → replaced "approximate slug from id + lemma_full" with "preserve V1's stable-pk-prefix URL contract" (point 3). User correction (post-Codex): the existing system DOES have a citation-stability mechanism — it lives in add_lemmas (which writes slugs as <pk>-<transliteration>) coupled with views.py:160 (which splits the slug, takes only the leading integer pk, and ignores the suffix). Any <pk>-anything URL resolves. Phase 1 captures BOTH legacy_lemma_id and v1_slug into EpistemicEntity.provenance; LemmaReadService.fetch_by_slug preserves the integer-prefix fallback verbatim. The split-pk logic in views.py:160 moves into the service, not deleted.
  • H5 (Reference/Model retirement contradiction) → reduced Phase 4 scope to Lemma + Job only; explicitly defer Reference, Model, Page, Feedback to a follow-up ADR.
  • M2 (from_slot doesn't track renames) → user stories and Decision wording reworded to "source-field rename" so the propagation claim matches the manifest contract.

The remaining medium finding M1 (LemmaView archetype field doesn't match terms_view columns) is fixed in design.md — archetype is dropped from the facade since terms_view is already filtered to TERM rows by construction.

Alternatives considered​

Considered: Direct rewrite of every V1 view handler to query EpistemicEntity without an intermediate Postgres view. Rejected: High edit blast radius (every Lemma.objects.… call site, every related-table join, every search filter) with high risk of subtle behavioral drift. The view layer is a clean SQL contract that V1 view handlers can swap onto with minimal diff.

Considered: Materialize EpistemicEntity → V1 Lemma table via an importer-side hook + keep V1 reads unchanged. Rejected: Two-write architecture. Every EpistemicEntity change has to also write Lemma. ADR-018 explicitly closed the door on dual-substrate writes; ADR-019 must not reopen it.

Considered: Add a v2 GraphQL bridge (lemma_for_v1_spa(...)) and update the V1 SPA to call GraphQL instead of REST. Rejected for Phase 1. Two simultaneous changes (substrate + transport) compound risk. GraphQL is the destination for the v2 SPA (ADR-015 native React shell); ADR-019 keeps the V1 SPA on REST and retires the V1 substrate beneath it.

Considered: Retire the V1 SPA entirely, ship the v2 native React tenant-admin shell as the public-facing surface too. Rejected for now. ADR-015 is in flight (Week 2 micro-app skeleton landed 2026-05-07). The public Entry/KE surface is a separate future-state — public-tenant pages have different requirements (SEO, anonymous access, performance, citation durability) than the admin shell. ADR-019 unblocks Entry Surface work by removing the V1 columnar substrate; ADR-029 and Spec 0009 then define the projection-first public contract.

Implementation​

Sprint plan: docs/superpowers/specs/0004-spa-reads-off-epistemic-entity/. Four phases:

  1. Phase 1: Extend per-archetype views to expose V1-compatible columns. Add per-tenant V1-compat manifest to atlomyapp/import_configs/<tenant>_v1_compat.json. Update the materializer to read it. Benchmark live-view vs materialized-view performance at atlas's TERM + PASSAGE cardinalities.
  2. Phase 2: Repoint V1 view handlers (atlomyapp/views.py) to query the per-archetype views. Use Django unmanaged models for the view tables (db_table = "terms_view", Meta.managed = False). Add deprecation warnings on Lemma.objects.create.
  3. Phase 3: Replace add_data's Coda-pull-to-ES with reindex_search_from_epistemic reading from EpistemicEntity / terms_view. Wire as Celery beat task replacing add_data orchestration. Retire Job.run_combined_commands auto-trigger (already gone post-stage-1; this phase removes the residual Configuration auto-fire path).
  4. Phase 4: Drop V1 column tables only where ADR-019 owns the substrate (atlomyapp_lemma) and retire Job after the reindex path has soaked. Reference, Model, Page, and Feedback retirement stays outside ADR-019 unless a later ADR explicitly scopes them in. Update V1 SPA bundle docs.

Each phase ships independently and is independently revertable. Phase 1 is research + extension (low blast radius). Phase 2 is the high-risk substrate switch and ships behind a per-tenant feature flag (V1_READS_FROM_EPISTEMIC_ENTITY) for staged rollout. Phase 3 is operational. Phase 4 is the cleanup.
