Context​

The v4 import wizard introduces a comfort dial on Stage 3 — a 4-level slider letting the researcher choose how involved they want to be: Hands off / Stay informed / Ask if unsure / Confirm everything. A single control serves first-time researchers and power users without a separate "advanced mode" fork.

The 2026-05-16 architecture pass reframed the dial. Two upstream realizations made the original strawman (level → confidence-threshold) inadequate:

  1. The dial is the routing layer between proposal generation and the apply pipeline. Per ADR-010 (Parser-First, LLM-Second), deterministic parsers generate the highest-trust proposals first — transcription rows, FK detection, lookup-vs-text disambiguation, missed-table discovery. The wizard surfaces these with parser-deterministic confidence. LLM-driven enrichment generates the additional opinionated proposals second — the wizard's distinctive value layer, including canonical archetype shape recognition (promote three flat tables to a canonical EVENT), cross-tenant pattern alignment (this Person/Affiliation/Project trio matches a hub-and-spoke pattern seen in N other tenants), FAIR/discoverability proposals, and slot-config canonical-flag inference. Heuristics also contribute proposals. (The transitional comparison-oracle at epistemic/services/proposals/comparison_oracle.py is a Pipeline-1-to-Pipeline-2 bridge artifact and will retire when Pipeline-1 is decommissioned; long-term, §11 cyclical parser-audit carries the LLM-proposal-validation role.) All proposals flow into the dial; the dial routes them (auto-apply / Stage 3 review card / Stage 4 ambiguity question) based on (a) which source generated the proposal, (b) what class it belongs to, and (c) the researcher's chosen comfort level. AI proposals span a wide class spectrum — from mundane transcription that surfaces what the source already declares, to archetype-canonical proposals the researcher didn't know to ask for.
  2. Tenants import once or a small number of times during onboarding. There is no per-tenant signal accumulation; the wizard's recommendation quality must be excellent on the first import. The algorithm cannot be researchers tuning manually, and per-tenant online learning is undermined by one-shot import volume.

These together rule out a static-threshold-only design and a per-tenant-only recommender. The dial governs a multi-class proposal taxonomy; the underlying recommender is cross-tenant pooled with structurally-informed priors, RLHF-shaped (preference-data fine-tuning the platform-wide prior); calibration is actively generated in three steps, not deferred to telemetry we don't have.

The dial also intersects with ADR-035's contributor permission model. The strawman ADR-033 v1 framing — "stops at SCHOLAR_APPROVED; tenant-admin apply is still required" — assumed a strict scholar/admin separation that v2 never actually enforced. ADR-035 replaces that with contributor permissions + sensitivity-tiered safety floor.

Why parser-surface-structural is a distinct class: per ADR-010 (Parser-First, LLM-Second), deterministic parsers handle structural inference — FK detection, lookup-vs-text disambiguation, missed-tables, inclusion dependency discovery. Modern data-integration literature (ML-FK classifiers, SPIDER-family algorithms, schema-matching benchmarks) places these findings at > 80% F-measure. The wizard's role for this class is to surface parser findings with confidence and provenance, not generate them. They tag with the STRUCTURAL_CERTAINTY reason code (§7) and inherit the low sensitivity tier — they describe the data's actual declared structure, not an opinion about it.

Why archetype-canonical-suggestion is the high-tier wizard-distinctive class: archetype shape recognition, cross-tenant canonical alignment, slot-config flag inference, FAIR/discoverability proposals, vocabulary canonical-term mapping, and provenance graph construction all require knowledge the parser does not have — canonical archetype contracts, cross-tenant patterns, or FAIR-standards normativity. This is the layer where the wizard earns its keep beyond surfacing parser facts. These proposals carry the CANONICAL_PATTERN_MATCH reason code (§7) and never auto-apply regardless of dial level (§2).

Concrete first example from real data (per importer test runs across the three tenants): a tenant uploads three flat sheets — events, participants, locations — each carrying a meeting_id column. The parser surfaces the shared-ID structural facts (the parser-surface-structural class, low-tier, STRUCTURAL_CERTAINTY). The wizard then proposes promoting the three sheets to a canonical EVENT archetype with PARTICIPANTS / DATES / LOCATION slots (the archetype-canonical-suggestion class, high-tier, CANONICAL_PATTERN_MATCH). The two findings reach the dial as two separate proposals at two different tiers. The parser finding routes via the low-tier path; the archetype proposal routes through Stage 3 cards regardless of dial level.

A separate concrete case: tenant uploads a terms sheet with term_en and term_he columns. Parser surfaces the columns as text fields (parser-surface-structural is silent — nothing structural to declare). The wizard proposes setting multilingual=true on the TERM slot config based on the column-name pattern + sample-data signature (archetype-canonical-suggestion class; CANONICAL_PATTERN_MATCH reason code; high tier).

6-class taxonomy calibration-confirmed (2026-05-16): Step 1 prior-art mining (docs/research/2026-05-16_comfort-dial-prior-art/internal-synthesis.md) cross-validated this taxonomy against 20 import config files, 40+ git commits on atlomyapp/import_configs/, Phase-2K devlogs, the long-tail fold audit, and Track H archetype-generality research. Each class has internal-evidence anchors (e.g., transcription via commit 9e6df0c5; parser-surface-structural via c00113b8 / 056f8c14; archetype-canonical via 0ae270d4; missing-content via 7054b6d8). The strongest single anchor — the empty-container-vote fix (docs/decisions/log.md:282-283) — is a real cold-start failure with exact before/after measurement (~90% of atlas TERM.descriptions were empty → slot config dropped the class → recall fell from 115 to 18 hits). Per-class base confidence scores derived from this synthesis populate §5 below.

1.1 Implementation classifier — classify by proposed action, then attach origin/evidence (Codex 2026-05-16 amendment)​

The 6-class taxonomy is named by what proposal class the action belongs to, not by what evidence generated the proposal. This prevents deterministic evidence from accidentally downgrading a destructive operation into a low tier (e.g., parser-deterministic dedup detection does NOT make destructive merge/delete low-tier). The rule: classify by proposed action; attach origin/evidence as a secondary attribute that informs reason-code routing (§7) and the human-affirmation half of the §2.0 gate, not the class itself.

2. Level × class behavior matrix (replaces strawman level-only matrix)​

The dial level interacts with proposal class to determine scope, threshold, and surface. Confidence threshold remains a knob within each class × level cell, but it is no longer the only varying axis.

2.0 Binding two-track auto-apply gate (Codex 2026-05-16 amendment)​

Every cell in the level × class matrix below is subject to a binding eligibility constraint. Auto-apply at any level for any proposal requires both machine confidence and human-affirmation confidence to clear thresholds:

auto_apply_eligible =
  risk_floor_allows_auto_apply
  AND machine_confidence >= threshold
  AND human_affirmation_confidence is known and >= threshold

Narrow exception — source-declared, formally provable low-tier facts: Coda format.type=lookup metadata, MySQL declared FK constraints with clean key/type proof, and equivalent source-declared structural facts treat the source declaration itself as sufficient affirmation. For these, human_affirmation_confidence is effectively asserted by the source schema and the fast path remains.

Parser-verification responsibility (Builder 2026-05-17 amendment, Amendment 1.a): the "clean key/type proof" is a parser-side pre-check, not a documentation phrase. Before granting the narrow exception, the parser must verify (a) the source-declared metadata is preserved in the imported data — e.g., a Coda column declared format.type=lookup still presents as a list of structured row references, not text; a MySQL declared FK still has matching key columns and intact referential integrity; (b) cardinality, type, and link integrity all match the declaration; and (c) any migration-step transformation between source and import did not silently degrade the structure. The Coda lookup→text migration bug is the canonical failure mode this responsibility protects against: a source column declared as lookup that, post-migration, presents as plain text has lost its source-declared structure and no longer qualifies for the narrow exception. If parser-verification fails for any of (a)/(b)/(c), the proposal does not qualify for the narrow exception — it falls back to the standard binding two-track gate and routes to Stage 3 review on null human_affirmation_confidence. The STRUCTURAL_CERTAINTY reason code (§7) is reserved for proposals that pass this end-to-end verification; parser-verification-failed source-declared facts carry a different reason code (e.g., SOURCE_DECLARATION_DEGRADED, or simply route via the same probabilistic path as parser-inferred proposals with appropriate reason-code attribution).

Default behavior for null human_affirmation_confidence: any inferred (non-source-declared) proposal where human-affirmation signal is null — including parser-heuristic structural proposals on unseen schemas — routes to Stage 3 review rather than auto-applying, regardless of how high machine_confidence is. The per-class base scores in §5 are machine-confidence seeds only; the human-affirmation axis must clear before auto-apply on inferred proposals. The matrix cells below describe per-cell behavior once the formula is satisfied; the formula is the binding gate.

3. Authority boundary (replaces strawman)​

The dial governs confidence-based auto-decision, not authority. Authority is governed by ADR-035 contributor permissions + sensitivity-tiered safety floor:

  • A contributor with can_apply_low_risk (default true) can drive transcription / parser-surface-structural / linguistic-fold proposals end-to-end at any dial level.
  • A contributor with can_apply_medium_risk (default true) can drive missing-content-suggestion proposals end-to-end.
  • High-tier proposals (archetype-canonical-suggestion / efficiency-suggestion) never auto-apply regardless of dial level. They require:
    • In multi-contributor tenants: a second contributor with can_apply_high_risk confirms.
    • In single-contributor tenants: the elevated-confirmation gate (typed confirmation + 30s reflection delay + audit-trail emphasis) per ADR-035 §4.

The strawman's "stops at SCHOLAR_APPROVED" line is removed. Flow B is state-driven, not role-driven; ADR-035 makes the contributor model explicit.

4. Recommender architecture: stratified-prior, cross-tenant pooled, RLHF-shaped​

4.1 Recommender shape​

Platform-wide prior (base "model" analog): per-(proposal-class × decomposed-source-shape-stratum) posterior over the confidence threshold that maximizes acceptance without raising undo rate. Stratified by feature decomposition (§4.2), updated by all three preference channels (§4.3). Cross-tenant; never reset.

Per-tenant residual (fine-tune layer analog): small local adjustment from a tenant's onboarding signal, used during their first few imports. Bounded so it cannot dominate the prior when the tenant has only one import worth of data.

4.1.1 Adversarial-resilience layer​

Cross-tenant pooled learning assumes cooperative tenants. A coordinated group feeding skewed feedback — high-volume aggressive accept-everything telemetry from a single high-volume tenant, or coordinated thumbs-down from a colluding subset — can subtly bias the prior for everyone consuming it.

Two candidate defenses, ratified at Sprint B kickoff after first-round telemetry data exists:

  1. Bayesian hierarchical clipping at 2σ (preferred): the prior is modeled hierarchically with per-tenant residuals around a platform-wide mean. A tenant's contribution to the platform mean is clipped if its residual deviates beyond 2σ from the platform-wide prior for that stratum. Allows legitimate edge tenants to push the prior over time (their residual stays well-formed within their stratum) while bounding any single tenant's per-update influence on the platform-wide signal.
  2. Winsorization at 95th percentile (fallback): simpler — cap any single-tenant contribution at the 95th-percentile of per-update magnitude before aggregating. Less principled but cheaper to ship and audit.

Both compose with the existing per-tenant residual bound (§4.1) and the privacy boundary (§6). Drift monitoring (named gap; sub-spec required before Step 3 onboarding) is the operational complement — clipping prevents poisoning at write-time; drift monitoring detects it at read-time across the deployed prior.

The choice between hierarchical clipping and winsorization is ratified at Sprint B kickoff based on what Step 1 mining + Step 2 test-run telemetry reveal about per-tenant residual distributions. Both ship as future-extensible policies on the recommender service surface; the v1 implementation can begin with winsorization and migrate to hierarchical clipping without rewiring the apply pipeline.

Connection to the broader adversarial-LLM threat model: this section addresses one specific attack surface — recommender prior poisoning via cross-tenant feedback aggregation — that complements rather than replaces the per-LLM-call adversarial surfaces (prompt injection, jailbreak, system-prompt leakage, supply-chain compromise) documented in docs/research/2026-05-05_telemetry-compliance-research/03-llm-call-telemetry-security.md. The existing telemetry-security research is OWASP-LLM-Top-10-aligned, covers hash-chain integrity for adversarial-gate replay, and proposes the redact-before-log + quarantine-bucket discipline for confirmed injection payloads (per ADR-016). The recommender-prior-poisoning surface added here is a new attack vector arising specifically from cross-tenant pooled learning — when the next AI Agent Resolver Epic (ADR-014-α) substrate work resumes, the security research should extend to recommender poisoning patterns as a sibling concern. The defenses here (clipping / winsorization) and the defenses there (redact-before-log, hash-chain forensics) compose: telemetry forensics let us detect attack patterns; clipping bounds the per-update influence of any single tenant. The telemetry-security research is a valid sibling reference; it does NOT itself cover recommender-prior poisoning at the depth required, because that threat emerges from cross-tenant feedback aggregation rather than from any single LLM call.

4.1.1.1 Poisoning-specific controls (Codex 2026-05-16 amendment — required before Step 3 onboarding)​

Beyond clipping / winsorization (above), the recommender-prior-poisoning threat model requires the following operator-facing controls before real tenant onboarding (Step 3, §5):

  • Per-tenant update caps — hard limit on per-tenant per-day contribution magnitude to the platform-wide prior. Tenants exceeding the cap have updates queued and pro-rated; the cap is on top of clipping/winsorization, not a replacement for it.
  • Unaffiliated-tenant quorum before stratum contribution — explicit at this layer (mirrors and reinforces the §6 stratum-quarantine rule): a stratum's posterior shifts in response to a feedback batch only if signal from ≥ 3 distinct, distinctly unaffiliated tenants has accumulated in that stratum within the update window. Single-tenant or two-tenant strata never move the platform-wide prior, regardless of signal strength.
  • Sybil / affiliation checks for "distinctly unaffiliated" tenants — tenant-affiliation graph maintained by the platform operator; tenants sharing institutional affiliation, billing entity, or admin user identities count as one tenant for quorum purposes. Required to prevent a single research group from spinning up multiple tenant accounts to inflate quorum.
  • Per-stratum anomaly detection — running per-stratum acceptance-rate / undo-rate / posterior-drift baselines; statistically anomalous batch updates (e.g., a single batch shifting posterior > 2σ from rolling mean) flag for operator review before contributing to the next prior update.
  • Quarantine of suspicious feedback batches — when anomaly detection flags a batch, the batch is moved to a quarantine bucket (parallel to the ADR-016 confirmed-injection quarantine bucket) pending operator triage. Quarantined batches do not contribute to the prior; operators decide release / discard / forensics escalation.
  • Operator-facing incident workflow for prior drift — when a per-stratum posterior drifts beyond a configured tolerance band, an operational incident fires (paging path / dashboard signal). Workflow includes: identify contributing tenants, audit recent batches, decide rollback (pin prior to pre-drift posterior) vs investigate (allow drift but escalate). The incident path is the operator's primary defense when a sophisticated coordinated poisoning attempt evades the per-update controls above.

These controls compose with the privacy boundary (§6) and the §4.3 reason-code anti-anchoring telemetry: privacy bounds what can be poisoned; clipping bounds per-update influence; quorum bounds per-stratum collusion; anomaly detection + incident workflow catch what slips through.

4.2 Decomposed source-shape features (for stratification)​

The recommender stratifies the prior by structural features, not by opaque source-type categorical, so new source types cold-start with non-empty priors. Candidate features (extensible at runtime per ADR-012):

  • is_tabular, is_graph, is_nested
  • has_multi_sheet, has_shared_id_edges, connectivity_topology (flat / star / hub-spoke / web)
  • column_count_bucket, nullability_profile
  • auth_kind (bearer / oauth / dsn-credential-reference / local-file)
  • archetype_mix (e.g., TERM-heavy / PASSAGE-heavy / hybrid)
  • domain_archetype — optional, tenant-admin-configurable (not researcher-facing during onboarding). Free-text or tag-set value capturing a domain hint when one is available. When unset (default), the recommender stratifies on shape features alone — which carry most of the load.

A new source type (REDCap / ARIADNE / etc.) starts wherever its feature decomposition lands in the existing prior — not at zero. Shape-feature stratification handles cold-start gracefully without needing a domain hint.

Why domain_archetype is optional, not required: the platform-wide prior is seeded from humanities/classics/prosopography tenants (Atlas, JPP, visionis), and there's a real risk that humanities-derived priors (which prefer normalization + hub-and-spoke FK resolution) would actively damage a biomedical-longitudinal or geospatial-appendonly tenant's data model. The original draft of this ADR proposed a Stage-1 researcher-declared dropdown to address this. That approach was withdrawn because: (a) adding friction at onboarding violates the "make-or-break first import" design constraint; (b) any fixed enum mis-categorizes — within "humanities" alone, Classics is epistemically very different from music theory or media studies, and the claims/evidence trails differ; (c) tenants from non-registered fields have no good answer; (d) shape features differ between humanities and biomedical naturally (longitudinal time-series tenants have very different connectivity topology, archetype mix, and nullability profile than relational humanities tenants), so the cross-domain bias the dropdown was supposed to fix is partly addressed by shape stratification anyway. The current design keeps domain_archetype as a feature the recommender can use when present, populated via tenant-admin configuration (not import-time researcher input) or future shape-inference logic; absent that signal, the recommender falls back to shape-only stratification. The deeper fix to humanities-prior leakage is at the calibration plan (§5 Step 2 mandates synthetic out-of-distribution probes covering non-humanities shapes) and at Step 3 (real non-humanities tenant onboarding).

Passive behavioral signals to instrument (all aggregate-only; no raw interaction logs cross tenant boundary per §6):

  • Dwell time on Stage 3 match cards — long dwell on a card before deciding indicates friction; the recommender lowers the per-class confidence prior for that proposal shape.
  • Show-me-the-cell → change-this sequence — researcher reveals the source cell, then changes the proposal. Strong implicit negative signal weighted heavily; the prior treats the proposal-shape × decomposed-feature pair as suspect.
  • Reason-code popover open rate (Codex 2026-05-16 polarity correction) — researchers opening "Why this suggestion?" on a class indicates low initial trust for that class; the recommender raises the auto-apply threshold (or lowers the confidence prior) for that proposal class in that stratum. The previous wording — "lowers the auto-apply threshold" — was inverted and is corrected here. High popover rate is a researcher signal that the proposal needs more justification before auto-applying, not less.
  • Fast-accept rate (Builder 2026-05-17 amendment — Amendment 2.a refined) — researchers accepting a proposal substantially faster than their own typical decision time for that proposal class is a conditionally positive signal. The "fast" threshold is self-calibrating per researcher: accepts below the researcher's P25 dwell for the (proposal class × stratum) pair qualify. For cold-start before per-researcher P25 data accumulates (~first 10 cards per researcher per class), a single absolute floor of 5 seconds catches outright rubber-stamps — there is no UX where a researcher reads source-to-destination, recalls column/table semantics, and decides in under 5 seconds. Fast accepts count as positive only when paired with: delayed reason-code reveal (the researcher chose to accept without seeing the reason text), no undo within the 8-second window, no post-apply edit within 7 days, and no later researcher rejection (§11.2). Fast accept without those conditions is treated as anchoring or rubber-stamping rather than genuine confidence and is not credited as positive signal. The earlier "two-second accept rate" framing was miscalibrated for the Stage 3 list-of-cards UX (where realistic decision time is 10-60s per card including optional off-platform DB verification) and is superseded by this self-calibrating signal.

Anti-anchoring telemetry (Codex 2026-05-16 amendment, addressing R3 over-reliance finding) — to detect the failure mode where explanations anchor researchers into rubber-stamping the model's narrative, instrument:

  • Reason-reveal delay per proposal class — time from card render to researcher requesting the reason code; short delays followed by acceptance are a candidate anchoring signal.
  • Accept rate after reveal vs accept rate before reveal per class — if revealing the reason code shifts acceptance up sharply, the reason text is anchoring rather than informing.
  • Undo / post-edit rate after fast accepts — if researchers who accepted within 2s subsequently undo or edit, the fast accept was uncalibrated trust.
  • Repeated fast accepts after probabilistic reason-code exposure — sustained below-P25-dwell accepts (per §4.3 Fast-accept rate) on PROPOSAL_CLASS_PRIOR / LOW_PRIOR_CONFIDENCE / CANONICAL_PATTERN_MATCH proposals after reveal is a strong anchoring signal; the recommender flags the stratum for engineering review.

These behavioral signals fit within the existing privacy boundary (§6) as aggregate outcomes — they roll up at K-anonymity per ADR-016 and carry no raw content. The new instrumentation surfaces in Sprint A and feeds the prior from Sprint B onwards.

The feedback-button text rationale, when filled, remains the highest-value-per-row signal: it tells us which decomposed-feature is missing from the stratification and informs future feature expansion. Low fill rate is expected and acceptable; passive telemetry carries the bulk of the calibration burden.

7. Reason codes — recommendation explainability contract​

Every recommendation surfaced to the researcher must carry a plain-English reason code so they can read AND override it without losing control. Reason-code shape:

{
  "code": "TEMPLATE_MATCH",
  "human_text": "We've seen this format before — looks like the Atlas monthly shape — you've imported it 3 times.",
  "evidence_refs": ["import_template:fp_abc123"],
  "override_action": "use_static_threshold"
}

Mandatory reason-code classes for v1:

  • STRUCTURAL_CERTAINTY — proposal derives from parser-deterministic findings (FK detection, type compatibility, key uniqueness, declared schema metadata). Distinguishes hard parser extractions from LLM-or-recommender-derived suggestions. Human text shape: "The source data strictly declares this." Carried by every proposal in the transcription and parser-surface-structural classes; carried by linguistic-fold proposals where the multilingual flag is declared rather than inferred. Researchers see this code and trust the proposal as mathematical fact about their source, not opinion.
  • TEMPLATE_MATCH — fingerprint matches a prior ImportTemplate.
  • CANONICAL_PATTERN_MATCH — proposal derives from a canonical archetype pattern aligned across the cross-tenant prior. Carried by archetype-canonical-suggestion proposals (shape recognition, cross-tenant alignment, slot-config flag inference, FAIR/discoverability proposals, vocabulary canonical-term mapping, provenance graph construction). Human text shape: "We've seen this shape in N other research databases — promoting to the canonical EVENT archetype would let you query / discover / cite it the same way they do." Researchers see this code and understand the proposal is opinion derived from cross-tenant pattern, not parser fact.
  • PROPOSAL_CLASS_PRIOR — recommendation derives from accumulated outcomes for this proposal class on tenants with similar shape. Used for missing-content-suggestion proposals and for archetype-canonical proposals where no clean canonical pattern matched but per-class prior favors surfacing.
  • RISK_CLASS_FLOOR — recommendation reflects sensitivity-tier safety floor per ADR-035.
  • LOW_PRIOR_CONFIDENCE — this is a novel shape; recommendation is conservative because the prior is weak.
  • REJECTED_BY_RESEARCHER (Codex 2026-05-16 amendment) — engineering-facing initially; emitted when a researcher rejects a proposal through any channel (Stage 3 reject, undo within the 8-second window, feedback-button "this is wrong", or post-apply edit within 7 days). Pairs with §11.2's researcher-rejection feedback loop. Not surfaced in the researcher-facing reason-chip set in v1; used by the recommender to recalibrate per-stratum priors and by engineering to detect stratum-wide trust regressions. Becomes a user-facing audit-trail code in v1.1 once the audit panel ships.
  • SUPERSEDED_BY_RESTRUCTURE (Spec 0025 ER-19 2026-05-27 amendment) — engineering-facing; emitted when a COLUMN/ARCHETYPE/RELATION proposal is automatically transitioned to REJECTED in the same transaction as an approved RESTRUCTURE proposal that superseded it (per Spec 0025 ER-19 Q5 cascade modal "Replace" action). Critically distinct from REJECTED_BY_RESEARCHER: the researcher did NOT reject the superseded proposal; the system superseded it as a structural consequence of the researcher accepting a higher-fidelity alternative (e.g., approving a LOOKUP_AS_PICKER RESTRUCTURE supersedes the flat-text COLUMN proposal for the same source column). Conflating the two codes would inject false negatives into the recommender's per-stratum prior for the superseded class (typically COLUMN), biasing it against value-overlap-based proposals across the platform. The §11.2 feedback loop treats SUPERSEDED_BY_RESTRUCTURE as a NEUTRAL signal on the superseded class's stratum (no positive or negative weight) while crediting the RESTRUCTURE's stratum with a positive accept signal. Audit-trail consumers can reconstruct "this column was mapped as a picker because the researcher approved a RESTRUCTURE on $DATE; the original flat-text proposal at $ID was superseded, not rejected on its merits."

Implementation note (2026-05-20): Spec 0018 implemented the persistent reason-code and DecisionEvent substrate for the §11.2 researcher-rejection loop. The shipped v1 channel covers explicit reject, 8-second undo, post-apply-edit classification, and Stage 3 inline feedback-button signals with bounded metadata. Tenant-admin and platform-admin views expose the resulting audit, telemetry, recommender, and operator-timeline surfaces without exposing raw tenant payloads.

Note on parser_audit_passed: this is evidence metadata attached to LLM proposals that survived the §11 cyclical parser-audit, not a user-facing reason code. It rides on the proposal payload as an evidence flag that the recommender and audit log can consume; the researcher-facing chip stays with CANONICAL_PATTERN_MATCH / PROPOSAL_CLASS_PRIOR per the proposal's actual epistemic class.

  • Efficiency-suggestion proposals → PROPOSAL_CLASS_PRIOR + RISK_CLASS_FLOOR for sensitivity emphasis.

  • A "Why this suggestion?" affordance on the dial (popover with human_text).
  • A muted reason chip on Stage 3 match cards (when the system chose to auto-apply at this level).
  • The "Recommended for your data" pill on the dial position when a strong prior exists.

  • Text rationale (when opt-in): ≤ 90 days; per-tenant KMS at rest; scrubbed for any tenant-content patterns at write time.
  • Stage 4 abstracted answers: medium retention (≤ 1 year) at abstracted form; raw answers stay tenant-local with normal Flow B retention.
  • All data subject to ADR-016 append-only + per-tenant KMS + audit-verification posture.

9. Evaluation metrics — does the recommender actually help?​

Step 2 / Step 3 evaluation tracks:

  • Median time-to-import (researcher wall-clock from Stage 1 to Stage 6 commit). Target: lower over time within a stratum as the prior matures.
  • Proposal acceptance rate (auto-applied proposals that don't get undone within the 8s window or in subsequent tenant-admin edits within 7 days). Target: ≥ 0.95 at the recommender-derived threshold for each class.
  • Researcher-decision count per import (Stage 3 + Stage 4 explicit decisions). Target: lower over time at fixed dial level.
  • Stage 4 question count (ambiguous-routed proposals). Target: lower over time as the prior reduces ambiguity.
  • Undo rate per dial level per class. Target: floor (below which the recommendation is too aggressive); should converge.
  • Qualitative researcher satisfaction (post-Stage-6 prompt + feedback button + Step 3 interviews). Target: positive trend across onboardings.

A recommender shipping is not evidence of value. Shipping + producing convergent acceptance and undo curves across ≥ 3 tenants is.

10. Per-tenant defaults + system-recommended-position​

  • New field: Tenant.default_comfort_level (IntegerField, 0–3, default 1).
  • Per-import override: MappingProject.comfort_level (IntegerField, nullable; null = "use tenant default").
  • The physical dial position is always strictly researcher-explicit. The slider never moves on its own. The recommender surfaces a "Recommended for your data" advisory pill (or a ghost marker on the level the prior suggests) as overlay only. The researcher must proactively drag the slider to the recommended position to accept the recommendation. The state-machine UI guarantees: physical slider position changes only on researcher drag events; the system never auto-relocates the dial. This preserves the steering-wheel intuition — the slider position is what the researcher chose, full stop. The recommendation is information; the position is intent.

When the prior is strong for a tenant's incoming shape (≥ N similar imports seen), the advisory pill renders next to the recommended level. When the prior is weak, no pill renders and the static default (Stay informed) governs the initial slider position.

11. Cyclical parser-audit of LLM-generated proposals​

Parser-first / LLM-second (ADR-010) is one-way as filed: parser extracts evidence; LLM proposes against that evidence; human approves. The wizard's apply pipeline extends this to a cyclical pattern: parser extracts → LLM proposes → parser audits the LLM proposal against deterministic checks before routing to Stage 3 cards.

Without the audit, LLM-generated archetype-canonical proposals (and missing-content / efficiency proposals) can reach Stage 3 with apparent confidence even when database mathematics make the proposal structurally impossible — set intersection of two columns is empty, cardinality is incompatible with the proposed FK direction, key uniqueness is violated by sample data, type compatibility fails. These hallucinations degrade trust and waste researcher attention.

The post-LLM parser audit runs deterministic checks:

  • Set intersection between candidate join columns must be non-empty above a configurable floor.
  • Cardinality must be compatible with the proposed relationship direction (one-to-many candidate columns must not have many-to-many sample data).
  • Type compatibility must hold (proposed FK target column type must match the candidate source column type after declared coercions).
  • Key uniqueness must hold on the target side of any proposed FK.
  • Sample-data sanity must hold (proposed canonical archetype slots must be populatable from the source data without all-null columns). For multilingual columns or script-detected slots, the audit uses language-aware sampling rather than uniform random — reusing detect_dominant_script from epistemic/services/language_detection/detection.py to establish baseline script from a first-pass sample, then targeting additional samples from rows outside the baseline. For returning imports where TenantArchetypeFormConfig.script exists for the related slot, the audit compares newly-detected script against the persisted value and flags significant disagreement as suspect. Implementation detail in Spec 0017 tasks.md §B.6 (Builder 2026-05-17 refinement).

LLM proposals that fail the audit are killed before reaching Stage 3. A new telemetry reason code REJECTED_BY_PARSER records the kill with the LLM's original framing. The reason code is never shown to the researcher; it exists for engineering to refine LLM enrichment prompts over time.

LLM proposals that pass the audit can claim higher certainty than raw LLM output because the parser has confirmed the structural mathematics. This composes with STRUCTURAL_CERTAINTY (§7) — parser-audited LLM proposals may carry both CANONICAL_PATTERN_MATCH (canonical archetype alignment) and a parser-audit-passed flag in their evidence payload.

This cyclical pattern is an extension of ADR-010's parser-first/LLM-second discipline, not a replacement. The parser remains the source of structural truth; the LLM remains the source of semantic enrichment; the parser is now also the validator of LLM enrichment before human review.

11.2 Cyclical researcher-rejection feedback loop (Codex 2026-05-16 amendment)​

Parallel to §11's cyclical parser-audit-of-LLM, the apply pipeline runs a cyclical researcher-rejection feedback loop. Every researcher rejection — Stage 3 explicit reject, undo within the 8-second window, post-apply edit within 7 days, or feedback-button = wrong — emits the REJECTED_BY_RESEARCHER reason code (§7) and feeds the recommender's per-stratum coverage estimate.

The auto-apply gate (§2.0) re-evaluates per-stratum coverage on every rejection batch update:

  • Stratum-wide rejection-rate threshold: when the rolling rejection rate in stratum S exceeds a configured ceiling (initial v1 default: 15% per-stratum per-class over the trailing 100 decisions, calibrated from Step 2), the auto-apply gate stops auto-applying in S for the affected proposal class until researcher signal recovers below the floor.
  • Per-proposal-shape suspect flagging: a specific proposal shape (decomposed-feature × proposal-class fingerprint) that accumulates REJECTED_BY_RESEARCHER signal at > 2× the stratum baseline is flagged suspect; the recommender treats it as LOW_PRIOR_CONFIDENCE regardless of the underlying machine confidence score until the rejection rate normalizes.
  • Operator escalation: stratum-wide rejection-rate spikes (e.g., a stratum jumping from 5% to 30% rejection in a 24-hour window) fire the same operator-incident workflow as §4.1.1.1 prior drift. The cause is often coincident — both surface "the prior shifted in a way the researchers don't trust."

This loop is the user-signal equivalent of the parser-audit loop: parser audit catches structurally impossible LLM proposals before researcher review; researcher-rejection feedback catches structurally plausible but semantically wrong proposals after researcher review. Together they form the two halves of the §2.0 binding gate's human_affirmation_confidence axis — parser-audit-passed proposals carry one half of the affirmation signal; researcher-non-rejection across the stratum carries the other half. Without the §11.2 loop, the wizard would learn from acceptance signal only and quietly accumulate trust regressions invisible to the apply pipeline. The empty-container-vote pattern (docs/decisions/log.md:282-283) is the canonical motivating example for why this loop is mandatory: machine evidence was self-consistent while researcher experience broke catastrophically.

11.2.1 Feedback-button as inline Stage 3 affordance (Builder 2026-05-17 amendment — deferral REVERSED)​

Earlier framing (REVERSED): a 2026-05-17 amendment deferred the feedback-button = wrong signal source on the rationale that "researchers fix things in-place; they don't revisit-and-rate." Subsequent parallel-fire R3 absorption added compensation amendments (auto-undefer triggers + dwell-and-scroll-past implicit signal) to plug the gap left by the deferral.

Why reversed (Builder 2026-05-17 after both absorptions): the rationalization conflated "feedback button" with "revisit-and-rate workflow." That's not the only shape the affordance can take. An inline Stage 3 affordance — captured at decision time, alongside the existing "looks good" / "change this" buttons (Spec 0017 B.1.3) — neither requires a revisit nor a separate UI surface. Implementation cost (~2.75h for US-B.5) is small compared to the compensation amendments (auto-undefer mechanism + onboarding micro-survey + implicit-positive dwell signal) that the deferral required. Net cost of "ship all 4 signals upfront" is negative.

Decision: the feedback-button signal source ships inline at Stage 3 in v1 as part of the existing match-card affordance set. Researcher clicks "change this" → small "tell us why" textarea opens optionally (researcher can dismiss and proceed; or fill in a short reason). Researcher clicks "looks good" → no extra prompt. Captures qualitative ground truth at decision time, fill rate not bound by revisit-and-rate behavior. Implementation: Spec 0018 US-B.5 status changes from DEFERRED → ACTIVE; restore +2.75h to Sprint B budget. Spec 0017 B.1.3 match-card component AC amended to include the inline affordance.

Calibration insight (Builder 2026-05-17) — recorded as durable methodology guidance: don't pre-pay for production-discipline patterns under greenfield/internal-team-only conditions. The deferral was rationalized by a "researchers don't revisit-and-rate" argument that only holds if the feedback button = revisit-and-rate workflow. By assuming that frame, the deferral added more compensation complexity than it saved. The discipline: when an architectural amendment proposes deferring a load-bearing primitive, check whether the deferral creates compensation work elsewhere; if yes, ship the primitive upfront.

The defense-in-depth signals (§11.2.2 + §11.2.3) remain valuable even with the active button restored. §11.2.2 distinguishes post-edit rejections vs refinements (useful for silent-correction signals where the researcher didn't click the explicit button). §11.2.3 implicit-positive dwell signal is removed in this reversal (the explicit "looks good" click IS the positive ground-truth signal — implicit dwell becomes redundant compensation).

11.2.2 Post-edit signal classification (R3 absorption 2026-05-17 — A1)​

The 7-day post-apply edit signal is inherently ambiguous: a researcher editing a previously-applied mapping within 7 days could be (a) genuinely rejecting the original proposal as wrong, or (b) refining a correct baseline with new information they didn't have at apply time (e.g., a new primary source, a domain-expert correction, a downstream clean-up pass). Without classification, the §11.2 cyclical feedback loop conflates these two intents and biases the recommender prior toward over-corrected per-stratum thresholds.

v1 classification heuristic (Sprint B emission wiring):

  • Edit-as-rejection: the edit reverts the auto-applied mapping target (FK pointer, archetype assignment, slot value) entirely — researcher chose a different target. Counts as REJECTED_BY_RESEARCHER with full weight in §11.2 rejection-rate threshold.
  • Edit-as-refinement: the edit augments the auto-applied mapping (adds a related entity, fills a previously-null slot, narrows a translation) without reverting the original target. Counts as a softer signal — MODIFIED_BY_RESEARCHER (engineering-only telemetry code) — and does NOT contribute to the §11.2 rolling rejection-rate threshold. May contribute to recommender feature-set updates as a "researcher saw value in the proposal but wanted more" signal.

The classification fires programmatically at edit-event time: compare MappingProposal.applied_payload snapshot vs the post-edit state. If the original target/mapping is intact → refinement; if it's been replaced → rejection.

Open question for Step 2 calibration: does the refinement-vs-rejection split also need a per-tenant weighting? Some tenant workflows may default to additive refinement (Atlas lemma editors); others may default to outright replacement (Visionis archaeology cataloguing). Tracked as Spec 0018 Sprint B emission-wiring open question.

11.2.3 (Removed 2026-05-17) — Implicit-positive dwell-and-scroll-past signal​

This subsection was added in the R3 absorption as compensation for the §11.2.1 feedback-button deferral. With the deferral reversed (§11.2.1 now ships the feedback button as an inline Stage 3 affordance from v1), the explicit "looks good" click is the canonical positive-ground-truth signal. An implicit dwell-and-scroll-past signal becomes redundant compensation that adds telemetry surface without proportionate signal value.

Removed: no implicit-positive dwell signal in v1. The §11.2 calibration channel uses explicit researcher actions only: Stage 3/4 reject, 8s undo, 7d post-edit classification, and Stage 3 inline feedback. The Stage 3 "change this" affordance emits a negative feedback_button DecisionEvent with bounded metadata; optional free text remains tenant-local proposal memory and does not enter telemetry. The "looks good" action remains on the existing approve/apply transition trail until a separate positive-transition DecisionEvent contract is accepted.

Reconsider only if: post-launch data shows the four signal sources still fail to converge per-stratum at v1 scale — at which point implicit signals (dwell, attention-time, scroll-velocity) become candidates for re-introduction as additional layers. Not load-bearing for v1 launch.

The Spec 0011 F0b-risk-recompute-at-apply guard remains authoritative. If a proposal recomputes from low to medium (or higher) before apply, the level × class matrix in §2 falls back to the higher tier's auto-apply rules regardless of original auto-apply intent. The dial cannot override the recompute guard.

13. Audit trail​

Every comfort-dial-driven apply records:

  • confirmation_method = comfort_dial_level_N (where N ∈ {0,1,2}) per ADR-035.
  • applied_by_permission_level snapshot per ADR-035.
  • recommendation_reason_code (from §7) when the apply was driven by a recommendation.
  • The undo-bar message reads "We turned on X for you" with X bound to the affected proposal subtree's plain-English summary.

Alternatives considered​

  1. Single confidence slider (current state). Reuses existing _apply_threshold. Rejected: same UX as today; doesn't deliver the v4 design's "Hands off" / "Confirm everything" affordance.
  2. Per-archetype confidence dials. Rejected: researchers don't think per-archetype.
  3. Skip the comfort dial; ship Stage 3 with static thresholds. Rejected: the dial is the most distinctive v4 UX innovation.
  4. Static thresholds for v1, recommender later. Retained as cold-start fallback only (§5). Not the chosen posture because Step 1 mining + Step 2 self-test together populate viable seed data before Sprint B; the recommender architecture itself ships with the apply pipeline.
  5. Per-tenant online learning recommender. Rejected: tenants import once during onboarding; per-tenant signal accumulation is too sparse. Cross-tenant pooled learning is the only viable shape.
  6. Cross-tenant pooled learning deferred to a separate privacy ADR. Rejected: the privacy boundary (§6) is bounded and can be specified inside this ADR. Spawning a separate privacy ADR delays Sprint B without adding clarity.
  7. Reason codes optional. Rejected: the recommender is advisory by design; researchers must understand and override every recommendation. Reason codes are mandatory.

Consequences​

Positive​

  • Single import-wizard flow serves first-time + power users without forking.
  • The recommender becomes the substrate that makes "first import is make-or-break" survivable — new tenants benefit from accumulated cross-tenant wisdom from day one.
  • The proposal class taxonomy lets the system surface canonical-shape proposals the researcher didn't know to ask for — promoting flat tables to canonical archetypes (EVENT, DOCUMENT, ATTESTATION), aligning slot configs with cross-tenant patterns, materializing FAIR-compatible discoverability edges. These are the wizard's distinctive value beyond surfacing what parsers already find.
  • The architecture composes cleanly with ADR-035 (contributor permissions) and ADR-016 (telemetry primitives).
  • The 3-step calibration plan turns the "we lack data" complaint into "we generate data deliberately."

Negative​

  • F0b apply-pipeline refactor is the most architecturally invasive task in Sprint B. Touches data_import/services/apply_proposal.py. Possible overlap with Codex's spec-0011/flowb-risk-apply worktree — coordinate before Sprint B.2.2 starts.
  • Recommender introduces a real algorithm surface (stratified-prior + RLHF-shaped update). Needs monitoring + drift detection in production.
  • Privacy boundary matrix (§6) introduces operational complexity: per-class consent flags + redaction discipline must be honored at write time, not retrofit at read time.

Risk​

  • Recommender drift: with cross-tenant pooled learning, a high-volume tenant could dominate the prior. Mitigation: weighted updates that floor per-tenant contribution; periodic offline review of prior posteriors.
  • Reason-code shallowness: if reason codes degenerate to template-shaped explanations, researchers stop reading them. Mitigation: Step 2 / Step 3 evaluation tracks researcher-override rate as a proxy for reason-code utility.
  • Cold-start mis-stratification: a brand-new source type's feature decomposition may land in a stratum where the prior is misleading. Mitigation: the recommender reports LOW_PRIOR_CONFIDENCE reason code when the matched stratum has < N similar prior imports; defaults to the static-threshold fallback in that case.

  2. Feedback button text rationale pooling — opt-in pool with redaction is in §6; should we instead never pool text and rely entirely on quantitative signals?
