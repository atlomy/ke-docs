ADR-013: Unify Tenant A Lemma → EpistemicEntity

Status: Deferred — placeholder Date proposed: 2026-04-30 (referenced as planned in state.md and roadmap board from this date forward) Date this placeholder authored: 2026-05-06 Deciders: To be assigned when the unification session is scheduled Related: ADR-002 (Hybrid Ontology), ADR-004 (Tenant Ontology Mapping), ADR-006 (Archetype Capability Contracts), ADR-009 (Platform-Native Entity Conventions), ADR-012 (Tenant Config via Runtime Pipeline) Trigger to activate: Tenant A migration off legacy Lemma table is scheduled

Why this placeholder exists​

Multiple documents reference ADR-013 as the locus for the Tenant A Lemma → EpistemicEntity unification decision:

  • roadmap/board.md (Ready queue): "ADR-013 + Session — Unify Tenant A Lemma → EpistemicEntity: needs ADR deciding URL stability, FK preservation, rollout sequence. Multi-session (1–2 weeks). Pre-session debt in state.md."
  • docs/context/partner_model.md 2026-05-03 calibration: ADR-013 cited as the open-question for Tenant A unification.
  • docs/devlogs/2026_w18/2026-05-01_*.md and docs/devlogs/2026_w19/2026-05-05_1153_round-8-absorption.md reference it as planned future work.
  • docs/research/2026-05-01_search-engine-comparison/*.md reference it as the migration that determines whether ATLOMY's existing Lemma indexer keeps working post-unification.

Until this placeholder existed, those references were dangling — nothing at docs/developer/architecture/adr/013-*.md. The doc-staleness lint (scripts/atlas/check_doc_staleness.py, F7) surfaced 32 broken ADR-013/ADR-014 references on 2026-05-06.

This file resolves the references and pins what is currently known. It deliberately does NOT make architectural decisions on the user's behalf — those land when the unification session is convened.

Status: Deferred (intentional)​

The unification work is real but not yet timed:

  1. The Tenant A Lemma model still backs the v1 ATLOMY corpus + the existing Elasticsearch index + the SPA /lemma/<id>/ URL. Live researcher traffic depends on those URL shapes.
  2. The post-Round-9 implementation overnight (2026-05-05 → 2026-05-06) restored Tenant A TERM via the Phase-2K.26 Coda-flat path: 1,189 v2-native TERM rows now sit alongside the legacy Lemma rows. Both surfaces work today.
  3. ADR-006 + ADR-012 + the slot-config substrate (Phase-2K.1 → 2K.8 + 2K.26) are the runtime ingredients the unification will use. Those landed on 2026-05-04 and 2026-05-05.
  4. The remaining open questions are operational, not architectural-paradigm: URL preservation policy, FK migration staging, dual-read/dual-write windows, deprecation timeline.

What the unification session must decide​

(Not decided here. Listed so the session can pick up cold.)

  1. URL stability: Do Tenant A's /lemma/<int>/ URLs (linked from external academic citations) remain canonical post-unification, or do they redirect to a new EpistemicEntity URL form? If redirect, what's the policy for 301 vs 302, and what's the deprecation horizon?
  2. FK preservation: How do existing FKs (TextLine, BodyPart, lemma-translations, lemma-references — all currently pointing at Lemma.id) migrate? Options: (a) keep Lemma rows as a thin shim pointing to the unified EpistemicEntity; (b) rewrite all FKs in a single migration; (c) dual-read window with a sync table.
  3. Rollout sequence: parser changes first or schema changes first? V1 Elasticsearch keeps working until when?
  4. Search index policy: Does the V1 ATLOMY ES index get re-seeded against the unified corpus, or does V2 PG-FTS / OpenSearch take over Tenant A's search surface entirely (per ADR-011's retreat target)?
  5. Read-side legacy path: how long does AtlasLemmaIndexer (the V1 → ES bridge) remain wired? The 2K.7 V1-vs-V2 benchmark assumed it stays; this ADR may mark its sunset.

Consequences (when the decision lands)​

Positive (anticipated):

  • Single conceptual model for academic terms across tenants. Today Tenant A has both Lemma and EpistemicEntity rows for what is essentially the same entity; unification removes that bifurcation.
  • The capability-flag substrate (ADR-006) becomes the only authoring surface; researchers stop seeing two related-but-different schemas.
  • The slot-config consistency lint (Phase-2K.6 dev-infra) covers Tenant A the same way it covers Tenant B and Tenant C.

Negative (anticipated):

  • Migration surface area is large (TextLine, BodyPart, references, translations all link to Lemma).
  • External academic citations may break if URL strategy is aggressive.
  • Indexing costs paid twice during the dual-read window.

Mitigations (to be designed in the session):

  • Schema-level checks (FK count audits before and after migration).
  • Telemetry-substrate signals (ADR-016) for ES vs PG-FTS query volume during cutover.
  • Dual-read tested under load on a staging tenant before Tenant A flip.

Alternatives currently in play​

  • Status quo (do nothing): the bifurcation persists; researcher confusion compounds; Tenant A becomes a special case in every cross-tenant feature.
  • Soft unification (keep Lemma as a model but project it through the EpistemicEntity GraphQL contract): partial benefit, defers the FK migration cost. Probably what the session lands on for v1.
  • Hard unification (drop Lemma, rewrite all FKs in one window): cleanest end-state, highest migration risk.

Pre-session debt​

Listed in state.md under various dates 2026-04-30 through 2026-05-05; consolidate into a unification-session brief when convened.

When this ADR moves out of "Deferred — placeholder"​

This file becomes a real ADR-013 when:

  1. The unification session is convened.
  2. URL-stability policy is decided.
  3. FK migration sequence is selected.
  4. A Status: Proposed (or higher) replaces Deferred — placeholder above.

Until then, treat references to ADR-013 as references to the planned-but-uncommitted unification work tracked here. The references resolve; the decisions don't yet exist.
