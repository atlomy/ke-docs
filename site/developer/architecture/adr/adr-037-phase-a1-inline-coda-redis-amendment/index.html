ADR-037 Phase A.1 Amendment: Inline Coda Credential — Session-Only → Short-TTL Ephemeral Redis

Disambiguation. "ADR-037" here is the import-deployment / inline-Coda credential decision tracked under ADR-037 Phase A.1 in docs/decisions/log.md (2026-05-21 deploy entry + the 2026-05-31 Phase A.1 retest D16 corrections), not the unrelated slot-type-taxonomy ADR whose file happens to be numbered 037-slot-type-taxonomy.md. This amendment does not touch the slot taxonomy.

  • Status: Proposed (2026-06-03) — ratified in scope by the platform owner for Spec 0040 Stream 2 (docs/superpowers/specs/0040-wizard-coda-edge-materialization-restore/tasks.md, "Ratified scope additions", T4d). Implementation landed; security review by the human pending.
  • Date: 2026-06-03
  • Deciders: Platform owner/architect + Claude (Spec 0040 Stream 2)
  • Context source: Spec 0040 (wizard Coda edge materialization restore) async materialize transport; consolidation-map.md § SOLVE-don't-accommodate (constraint 2).

Context​

ADR-037 Phase A.1, as corrected in the 2026-05-31 retest (decision-log D16 correction), established the inline-Coda credential rule for self-service imports:

The one-time inline Coda API key is session-carried only — it lives in the server-side request.session for the request/resume window and is scrubbed on use. It is never written to ImportWizardJob.payload, the project source_evidence, telemetry, or any DB ledger. (Tenant self-service credential storage / BYOK remains deferred to ADR-014-α + Spec 0023.)

This rule worked because materialize ran synchronously in the request: the view held the key in its own session and handed it to the materializer inline.

Spec 0040 changes the transport. The wizard materialize site (the retained-Coda source-row replay that hit the 157s > 120s gunicorn timeout) is converted to an asynchronous MATERIALIZE job drained by a separate worker process (the Celery worker/beat in prod; the admin daemon thread for immediate drain in dev). A separate process cannot read the originating request's request.session. So the inline-key rule, as written, makes inline-key Coda imports un-backgroundable — which is exactly the timeout we are removing.

Three transport options were considered (see consolidation-map.md constraint 2):

  1. Keep inline-key materialize synchronous (background only configured-creds jobs). Rejected: leaves the largest, slowest imports (the timeout case) on the request thread — it does not solve the problem.
  2. Put the key on the job payload. Rejected outright: violates the ADR-037 never-persist-to-the-ledger invariant; the payload is durable in the tenant DB (and any backup), readable by anyone with DB access, and survives well past the request.
  3. A short-TTL ephemeral Redis key, keyed by job_id, read-and-deleted by the worker, with TTL as a backstop. Selected (this amendment).

Decision​

For an inline-key MATERIALIZE job, the inline Coda API key is carried from the enqueueing request to the draining worker via a dedicated, short-TTL Redis cache key, written on enqueue and consumed (read and deleted) by the worker:

  • Storage: Django CACHES['default'], a RedisCache (Django 6 built-in; uses the already-vendored redis library — no new dependency) on a dedicated Redis logical DB index /2, distinct from the Celery broker (/0) and result backend (/1). Key shape: ke:import_wizard:materialize_inline_key:<job_id> (the ke prefix is the cache KEY_PREFIX). Implementation: store_inline_materialize_key / pop_inline_materialize_key in data_import/services/import_jobs.py.
  • Write: at enqueue time, in the request thread, only when the project is an inline-Coda replay (coda_inline_replay_descriptor_for_project returns a descriptor) and the operator re-entered the key at the Stage-6 Start prompt. The key is never placed on the job payload, result_payload, source_evidence, or any DB row — only the non-secret materialize_replay_source_rows / materialize_project_id markers go on the payload.
  • Read: in the worker (_execute_materialize), pop_inline_materialize_key performs consume-once: cache.get then immediately cache.delete. A successful materialize therefore leaves no credential at rest.
  • TTL backstop: INLINE_MATERIALIZE_KEY_TTL_SECONDS = 600 (10 minutes). If the worker dies before consuming the key (so delete never runs), the key self-expires. The TTL must exceed (beat poll interval ~2 min) + (worst-case observed materialize duration ~157 s) with margin; 10 minutes is that bound rounded up. Rationale recorded inline at the constant.

The configured-credential lane (operator/background jobs that reference an ExternalServiceCredential) is unchanged — those jobs resolve the secret from the existing credential store inside the worker and never use this Redis key.

Threat model​

What changes vs. ADR-037 (session-only):

PropertyBefore (session-only)After (this amendment)
At-rest location during the windowdjango_session row (default DB session backend)Redis DB /2, single key
At-rest lifetimeuntil resume scrubs it (request window)until worker consumes it; TTL ≤ 10 min backstop
In job payload / result_payload / project / telemetry / any DB ledgerNo (invariant)No (invariant preserved — asserted by test)
Readable by a separate processNo (the limitation we are removing)Yes — by design, only the draining worker

Net at-rest exposure is comparable, not worsened. ADR-037's session-only design was already not fully at-rest-free: with Django's default DB session backend the key rests transiently in the django_session table (and any backup taken during the window) until scrubbed — this caveat is recorded in the existing _coda_inline_session_key docstring and the 2026-06-01 19:52 state note. The Redis key is a sibling transient at-rest store with a hard TTL ceiling the session path lacks.

Controls:

  • No-persist invariant (the control a reviewer should check hardest): the key is never serialized into payload, result_payload, source_evidence, telemetry run_metrics, or last_error. Enforced by enqueue_materialize_job (it stashes via the Redis helper, never the payload) and asserted by test_inline_key_never_lands_in_job_payload_or_result_payload and the migrated test_inline_coda_materialize_reprompts_key_without_persisting_secret.
  • Consume-once read+delete minimizes the live window; the TTL is a backstop, not the primary control.
  • Namespace isolation: dedicated Redis logical DB /2 (not the shared broker namespace), so a credential key cannot collide with or be enumerated alongside broker/result traffic.
  • Network isolation: Redis is reachable only on the internal Docker/cluster network (no public ingress); production should additionally apply Redis AUTH / TLS / network policy per the existing deployment posture (deploy/cloud/README.md).
  • Coalescing: the materialize job is coalesced per project (coalesce_key=materialize:project:<id>), so a double-submit cannot stash two divergent keys for one project.

Residual risks (explicit):

  • Redis persistence: if Redis is configured with RDB/AOF persistence, a key live at snapshot time could be written to disk.

    ⚠️ Correction (2026-06-03, post-review): the earlier "disable persistence on the cache DB /2" mitigation was WRONG. Redis RDB/AOF persistence is configured per-instance, not per-logical-DB — /0 (Celery broker), /1 (result backend), and /2 (this cache) share one instance and one persistence config. You cannot disable persistence for /2 alone, and disabling it instance-wide would make the Celery broker (/0) lose queued tasks on restart. A boot-time assertion that refuses to start when persistence is on is therefore both infeasible (can't target /2) and harmful (self-DoS on any deploy where the broker wants durability, or a managed Redis with persistence on).

    Correct mitigation: encrypt the inline key before caching it (e.g. Fernet with a key from settings), so even if RDB/AOF writes it to disk it is ciphertext, not plaintext — instance-persistence-agnostic, no broker harm. Fallbacks: a separate Redis instance for the credential cache with persistence off (instance-level, controllable; adds infra), or keep inline-key materialize synchronous for small jobs and defer to BYOK (ADR-014-α / Spec 0023). Tracked as a follow-up (Spec 0040 tasks.md, R11 absorption).

  • Worker-crash window: a crashed worker leaves the key until the TTL expires (≤ 10 min). This is a deliberate trade — the alternative (delete-on-read-before-use) would lose the key on any transient worker failure and require the operator to re-enter it, the same failure ADR-037's session-pop already has, but without the retry affordance.
  • Rollback-orphan window (added 2026-06-03; surfaced by the ADR-054 stress-test). store_inline_materialize_key writes the key to Redis /2 outside the enclosing DB transaction, so it is a second non-transactional dual-write (DB job row in Postgres
    • key in Redis). If the enqueue path rolls back after the Redis write, the secret is orphaned at rest until the TTL (≤ 600s). Owner decision (2026-06-03): ACCEPTED for the pilot — the window is short, the key is encrypted (Fernet), and the 3-tenant pilot exposure is low. The fix (write the Redis key only on transaction.on_commit, with a rollback compensator) is promoted to P1 when the worker-tier split lands (ADR-054 P0 increment-B / the dispatch arc), not before. This residual must be re-evaluated at that point.

What this amendment supersedes​

  • The Spec 0040 design.md / Task-4 language proposing a "small/sync fallback for inline-key, or require configured creds for large rowCount" is superseded: because the worker reads the key from Redis uniformly (regardless of whether the daemon thread or the beat worker drains it), inline-key materialize always backgrounds. No size-branching is reintroduced on the wizard — the 157s timeout was the entire motivation for backgrounding, so keeping any inline case synchronous would defeat it.

Scope boundaries (unchanged)​

  • This does not introduce persistent / saved tenant credentials. BYOK and self-service connector storage remain deferred to ADR-014-α + Spec 0023.
  • The configured-ExternalServiceCredential lane is untouched.
  • The materialize_project signature is untouched (Spec 0040 Stream-1 boundary).

Consequences​

  • Inline-key Coda imports background like every other import — the wizard timeout is removed for the inline lane, not just the configured-creds lane.
  • A new at-rest credential location (Redis /2) exists for ≤ 10 minutes per inline job. The no-persist-to-ledger invariant — the load-bearing ADR-037 guarantee — is preserved and test-asserted.
  • The deploy posture gains a follow-up: encrypt the cached credential at rest (not "disable persistence on /2" — see the corrected residual-risk note above; persistence is instance-level and disabling it harms the broker), and apply Redis AUTH/TLS in prod.
