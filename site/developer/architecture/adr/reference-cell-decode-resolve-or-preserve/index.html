ADR-056: Reference-Cell Decode Contract — Resolve-or-Preserve, Fail-Loud Only on Malformed Payloads

Date: 2026-06-07 Status: Accepted (2026-06-07 owner ratification — contract direction confirmed in-session during the escorted import retest) Deciders: Builder + spec owner (this ADR records a settled decision and pairs with the code implementation owned by Codex) Amendments: 2026-06-07 (owner) — defined the fatal-case blast radius as collect-all, never abort-on-first (Decision §"The fatal case is collect-all…"); closes the gap where "fail loud" alone could still abort the whole import on the first malformed cell.

Context​

The cold import wizard reads source rows in two different shapes through the same adapter:

  • Read / practice ("ready to save") path — the tolerant value format (simpleWithArrays via list_rows, coda_adapter.py:319). Display text flows straight through; reference columns are plain strings; edges resolve downstream by text-match.
  • Materialize (write) path — the strict, rowId-bearing value format (rich via list_rich_rows, coda_adapter.py:340), which carries a reference column's intrinsic row identifiers (the exact edge-join key introduced by Spec 0040).

The strict path runs a fail-fast gate, validate_rich_row (coda_adapter.py:591, added as Spec 0040 decision B1). That gate raises a fatal error the moment any reference-column cell is a non-empty, non-dict value (_is_malformed_reference_item, line 576 — "not a dict"). The instinct behind B1 was sound: under rich, a reference value should be a JSON-LD StructuredValue, so a bare scalar looked like a wrong-format payload that the lenient decoder would silently turn into a dropped edge.

Two problems surfaced when this ran end-to-end against a real Coda-backed tenant for the first time:

  1. Legitimate unlinked-text reference cells are normal, not malformed. A lookup/reference column can hold plain display text instead of a hard row-link — most commonly when a source was assembled or migrated by paste/import and the cells were never converted to real links. This is invisible in the source tool's own UI and in the tolerant value format; only the strict rich read exposes linked-vs-unlinked. A live scan of one large reference table found unlinked-text rates from a few percent up to ~71% in a single column — i.e. thousands of cells. This is not corruption: a record attested but not yet linked to its target (e.g. an entity recorded before its companion entity exists) is valid in-progress scholarship and must survive the import. The fail-fast gate aborts the entire multi-thousand-row import on the first such cell, in row order, so fixing one cell in the source merely surfaces the next — whack-a-mole that does not converge.

  2. The decode and the gate disagree, and removing the gate alone is not safe. The actual decoder, extract_rich_reference_row_ids (coda_adapter.py:460), already tolerates a bare-text reference cell — by returning []. So if B1's gate were simply deleted, the text would be silently collapsed to [], losing both the edge and the value — exactly the silent-drop B1 existed to prevent. A correct fix must resolve or preserve the text, not merely stop failing on it.

A third issue is structural rather than a bug: because "ready to save" validates the tolerant path and the write uses the strict path, a fully green practice run cannot, by construction, catch a strict-path decode failure. The wizard reported "ready, all rows validated" and then failed at the write.

This failure mode — "a cell displays as a reference but is not a linked record" — is platform-general. Any adapter assembling rows from a paste/import-built source (Coda today; MySQL and XLSX lanes are not yet retested but are subject to the same class) will encounter it.

Decision​

Reference-column decoding is governed by a resolve-or-preserve contract with a single fail-loud case. For each reference cell the decoder produces one of four outcomes, and a missing or unresolvable link never drops the row and never aborts the import:

Cell shapeMeaningOutcome
StructuredValue (or list) carrying a rowIdlinked recordresolve rowId → typed edge
bare display text that matches exactly one target rowan intended link the source never hard-linkedresolve by text-match → typed edge
bare display text that matches multiple target rows (ambiguous)the join key is not unique — the exact reason rowId was adoptedleave unresolved — preserve the value, no edge; do not guess first-match
bare display text that matches nothingvalid in-progress scholarship (target not yet created)preserve the value, no edge, must pass — pass the text through into JSONB so the downstream unresolved-preserve path retains it
empty / None / []no referenceno edge, no error
a dict that is genuinely the wrong shape (e.g. missing rowId)a real malformed payloadfail loud, collect-all — the only fatal case; scan the whole table and report every malformed cell at once, never abort on the first (blast radius below)

This amends Spec 0040 decision B1: fail-loud is narrowed from "any non-dict reference cell is fatal" to "only a structurally-malformed reference payload is fatal." rowId-first preserves Spec 0040's intent (the row identifier is the exact join key when present); text-match fallback is not negated by the rowId work — it remains the resolution path the committed importer already relies on.

The fatal case is collect-all, never abort-on-first. "Fail loud" alone is underspecified: an implementation that raises on the first malformed cell — the original validate_rich_row behavior — still lets one bad cell abort the whole multi-thousand-row import, which is the exact brittleness this ADR exists to remove (it would merely make the abort rarer, not fix it). The required behavior is scan-complete-then-decide: the decoder scans the entire table, accumulates every malformed-dict cell with its (table, row, column) coordinates, and then takes one terminal action — fail loud once with the complete manifest (so the operator gets a single fix-pass, not whack-a-mole, where each fix surfaces the next bad cell). An implementation may instead choose the stronger quarantine-and-continue variant (skip the specific malformed cells, import the rest, and surface the count), which is even more aligned with this ADR's founding principle; that choice is left to the paired code. What is non-negotiable: a malformed cell must never abort-on-first, and the report must be complete. This scan runs in the pre-flight strict decode (the parity requirement below), so malformed cells surface at the practice run — before the write — not at materialize.

The contract is platform-general; Coda text-match resolution is its adapter-specific realization. The MySQL and XLSX adapters must honor the same four-state contract.

The fix scope is the upstream decode/gate only. The downstream relationship materializer already implements the preserve-unresolved behavior the third row requires (relationship_materializer.py:70-71,116-119: unresolved refs stay in JSONB, are counted, never fail; materialization/relationships.py:145-156: endpoint-less rows are skipped-with-warning, never fatal). That behavior must not be reinvented; the decode change exists to let legitimate text reach it.

Separately, the wizard's pre-flight / "ready to save" validation must exercise the same strict decode the write performs. No readiness check may pass against a weaker code path than the one the materialize uses. (Implementation — unify on one decode path, or run the strict decode during the practice run — is left to the paired code and Spec 0040 follow-up.)

Consequences​

Positive​

  • Imports complete in the presence of legitimate unlinked-text reference cells — the common real-world state — instead of aborting on the first one.
  • Edges the source intended but never hard-linked are recovered by text-match, rather than lost.
  • In-progress scholarship (records whose target does not yet exist) survives import and can be linked on a later re-import once the target exists (aligns with --merge-replace identity matching, ADR-017).
  • A green practice run becomes a real guarantee: "ready to save" validates the code the write runs.
  • The contract is stated once and binds every source adapter, so MySQL/XLSX do not each re-derive their own answer.

Negative​

  • Text-match resolution is weaker than a rowId join: it can mis-resolve when display strings collide across target rows. The contract mitigates by leaving ambiguous multi-row matches unresolved (preserved, not guessed) — never first-match — which is the entire reason rowId was adopted. This trades some recoverable edges for correctness.
  • "Preserve, no edge" means an entity can carry an unresolved reference indefinitely if the target is never created. This is intended (valid in-progress data), but raises the importance of surfacing the unresolved count to the user so silent non-linking is visible.
  • Narrowing fail-loud re-admits a small risk that a genuinely malformed payload is treated as text and preserved rather than failed. Bounded by keeping the malformed-dict case fatal.

Mitigations​

  • Surface an "N references not linked yet" count to the user at decision/receipt time, so preserve-unresolved is transparent rather than silent.
  • Fixtures must exercise every state per cell, not per column (a single column legitimately mixes linked, unlinked-text, and empty cells): single StructuredValue; list of StructuredValue; text-resolves-to-one-edge; text-matches-multiple-left-unresolved; text-matches-nothing-preserved; empty; and multiple genuinely-malformed-dict cells across different rows/columns — which must produce one complete report covering all of them, proving collect-all and not abort-on-first.

Alternatives Considered​

  • Keep B1 as-is (fail-loud on any non-dict reference cell). Rejected: aborts real imports on normal data; un-converges into whack-a-mole source cleanup; treats valid in-progress scholarship as corruption.
  • Delete the gate and let the decoder return [] for text. Rejected: silently drops both the edge and the value — the exact harm B1 was built to prevent.
  • Degrade unlinked-text reference cells to flat text / no-edge at the decode gate. Rejected (an earlier framing during diagnosis): discards the scholarly edge the reference column exists to hold, when that edge is recoverable by text-match.
  • Guess the first row on an ambiguous multi-row text match. Rejected: reintroduces exactly the cross-row collision that motivated adopting rowId; preserve-unresolved is safer than a wrong edge.
  • Fix the data in the source instead of the code. Rejected as a primary path: the unlinked-text condition is pervasive (thousands of cells, one column ~71% unlinked) and is a property of how real sources are assembled, not a one-off. Source re-linking remains available to a tenant but cannot be the contract.

Implementation​

Implementation of the decode change and the pre-flight parity is owned by Codex (started 2026-06-07), test-first. The approved approach is heal-at-adapter: resolve text→rowId against already-fetched target tables, preserving the intrinsic join id when present. Three must-haves the code carries, mirrored here so doc and code do not drift:

  1. On no-match, pass the text through (do not null it) so the materializer's unresolved-preserve path retains it. Highest priority — this is what makes the third contract row work.
  2. On ambiguous multi-row match, leave unresolved — do not guess first-match.
  3. Surface the unresolved count to the user.

Close the pre-flight gap so the strict rich decode is exercised before "ready to save," not only at the write.

What proves it works: a fixture import containing a reference column with mixed linked / unlinked-text-resolvable / unlinked-text-unmatched / empty cells completes; produces edges for the linked and text-resolvable cells; preserves the unmatched cells' values with no edge and zero failures; reports the unresolved count; and — when several genuinely-malformed reference dicts are present across rows — fails loud once with the complete list (or quarantines them all and continues), never aborting on the first.

Compliance​

  • Spec 0040 (wizard Coda edge materialization restore) — amends decision B1. The rowId-first read is retained; the fail-loud scope is narrowed; text-match resolution is affirmed, not negated.
  • Deterministic-first — resolution is keyed on declared column metadata and the actual cell shape (rowId vs text vs empty vs malformed), not heuristics.
  • Generalization guard — the contract is platform-canonical and binds all source adapters; no tenant-specific drop-lists or aliases. Coda is the first adapter instance; MySQL/XLSX inherit the same contract.
  • ADR-017 (importer merge discipline) — preserve-unresolved composes with --merge-replace: a later re-import can create the edge once the target entity exists.
  • Canonical structure shared; interpretation tenant-specific — the four-state decode is shared structure; which target a text string resolves to is tenant data.

Open Question — cross-source reverse-edge & dual-side editing (deferred)​

This ADR governs decoding a reference cell. It does not resolve how a computed/derived reverse-rollup reference column should be detected and de-duplicated against its forward edge without source-specific computed-column metadata (MySQL/XLSX cannot flag a "rollup"), nor whether dual-side relationship editing is a first-class feature. That is a separate architecture question raised in the same retest (finding F22) and is left for a dedicated ADR; it must not be silently re-decided here.
