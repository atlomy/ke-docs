ADR-042: Layered substrate naming and Tenant* prefix retirement

Status: Accepted (ratified 2026-05-30; v1.1 design 2026-05-22) Date: 2026-05-21 (v1.0); amended 2026-05-22 (v1.1 — R2-NEW-3 runtime boundary enforcement split + R2-NEW-5 standalone-sprint sequencing; ratified by user direction "Ratify" on closeout devlog 2026-05-22_0800_overnight-session-final-ratification-and-merge.md) Deciders: User; architecture team Related: ADR-004 (Tenant Ontology Mapping), ADR-012 (TenantArchetypeFormConfig as data, not code), ADR-017 (slot config as DB, not code), ADR-026 (Tenancy strategy at scale), ADR-037 (Slot-Type Taxonomy and Tenant Vocabulary Layer), ADR-038 (Federated Preset Registry as Federation Contract)

TL;DR​

The platform's Tenant* model prefix (TenantOntology, TenantArchetypeFormConfig, TenantSlotPreset, TenantCSLStyle, …) is non-idiomatic for Django, asymmetric (the actual tenant-isolation-boundary model is named customers.Client, not Tenant), and blocks the customer-hierarchy vocabulary the platform will need as it grows beyond a single layer (institution / organization / workspace / knowledge environment). The prefix enforces nothing — search_path switching in django-tenants' middleware is what enforces tenant isolation, regardless of model name. The prefix is documentation, not a safety mechanism.

This ADR records the decision to drop the Tenant* prefix on domain models and instead use Django app placement (epistemic/, platform/, customers/, ke_core/, …) as the layer signal. The convention follows django-tenants' own example projects, Django general style (HackSoft Django Styleguide), and the broad industry pattern (Wagtail, Strapi, Slack, Notion, Auth0, AWS SaaS Lens) which all converge on app/schema namespacing rather than per-model prefixes. The Tenant class name is retained only on the TenantMixin subclass that is the actual isolation boundary (today: customers.Client).

The symbolic-only safety the prefix provided gets replaced by an actual CI-enforced layer boundary via an import-linter contract: epistemic may not import from platform, etc. This is stronger than a name prefix because it fails the build instead of merely embarrassing the reviewer.

The immediate test case is Phase A.1 (PR #365, merged 2026-05-21T17:27), which added the Tier-1/2/3 vocabulary registry triplet PlatformVocabularyEntry / TenantSlotPreset / UngroundedVocabularyValue. That triplet is precisely the asymmetric Platform* / Tenant* / un-prefixed pattern this ADR critiques. When the rename sprint runs, those three rename symmetrically (platform.VocabularyEntry, epistemic.SlotPreset, epistemic.UngroundedVocabularyValue) along with the rest of the tenant-layer inventory.

Context​

What the Tenant* prefix is doing today​

Tenant-layer models currently carrying the Tenant* prefix:

ModelPurpose
TenantOntologyADR-004 tenant ontology mapping — per-tenant alias of platform archetypes ("Era" vs "Period" vs "Time").
TenantArchetypeFormConfigADR-012 — tenant-side declarative form/wizard config.
TenantArchetypeTableTenant-side archetype table view config.
TenantSlotPresetADR-037 + ADR-038 — Tier-2 tenant-scoped slot preset (Phase A.1, PR #365).
TenantCSLStyleTenant-side citation style binding (Spec 0008).

Platform-layer model currently carrying the Platform* prefix:

ModelPurpose
PlatformVocabularyEntryADR-037 + ADR-038 — Tier-1 platform-canonical vocabulary entry (Phase A.1, PR #365).

The convention is already inconsistent. The model at the actual tenant-isolation boundary — the TenantMixin subclass that django-tenants uses to drive schema-per-tenant routing — is customers.Client. It does not carry a Tenant* prefix; "Client" is a customer-facing word from the customers app's vocabulary. So the platform already accepts that the actual tenancy-mechanical model can have an idiomatic, domain-suited name and that the layer signal lives elsewhere (in this case: in the customers app).

The asymmetry shows up most cleanly in PR #365's triplet:

  • PlatformVocabularyEntry — Tier-1, lives in the public schema, Platform* prefix.
  • TenantSlotPreset — Tier-2, lives in tenant schemas, Tenant* prefix.
  • UngroundedVocabularyValue — Tier-3, lives in tenant schemas, no prefix.

Three models on the same tier ladder; three different naming conventions. That is the immediate trigger for this ADR.

The user's two concerns​

The user (2026-05-21 evening) raised two concerns when asked whether to keep the Tenant* prefix going forward:

  1. Layer-vocabulary confusion as the customer hierarchy grows. The platform is moving toward a richer customer hierarchy: Knowledge Environment (the customer-facing entity — what users call "their KE"), Institution / Organization (a future grouping above or across KEs), Workspace (a future intra-KE working area). If Tenant* is the prefix today, what happens when an Institution model arrives that owns several Tenants? Or when Workspace arrives as an intra-tenant scope below Tenant? The prefix risks collapsing several distinct hierarchy levels into one word.
  2. Security and lint implications of dropping the prefix. Does Tenant* provide an actual safety property — a reviewer-visible signal that helps prevent cross-tenant data leaks? Would removing it weaken the existing tenant-isolation guarantees, or weaken the existing lints (notably scripts/lint_no_tenant_vocabulary.py)?

Both concerns are addressed below — concern (1) via the Auth0 two-axis pattern (§ "Auth0 two-axis pattern"), concern (2) via the import-linter substitute (§ "Decision").

Why now​

Phase A.1 just landed (PR #365, merged 2026-05-21T17:27), adding three more vocabulary registry models. Spec 0022 work is starting and will add more. The longer the rename is deferred, the larger the blast radius. The right time to decide on the convention is before more new models follow it.

A representative scan of mature multi-tenant Django and SaaS codebases (django-tenants ecosystem, Wagtail multi-site/multi-tenancy, Strapi multi-tenant plugin, Slack, Notion, Auth0, AWS SaaS Lens, Azure SaaS guidance):

The Tenant* prefix is an outlier. None of the surveyed platforms prefix all tenant-layer domain models with Tenant*. The HackSoft Django Styleguide explicitly treats name-duplication-with-app-name as an anti-pattern (orders.OrderItem is overdetermined; orders.Item is clearer).

django-tenants specifically​

The django-tenants package — the substrate this platform is built on — does not prescribe a Tenant* model prefix anywhere in its installation, usage, or migration docs. Its example projects (and the predecessor django-tenant-schemas) use plain domain-named models like Client, Customer, Domain. The layer mechanism is the SHARED_APPS vs TENANT_APPS setting in settings.py: apps placed in SHARED_APPS live in the public schema; apps placed in TENANT_APPS live in per-tenant schemas. Schema-per-tenant is the namespace; the model name does not need to repeat it.

The actual security mechanism is TenantMainMiddleware switching search_path per request. Cross-tenant data access is blocked at the PostgreSQL level by the search-path switch, regardless of whether the model is named Ontology or TenantOntology. The name carries zero enforcement weight.

Auth0 two-axis pattern​

Auth0's multi-tenant SaaS architecture docs draw a load-bearing distinction the platform should borrow:

  • Tenant is the technical isolation boundary — the unit a tenant's data is partitioned under (a schema in django-tenants; a tenant-id discriminator in Auth0's case). It is an infrastructure-layer concept.
  • Organization is the customer-facing grouping — the entity a paying customer recognizes as "their thing". Multiple Organizations may live within one Tenant; or each Organization may map 1:1 to a Tenant; the choice is independent.

This separation cleanly resolves the user's concern (1). When KE adds future hierarchy entities — KnowledgeEnvironment (the customer-facing entity), Institution / Organization (the grouping above or across KEs), Workspace (the intra-KE working area) — they each get their own un-prefixed domain name in their own app. The word "Tenant" stays bound to the technical isolation boundary (the TenantMixin subclass), and the customer-hierarchy vocabulary lives alongside it without collision.

The platform already partially follows this pattern: customers.Client is a customer-facing word for what is technically a tenant; the customers app is the carrier. Extending the pattern is consistent with what is already there, not a reversal.

Security and lint implications (concern 2)​

The user's second concern was whether dropping the prefix weakens security or lint coverage. The answer is no — and app-namespacing is in fact a slight positive on most axes:

  • Tenant isolation enforcement: provided by search_path switching in TenantMainMiddleware. Independent of model naming. No change.
  • Migrations: migrate_schemas walks tenant schemas for apps in TENANT_APPS and the public schema for apps in SHARED_APPS. App placement is the migration signal — the prefix is redundant. App-namespacing makes the layer assignment more visible (the app is in SHARED_APPS or it is not).
  • Cross-layer foreign keys: django-tenants warns against FKs from tenant → public → tenant. Today the prefix signals which side a model is on; with app-namespacing, the import line signals it (from platform.models import VocabularyEntry makes the cross-layer reference explicit at the import site, not buried in the model name). This is more visible during review, not less.
  • GenericForeignKey across the boundary: contenttypes-based GFKs that cross the layer boundary are a known footgun. Today the prefix gives a vague hint; with app-namespacing the imports must cross app boundaries, which surfaces the GFK during review and during static analysis. Slight positive.
  • mypy / django-stubs: model class names must be unique within a Django project for unambiguous reverse-accessor typing. Two models named Ontology in different apps is fine — they are epistemic.Ontology and (if it existed) platform.Ontology, two distinct app_label.Ontology identifiers. Reverse accessors disambiguate via related_name. No issue.
  • scripts/lint_no_tenant_vocabulary.py: this lint is about tenant vocabulary leaks — checking that platform code does not hardcode tenant-specific terms like "cardiovascular", "Aristotle", domain-specific aliases, etc. It is not about model class naming. The rename is orthogonal to this lint; the lint continues to work unchanged.
  • Grep-ability: a minor negative. Today grep TenantOntology finds the model directly. After the rename, finding "the tenant-side ontology model" is grep -r 'class Ontology' epistemic/ or an IDE Go-to-Symbol. Slightly more friction; not significant.

Net: app-namespacing is neutral-to-positive on security, positive on lintability (because an import-linter contract can be added; see § "Decision"), and mildly negative on grep-ability.

Decision​

D1 — Drop the Tenant* and Platform* prefixes on domain models​

Going forward, domain models do not carry layer prefixes. The Django app they live in is the layer signal. Concretely:

  • Tenant-layer models live in tenant-side apps (epistemic/, epistemic_core/, etc., placed in TENANT_APPS).
  • Platform-layer models live in platform-side apps (platform/, etc., placed in SHARED_APPS).
  • The customers/ app hosts the tenancy-mechanical models (Client, Domain) per its current shape.

D2 — Reserve Tenant as a class name only for the actual isolation boundary​

The word "Tenant" stays bound to the TenantMixin subclass — the model django-tenants actually uses to drive schema routing. Today that model is customers.Client. If the customer-hierarchy refactor later promotes KnowledgeEnvironment to the isolation-boundary class, the Tenant word migrates with it. Either way, "Tenant" never returns as a domain-model prefix elsewhere.

The rename of customers.Client itself to a product-language-aligned name (e.g. KnowledgeEnvironment) is out of scope for this ADR and flagged as a candidate for a future product-language-alignment ADR. The cost-benefit is different (it touches every login URL pattern, every domain-routing reference, every Django admin link) and warrants its own decision.

D3 — Reserve customer-hierarchy vocabulary for future use​

The following words are reserved for future customer-hierarchy entities. They are not adopted by this ADR; they are explicitly held back so that no premature claim is made on them:

  • KnowledgeEnvironment — the customer-facing entity. What a customer or a user calls "their KE" — the product-noun for what is technically a Tenant. Likely arrival: alongside the product-language alignment effort.
  • Institution / Organization — a future grouping above or across KEs. Per the Auth0 two-axis pattern, multiple KEs may belong to one Institution, or vice versa; the relationship is not pre-committed here.
  • Workspace — a future intra-KE working area. Likely an authoring/curation scope below the KE level; will sit inside the tenant schema.

These are reserved now so that no current model takes one of these names by accident and forces a rename when the hierarchy refactor arrives.

D4 — Use Django app placement as the layer signal​

The layer of a model is determined by which app it is in and where that app sits in SHARED_APPS vs TENANT_APPS. This is the same mechanism django-tenants already uses for migrations and for search_path routing. No prefix is necessary on top of it.

Initial app→layer mapping (consistent with the existing structure):

platform/shared / publicPlatform-canonical vocabulary entries, presets, registries
epistemic/tenantTenant-scoped ontology, slot presets, form configs, archetype tables

The mapping is illustrative; the rename sprint owns the authoritative table.

D5 — Add an import-linter contract to enforce layer boundaries in CI​

The symbolic-only safety the Tenant* prefix used to provide is replaced by an import-linter contract enforced in CI. The contract expresses rules such as "the epistemic app may not import from the platform app" (or whichever direction the cross-layer rule should run; the rename sprint owns the final contract direction). The point is: a layer-boundary violation fails the build rather than merely being conspicuous to a careful reviewer.

The contract syntax and the exact set of forbidden directions are implementation details for the rename sprint; this ADR only commits that some import-linter contract will land alongside the rename. Without that contract, the rename trades a weak prefix-as-signal for nothing; with it, the rename trades a weak prefix-as-signal for a strong CI-enforced boundary.

Coverage caveat (v1.1): import-linter contracts catch standard top-of-file Python imports. They do NOT catch conditional imports inside functions, runtime __import__() resolvers, Django signal handlers, GraphQL schema introspection leaks, or from X import * patterns that bypass static-import detection. The runtime-enforcement augmentation in §D6 closes those gaps; the star-import audit in §D6 is a precondition for the import-linter being trustworthy at all.

D6 — Runtime boundary enforcement (v1.1, R2-NEW-3 ratified 2026-05-22)​

Augment §D5's import-linter with runtime-side enforcement. The R2 reconciliation split this into "now" and "deferred-with-trigger" parts:

D6.1 — Apply NOW alongside the rename sprint:

  • Exhaustive star-import audit: AST-parse the entire codebase to identify and eradicate from X import * patterns before turning the import-linter on. Star imports bypass static import detection and silently void any import-linter contract's guarantees. This is a precondition, not a nice-to-have.
  • Custom Django system check (manage.py check): at app startup, analyze django.dispatch.signal._receivers to detect cross-layer leaks. If epistemic.* signal receivers mutate platform.* state (or vice versa per the rename sprint's chosen contract direction), fail the boot with a fatal error. The system check is the runtime complement to the static import-linter — together they cover the static graph plus the signal-receiver graph that import-linter cannot see.

D6.2 — DEFER WITH TRIGGER (queued; not in the rename sprint):

  • CI-level GraphQL schema diff: a script that introspects the public GraphQL schema and fails the CI build if any epistemic.* type leaks into the cross-tenant platform.* namespace (or any privileged operation appears unauthenticated). This is deferred because it has no concrete leak evidence today and would impose a CI step that may produce false positives during in-flight schema work. Trigger to resurface: first cross-tenant federation surface lands (per ADR-038's federated preset registry going beyond first-party scope), OR first tenant onboards whose federation/marketplace bundle introduces cross-tenant query paths. At trigger, add the schema-diff CI step + an allowlist for the new federation types.

Rationale: §D5's static import-linter is necessary but not sufficient. §D6.1's runtime augmentations are cheap (the system check is ~30 lines of Django startup code; the star-import audit is a one-time AST pass) and close real leak modes. §D6.2's schema diff is more invasive and has no current leak evidence; it waits for the federation surface that would create the leak it's designed to catch.

D7 — Explicit-import convention​

The platform convention is explicit imports, never wildcard. from platform.models import VocabularyEntry is permitted; from platform.models import * is not. This keeps the cross-layer dependency surface visible at every import site, makes the import-linter contract easier to reason about, and is enforced by the §D6.1 star-import audit.

D9 — Standalone-sprint sequencing (v1.1, R2-NEW-5 ratified 2026-05-22, PARTIAL ACCEPT)​

ADR-042's rename is a standalone isolated sprint, NOT a Spec 0022 / Spec 0023 precondition. Sequencing implications:

  • Spec 0022 + Spec 0023 ship independently of ADR-042 status. If ADR-042 lands first, they pick up neutral names per §D8. If ADR-042 has not landed by their sprint Day 1, they ship under current Tenant* names; the rename PR catches them as part of its own scope. Spec 0022's own fallback paragraph in requirements.md §"Sprint sequencing" already admits this.
  • Multi-agent coordination during the rename PR window is handled by rebase discipline, not by a code freeze. Active parallel branches (Codex, Copilot, Claude) rebase onto the post-rename v2 HEAD after merge; conflicts are mechanical name-substitutions that git mergetool + sed-style replacements resolve quickly.
  • The previous proposal of a 1-day code freeze on v2 during the rename PR open-merge window is NOT adopted. Rationale (R2 reconciliation): a 1-day freeze is over-engineered for the 3-AI-agent + internal-team workflow currently in play. The cost of pausing Codex/Copilot/Claude work for a day exceeds the cost of rebasing 1-3 active branches post-merge.
  • Single-author / fast-merge for the rename PR remains a soft recommendation. The rename PR is high-churn but mechanical; one author shepherding it through review minimizes merge-conflict surface area.

What this preserves from the proposed amendment: standalone-sprint framing; explicit decoupling from Spec 0022/0023 timing; the recommendation that the rename PR be single-author / fast-merge.

What this drops: the 1-day code freeze on v2. Replaced by rebase discipline on active parallel branches.

Rationale why user ratification matters: this sequencing decision affects multi-agent coordination and was explicitly queued for user judgment in the R1 absorption devlog. User ratified PARTIAL ACCEPT on 2026-05-22 per the closeout devlog.

Alternatives Considered​

Option B — KE* prefix (KEOntology, KEVocabularyEntry)​

Use KE as a brand-aligned prefix in place of Tenant* / Platform*. Domain models become KEOntology, KEArchetypeFormConfig, etc.

Why not chosen: this is precisely the anti-pattern the HackSoft Django Styleguide warns against — repeating the project name on every model. The brand belongs at the product surface, not in every class name in the ORM. It also leaves no room for the future customer-hierarchy vocabulary (concern 1): if KE is the prefix, what does an Institution model look like? KEInstitution reads as either redundant or confusing. Worst on KE-alignment scoring superficially, but actually weakest on long-run scalability.

Option C — Environment* prefix (EnvironmentOntology, EnvironmentVocabularyEntry)​

Use "Environment" — short for Knowledge Environment — as the prefix.

Why not chosen: collides with Python's os.environ mental model and with deployment-environment vocabulary (production / staging / dev). The word "environment" is overloaded enough in software contexts that a prefix-level claim on it would confuse code reviewers from outside this project. Worse than Option B on industry-recognizability.

Option D — Workspace* prefix (Slack/Notion idiom)​

Use "Workspace" as the prefix, following the Slack/Notion pattern where Workspace is the customer-facing tenant noun.

Why not chosen: Workspace is industry-recognizable and would feel natural for users moving from Slack/Notion, but it conflates the technical tenant isolation boundary with the intra-tenant working area (which the user explicitly named as a separate future entity, per D3). Adopting Workspace at the tenant-isolation level would force the future intra-KE working-area entity to take another name and would carry the same long-run scalability problem as Option B. Workspace is reserved for the intra-KE level (D3), not promoted to the tenant level.

Option E (chosen alongside Option A) — Auth0 two-axis vocabulary​

Keep "Tenant" as a class name only on the TenantMixin subclass (today: customers.Client); use KnowledgeEnvironment as the customer-facing entity name; use Institution / Organization for future grouping; use Workspace for future intra-KE working areas. Domain models stay un-prefixed.

Why chosen (in combination with Option A): this is the Auth0 precedent (§ "Auth0 two-axis pattern"). It cleanly decouples the technical-isolation axis from the customer-hierarchy axis. The platform already partially follows it (customers.Client is a customer-facing word; the customers app is the carrier). Extending it forward gives the platform room for institution-level federation, intra-KE workspaces, and cross-tenant staff layers without renaming again.

The chosen decision is Option A + Option E together: drop Tenant* on domain models (A); reserve the customer-hierarchy vocabulary so that future entities have somewhere to land (E).

Consequences​

Positive​

  • Idiomatic Django. Aligns with django-tenants' own example projects, HackSoft styleguide, and the general Django anti-prefix posture.
  • Future customer-hierarchy vocabulary survives unmangled. KnowledgeEnvironment, Institution / Organization, Workspace each get their own names without colliding with a Tenant* prefix.
  • CI-enforced layer boundaries. The import-linter contract (D5) plus runtime boundary enforcement (D6: Django system check + star-import audit) is stronger than the prefix it replaces. Static + signal-graph layer violations fail the build instead of relying on reviewer vigilance.
  • Aligns with the Auth0 / Slack / Notion two-axis pattern. Reviewers and contributors from those ecosystems find the convention immediately recognizable.
  • GenericForeignKey footgun more visible. Contenttypes-based GFKs that cross the layer boundary now require cross-app imports, surfacing the dangerous pattern at the import site.
  • Resolves the PR #365 asymmetry. PlatformVocabularyEntry / TenantSlotPreset / UngroundedVocabularyValue rename to a single consistent convention. The Tier-1/2/3 ladder no longer reads as three different naming schools.

Negative​

  • Rename has non-trivial blast radius. Every import, every migration history reference, every doc/devlog reference, every URL pattern that mentions a model by name will need updates. The change itself is mechanical (git grep driven, name-by-name), but the surface is large.
  • Grep-ability is mildly degraded. grep TenantOntology is currently a one-step lookup; after the rename, locating "the tenant-side ontology model" is grep -r 'class Ontology' epistemic/ or an IDE Go-to-Symbol. Minor friction.
  • Migration history references the old names forever. Django migrations recorded against the old class names remain in migrations/ directories; the rename is via Meta.db_table preservation + RenameModel operations. Migration files are not retroactively updated. New contributors reading old migration files will see TenantOntology and PlatformVocabularyEntry historically; that is fine.
  • Devlogs and ADRs reference the old names. Existing devlogs, ADR-004 / ADR-012 / ADR-017 / ADR-037 / ADR-038, and the brainstorm files all reference the old names. The rename sprint does not rewrite history in those documents — they are dated artifacts. New documents from the rename sprint forward use the new names.

Migration plan (out of scope here — pointers only)​

The rename itself is a separate sprint; this ADR does not propose a timeline. Pointers the rename sprint will need:

  • Enumerate touch points via git grep -l 'Tenant[A-Z]' and git grep -l 'Platform[A-Z]' and batch by app.
  • Use RenameModel migrations with explicit db_table preservation to avoid table renames at the SQL layer (data does not move; only Python identifiers change). For Phase A.1's PR #365 models, this is the critical mechanic — the underlying tables stay put.
  • Ship the import-linter contract (D5) plus the D6.1 runtime augmentations (star-import audit + Django system check) in the same sprint, so the rename's positive consequence lands at the same time as the rename's mechanical work. D6.2 (GraphQL schema diff) waits for the trigger in §D6.
  • Spec 0022's new fields and models adopt the new naming directly (per D8) so the rename sprint does not have to rename them a second time.

Coordination with existing lints​

  • scripts/lint_no_tenant_vocabulary.py checks for tenant vocabulary leaks (cardiovascular, Aristotle, etc.) into platform code. It is orthogonal to model naming. The rename does not change this lint and the lint does not enforce the rename. Both continue to operate independently.
  • The new import-linter contract (D5) is the lint that takes over the layer-boundary enforcement that the Tenant* prefix used to gesture at.

Out of scope for this ADR​

  • The rename sprint timeline and per-model order.
  • Specific import-linter contract syntax.
  • The rename of customers.Client → KnowledgeEnvironment (or any product-language alignment of the TenantMixin subclass itself). Flagged as a candidate for a future product-language-alignment ADR.
  • Promotion of Spec 0022's new models to the new convention — the spec author should adopt D8's naming directly during authoring.
