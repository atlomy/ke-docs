What surfaced in Round-16 absorption​

Audio open critique (eeb04c8f-b718-435f-b484-b1c43cc2ec36, "Hardening brittle bindings and claim clusters") surfaced four concerns. All four verified with primary evidence; all four accepted as amendments (one twice — see C1):

  2. C2: Walk-derived claims are emergent from attestation_walk; novel researcher propositions that synthesize across artifact-types (TEI passage + 3D mesh + IIIF region together) cannot be walk-inferred. Storage required. Fix: ClaimCluster thin junction primitive in v1.

Decision​

Part A — Platform principle: media is a catalogued research artifact + new primitives + extension of attestation_walk​

Media is a research output and process, not an attachment. The architecture commits to media as a catalogued, citable, shareable research output in the broader scholarly ecosystem — may have its own DOI (via DataCite), Zotero entry, institutional handle. Each addressable subdivision (mesh, region, element, timecode) may be independently citable.

A.1 — Three new platform primitives

  • Anchor — addressable region/segment inside an artifact. Cross-source-type. Replaces the implicit anchor-fused-into-edge metadata pattern. New table. Uniqueness invariant (Codex review): (tenant_id, source_type, external_locator) is unique per Anchor row; cross-tenant duplicates allowed (the same shared artifact node can be anchored independently by multiple tenants per A.6). Lookup-by-locator is exact-match on this triple.
  • ArtifactVersion — Hybrid Revision/Edition (see A.5). New table.
  • ClaimCluster + ClaimClusterMember — thin junction-table primitives holding refs to multiple Attestations (not raw Anchors) across distinct Anchor source-types, with researcher provenance. ClaimClusterMember.attestation FKs to the Attestation primitive; in v1, the Attestation primitive is EntityRelationship rows whose rule_name is one of the configured attestation_walk rule_names + metadata.anchor_durable_id pointing at the Anchor. A future ADR may introduce a dedicated Attestation table; until then, the junction stays at the EntityRelationship layer. Stores novel researcher propositions that walks cannot synthesize. New tables; authoring UI deferred to Phase 5.

Attestation is NOT new — it reuses ADR-020's existing attestation_walk primitive. ADR-022 extends attestation_walk to media as a source-type alongside PASSAGE/DOCUMENT/GIS/lab-report/AV/TEI. Concrete v1 mapping: an Attestation IS an EntityRelationship row whose rule_name is one of the configured attestation_walk rule_names; ADR-022 adds metadata.anchor_durable_id to thread the Anchor reference through. ClaimClusterMember semantics: "Claim X is built from Attestation Y (which itself binds Anchor Z to research entity R)" — three-level chain, not two.

A.2 — Media as a source-type for ADR-020 attestation_walk

ADR-020 §B committed attestation_walk as the platform-canonical anchor → occurrence → paired-editions pattern across Classics / Archaeology / Biodiversity / Numismatics / Textual criticism / Paleography / Botanical / Construction history. That commitment was only fleshed out for textual sources (PASSAGE/DOCUMENT). ADR-022 extends it to media:

The unifying frame: every source-type produces Anchors; Anchors carry Attestations (per ADR-020) of research-substrate concepts; Claims aggregate Attestations either by walk-derivation (ADR-020 §A platform-canonical-projection-principle) or by explicit ClaimCluster storage (A.1 above) when the proposition is novel.

Whether to retroactively split PASSAGE into Anchor + Attestation is its own question — NO in v1 (PASSAGE is settled; minimum viable change).

A.3 — Anchor selector vocabulary (W3C SpecificResource shape; initial supported subset in ADR-022)

The Anchor table fields are platform-canonical (artifact_id, version_id, archetype_binding, durable_id, human_label, source_type). The selector field stores a W3C SpecificResource shape as JSONB.

ADR-022 includes the initial supported subset of W3C SpecificResource selector kinds (Round-16 C3 fold-in eliminates cross-ADR blocking ratification dependency; Codex-amended: "FULL canonical selector vocabulary" was overstated — the W3C Web Annotation Data Model also defines CssSelector, XPathSelector, TextPositionSelector, and RangeSelector not yet in scope for v1):

  • FragmentSelector — RFC 3987 IRI fragment. Used for glTF (#node=καρδία or #node-path=/scenes/0/nodes/3), IIIF (#xywh=100,200,400,300), AV. Note (Codex): Media Fragments URI is normally represented as FragmentSelector + conformsTo: http://www.w3.org/TR/media-frags/, not as a separate MediaFragmentSelector kind. ADR-022 v1 keeps both for clarity but production implementations should prefer the FragmentSelector + conformsTo form.
  • SvgSelector — non-rectangular regions defined by SVG path.
  • MediaFragmentSelector — W3C Media Fragments URI 1.0 (temporal + spatial). Equivalent to FragmentSelector + conformsTo.
  • TextQuoteSelector — exact-text-with-prefix-and-suffix (for textual anchor cases that PASSAGE doesn't already cover).
  • DataPositionSelector — raw byte ranges (binary media where structure is byte-offset addressable).

Other W3C selectors deferred (add when first tenant exercises them): CssSelector, XPathSelector, TextPositionSelector, RangeSelector. No Atlomy-specific selector extension is needed in v1 — the artifact's natural self-description (per A.4 below) IS the selector value. Custom Atlomy selector kinds are deferred until / unless empirical need surfaces (Round-15 V2 calibration: ratify principles whose value is empirically proven).

A.4 — Three-layer identity model (platform never writes to artifacts)

Round-16 user-sharpened C1: a media artifact is a catalogued, citable, shareable research output. The platform must NEVER write platform-internal data into the artifact, because:

  • Citation surface pollution: anyone downloading the file sees our internal Anchor.durable_id UUIDs in extras
  • Cross-platform identity conflict: when a re-catalogued artifact arrives at another KE-platform tenant (or back into the originating tenant via Zotero/DOI re-registration), embedded UUIDs from our previous instance create confusion
  • Sensitive-data leak: tenant-internal identifiers traveling with the artifact across institutional boundaries
  • Coupling: the artifact becomes platform-instance-coupled rather than standing on its own as a research output

The architecture commits to strict three-layer identity:

Layer 1 — External / publishable identity (canonical for citation; authored/owned by Layer 1 actors only):

  • Artifact has stable external identifier — DOI (via DataCite, future ADR-023) / Zotero key / institutional handle / platform-minted handle for new artifacts created in a tenant.
  • Parts addressable via the artifact's natural self-description (modeler/editor-authored, part of the file's own author content):
    • glTF: scene-graph node path or node name (modeler chooses)
    • IIIF: canvas URI + W3C region selector (durable by IIIF spec)
    • TEI: @xml:id (durable by TEI convention)
    • AV: t=start,end Media Fragment URI + optional cue ID (durable by W3C Media Fragments spec)
    • GIS: geometry literal + SRS
    • Tabular: row PK + column name
  • Citations point at Layer 1: <artifact_external_id>#<part_locator>. W3C Web Annotation SpecificResource serializes this for cross-platform interop.

Layer 2 — Platform-internal identity (canonical for foreign keys; never published):

  • Anchor.durable_id — UUID, foreign-key target for Attestation.anchor_id, ClaimClusterMember.attestation_id (transitively), etc.
  • NEVER appears in any artifact, export, IIIF manifest, RO-Crate package, or any published surface. Strictly internal to the platform's relational graph.

Layer 3 — Locator (binding Layer 1 ↔ Layer 2):

  • Anchor.external_locator JSONB shape: { "artifact_external_id": "<doi|zotero|handle|platform-minted-handle>", "in_artifact_path": "<source-type-natural-locator>" }
  • On re-ingest, the platform reads the file's own self-description, computes the (external_id, in_artifact_path) tuple, and looks up the Anchor row by external_locator. NO stamping. NO cache. NO writes.

Concrete consequences:

  • Renames create researcher-review surface events, not silent re-binding. If the modeler renames a node, the previous tuple no longer resolves on re-ingest and the new tuple is new. Platform surfaces this with heuristic match-confidence (scene-graph position + mesh vertex count + sibling-ordering signals) for researcher decision. Aligned with W3C Web Annotation + IIIF + TEI + AV's existing patterns; the glTF source-type joins those already-durable conventions.
  • Cross-tenant shared assets work without conflict: each tenant has its own Anchor rows referencing the same (artifact_external_id, in_artifact_path) tuple. No platform writes = no overwrite race.
  • Coupling with ADR-023: Layer 1 identifiers are exactly what ADR-023 (Publication & Persistent IDs) is about. ADR-022 declares "external_locator references Layer 1" without prescribing the scheme; ADR-023 prescribes the scheme for platform-minted vs externally-sourced artifacts. Not circular — clean dependency.

Trade-off accepted: renames have scholarly cost regardless of platform binding (citations from other scholars break too); making them visible at the platform layer is appropriate, not regression. Modeler discipline encouraged: rename only when scholarly intent supports it; treat node names as part of the published vocabulary.

A.4.1 — MEDIA EpistemicEntity surfacing the canonical External ID (amendment 2026-05-16)

Atlas day-1 surfaced a gap in §A.4 as written: §A.4 declares that Anchor.external_locator.artifact_external_id is the Layer 1 identifier, but Plan 5 (3D viewer SPA un-stub) needs the same identifier addressable via the MEDIA EpistemicEntity itself — so SPA URL→entity lookups, the media review surface, and any future Layer-1-keyed query can resolve (tenant, artifact_external_id) to a MEDIA entity without joining through Anchor + ArtifactVersion. The runtime atlas backfill that solved this for atlas day-1 was undocumented; Plan 6 (2nd-tenant validation) needed a platform-canonical contract.

This amendment formalizes the contract:

  • Slot name is platform-canonical: tenants who want their MEDIA entity to surface the artifact's Layer 1 identifier declare a slot named external_id in TenantArchetypeFormConfig(archetype="MEDIA"). The slot_name "external_id" is the platform's canonical name; the slot's source_field (the JSONB key path on EpistemicEntity.data where the value lives) is per-tenant and freely chosen.
  • Path constraint: source_field must be a top-level data.<key> reference. Deeper paths (data.handles[0].value, data.foo.bar) are rejected at write time. Tenants who need richer shapes declare a single canonical key for their Layer 1 identifier.
  • Idempotent ladder on writes: when any platform code seeds the slot for a MEDIA entity, the contract is: empty/missing slot → write the supplied artifact_external_id; slot already equals the supplied value → no-op; slot differs → refuse with a researcher-conflict error. Never silently overwrites a researcher-set value.
  • Optional contract: tenants who do not declare the external_id slot opt out of Layer-1-on-MEDIA entirely. The slot's absence is interpreted as "this tenant has not yet onboarded the contract" (quiet no-op for the helper); Layer-1 lookups must then go through Anchor.external_locator directly, as they did pre-amendment.

Implementation surfaces (citations for cross-reference):

  • Platform-canonical helper: epistemic.services.media.external_id.ensure_media_canonical_external_id (idempotent ladder; raises CanonicalExternalIdError on conflict, decoupled from Django's CommandError so future GraphQL mutations / async jobs can use it without depending on management-command exceptions).
  • Ingest-time enforcement: atlomyapp.management.commands.ingest_3d_model_glb._apply_edges calls the helper for every supplied --artifact-external-id. Existing call site preserved via a thin backward-compat wrapper that translates CanonicalExternalIdError → CommandError.
  • Tenant-onboarding command: atlomyapp.management.commands.seed_media_external_id wraps the same helper for one-off and bulk-from-source seeding (REPORT mode default; --apply writes; bulk mode continues past per-row conflicts and exits non-zero at end). Plan 6 onboarding contract.
  • Test substrate: tests/integration/test_seed_media_external_id_command.py (9 tests covering explicit/bulk × write/REPORT/conflict + arg validation) and tests/integration/test_ingest_seeds_canonical_external_id.py (6 tests covering the ingest-time enforcement). All 15 pass against the same shared helper.

The contract is additive — it does not change Anchor.external_locator semantics or how Layer 1 identifiers reach Layer 3 selectors. It documents and standardizes a per-MEDIA mirror of the same identifier the locator already references, so consumers needing entity-keyed lookup don't have to construct ad-hoc joins.

A.5 — ArtifactVersion: Hybrid Revision/Edition

Two-tier model:

  • Revision — every upload creates an internal Revision (mutable working state).
  • Edition — researcher marks a Revision as an Edition (frozen, citable, peer-review-targetable, DOI-mintable).

Atlas day-1 ignores Editions (1 model, no peer-review yet); the model accommodates that without retrofitting later. Aligns with DataCite version semantics + Output 2's "freeze when entering review" pattern. DOI minting policy (per-Edition vs per-Revision vs designated checkpoints only) deferred to ADR-023.

A.6 — Tenancy-agnostic table discipline

Every new media table (Anchor, ArtifactVersion, ClaimCluster, ClaimClusterMember) carries explicit tenant_id FK from day one, even though under schema-per-tenant the schema name redundantly encodes that. Forward-compat for ADR-026's tenancy-strategy decision (schema-per-tenant vs row-level vs hybrid at thousand-tenant scale). Cheap insurance; expensive to retrofit if scale lands first.

Part B — Embedded-convention extractor framework (Proposed pending 2nd-tenant validation)​

Adopt a platform-shipped extractor framework that runs tenant-declared parsers against media internal structure. Framework runs in two phases:

  1. Internal-structure walker (platform primitive): gltf_node_names, iiif_canvas_annotations, tei_xml_corresp, darwin_core_metadata. Each ships a single function: media artifact → list of structured items.
  2. Convention parser (platform primitive): delimited_split (with fallback_lookup_fields per-tenant config support), regex_capture, xml_attribute_lookup, key_path_extract. Tenants declare which parser + how, in their config.

Parsed bindings get materialized to:

  • Anchor rows (with Layer 3 external_locator pointing at the artifact's natural self-description)
  • Attestation rows (linking Anchor to research-substrate entities via attestation_walk per ADR-020)

via a single platform mgmt command (idempotent; REPORT/APPLY modes following the backfill_entity_identity_ledger pattern from ADR-017 Phase 2.B).

§B status: Proposed pending non-classics 2nd-tenant validation. §B has sample-size = 1 (the dev-tenant GLB convention) until at least one extractor for a different source type (likely IIIF or TEI) lands in any other tenant. Per Round-15 V2 calibration, locking §B as Approved without validation repeats the ADR-020 §B premature-codification risk Round-15 stress-tested. Promote §B → Approved after Phase 7 (2nd-tenant validation).

Researcher UX layer (unchanged from ADR-021): overrides, not primary editor​

The legacy ModelMapping admin tab put researchers in the role of primary editor; that fights the workflow because the modeler edits the GLB in Blender and manual mappings drift.

ADR-022 reframes researchers as reviewers / overriders:

  • Bulk view: "MEDIA Aristotle Respiratory System has 25 Anchors with Attestations; 22 mapped to existing TERMs; 3 unmapped (lemma not in DB or spelling variant)."
  • Per-edge review: approve / strip / amend the extractor's proposed Attestation; researcher's action recorded as metadata.researcher_override = true with timestamp + actor.
  • Manual add: researcher can add an Attestation that the extractor missed, recorded as metadata.source = 'researcher_manual'.
  • Re-run extraction: when the modeler updates the artifact (new Revision), re-run the ingestion command; researcher overrides persist (materialization rule preserves any Attestation with researcher_override=true); auto-extracted Attestations are refreshed.
  • ClaimCluster authoring (Phase 5): researchers can author novel cross-artifact-type propositions referencing multiple Attestations.

Same pattern AI-in-the-loop work uses (status: AI_PROPOSED → HUMAN_REVIEW → APPROVED). Extractor-proposed Attestations + AI-proposed Attestations + researcher-manual Attestations flow through the same review surface.

Consequences​

Positive:

  • Media is a first-class catalogued artifact. Researchers gain a workflow that respects the artifact's research-output nature; citations, DOIs, and cross-platform sharing work natively.
  • Three-layer identity makes the platform a clean reader, not a writer. Files are read-only from the platform's perspective; no sensitive-data leak; no cross-platform identity conflicts; aligned with how W3C Web Annotation + IIIF + TEI + AV already operate.
  • Cross-tenant generalization. A prosopography tenant declares a TEI extractor; a manuscript-imaging tenant declares an IIIF extractor; a biology tenant declares a Darwin Core extractor; all share the same framework + Anchor + Attestation primitives + UX. Each declares its convention via tenant config; platform code carries no tenant-specific names.
  • AI-in-the-loop convergence. Extractor-proposed and AI-proposed Attestations flow through the same review surface; researcher review discipline accumulates across both.
  • ClaimCluster supports novel scholarly propositions. Researchers can assert claims spanning multiple artifact-types that walks cannot generate.
  • ADR-020 attestation_walk principle generalizes. Media joins textual sources as a first-class source-type for the cross-discipline pattern.

Trade-offs:

  • Schema is larger than ADR-021 framed. Three new tables (Anchor, ArtifactVersion, ClaimCluster) + ClaimClusterMember junction + extension of attestation_walk to media. Comparable to ADR-017 Phase 2.B's ledger investment.
  • Renames create researcher-review events instead of "transparent UUID survival." Trade accepted because renames have scholarly cost regardless of platform binding; surfacing them is appropriate.
  • §B sample-size = 1 until Phase 7. §B specifics may need revision based on 2nd-tenant validation; status stays Proposed.
  • 3D viewer placeholder persists for full sprint duration (~6+ weeks) in the case-study tenant where the viewer is currently stubbed. Acceptable per Build context preamble: this is a dev environment, not production; the placeholder is "internal dev placeholder during build," not "user-facing regression in production."

Honest constraint (per ADR-020 §B's Round-15 calibration):

§B has sample size = 1 (the case-study tenant's GLB) for the embedded-convention extractor specifics. Keep §B in Proposed status until at least one extractor for a different tenant + different source type lands (Phase 7).

Phasing​

Bottom-up sequence; substrate first, viewer last. Architectural correctness preferred over fast user-facing wins.

  1. Phase 0 — case-study tenant's GLB ingestion as reference implementation (SHIPPED, commit d539764b; tenant-scoped code at atlomyapp/services/glb_lemma_extractor.py)
    • Tenant-scoped seed in atlomyapp/; gets refactored or deleted as Phase 3 framework lands.
  2. Phase 1 — MEDIA archetype slot config + admin overlay (deployed first in the case-study tenant that has media; ports to other tenants as they onboard media)
  3. Phase 2 — Anchor table + ClaimCluster table + full W3C SpecificResource selector vocabulary inline + external-locator-only binding policy (read-only from platform's perspective; no stamping mgmt cmd; researcher-review surface for rename reconciliation; tenant-scoped Anchor rows per A.6)
  4. Phase 3 — Extractor framework: internal-structure walkers + convention parsers (with fallback_lookup_fields support) + materialization mgmt (REPORT/APPLY); regression test for the case-study tenant's documented asymmetric-variant case (design discipline; Phase 0 retirement happens here as normal codebase evolution)
  5. Phase 4 — ArtifactVersion (Revision/Edition split) + version-aware extractor re-run preserving researcher overrides
  6. Phase 5 — Researcher review UX (bulk view, per-edge approve/strip/amend, manual add, re-run extraction, ClaimCluster authoring)
  7. Phase 6 — 3D viewer un-stub (and parallel image/AV/TEI viewer consumers as Anchor consumers)
  8. Phase 7 — Second-tenant validation. Pre-condition: a non-classics-anatomy tenant must first onboard at least one media artifact (currently MEDIA=0 in both tabular-importer dev tenants per Build context's live-DB probe table). Likely paths: a manuscript-imaging tenant uploads an IIIF manifest; a prosopography tenant uploads a TEI document; OR another tenant onboards with media as their primary substrate. The choice is contingent on which onboarding happens first. On successful validation (extractor framework produces equivalent Anchor + Attestation output for the new tenant's media as it does for the classics-anatomy seed), promote §B Proposed → Approved.

Alternatives considered​

Alternative A — Build a researcher-facing admin tab to hand-edit TERM↔MEDIA edges​

Rejected — re-creates the legacy ModelMapping desync problem. Modeler edits GLB in Blender; admin-tab edges drift.

Alternative B — Build the 3D viewer first against existing schema; defer media architecture​

Rejected — the existing schema is under-specified (zero MEDIA slot config). Building viewer first commits to a data shape before validation. Round-15 V1 stress-tested this exact pattern.

Alternative C — Keep ModelMapping table, port to v2​

Rejected — ModelMapping was retired in ADR-019 Phase 4 because it conflated operational truth (Lemma table dropped on re-import) with epistemic interpretation (lemma↔mesh as a research claim).

Alternative D — Stamp UUIDs into glTF extras as canonical identity​

Rejected (Round-16 C1 + user-sharpening) — embedding platform-internal UUIDs into a catalogued, citable, shareable artifact is a sensitive-data leak that pollutes the citation surface and creates cross-platform identity confusion. Three-layer model with no platform writes is the architectural answer.

Alternative E — Defer Claim primitive entirely to a future ADR​

Rejected (Round-16 C2) — researchers' novel cross-artifact-type propositions cannot be walk-inferred. Substrate cost (one junction table) is small; retrofitting after Phase 5 ships review UX would be expensive. Ship ClaimCluster schema in v1; defer authoring UI to Phase 5.

Alternative F — Peel W3C selector vocabulary out as standalone ADR-024​

Rejected (Round-16 C3) — selector vocabulary is intrinsic to the Anchor table; splitting creates blocking ratification dependency. Folded into ADR-022 §A.3; ADR-024 rescoped to UI/integration only.

Alternative G — Production-grade atomic switchover for Phase 0 retirement​

Rejected (Round-16 C4 user-reframe) — greenfield-dev work; no production transition exists. Phase 0 retirement is normal codebase evolution; design discipline + regression test only.

Open questions​

  1. 2nd-tenant validation timing — which non-classics-anatomy tenant onboards a media artifact first (e.g., IIIF manuscript image, TEI document, AV recording, GIS layer)? Implication: shapes which extractor primitives are in flight first. Roadmap signal needed.
  2. Source sync UI integration — does media re-ingestion plug into the existing /app/admin/source-sync/ (commit ded020f5) umbrella surface, or get a dedicated workspace? Tentative: keep umbrella with source-type tabs.
  3. Build-vs-Buy specifics — for each viewer family the platform commits to (3D, IIIF, TEI, AV), what's the canonical library? Tentative (from research convergence): Three.js (3D, current); Mirador + OpenSeadragon + Annotorious (IIIF); CETEIcean / EVT (TEI); HTML5 + wavesurfer.js + Video.js (AV). Belongs in ADR-024.
  4. Researcher override conflict resolution on re-run — when re-extraction proposes an Anchor that the researcher previously stripped, does the system silently re-strip, surface for re-review, or refuse to overwrite? Opinion: surface for re-review with a "reaffirm strip" button; never silently overwrite human intent.
  5. MEDIA file storage substrate — inline binary (impractical for 70MB GLB), filesystem-mounted (current ad-hoc atlomy_3d_assets/), or S3-backed? Production: S3-class durability. Dev: filesystem. Switch by environment.
  6. Tenant onboarding playbook — documentation, not architecture; ship after Phase 7 (2nd-tenant validation).

Phase 0 reference implementation — shipped 2026-05-08​

Tenant-scoped to the case-study tenant for 3D anatomical models (code path: atlomyapp/):

  • atlomyapp/services/glb_lemma_extractor.py — pure-Python parser for the tenant's <Greek lemma>;/<transliteration>/;<English gloss>;text GLB node convention. Returns normalized BindingCandidate objects.
  • atlomyapp/management/commands/ingest_3d_model_glb.py — REPORT / APPLY cmd. REPORT shows which lemmas resolve, which fall back via the tenant-declared alternative-spelling rule, which are unmapped. APPLY creates EntityRelationship(rule_name='three_d_model') edges with provenance metadata.
  • tests/integration/test_glb_lemma_ingest.py — 20 tests (15 parser + 5 structural). All passing.

Phase 0 explicitly does NOT generalize. It exists as a dev seed reference. When Phase 3 lands the platform extractor framework, Phase 0's parser logic moves into the platform delimited_split parser (with fallback_lookup_fields declared in the tenant's config), and Phase 0's tenant-scoped code in atlomyapp/services/ gets refactored or deleted in the same PR.

Phase 0 edges in the case-study tenant's dev DB (Codex live-DB-probe-corrected): EntityRelationship(rule_name='three_d_model') shows 21 rows (not 18 as stated in the original Phase 0 devlog — additional manually-added or experimental edges accumulated). 20 of 21 carry metadata.glb_node_name; 1 has empty metadata (legacy or hand-created edge). None carry file_hash in metadata — the original ADR-022 claim "(file_hash, glb_node_name) IS the Layer 3 shape" was overspecified; only glb_node_name is present. Additionally, sampled EntityRelationship.tenant_id is None (the schema-per-tenant model encodes tenancy via schema name, not column).

Migration is ADDITIVE not destructive (Codex-amended; "no migration needed" was incorrect — the rows DO need an Anchor row backfilled per edge):

  • For each of the 20 edges with glb_node_name: create one Anchor row with external_locator = {artifact_external_id: <supplied at migration time>, in_artifact_path: <glb_node_name>}; update the edge's metadata with anchor_durable_id.
  • The 1 edge with empty metadata: report (do not silently drop); fail-closed unless an explicit --include-orphan-edges flag is passed.
  • tenant_id derivation: pull from the active connection.schema_name (django-tenants schema context), not from edge.tenant_id which is None.

Plan 1 Task 6 implements the migration with REPORT/APPLY modes; the regression discipline asserts: post-migration, every three_d_model edge with glb_node_name has a corresponding Anchor row with the correct external_locator and selector.
