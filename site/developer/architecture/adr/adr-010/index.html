ADR-010 — Parser-First, LLM-Second for Relationship Resolution

Status: Proposed Date: 2026-04-30 Branch: experiment/v2-anchor-and-seamless-edit Supersedes: parts of ADR-008's free-form composition_rules; tightens ADR-009's relationship widget proposal Related: ADR-002 (Hybrid Ontology), ADR-004 (Tenant Ontology Mapping), prior-art-survey P2 trichotomy + Section 1 of comments-and-suggestions-2026-04-29.md

Context​

When a tenant's slot is a relationship — attestations, literature, synonyms, related_terms — the platform must know how to resolve the linked records. Two failure modes the critique audios surfaced:

  1. AI-only resolution: LLM proposes joins from raw schema with no deterministic anchoring; produces plausible-looking but incorrect joins; humans rubber-stamp.
  2. JSONB-blob resolution: relationship payload shoved into a JSONB column or _raw extension dict at materialization time; structure becomes invisible to query planner, AI, and operators.

Both fail because they collapse the evidence layer into the interpretation layer. The platform-principles doctrine is the opposite: structure is shared; interpretation is tenant-specific.

Decision​

Relationship resolution proceeds in three strictly-ordered passes:

Pass 1 — Parser (deterministic)​

Walks the tenant's actual storage (Postgres schema, Elasticsearch index, etc.) and produces machine-verifiable evidence:

  • Real Django/Postgres FKs → fk_walk candidates with confidence 1.0.
  • Value-overlap analysis: column X on table A vs column Y on table B, sampled, with confidence = overlap ratio.
  • Field-name fingerprints (e.g., *_id columns).
  • Schema introspection: column types, nullability, indexed-ness.

Scope discipline: parser runs at slot-config-time only, not on every read. Not the full SourceSchemaGraph N² pre-pass — narrowed to candidate joins for declared relationship slots.

Pass 2 — LLM (semantic, gated)​

Runs ONLY where the parser is uncertain. Inputs:

  • Parser-produced candidates with confidence scores
  • Tenant ontology context (display labels, archetype contracts)
  • Existing TenantArchetypeFormConfig rows for similar slots in other tenants

Output: proposed resolver_kind + resolver_args for each unresolved slot.

LLM cannot invent a join the parser didn't surface evidence for. If parser confidence is below threshold and LLM has no candidate, the slot stays unresolved and surfaces in the schema-review queue.

Pass 3 — Human approval​

Reviewer approves the proposal. From this point, a TenantArchetypeFormConfig row exists; the resolver runs deterministically per request. No LLM in the read path, ever.

Resolver dispatch (runtime)​

A thin Python module takes a TenantArchetypeFormConfig row and resolves the relationship by resolver_kind:

  • fk_walk → ORM instance.<related_name>.all()
  • string_match → indexed equality query against the target table/index
  • composed → call a named pure-function from the epistemic.resolvers registry

No code path executes a relationship without a config row that declared how.

Schema additions​

TenantArchetypeFormConfig gains three columns (migration 0048_form_config_resolver_fields.py):

ColumnTypePurpose
source_layerenum: model / epistemic_entitiesWhich storage layer holds the slot's data. Default model.
resolver_kindenum: direct / fk_walk / string_match / composedHow the resolver fetches related rows. Default direct (= not a relationship).
resolver_argsJSONB (small)Pure parameters for the resolver. Schema depends on resolver_kind.

resolver_args is intentionally JSONB but kept small — it stores parameters, not structural data. source_field, target_archetype, etc. stay as relational columns.

Why no es_index / search_engine source_layer​

An earlier draft of this ADR included a third es_index source layer, justified as "reuses v1 ATLOMY's lemma_index indexer." It was removed before this version because:

  • Each tenant's ES index requires its own indexer (the v1 ATLOMY indexer is 551 lines of ATLOMY-specific join logic on the ai-mapping branch). That re-introduces the per-tenant code antipattern this architecture exists to prevent.
  • ES is not the only search engine, and the cloud-vendor / licensing landscape has shifted (AWS-Elasticsearch fork → OpenSearch). Hard-binding detail-page rendering to ES creates a rebuild risk that doesn't exist if the read path is Postgres-direct.
  • "Detail-page rendering" and "search/discovery" are different needs that v1 happened to solve with one tool; the platform shouldn't conflate them.

Detail-page rendering goes through the resolver dispatcher against Postgres. Search and discovery (full-text, faceted, federation) is a separate later ADR that will pick a search engine (OpenSearch / Postgres FTS / Typesense / Meilisearch) based on benchmarks against Postgres-direct performance. Until that ADR lands, we deliberately don't have a search-engine binding in the slot config.

What this is NOT​

  • Not a runtime LLM call. Once configured, resolution is pure code.
  • Not an LLM-only pipeline. Parser must always run first.
  • Not a return of the _raw antipattern. resolver_args is parameters; tenant data stays in typed columns.
  • Not a replacement for ADR-006 archetype contracts. Contracts say what slots an archetype has; this ADR says how a tenant's slot is resolved.

Consequences​

Wins:

  • AI proposals are bounded by parser evidence — no hallucinated joins.
  • Read path stays deterministic and indexable.
  • Resolution declared as data → diffable, queryable, AI-readable, operator-editable.
  • Cross-tenant pattern reuse: a string_match resolver written once works for any tenant whose slot config declares it.

Costs:

  • Parser implementation (FK introspection, value-overlap sampling) is real work. Deferred from this ADR; lives in the epistemic.parser module to be built in subsequent work.
  • Adds 3 columns to TenantArchetypeFormConfig. Small.

Implementation phases​

  1. ✅ Schema landed (this ADR + migration 0048).
  2. Implement resolver dispatch for fk_walk (one ATLOMY relationship as proof — Lemma ← ModelLemma → Model).
  3. Implement string_match against Postgres tables (not ES) for attestations and literature — using the ai-mapping module (data_import/ai_mapping.py, the generalized successor to the original per-tenant join file) as the reference document for which fields to match, but executing the joins as universal-dispatcher Postgres queries with appropriate B-tree indexes on the soft-FK string columns.
  4. Implement composed resolver registry — start with ATLOMY's citation-rendering function ({Author}, {Treatise}, p. {Page} (Bekker {bekker})). Each function is pure, named, parametrized via resolver_args. Reusable across tenants whose citations follow similar shapes.
  5. Implement parser pass (FK introspection + value-overlap) and LLM proposal step. Together these become the new-tenant onboarding flow.
  6. Deprecate ADR-008's composition_rules in favor of resolver_kind=composed + registry function.

Out of scope (separate later ADR): search engine choice, full-text search, cross-tenant federation. These join the roadmap once Postgres-direct performance becomes the actual bottleneck — measured, not assumed.

Open questions​

  • Where does the resolver registry live? Proposed: epistemic/resolvers/__init__.py with named functions; per-tenant resolvers in epistemic/resolvers/<tenant>/....
  • Does the parser run on a schedule or on-demand at tenant-onboarding? Proposed: on-demand; cached.
  • How do we version resolver_args schema per resolver_kind? Proposed: validate on write via Pydantic models in code; store the model name in resolver_args._kind.

These are tractable design questions for the implementation phase, not blockers.

§A — 2026-05-07 amendments (Codex review of MappingProposal pipeline)​

This amendment section absorbs corrections + extensions surfaced by Codex review on 2026-05-07. Pattern follows ADR-016's R-N absorption amendments discipline — the original Decision section above is unchanged; this section captures the implementation correction and the LABEL-kind extension. Both fit ADR-010's existing parser-first/LLM-second/human-approval pattern; neither warranted a new ADR.

A.1 — Implementation correction: one MappingProposal per finding​

Symptom found by Codex review: builder at epistemic/services/proposals/builder.py:117-161 loops for arche in all_archetype_candidates for an ambiguous table, calling try_llm_refinement once per candidate. Each call produces a separate ProposalRow with the same target_ref={"table": <name>}. Persistence at epistemic/services/proposals/persistence.py:52-62 then post-hoc dedupes by keeping highest-confidence — discarding the other LLM analyses.

For an ambiguous table with 3 archetype candidates: 3 LLM calls fire, 3 ProposalRow objects created, persistence keeps 1, 2 LLM analyses are discarded. Wasteful; conceptually muddy (the dedupe masks a builder bug).

Why this is a deviation, not a new decision: ADR-010 commits to "parser surfaces findings; LLM refines low-confidence findings; one finding = one decision = one persisted proposal with audit trail." A finding in the archetype-decision case is "this table needs an archetype assignment" — ONE finding per table, with the candidates as alternatives within it. The builder's per-candidate loop produced N proposals for ONE finding. The dedupe is the symptom; the loop is the cause.

Correction (implementation, not architectural change):

  • Builder emits ONE ARCHETYPE proposal per table (per finding).
  • parser_payload shape changes from a single ArchetypeCandidate dict to {"candidates": [<ArchetypeCandidate>, ...], "preferred": <ArchetypeCandidate>} carrying all candidates.
  • try_llm_refinement is called ONCE per finding with the full candidate list as context. The LLM picks (or stays null), informed by the full sibling set.
  • Persistence-layer dedupe stays as defensive belt-and-suspenders, but is no longer triggered in steady state.

The principle "one MappingProposal row per parser finding" was the intent; the builder loop was the bug.

A.2 — Threshold consistency​

HIGH_CONFIDENCE_THRESHOLD = 0.7 in epistemic/services/proposals/builder.py:34, but two user-facing strings in data_import/admin.py:212, 265 hardcode "≥ 0.8". A third string at admin.py:536 correctly derives from the constant. User sees inconsistent threshold values.

Correction: all user-facing strings about the auto-approval threshold MUST derive from HIGH_CONFIDENCE_THRESHOLD. Pure UX/doc fix; no behavioral change.

A.3 — LABEL as a 4th MappingProposal.Kind (extension, not a new ADR)​

The 2026-05-07 user surfaced an idea that aligns with ADR-010's existing pattern: the import wizard could SUGGEST tenant-display labels for archetypes (e.g., "Lemma Pool" → "Lemma") with same parser-first / LLM-second / human-approval discipline.

Extension: add a fourth value to data_import.MappingProposal.Kind when the wizard ships:

class Kind(models.TextChoices):
    ARCHETYPE = "ARCHETYPE", "Archetype assignment for a table/sheet"
    COLUMN = "COLUMN", "Column → slot mapping"
    RELATION = "RELATION", "Cross-table relation"
    LABEL = "LABEL", "Tenant-display label for archetype"   # NEW

LABEL proposals follow ADR-010's pattern unchanged:

  • Parser proposes deterministic candidates (rule-based: drop "Pool" / "Bibliography" generic suffixes, prefer singular, prefer KE-archetype-canonical when fit). High-confidence rules auto-approve.
  • LLM refines low-confidence candidates with bounded prompt (source table name + sample data + KE archetype contract).
  • Reviewer approves/rejects via the same MappingProposal admin UX. Approved proposals seed TenantOntology.display_label.

Default behavior remains source-name-verbatim. Suggestions are NUDGES toward platform vocabulary, not impositions. Tenant accepts / rejects / edits each.

One LABEL proposal per (project, archetype) — same one-finding-one-proposal discipline as A.1.

No new ADR needed — this is an extension within ADR-010's existing pattern. ADR-014 explicitly disclaims the mapping-proposal substrate ("is not what ADR-014 covers"); the proposal pipeline is ADR-010 territory.

A.4 — Discipline confirmation: "one finding = one proposal"​

A.1 + A.3 reinforce a single principle: a MappingProposal row corresponds to ONE finding requiring ONE decision. The builder MUST emit one row per finding (regardless of candidate cardinality); the LLM MUST run ONCE per finding (with all candidates in context if multiple); the reviewer approves/rejects ONCE per finding.

Future proposal kinds added to Kind.choices (LABEL is the next; future kinds may include WIDGET-CHOICE refinement, MULTILINGUAL-RULE detection, etc.) MUST follow this discipline. A test or pre-commit lint could enforce: for kind in Kind: builder produces one proposal per (project, target_ref) tuple.

A.6 — Cyclical parser-audit of LLM proposals (cross-reference)​

ADR-033 §11 (2026-05-16 amendment) extends the parser-first / LLM-second discipline to a cyclical pattern in the import-wizard apply pipeline: parser extracts evidence → LLM proposes against that evidence → parser audits the LLM proposal against deterministic checks (set intersection, cardinality, type compatibility, key uniqueness, sample-data sanity) before the proposal reaches Stage 3 review cards. LLM proposals that fail the audit are killed with a new telemetry reason code REJECTED_BY_PARSER (engineering-only; never shown to researcher).

This is an extension of ADR-010's existing pattern, not a deviation. The parser remains the source of structural truth; the LLM remains the source of semantic enrichment; the parser is now also the validator of LLM enrichment before human review. Parser-audited LLM proposals can claim higher certainty than raw LLM proposals — they compose with the STRUCTURAL_CERTAINTY reason code (ADR-033 §7) for the audit-passed component while retaining CANONICAL_PATTERN_MATCH for the canonical-archetype-alignment component.

The cyclical pattern is wizard-pipeline-scoped (it lives in data_import apply pipeline plumbing). The ADR-010 read-path discipline is unchanged: once a TenantArchetypeFormConfig row exists, no LLM runs in the read path, ever.
