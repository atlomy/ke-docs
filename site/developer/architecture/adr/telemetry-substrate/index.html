ADR-016 — Telemetry substrate: hybrid storage, redact-before-log, hash-chained integrity

Status: Proposed (with §A R1-absorption amendments — see bottom) Date: 2026-05-05 (drafted) / amended 2026-05-05 (Round-1 absorption) Branch: experiment/v2-anchor-and-seamless-edit Related: ADR-001 (Epistemic/Operational Separation), ADR-002 (Hybrid Ontology), ADR-012 (Tenant Config via Runtime Pipeline), ADR-014 (In-App AI Orchestration — deferred file; this ADR is a prerequisite), ADR-015 (Tenant Admin Shell), docs/superpowers/specs/2026-05-03_telemetry-system-design.md, docs/superpowers/specs/2026-05-04_2300_telemetry-session-brief.md, docs/research/2026-05-05_telemetry-compliance-research/01-04*.md, docs/devlogs/2026_w19/2026-05-05_1230_round1-ke-telemetry-absorption.md, docs/notebooklm/ke-telemetry-round-1/transcripts-summary.md Supersedes: nothing Amendment history: §A added 2026-05-05 from KE Telemetry NotebookLM Round-1 absorption — 8 substrate amendments (per-tenant chains, TR39 companion, per-tenant KMS day-one, per-tenant DPIA on request, K=11 default + build-crash gate, Bedrock SCP-shipped, controller-only-past-K-line, implementation-status deltas) + 8 deferred-with-named-trigger items.

Context​

The Round-5 / Round-6 critique absorption arc produced multiple architectural amendments scoped as "telemetry-driven activation." Phase-2h per-cell language detection, the D-auto confidence-delta trip-wire, the AI Agent Resolver epic (ADR-014-α candidate), Phase-2F adversarial gates, and token-aware back-pressure all phrase their activation criteria as "telemetry shows X." Without a defined telemetry substrate, "defer until evidence" is vagueness, not discipline.

This ADR commits the platform to the substrate. It does not wire production capture; that follows in increments per Phase-2K.26 timing and AI-α implementation timing. It locks in the architecture so future increments can land without re-litigating storage shape, integrity model, or privacy posture.

The session deliberately constrained scope to the smallest signal set that unblocks the most pending amendments simultaneously, per the brief. Three signal classes are in scope: LLM-call telemetry (per-invocation), search-quality telemetry (per-query), and ingestion-pipeline telemetry (per-import-run). Engineering APM, security IDS / WAF, business CRM-shape metrics, and product analytics beyond the search subset are explicitly out of scope.

The user explicitly directed (2026-05-05) that the design must be grounded in regulatory and security best practices, not engineer intuition. Four parallel research agents produced a citable substrate of findings under docs/research/2026-05-05_telemetry-compliance-research/. This ADR synthesizes the decisions; the spec at docs/superpowers/specs/2026-05-03_telemetry-system-design.md carries the implementation roadmap.

Decision​

The platform commits to a hybrid two-layer storage model with redact-before-log capture and hash-chained integrity. Concretely:

This shape preserves the django-tenants invariant ("tenant content stays in tenant schema") while still enabling the cross-tenant rollups the AI-α cost-budget gate and the LLM-cost reconciliation flow require.

2. Capture discipline — redact-before-log, in-process​

All payloads are reduced to redacted summaries before the durable telemetry row is written. The capture layer enforces this; downstream consumers (dashboards, BI extracts, debugging tools) never see raw payloads (research reference 03 §1, OWASP LLM02:2025).

For LLM calls (telemetry_llm_call):

  • Stored: agent_role, agent_version, model_id, model_version_pin, temperature, max_tokens, latency_ms, tokens_in, tokens_out, tokens_cache, confidence_score (numeric, non-gating), confidence_method, result_kind (enum: composition_template / strawberry_resolver / escalation / refusal), validation_lint_pass, validation_ast_pass, validation_test_pass, plus six Phase-2F adversarial-gate boolean columns, provenance_hash, output_hash, system_prompt_hash, tool_definitions_hash, prompt_template_version_hash, source_format_dialect_version, tenant_id, invocation_trigger, provider (enum: bedrock / anthropic_api), injection_classifier_verdict, injection_classifier_score, input_hash, input_length, input_dialect, input_shape (NFC-aligned + diacritics-preserved, ≤256 chars; see §2a).
  • NOT stored in the events table: raw prompt bytes, raw response bytes.
  • Confirmed-injection raw bytes go to a separate S3 quarantine prefix with Object Lock in compliance mode, 90-day default retention, IAM-restricted to a security-review group; the events row carries only quarantine_uri (research reference 03 §6).

For search queries (telemetry_search_query_buffer + telemetry_search_query_rollup):

  • Active-session buffer (telemetry_search_query_buffer): per-tenant, opt-IN only. Holds raw query strings with a 60-minute idle-flush TTL and a 24-hour hard cap. Buffer purge on right-to-erasure (research reference 04 §4).
  • Rollup (telemetry_search_query_rollup): always-on (anonymous aggregate, not personal data once the buffer is deleted). Holds HMAC-SHA-256(query, per-tenant-key) hashes with K-anonymity threshold K=5; queries below threshold are bucketed as "rare." Rollups are not deleted on right-to-erasure — they are anonymous aggregates per Art. 17(3)(d)/(e) (research references 01 §1.3, 04 §4.2).

For ingestion runs (telemetry_ingestion_run):

  • Per-import-run rows. Tenant + source format + entity counts before/after by archetype + materializer outputs + structured sanitized run_metrics for importer-adjacent counters + error counts + duration. No PII at this signal class by construction; all payload-sensitive content lives downstream in EpistemicEntity rows.

2a. input_shape — alignment with Atlas's normalization model​

input_shape is a length-bounded structural signature stored on every LLM-call row. Its construction is deliberately conservative for an academic platform serving multilingual scholarly content (Greek polytonic, Arabic, Hebrew, Vietnamese, Latin, Japanese, plus tenant-specific obscure / ancient scripts).

Atlas's existing normalization model (epistemic.services.indexers._indexer_common) defines two distinct operations:

  1. normalize_unicode(text) → NFC, used at indexing/identity-matching time. NFC collapses combining-mark vs precomposed forms (ά U+03AC ↔ α U+03B1 + U+0301) without destroying any character information. Never NFKC — NFKC's compatibility decomposition would destroy ligatures and presentation forms used in diplomatic editions of medieval/ancient scholarship.
  2. fold_for_search(text), used at search-recall time only. NFD-decompose → strip combining marks EXCEPT a deliberate 2-codepoint keep-list (U+0301 acute, U+0308 diaeresis — chosen because they carry semantic stress + vowel-disambiguation across multiple modern scripts simultaneously) → NFC-recompose. Tenant-specific deeper folding lives in accent_fold slot-config metadata, not in platform code.

The platform's documented normalization rule (docs/context/state.md): edge materialization may use NFC canonical equivalence for identity matching, but must not use fold_for_search, asciifolding, transliteration, or accent_fold search-recall behavior to create edges. Original source values remain unchanged.

input_shape MUST honor that rule. Therefore:

  • NFC normalize (matches normalize_unicode's identity-matching baseline). Combining-mark vs precomposed forms collapse; ligatures + presentation forms preserved.
  • Diacritics PRESERVED. ASCII-folding would destroy:
    • Greek polytonic breathings, accents, iota subscripts (ἄλφα ≠ ἀλφα ≠ άλφα ≠ αλφα — these are distinct lemma forms in the scholarly corpus).
    • Arabic kasra / fatha / damma (كِتاب ≠ كتاب — vocalised vs unvocalised text is an editorial distinction).
    • Hebrew niqqud (בָּרוּךְ ≠ ברוך).
    • Vietnamese tonal marks (Tiếng ≠ Tieng).
    • Latin diacritic precision (café ≠ cafe, naïve ≠ naive). These are not "accents" — they are part of the character identity in the scholarly corpora Atlas serves.
  • Case PRESERVED. Case is part of the structural signature; lowercasing would discard discriminating value (Cyrillic vs Latin capitalization patterns differ).
  • NO TR39 confusables-skeleton mapping in α. UAX #39's cross-script confusables-skeleton would collapse legitimate Greek queries to Latin shapes (Greek α → Latin a in some TR39 tables). The α decision: do not apply TR39 in input_shape; cross-script homoglyph defense lives in the SEPARATE injection_classifier_verdict field. The classifier itself can apply TR39 + mixed-script-frequency analysis as input features without input_shape needing to encode the verdict. Two distinct signals — one structural, one adversarial — beats one overloaded signal.
  • Length cap 256 chars — applied AFTER NFC, on the output (NFC may produce a string longer or shorter than input).

A future increment may add an opt-in input_shape_tr39 = sha256(tr39_skeleton(input)) companion column for tenants who explicitly want TR39-class homoglyph telemetry. That increment would not modify input_shape's α semantics; it would add a new column with documented opt-in, not redefine an existing one.

This decision is pinned by tests/unit/test_telemetry_redaction.py which verifies polytonic Greek, Arabic kasra, Hebrew niqqud, Vietnamese tonal marks, Latin diacritic precision, and case all survive input_shape; and that Cyrillic 'а' and Latin 'a' do NOT collapse in α.

Cross-reference: Phase-2K.15 ADR draft (Normalization Model) at docs/superpowers/specs/2026-05-04_phase2k-import-quality-and-followups.md §"2K.15". When the Phase-2K.15 ADR is ratified, this section may be updated to cite it.

3. Hashing scheme — HMAC-SHA-256 with per-tenant key, annual rotation​

Query strings, user identifiers (when stored anywhere), and any other field where reversibility-by-attacker matters use HMAC-SHA-256 with a per-tenant secret key. EDPB 2025: keyed MACs are stronger pseudonymisation than salted hashes because the secret is held out-of-band (research reference 04 §1.3).

  • Key scope: one key per tenant. Cross-tenant linkage is research-sensitive (overlapping research interests across tenants); per-tenant keys make linkage cryptographically impossible.
  • Key rotation: annual baseline, aligned to the 30-day rollup boundary so no rollup spans a key change. Key version is recorded in rollup metadata.
  • Key custody for α: platform-managed KMS. Per-tenant external KMS (each tenant brings their own key) is an α → β migration path documented but not implemented; some EU university DPOs may require it as a contract precondition (research reference 04 §7.3).
  • Compromise contingency: rollups produced under a compromised key are treated as re-identifiable until purged; the rotation runbook covers this case.

4. Integrity — hash-chained public.platform_event with daily-signed digest​

sequenceDiagram
    participant App
    participant PE as platform_event
    participant Trig as BEFORE INSERT trigger
    participant Cron as Daily digest task
    participant Ver as Nightly verifier

    App->>PE: INSERT
    PE->>Trig: fire
    Trig->>PE: SELECT last row_hash FOR UPDATE
    Trig->>Trig: NEW.prev_hash = last_hash<br/>NEW.row_hash = SHA-256(canonical || last_hash)
    Trig-->>PE: row inserted

    Note over App,PE: BEFORE UPDATE/DELETE → RAISE EXCEPTION

    Cron->>PE: read head row_hash
    Cron->>PE: store Ed25519(digest_at, head_seq, head_row_hash)<br/>in platform_event_digest

    Ver->>PE: walk genesis → head, recompute hashes
    Ver->>PE: write outcome to platform_event_audit_verification

Every row in public.platform_event carries prev_hash (the previous row's row_hash, or all zeros for genesis) and row_hash = SHA-256(canonical_serialization(row_minus_row_hash) || prev_hash). A BEFORE INSERT Postgres trigger computes the chain under a serializable transaction; sequence numbers come from a monotonic database identity, never the application (research reference 03 §3.2).

A daily Celery task signs the latest row_hash with a platform-controlled Ed25519 key and writes the signature to public.platform_event_digest. A nightly verifier walks the chain from genesis and writes results to public.platform_event_audit_verification.

A column is reserved for periodic Merkle-root anchoring (Sigstore Rekor / S3 Object Lock) when external attestation becomes a contractual requirement; α does not ship Rekor integration. No per-row signing in α — overkill at this scale (research reference 03 §3.3).

public.platform_event is INSERT-only at the database role level: UPDATE and DELETE privileges are revoked from the application user, plus a BEFORE UPDATE/DELETE trigger that raises. Soft-deletes (e.g., GDPR erasure of a quarantine reference) write tombstone rows; they never mutate.

5. Lawful basis, retention, residency​

  • Lawful basis: legitimate interest under GDPR Art. 6(1)(f) for all three signal classes, with a documented LIA per signal class. Operational integrity, post-market AI monitoring, abuse detection are the recognized interests (research reference 01 §1.1, EDPB 1/2024 + Opinion 28/2024). Consent (Art. 6(1)(a)) is reserved as a fallback for SPA-side analytics if/when introduced (ePrivacy Art. 5(3)).
  • Retention defaults (per-tenant overridable; recorded in tenant config + DPO sign-off):
    • LLM-call telemetry: 30 days verbatim, 12 months hashed/structural.
    • Search-query buffer: 24 hour hard cap (60-min idle flush is the primary discipline).
    • Search-query rollup: 30-day rolling window, aligned with key rotation.
    • Ingestion-pipeline telemetry: 12 months (typically no PII).
    • Validation/abuse audit (security-relevant rows): 2 years, Art. 17(3)(e) basis, aligned with Anthropic Usage-Policy retention ceiling. Quarantine bucket Object Lock is the durable artifact, not the events table (research references 01 §4.2, 03 §8).
  • Residency: EU tenants → Bedrock EU geographic inference profile + EU-region telemetry storage by default; US tenants → US regions acceptable; mixed-affiliation tenants → strictest applicable regime (default EU). Residency is a per-tenant attribute on customers.Client (research reference 01 §4.5).
  • DPIA: required before turning on telemetry capture in production. Single platform-wide DPIA with annual + event-driven refresh cadence (research reference 01 §4.4).

6. Tenant flags governing capture posture​

The following per-tenant attributes (on customers.Client) gate telemetry behavior:

  • is_used_for_coursework (default False): if True, suppresses identifiable per-user logging entirely (FERPA-compliant pseudonymous-only mode; research reference 01 §4.3).
  • telemetry_residency (enum: eu / us / default-strictest; default default-strictest).
  • search_query_raw_optin (default False): controls the active-session raw buffer. Off by default per EU GDPR baseline + US academic-IRB norm + research-sensitivity convergence (research reference 04 §5.2). Override requires DPO sign-off captured in tenant config (text + timestamp + signer name).
  • k_anonymity_threshold (default 5, override 11 for stricter tenants).
  • retention_overrides JSONB (per-signal-class day counts; bounded by platform-set min/max).

7. Capture mechanism — three distinct paths​

Three capture paths feed the same telemetry pipeline (research reference 03 §4.3):

  1. LLM-call context manager — wraps every Anthropic SDK call. Computes provenance_hash, input_hash, input_shape, redacts payload, classifies for injection, writes both the tenant-scoped row and the public-schema metric-row.
  2. Ingestion-pipeline adapter hook — invoked by every importer (coda_v2_import, seed_tenant_anchor_from_config, migrate_legacy_relationship_entities, etc.). Records run-summary fields per-tenant.
  3. Search middleware — wraps IndexerProtocol.search() at the dispatcher boundary. Writes to the tenant's active-session buffer (when opt-in) and updates the rollup on session close.

In α, paths 1 and 2 ship with capture wired but disabled by default (a feature flag controls whether telemetry rows are actually written). Path 3 ships as scaffold only — wiring deferred until Phase-2K.26 reimport produces a meaningful signal (per session brief §117 right-sizing acknowledgment; telemetry over impaired-index data misleads).

8. Tenant rights interaction​

  • Right-to-export: per-tenant dump_telemetry management command runs in the tenant's schema_context, exports telemetry_* to JSON Lines + signed manifest. Public-schema platform-event rows referencing the tenant are not part of tenant export by classification — they are platform metrics about tenant behavior, not tenant payload. This must be in the tenant DPA.
  • Right-to-erasure: buffer purge yes; rollups retained as anonymous aggregates (Art. 17(3)(d)/(e)); tenant-schema events table user-identifying rows pseudonymised in-place (replace user-key with tombstone token), not deleted.
  • Tenant offboarding: schema drop removes tenant payload; public.platform_event rows for that tenant have tenant_id rewritten to a stable opaque hash but are retained for cost-history continuity. The hash-chain remains valid because the rewrite is itself an event row (tombstone), not an in-place mutation.

9. Bedrock invocation-logging posture​

Bedrock model-invocation logging is off by default; the Atlas-side context manager (path 1) does the work. Rationale: Bedrock writes full request/response JSON (≤100 KB inline) to S3/CloudWatch — precisely the raw-payload exposure surface §2 forbids (research reference 03 §4). If Atlas later requires Bedrock-managed logging for any reason, an Atlas redaction Lambda must process the bucket before any human-readable downstream sees it.

10. Controller / processor posture​

Atlas operates a dual posture:

  • Processor for tenant content (the data tenants ingest into Atlas).
  • Controller for platform-improvement telemetry (LLM-call rollups, abuse-rate aggregates) collected for Atlas's own operational purposes.

This dual posture must be articulated in the tenant DPA template before telemetry goes live in production (research reference 01 §5.1). The α deliverable is the substrate; the DPA-template work is downstream.

What this constrains​

  • No telemetry capture path may bypass the redact-before-log discipline. A capture path that writes raw prompts or queries to any durable surface is not eligible for merge.
  • No code may add columns containing free-text payload to public.platform_event. Free-text payload lives in tenant-schema tables only; if a metric needs free-text context, it lives in a <tenant>.telemetry_* table and is referenced by hash from the public table.
  • Hashing without HMAC + per-tenant key is forbidden for any reversibility-sensitive field. Plain SHA-256 of low-entropy inputs (single names, four-digit years) is rainbow-table-reversible and does not satisfy GDPR pseudonymisation under EDPB 2025 — it is reserved for provenance_hash-style high-entropy provenance keys, never for query-string or user-identifier reduction.
  • No telemetry table may be in scope for an UPDATE or DELETE migration (with the documented exception of erasure-tombstone migrations, which are explicit appends recording the erasure).
  • Bedrock model-invocation logging stays disabled unless an explicit redaction-aware delivery path lands first.

What this doesn't constrain​

  • Existing monitoring.PlatformMetric and monitoring.Alert rows — these are the prior generic key/value/tenant rows. They are not on the integrity chain and remain operational telemetry without payload risk; they coexist with the new platform_event table.
  • Logging via Django's logging module — the platform-events table is for structured telemetry events, not free-form log lines. logging.info(...) calls do not need to route through this substrate.
  • Standard Django-tenants queries against existing EpistemicEntity data — telemetry is observational; it does not change how tenant content is read or written.
  • One-time data-fix migrations on telemetry tables are fine if they're explicit appends (e.g., re-hashing rollup rows after a key compromise — the rehashed rows are new appends, not mutations of existing rows).

Alternatives considered​

A. Pure schema-per-tenant (Pattern A from research 02 §2.1)​

All telemetry in tenant schemas; cross-tenant rollups by async ETL fan-out across Tenant.objects.all(). Reject. Cost-budget enforcement and abuse-pattern detection need cross-tenant freshness < 5 min; cron fan-out scales poorly past ~50 tenants; the per-tenant-LLM-cost rollup query against the platform's payment provider becomes architecturally distant from the data.

B. Pure public-schema events with row-level security (Pattern B from research 02 §2.3)​

One events table, RLS on tenant_id. Reject. RLS in the pooled-Django + django-tenants setup has multiple known footguns (PgBouncer pool reuse, owner bypass, non-LEAKPROOF predicate planning regressions, unique-constraint side-channels). Atlas already has a stronger isolation primitive (schema search_path) — duplicating it at a weaker layer adds failure modes without privacy gain.

C. Sidecar OLAP (ClickHouse / TimescaleDB / DuckDB) from day one (Pattern E)​

Reject for α. Production DP/OLAP deployments justify the operational tax at ≥ 10⁷ events/day. Atlas at 3 tenants × ~1K queries/day pre-AI-α is roughly four orders of magnitude below that threshold. The Postgres path keeps options open: TimescaleDB hypertables are an in-Postgres extension upgrade with zero application-code change when the first pressure point fires.

D. Differential privacy from day one​

Reject. Production DP deployments operate on millions of user-days (Apple Health, Wikimedia, LinkedIn). At 3 tenants × ~1K queries/day, the noise required to satisfy any reasonable ε would dominate the signal — zero-result-rate would become a coin flip. K-anonymity + suppression + retention limits + the redact-before-log discipline already prevent the AOL-2006 failure mode. Re-evaluate when scale reaches ~10 tenants × 100K/day or when a regulator-grade public dataset release is planned.

E. Per-row Ed25519 signing for platform_event​

Reject for α. Per-row signing solves non-repudiation (which signer wrote which row); telemetry's threat model is tamper-evidence, not non-repudiation. Hash-chain + daily-signed digest is the cheapest construction that produces tamper-evidence at scale; Merkle anchoring is the documented escalation path.

F. Defer this ADR until a tenant signs a regulated DPA​

Reject. The brief and the partner-model right-sizing principle agree: defer implementation until evidence justifies, but lock in substrate now so future amendments can phrase activation criteria measurably. Without this ADR, every downstream amendment must re-derive its own privacy posture, and the risk of inconsistent decisions across amendments is high.

Consequences​

Positive​

  • Downstream amendments unblocked. Phase-2h, D-auto trip-wire, AI-α confidence tuning, Phase-2F adversarial-gate replay, and token-aware back-pressure all have a defined substrate to phrase activation criteria against. Each amendment now writes "telemetry shows X" in terms of measurable, citable signals rather than abstract intent.
  • Privacy posture defensible to EU university DPOs and US academic IRBs. The combination — HMAC + K=5 + opt-in raw + redact-before-log + 30-day verbatim / 12-month hashed defaults + DPIA — is the strictest applicable convergence across GDPR Art. 6(1)(f), CCPA, FERPA, and Common Rule.
  • Tenant isolation invariant preserved. The cross-tenant boundary is a payload boundary; no tenant payload ever appears in a public-schema row. The django-tenants discipline that the rest of the platform relies on extends naturally to telemetry.
  • Forensic-grade evidence available for adversarial replay. The hash-chain + quarantine bucket pattern lets the Phase-2F red-team gates produce a forensically meaningful provenance map rather than a "we logged something" story.
  • Migration paths documented. TimescaleDB at first OLTP-write-contention pressure point; ClickHouse at second; Merkle anchoring at first contractual-attestation requirement. Each migration is a zero-application-code-change extension of what α ships.

Negative / cost​

  • Per-tenant migration weight increases by four telemetry tables (telemetry_llm_call, telemetry_search_query_buffer, telemetry_search_query_rollup, telemetry_ingestion_run) plus a new telemetry/ Django app. Migration footprint per-tenant grows; tenant onboarding includes a tenant-tables migration step.
  • Application code must enforce redact-before-log. A bug in the capture layer that writes raw payload is a privacy incident. Test coverage on the redaction surface is non-negotiable.
  • HMAC key management is a new operational responsibility. Platform-managed KMS works for α; per-tenant KMS migration when an EU university tenant requires it is a real architectural commitment, not a config flag.
  • DPIA process overhead before production cutover. Single platform-wide DPIA + annual refresh is the lighter end of the cost spectrum; if a regulated-tenant onboarding requires per-tenant DPIA, the cost grows.
  • Dashboard work explicitly deferred. Tenant admins cannot self-inspect their LLM-cost / refusal-rate / zero-result-rate at α. The substrate makes the dashboard easy to add later but does not ship one.

Amendment §A — Round-1 KE Telemetry Substrate absorption (2026-05-05)​

The KE Telemetry Substrate NotebookLM round 1 (d222bacc-e2c1-46fd-9abe-cb7d187534e7) produced 4 artifacts (prescriptive critique + open critique + 5-decision debate + explainer video) against this ADR + the research substrate + the platform-context sources. Three debate verdicts explicitly mandated ADR-016 amendments; two critiques converged on additional substrate-level changes. The absorption devlog is at docs/devlogs/2026_w19/2026-05-05_1230_round1-ke-telemetry-absorption.md; transcripts summary at docs/notebooklm/ke-telemetry-round-1/transcripts-summary.md.

This block ratifies the Tier 1 + Tier 2 + Tier 4 verdicts from that absorption. The original §1–§10 decisions remain in force as the foundational substrate; §A points are the deltas.

§A1 — Per-tenant hash chain via Postgres native partitioning (amends §1, §4)​

Original posture (rejected by R1): single shared public.platform_event chain; per-tenant chain isolation deferred to triggering condition.

Amended posture: public.platform_event partitioned by tenant_id_opaque using PostgreSQL native list/hash partitioning. Per-tenant Genesis blocks + per-tenant monotonic sequences + per-tenant hash chains. The BEFORE INSERT trigger (platform_event_compute_hash) reads the latest row_hash SCOPED to the inserting partition, not the global head.

Rationale: the original "shared chain is operationally simpler" defense doesn't survive cross-tenant audit reasoning. Proving the integrity of one tenant's chain in a shared structure requires processing other tenants' hashes — this breaks tenant isolation at the cryptographic level regardless of payload. Per-tenant chains, when added day-one via partitioning, are operationally inexpensive (one CREATE TABLE … PARTITION BY change in monitoring/migrations/0002_*.py); retrofit later requires unwinding all historical chain state. The debate's verdict was "ADR-016 must amend §4 to mandate per-tenant chains" (round-1 debate decision 2). Open critique §2 and prescriptive critique #6 independently converged on the same conclusion.

§A2 — TR39 tenant-script-profile companion column (amends §2a)​

Original posture (refined by R1): blanket TR39 cross-script confusables-skeleton mapping is wrong for KE's multilingual scholarly content (Greek polytonic, Arabic, Hebrew, etc.); deferred entirely; cross-script homoglyph defense relies on injection_classifier_verdict.

Amended posture: add input_shape_tr39 companion column on telemetry_llm_call. The TR39 normalization dictionary is per-tenant, derived from the tenant's active script profile registered in tenant config. Example: ATLOMY's TR39 dictionary maps Cyrillic / Modern-Latin-confusables substitutions targeting expected Greek/Arabic/Latin contexts; it does NOT collapse legitimate Greek-Latin-Arabic mixes. The original input_shape (NFC + diacritics-preserved) remains the structural-fidelity signal; input_shape_tr39 is the adversarial-detection signal.

Rationale: the original blanket-TR39 deferral correctly identified that cross-script collapse breaks multilingual scholarship. But complete deferral leaves zero homoglyph defense at the structural-shape layer; the injection classifier alone is a "lossy probabilistic substitute for a deterministic structural defense" (round-1 debate decision 3 Side B; round-1 prescriptive critique #9; round-1 open critique #1). The threadable middle is per-tenant script-profile-aware TR39 — preserves multilingual fidelity, adds homoglyph defense, two distinct columns for two distinct purposes.

This honors §2a's discipline: NFC + diacritics-preserved is still the primary structural signature; input_shape_tr39 is an adversarial signal generated separately. NOT a replacement; a companion.

§A3 — Per-tenant KMS keys at tenant-schema creation; 90-day rotation default (amends §3)​

Original posture (rejected by R1): platform-managed KMS for α; per-tenant external KMS migration deferred to first EU university DPA requirement; annual HMAC rotation aligned to 30-day rollup boundary.

Amended posture:

  • Per-tenant KMS keys provisioned at Django tenant-schema creation. Every tenant gets their own AWS KMS key from day one. Platform retains custodian-of-default-keys posture for α.
  • Per-tenant external-KMS migration becomes a documented IAM-policy update when first EU university tenant requires it, NOT a re-encryption migration of historical telemetry. The tenant's IAM grant flips from platform-tenant-key-A to tenant-A-external-KMS; future writes use the new key with a key_version increment in rollup metadata.
  • HMAC rotation 90 days for new tenants (paired with per-tenant KMS automation via AWS KMS scheduled rotation), aligned with the 90-day quarantine Object Lock period. Annual rotation grandfathered for any tenant that pre-dates this amendment until that tenant's first natural rotation.

Rationale: round-1 open critique §2 named this a "catastrophic one-way architectural door." Migrating populated rollup data to a new external key requires either dropping the historical data or running a re-encryption migration with cross-tenant contamination risk. Day-one per-tenant key provisioning collapses that one-way door into a permissions update — operationally cheap on day one, prohibitively expensive on retrofit. 90-day rotation cuts the key-compromise blast radius from 12 months to 90 days at modest operational cost given AWS KMS automation (round-1 prescriptive critique #7).

§A4 — Per-tenant DPIA on request (amends §5)​

Original posture (rejected by R1): single platform-wide DPIA with annual + event-driven refresh.

Amended posture: single platform-wide DPIA remains the BASELINE, with per-tenant DPIA available on request. Per-tenant DPIA process documented in DPA template (deferred to first paying tenant per §"Open questions" point 4). Tenants whose risk profile materially differs from the platform-wide DPIA's assumptions (e.g., FERPA-coursework-bound, CUI-handling, Forschungsdatengesetz-bound) trigger per-tenant DPIA review.

Rationale: round-1 debate decision 5 verdict was "ADR-016 must amend §5 to mandate per-tenant DPIA on request." Heterogeneous tenant risk profiles across FERPA / GDPR / Common Rule / CUI / Forschungsdatengesetz make a single platform-wide DPIA a "legal fiction" once the tenant set spans those regimes. The amendment is process work, not engineering work — but the architectural commitment matters for tenant DPA negotiations.

§A5 — K=11 hashed-only default + opt-in raw buffer behind build-crash gate (amends §6, §7)​

Original posture (refined by R1): K=5 default; opt-in raw query buffer per-tenant behind search_query_raw_optin flag with DPO sign-off.

Amended posture:

  • K=11 hashed-only as the default for telemetry_search_query_rollup. K=5 remains as a per-tenant override for tenants whose risk profile permits the looser threshold; K=11 is the default-defensible-in-EU-research posture.
  • Opt-in raw buffer remains in schema but capture is structurally gated: a Django startup check raises ImproperlyConfigured if TELEMETRY_CAPTURE_ENABLED=True AND any tenant has search_query_raw_optin=True AND no verified active tenant-admin webhook is registered. The build literally crashes until consent UI ships AND tenant-admin attestation lands.
  • Raw buffer wiring into search middleware remains deferred until both the consent UI ships and the per-tenant search_query_raw_optin defaults are confirmed by tenant DPO sign-off.

Rationale: round-1 debate decision 4 verdict was "ADR-016 must amend §6 to enforce always-hashed-only with K=11 default." The pure-Side-B reading is "drop opt-in entirely." Round-1 prescriptive critique #1 surfaced a more threadable position: keep opt-in in schema, but add a structural enforcement gate that prevents capture-without-consent-architecture. The two together (K=11 default + build-crash gate) honor both the research-sensitivity argument (scholar's unpublished search direction = unpatented IP) and the operational-debugging value (DPO-sign-off opt-in remains available when consent UI exists).

§A6 — Bedrock redaction Lambda + AWS SCP shipped as substrate (amends §9)​

Original posture (rejected by R1): Bedrock invocation logging OFF by default; redaction Lambda deferred until AWS-managed logging becomes contractual.

Amended posture:

  • AWS Lambda attached to Bedrock logging destination ships as part of the α substrate. Strips raw prompt + response from the logged record before any human-readable downstream sees it. Keeps only the metadata envelope (model, IAM role, timing).
  • AWS Service Control Policy at the organizational level that physically prevents Bedrock invocation logging from being enabled on the account UNLESS the redaction Lambda is verified-attached. This is fail-safe at infrastructure level — accidental misconfiguration cannot turn logging on without the Lambda.

Rationale: round-1 open critique §4 named this as "things that should not be deferred." If Bedrock invocation logging is ever turned on (institutional policy shift, accidental misconfiguration, contractual requirement), raw prompts immediately write to AWS S3/CloudWatch — bypassing the entire application-level redact-before-log discipline §2 forbids. The Lambda + SCP combination is fail-safe at infrastructure level: even if the application-tier capture path is compromised, the AWS-managed logging cannot record raw payloads.

§A7 — Controller posture only past K-suppression line (amends §10)​

Original posture (refined by R1): dual processor (tenant content) + controller (platform-improvement telemetry) posture.

Amended posture: KE acts as processor for ALL telemetry up through K-anonymity suppression. KE acts as controller ONLY for K-anonymized rollup data that has passed the K=11 (or K=5 per-tenant override) threshold. The DPA template articulates the suppression-line as the controller-tier transition.

Rationale: round-1 prescriptive critique #3. HMAC-pseudonymized data is mathematically reversible by the keyholder under EDPB 2025 — it remains personal data. If KE acts as controller for HMAC-pseudonymized-but-not-yet-K-suppressed data, KE is inadvertently handling personal data outside processor protections. The suppression line (K=11 or per-tenant override) is the only architecturally clean point at which the data is genuinely no longer personal data. Controller posture begins past that line; processor posture covers everything before.

Batch-hash optimization for bulk Stage 3 micro-decisions (R3 parallel-fire absorption 2026-05-17 — NEW-3):

Per-tenant HMAC-SHA256 encryption applied per-row creates a write-amplification bottleneck under bulk corrections. Concrete scenario: a researcher cleaning up the JPP 40%-unresolved-edges issue rejects 5,000 structurally-identical proposals in one session → 5,000 separate HMAC operations in a tight loop on the apply-pipeline critical path → severe UX latency (UI freezes while DB churns through encryption budget) + partitioning pressure.

Optimization: when bulk Stage 3 rejection captures a cluster of proposals sharing the same proposal_class + risk_class_at_apply + recommendation_reason_code stratum, the capture helper aggregates them into a single DecisionEvent row whose proposal_ids field is a JSONB array of the rejected proposal IDs. One HMAC operation hashes the entire array; one row insert; one partition write.

The recommender unhashes the array at calibration time, sees N specific individual mappings rejected, and credits the §11.2 rolling-rejection-rate threshold math with N micro-decisions. Per-mapping conceptual grain is preserved for telemetry purposes; physical-layer write count drops from N to 1.

Eligibility for batch-hash (engineering discipline):

  • Proposals must share proposal_class (transcription / parser-surface-structural / linguistic-fold / missing-content / archetype-canonical / efficiency)
  • Proposals must share risk_class_at_apply (low / medium / high)
  • Proposals must share recommendation_reason_code (the §7 reason code that drove auto-apply)
  • Captured within a single bulk-action UI gesture (NOT across unrelated user sessions; preserves audit semantics)

If any one of these differs, fall back to per-row capture. This protects the recommender from collapsing distinct calibration signals into a single noisy aggregate.

Implementation hook: capture_decision_event context manager (Spec 0018 US-A.5) gets an optional batch_proposal_ids: list[str] parameter; when present, captures one DecisionEvent row with proposal_ids JSONB array + sets is_batch=True marker + records batch_size for query convenience. Single-row capture path remains the default for non-bulk actions (Stage 3 single reject, 8s undo, post-edit).

Cross-reference: also informs ADR-033 §11.2 calibration math — per-stratum rejection-rate counter increments by len(proposal_ids) for batch events, by 1 for single-row events. Both paths produce equivalent statistical signal.
