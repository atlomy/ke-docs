ADR-020: Generic projection contract — attestation walk + paired-editions + the platform-canonical-projection principle

Date: 2026-05-07 Status: Proposed (stub — opened during Sprint 0004 wrap to capture the generalization the user surfaced) Deciders: Atlomy Account, assistant Related: ADR-002 (Hybrid Ontology), ADR-006 (Archetype Capability Contracts), ADR-015 (Native React Tenant Admin Shell), ADR-017 (Slot Config Manifest), ADR-019 (V1 SPA reads from EpistemicEntity), the existing relationship_resolver.py framework (string_match + enrich_via). Supersedes: nothing — opens scope deferred from ADR-019 §H5 (Reference / Model / Page / Feedback retirement) plus the classics-bibliography projection gap surfaced 2026-05-07 ~22:30.

Context​

What ADR-019 left open​

ADR-019 (Sprint 0004) shipped the V1 SPA's read-side substrate switch but explicitly deferred:

  1. Reference / Model (3D anatomy) / Page / Feedback model retirement
  2. ModelLemma join-table treatment (3D viewer rewire)
  3. The _build_ancient_word_references projection that V1's add_data used to assemble the classics-style nested text_location.{early_edition[], modern_edition[]} shape

Item 3 was characterized in docs/devlogs/2026_w19/2026-05-07_2300_sprint0004-fresh-import-field-gap-report.md and partially implemented in Sprint 0004 wrap (in epistemic/services/epistemic_to_v1_es_assembler.py::_build_ancient_words). That implementation is atlas-specific — hardcoded Modern Edition / Early Edition join keys, hardcoded Lemma Word join, hardcoded DOCUMENT field map.

The pattern that surfaced​

The user's Sprint-0004 wrap question:

Think if we can extrapolate a general principle out of the classics metadata editions details presentation logic. See if this is something we can generalize across needs in different disciplines. See if this can also be factored into tenant workspace UI.

The classics-references shape recurs structurally across knowledge-environment disciplines:

DisciplineAnchorOccurrencePaired Editions
Classics (atlomy)TERM (lemma)PASSAGE (attestation)early_edition (Bekker, Kühn) + modern_edition (Balme, Jones, Kühlewein)
ArchaeologyARTIFACT / FEATUREFIND_RECORDoriginal site report + revised stratigraphy + radiocarbon revision
Biodiversity (Darwin Core)TAXONOCCURRENCE / SPECIMENoriginal_description + taxonomic_revision + DNA_reidentification
NumismaticsCOIN_TYPESPECIMENSear catalog entry + RIC + BMC + dealer-card
Textual criticismLEMMA / READINGWITNESS (manuscript)diplomatic_transcription + critical_edition + translation
PaleographyDOCUMENT_INSTANCEWITNESSoriginal manuscript + facsimile + digital edition
Botanical / herbariumTAXONSPECIMENoriginal collection card + revised determination + DNA-based
Architecture / construction historyBUILDING_FEATUREATTESTATIONoriginal survey + later survey + photographic record

In every case:

  • Anchor → Occurrence is a 1:N relationship (one TERM has many PASSAGEs, one TAXON has many OCCURRENCEs, etc.).
  • Occurrence → Source is N:M, but in practice each occurrence cites a small set of canonical sources — typically TWO classes: the original/early/primary witness + the modern/critical/revised representation.
  • The presentation surface pairs the editions side-by-side: "Bekker says 510a21; Balme says p. 123" / "original site report says iron-age; revised stratigraphy says hellenistic".

Why this matters for the platform​

The pattern is structurally identical regardless of vocabulary. The differences are:

  • Vocabulary: "edition", "witness", "publication", "specimen", "field record"
  • Locator fields: classics uses Bekker (page-column-line); archaeology uses GPS + stratigraphic context; biodiversity uses field-collector-number + date + locality
  • Bibliographical metadata: classics has author + treatise + editor + page + year; biodiversity has collector + institution + accession-number
  • Quote-context: classics has Greek quote + word_before + word_after; archaeology has photo reference + drawing reference; biodiversity has voucher + observation field-notes

If the platform commits to a single attestation-walk contract that's vocabulary-agnostic, every tenant gets:

  • The same V1-shape ES projection mechanism (under whatever names the tenant chooses)
  • The same v2 native React shell occurrence-block component (auto-rendered from the contract declaration)
  • The same enrich_via walk machinery (already coded in relationship_resolver.py)

Decision (proposed) — two-part​

Part A — Platform-canonical-projection principle​

Refined post-Sprint-0004 wrap (2026-05-07 ~23:00) and validated by the lint catch + user's "you started panicking and hardcoding tenant names fields, forgetting about the first principles":

Platform code carries no domain vocabulary. The platform's V1-shape ES projection assembler at epistemic/services/epistemic_to_v1_es_assembler.py is purely a generic walker. It accepts a tenant-supplied v1_es_projection block and emits docs accordingly. It knows nothing about classics terms (lemma_full, morph_1, ancient_words, Modern Edition, Author, Lemma Word, etc.) or any tenant's Coda/source field names.

The only vocabulary the platform ships is the projection-primitive vocabulary — domain-neutral kinds:

PrimitiveWhat it does
scalar_fieldsProject one anchor data-key to one V1-output-key. Supports coerce: "string" / "string_or_list", composition_template, default, constant.
multilingual_list_fieldsProject a list of {value, language_code, analyzer} dicts; flattens list-valued value to string.
list_to_nested_fieldsProject a list[str] to V1's NestedField shape [{<wrap_key>: ...}].
string_split_list_fieldsProject a free-text string into a flat list by splitting on a separator (default \n).
descriptionsProject per-language descriptions block; tenant declares short/long data-keys + language code.
attestation_walkThe core ANCHOR → OCCURRENCE → PAIRED-EDITIONS walk (Part B below).
csl_projectorProject structural-projection output to CSL JSON conforming to csl-data.json v1.0. Carries CSL standard vocabulary only; tenant config declares which structural fields map to CSL variables plus custom.* extensions. Used by Sprint 0008 (Citation Framework).
related_terms_edge_rule_nameEntityRelationship rule that joins anchors to other anchors of the same archetype.
v2_meta_output_keyPlatform-emitted provenance pointer (epistemic_entity_id + V1 slug + legacy_lemma_id).

Every domain-specific name — lemma_full, Lemma Word, Modern Edition, early_edition, ancient_words, Author, Treatise — lives ONLY in the tenant's V1-compat manifest. The platform reads the manifest and emits whatever the tenant declares.

This is enforced by scripts/lint_no_tenant_vocabulary.py --strict. Atlas codenames + atlas-domain vocabulary are flagged as a leak when they appear as string literals in epistemic/, data_import/, customers/. Sprint 0004's wrap caught a panic-pattern (5 leaks: lemma_full, morph_1/2/3, ancient_words hardcoded as Python string literals); the refactor cleared all of them.

Amendment 2026-05-08 (Sprint 0008): csl_projector added to the primitive list. Per the platform-canonical-projection principle, csl_projector ships generic CSL vocabulary only (CSL 1.0.2 standard variables); all tenant-specific names live in TenantArchetypeFormConfig.csl_field_mapping. See docs/superpowers/specs/0008-citation-framework-csl/.

Part B — Attestation walk + paired-editions contract​

Adopt attestation_walk as the platform-canonical primitive for the anchor → occurrence → paired-editions pattern, declared in tenant config alongside the other primitives:

{
  "archetype": "TERM",
  "slot_name": "attestations",
  "kind": "attestation_walk",
  "occurrence_archetype": "PASSAGE",
  "anchor_join": {
    "rule_name": "lemma",          // EntityRelationship rule that joins anchor↔occurrence
    "direction": "inbound"         // PASSAGE.target = TERM
  },
  "editions": [
    {
      "name": "modern_edition",     // role-key the SPA renders under
      "occurrence_field": "Modern Edition",    // PASSAGE.data["Modern Edition"]
      "source_archetype": "DOCUMENT",
      "source_join_field": "Name",  // DOCUMENT.data["Name"]
      "occurrence_locator": {       // pulled from PASSAGE.data
        "page": "Page", "chapter": "Chapter", "section": "Section",
        "line": "Line Number", "quote": "Quote",
        "word": "Word", "word_before": "Word Before", "word_after": "Word After",
        "word_translation": "Translation (EN)"
      },
      "source_metadata": {          // pulled from DOCUMENT.data
        "author": "Author", "treatise": "Treatise", "title": "Edition Title",
        "editor_name": "Editor Name", "publisher": "Publisher",
        "page": "Page", "year_of_publish": "Year of publication",
        "place_of_publish": "Place of Publication", "century": "Century",
        "volume": "Volume"
      }
    },
    {
      "name": "early_edition",
      "occurrence_field": "Early Edition",
      "source_archetype": "DOCUMENT",
      "source_join_field": "Name",
      "occurrence_locator": {
        "page": "Early Page", "chapter": "Chapter", "section": "Section",
        "quote": "Quote", "word": "Word",
        "word_before": "Early Word Before", "word_after": "Early Word After"
      },
      "source_metadata": {
        "author": "Author", "treatise": "Treatise", "title": "Edition Title",
        "editor_name": "Editor Name", "page": "Page",
        "century": "Century", "volume": "Volume"
      }
    }
  ]
}

A tenant in archaeology declares the same contract with occurrence_archetype: "FIND_RECORD", editions: [{name: "site_report", ...}, {name: "revised_stratigraphy", ...}] — same machinery, different vocabulary.

Consequences​

Positive:

  • One walker, all tenants. The platform-shipped walker reads the contract, builds the nested projection. No per-tenant code paths.
  • relationship_resolver.py is the substrate. The existing string_match + enrich_via already handles two-hop walks with bulk-fetch (no N+1). The new contract just declares the call shape per slot.
  • Tenant workspace UI factors out. The v2 native React shell ships ONE OccurrenceBlock component that reads the contract and renders the paired editions. Atlas's classics-rendering becomes the reference; archaeology / biodiversity / etc. tenants get the same component automatically.
  • Citation-style rendering stays presentation-layer. The "Arist., HA III, , p. 123 Balme (510a21)" formatting is React-side, driven by editions[].name + occurrence_locator + source_metadata. Each tenant can customize the format function (registered formatter) without touching the data shape.
  • Sprint 0004's V1 ES assembler must stay contract-driven. Earlier implementation notes described a hardcoded interim assembler; that is stale. The current platform assembler reads the tenant V1-compat manifest and keeps domain-specific projection names in configuration.

Trade-offs:

  • Slot-config schema extension. TenantArchetypeFormConfig gains a kind field with attestation_walk as a new value alongside linkable / composition_template; alternatively the kind is implicit in the presence of editions[]. Schema migration + ADR-017 manifest contract update needed.
  • Contract complexity. Tenants new to the platform face a richer slot-config vocabulary. Mitigation: ship 2-3 starter contracts (classics, biodiversity, archaeology) as in import_configs/ JSON examples.
  • Performance. Two-hop walks per anchor are O(N_anchors * (N_occurrences + N_distinct_sources)). The existing enrich_via does ONE bulk query per source archetype for the full set, so this scales reasonably; benchmark before declaring a hard ceiling.

Take-overs from ADR-019 §H5 (post-Phase-4 follow-ups)​

Sprint 0005 / next-architectural-arc scope under ADR-020:

  1. Attestation projection consolidation — keep epistemic/services/epistemic_to_v1_es_assembler.py contract-driven and move any remaining attestation-walk declaration that still lives only in the V1-compat manifest toward the slot-config / contract-compiler layer.
  2. Slot-config schema migration — add kind (or attestation_walk_spec) JSONField to TenantArchetypeFormConfig. Update materializer + manifest validator.
  3. Reference retirement — atlas's V1 Reference model is replaced by DOCUMENT entities + the walker shipped here. Drop after a soak.
  4. Page, Feedback retirement — independent of the attestation walk; group with Reference if desired.
  5. 3D anatomy rewire (still requires user input on data model) — ModelLemma retirement + TERM ↔ MEDIA archetype EntityRelationship rules. User signaled they will provide a data model; not started today.

Status update — 2026-05-07 ~23:30​

Part A (the principle) was shipped during Sprint 0004 wrap: the platform assembler is now config-driven; atlas's V1-compat manifest carries every domain-specific name; lint_no_tenant_vocabulary.py --strict runs clean.

Part B's attestation_walk primitive was shipped as part of the same refactor: the contract above is the manifest's actual current shape (modulo the slot-config-level kind=attestation_walk declaration which Phase 1 of the implementation plan will move into TenantArchetypeFormConfig). Atlas's atlomy_atlas_v1_compat.json has a working example.

End-to-end verified:

  • Search at /results/1?search_word=phleps returns 3 lemmas with full descriptions, system tags, and authors.
  • Lemma page at /lemma/φλέψ/ renders 4 references with classics-style bibliography (Hipp. Morb. sacr. 3.3 (=6 Jones), Jouanna 11,13 = L. 6.366) + 7-entry literature list.
  • ES query layer fixed (deep-nested mapping for ancient_words.references.text_location.{early_edition, modern_edition}; get_nested_field wraps queries in nested clauses); the V1 SPA's nested-aggregation queries work.

What still pivots forward:

  • TenantArchetypeFormConfig.kind = attestation_walk schema migration (Phase 1) — currently the contract lives in <tenant>_v1_compat.json::v1_es_projection instead of in the slot-config table. Either is valid; consolidating into slot config is the cleaner end state per ADR-017.
  • Cross-discipline pilot tenant — until biodiversity or archaeology lands, the abstraction is untested outside classics.
  • Reverse direction: v2 native shell ↔ same contract — Phase 3 of the implementation plan ships an OccurrenceBlock React component that reads the same contract and renders attestations independent of the V1 ES assembler.

What's already coded (verified 2026-05-07)​

  • ✅ atlomyapp/services/relationship_resolver.py has string_match + enrich_via resolvers. The two-hop walk ANCHOR → OCCURRENCE → SOURCE is supported today as resolver_args. Atlas's slot configs declare these as resolver_kind=direct (passive); upgrading to string_match with enrich_via is a slot-config change, not a code change.
  • ✅ EntityRelationship rule_name='lemma' edges (5245 in atlas) are the anchor↔occurrence join. Materialized by materialize_entity_relationships on import.
  • ✅ DOCUMENT entities (79 in atlas) are populated with all bibliographical metadata.
  • ✅ V1 ES assembler attestation projection is manifest-driven in platform code. Domain-specific output keys and source-field names live in tenant configuration; platform code owns only the generic walk and nested ES projection behavior.

What's missing for ADR-020 is the slot-config-level declaration — consolidating the manifest-level attestation-walk shape into slot config / contract compiler metadata so tenant admin tooling can inspect and edit it directly.

Alternatives considered​

Option A (chosen above): declarative attestation_walk contract in slot config, projection via platform-shipped walker.

Option B: per-tenant Python adapters registered via the existing composed resolver formatter registry. Keeps slot config simple but leaks tenant-specific code into the platform tree. Rejected — violates ADR-012 (tenant configuration in runtime data, not platform packages).

Option C: do nothing, leave each tenant to write its own assembler. Maximum flexibility, minimum reuse. Rejected — atlas already has the pattern; not generalizing leaves non-atlas and future tenants reinventing it.

Implementation phasing​

  1. Phase 1: spec the attestation_walk slot kind in ADR-017 manifest + slot-config schema migration. Update materializer to pass-through the new kind.
  2. Phase 2: move the manifest-level attestation-walk declaration into slot config / contract compiler metadata. The existing manifest-driven assembler behavior remains the compatibility target.
  3. Phase 3: ship a v2 native React OccurrenceBlock component (ADR-015 territory) that reads the same contract and renders the paired-editions UI. Atlas's classics rendering becomes the reference component; tenant-specific format functions register via formatter registry.
  4. Phase 4: pilot on a non-classics tenant (when one lands) — biodiversity or archaeology. Validate that the contract holds without atlas-specific assumptions.

Each phase ships independently. Phase 1 is required for Phase 2; Phase 3 is independent of Phase 2 (the v2 native shell can read the contract directly without going through the V1 ES assembler).
