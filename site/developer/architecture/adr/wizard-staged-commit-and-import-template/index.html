ADR-034: Wizard Staged-Commit Semantics and ImportTemplate Entity

Date: 2026-05-15 Status: Accepted (2026-05-19 user ratification; includes R6 C0 addendum + metadata reconciliation) Deciders: Atlomy Account, assistant Context source: Spec 0017 rev 2 design.md §7.2 (strawman), wires-v4.jsx UndoContext lines 173–224, Stage1 template diff lines 591–637, Stage2 recognition banner lines 686–710, 2026-05-19 user ratification Related: ADR-010, ADR-017, ADR-033 (comfort dial; Sprint B gate), ADR-035 (Tenant Contributor Permission Model — supersedes the scholar/admin authority framing this ADR originally referenced), Spec 0008 (Flow B), Spec 0011, Spec 0017

Context​

The v4 import wizard introduces three persistent affordances that together form the institutional-memory + trust layer of the experience:

  1. Undo bar — 8-second window to reverse a system-applied auto-decision (typically fired by the comfort dial's Hands off or Stay informed levels).
  2. ImportTemplate — per-tenant memory of past imports so the wizard can fire the "we've seen this format before" recognition banner on Stage 2 and render the hover-revealed diff popover on Stage 1's template cards (✓ N columns the same · ~ 1 new column: etymology · ~ lang_code now uses 'grc' not 'gr').
  3. Ambient chat — contextual LLM affordance that sees the current wizard stage + the parse/proposal payload, accessible via a floating BrainGlyph icon.

Each is non-trivial and has architectural decisions that need to be resolved together because they share infrastructure (apply-pipeline awareness for undo; persistence for templates; telemetry + cost-guard wiring for chat).

2026-05-16 update: the current design pass surfaced a mini-recommender layer for the smooth-migration researcher flow. ImportTemplate rows, Stage 4 answers, undo outcomes, and ambient-chat context may become recommender features rather than only product-memory affordances. Sprint C backend implementation is therefore deferred until this ADR decides feature retention, privacy, safe metrics, and UI explanation requirements.

2026-05-19 R6 NotebookLM absorption note: final ratification does not treat the feature-retention table as sufficient by itself. Acceptance includes four checks: (1) raw tenant-local fields such as MappingProject.wizard_answers, MappingProposal.combined_rationale, and revision_notes remain product memory only unless an explicit opt-in/redaction/KMS/retention path exists; the recommender consumes separate abstracted signals, not those raw fields; (2) data_import/services/proposal_audit.py gets an orchestration/materialization hook and researcher-visible audit status without mutating page-render GETs; (3) the Sprint B ghost preview is a v1 layout stub, not proof of the future SPA preview contract; a real preview must consume the production JSON contract; and (4) stacked-undo semantics are ratified before any undo UI or template-recall implementation begins.

Decision (accepted 2026-05-19)​

Undo-bar reversal semantics​

Decision: Option C — Mixed. Transactional reverse for proposal-level applies (small, well-defined inverse: undo a single proposal subtree's row creation/edit); saga-style compensating action for cross-cutting applies (e.g., a comfort-level-0 auto-apply that touched many proposals at once and where a transactional staging table is impractical).

Alternatives:

  • Option A — Pure transactional reverse: every apply runs through an 8-second staging phase before committing. Cleanest UX (Undo is a literal rollback). Hardest implementation — requires a WizardStaging table parallel to the canonical tables, with commit/rollback wiring at the pipeline boundary.
  • Option B — Pure saga: apply commits immediately; Undo posts a compensating action (delete the rows that were created, restore the values that were changed). Simpler implementation. Risk: compensating action can fail if downstream consumers (search indexer, projection rebuilds) already saw the change.
  • Option C — Mixed (recommended): pragmatic, splits the difference. Per-proposal applies use staging (small surface, well-defined inverse). Cross-cutting comfort-dial auto-applies use saga (already messy, hard to stage transactionally).

Undo authority (per ADR-035): any contributor with can_undo_within_window=true can trigger the undo within the 8-second window regardless of which contributor drove the original apply. The undo-bar is a tenant-shared affordance, not a per-actor one — important for multi-contributor sessions where one researcher applies and a colleague catches the issue.

ImportTemplate entity​

class ImportTemplate(models.Model):
    tenant_schema = models.CharField(max_length=63, db_index=True)
    fingerprint = models.CharField(max_length=64, db_index=True)  # SHA-256 hex
    label = models.CharField(max_length=255)
    last_used_at = models.DateTimeField(default=timezone.now)
    use_count = models.PositiveIntegerField(default=1)
    answers_jsonb = models.JSONField(default=dict)  # researcher's Stage 4 answers
    column_profile_jsonb = models.JSONField(default=dict)  # for diff renderer
    metadata = models.JSONField(default=dict)  # tenant-local non-secret mode flags

    class Meta:
        unique_together = [("tenant_schema", "fingerprint")]
        indexes = [models.Index(fields=["tenant_schema", "-last_used_at"])]

2026-05-19 reconciliation: the Spec 0017 design amendment introduced ImportTemplate.metadata for reusable mode flags such as strict_transcription, but this ADR's original entity sketch did not carry the field forward. Treat metadata as part of the accepted entity contract. It is tenant-local, non-secret product memory only; it must not store raw source rows, document/table names, file paths, credentials, schema names, job IDs, arbitrary source identifiers, or raw researcher notes. The model enforces this as a positive allowlist of explicit setup flags; new metadata keys must be added deliberately when a future setup flag is ratified.

Fingerprint algorithm​

3-component SHA-256:

  1. Column-name set hash: sorted lowercase column names from all sheets, hashed.
  2. Datatype profile hash: per-column inferred datatype + nullability profile, hashed.
  3. Connection topology hash: detected shared-ID edges between sheets (sorted, normalized), hashed.

Final fingerprint: SHA-256 of the three component hashes concatenated.

flowchart LR
    Source["Imported source<br/>(sheets, columns, types,<br/>shared-ID edges)"]
    Source --> H1["Component 1:<br/>sorted lowercase column names<br/>→ SHA-256"]
    Source --> H2["Component 2:<br/>per-column datatype<br/>+ nullability profile<br/>→ SHA-256"]
    Source --> H3["Component 3:<br/>shared-ID edges<br/>(sorted, normalized)<br/>→ SHA-256"]
    H1 --> Concat["Concatenate component hashes"]
    H2 --> Concat
    H3 --> Concat
    Concat --> Final["Final fingerprint:<br/>SHA-256(H1 ‖ H2 ‖ H3)<br/>= ImportTemplate.fingerprint"]

Figure 8 — 3-component SHA-256 fingerprint. Each component captures a different shape dimension (vocabulary / types / topology), so partial matches at the component level drive the Stage 2 recognition-banner confidence percentage (3 of 3 = 100%; 2 of 3 = ~70%; etc.).

Lifecycle​

  • Created on first successful import.
  • Updated on each subsequent matching-fingerprint import: use_count += 1, last_used_at = now(), answers_jsonb merged (new keys added; existing keys overwritten with latest researcher answer).
  • May carry tenant-local non-secret setup flags in metadata, such as strict_transcription, so a repeated import can inherit an explicitly chosen researcher mode without converting that flag into recommender payload.
  • Never auto-deleted. User-triggered deletion from a Stage 1 "all saved setups" sub-page (Sprint C scope).
  • Per-tenant scope. Cross-tenant federation of templates is a future ADR.

Recognition banner threshold​

The Stage 2 "We've seen this format before" banner fires when the incoming file's fingerprint matches an existing ImportTemplate.fingerprint with use_count >= 2 (≥ 1 prior import that resembled it). Confidence percentage rendered in the banner is derived from match quality of the 3-component hashes (all 3 match = 100%; 2 of 3 = ~70%; 1 of 3 = ~40% — exact formula TBD at Sprint C kickoff after fingerprint calibration).

Ambient chat conversation persistence + cost guard​

  • Scope: session-only. Conversations don't persist across browser sessions (researchers ask "what's this?", they don't expect long chat threads).
  • Token budget: Tenant.ai_session_token_budget (new field, IntegerField, default 50000). When session token spend exceeds the budget, the chat panel shows a quota notice instead of blocking — researcher can still complete the import.
  • Telemetry: capture_llm_call (existing) emits one event per chat turn with purpose = 'wizard_ambient_chat' + stage context for analysis.
  • Stage context: each LLM call passes {stage, mapping_project_id, current_step_payload} as a system-prompt preamble. The LLM sees what the researcher sees.

Implementation note (2026-05-20): Sprint C implemented the bounded version of this contract in data_import.services.ambient_chat and MappingProjectAdmin.wizard_ambient_chat_view. The payload is deliberately summary-shaped (project, source_summary, proposal_summary) instead of a raw source dump; transcript persistence is session-only; token spend is stored in the same session key; telemetry records the purpose/stage/project marker and answer length/response-shape metadata, not the raw answer body.

Hardening note (2026-05-21): direct mutation requests are intercepted by a local action-intent guard before an LLM provider call. Blocked turns remain in the session transcript with intent="mutation_request_blocked" but do not increase token spend and do not mutate MappingProposal or template state. Questions that ask how to use a visible wizard control remain explainable.

Ratification addendum — R6 C0 decisions (2026-05-19)​

Acceptance includes these Sprint C gates:

  1. Raw tenant-local signal quarantine: MappingProject.wizard_answers, MappingProposal.combined_rationale, revision_notes, ambient-chat message bodies, raw source rows, source document/table names, file paths, credentials, schema names, job IDs, and arbitrary source identifiers remain tenant-local product memory by default. Recommender jobs may consume only explicit abstractions named in this ADR and ADR-033: question type, answer type, reason category, template/diff class counts, undo outcome, aggregate friction signals, and materialization outcomes. Any future raw-text recommender ingestion requires a separate opt-in/redaction/retention/KMS decision before implementation. ImportTemplate.metadata is limited to explicit non-secret mode/setup flags such as strict_transcription; it is not a place for raw payloads or source identifiers.
  2. Parser-audit orchestration: data_import/services/proposal_audit.py becomes an orchestration/materialization gate, not a page-render side effect. The first implementation path should run after proposal persistence and before Stage 3 researcher review; materialization should re-check when retained source rows are available. Page-render GETs remain pure reads. Until a parser-side DecisionEvent contract is explicitly accepted, REJECTED_BY_PARSER persists on MappingProposal / audit status and may roll up only as bounded aggregate audit metrics. Stage 3 must show pending/passed/failed audit state before comfort-driven auto-apply can rely on the row.
  3. Ghost-preview contract boundary: the Sprint B server-rendered ghost rail is a v1 layout/proof-of-interaction stub. A real public-preview integration must consume the production JSON contract expected by the shared public preview component and must have repeatable desktop/mobile breakpoint verification. Implementation note (2026-05-20): Sprint C adds an admin-only draft public-reader preview route for Stage 5. It builds EntryDetail-shaped draft payloads from approved proposals and retained/sample source rows, renders a reader-like page for review, and creates no EpistemicEntity, EntryProjection, public route, search document, index row, or JSON-LD artifact.
  4. Sprint C ordering: ADR-034 acceptance happened first; stacked undo semantics and Spec 0018 B.3 undo emission are the next implementation priority if safe production capture remains the priority; template recall follows the undo contract; ambient chat waits for its privacy/context/cost guard implementation unless explicitly reordered.

Recommender feature retention (revised 2026-05-16, Spec 0017 architecture pass)​

Feature classification — each candidate is classified as product memory (recall affordance only, never feeds recommender), recommender signal (feeds the prior, may or may not be displayed), or both. Cross-tenant pooling boundary follows ADR-033 §6 privacy matrix. Proposal-class references below use the 6-class taxonomy in ADR-033 §1 (transcription, parser-surface-structural, linguistic-fold, missing-content-suggestion, archetype-canonical-suggestion, efficiency-suggestion).

Raw source rows, document/table names, file paths, credentials, schema names, job IDs, and arbitrary source identifiers remain outside cross-tenant pooling per ADR-033 §6. If a feature is used for recommendations, the UI surfaces a plain-English reason code per ADR-033 §7 (STRUCTURAL_CERTAINTY, CANONICAL_PATTERN_MATCH, TEMPLATE_MATCH, PROPOSAL_CLASS_PRIOR, RISK_CLASS_FLOOR, LOW_PRIOR_CONFIDENCE, plus engineering-facing REJECTED_BY_PARSER per ADR-033 §11 and REJECTED_BY_RESEARCHER per ADR-033 §7 + §11.2) — for example: "we suggested this because this file matches a setup you've used three times" (TEMPLATE_MATCH), or "we've seen this shape in seven other research databases" (CANONICAL_PATTERN_MATCH) — no hidden identifiers leak through the explanation. Delivery discipline (Codex 2026-05-16 amendment) per ADR-033 §7.1: probabilistic reason codes (CANONICAL_PATTERN_MATCH, PROPOSAL_CLASS_PRIOR, LOW_PRIOR_CONFIDENCE) use delayed reveal (surfaced on researcher request via "Why this suggestion?"); source-declared deterministic codes (STRUCTURAL_CERTAINTY for source-declared facts, TEMPLATE_MATCH for tenant-local product memory) may use immediate reveal. The anti-anchoring telemetry block above measures whether the discipline is working.

Alternatives considered​

  1. Skip the undo bar; rely on existing Flow B revision/reject UX. Rejected: the dial-driven auto-apply is the v4 design's defining trust gesture (the "I noticed; let me adjust" affordance). Without undo, the comfort dial loses its safety guarantee.
  2. Cross-tenant ImportTemplate federation in v1. Rejected: tenants have wildly different shape vocabularies; cross-tenant federation needs its own ADR (and possibly a privacy review).
  3. Persistent ambient-chat conversations. Rejected: researchers don't expect long threads; persistence increases cost + privacy surface.
  4. Treat template memory as recommender input by default. Deferred: useful, but too implicit. The accepted ADR must name the feature set and metrics rather than letting persistence become training data accidentally.

Consequences​

Positive​

  • Stage 1's "Pick up where you left off" + Stage 2's recognition banner make repeat imports feel like minutes-not-hours; they realize the v4 design's "we won't ask again next month" promise.
  • Undo-bar removes the all-or-nothing fear from comfort-dial-driven auto-decisions.
  • Ambient chat with stage context makes the wizard feel like a collaborator instead of a form.

Negative​

  • The undo-bar staged-commit work is the largest single task in the Epic (~4 hr estimated; calibration ratio prior of 0.37 suggests ~1.5 hr actual, but it touches the apply pipeline and may surprise).
  • ImportTemplate introduces a new entity that has to survive tenant schema changes; per-tenant scope keeps blast radius bounded, but the migration must be defensive.
  • Ambient chat costs: 50k tokens/session × per-tenant users × imports/month is non-trivial AWS Bedrock spend. The cost-guard is the brake.
  • Recommender feature retention expands the privacy and telemetry surface. The design must prefer tenant-local raw signals, no-payload public aggregates, short retention where possible, and user-visible explanations.

Open questions (resolved 2026-05-16 per Codex review — architecture-pass amendment pass)​

  1. Mixed (Option C) really the right call, or commit to one of A/B? Resolved 2026-05-16 (Codex review): Keep mixed Option C. Require idempotent compensation and projection/search rollback checks for saga paths. High-tier structural changes should prefer sandbox/staging over immediate saga (composes with ADR-035 §4 layered safety floor).
  2. Default Tenant.ai_session_token_budget of 50k — too high, too low, or right for the typical research import session? Resolved 2026-05-16 (Codex review): Accept 50k as v1 default with tenant override and per-session telemetry. It is a cost guard, not a privacy boundary.
  3. Should the fingerprint include column-value sample patterns (e.g., "this column has Greek text", "this column has dates") in addition to column-name + datatype? More accurate matching but more compute per import. Resolved 2026-05-16 (Codex review): Defer raw/sample-value fingerprinting to v1.1. V1 should use column names, datatype profile, nullability, topology, and possibly non-content language/type signatures only.
  4. Template label defaults: should the system auto-generate ("Monthly lemma export — first seen 2026-04-22") or require the researcher to name it on first use? Resolved 2026-05-16 (Codex review): Auto-generate; allow rename from saved-setups page.
  5. Are ImportTemplate, Stage 4 answers, undo outcomes, and ambient-chat summaries recommender signals in v1, or product memory only? Resolved 2026-05-16 (Codex review): The Recommender feature-retention table resolves this in principle (rows above). Keep raw product memory tenant-local; allow aggregate/abstract recommender signals under ADR-033 §6.
  6. If ambient chat contributes recommender features, what summary shape is retained and what raw prompt/response data is discarded? Resolved 2026-05-16 (Codex review): Intent enum + stage + coarse question type only, opt-in before crossing tenant boundary. No raw prompt/response body in recommender features.
  7. What UI explanation is required when a recommendation is based on a prior template, a previous answer, or an undone auto-decision? Resolved 2026-05-16 (Codex review): Use reason codes (ADR-033 §7), but delayed reveal for probabilistic recommender claims per ADR-033 §7.1. Product-memory explanations like TEMPLATE_MATCH can reveal immediately if they cite tenant-local saved setup without hidden identifiers.
  8. What metrics prove the recommender reduces researcher workload without increasing wrong auto-decisions or silent trust loss? Resolved 2026-05-16 (Codex review): Use time-to-import, decision count, undo/post-edit, human-affirmation acceptance curve, satisfaction, and reason-code anchoring metrics. Do not treat faster completion alone as success.
