ADR-011 — OpenSearch + ICU + Per-Language Analyzers as the Per-Tenant Search Engine

Status: Proposed (Phase-0 gates pending) Date: 2026-05-01 Branch: experiment/v2-anchor-and-seamless-edit Related: ADR-002 (Hybrid Ontology), ADR-012 (Tenant Config via Runtime Pipeline), Session-05 spec, comparison essay at docs/research/2026-05-01_search-engine-comparison/essay.md, wider-net analysis at docs/research/2026-05-01_search-engine-comparison/wider-net-multilingual.md, Phase-0 gate design at docs/research/2026-05-01_search-engine-comparison/prototype-notes.md

Context​

Atlas v2 must provide search + autocomplete + faceted filtering as a platform-level capability, not a per-tenant feature. Three tenants today (Tenant A, Tenant B, Tenant C) bring Greek (polytonic), Latin, Arabic, English, Italian, French, German. The next anticipated tenant (Tenant D) brings Chinese (Classical 文言文 + Modern Mandarin) alongside Arabic and English. Future tenants are expected to bring Hebrew, Sanskrit (Devanagari), Persian, Coptic, Ottoman Turkish, Tibetan, Aramaic, Korean, Japanese, and others. The DH community frames this gap as the "Asia deficit within Digital Humanities"; Atlas's positioning places it on this frontier.

Each tenant exposes config-driven slot definitions in TenantArchetypeFormConfig. The search index must be driven by that config — zero tenant vocabulary in code, per ADR-012.

The current v1 search baseline is Elasticsearch with a LemmaDocument whose every field is a KeywordField with lowercase + asciifolding only — no per-language analyzers, no stemming, no morphological recall. A 280-line MultilingualProcessor module (data_import/services/multilingual.py) implements language detection + character-level transliteration (Greek→Latin via ISO 843, Arabic→Latin, Latin diacritic stripping) and documents an "index original alongside transliteration" design — but is not wired into the v1 indexer. Atlas therefore enters this decision with building blocks plus an unexecuted design, not a working morphology-aware baseline.

The independent architecture review (2026-04-29 §3.4) flagged ES as fragile in its current triple-write form and recommended treating it as a projection rather than a bridge — a strangler-adapter pattern waiting for a use case worth executing. The federated_discovery_spec (docs/architecture/federated_discovery_spec.md, 2026-02-03 draft) separately assumes a public ES index for cross-tenant federated search.

A first cut of the comparison essay scoped this decision to three tenants and concluded with a Postgres FTS verdict. The user pushed the scope wider ("Tenant D alone has Arabic, English, Chinese (ancient and modern) and more. Cast a wider net"); under the wider net, Postgres FTS does not survive — Chinese is not in the bundled 29 dictionaries, neither is Hebrew, Sanskrit, Persian, Coptic, or most other scripts a future tenant might bring. Per-language Postgres extensions exist for Chinese (zhparser, pg_jieba, pg_bigm) but each is single-language plugin work that does not scale with "many tenants could join." See docs/research/2026-05-01_search-engine-comparison/essay.md and wider-net-multilingual.md for the full deliberation.

Decision​

Adopt OpenSearch with the analysis-icu plugin and per-language analyzers as the per-tenant search engine for Atlas v2.

The indexer (epistemic/services/indexer/opensearch.py) reads TenantArchetypeFormConfig and configures per-slot analyzer chains based on declared language metadata. ICU folding handles polytonic Greek normalization (Wikimedia precedent T75605). Per-language analyzers — Lucene Arabic root analyzers, SmartCN/IK for Chinese, Kuromoji for Japanese, Nori for Korean, community plugins for Hebrew/Persian/Sanskrit, ICU general Unicode for Coptic/Aramaic/Tibetan — are added per tenant slot as tenants arrive.

The previously-orphaned MultilingualProcessor module becomes the supplementary preprocessing layer for languages where Lucene plugins underdeliver — Latin macron stripping, Classical Chinese pre-segmentation if SmartCN underdelivers, transliteration-augmented secondary fields for cross-script queries.

Per-tenant search isolation continues to use the v1 index-naming pattern ({schema_name}_lemma_index → generalized to {schema_name}_{archetype}_index).

Faceted filtering, autocomplete, and tenant-scoped search continue to be governed by TenantArchetypeFormConfig slot config — Session 05 adds searchable, facet, autocomplete_eligible, and search_boost columns; values flow through MappingProposal → materialization, never seeded directly in migration bodies (per ADR-012).

Why not Postgres FTS + pg_trgm​

Postgres FTS ships 29 language dictionaries and does not include Chinese, Hebrew, Sanskrit, Persian, Coptic, Aramaic, Tibetan, Korean, or Japanese. Per-language Postgres extensions (zhparser, pg_jieba, pg_bigm for Chinese; others for Japanese/Korean) are single-language plugins — adding a tenant in a new script becomes per-deployment build work that does not scale. The transliteration scaffolding in MultilingualProcessor works for Latin-derivable scripts (Greek polytonic, Arabic, Latin) but does not generalize to CJK, where the search problem is word segmentation, not character normalization. Insufficient for the wider net.

Why not PGroonga (one of two named in-Postgres alternatives)​

PGroonga is a single Postgres extension billed as "all languages, zero ETL" — general Unicode tokenization plus Mecab/bigram tokenizers for CJK. Engineered for general multilingual full-text search, not classical philology. Lucene's analyzer ecosystem has decades of investment in Ancient Greek polytonic normalization, Arabic root analyzers, and DH-community-specific tooling that PGroonga's generic tokenizers do not match. The DH platforms doing what Atlas wants to do — Wikimedia, Perseus, Sketch Engine + OPUS, Ugarit Translation Alignment — run on Lucene-family backends.

PGroonga is now a named per-tenant retreat target, not just an engine-wide retreat. For tenants whose primary need is general-multilingual text matching at low operational cost (small corpus, no Lucene-specific analyzer requirements), PGroonga may be the right choice on its own merits.

Why not ParadeDB (the second in-Postgres alternative; added 5th revision)​

ParadeDB is a Postgres extension that embeds Lucene-family BM25 ranking inside Postgres via Tantivy (a Rust port of Lucene). It pairs the operational simplicity of in-Postgres search (transactional consistency, no replication lag, single-service deployment) with the BM25 ranking quality of the Lucene family. ICU folding is supported via Tantivy. ParadeDB is real, production-ready, schema-driven (matches the canonical-data-derivation pattern natively).

Why ParadeDB is not the platform-wide default: Tantivy's per-language analyzer ecosystem is narrower than full Lucene/OpenSearch. There is no SmartCN or IK port for Classical Chinese, no lucene-arabic-analyzer port for Arabic root extraction, no Kuromoji port for Japanese. For tenants whose query model requires those analyzers, ParadeDB is insufficient.

Where ParadeDB shines: tenants with smaller corpora and Lucene-family-but-ICU-only language needs (e.g., Greek polytonic + Latin, where ICU folding via Tantivy is sufficient). For such tenants, ParadeDB offers BM25 ranking quality competitive with OpenSearch at a fraction of the operational cost (no separate cluster, no JVM, transactional consistency).

ParadeDB is therefore a second named per-tenant retreat target, evaluated alongside PGroonga in Gate 1. The candidate set per tenant becomes three engines: PGroonga (general-multilingual, in-Postgres), ParadeDB (Lucene-family BM25, in-Postgres, narrower analyzer ecosystem), OpenSearch+paired-strategy (broadest analyzer ecosystem, separate service).

Why not Typesense / Meilisearch​

Strong autocomplete UX and typo tolerance, but no per-language stemming for classical scripts. Their value is real for autocomplete; OpenSearch's completion suggester or pg_trgm on a side table covers autocomplete adequately without a fourth data store.

Consequences​

Accepted​

  • Broadest analyzer ecosystem of any candidate — covers all current + most plausible future tenant languages with mature plugins.
  • DH-community precedent — Wikimedia ICU folding for ancient Greek (T75605); Lucene Arabic root analyzers (lucene-arabic-analyzer, AlKhalil-derived); SmartCN/IK + STConvert for Chinese; Perseus and Sketch Engine + OPUS as comparable scholarly platforms.
  • Federation alignment — collapses per-tenant + federation engine choice into one, eliminating drift.
  • Strangler-adapter realized — replaces v1's dumb-text LemmaDocument with an analyzer-aware indexer driven by TenantArchetypeFormConfig; closes the architecture review's prescription.
  • MultilingualProcessor repurposed, not wasted — supplementary preprocessing layer for languages where Lucene plugins underperform.
  • Apache 2 license — no Elastic vendor lock-in.

Lost​

  • In-stack simplicity. OpenSearch is a separate service with its own operational profile. Postgres FTS / PGroonga would have been lighter.
  • Synchronization simplicity. ES is eventually consistent vs Postgres; reindexing on slot-config changes requires a queue + idempotency layer. Manageable; not novel.
  • Some operational headroom on a thin deployment-engineering team. Production-grade OpenSearch (replica counts, cluster sizing, reindex pipelines, lifecycle policies) is non-trivial.

Risks named explicitly​

  • v1's existing ES container is single-node replicas=0 (per the v1 search-document module (single-node, replicas=0)) — not production-grade. Productionization is a separable workstream the architecture review already flagged. Prototype phase is fine on the existing single-node config; production hardening is its own track. Not in Session 05.
  • Classical Chinese (文言文) is not solved out of the box by any engine. SmartCN/IK are tuned for modern Mandarin. Tenant D's Classical Chinese corpus may need custom Lucene analyzer development or MultilingualProcessor-style pre-segmentation. Intra-OpenSearch escalation, not engine swap.
  • Operational cost ceiling. If Atlas's deployment-engineering capacity stays thin, running production OpenSearch becomes a tax. The mitigation is the prototype phase: prove the integration shape on the existing single-node container before committing to productionization. PGroonga remains the retreat target.

Phase-0 Gates (revised 2026-05-01 — per-tenant search quality first)​

Round-2 audio review surfaced four further actionable concerns: (1) gate sequencing under the original framing was wrong; (2) paired-strategy is engineered against modeled queries, not measured; (3) the custom-dict 100-200-entry estimate is a fiction at corpus scale; (4) federation should be severed completely from the evaluation criteria. The user reframe — "the main and first goal is to give each tenant fast and thorough search and discoverability" — corrected (1) more decisively: per-tenant search quality is the actual product question; multi-tenant load is downstream, not primary.

The gates are reordered accordingly. Phase-0 must complete before Session 05's substantive engineering work begins. Total budget: ~2 sprints (the revised gate set is more empirically demanding). See docs/research/2026-05-01_search-engine-comparison/prototype-notes.md for full gate design.

Gate 1 — Per-tenant search-quality benchmark (PRIMARY)​

The actual product question: does each tenant's researcher get fast and thorough search to find relevant term pages? This is a single-tenant test, not a multi-tenant test. Each tenant's data is indexed on three candidate engines (5th-revision: ParadeDB added as third candidate) on a single-node container; the same curated query set runs against each engine for that tenant.

Three Gate 1 engines per tenant:

  1. PGroonga (Postgres extension; general-multilingual; bigram for CJK; lightest operationally)
  2. ParadeDB (Postgres extension; BM25 via Tantivy; Lucene-family ranking; in-Postgres; narrower analyzer ecosystem than OpenSearch)
  3. OpenSearch + paired-strategy (separate service; broadest Lucene analyzer ecosystem; Gate 2's paired-strategy preprocessing for Classical Chinese)

Per-tenant verdict from Gate 1 is expected to vary by tenant. Possible outcomes:

  • A small Greek+Latin tenant may land on ParadeDB (in-Postgres + Lucene-family BM25 + ICU folding sufficient).
  • A multilingual classical tenant with Arabic root extraction needs may land on OpenSearch (lucene-arabic-analyzer is decisive).
  • A general-multilingual tenant with no specific Lucene-analyzer requirement may land on PGroonga (operational simplicity wins).

Per-tenant retreat is a first-class outcome, not a fallback hack. Each tenant's slot config is independent (ADR-012); engine choice can vary per tenant without code forks.

Test corpus: each existing tenant's EpistemicEntity rows, indexed in their own schema. No multi-tenant sharing during Gate 1.

Curated query set per tenant (~10-15 queries each, authored from canonical scholarly-domain expertise — not from measured user logs, since the platform is pre-launch and niche-scholarly-field user volume will not materialize at the cadence Phase-0 needs). The query set is explicitly modeled, not measured; measurement-based revalidation becomes a post-launch concern (see follow-up below). Initial seed:

  • Tenant A: Ancient Greek polytonic (e.g., αλφα finds ἄλφα and άλφα); Latin treatise abbreviations; English transliteration of Greek lemmas.
  • Tenant B: Arabic root-based (e.g., كتب finds كتاب, كاتب, مكتبة); English-Arabic cross-references; Classical Arabic with diacritics.
  • Tenant D: Classical Chinese personal/place names (e.g., 也的沙, 起輦谷); Han chronicle titles; mixed-script citation strings.

Risk budget (per-tenant; quality + cost dimensions per the 5th revision):

Quality:

  • Recall ≥ 80% on curated queries against a manually-prepared ground-truth set.
  • p95 search latency ≤ 200 ms (single-tenant, single-node — strictly better than the multi-tenant 500 ms threshold of Gate 3).
  • "Find relevant term pages" — for representative researcher queries, the relevant term page appears in the top-5 results.

Cost / speed / stability (5th-revision; from external research on canonical-data-derivation patterns):

  • Index size: ≤ 3× canonical-data size per tenant (the index is a derived projection, not a duplicate of the source). Industry rough rule from research; refine empirically per tenant if Gate 1 reveals tighter or looser practical limits.
  • Write amplification: ≤ 2× canonical-DB write latency under continuous indexing load. Tested by inserting 1K EpistemicEntity rows and measuring INSERT latency with/without index sync enabled.
  • Propagation latency (canonical change → searchable): ≤ 30s in batch mode; ≤ 5s if streaming is implemented. Measured by timestamping a canonical INSERT and a successful query for the new row.
  • Multi-cloud compatibility: engine runs on AWS or GCP without vendor-specific lock-in (all three candidates pass: Apache 2 / open-source).
  • Flat infra cost under varying user load: cost is invariant to query count + concurrent users. No per-query / per-record pricing models in scope (rules out Algolia, Elasticsearch Cloud commercial tier; the three Phase-0 candidates all qualify).

Pass: a tenant meets quality + cost/speed/stability budgets on at least one engine. Fail: that tenant may need custom analyzer development or specialized infra; document and flag.

Per-tenant outcome: each tenant lands on the engine that best meets its specific budget profile. ATLOMY's small corpus + Greek+Latin-only need may favor in-Postgres engines (PGroonga or ParadeDB); JPP's CJK + faceted-compound needs likely favor OpenSearch despite higher operational cost. Three different engines for three tenants is an acceptable Phase-0 outcome.

Gate 2 — Paired-strategy validation against measured queries (was the old Gate A)​

The earlier Gate A confirmed paired-strategy is empirically necessary against the corpus statistics (41.5% jieba_fewer_tokens, 7.0% jieba_more_tokens). Gate 2 validates this against the measured query log from Gate 0:

  • Of the ≥ 50 captured queries per Chinese-bearing tenant, how many trigger the paired-strategy benefit (jieba_fewer_tokens scenarios) vs. the bigram-rescue (jieba_more_tokens scenarios)?
  • Does the doubled index size + ranking complexity justify the marginal recall benefit on measured queries?

Pass: ≥ 5% of measured queries demonstrably benefit from paired-strategy over either single-strategy alternative. Fail: simplify to a single-strategy indexer per tenant slot; document that the corpus-statistic 7% jieba_more_tokens rate did not translate to user-facing recall misses.

Gate 3 — Multi-tenant load test (was the old Gate B; now SECONDARY)​

Only meaningful after Gate 1 confirms per-tenant search quality is achievable on the chosen engine. Gate 3 tests whether multi-tenant operation is sustainable on the team's actual deployment-engineering capacity.

Test infrastructure: 3-node OpenSearch cluster + ≥1 replica + JVM heap 2 GB/node. Plugins: analysis-icu, analysis-smartcn, analysis-stconvert, analysis-kuromoji, lucene-arabic-analyzer. Parallel PGroonga deployment on identical hardware.

Risk budget (any single threshold breach triggers retreat):

  • JVM heap usage ≤ 80% under multi-tenant load.
  • p95 search latency ≤ 500 ms across the workload mix.
  • Indexing throughput: full reindex per tenant ≤ 30 min for ~10K-scale per-tenant data.
  • Noisy-neighbor: no tenant's queries see > 2× p95 latency degradation.
  • Zero utf8mb3 character truncation.

Pass: all thresholds met. Fail: immediate retreat to PGroonga (engine-wide), or per-tenant split if Gate 1 already validated the lighter-load tenants on OpenSearch.

Gate 4 — Per-tenant onboarding cost (was the old Gate C)​

Onboard a new-language tenant (Hebrew via analysis-hebrew community plugin, smoke test). Pass: ≤ 4 hours, fully declarative (no per-tenant Python). Fail: do not change verdict but weaken the "as tenants arrive" framing.

Query logging — post-Phase-0 follow-up (NOT a gate)​

A lightweight always-on opt-in query logger ships separately from Phase-0 (cheap; days of work) and starts collecting search strings + tenant context + result counts + clicked-result IDs whenever any tenant has any users. No gate blocks on its accumulation. Once a tenant has measurable user volume (post-launch, when scholarly-research uptake materializes), the logged queries become the basis for revalidating Gate 2's paired-strategy verdict against measured behavior. Until then, Gate 1's curated canonical query set is the best signal available and is honest about its evidentiary status: domain-expert-authored, not user-measured.

This is consistent with the platform's actual user-base reality (pre-launch; niche scholarly fields; few per-project researchers; admin/data-entry interfaces are the dominant search surface at launch, not the public search bar). A measured-query gate would have introduced a 2-week stall waiting for data that does not arrive at Phase-0 cadence.

Custom-dictionary path (revised — automated from canonical Postgres tables)​

Replaces the original ADR-011 estimate of "100-200 entries pulled from high-frequency entity name patterns" — that estimate was three orders of magnitude too small for a serious prosopographic corpus.

Implementation: epistemic/services/indexer/dict_generator.py reads the tenant schema's EpistemicEntity rows at index-build time and emits person names, place names, and high-frequency keyword forms to a .dict file native to OpenSearch analyzer plugins. The dict scales with the corpus automatically; researchers add new historical aliases via the existing data-import pipeline (parser + LLM + reviewer materialization), and the search engine's dictionary learns them on the next sync.

Maintenance burden shifts from "human lexicographer typing a text file" to "existing database ingestion workflow." This is consistent with ADR-012's runtime-config principle: data drives configuration, not code.

For the prosopography corpus, this means automatic coverage of all 13,884 person names + 4,023 place names + 7,616 keyword-name forms, vs. a hand-curated 200-entry dict — a coverage improvement of ~125×.

Swap and Escalation Criteria (revised — per-tenant retreat is allowed)​

The swap criteria are now immediate-trigger rather than time-deferred, AND can apply per-tenant rather than only engine-wide:

Per-tenant retreat trigger — for a single tenant, retreat to PGroonga (with same indexer-adapter shape) if:

  1. Gate 1 fails for that tenant — per-tenant search quality (≥80% recall, ≤200ms p95, top-5 relevance) cannot be achieved on OpenSearch within the gate budget. The other tenants may still proceed on OpenSearch.

Engine-wide retreat trigger — retreat all tenants to PGroonga if:

  1. Gate 1 fails for ≥2 tenants — per-tenant search quality is broadly unattainable on OpenSearch.
  2. Gate 3 fails during Phase-0 — multi-tenant load on production-shape infrastructure exceeds the risk budget. Retreat is immediate, not deferred.
  3. Gate 2 fails AND OpenSearch's primary justification weakens to the point that PGroonga's operational simplicity outweighs its analyzer gap.
  4. Post-launch: documented sustained operational incidents that exceed deployment-engineering capacity. (Time-bounded: if 2 distinct incidents in any rolling 90-day window cause user-facing search outages, evaluate retreat at that moment, not at 6 months.)

Intra-OpenSearch escalations (not engine swap) for languages where Lucene plugins underdeliver after Phase-0 passes:

  1. Per-language Python preprocessing — Classical Chinese pre-segmentation, Coptic, Aramaic, niche Sanskrit. Triggered by ≥ 3 distinct user complaints per quarter per tenant about a specific language's recall.
  2. Lucene custom analyzer development for niche classical languages.
  3. Specialized DH backend (PhiloLogic, Lucene fork, dedicated NLP pipeline) for single-tenant needs.

The swap path is intentionally an adapter swap, not a rebuild. Indexer structured around build_search_document(entity, slot_config) -> dict. OpenSearch and PGroonga are alternative concretions of that interface; the schema layer (TenantArchetypeFormConfig columns) and the GraphQL surface are engine-agnostic. Because each tenant's slot config is independent (per ADR-012), per-tenant retreat is a first-class outcome, not a fallback hack.

Federation positioning (revised — fully severed from evaluation criteria)​

Round-1 critique downgraded federated_discovery_spec (2026-02-03 draft) from "forcing function" to "informing factor"; Round-2 critique pressed harder, observing that letting an unbuilt draft spec inform present-day infrastructure at all is still premature optimization — especially when the cited DH precedents (Wikimedia, Sketch Engine, Perseus) operate at 1000–10,000× the platform's near-term scale where Lucene's operational cost amortizes against throughput. At Atlas's scale, that amortization is far weaker.

Combined with the user reframe — "per-tenant fast and thorough search and discoverability is the main and first goal" — federation is now fully severed from ADR-011's evaluation criteria:

  • Engine choice is evaluated strictly on: (a) per-tenant search quality (Gate 1) + (b) operational cost on current deployment-engineering capacity (Gate 3) + (c) per-tenant onboarding cost (Gate 4).
  • Federation is not an evaluation criterion for ADR-011, even as informing factor. It is a separate concern with a separate ADR boundary.
  • A localized adapter strategy is the future-federation pattern: each tenant's local index (whatever engine) syncs to a future federation tier via an asynchronous adapter at federation time. Engine-agnostic at the federation layer. This decouples local search architecture from any 2027+ federation aspiration entirely.

The OpenSearch verdict now stands on (a) language coverage breadth via the Lucene analyzer ecosystem + (b) the strangler-adapter realization over v1's existing-but-dumb ES service. If Phase-0 invalidates (a) per-tenant or operational cost (Gate 3) overwhelms (b), retreat is triggered. Federation contributes nothing to either side of that calculation.

Cost, speed, stability, and user-tier model (5th-revision)​

External research (two independent agents on the canonical-data-derivation pattern, no Atlas context) validated the architectural direction and surfaced cost/speed/stability dimensions that Phase-0 hadn't budgeted. Combined with user-stated constraints — multi-cloud (AWS/GCP), flat infra cost, no per-query/per-record pricing, different search capabilities for different user types — these dimensions are now explicit evaluation criteria.

Cost dimension​

  • Flat infra cost is required. Per-query / per-record pricing models (Algolia, Elasticsearch Cloud commercial tier, certain managed search SaaS) are ruled out. The platform should pay for fixed infrastructure regardless of user count or query volume.
  • All three Phase-0 candidates qualify: PGroonga and ParadeDB run inside Postgres (no extra service cost). Self-hosted OpenSearch (Apache 2 license) on EC2/GCE/GKE is flat-cost. AWS managed OpenSearch Service is per-instance (not per-query) — also acceptable.
  • No vendor lock-in. Apache 2 license + multi-cloud compatibility is an explicit selection criterion. All three candidates satisfy.

Speed dimension​

  • Read latency (search query) is the primary user-facing metric. Gate 1 budget: p95 ≤ 200 ms single-tenant single-node.
  • Write amplification is the cost paid on the canonical DB. Gate 1 budget: ≤ 2× INSERT latency under continuous indexing load.
  • Propagation latency (canonical change → searchable) is the freshness vs. throughput tradeoff. Gate 1 budget: ≤ 30s batch; ≤ 5s if streaming is implemented.

Stability dimension​

  • Index size budget per tenant: ≤ 3× canonical data size (industry rough rule per research; refine empirically). Larger ratios indicate over-indexing — symptoms include indexing every field instead of searchable=True slots only.
  • Failure modes documented per engine. PGroonga: no-search-during-postgres-restart but recovers automatically. ParadeDB: same. OpenSearch: cluster failures need manual intervention; mitigated by having only one cluster + retreat target available.
  • Operational complexity scales with engine count. Three engines across three tenants is acceptable because each tenant's slot config is independent and the indexer adapter shape (build_search_document(entity, slot_config) -> dict) is engine-agnostic; but the platform team will need to operate all three. Phase-0 outcome will inform whether one engine ends up dominant in practice.

Structural-vs-curated line (auto-derive vs hand-curate)​

Research surfaced a sharp line:

Auto-derived from canonical dataStill hand-curated by experts
Which entities and fields exist (slot config)Relevance models (BM25 weights, boosts, decay)
Allowed values, vocabularies → dictionariesQuery strategies (multi-field, fuzziness, completion suggester tuning)
Relationships between entities (joins, aggregations)Index-specific structures (n-grams, chunking, vector dimensions)
Synonym tables → analyzer synonym filesAnalyzer choice per slot (which Lucene analyzer? which custom dict?)
Per-archetype dict generation (person names, places, keywords)Per-tenant ranking + boost tuning (search_boost column)

Implication: dict_generator.py automates the structural skeleton of search configuration (which fields are searchable, which slot-values become tokens, which canonical names feed the analyzer dict). Relevance tuning, analyzer choice, BM25 weight adjustments remain expert decisions per tenant — encoded in TenantArchetypeFormConfig's search_boost column and slot-level analyzer metadata, not derived from canonical data.

User-tier model (deferred to Phase-1)​

User-stated requirement: "different levels of search ability for different user types … without us paying through the roof or at all for how much users use it or how many."

Interpretation: the platform should support role-based feature gating at the GraphQL search-resolver layer (one engine, multiple feature sets) rather than separate engines per tier. Anonymous users get basic full-text search; registered scholars get faceted exploration + autocomplete; premium users (when defined) get vector similarity, AI rerank, etc.

Phase-0 implication: the chosen engine must SUPPORT premium-tier features (vector similarity, AI rerank, completion suggester, cross-tenant federation) even if Phase-0 doesn't enable them. OpenSearch wins on this axis natively. ParadeDB has BM25 + native Postgres indexes for vectors via pgvector extension. PGroonga is weaker on vector search.

Phase-1 implication: implement role-based feature gating at the GraphQL resolver layer; document tier-to-feature mapping; ensure flat infra cost (no per-query pricing in any path).

This is deferred from Phase-0 — Phase-0 focuses on per-tenant search quality (Gate 1) on each engine; Phase-1 adds the tier model on top of the chosen engine(s).

Dictionary scope refinement (5th-revision)​

Research-derived refinement to the automated dict_generator.py design:

Old (4th revision): one .dict file per tenant from canonical name tables.

New (5th revision): scoped per archetype/language within each tenant. Reasons (from research):

  • "Generate scoped synonym/lexicon files (per language, per product area) instead of a global mega-dictionary; this keeps FTS and Lucene analyzers fast and cheaper to maintain."
  • Smaller dict files load faster, regenerate cheaper on canonical change, and isolate failures.

Implementation: dict_generator.py emits one dict per (tenant_schema × archetype × language) combination:

{schema}_person_names.dict      # ENTITY archetype, name slot, all languages
{schema}_place_names.dict       # PLACE/ENTITY where slot type=place
{schema}_keywords.dict          # KEYWORD/RELATIONSHIP archetype where slot type=keyword/tag
{schema}_periods.dict           # PERIOD/EVENT archetype, period names

Each dict file is incrementally regenerated when its source rows change, not on every canonical write. The slot config (searchable/facet columns on TenantArchetypeFormConfig) determines which slots contribute to which dicts. Slots with no searchable/facet flag don't reach any dict.

This embodies the research-derived principle: "design read models per use-case, not 'mirror the DB'." Atlas's dict generator derives scoped dicts from canonical data; doesn't blindly export every column.

## Implementation Notes (Session 05)​

The Session-05 spec breaks into three reviewer surfaces:

  1. Decision + canonical structure: this ADR + a migration adding searchable / facet / autocomplete_eligible / search_boost columns to TenantArchetypeFormConfig (defaults only — no tenant-specific values, per ADR-012). Materialization-service extension to propagate the four fields from MappingProposal.parser_payload / llm_payload (mirror of the 04b extension for resolver_args/widget/label).
  2. Generic indexer: epistemic/services/indexer/opensearch.py reading TenantArchetypeFormConfig. Builds OpenSearch index mapping per tenant + archetype, with analyzer chains chosen from declared language metadata. Handles source_layer=OPERATIONAL (Django ORM walks for legacy v1 anchor-tenant tables) and source_layer=EPISTEMIC (EpistemicEntity.data JSONB). Wires MultilingualProcessor as supplementary preprocessing for languages where Lucene plugins underdeliver. Reindex maintained via Django signals on EpistemicEntity + Lemma (transitional dual-source — ADR-013 will collapse).
  3. GraphQL + SPA + tests: search, autocomplete, searchFacets resolvers in the v1 platform GraphQL schema module (de-facto platform GraphQL surface — note placement debt for a separate refactor). Tenant-scoped via schema_context and {schema_name}_{archetype}_index index naming. SPA: search bar + autocomplete + faceted sidebar in spa/src/apps/anchor_explorer/. Tests: GraphQL integration, tenant isolation, perf smoke (p50 < 100ms on full Tenant A Lemma dataset on the existing single-node ES container).

The prototype starts Tenant A-only with a single ICU-folding analyzer chain plus asciifolding + an explicit Greek polytonic stack. Tenant B Arabic root-analysis, Tenant D CJK plugins, and Tenant C per-language stemming follow as those tenants onboard — incrementally, not as a big-bang Session 05 deliverable.
