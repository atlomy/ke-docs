ADR 055: Evidence-Gated Deferrals Must Instrument Their Un-Defer Trigger

  • Status: Accepted (owner-directed 2026-06-03; implementation scoped below)
  • Date: 2026-06-03
  • Deciders: Premshay (platform owner, directing the requirement), assistant
  • Context source: Overnight ADR-054 session — the platform owner observed that the recent arcs (ADR-054, Spec 0040) defer machinery "until operational evidence justifies it" but nothing measures the evidence, so the deferrals can never trigger and the signal reaches neither the superadmin dashboards nor the agents.

Context​

The platform's greenfield discipline is "seams now, machinery on evidence" (ADR-054): cheap abstraction boundaries are placed now; the expensive machinery behind them (transactional outbox, per-tenant claim-lock, worker-tier split, chunked materialize, OpenTelemetry, durable-workflow engines) is deferred until operational evidence justifies it. Spec 0010 states the same ("modular monolith first, split only where operational evidence justifies").

The hole: an evidence-gated deferral with no instrumentation is a silent permanent deferral. Each deferral names an un-defer trigger ("if the dual-write gap proves unacceptable…", "split the worker tier where evidence justifies…"), but no metric measures the trigger signal. So the evidence never arrives — to the superadmin telemetry dashboards (humans deciding to invest) or to the agents (a future session-start deciding to revisit a deferral). The deferral decision is honest only if its trigger is observable.

A telemetry substrate already exists and import runs already emit into it — telemetry.models.IngestionRunEvent (run_metrics is an open JSONField), DecisionEvent, and StratumHealth (periodic rollup snapshots), via telemetry/services/ingestion.py (capture_ingestion_run / record_run_metrics / record_materializer_output); data_import/services/import_job_telemetry.py already records routing signals (e.g. route_cap, size_bucket); the superadmin surface is atlomyapp/dashboard.py (dashboard_callback panels). So this needs no new substrate — it needs deferral-trigger metrics on it, a dashboard panel, and an agent digest.

Decision​

Every evidence-gated deferral MUST ship with its un-defer trigger instrumented. Concretely, a deferral is not "done" until:

  1. A deferral-trigger metric measures the signal whose threshold would justify un-deferral, emitted on the existing telemetry substrate (IngestionRunEvent.run_metrics via record_run_metrics, or a DecisionEvent/rollup where a per-run metric is the wrong grain). The metric carries an explicit named threshold (the level at which the deferral should be revisited).
  2. It surfaces on the superadmin telemetry dashboard — a "Deferral Evidence" panel (in dashboard_callback) showing each tracked deferral's current signal vs its threshold and a clear threshold-crossed? indicator, so the human deciding to invest sees the evidence.
  3. It surfaces to agents — a compact, agent-readable "operational-evidence" digest (a management command + a section the session-start hook can include / state.md can point at), so a future session-start agent sees when a deferral's evidence has crossed and the deferral should be revisited. This closes the loop the deferral opened.

This makes "defer until evidence" a falsifiable commitment rather than a euphemism for "never."

Alternatives considered​

  • Instrument only when un-deferring (gather evidence reactively once someone suspects a problem). Rejected: you cannot know to look without the signal; the incident that proves "evidence arrived" (a starved tenant, a lost job, a timeout) is the very harm the deferral promised to pre-empt.
  • Adopt OpenTelemetry first, then build deferral metrics on it. Rejected as sequencing: OTel is itself one of ADR-054's deferrals; the deferral-trigger metrics ride the existing substrate today and do not block on it (OTel adoption can later carry them).
  • Dashboards only (no agent digest). Rejected: the agents are first-class operators of this platform and make the un-defer recommendations between human reviews; evidence that only a human can see breaks the agent-in-the-loop workflow the owner called out.

Consequences​

Positive​

  • The deferrals become honest and self-auditing; the platform learns when to invest, with the same signal reaching humans and agents.
  • Near-zero new infrastructure — rides IngestionRunEvent.run_metrics + the existing dashboard/rollup precedents.

Negative​

  • A small standing instrumentation cost at each deferral site (emit the trigger metric) and the discipline to keep the threshold honest.
  • Risk of metric sprawl if every micro-deferral spawns a metric — mitigated by scoping to the named deferrals in an ADR/spec, not every TODO.

Neutral​

  • The agent digest is a new artifact the session-start surface consumes; it composes with state.md (which already carries open-questions) rather than replacing it.

Build phases (follow-up): (P1) emit the cheap trigger metrics at the materialize/dispatch/upload sites via record_run_metrics (additive, low-risk); (P2) a "Deferral Evidence" panel in dashboard_callback aggregating run_metrics vs thresholds; (P3) an operational_evidence_digest management command + session-start inclusion (the agent surface). Each phase is independently shippable; P1 is the gate (no panel/digest without the data).

P1 status (SHIPPED 2026-06-04, PR #473): five data_import-resident trigger metrics emit onto IngestionRunEvent.run_metrics under one shared deferral_evidence signal — materialize_wall_ms / edge_count / entity_count + concurrent_materialize_collision_count (the materialize worker, the latter on the already-MATERIALIZED idempotency guard) and dispatch_publish_lost_count (the scheduler sweeper, via the deterministic is_orphaned_dispatch detector: post-claim attempt_count == 1 + run_after ≈ created_at + age past the beat window). Emission is threshold-free; the illustrative thresholds live in data_import/services/deferral_evidence.py (owner pins). Capture is owner-gated: the metrics ride the existing ingestion_run capture flag, OFF by default (DPIA-pending) — the same dormant gate the existing materialize/scheduler telemetry already rides. So P1 is wired-but-dormant until the owner enables capture. That is the explicit, documented owner decision this ADR demands — NOT a silent permanent deferral, because the gate is documented and owner-pending.

P2 status (PARTIAL — per-tenant panel SHIPPED 2026-06-04, PR #474; cross-tenant superadmin view NOT built): a "Deferral evidence" panel in the KE dashboard (atlomyapp/dashboard.py _ke_dashboard_panels → templates/admin/ke/_dashboard_panels.html, rendered via the index.html include) aggregates the current tenant's deferral_evidence signal over the recent IngestionRunEvent window via summarize_deferral_evidence (gauges→max, counters→sum) and shows each metric's value vs its threshold with an over/ok/none indicator. The header surfaces whether ingestion_run capture is on; dormant (the default) renders an explicit "enable capture" message, so the panel advertises the owner-gated enablement.

Grain gap (honest record): this is a per-tenant panel — it renders on each tenant's dashboard against that tenant's telemetry. It does NOT yet satisfy the superadmin surface this ADR's Decision §2 names: telemetry is a tenant-only app, so on the public/superadmin schema the panel shows "dormant" regardless of what tenants recorded. A true cross-tenant superadmin rollup (one public-schema view aggregating all tenants) is a distinct, unbuilt increment — and P3's agent digest does not cover it either (different consumer: a management-command digest, not a human superadmin dashboard). Owner decision: fold the cross-tenant rollup into P2 (iterate tenant schemas in a public-schema panel) or track it as its own increment.

P2 correction (2026-06-04, follow-up PR): the owner chose fold — and named the real defect. The per-tenant Unfold dashboard panel was an implementation divergence from this ADR's Decision §2 ("surfaces on the superadmin telemetry dashboard"). That dashboard already existed and was live — the React Platform Admin at /admin/monitoring/platform/ (Spec 0018 Sprint C) — and the per-tenant panel was built against the wrong surface without checking it (a discoverability miss, not a grain choice). Corrected: a fleet-aggregate "Deferral evidence" panel now lives on the Platform Admin Operations tab, backed by the platformDeferralEvidence GraphQL query (require_platform_staff-gated) → build_platform_deferral_evidence_summary (gauges → fleet-MAX, counters → fleet-SUM across all tenant schemas; no tenant identity surfaced, per the Spec 0018 K-anon/hashing discipline). The un-defer decision is platform-scoped ("trigger this deferral across the platform?"), so a fleet aggregate — not a per-tenant breakdown — is the correct grain; per-tenant hashed/K-gated drilldown is a possible later increment only if an operator needs to investigate which tenant. The per-tenant Unfold panel (_ke_dashboard_panels deferral block + its template panel + test_deferral_evidence_dashboard.py) was removed — it had no tenant consumer. The proposal/Lemma savepoints noted below stay. Capture enablement: ingestion_run is now env-gated (KE_CAPTURE_INGESTION_RUN, default OFF) — no-PII (ADR-016 §2) and independent of decision_event, so enabling it does NOT trip the DPIA-refresh machinery; the panel reads "capture dormant" until it is enabled.

Drive-by robustness fix: the existing proposal/Lemma panel probes now run inside transaction.atomic() savepoints so a missing table on a non-atlas-shape tenant no longer poisons the transaction for downstream panels.

P3 status (SHIPPED 2026-06-04, PR #475): the operational_evidence_digest management command (telemetry/management/commands/) + the build_operational_evidence_digest service iterate all tenant schemas and report, per tenant, which deferrals have crossed their threshold + whether capture is on — the cross-tenant view for the agent consumer that the per-tenant P2 panel does not provide (it also closes the P2 grain gap for agents, though not for a human superadmin dashboard). --json for machine consumption, --crossed-only/--schema filters; unreadable tenants are skipped, not failed. Agent surface: state.md points at the command (cat'd by the session-start hook) — a deliberately lighter wiring than running a container exec inside the host hook, which would couple session-start to the container being up and add latency for a signal that is dormant until capture is enabled.

Phased past P1: llm_in_request_ms → P1.b (needs a cross-app contextvar bridge from the epistemic proposal path back to the import telemetry recorder; reads ~0 under the default mock LLM, so phasing loses no current evidence). inline_credential_queue_wait_ms, the per-tenant-fairness pair (tenant_queue_wait_ms p95 + jobs_pending_per_tenant), and the Spec-0040 B2 routing weight instrument at their own deferral sites (the inline-key Redis store, the scheduler, the router) and are tracked for a later increment.

Open question (owner — proposed, not built): should the deferral-evidence metrics — PII-free operational counters by construction — ride a separate capture class enableable without the full content-DPIA, so operational evidence can flow before ingestion-content capture is cleared? Left as a possible ADR-055 amendment rather than implemented overnight, because building it would make a privacy-exemption determination that is the owner's and add the very substrate this ADR says to avoid.

Finding W trigger evidence (2026-06-09): the worker-tier-split / chunked-materialize trigger metrics (materialize_wall_ms / edge_count / entity_count) now have their first profiling evidence — a cProfile pin of the two materialize hot paths (re-apply bulk_update CASE/WHEN explosion vs first-import edge N+1 + per-edge hashing). Recorded under ADR-054's Implementation notes → "Finding W — materialize hot-path profiling evidence"; the cheap re-apply skip-unchanged win shipped, the chunked/worker-tier machinery stays deferred behind these metrics.
