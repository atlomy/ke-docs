ADR-045: Chat-transcript retention regime for in-product AI chat surfaces

  • Status: Proposed
  • Date: 2026-05-24
  • Deciders: User; architecture team
  • Context source: ADR-044 Open Question Q1 (chat-transcript retention is the only platform-wide concern ADR-044 surfaced but could not resolve); ADR-014-α activation 2026-05-21 codifying single-call assist + ambient chat as the in-product AI baseline; partner_model entry 2026-05-24:722-748 (chat is platform intent, not opt-in)
  • Related: ADR-014-α (In-Product AI Runtime — single-call assist contract; this ADR adds the retention regime under that umbrella), ADR-016 (Telemetry Substrate — inherited for redact-before-log discipline, retention defaults, classifier integration, pseudonymisation, Art. 17 erasure pattern; ADR-016 explicitly scoped to three signal classes and excluded chat, leaving this ADR to fill the gap), ADR-044 (Voice and vocabulary substrate — discipline-priors chat at import start is the first downstream consumer requiring this regime), Spec 0017 C.3 (ambient chat — first chat surface, already shipped, currently follows session-only by implementation accident), Spec 0020 v1.2 §10.2 Wave 2 (AI-assisted manual grounding — sibling consumer under ADR-014-α)

TL;DR​

KE has shipped one chat surface (Spec 0017 C.3 ambient chat) and will ship more under ADR-014-α (Spec 0020 v1.2 §10.2 Wave 2 next; ADR-044 Phase 3 discipline-priors chat; future agent-resolver-epic surfaces). ADR-016 (telemetry substrate) explicitly scoped to three signal classes (LLM-call / search-query / ingestion-run) and excluded chat. No platform-level rule on chat-transcript retention exists today. This ADR fills that gap: chat transcripts default to session-only (not persisted beyond the active session); structured outputs extracted from chat (ImportContext, suggestion outcomes) persist under their own per-output retention; longer retention requires explicit per-surface justification + DPIA delta + tenant DPA template language. The regime composes with ADR-014-α bounded-agency and ADR-016 redact-before-log discipline; it does not replace either.

Context​

What "chat" means here​

Any in-product surface where the platform exchanges multiple turns of free-form text with a user, where each turn includes user-authored content and AI-generated content, and where the exchange is bounded to a single workflow surface per ADR-014-α §1 scope. Examples:

  • Spec 0017 C.3 ambient chat in the import wizard (shipped)
  • ADR-044 Phase 3 discipline-priors chat at import start (planned)
  • Spec 0020 v1.2 §10.2 Wave 2 AI-assisted manual grounding (planned)
  • Future tenant-bootstrap onboarding chat (planned)
  • Future agent-resolver-epic chat surfaces (in research)

Single-call LLM patterns (one prompt, one response, no multi-turn exchange) fall under ADR-014-α §1 directly and do not produce chat transcripts in the sense this ADR governs. The user-prompt and model-response are still subject to ADR-016 redact-before-log telemetry, but they are not "chat" for this regime.

Why no rule exists today​

ADR-016 (telemetry substrate, Approved) scoped explicitly to three signal classes: LLM-call records, search-query records, and ingestion-run records. Chat was deliberately not enumerated, partly because Spec 0017 C.3 ambient chat was the only chat surface in production at ADR-016's drafting time and its retention behavior was bounded by implementation (session-state, not persisted), not by policy.

The implementation-accident situation is not stable. Three pressures force the question now:

  1. ADR-044 Phase 3 discipline-priors chat introduces a new chat surface that captures free-form researcher self-description ("what are you bringing in this time?"). The extracted structured output (ImportContext) needs persistence to be useful to downstream wizard stages. The raw transcript bytes do not necessarily need persistence — but the policy question must be answered before Phase 3 codes.

  2. Spec 0020 v1.2 §10.2 Wave 2 ships AI-assisted manual grounding, where admins converse with the AI to refine vocabulary suggestions. The exchange may produce learning signal (which suggestions admins accept / reject / refine in conversation) the platform's recommender wants.

  3. The agent-resolver-epic (in research) anticipates multi-step agent loops under a future ADR-014-β. Multi-step loops produce longer transcripts with more state.

What ADR-016 already gives us (and what it doesn't cover)​

ADR-016 §2 establishes:

  • Redact-before-log discipline for free-text values entering telemetry storage. Verbatim free-text retention defaults to 30 days; hashed/aggregate retention beyond that.
  • injection_classifier_verdict enum on every LLM-call row, with quarantine routing per §6.3 when verdict is confirmed_injection.
  • Pseudonymisation via per-tenant HMAC key for personal data that needs retention beyond the verbatim window (§3).
  • Art. 17 erasure pattern: redact in place, don't delete row (preserves audit per §8).
  • Tenant.is_used_for_coursework gate for FERPA-mode tenants (§6).

These mechanisms are directly applicable to chat transcripts. What ADR-016 does NOT specify:

  • Whether chat transcripts are subject to the same 30-day verbatim default or a stricter default
  • Whether transcripts are stored centrally (in telemetry/ tables) or per-tenant (in tenant-schema tables)
  • How structured outputs extracted from transcripts (ImportContext, suggestion outcomes, agent observations) relate to the underlying transcript bytes for retention purposes
  • Whether session-only is acceptable as a default or whether all chat must be at least minimally persisted for telemetry purposes

This ADR fills those gaps.

Platform principles and constraints this regime must honor​

  • GDPR Art. 5(1)(c) data minimisation: free-text personal data should be retained only as long as necessary for stated purposes.
  • GDPR Art. 5(1)(e) storage limitation: explicit time limits per data class.
  • CCPA §1798.140(v) "interaction with an application" personal data definition includes chat transcripts.
  • partner_model.md:349-354 discipline ("derivation is canonical; manual entry is escape hatch only") applies pragmatically: chat-extracted structured outputs should be derivation inputs, not manual-entry persistences.
  • ADR-014-α §1 bounded-agency: chat-produced AI output cannot mutate platform state without an explicit user action gated by ADR-035 capabilities. This narrows the threat model for transcript content — a malicious transcript cannot become a malicious action.

Decision​

Chat surfaces in KE follow a tiered retention regime under ADR-014-α bounded-agency and ADR-016 redact-before-log discipline.

1. Four retention tiers​

Every chat surface picks one tier at design time, recorded as transcript_retention on the chat surface's canonical implementation (e.g., AmbientChatSession class field, configuration constant, or equivalent).

TierBehaviorWhen to use
session_only (default)Transcript exists in session state only; discarded at session end. Structured outputs extracted before discard persist under their own retention.Default for all new chat surfaces. Use unless a specific persistence need is documented.
extract_onlyStructured-extraction is mandatory and physically distinct from session_only: the extractor runs on a turn-boundary trigger via an asynchronous transient memory broker that destroys raw bytes upon extraction completion (not at session-end policy promise — at extraction completion, in process memory only). The broker holds raw turn bytes ONLY long enough for the extractor to consume them, then immediately zeroes the buffer. Structured output (ImportContext, suggestion outcome, etc.) persists under its own retention. Raw transcript bytes NEVER reach disk under this tier. (R1 absorption A5) — distinguishes operationally from session_only, which allows raw bytes to live in standard session state until session close.When the chat is purpose-built to produce structured output AND the platform requires stronger guarantees than session_only's "raw bytes die at session end" (e.g., ADR-044 Phase 3 discipline-priors chat → ImportContext).
30_day_verbatim_with_redactTranscript persists for 30 days, subject to ADR-016 §2 redact-before-log discipline (HMAC-with-per-tenant-key pseudonymisation, classifier verdict captured, confirmed_injection quarantine). Hashed/aggregate rollup at 30-day expiry, retained for 12 months.When the platform needs the transcript for telemetry purposes (recommender training, suggestion-quality metrics) and the per-surface DPIA approves. Composes with ADR-016 telemetry tables.
research_consentedTranscript persists indefinitely subject to explicit per-user research consent flow (signed DPA addendum, opt-in toggle, individual record-level Art. 17 erasure on request).Only when a research study has IRB/ethics approval and the user has signed an additional consent. NOT for routine platform operation. Effectively never the default.

session_only is the floor. Anything above session_only is a deliberate, documented per-surface decision.

2. Per-surface implementation requirements​

Any chat surface that picks a tier above session_only MUST file the following before code ships:

  • Retention justification: one-paragraph rationale for why session-only is insufficient. "We might want it" is not a rationale.
  • DPIA delta: incremental data-protection impact assessment delta versus the platform baseline (parallel to ADR-016 §5 DPIA discipline for the three telemetry signal classes). Recorded in docs/runbooks/dpia-deltas/ (directory to be created on first use).
  • Tenant DPA template language: the per-surface retention promise added to the tenant Data Processing Agreement template, so prospective tenants see the regime before onboarding.
  • FERPA gate: if Tenant.is_used_for_coursework is true, the surface either disables transcript retention entirely for that tenant or uses pseudonymised storage that doesn't permit per-student re-identification.
  • Art. 17 erasure pathway: documented procedure for redacting a specific user's transcripts on request, consistent with ADR-016 §8 (redact-in-place, preserve audit).

session_only surfaces do not need the above (the default IS the policy).

(R1 absorption B12) CI-enforced tier-upgrade gate: a PR that changes any chat surface's transcript_retention from session_only or extract_only to a higher tier MUST include a docs/runbooks/dpia-deltas/<surface>-<date>.md file in the same commit. CI rejects the merge if the upgrade is detected without the DPIA delta file present. Policy alone won't hold against debugging-convenience pressure (cf. open critique: "first P1 bug requiring raw transcripts → developers quietly upgrade to 30-day"); CI enforcement is the mechanism.

(R1 absorption B10) Standardized DPA addendum generator: routine chat-escalation patterns (e.g., recommender-training opt-up from extract_only to 30_day_verbatim_with_redact) get pre-approved DPA addendum templates in docs/runbooks/dpa-templates/. A CI/CD module reads the chat surface's transcript_retention value + a metadata file declaring the chat's purpose, and auto-generates the boilerplate DPA addendum + DPIA-delta skeleton. Engineers fill in surface-specific blanks; they don't draft from scratch. This reduces the per-surface paperwork friction that would otherwise incentivize feature bundling (multiple unrelated chat features crammed into one surface to amortize the DPIA paperwork).

3. Structured outputs extracted from chat persist under their own retention​

When a chat surface extracts structured output — ImportContext populated by Phase 3 chat, suggestion outcome populated by Spec 0020 Wave 2 chat, agent observation populated by future agent-loop surfaces — the structured output is governed by its own retention rule, NOT by the transcript tier. Examples:

  • ADR-044 Phase 3 discipline-priors chat: extract_only tier. ImportContext persists on MappingProject.wizard_answers (existing JSONField); its retention follows the parent MappingProject lifecycle. Raw transcript bytes discarded at session end.
  • Spec 0020 Wave 2 chat: tier TBD by Spec 0020 design; structured suggestion-outcome rows persist in the existing telemetry tables under ADR-016 §2 retention.
  • Future agent-loop surfaces: tier and structured-output retention specified per ADR-014-β when β activates.

Structured outputs themselves are subject to GDPR Art. 5(1)(c) minimisation: only fields actually consumed downstream should be retained.

4. Sanitization and bounded-agency at the consumption boundary​

Per ADR-014-α §1 bounded-agency, transcript content (including malicious or prompt-injection-shaped content) cannot directly mutate platform state. The chat-side sanitization needs are therefore narrower than they would be without bounded-agency:

  • Telemetry integration: every LLM call within a chat surface emits a row under ADR-016 §2 with injection_classifier_verdict captured. Verdicts of confirmed_injection route the call to quarantine per ADR-016 §6.3 and the chat surface offers a graceful retry path.
  • Display sanitization: chat output rendered back to the user MUST escape HTML/Markdown that could allow XSS or content-spoofing in the chat surface's UI. Standard escaping discipline; no chat-specific exception.
  • Cross-tenant isolation: cache-scoping discipline from ADR-044 §Cache Scoping applies — chat session state is keyed by (connection.schema_name, session_id) derived from server-side state, never from user input.

5. Spec 0017 C.3 ambient chat — current state recorded, not changed​

Spec 0017 C.3 ambient chat currently operates by implementation as session_only (no transcript persistence). This ADR ratifies that behavior as policy. No code change required for the existing surface. If a future Spec 0017 amendment proposes upgrading the tier (e.g., for recommender training), it follows the per-surface implementation requirements in §2.

Alternatives considered​

(a) Persist everything by default (verbatim, indefinite)​

Rejected. Open-ended retention liability; violates GDPR Art. 5(1)(c) and (e); creates an outsized Art. 17 erasure burden; defeats the bounded-agency stance that says "we don't need the transcript to act."

(b) Persist nothing ever (no telemetry, no extraction)​

Rejected. Debugging chat issues, measuring suggestion quality, and producing structured outputs that the platform genuinely needs (ImportContext for matching priors; suggestion outcomes for the recommender) all require some form of persistence. Pure-zero is incompatible with ADR-014-α §1's "explain, suggest, propose for review" mandate.

(c) Per-surface ad-hoc decisions, no platform regime​

Rejected. This is the current state and has produced exactly one chat surface (Spec 0017 C.3) which happens to be session-only by implementation accident. Adding more chat surfaces without a regime would produce inconsistent retention behavior across the platform, no DPIA discipline, no tenant DPA template alignment, and an audit risk if a tenant discovers chat retention practices that don't match what they were told.

(d) Inherit ADR-016 §2 defaults wholesale (30-day verbatim default for chat)​

Rejected. ADR-016's 30-day default fits the telemetry use case (recommender training over weeks; observed signal patterns); it is overly retentive for chat where the structured output is usually what the platform needs and the raw bytes are exhaust. session_only as the floor produces a smaller default footprint while preserving the option to opt up.

Consequences​

Positive​

  • Clear default for every new chat surface: pick a tier, justify if above floor, ship.
  • Aligns with GDPR data minimisation without making chat impossible.
  • Composes with existing platform discipline: ADR-014-α bounded-agency (narrows threat model), ADR-016 telemetry (provides per-call redact-before-log machinery, classifier integration, quarantine routing).
  • Per-surface DPIA + DPA discipline scales linearly with new chat surfaces and is explicit to prospective tenants.
  • Spec 0017 C.3 ambient chat is ratified as-is; no breaking change to a shipped surface.
  • ADR-044 Phase 3 discipline-priors chat unblocked: picks extract_only, ships under the regime.

Negative​

  • Adds per-surface paperwork (DPIA delta + DPA template addition) for any tier above session_only. Real friction for any team building a chat surface that needs retention.
  • session_only default makes some debugging harder: if a user reports "the chat said something weird," there is no transcript to inspect post-hoc unless the surface was already at 30_day_verbatim_with_redact or higher. Mitigation: surfaces can adopt opt-in instrumentation (user-initiated "save this conversation" button) without changing tier.
  • Research consent flow for research_consented tier is heavy and effectively limits that tier to formally-approved studies. This is intentional but means casual "let's collect chat data for a paper" is impossible without IRB/ethics review.
  • Structured-output retention is governed by its own rule (not transcript tier), which can confuse implementers: deleting a transcript does NOT necessarily delete the extracted output. Documentation discipline required.

Neutral​

  • The four-tier regime is novel relative to industry practice. Most consumer chat products either persist everything or follow ad-hoc per-feature rules. The tiered + per-surface DPIA discipline is closer to clinical-trial conversation handling than to consumer-AI chat handling. This fits KE's scholarly/multi-tenant posture.
  • 30_day_verbatim_with_redact and research_consented tiers exist but no current surface uses them. They are documented for completeness and for the future cases that will need them.
  • Implementation surface is per-chat-class field (e.g., AmbientChatSession.transcript_retention); no central registry table required initially. If chat surfaces proliferate, a central registry becomes useful and can be added.

Implementation notes​

Sprint D coordination with ADR-044​

ADR-044 Phase 3 discipline-priors chat ships under extract_only:

  • ImportContext extracted at session end (or per-turn for streaming context)
  • ImportContext persists on MappingProject.wizard_answers
  • Raw transcript bytes discarded at session end
  • No DPIA delta required (tier is extract_only, not above session_only for retention purposes — extract_only is a sibling of session_only, both at the floor for raw-byte retention)
  • AI-self-flagged-low-confidence offers to skip per ADR-044 Decision §7

Spec 0017 C.3 ambient chat retroactive ratification​

Add a one-line annotation to Spec 0017 §3 (or the ambient chat design subsection): "Transcript retention: session_only per ADR-045." No code change.

Spec 0020 v1.2 §10.2 Wave 2​

Spec 0020 design picks a tier. If above session_only, files DPIA delta and DPA addendum per §2 of this ADR before code ships.

Future agent-resolver-epic and ADR-014-β surfaces​

Each surface picks a tier per this ADR. Multi-step agent loops may have legitimate reasons for higher tiers (debugging multi-step plan failures requires more transcript than single-turn) but each must follow the per-surface implementation requirements.

docs/runbooks/dpia-deltas/ directory​

Created on first use (the first chat surface that picks a tier above session_only files the first DPIA delta there). Cross-references ADR-016 §5's main DPIA. Naming convention: dpia-delta-<surface-name>-<YYYY-MM-DD>.md.

Tenant DPA template language​

Append per-surface promise to the template when a tier above session_only is adopted. Suggested phrasing:

"Conversational interactions with [SURFACE NAME] are retained for [N days] in pseudonymised form to support [STATED PURPOSE], in accordance with the platform's chat-transcript retention regime (ADR-045). Tenants may exercise individual erasure rights per Art. 17 GDPR via [PROCEDURE]."

session_only surfaces do not need DPA template additions (the platform's default DPA already covers session-state transience).

Open questions​

Q1 — Sliding-window retention for 30_day_verbatim_with_redact​

Should the 30-day window be sliding (last 30 days at any moment) or anchored (first 30 days from session start)? Sliding gives consistent user experience; anchored gives consistent compliance accounting. Pick at first adoption of the tier; default suggestion: sliding.

Q2 — Cross-session continuity for extract_only surfaces​

If the same researcher returns next week and starts a new chat with the same surface, do extracted outputs from the prior session pre-load? For ADR-044 Phase 3 chat the answer is "yes via MappingProject.wizard_answers per-import scoping" (each import is its own project). For other surfaces this needs per-surface design.

Q3 — Research consent revocation handling for research_consented tier​

If a user withdraws research consent mid-study, what happens to their retained transcripts? Art. 17 erasure is the floor. Studies may need additional protocols (e.g., aggregate-level analysis already published cannot be retracted). Pick per study.

Q4 — Multi-step agent loop transcript shape (β scope)​

Multi-step agent loops produce structured plan / observation / re-plan transcripts that are more than chat. The tier regime here applies to the chat-shaped part; the structured plan-state may need its own retention story. Defer to ADR-014-β.
