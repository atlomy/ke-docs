ADR-015: Tenant Admin Shell as Native React Implementation of ADR-005's Shared React Shell

Status: Approved (with 2026-05-08 amendment — embed not standalone; scope-narrowed 2026-05-19 by ADR-036) Date: 2026-05-04 Deciders: Architecture team Related: ADR-001 (Epistemic vs Operational Separation), ADR-002 (Hybrid Ontology), ADR-003 (GraphQL Epistemic Contract), ADR-004 (Tenant Ontology Mapping), ADR-005 (React Integration Pattern), ADR-006 Rev 2.1 (Archetype Capability Contracts), ADR-010 (Parser-First / LLM-Second Relationship Resolution), ADR-012 (Tenant Config via Runtime Pipeline), ADR-036 (Workspace and Operations Surface Split — scope-narrows this ADR) Supersedes: nothing (formalizes a decision implicit in ADR-005's "Shared React Shell V2.0" mitigation) Companion spec: docs/superpowers/specs/2026-05-04_native-admin-shell-vertical-slice.md

2026-05-19 scope-narrowing note — read first​

This ADR's scope was narrowed by ADR-036 (Workspace and Operations Surface Split, 2026-05-19).

After ADR-036, this ADR governs only the operations admin substrate — the Django + Unfold pages hosting embedded React islands (imports, permissions, audit, telemetry, platform super-admin). The 2026-05-08 amendment below remains the controlling mount decision for those operations surfaces.

Researcher workspace surfaces — /app/workspace/<archetype>/, DB Views, Row Detail Drawer with split editor + live <PublicPreview>, search, saved views, multi-view (Board / Gallery / Calendar / Map / Timeline) — are governed by ADR-036.

What stays valid from this ADR for both surfaces:

  • Native React substrate ownership; external no-code path stays retired.
  • Free-tier libraries only (AG Grid Community v35, TanStack Query, Radix UI, react-hook-form, Tailwind, Plate via ADR-028).
  • Capability flags map 1:1 to React component variants.
  • Capability vocabulary is the platform contract; React composition is its rendering.
  • Reuse of shipped infrastructure (ArchetypeGrid, PlateFullEditor, MultilingualCellEditor, LinkedRecordCellEditor, SchemaEditModal, FormViewDrawer, SlotField).

What is no longer canonical from the original 2026-05-04 decision body below (preserved as historical record):

  • The "standalone Native React micro-app at /app/admin/" target. Per the 2026-05-08 amendment, /app/admin/ is deprecated; per ADR-036, the new researcher home is /app/workspace/<archetype>/, conceptually different from /app/admin/.
  • The Compliance line "standalone SPA at /app/admin/; no admin chrome" applies to workspace only, not operations admin. Operations admin uses Django + Unfold chrome (per 2026-05-08 amendment) hosting React islands.

The 2026-05-04 decision body below is preserved verbatim as historical context for what the original decision required and why. Cross-ADR citations to ADR-015 should be understood with this scope-narrowing applied unless they explicitly invoke the 2026-05-04 original.

2026-05-08 amendment — embedded template islands, not a standalone shell​

After 5 weeks of iteration on the standalone /app/admin/ SPA, researchers flagged it as feeling like "a separate beta", echoing the same divergence problem that motivated leaving the old external no-code surface (separate-from-Django, separate auth surface, separate visual chrome). The fix is to invert the embedding direction: instead of building a parallel React shell next to Django admin, mount the React table + form editors as template islands inside Django admin's existing pages.

Concretely:

  • EpistemicEntityAdmin's change_list.html hides the default Django changelist results and mounts <div id="ke-grid-mount" data-archetype data-canonical-type> — the same ArchetypeGrid React component that /app/admin/ used, now wrapped in Django Unfold's chrome (sidebar, top bar, breadcrumbs, theme).
  • The change_form's _term_form_overlay.html renders slot rows via _slot_row.html and mounts React editor islands per editable slot (data-ke-plate-mount, data-ke-multilingual-mount, data-ke-linked-record-mount). The same Plate editor / multilingual editor / linked-record editor ship inside the Django change_form; the existing iframe preview alongside renders the public reader's view of the entity.
  • Sidebar links go to /admin/epistemic/epistemicentity/?archetype__exact=X &canonical_type__exact=Y — the canonical Django admin URLs — driven by the TenantArchetypeTable model that names the tenant's workspace tables (Lemma Pool, Modern Editions, Early Editions, Ancient Word Full Reference, Reference - Abbreviated, etc.).
  • /app/admin/ stays online during the transition with a deprecation banner pointing researchers to /admin/. Removal follows once the embed has been in production for one full sprint without regressions.

Why this doesn't contradict ADR-005's "no embedded React in admin": that prescription targeted the public-facing epistemic apps (anchor explorer, data editor, knowledge explorer) where standalone SPAs are the right shape. The tenant admin is operational tooling, not a public app, and it inherits more from "shared admin chrome" than from "standalone SPA". The amendment recognizes that classification distinction.

The investment from the original ADR-015 work is preserved entirely — the React components (ArchetypeGrid, PlateFullEditor, MultilingualCellEditor, LinkedRecordCellEditor, RichTextCellRenderer, SchemaEditModal) all ship as-is, just mounted into Django admin pages instead of a standalone React routes. The Shell.tsx wrapper is dropped; everything else stays.

See docs/devlogs/2026_w19/2026-05-08_*_consolidation-into-django-admin.md for the implementation devlog.

Original (2026-05-04) decision body follows.​

Context​

ADR-005 (2025-12-28) mandated: "Epistemic React applications SHALL be implemented as standalone SPAs, not embedded in Django Admin." It prescribed URL structure (/app/*), template architecture (no admin chrome), tenant-driven module composition (data-driven from TenantOntology + archetype contracts), and page composition (regions + ordered slots, Shape 2). The Negative Consequences section flagged: "Duplicate Chrome — React apps must implement their own nav/shell" with mitigation "Shared React Shell: Create reusable nav/auth/tenant components (V2.0)."

That V2.0 mitigation never fully landed. An external no-code surface was wired in as a tactical workaround for tenant data editing (curating slot values, managing entity relationships, reviewing AI-suggested mappings). ADR-018 preserves the historical record of why that path was retired.

Two structural problems with the workaround surfaced in 2026-05:

  1. SSO and embed behavior were not viable on the required tier, forcing either separate tenant logins or paid vendor coupling for identity integration.
  2. The capability-flag model that landed in Phase-2K.4 (commits fb56cc24 + 588322a0 + 6da27cda) introduces capability flags (linkable, target_archetypes, display_field, lookup_for, target_field, multilingual) whose UX assumptions don't map cleanly onto a generic external table editor. Multi-target links, multilingual lookups, and AI-proposal status lifecycle each introduce friction.

A 2026-05-04 alternatives analysis surveyed Mathesar, Directus, Teable, Grist, Omeka. Findings:

  • Teable: Postgres backend, but owns its own schema (creates columns through its UI); requires a sync layer to/from Atlas's Django-migration-owned tables. Same architectural problem as Grist, less obvious because the backend is also Postgres.
  • Grist: SQLite-per-document. Fatal for Atlas's invariants (Postgres FK CASCADE, GIN indexes, JSONB containment, pg_trgm).
  • Omeka: Conceptually closest match (built for scholarly digital collections + linked data + per-property data types) but MySQL/MariaDB only. Postgres incompatibility is fatal for integration; useful as design inspiration only.
  • Directus: Adopts existing Postgres tables without modification; per-cell Vue Interface extensions are uniquely 1:1 with capability flags; BSL 1.1 license with $5M revenue threshold (not blocking); Vue framework hop from Atlas's React SPA.
  • Mathesar: Adopts existing Postgres tables; native Postgres role-based access control (cleanest django_tenants fit); GPL-3.0 nonprofit foundation (best license posture); Django/Svelte stack (potential deep integration); extension story unverified.
  • Native React: Total architectural alignment; React 19 stack matches Atlas SPA; no embed-translation-layer; capability flags map 1:1 to React component props; build cost concentrated in Grid + view modes + capability-flag-aware editors.

Codebase exploration (2026-05-04) revealed Atlas already has 60-70% of the Native infrastructure shipped:

  • spa/src/apps/anchor_explorer/components/SlotField.tsx (253 LOC): slot-config-driven widget renderer; zero hardcoded slot names; reads widget enum to dispatch to text / richtext / array / linked_record / passage / bibliography / media. Already production code.
  • spa/src/apps/data_editor/components/Grid.tsx (104 LOC): production AG Grid Community editable grid with cell-level mutations, optimistic updates, PATCH to /api/v1/lemmas/{id}/, pagination, sort, filter.
  • GraphQL schema: tenant_form_config(), term_detail() (returns AnchorPayloadType with full slot projection + capability flags including just-shipped Phase-2K.4 linkable), tenant_ontology(), mapping_proposals(), approve_mapping_proposal / reject_mapping_proposal / approve_mapping_project mutations.
  • Auth: dual-mode session + JWT; tenant routing via subdomain + TenantMainMiddleware; matches ADR-005's prescribed pattern.
  • Design tokens: SCSS _variables.scss (color palette, typography, spacing, breakpoints, shadows), Tailwind 3, Radix UI primitives, ThemeContext, AccessibilityControlPanel.
  • Micro-app pattern: 7 existing apps follow ADR-005's standalone-SPA prescription (anchor_explorer, data_editor, data_import, knowledge_explorer, database_visualizer, schema_review, admin_dashboard).

Conclusion: ADR-005's "Shared React Shell V2.0" was always the canonical destination for tenant data editing; the external no-code path was the v1 workaround. The architectural pattern, the substrate, the design system foundation, and the GraphQL contract are all in place or imminent. The remaining work is composition.

Decision​

The tenant admin shell SHALL be implemented as a Native React micro-app at /app/admin/, formally retiring the external no-code workaround.

This is the canonical implementation of ADR-005's prescribed "Shared React Shell V2.0" mitigation. New tenant onboarding and new admin-shell features land in the Native shell.

Concretely​

  1. New micro-app: spa/src/apps/tenant_admin/ follows the established pattern (anchor_explorer, data_editor, etc.). Mounted via Django template at /app/admin/. Minimal Django context per ADR-005 (tenant_id, csrf_token, current_user_id).
  2. Capability flags drive UI: each capability flag (text, richtext, multilingual, linkable, lookup_for, accent_fold, script, language) maps 1:1 to a React component variant (TextCellEditor, RichTextCellEditor, MultilingualCellEditor, LinkableCellEditor, LookupCellEditor, etc.). The capability vocabulary is the platform contract; React composition is its rendering.
  3. Reuse existing infrastructure: SlotField (extended with edit-mode branches), Grid.tsx pattern (generalized for archetype-driven columns), GraphQL term_detail (extended with entities bulk projection), auth, tenant routing, design tokens. No greenfield platform work; composition only.
  4. Free-tier libraries only: TanStack Query (already in stack), TanStack Table OR AG Grid Community (already in stack), Radix UI (already in stack), react-hook-form (already in stack), styled-components / Tailwind (already in stack), django-prose-editor (already in stack). No paid-tier dependencies.
  5. Vertical-slice spike first: 5-week time-boxed proof on the Atlas anchor tenant × TERM × related_terms + related_terms_translations + description + lemma. Spec at docs/superpowers/specs/2026-05-04_native-admin-shell-vertical-slice.md. Horizontal expansion (other archetypes, view modes, tenants) follows from working v0.
  6. Honor the epistemic-canonical lifecycle: AI proposals (status='AI_PROPOSED') surface in the admin's proposal review queue; approval triggers materialization via trigger_materialization mutation; status pill component visualizes the full lifecycle (DRAFT → AI_PROPOSED → HUMAN_REVIEW → APPROVED → APPLYING → APPLIED_TO_CANONICAL).
  7. Tenant identity respected, platform identity coherent: per-tenant accent + lock-up + TenantOntology archetype label overrides. Platform-wide tokens (typography, spacing, primitives) constant across tenants. Per the Claude Design brief.

Non-goals​

  • This decision does NOT require deleting existing tenant data overnight; new admin-shell capabilities land Native-side.
  • This decision does NOT prescribe specific UI / visual design — that's the Claude Design sprint's deliverable, downstream of this ADR.
  • This decision does NOT cover the public-facing reader (the SPA at /lemma/<id> etc.) — that's already shipped under ADR-005's prescription.
  • This decision does NOT preclude later use of an embedded tool (Mathesar / Directus) as a power-user fallback for specific workflows that benefit from a spreadsheet UX paradigm. If researchers report unmet needs that Native v0 can't address, embed-as-supplement is permitted.

Consequences​

Positive​

  • Honors the canonical pattern: ADR-005's prescribed "Shared React Shell V2.0" lands.
  • Architectural coherence: capability flags map 1:1 to React component props; no translation-layer maintenance.
  • No vendor lock-in: free-tier libraries only; no SSO paywall risk; no BSL revenue threshold; no per-developer subscription that breaks production if unpaid.
  • Reuses existing infrastructure: 60-70% of build is composition, not greenfield.
  • Closes the loop with public reader: same SlotField + AnchorDetailPage infrastructure powers admin and public surfaces.
  • Researcher-first UX: capability vocabulary surfaces in researcher language via runtime-injectable hint copy library.
  • Aligns with ADR-001: epistemic users get a React surface; operational concerns stay in Django Admin.

Negative​

  • Build cost concentrated upfront: ~5 weeks for v0 vertical slice; ~6-12 weeks for full horizontal coverage. Embedded tools (Directus / Mathesar) ship faster at v0 with more out-of-the-box features.
  • Polish features built incrementally: Atlas builds formulas / saved views / pivots / advanced exports as needed, rather than getting them upfront from a mature embedded tool.
  • Maintenance burden owned by Atlas: no external community contributing features; Atlas's bug surface is its own.
  • No spreadsheet-power-user fallback by default: if researchers want spreadsheet UX paradigms (drag-to-fill, Excel-like formulas, etc.), Atlas builds them or uses an embed-as-supplement.

Mitigations​

  • Vertical-slice spike de-risks the commitment: 5 weeks before fuller commitment; fallback to embed-as-supplement remains optional.
  • Reuses Atlas's existing libraries (Radix, react-hook-form, AG Grid Community, TanStack Query): composition-not-creation reduces real upfront cost.
  • Claude Design sprint produces design system + component primitives + handoff bundle: closed-loop with Claude Code closes the implementation gap.
  • Embed-as-supplement remains permitted if researchers request specific spreadsheet paradigms Native doesn't cover.

Compliance​

This decision must:

  1. Align with ADR-005: standalone SPA at /app/admin/; minimal Django context; no admin chrome; tenant-driven module composition from TenantOntology.
  2. Align with ADR-001: epistemic users (researchers) get this surface; admin-specific operations stay in Django Admin.
  3. Align with ADR-006 Rev 2.1: 7 entity archetypes + typed-edge layer (entity_relationships); capability flags as platform vocabulary.
  4. Align with ADR-012: tenant config flows through runtime pipeline (source-schema evidence → MappingProposal → review → materialization). The admin shell reads slot config from the materialized state and surfaces materialization triggers per ADR-012's flow.
  5. Honor lint-no-tenant-vocabulary structural guard rail: capability vocabulary is platform-standard; tenant-specific names live in TenantOntology mapping rows.

Implementation gating​

The vertical-slice spec (docs/superpowers/specs/2026-05-04_native-admin-shell-vertical-slice.md) specifies:

  • 5-week time-box (Week 1: GraphQL + identity; Week 2: shell + read-only Grid; Week 3: edit mode + linkable + lookup; Week 4: AI proposal review + lifecycle; Week 5: E2E verification)
  • Acceptance criteria per week
  • Decision points + fallback to embed-as-supplement if structural blockers surface
  • Commit plan with 6 ordered commits
  • Cold-start entry point for fresh-session execution

Decision log​

  • 2026-05-04: ADR drafted. Triggered by external no-code SSO/embed constraints + alternatives analysis (Mathesar, Directus, Teable, Grist, Omeka) + codebase exploration confirming 60-70% Native reuse + ADR-005 re-read confirming Native is the canonical pattern. Vertical-slice spike scoped at 5 weeks; ADR-015 + spec land together.

  • 2026-06-09 — TenantArchetypeTable identity widened to (archetype, canonical_type, source_table) (Spec 0040 Task 5, B-FULL; owner decision). The per-collection workspace-table model (the TenantArchetypeTable follow-up to this ADR) previously enforced UniqueConstraint(archetype, canonical_type). That forbade the genuine 1:many case: two physical source tables that share one canonical_type — the MySQL/XLSX importer leaves canonical_type empty-but-equal, or two tables explicitly declare the same subtype — must still become two distinct workspace tabs. A new source_table = CharField(blank=True, default="") (mirrors EpistemicEntity.provenance.table) becomes the third identity dimension; the constraint is now UniqueConstraint(archetype, canonical_type, source_table) (renamed tenant_archetype_table_unique_with_source). source_table="" for config/CLI-seeded rows that cover a logical collection rather than one physical table. The owner accepted that this widening "may open up other issues but we have to do it." Why now: Spec 0040 Task 5 makes the wizard auto-seed these rows at materialize (the analog of _seed_ontology — config writes already happen at materialize per the 2026-05-29 decision), keyed on the triple via create-if-absent + refresh-seeder-owned-fields — never clobbering admin edits (visible_slots / is_active / admin extra_filter keys; the provenance.table key is merged, not replaced). Before this, the sole populator (seed_tenant_archetype_tables) was auto-invoked nowhere, so wizard tenants had 0 rows and the workspace synthesized generic-archetype-labelled virtual tables. The seeded label is now the real source-table name (also fixing "Lemma Pool shows 'Lemma'" — the label is the physical table, not the subtype), and the per-tab GraphQL count/filter scope by provenance.table so the 1:many split shows correct rows/counts per tab. Reconciled with PR #511's extra_filter-derived source_table (resolver now PREFERS the real field, falls back to extra_filter); PR #512 (canonical_type defaults to source-table name when undeclared) is complementary. Migration 0003 is safe regardless of row count: the new constraint is strictly weaker than the old one (any dataset satisfying unique(arch, ct) satisfies unique(arch, ct, src) for any src). Cross-ref: PR #512 (50003273), docs/decisions/log.md (2026-06-09 entry). One surfaced edge case (flagged, not solved here): a tenant carrying BOTH Step-1 import-config rows (source_table="") AND materialize-seeded per-source rows for the same (archetype, canonical_type) would render both, double-counting the config tab via the all-entities agg; pure-wizard tenants only get per-source rows and are unaffected. __reference__ synthetic-support / controlled-vocab rows are excluded from seeding (lookup tables, not user-facing tabs), consistent across the materialize seeder and the management command.
