ADR-005: React Integration Pattern for Epistemic Applications

Status: Accepted
Date: 2025-12-28
Deciders: Architecture Team
Context: Sprint 12 - Database Visualizer Implementation

Context​

During implementation of the Database Visualizer (Sprint 12), we encountered a fundamental architectural conflict between Django Admin's context model and our multi-tenant, epistemic/operational separation.

The Trigger​

Attempting to embed the React-based Database Visualizer within Django Admin led to:

  • Cascade of NoReverseMatch errors for admin.site.each_context(request)
  • Incompatibility between single-admin assumptions and multi-tenant reality
  • Violation of ADR-001 (Epistemic/Operational Separation) in spirit

Root Cause​

admin.site.each_context(request) assumes:

  • Single, universal admin site
  • Global introspection over all registered apps
  • Unified URL namespace
  • No domain-based separation

Our architecture explicitly rejects these assumptions via:

  • Multi-tenancy (django-tenants)
  • Domain-based admin separation (public vs tenant)
  • Epistemic vs Operational UI separation

Conclusion: Django Admin cannot be partially embedded in a multi-tenant, domain-separated architecture.

Decision​

Epistemic React applications SHALL be implemented as standalone SPAs, not embedded in Django Admin.

2026-05-11 Amendment: Public Entry Delivery Boundary​

ADR-005 remains the rule for epistemic applications and researcher/admin tools: React apps are standalone and do not embed Django Admin chrome.

ADR-005 must not be read as a requirement that every public scholarly surface be a monolithic client-side SPA. ADR-029 narrows the public Entry direction: published Entry pages, exports, federation resources, citation payloads, and institutional integrations read from versioned EntryProjection / EntryPublishService outputs. React remains the right substrate for interactive modules, profiles, teaching tools, 3D/media viewers, and research workflows, but the durable public artifact must be HTML/export-capable and not depend on V1 REST/Elasticsearch payloads.

This amendment preserves the original admin-separation decision while preventing the "standalone SPA" rule from being over-applied to published scholarship.

Core Principles​

  1. Admin === Operational Only

    • User management
    • Tenant provisioning
    • Configuration
    • Logs and monitoring
    • Infrastructure operations

  2. React SPA / React Modules === Epistemic Only

    • Data exploration
    • Knowledge building
    • Schema visualization
    • Research workflows
    • Content creation
    • Public Entry interactions where ADR-029's published artifact remains the baseline

  3. No Hybrids

    • If a view needs admin.site.each_context(), it IS an admin view
    • If it doesn't, it is NOT an admin view
    • Zero React apps embedded in admin chrome

URL Structure​

Admin URLs (Operational):

/admin/
/admin/tenants/
/admin/users/
/admin/monitoring/

App URLs (Epistemic):

/app/schema/          # Database Visualizer
/app/suggestions/     # Schema Review
/app/knowledge/       # Future epistemic tools

Template Architecture​

Epistemic templates MUST:

  • Be standalone HTML documents
  • NOT extend Django admin base templates
  • NOT use admin.site.each_context()
  • Provide their own navigation (React-based)

Example:

<!DOCTYPE html>
<html lang="en">
<head>
  <title>{{ title }}</title>
  {% load static %}
  <link rel="stylesheet" href="{% static 'spa/css/app.css' %}">
</head>
<body>
  <div id="root"></div>
  <script>
    window.csrfToken = "{{ csrf_token }}";
    window.tenantId = "{{ tenant_id }}";
  </script>
  <script src="{% static 'spa/js/[app].bundle.js' %}"></script>
</body>
</html>

Tenant-Driven Module Composition​

The same deployed SPA code renders different page structures per tenant. On startup, the React app fetches the tenant's TenantOntology (ADR-004), which determines:

  • Which archetype pages exist (ATLOMY has no EVENT pages; VISIONIS has TIME period pages)
  • What labels appear ("Lemma" vs "Lexical Root", "3D Model" vs "Manuscript Image")
  • Which page modules render (ATLOMY: 3D viewer, parallel terms sidebar; VISIONIS: 2D image viewer, faceted classification tags)
  • Which classification facets appear in search/filter (ATLOMY: body region; VISIONIS: perspective, subject, genre, location, time period)

This means no per-tenant SPA builds, no per-tenant React code, no conditional imports by tenant name. Variation is data-driven from TenantOntology + archetype contracts. A new tenant gets its own research environment by populating TenantOntology rows, not by writing React components.

Page Composition (Draft vs Published States)​

Tenant-driven module composition (above) determines which modules exist. Page composition determines how those modules are arranged per page type and when arrangement changes go live for outward-facing readers. This is the SPA-side contract that pairs with the three-layer update contract in docs/superpowers/plans/2026-04-15-mvp-knowledge-environment-pipeline.md platform principle #4.

Model​

# atlomyapp/models.py (proposed, lands in Sprint 18.5)
class TenantPageConfig(models.Model):
    tenant = models.ForeignKey("Tenant", on_delete=models.CASCADE)
    page_type = models.CharField(max_length=64)   # "lemma_detail", "root_detail", "term_index"
    archetype = models.CharField(max_length=50)   # TERM, DOCUMENT, ENTITY, EVENT, MEDIA
    variant = models.CharField(max_length=50, blank=True)
    template = models.CharField(max_length=64)    # "single_column", "two_column", "hero_top"
    draft_config = models.JSONField()             # currently-edited state
    published_config = models.JSONField(null=True)  # what public readers see
    published_at = models.DateTimeField(null=True)
    published_by = models.ForeignKey("auth.User", null=True, on_delete=models.SET_NULL)

    class Meta:
        unique_together = [("tenant", "page_type")]

JSONB Schema (Shape 2 — Slot List + Column Positioning)​

{
  "layout": "two_column",               // matches a template the SPA ships
  "regions": {
    "main": [
      {"id": "term_header", "visible": true, "label_override": null},
      {"id": "description", "visible": true, "label_override": "Overview"},
      {"id": "ancient_words", "visible": true, "label_override": null}
    ],
    "sidebar": [
      {"id": "media_gallery", "visible": true, "label_override": null},
      {"id": "related_terms", "visible": true, "label_override": null},
      {"id": "citations", "visible": false, "label_override": null}
    ]
  }
}

Each slot.id is a stable identifier registered by the renderer module (Sprint 18). Slots are drag-drop reorderable within a region and across regions. Renderers declare which slot IDs they provide; the preview canvas composes only from registered slots.

Platform Boundary​

The contract validator blocks a publish attempt when:

  • A required field from the archetype contract (ADR-006) has no active slot on the page.
  • A slot targets a JSONB key the tenant has never populated for that archetype.
  • A template declares a mandatory slot (e.g., templates with a hero region require a media_gallery or term_header slot) that is missing or hidden.

These constraints are enforced server-side at publish time, not purely in the canvas UI.

Draft vs Published Semantics​

  • Public renderer reads published_config (cached). If published_config IS NULL, the page falls back to a template-default composition derived from archetype contract required fields.
  • Preview renderer (authenticated team only, gated on role) reads draft_config and renders with a visible "PREVIEW — NOT PUBLISHED" banner.
  • Publish action: atomic copy draft_config → published_config, stamp published_at/published_by, and write the prior published_config to a history table (keep last N versions for one-step revert).
  • No scheduled publishing and no per-user draft branches in MVP scope (see Sprint 18.5 non-goals).

Why Shape 2, Not Shape 3​

A richer component-tree shape (arbitrary nesting, mini page-builder) was considered and deferred:

  • Shape 1 (flat slot list): Too thin — no way to express "media in sidebar, body in main," which is the realistic tenant divergence already observed (ATLOMY 3D widget sidebar vs VISIONIS image hero).
  • Shape 2 (regions + ordered slots): Adopted. Covers observed tenant needs, trivial to validate against contracts, bounded in scope.
  • Shape 3 (arbitrary component tree): Rejected for MVP. Validation-against-contract logic becomes materially more complex, and no tenant has yet asked for capabilities beyond regions + ordering.

Shape 3 remains a future extension if a pilot's feedback demands it.

Context Requirements​

Django views for epistemic apps should provide ONLY:

context = {
    'title': 'App Name',
    'tenant_id': request.tenant.id if hasattr(request, 'tenant') else '',
    # Minimal, explicit context only
}

Never:

  • admin.site.each_context(request)
  • available_apps
  • Admin navigation variables

Consequences​

Positive​

✅ Clean Separation: Epistemic and operational concerns fully decoupled
✅ No URL Conflicts: Multi-tenant admin sites work without interference
✅ Scalable: Add new epistemic apps without admin registration concerns
✅ Maintainable: React apps are independent, versionable units
✅ Aligns with ADR-001: Explicit enforcement of architectural boundaries

Negative​

⚠️ Duplicate Chrome: React apps must implement their own nav/shell
⚠️ Migration Work: Existing embedded apps need refactoring
⚠️ User Confusion: Users navigate between /admin/ and /app/ URLs

Mitigations​

  1. Shared React Shell: Create reusable nav/auth/tenant components (V2.0)
  2. Clear Routing: Document URL structure for users
  3. Gradual Migration: Refactor existing apps incrementally

Compliance​

New Applications​

All new epistemic React applications MUST:

  • Use standalone templates (no admin base)
  • Provide minimal context (no each_context)
  • Route under /app/* namespace
  • Implement own navigation in React

Existing Applications​

  • schema_review: Already compliant (verify)
  • database_visualizer: Update per this ADR

Examples​

✅ Correct Implementation​

View (dbvisualizer/views.py):

@login_required
def react_designer(request):
    context = {
        'title': 'Database Visualizer',
        'tenant_id': request.tenant.id if hasattr(request, 'tenant') else '',
    }
    return render(request, 'database_visualizer.html', context)

URL (dbvisualizer/urls.py):

urlpatterns = [
    path('app/schema/', views.react_designer, name='schema_visualizer'),
]

❌ Incorrect Implementation​

# DON'T: Embedding in admin
context = {
    **admin.site.each_context(request),  # ❌
    'custom_data': data,
}
