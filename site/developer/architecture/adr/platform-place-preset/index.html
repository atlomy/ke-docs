ADR-039: Platform-canonical Place preset (platform-place/v1)

Status: Proposed (v1.1 — amended 2026-05-20 per R1d targeted stress-test absorption; see docs/superpowers/plans/2026-05-20-period-place-spatial-architectural-pass.md for provenance) Date: 2026-05-20 Deciders: User; architecture team Related: ADR-037 (Slot-Type Taxonomy and Tenant Vocabulary Layer; GEOMETRY SlotKind in Threshold-C queue), ADR-038 (Federated Preset Registry as Federation Contract; Classics bundle alignment), ADR-040 (Period preset; sibling preset for temporal extent; ADR-039 + ADR-040 compose for CIDOC E4 multi-inheritance per ADR-040 v1.2 §Compliance E4 multi-inheritance note), ADR-041 (Spatial substrate — PostGIS + GeoSPARQL + MapLibre; substrate dependency), ADR-006 (Archetype Capability Contracts), ADR-022 (Anchor + ClaimCluster substrate; GIS_GEOMETRY anchor type), ADR-029 (Projection-First Published Entry Layer), ADR-030 (CIDOC + Linked Art Export Profile Choice) Companion:

  • ADR-041 — Spatial substrate (PostGIS + GeoSPARQL + MapLibre GL JS); ADR-039 + ADR-041 land paired per ADR-038 v1.2 §D8 staggering rationale
  • Spec 0019 — MapView design.md (consumer of the Place preset's ke:supportsSpatialRendering capability URI)
  • docs/superpowers/plans/2026-05-20-period-place-spatial-architectural-pass.md — post-307 absorption provenance
  • docs/research/standards/CROSSWALK_extensions_2026-05-20.md — Phase 1.5 standards extension; PROMOTE verdict for PLACE under extended standards set

TL;DR​

ADR-038 v1.2 §D8 commits the platform to six initial-library PlatformPreset entries. ADR-039 ratifies the second of those: platform-place/v1 — a federation-contract-bearing preset that gives tenants with place-like entities (geographic regions, historical settlements, archaeological sites, administrative jurisdictions, virtual / conceptual places) a single platform-canonical shape to subscribe to.

The preset is spatial-substrate-bound: it requires PostGIS + GeoSPARQL via ADR-041 to ratify. The text-only path that ADR-040 took is not available here — geometry is the defining content of a Place, not a peripheral attribute. ADR-039 + ADR-041 land together; Phase 5 + Phase 6 of the post-307 architectural pass.

Nine standards land in this preset's complies_with declaration: GeoSPARQL (OGC; gold authority for geospatial RDF), CIDOC-CRM E53_Place, schema.org/Place, GeoJSON (RFC 7946), Pleiades (ancient places gazetteer), GeoNames (modern places gazetteer), Wikidata Q-IDs (universal identifier substrate), dcterms:Location (Dublin Core compatibility), EPSG / Spatial Reference Identifiers.

Cross-preset interaction with ADR-040: tenants subscribed to BOTH platform-period/v1 AND platform-place/v1 produce composed projections where the period entity's spatialExtent slot (ADR-040 v1.2 §D3 recommended) projects to a CIDOC E4-with-E92-Spacetime-Volume shape — the spec's permissive language in ADR-040 v1.2 §Compliance permits text-centric Period; composing with Place subscription upgrades to full E4 with spacetime representation.

Context​

Why a Place preset, why now​

Four threads converged on the need:

  1. CROSSWALK Phase 1.5 extension verdict (docs/research/standards/CROSSWALK_extensions_2026-05-20.md): the extended standards matrix re-runs Clause 1 for PLACE: 5 strong standards × 5 families (geospatial: GeoSPARQL + GeoJSON; metadata: CIDOC E53 + dcterms:Location; identifiers: Pleiades + GeoNames + Wikidata; harvesting: RO-Crate location; STEM/CRMarchaeo). Passes Clause 1 with margin (5 families vs Period's 2). The PROMOTE verdict for PLACE is the strongest in the Phase 1.5 extension.

  2. Three-tenant evidence recount (ADR-037 ratification brief §2.8.e):

    • Atlas: implicit spatial dimension (lemma-context locations; treatise-place-of-composition; not a first-class archetype today).
    • JPP: 4,540 places rows + 5 junction tables (persons_places, events_places, etc.) carrying explicit ENTITY rows with place-equivalent canonical_type. The richest empirical evidence in the four-tenant pool.
    • Visionis: dedicated PLACE archetype with geographic-context (Andalusia + Maghreb + Mashriq + etc.) tied to thematic-period entries; CIDOC-style cultural-phenomenon spatial extent.
    • Integrative tenant: archaeological sites (85+ per the brainstorm-cited research) + city polygons + stratigraphic units with absolute coordinates + drone-captured orthophotos. The most demanding spatial substrate consumer in the prospective tenant pool.

  3. MapView is the primary research surface for integrative tenants (per docs/superpowers/plans/2026-05-19-mapview-spatial-anchored-surface-brainstorm.md). For these tenants, click on a city / site / region → see all historical references + archaeological finds + environmental layers + isotopic data + photogrammetry. The map is not "a view kind some tenants might use"; it's a peer surface to Table / Details / Relations / Publish.

  4. Composed E4 conformance for ADR-040 subscribers. Per ADR-040 v1.2 §Compliance E4 multi-inheritance note, the CIDOC v7.1.3 spec permits discussing E4 Period without representing the spacetime volume. But the spec's preferred shape — and the integrative-tenant use case — is full E4 with both E52 timespan AND E53 place populated. ADR-039 + ADR-040 together enable this composed projection.

Why Place can't move text-centric like Period did​

ADR-040 chose text-centric for v1 because:

  • The CIDOC v7.1.3 spec explicitly permits discussing E4 without representing the spacetime volume
  • Tenants doing rough-authoring (Atlas BC/AD century lifespans) shouldn't be blocked
  • PostGIS + GeoSPARQL substrate was at brainstorm stage; deferring kept Period ratifiable independently

For Place, the equivalent argument doesn't apply:

  • CIDOC E53_Place IS the spatial primitive in v7.1.3. There's no spec-supported "discuss E53 without representing the place" escape clause. The class is defined by its spatial extent + identification.
  • JPP's 4,540 places are not "rough authoring" — they're authoritative geographic data points with real coordinates, expected to participate in spatial queries.
  • The integrative-tenant use case is spatial-first: stratigraphic finds anchored to specific archaeological-unit coordinates, drone orthophotos with georeferenced bounds.

A "text-only Place" v1 would create perpetual technical debt: every Place entity would need migration to structured geometry when tenants actually use the spatial layer. Better to ship the substrate + preset together.

What this ADR does NOT decide​

  • Spatial substrate implementation details (PostGIS extension config, GeoSPARQL query support layer, MapLibre GL JS substrate, tile server architecture): orthogonal; lands in ADR-041. ADR-039 declares the data contract; ADR-041 declares the substrate.
  • MapView UI architectural design (Leaflet vs MapLibre vs Mapbox; vector vs raster layer composition; timeline scrubber UX; cell-editor integration): Spec 0019 upgrade from brainstorm to design.md. ADR-039 declares the capability URI; Spec 0019 declares the implementation.
  • 3D viewer integration for stratigraphic / photogrammetry data: handled by existing spa/src/pages/three_d_model/ viewer; ADR-039 cross-links via ke:supportsThreeDDrillIn URI (forward-referenced from MapView spec).
  • Tile server architecture (host on platform / external WMS / per-tenant): ADR-041 D7 decides; ADR-039 just requires that the geometry data exists somewhere queryable.

Decision​

D1 — Preset identity​

The platform ships platform-place/v1 as a PlatformPreset (RDF type ke:PlatformPreset per ADR-038) with the canonical IRI:

https://<platform-domain>/presets/platform-place/v1

⚠️ Platform-domain placeholder: ADR-038 v1.0 + ADR-040 v1.0 used ke.atlomy.org for this URL pattern. This is incorrect and inherited unchallenged — KE is the multi-tenant platform; Atlomy Atlas is one tenant. A platform-canonical preset registry must NOT live under a tenant's domain. The eventual canonical domain is a platform-naming + infrastructure decision pending (parent organization choice; candidate alternatives include ke.org-class TLDs, knowledge-environments.org-class explicit names, or a parent-organization subdomain). Until the platform domain resolves, ADR-039 uses <platform-domain> as a syntactic placeholder; existing references to ke.atlomy.org in ADR-038 + ADR-040 are tracked for amendment in §Open Questions §0 below + a follow-up decision-log entry.

Preset version 1 is the initial-library ratification commitment (per ADR-038 v1.2 §D8 staggering — ADR-039 + ADR-041 land paired). Evolution to v2+ follows ADR-038 D4 (monotonic addition of required slots or complies_with declarations only).

Primary domain alignment: Classics bundle (per ADR-038 v1.2 §D9). Secondary applicability: archaeology, prosopography, art history, geography, geological survey, biodiversity (Darwin Core sample locations), cultural heritage. The Place preset is high-applicability across domains — it's the most cross-domain preset in the D8 initial library.

D2 — Required slots​

Every entity subscribing to platform-place/v1 MUST populate:

SlotSlotKindModifiersSemantics
prefLabelTEXTmultikey_kind=language, multilingualDisplay name (untagged label from source); SKOS prefLabel semantics. At least one language entry required. Label text is what vanilla-RAG embedding pipelines key on (the embedded text, not the IRI); a populated prefLabel benefits any retrieval system regardless of whether it consumes the structure.

Why these three are required:

  • prefLabel: federation discovery (structured SPARQL queries across tenants) requires a primary label per place IRI; required for search-engine entity recognition (schema.org/Place expects a name field that maps to prefLabel); required for human-readable rendering on MapView popups.
  • geometry: the spatial extent IS the defining content of a Place. Unlike ADR-040 §D2's text-permitting interval, Place's geometry cannot fall back to text — CIDOC E53 + GeoSPARQL + GeoJSON all require structured spatial primitives. The kind=GeometryCollection shape supports complex multi-part places when needed.
  • placeType: subscriber discoverability + JSON-LD type-disambiguation. Without placeType, downstream consumers cannot distinguish a city from a geological formation or an archaeological site; CIDOC E53 typing benefits from explicit kind.

Why NOT also requiring centroid as a separate field: per CIDOC v7.1.3 §E53 + GeoSPARQL practice, the centroid is derivable from the geometry for any non-Point type. Requiring both would either force tenant-admin double-entry or risk drift between geometry edits + cached centroid. The recommended centroid slot (§D3) carries an EXPLICIT centroid only when it differs meaningfully from the geometry's computed centroid (e.g., a city's "center" vs the polygon's geometric centroid).

Projection-layer emits the full CIDOC E4 + E52 + E53 trio with P4 has time-span + P7 took place at triples.

D4 — Forbidden patterns (v1.1 corrected per re-audit of R1d N1+N4 absorption)​

  • canonical_type=Person, canonical_type=Period, canonical_type=Event: Place is a distinct concept; cross-archetype overloading is rejected. Per CIDOC v7.1.3 class hierarchy: E53_Place is independent of E21_Person and E5_Event; only E4_Period multi-inherits from E92_Spacetime_Volume (which composes with E53). The §D4 stance preserves archetype boundaries while permitting cross-preset projection where the spec supports it.
  • (v1.0 "empty geometry AND empty centroid → blocked" rule REMOVED per re-audit.) TEI §14.3.4.1 "Varieties of Location" explicitly permits five ways to specify location — only one requires coordinates. Verbatim from TEI: "A location may be specified in one or more of the following ways: by supplying a string representing its coordinates in some standardized way within a geo element; by supplying one or more place name component elements (e.g. country, settlement etc.) to place it within a geo-political context; by supplying a postal address, e.g. using the address element; by supplying a brief textual description, e.g. using the desc element; by using a non-TEI XML vocabulary such as the Geography Markup Language." A Place entity specified by name + geo-political context (e.g., prefLabel="Yorkshire", parentPlace=<england-place-iri>) without coordinates IS a valid Place under both TEI's location semantics + the platform's Place-vs-TERM archetype distinction. When coordinates are added later, the entity stays the same row — just gets richer. The v1.0 "blocked" rule was architecturally weak from the start (over-strict; conflated "geometry is recommended" with "geometry is required for valid Place existence") and is therefore dropped from §D4. The wizard surfaces a soft prompt at save time when geometry+centroid both empty: "This Place has no coordinates yet. That's fine — Places can be specified by name + geo-political context per TEI §14.3.4.1. Add coordinates when available for spatial-query participation."
  • Place entities whose geometry is exclusively kind=GeometryCollection containing only Point items: SOFT WARNING (not hard block) at the wizard layer. The Point-only GeometryCollection shape is technically valid — Points have BBOXes (zero-area), ST_AsMVT handles Point features, GIST indexes Points fine. The wizard advises that such data is often better modeled as N separate Place entities (each Point gets its own Place) OR as a single Place with an aggregate Polygon (e.g., a convex hull around the Points) for better federation-query semantics, but the platform doesn't block the pattern. The wizard message: "Point-only GeometryCollection works but often signals 'this should be N Place entities' or 'this Place has an aggregate Polygon yet to be drawn.' Continue if intentional." (v1.1 correction per re-audit — R1d N4 claim that Point-only collections "fail BBOX availability for Z0-Z5 vector tiles" was technically incorrect; Points have BBOXes; rendering works.)

D6 — Capability activations on subscription​

Per ADR-038 v1.2 §D6, capability activations are declared via abstract capability URIs, NOT specific React widget names. The v1.1 capability URI vocabulary:

Capability URIWhat it declares the subscribing consumer surface needs to support

ke:supportsGazetteerLookup (hints: pleiades, geonames, wikidata)Authority lookup against external gazetteers. ke:supportsStandardsExport (hints: GeoJSON, KML, WKT, GML, CIDOC-XML, LinkedArt-Place, RO-Crate)Activate compliance-export surfaces per D5 declarations.

Public reader surface (ADR-029 projection):

  • JSON-LD output with dcterms:conformsTo enumerated per D5 (all nine declarations).
  • @type array: [schema:Place, cidoc:E53_Place, dcterms:Location, geo:Feature] — multi-vocabulary typing enables structured-retrieval consumers to recognize the entity under whichever vocabulary they prefer. NOT a benefit for vanilla-RAG text-embedding retrieval.
  • Geometry emitted in multiple serializations: GeoJSON geometry object (primary), WKT (geo:hasSerialization with WKT literal), GML (optional via export view), KML (export-view-only).
  • External gazetteer triples emitted when corresponding slots populated: owl:sameAs <pleiades-iri> | <geonames-iri> | <wikidata-iri>.

Compliance export surface:

  • GeoJSON export view — RFC 7946-conformant FeatureCollection for tenants subscribed to GIS-export workflows.
  • KML export view — for Google Earth / mapping-tool import.
  • CIDOC-XML E53_Place export view — for cultural-heritage repositories.
  • Linked Art Place export view — CIDOC-CRM-conformant Linked Art Place projection (per ADR-030 ratification).
  • RO-Crate location projection — for research-data-package consumers.

D8 — Subscription discipline + fork rationale​

Subscription mechanics follow ADR-038 D3 generically. Place-specific guidance:

  • At subscription time: back-check existing tenant entities with place-like canonical_type (canonical_type=Place, canonical_type=Site, canonical_type=Region, canonical_type=City, etc.) against the required-slot contract. Surface conformance gaps to the tenant admin; admin closes gaps before subscription completes. JPP's 4,540 places have place-equivalent rows; subscription back-check identifies which rows have populated geometry vs which need migration.
  • Tenant alias mapping: per ADR-004 tenant ontology mapping, tenants can label the preset locally — "Region" (Atlas implicit), "Place" (JPP), "Geographic Location" (Visionis), "Site" (integrative-tenant archaeological pattern), "Jurisdiction" (potential future modern-law-KE tenant), "Habitat" (potential future biodiversity-KE tenant). Aliases are tenant-facing only; the canonical preset IRI stays stable.
  • Fork rationale guidance: if a tenant's place authoring requires additional required slots beyond D2, the fork rationale (per ADR-038 v1.2 §D7 hardening) MUST declare a constrained-vocabulary divergence-category (discipline-specific-authoring-shape / regulatory-compliance-requirement / research-protocol-divergence / other). The platform validates monotonicity per ADR-038 D4 + the divergence-category declaration per ADR-038 v1.2 §D7.
  • Fork lineage predicate (per ADR-038 v1.2 PROV-O semantic): forks declare <fork-iri> prov:specializationOf <parent-preset-iri> (NOT prov:wasDerivedFrom). The "shares all aspects" specialization semantic matches the fork-as-monotonic-refinement model.

Anticipated fork patterns (not committed at v1, but documented for reference):

  • Archaeological-site fork (crmarchaeo-place/v1): would add CIDOC-CRMarchaeo conformance + stratigraphic-context slots (stratigraphicLayer, excavationContext, findContext, A1 Excavation Unit references). Drives from integrative-tenant pattern. v1.1 prominence note: per R1d N2, this is the most-likely-near-term fork given the integrative-tenant pattern + JPP's archaeological adjacency. Phase B.5 onboarding doc surfaces this fork pattern as a primary worked example.
  • Environmental-science fork (crmsci-place/v1): would add CIDOC-CRMsci conformance + environmental-context slots (materialSubstantialContext, environmentalCondition, samplingLocation, S10 Material Substantial references). Drives from potential future biodiversity / paleoclimate-research tenant.
  • OGC API Features fork (ogc-api-features-place/v1): would add OGC API - Features 1.0 conformance for modern GIS interop (separate from GeoSPARQL — OGC API - Features is REST-based, while GeoSPARQL is RDF-based). Drives from potential future GIS-aggregator tenant.
  • Jurisdiction fork (platform-jurisdiction/v1): would add legal-jurisdiction-specific slots (jurisdictionType, parentJurisdiction, effectiveLaw). Drives from potential future modern-law-KE tenant.
  • Habitat fork (darwincore-habitat/v1): would add Darwin Core habitat-specific slots (habitatType, ecologicalContext, biodiversityIndex). Drives from potential future biodiversity-KE tenant.

Cross-reference for IIIF-spatially-anchored content: tenants needing IIIF-Presentation 3.0 georeferencing of manuscript folios / drone orthophotos consume the platform's IIIF Manifest contract via Spec 0019 MapView AC8 (which extends ADR-024). IIIF-Presentation is NOT a Place preset complies_with declaration because IIIF semantics are at the MEDIA archetype layer, not the Place archetype layer; the Place preset receives spatially-anchored IIIF content via cross-archetype RELATION slots (e.g., a referencedImagery slot pointing at MEDIA entities with IIIF Manifest projections).

None of these forks land at v1; per ADR-038 v1.2 §D9, the Classics bundle is the only validated bundle. Forks emerge via the Threshold-A path per ADR-038 v1.2 §D7 (Path 2a cross-disciplinary default after non-Classics tenants onboard; Path 2b single-discipline carve-out for early-stage convergence).

Alternatives Considered​

Text-centric Place preset (deferred-substrate path; ADR-040's pattern)​

Ship Place preset with a free-text location slot; defer the spatial substrate to a future ADR; tenant configs subscribe to platform-place/v1 with text-only place data initially.

Why not chosen: covered in §"Why Place can't move text-centric like Period did" above. CIDOC E53_Place IS the spatial primitive; there's no spec-supported text-only escape clause. JPP's 4,540 places are authoritative geographic data, not rough authoring. The migration cost when tenants actually use the spatial layer would be unbounded. Ship the substrate + preset together.

Place as archetype promotion (ADR-006 Path A — revisited)​

Add PLACE as a new entry in ADR-006's archetype list (rather than as a PlatformPreset under ADR-038). Each Place row is its own archetype row with platform-enforced contracts.

Why not chosen: same rationale as ADR-040's §Alternatives "Promote TIME_PERIOD to a new archetype" — the architectural answer Path B (ADR-038's preset registry) supersedes Path A. The four-tenant evidence + the CROSSWALK extension verdicts mean the conditions for promotion are met, but the preset path accommodates long-tail discipline divergence (CRMarchaeo + jurisdiction + habitat forks) without forcing platform-default uniformity. Plus no data migration in JPP + Visionis.

Geometry as RICHTEXT (storing GeoJSON as string)​

Skip the GEOMETRY SlotKind Threshold-C amendment; store geometry as a RICHTEXT slot containing GeoJSON string content.

Why not chosen: stringly-typed geometry has the same failure modes Bundle D Finding 1 flagged for stringly-typed intervals (ADR-040 v1.0's wrong-v1-choice). Spatial queries cannot traverse strings; PostGIS GIST indexes don't exist on TEXT columns; federation-query geo:sfWithin operations need real geometry primitives. The GEOMETRY SlotKind is a Threshold-C amendment to ADR-037 (queued in the Threshold-C amendment queue per ADR-037 v1.1; ratification gated alongside ADR-039 + ADR-041) precisely because storing geometry as text is the wrong shape.

Defer Place preset until Phase A.2 frontend lands​

Hold Place preset authoring until ADR-037 Phase A.2 (frontend rewrite consuming the slot-taxonomy foundation) ships, so the MapView surface for place editing is real before the preset's required-slot contract commits.

Why not chosen: same rationale as ADR-040's equivalent — the preset's contract is platform-canonical and stable; Phase A.2 consumes it, not the other way around. Drafting the preset now lets Phase A.2 + Spec 0019 MapView design.md target the canonical contract during their implementation; deferring would force them to target a moving spec. The G3 demonstration fixtures (D7) are the ratification gate; they can land alongside Phase B.5 work without blocking the ADR's authoring.

Consequences​

Positive​

  • Multi-CRS tenants supported natively. Tenants whose source data carries non-WGS84 CRSs (local archaeological grids; national geodetic systems; ancient cartographic projections) declare the srid modifier per slot; projection layer emits CRS-aware GeoSPARQL geo:hasSerialization. No tenant-side conversion code in the platform's required path.
  • Nine-standard interop in one declaration. GeoSPARQL + CIDOC E53 + schema.org + GeoJSON + Pleiades + GeoNames + Wikidata + dcterms:Location + EPSG aligned via complies_with at the preset level; subscribers project to all nine in JSON-LD with no tenant code. Structured-retrieval consumers (search engines, GraphRAG, federation SPARQL, scholarly-infrastructure ingestion) recognize the place under whichever vocabulary they prefer.
  • CIDOC E4 composed projection unlocked. Subscribers to both platform-place/v1 AND platform-period/v1 produce full E4 (Spacetime Volume + Event lineage) per ADR-040 v1.2 §Compliance E4 multi-inheritance note. Cultural-heritage repository ingestion (museums; Linked Art) consumes the composed E4 cleanly.
  • JPP migration unblocked. JPP's 4,540 places have structured geographic data that can subscribe to platform-place/v1 with conformance back-check identifying any rows missing geometry. No data migration to a new table; subscription is config-only.
  • Visionis CIDOC-style spatial extent accommodated without platform pollution. Visionis's geographic-context (Andalusia / Maghreb / Mashriq) lands as platform-default Place subscriptions; their thematic-period entities cross-link via temporalCoverage per D3.
  • Integrative-tenant readiness. The platform substrate + preset together unblock the integrative-tenant pattern (multi-disciplinary humanities + archaeology + ecology + GIS). MapView graduates to first-class surface per Spec 0019.

Negative​

  • ADR-039 + ADR-041 paired ratification cost. The spatial substrate is a real architectural commitment (PostGIS extension, GIST indexing, GeoSPARQL query layer, MapLibre GL JS substrate, tile server architecture). Ratifying ADR-039 requires ratifying ADR-041 too; deferring either blocks both.
  • GEOMETRY SlotKind Threshold-C amendment dependency. ADR-037 v1.1 queues GEOMETRY in §Evolution Threshold-C amendment queue; ADR-039 ratification requires that amendment to land (with G1 impact + G3 fixture commitments per ADR-037 §G1 / §G3).
  • Per-tenant CRS coordination overhead. Tenants with local-grid coordinate systems need explicit srid declarations in tenant config; cross-tenant federation queries need CRS reprojection at query time. PROJ library + PostGIS handle this, but tenant onboarding requires explicit CRS choice.
  • Three-surface fixture authorship is non-trivial. The G3 demonstration set (public reader JSON-LD with multi-vocabulary triples; MapWidget snapshot test; compliance exports across 4 formats) is multi-file, multi-format work. Phase B.5 implementation owns the fixture authorship; ratification blocks on it.
  • External gazetteer dependencies. Pleiades + GeoNames + Wikidata are external services; their endpoint availability is platform-uncontrolled. Mitigation: same as ADR-040 PeriodO authority lookup — the gazetteer lookup is optional per tenant; place authoring proceeds without it; the dependency is read-only and bounded.

Mitigations​

  • Phase B.5 ships the canonical Visionis Place subscription + JPP Place subscription alongside the preset as documentation + working examples. Tenants reference the subscription pattern rather than authoring conformance back-check tooling from scratch.
  • Gazetteer authority lookups degrade gracefully: when external endpoints are unavailable, the wizard surfaces a "lookup unavailable; enter manually" message and falls through to the standard place-create flow. No write-path dependency.
  • G3 fixtures + the geometry-corruption regression case are explicitly named to prevent silent shape erosion under future SlotKind amendments. The fixture set is the engineering enforcement; the prose section here is the ratification commitment.
  • Tenant-facing CRS choice uses the srid modifier with PROJ library backing; tenant onboarding flow explicitly surfaces the CRS choice at tenant-config time with WGS84 as the default fallback.

Compliance​

Foundational principle​

Canonical Structure Is Shared; Interpretation Is Tenant-Specific. The platform-default preset carries the shared canonical structure (prefLabel, geometry, placeType). Tenant interpretation lives in tenant ontology mapping (Atlas's "Region" vs JPP's "Place" vs Visionis's "Geographic Location" vs potential modern-law-KE "Jurisdiction") + tenant forks (CRMarchaeo for archaeology; jurisdiction-specific for legal; habitat for biodiversity). The complies_with declarations are platform-canonical; the CRS choice and place-type vocabulary extensions are tenant-supplied via the managed multikey_kind=custom + Three-Tier vocabulary extensibility mechanisms per ADR-038 v1.2 §D10. Boundary preserved.

Open Questions​

These resolve in the Phase B.5 implementation spec or in companion ADRs:

  1. Platform domain for the preset-registry IRI scheme — load-bearing for ALL initial-library preset ADRs (ADR-038, ADR-039, ADR-040, and the future Person, Document, Event, and ClaimCluster preset ADRs). v1.0 of ADR-038 + ADR-040 used ke.atlomy.org, conflating the platform with the Atlomy tenant. The eventual canonical domain is a platform-naming + infrastructure decision (parent organization owns the choice; candidates include ke.org-class TLDs, knowledge-environments.org-class explicit names, or a parent-org subdomain). Resolution gates ADR-039 ratification (and retroactively requires ADR-038 + ADR-040 amendment to replace ke.atlomy.org references). File as a decision-log entry once platform-naming converges; until then, ADR-039 uses <platform-domain> placeholder.
  2. External gazetteer endpoint resilience: if Pleiades / GeoNames / Wikidata endpoints degrade, should the platform cache snapshots for offline lookup? Recommend: cache subscribed-tenant gazetteer entries locally on first lookup; refresh on a configurable cadence (similar to ADR-040 v1.2 §Open Question 2 PeriodO cache pattern). Resolved in Phase B.5 implementation note.
  3. Geometry simplification for federation queries: complex MultiPolygons (e.g., the Bronze Age technological adoption in disjoint regions) can be computationally expensive in federation geo:sfWithin queries. Should the platform pre-compute simplified bounding-box approximations? Recommend: yes — bbox slot (§D3) carries the simplification; PostGIS GIST index accelerates federation queries against the bbox. Resolved in ADR-041 + Phase B.5.
  4. Cross-CRS query reprojection at federation time: when a SPARQL query specifies a bbox in WGS84 but a target tenant's geometries are in EPSG:27700 (British National Grid), should the platform reproject at query time or require the query to be CRS-explicit? Recommend: auto-reproject at query time via PROJ; surface CRS-explicit query form as an advanced option. Resolved in ADR-041 + Phase B.4 federation queryability work.
  5. 3D-place handling: archaeological stratigraphy + photogrammetry produce 3D point clouds + meshes. Should geometry support 3D coordinates (z-axis)? Recommend: GeoJSON RFC 7946 supports 3D Position; the GEOMETRY SlotKind accepts both 2D and 3D coordinate arrays; visualization layer renders 3D via the existing spa/src/pages/three_d_model/ drill-in. Resolved when 3D-archaeology use case is first implemented (post-Phase B.5).
  6. placeType vocabulary growth via tenant-fork: which Tier 1 platform-canonical values land in v1 vs which are deferred to tenant-fork emergence? §D2's initial enum has 12 values; a CRMarchaeo-aligned fork would add stratum, excavation-unit, find-context; a jurisdiction fork would add legal-district, treaty-area. Recommend: v1 ships the 12 generic values; fork-specific values land via tenant-fork (Tier 2) and may auto-promote to Tier 1 via Threshold-A. Resolved per ADR-038 v1.2 §D7 emergence mechanism.
  7. Privacy + data-sensitivity for places: some place entities are sensitive (archaeological site coordinates that should not be public to prevent looting; private property boundaries). Should the preset declare a privacy-sensitivity flag? Recommend: yes — add a recommended placeSensitivity slot in §D3 (enum: public / tenant-internal / tenant-private) per ADR-035 capability-flag permission model; projection layer respects the flag (public-reader surface filters tenant-internal places out by default). Deferred to ADR-039 v1.1 amendment after integrative-tenant onboarding surfaces the use case.
  8. Composed E4 projection edge cases: when a Period subscriber's spatialExtent references a Place subscriber whose geometry is MultiPolygon (e.g., the Bronze Age in disjoint regions), how does the CIDOC E4 projection emit? Recommend: emit each Polygon as a separate E92 Spacetime Volume linked via P10 falls within to the parent E4 Period; cluster as the composed projection. Resolved in Phase B.5 implementation + ADR-030 SHACL fixture authoring.
