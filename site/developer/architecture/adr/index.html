Architecture Decision Records (ADRs)

This directory contains Architecture Decision Records for the KE (Knowledge Environments) Platform. Atlomy Atlas is the original software the platform grew out of, now one tenant among others; "Atlomy" persists as brand. Older ADR prose may still say "Atlomy" when referring to the platform — read in that historical context.

What is an ADR?​

An ADR documents an important architectural decision, including:

  • Context: What forces led to this decision?
  • Decision: What did we decide?
  • Consequences: What are the trade-offs?
  • Alternatives: What else did we consider?

Purpose: ADRs are our institutional immune system. They prevent future engineers from:

  • Reintroducing anti-patterns
  • Asking "why did we do it this way?"
  • Undoing decisions without understanding the trade-offs

Foundational Principle​

Canonical Structure Is Shared; Interpretation Is Tenant-Specific

See Platform Principles for the complete architectural foundation.

The Pillars​

These ADRs form a self-reinforcing system:

  1. ADR-001: Who the system serves (operational vs epistemic users) — and that the epistemic interface is a configurable shell, not a fixed Atlomy UI
  2. ADR-002: What can exist (hybrid ontology with governance) — relational floor + JSONB tenant extensions
  3. ADR-003: How knowledge is queried (GraphQL as contract) — archetype-polymorphic, tenant-label-aware
  4. ADR-004: How meaning drifts safely (tenant ontology mapping) — labels, sub-types, vocabularies, field mappings
  5. ADR-005: How the frontend is structured (standalone React SPAs) — data-driven module composition per tenant
  6. ADR-006 (Sprint 13): What archetypes exist and what they guarantee (capability contracts)
  7. ADR-007: Sub-tenant workspaces
  8. ADR-008: Tenant composition rules and reviewer guidance
  9. ADR-009: Platform-native entity conventions and relationship UX
  10. ADR-010: Parser-first, LLM-second relationship resolution
  11. ADR-011: OpenSearch + ICU + per-language analyzers as the per-tenant search engine — Lucene's analyzer ecosystem covers the wider-net language tail (Greek polytonic, Arabic root, CJK, Hebrew, Sanskrit, Persian, Coptic, ...); aligns with the federated_discovery_spec's ES-based aggregator tier; PGroonga is the named retreat target
  12. ADR-012: Tenant configuration flows through a runtime pipeline, never code — closes the proposal-to-config loop, forbids per-tenant Python migrations for slot/resolver wiring
  13. ADR-029: Published Entry surfaces read from versioned projections/export snapshots — keeps live authoring on django-tenants while making public scholarship durable, cacheable, institutional-facing, and not dependent on a pure SPA or V1 search documents
  14. ADR-031: Authoring source rows carry explicit versions/content hashes — makes optimistic concurrency, importer merge discipline, and publication dependency evidence share one source-model contract

See Platform Principles for how these connect. See Tenant Capability Matrix for concrete ATLOMY vs VISIONIS realizations.

Creating a New ADR​

Use this template:

# ADR-XXX: [Title]

**Date**: YYYY-MM-DD
**Status**: Proposed | Approved | Deprecated | Superseded
**Deciders**: [Who decided]

## Context
What forces led to this decision?

## Decision
What did we decide?

## Consequences
### Positive
### Negative
### Mitigations

## Alternatives Considered
What else did we evaluate?

## Implementation
How will this be done?

## Compliance
How does this align with other decisions/principles?

## References
Links to related docs, discussions, etc.

ADR Lifecycle​

Proposed → Under review Approved → Active, should be followed Deprecated → Still honored but being phased out Superseded → Replaced by newer ADR (link to replacement)

Governance​

Who can create ADRs?

  • Any engineer can propose
  • Architecture team + tech lead must approve
  • Significant decisions require consultant review

When to create an ADR?

  • Choosing a major technology (React, GraphQL, etc.)
  • Establishing a pattern that affects multiple teams
  • Making a decision with long-term consequences
  • Preventing a known anti-pattern

When NOT to create an ADR?

  • Implementation details (use code comments)
  • Temporary workarounds
  • Decisions easily reversible
