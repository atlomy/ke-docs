ADR-017: Slot Config as Tenant-Authoritative Manifest with Platform-Canonical Contract Compiler

Date: 2026-05-07 Status: Proposed Deciders: Architecture Team (Round-11 absorption + 2026-05-07 three-source synthesis) Related: ADR-002 (Hybrid Ontology), ADR-003 (GraphQL Epistemic Contract), ADR-006 (Archetype Capability Contracts), ADR-012 (Tenant Config via Runtime Pipeline), ADR-015 (Tenant Admin Shell — Native React), ADR-016 (Telemetry Substrate) Supersedes: nothing — formalizes a strategic question implicit in ADR-002 ("Tables define what can exist; JSON defines how it is expressed") and clarifies the role of TenantArchetypeFormConfig as the canonical tenant-interpretation manifest. Evidence chain: docs/devlogs/2026_w19/2026-05-07_0905_round11-absorption.md (Round-11 absorption), docs/devlogs/2026_w19/2026-05-07_0101_ke-term-form-editable-jsonb-mirror.md (Round-10 implementation arc), in-conversation 2026-05-07 three-source synthesis (industry-pattern survey + Codex prior-art analysis).

Context​

The KE Admin Overlay (Phase 0–12, May 2026) shipped a slot-driven term-form editing surface backed by TenantArchetypeFormConfig rows + a JS "JSONB-mirror" that syncs slot inputs into the standard Django JSONField textarea. The overlay works end-to-end on atlomy_atlas, but Round-11 NotebookLM absorption (4 artifacts) plus 2026-05-07 prior-art analysis surfaced three load-bearing structural concerns that this ADR addresses.

Concern 1 — Manual authorship cost felt unscalable​

Slot configs are manually authored or update_or_create-materialized per-tenant. atlomy_atlas accumulated 37 TERM slots before Round-10 cleanup brought it to 31 — six were broken duplicates, two had source_field values that no longer matched any Coda key. Initial framing: "manual authorship doesn't scale to 1000 tenants — replace with typed-schema source-of-truth." Codex synthesis (verified against atlomyapp/models.py:357-359) corrected this framing: TenantArchetypeFormConfig is explicitly modeled on Directus's directus_fields pattern — "the form/display layer is data, not code." The authorship surface is right; what's missing is the contract compiler that generates editor schemas, validators, and projections FROM the slot config.

Concern 2 — Drift is silent and additive-only​

Verified in epistemic/services/slot_config_materializer.py:200 + atlomyapp/services/coda_epistemic_import.py:815: the materializers use update_or_create keyed on (archetype, slot_name). They never delete rows whose source_field no longer resolves in any entity. A renamed Coda column writes a new slot; the old slot survives forever. The escape hatch (prune_atlas_retired_slot_configs) is reactive — only deletes rows explicitly listed in the retired list. Drift accumulates across the lifetime of the tenant.

Concern 3 — JSONB-mirror has a silent-failure surface​

Verified at templates/admin/ke/_term_form_overlay.html:228-238:

try { data = JSON.parse(ta.value || "{}"); }
catch (err) {
  console.warn("KE: data JSONB invalid; slot edit not synced", err);
  return;
}
// Shallow path only — most Coda-imported keys are flat.
// Multilingual / list-shaped slots are out of scope until the
// slot-aware writer view ships.
if (path.indexOf(".") !== -1) return;
data[path] = input.value;
ta.value = JSON.stringify(data, null, 2);

console.warn is invisible to users. Early return is silent. Multilingual / list-shaped slots silently drop edits. Per-slot validation (the required flag) is unenforced — standard ModelForm only validates "is this valid JSON?", not slot-level constraints.

Why now — and what changed in framing​

ADR-002 (Hybrid Ontology) and ADR-003 (GraphQL Epistemic Contract) committed the platform to typed contracts as the destination. ADR-015 (Native React Shell) targets a typed-API React frontend. The slot-config + JSONB-mirror system is the BRIDGE — and Round-11 evidence shows the bridge is bleeding manual-authorship cost and silent-failure risk.

This ADR was initially drafted (v1, deleted) with the framing "slot configs become a projection of typed schema." That framing was REJECTED during the 2026-05-07 three-source synthesis (in-conversation analysis + first researcher's draft + Codex prior-art analysis). Reasons:

  1. TenantArchetypeFormConfig already declares more than form fields: widgets, source paths, required, linkable slots, lookup projections, multilingual policy, composition templates, capability flags. It IS the canonical manifest.
  2. Replacing it with an authored typed schema would shift authorship cost, not eliminate it — same per-(tenant, archetype) authorship work in a different formalism.
  3. ADR-006 (Archetype Capability Contracts) + ADR-012 (Tenant Config via Runtime Pipeline) already commit the platform to "tenant interpretation as data, not code." Slot config IS that data layer.
  4. Salesforce metadata virtualization, Directus directus_fields, Jetpack Compose / React slot APIs all use metadata-table-as-source — slot config is the industry-canonical primitive, not an anti-pattern.

The corrected framing: slot config IS the source of truth. What's missing is the contract compiler that generates editor schemas, server-side validators, projection views, and (optionally) DB-level CHECK constraints — and per-write validation that prevents drift structurally.

Decision​

The platform commits to Slot Config as Tenant-Authoritative Manifest, with Platform-Canonical Contract Compiler operating over a Platform-Canonical Capability Vocabulary. Concretely:

How this respects the foundational principle​

The platform's foundational principle is "Canonical Structure Is Shared; Interpretation Is Tenant-Specific." This ADR's architecture lands cleanly inside that split:

  • Platform-canonical (shared, in code, not tenant-customizable):

    • The archetype vocabulary (TERM, DOCUMENT, PASSAGE, ...) — epistemic/models.py ARCHETYPE_CHOICES
    • The widget vocabulary (text, richtext, multilingual, linked_record, ...) — Widget enum in atlomyapp/models.py:362
    • The capability vocabulary (linkable, multilingual, lookup_for, source_layer, resolver_kind) — enums + columns defined in code
    • ADR-006 archetype capability contracts (what each archetype MUST support, regardless of tenant)
    • The TenantArchetypeFormConfig model structure (Django model definition, columns, indexes)
    • The Contract Compiler service itself — runs the same algorithm for every tenant
    • Validation rules in EpistemicEntity.clean() + SlotWriteService enforcing the canonical capability vocabulary

  • Tenant-specific (interpretation, in tenant data, tenant-authored):

    • TenantArchetypeFormConfig rows — which slots exist for this tenant's TERM, what they're labeled, which widget choice within the platform vocabulary, which source_field path, which composition_template
    • EpistemicEntity.data JSONB body — tenant data in tenant interpretation
    • Editor contracts, projection views, validators, and (Phase 5) DB CHECK constraints emitted by the Contract Compiler — generated per-tenant FROM each tenant's own slot config

The Contract Compiler runs canonical algorithm against tenant data, producing tenant outputs. Slot config rows are the tenant-authoritative source-of-truth (within each tenant's scope) — they are NOT platform-canonical. "Canonical" in this ADR's wording always refers to the platform-shared layer; the slot-config rows are deliberately the tenant interpretation half of the principle.

Three-layer UI surface model (Codex synthesis, 2026-05-07)​

Every tenant-data UI surface in KE renders from one of three distinct layers. Naming them prevents accidental conflation (which is what produced the "Terms not Lemma Pool" + "no slot data on changelist" UX gaps in 2026-05-07):

LayerResearcher answerDefault state todayOwned by
Source mirror"Show me Coda's Lemma Pool as it was imported" — faithful reproduction of original column names + values, no platform interpretationNOT IMPLEMENTED. Open Question for Round-12.Researcher / archivist surface
Tenant projection"Show me my Terms with my fields" — driven by TenantArchetypeFormConfig through the Contract CompilerPartially implemented (form: yes; changelist: no; sidebar: no)Researcher daily-use surface
Platform substrate"Show me all EpistemicEntity rows + governance metadata"What the default Django Admin changelist currently shows; it is the WRONG default for researchersPlatform admin / debugging surface

Default surfaces are tenant projection, not platform substrate. Provenance, governance, lifecycle, status, confidence, canonical_type, and source_mapping_proposal_id are platform-substrate fields — they are admin/debugging metadata, not daily researcher data. They MUST be demoted to advanced/admin surfaces (collapsed fieldsets, list_filter, dedicated /admin-debug/ views, or toggleable). Default views for researchers MUST surface tenant projection (slot-driven columns, tenant-relabeled archetype names).

This is the load-bearing UX consequence of the foundational principle: tenant interpretation is the default; platform substrate is the exception. Surfaces that violate this must be explicitly listed and audited (see Compliance — UI-surface audit).

The decision​

  1. TenantArchetypeFormConfig stays as the tenant-authoritative manifest. It is the single declared source-of-truth WITHIN each tenant's scope for slot existence, widgets (chosen from the platform-canonical Widget enum), source paths, capability flags (chosen from the platform-canonical capability vocabulary), multilingual policy, composition templates, and lookup projections. ADR-002 fidelity preserved. Sharpening sentence (Codex review, 2026-05-07): "TenantArchetypeFormConfig is not platform-canonical structure; it is the authoritative tenant-scoped interpretation manifest constrained by platform-canonical archetype contracts." "Canonical slot config" in this ADR means "the one source for generated tenant editor behavior," NOT "tenant config becomes shared ontology."

  2. Add a Contract Compiler. A service layer that consumes slot configs and generates, in order of load-bearing weight:

    • Editor contract for ADR-015 Native React shell — the LOAD-BEARING long-term output (GraphQL schema or typed JSON descriptor — Round-12 decides). The Native React shell is the canonical editing surface per ADR-015; this is what Phases 3-4 build for.
    • Sidebar projection — per-tenant archetype labels via TenantOntology.display_label (ADR-004 infrastructure already exists). Resolves the "TERM" vs "Lemma Pool" gap. Phase 1 wiring (~30 min) is the cheapest tenant-projection win available; full Contract Compiler integration in Phase 3.
    • Changelist projection — tenant-projection list columns per archetype, derived from slot config (display_in_list flag or top-N by display_order). Replaces today's platform-substrate-default changelist (status/confidence/canonical_type) with researcher-default (lemma / translations / morphology). Phase 3 of the Contract Compiler.
    • Per-archetype projection views (already partially shipped — epistemic/services/per_archetype_views.py:753 is KE infrastructure, used by read paths, search, and any external editor surface). Generated from slot config; not Directus-specific.
    • Server-side write validator — a SlotWriteService that accepts {entity_id, slot_name, value}, resolves the slot config, writes the value to JSONB OR the typed edge layer (EntityRelationship), validates required/type/widget shape, returns structured errors. Used by both Django Admin overlay (bridge) and Native React shell (long-term).
    • JSON Schema artifacts for testing + auditing per archetype.
    • Optional DB-level CHECK constraints via pg_jsonschema — for mature archetype contracts only, after shape stabilizes (Codex caveat: Postgres CHECK constraints assume immutable expressions; making every slot-config save emit DDL is operationally untenable for early-stage archetypes).
    • Optional Directus metadata refresh — only for tenants electing the experimental Directus bridge (docker-compose.directus-tenant.yml / directus-jpp.yml). Not a core platform output. Treated as an optional consumer of the contract compiler, not a primary target.

  3. Per-write validation closes the EDIT-PATH drift surface. A platform-canonical slot validation service (the same logic that powers SlotWriteService) is invoked by admin forms, importers, APIs, management commands, and is delegated to by EpistemicEntity.clean() where applicable (Codex caveat, 2026-05-07: Django's clean() is NOT guaranteed on all save/import paths — raw .save() skips it; importers and APIs typically use raw .save(). The service must be the primary enforcement point, with clean() as one consumer of it, not the reverse). The service enforces:

    • Required slots reject save when empty.
    • Widget-typed values reject mismatched payloads.
    • Phantom keys (data without slot config) flagged as warnings.
    • Orphan slot configs flagged via audit, NOT a hard reject. Validation against actual entity rows is appropriate when a source-schema/materializer registry is unavailable; with one available, validate against the registry and treat zero data hits as audit warning UNLESS the slot is required (which becomes a hard reject only when the registry confirms the source is reachable). This avoids false-positives on greenfield, sparse, optional, and newly-added slots (Codex review, 2026-05-07).
    • Import/materializer drift (rows accumulated by the additive update_or_create pattern across multiple imports) is NOT closed by per-write validation alone — it is made detectable by the audit flow and governed by the audit_slot_configs command + the existing prune_atlas_retired_slot_configs retired-list pattern. Drift policy = audit + reactive prune, not silent cleanup.

  4. JSONB-mirror is replaced in stages, not patched. Per-keystroke JSON.parse → Alpine reactive store (Phase 1) → typed editor state object validated by the slot validation service before submit (Phase 2+). Honest scope (Codex review, 2026-05-07): Phase 1 Alpine store eliminates the per-keystroke JSON.parse race — that's the silent-failure surface that disappears in Phase 1. Multilingual / list-shaped / nested-dotted paths still require explicit handling (or disabled/error states with clear UX) until Phase 2's SlotWriteService lands. Don't claim Phase 1 closes everything.

  5. Capability flags stay declarative; validation moves to write-time. linkable, multilingual, required, is_relationship remain explicit slot-config columns (matching Directus's pattern); the contract compiler enforces their consequences (typed-edge writes via EntityRelationship for linkable=True, multilingual repeater UI for multilingual=True, etc.).

Migration Path​

Phase 1 — Validation + Reactive Mirroring (Bridge, ~1 sprint)​

Tactical focus: eliminate Round-11's HIGH-severity concerns without rewriting the substrate. Maps to Round-11 action items A1-A5 + B5.

  • A1 (revised) — Alpine reactive store replaces the DOM-scraping JS mirror in templates/admin/ke/_term_form_overlay.html. All slot inputs bind to a single x-data reactive object via x-model; serialization to the hidden data textarea happens exactly once on Save submit. Eliminates the per-keystroke JSON.parse race entirely.
  • A2 — Per-slot required validation in the slot validation service (invoked by admin forms, importers, APIs; delegated to by clean() where applicable). JS pre-submit also validates for fast UX feedback, but the service is the enforcement point.
  • A3 — TenantArchetypeFormConfig.clean() validator resolves source_field against the source-schema/materializer registry when available; falls back to "≥1 entity row of that archetype" only when no registry is available. Zero data hits = audit warning, not hard reject, UNLESS the slot is required AND the registry confirms the source path is reachable. --allow-greenfield flag for tenants with no data yet. (Codex review, 2026-05-07: avoids false-positives on greenfield / sparse / optional / newly-added slots.)
  • A4 — audit_slot_configs Django command formalizes the markdown-script as a reusable per-tenant audit; runnable as a post-import webhook.
  • A5 — Pre-commit hook for multi-line {# #} (promoted from docs/troubleshooting.md's audit script — two-strikes-equals-automation discipline).
  • A6 (NEW, 2026-05-07) — Wire TenantOntology.display_label into sidebar. atlomy/settings.py sidebar lambda currently hardcodes ('TERM', 'Terms', ...); should read TenantOntology rows for the active tenant and use display_label per archetype. Restores tenant relabel ("Lemma Pool" instead of "Terms" for atlomy_atlas; tenant-specific labels for jpp/visionis). Infrastructure already exists per ADR-004; ~30 min wiring fix. Stable, immediate, user-visible.
  • A7 (NEW, 2026-05-07) — Demote provenance/governance from default changelist. epistemic/admin.py list_display currently surfaces status, confidence_score, canonical_type, created_at as default columns — these are platform-substrate fields, not researcher-data. Move them to list_filter (still findable) + collapsed form fieldsets (already collapsed per Round-10). Default changelist becomes researcher-friendly. Stable bridge until full Phase 3 Contract Compiler ships.
  • B5 — Sidebar deep-link for the optional Directus bridge (only for tenants currently exercising the docker-compose.directus-tenant.yml experimental path). Honest framing: Directus is an experimental bridge, not the destination — Native React (ADR-015) is. B5 is a small ergonomic patch for tenants on the bridge today; it does not commit the platform to Directus.

Phase 2 — SlotWriteService + atlomy_atlas TERM POC (~2 sprints)​

  • Build the SlotWriteService: Python service accepting {entity_id, slot_name, value}. Resolves slot config; routes write to JSONB OR EntityRelationship typed edge per slot's is_relationship flag; validates against the slot's widget + capability flags; returns structured errors.
  • Wire the Django Admin term-form to use SlotWriteService instead of direct JSONField textarea persistence (the textarea remains as a debug/view surface, not the write path).
  • Unit + integration tests covering: required-violations, widget-type mismatches, multilingual writes, linkable writes via typed edges.

Phase 3 — Contract Compiler v1 (Editor Schema + Projection Views) (~1-2 sprints)​

  • Build the contract compiler service: takes a (tenant_schema, archetype) pair, emits a typed editor schema (form: GraphQL descriptor or JSON envelope — Round-12 decides).
  • Formalize the per-archetype views pipeline (epistemic/services/per_archetype_views.py) as a contract-compiler-driven generator: views are derived FROM slot config, not authored alongside it.
  • Generate JSON Schema artifacts as validation/test artifacts (NOT yet wired as DB constraints).
  • (Optional, deferred) Directus metadata regeneration as an additional consumer of the contract-compiler output, gated on whether any tenant continues to use the experimental Directus bridge at this point.

Phase 4 — Native React Editor Consumes Contract (~1-2 sprints, gated on ADR-015 maturity)​

  • ADR-015 Native React shell consumes the editor contract; renders slot rows from contract output, not from raw slot-config rows.
  • Editor state in React is the typed validated object (per Codex's "typed editor state validated before submit" recommendation).
  • JSONB-mirror is now a fallback path used only by the Django Admin overlay.

Phase 5 — Optional DB-Level Hardening + Bridge Deprecation (~1 sprint per archetype that matures)​

  • For archetypes whose contracts have stabilized (low rate-of-change in slot config + clear required/type invariants): emit pg_jsonschema CHECK constraints from the contract compiler. These are the deepest defense against silent data corruption.
  • Hot-slot expression indexes from telemetry (ADR-016 dependency): when telemetry shows a slot is high-frequency-filtered or full-text-searched, the contract compiler can emit CREATE INDEX ... ON entity ((data->>'X')) for that slot. Per-tenant, telemetry-driven, NOT universal wide-table.
  • Once ADR-015 is mature: the JSONB-mirror in the Django Admin overlay is removed; the React editor is the single editing surface for tenant data; Django Admin remains for platform-admin / debugging.

Alternatives Considered​

  • A. Patch the current pattern only (Round-11 "warning banner" — A1 v1). Rejected as standalone. Mitigation only; does not eliminate the parse race or the drift root causes. Subsumed by Phase 1's reactive store, which fixes the cause, not the symptom.
  • B. Coda metadata as source of truth. Rejected. Solves atlomy_atlas only; doesn't generalize to jpp / visionis / future tenants. Per-tenant solution where a platform-wide one is needed.
  • C. Salesforce "Wide Table" pattern. Rejected. Premature optimization at KE's scale (atlomy_atlas: ~7000 entities). Conflicts with ADR-002's principle. Maintenance ceiling (~50-100 typed columns) doesn't fit slot-rich archetypes. Salesforce's actual lesson is metadata-as-source (which we already do); the wide-table storage substrate is not the export.
  • D. Typed schema as source of truth (ADR-017 v1, withdrawn). Rejected on reflection. Initial framing proposed authoring a typed schema per (tenant, archetype) and demoting slot config to an overrides table. Codex synthesis correctly identified this as: (a) shifting authorship cost into a different formalism, not eliminating it; (b) conflicting with ADR-006 + ADR-012's existing commitment to "tenant interpretation as data"; (c) ignoring that TenantArchetypeFormConfig already follows the industry-canonical metadata-as-source pattern (Directus directus_fields, Salesforce metadata tables). The strategic concerns the v1 framing surfaced are absorbed by the Contract Compiler approach without the cost.
  • E. Slot Config as Canonical Manifest + Contract Compiler. CHOSEN. Preserves the right primitive; adds the missing layer (compiler + validator + per-write enforcement); aligns with ADR-002/006/012; supports ADR-015 React shell via generated editor contract; supports ADR-016 telemetry via hot-slot index decisions.

Consequences​

Positive​

  • Edit-path drift is closed at write-time. Phase 1's slot validation service + Phase 2's SlotWriteService make new edit-path drift structurally impossible — invalid slot configs reject save before persisting; phantom keys flagged. Import/materializer drift (the additive update_or_create accumulation across imports) becomes detectable by the audit flow and governed by audit_slot_configs + the existing prune_atlas_retired_slot_configs retired-list pattern. (Two distinct drift channels; this ADR closes the edit channel and adds detection + governance for the import channel — does not silently auto-prune.)
  • JSONB-mirror silent-failure surface eliminated structurally. Phase 1 reactive store removes the per-keystroke parse path entirely. Multilingual / list-shaped slots that today silently drop edits (templates/admin/ke/_term_form_overlay.html:233) get explicit handling in Phase 2's SlotWriteService.
  • Tenant authorship cost stays bounded. No new authoring surface introduced. The TenantArchetypeFormConfig admin remains; tenants edit labels, widgets, capability flags as today. The contract compiler removes derived-artifact authoring (editor schemas, Directus metadata, validators) — those become generated.
  • ADR-015 React shell unblocked. Phase 4 consumes a generated editor contract instead of raw slot configs — the boundary is typed, the React shell stays decoupled from per-tenant slot-config row shapes.
  • ADR-016 telemetry leveraged. Phase 5 hot-slot indexes are telemetry-driven, not universal — they're a NATIVE consumer of the telemetry substrate ADR-016 commits to.
  • Industry-canonical alignment validated. The Directus / Salesforce / Compose-Slot precedents the 2026-05-07 prior-art analysis cited all use metadata-as-source. KE is on the canonical path.
  • Multi-stage hardening discipline. App-layer validation → JSON Schema artifacts → optional DB CHECK constraints → expression indexes. Each stage gated on archetype maturity; nothing forced everywhere upfront.

Negative​

  • Multi-sprint engineering investment. Estimated 4-6 sprints across Phases 2-5. Phase 1 (~1 sprint) is the only low-cost increment.
  • SlotWriteService is a real abstraction (~2-sprint Phase 2). Adds a service layer the Django Admin term-form must route through; admin-form code currently writes via standard JSONField widget. Migration risk is bounded but real.
  • Contract compiler must handle multilingual + RichText + Reference shapes carefully. Not novel work, but non-trivial — multilingual [{value, language_code}] shapes need per-language repeater UI; RichText needs sanitizer integration; references need typed-edge writes via EntityRelationship.
  • Phase 4 timing is gated on ADR-015 (Proposed-not-Approved). If ADR-015 ratification slips, Phase 4 slips with it. Phase 1-3 are independent.
  • pg_jsonschema operational friction confirmed. Phase 5 DB-level CHECK constraints are HIGH-VALUE for stable archetypes, but: per-tenant constraint regeneration on slot-config changes; custom Postgres image build; per-environment install. Re-import preservation of researcher edits (2026-05-07 amendment)​

The load-bearing concern: tenants edit entities in KE platform AFTER importing from source; subsequent re-imports must NOT clobber researcher edits. With the slot UI now editable + reactive-store-validated (Phase 1 A1), researchers WILL edit entities. Verified in atlomyapp/services/coda_epistemic_import.py: today's --replace is destructive (delete-and-recreate). Any researcher edits stored in EpistemicEntity.data on those rows are lost on re-import unless represented again by the source payload — which is silent data loss.

The architectural model:

source-managed fields     refreshed from import payload (importer owns)
tenant extension fields   preserved from existing entity.data (researcher owns)
identity key              matches source row → existing entity (per-tenant config)

Three primitives needed (general platform code, not tenant-specific):

  1. Per-tenant identity_key configuration — declared in tenant import config (atlomy_atlas_coda.json / jpp_mysql.json / visionis_*.json). Names the stable source-system primary key that lets the importer match new-payload-row to existing-entity. Prerequisite work: importer must preserve this key into EpistemicEntity.provenance on every import (see Prerequisite Gap below). Examples:

    • Coda: row ID (provenance.source_id)
    • MySQL: declared primary key column

  2. Source schema introspection at import time — the importer knows which keys it manages (the source's columns). Anything OUTSIDE the source schema in existing data is tenant-extension and preserved by the merge.

  3. Per-field merge semantics:

    • Keys IN source schema: source value wins (refresh)
    • Keys NOT IN source schema: existing value wins (preserve as tenant extension)
    • When source schema removes a key (column dropped/renamed): retire the slot config (orphan-retirement, source-shape-aware per Codex review) — but ONLY when the key was source-managed AND ONLY behind an explicit --prune-orphan-slot-configs flag, never silent.

Dual-mode flag (Codex review, 2026-05-07): Don't silently change --replace semantics. Today's destructive --replace keeps current behavior; introduce a new mode for the merge:

  • --replace (current): destructive — wipes imported state including researcher edits. Useful for true "start over" scenarios.
  • --merge-replace (new): preserves tenant extensions; refreshes only source-managed fields; flag-gated orphan slot-config retirement.

Once the new mode is proven (atlas re-import works without losing researcher edits across multiple cycles), promote --merge-replace to the default; require explicit --full-wipe for the destructive variant.

Prerequisite gap discovered (Codex review, 2026-05-07): atlas's current Coda config drops Row ID for TERM imports. The importer must preserve that key into provenance.source_id (or equivalent per-tenant identity-key field) BEFORE the merge mechanism can match rows reliably. source_row_index is not enough — row order changes between exports. This is a small importer fix (one-time, atlas-config edit + importer write-side change) that unblocks the whole merge architecture.

Implementation phases:

  • Phase 1.5 (prerequisite, ~1h): importer preserves provenance.source_id from each tenant's declared identity-key column. Atlas config update + importer code change.
  • Phase 2.A (merge mechanism, ~2-3h): implement --merge-replace mode in import_coda_epistemic + import_mysql. Source schema introspection + tenant-extension preservation logic. Tests covering: (a) source-managed field refreshed; (b) tenant-added field preserved; (c) tenant-modified field preserved; (d) source-renamed key + flag-gated retirement.
  • Phase 2.B (orphan retirement, ~1h): source-shape-aware retirement behind --prune-orphan-slot-configs flag. Compares slot configs to imported payload schema (NOT to value resolution). Sparse-but-valid slots survive.
  • Phase 2.C (atlas migration, ~30 min): run --merge-replace --archetypes=DOCUMENT,PASSAGE to complete v2-native migration safely.

Until merge mechanism ships, atlas DOC/PASS re-import is BLOCKED — running it under current --replace semantics would destroy any researcher edits accumulated since Phase 1 A1 shipped.

Compliance — Diagnostic vs Closure principle (Codex review wording, 2026-05-07)​

"Diagnostic tools should not become cleanup infrastructure. A healthy enforced tenant should have zero unexpected audit findings; any recurring finding means a source/import/write loop is still open. Grouping/dedup in audit output is useful for readability, but it is not the fix."

The audit (audit_slot_configs) is a regression detector for steady state, not a cleanup tool. Findings push fixes UPSTREAM into import/materialization/write paths. Dedup or grouping in audit output is acceptable for readability but is NOT a substitute for closing the upstream loop. When a tenant's audit produces noise, the response is "fix the import/materializer/write path"; not "make the audit quieter."

Round-13 absorption corollary (2026-05-07): configurable suppression mechanisms for sparse-but-valid findings (config-file ignore lists, dynamic-threshold auto-hide) ARE post-hoc closure paths and were rejected for the same reason. SPARSE_SLOT_CONFIG warnings are actionable signals (column exists in source schema; researcher decides to populate or remove). Silencing them via config moves the diagnostic INTO the closure loop — exactly the conflation this principle warns against.

Compliance — Compare declared layer to declared layer, never to instance state (formal phrasing, 2026-05-07)​

The structural-comparison invariant — when validating a declared schema layer against runtime state, compare declared layer to declared layer, never to instance state — is load-bearing across multiple Phase 2.A mechanisms. Snappy form for casual contexts: "compare structure to structure, not values."

Three independent mechanisms in this ADR honor the invariant:

  1. F3 audit ORPHAN_SLOT_CONFIG vs SPARSE_SLOT_CONFIG split: ORPHAN compares slot config's data.X source key against the observed entity-key union (declared-layer-to-declared-layer-proxy). SPARSE acknowledges instance-state emptiness without conflating it with structural absence.
  2. compute_orphan_slot_configs (import-time pruner): compares slot configs against fresh-payload source schema (declared-to-declared, with no proxy needed when fresh payloads are available).
  3. Retirement schema extension (source_field on retired entries): compares retired-shape declaration against current slot config declaration; instance state is irrelevant.

The phrase "structure to structure" was the snappy form added to partner_model 2026-05-07 ~13:00 during Phase 1 design discussions. Round-13 prescriptive review #5 caught the ambiguity ("what is 'structure'? schema? proxy? data shape?") and proposed the formal "declared layer to declared layer" form for ADRs and architecture docs. Both forms convey the same invariant; pick by reading-context.

B.1 — What changed​

The Phase 2.A identity strategy ("provenance.source_id from a tenant-declared source-system primary key") is preserved as the SHIPPED mechanism but is now framed as a TRANSITIONAL substrate, not the architectural endpoint. The new endpoint: an internal identity ledger as universal platform substrate; source-system IDs become INPUTS to the ledger, not the identity layer itself.

B.2 — Decision (amended per Codex review 2026-05-07; see §B.8 for verdict)​

The platform owns identity. The ledger is platform-canonical.

EntityIdentityLedger (per-tenant schema; mirrors EpistemicEntity scoping)
- platform_uuid     : UUIDField (primary, platform-minted at first import)
- archetype         : CharField (scoping)
- source_key        : CharField (stable configured key per tenant config —
                                 e.g. "atlas-coda-prod", "jpp-mysql-2026",
                                 NOT a DSN, file path, or filename)
- table_key         : CharField (Coda table, MySQL table, XLSX sheet)
- source_id         : CharField (the tenant-declared identity_key value)
- created_at, updated_at
- provenance        : JSONField (operational metadata: actual DSN/path/filename
                                  at time of import, init context, retire
                                  reasons, refresh history — operational, NOT
                                  identity-bearing)

Codex H1 fix (2026-05-07): source_key is a stable configured identifier per tenant config (e.g. "atlas-coda-prod"). It is NOT the DSN, file path, or filename — those are operational metadata that changes when an admin moves a file or rotates a DSN. The DSN/path/filename lives in provenance JSONB so an audit trail still exists, but it does NOT participate in identity uniqueness.

Invariants:

  • One row per (archetype, source_key, table_key, source_id) tuple.
  • EpistemicEntity.id references EntityIdentityLedger.platform_uuid (FK or stable equality).
  • On re-import: importer queries ledger by (archetype, source_key, table_key, source_id) to find the platform_uuid; merges into the matching EpistemicEntity. No source_id match → ledger insert + new entity.
  • Codex M1 fix (2026-05-07): created_by is NOT in the uniqueness scope. Actor attribution is provenance, not identity. Including it would fragment the same source row into multiple platform identities depending on which agent ran the import.
  • Codex H3 fix (2026-05-07) — atomicity model: ledger insert/update + corresponding entity insert/update happen IN THE SAME transaction.atomic() block as the existing merge body. A crash between ledger write and entity write rolls both back together. Phase 2.A.X's MergeRunState dirty-flag tracker is updated OUTSIDE the atomic block (start before, complete after) — same pattern as Phase 2.A.X. The dirty-flag tracker continues to surface partially-completed merges; the per-merge atomic block guarantees ledger and entity rows are consistent at write time.

Coexistence with EpistemicEntity.provenance.source_id (Codex H4 fix, 2026-05-07):

  • After Phase 2.B ships, provenance.source_id becomes a DEPRECATED COMPATIBILITY SIDECAR. The ledger is the authoritative identity layer; provenance.source_id is preserved on existing rows for backward-compatibility (read-only consumers, F1 backfill audit) but is NEVER WRITTEN BY NEW MERGE PATHS.
  • Pre-Phase-2.B existing rows retain their populated provenance.source_id field. The B.5.2 migration backfills the ledger from those rows; once backfilled, ledger is the lookup path.
  • Identity has ONE writable home (the ledger). A future ADR amendment can decide whether to drop provenance.source_id entirely (data migration) once consumers migrate; until then, deprecated-but-present coexistence prevents asymmetric-protection holes.

Source-restructure refresh pathway (Codex H2 fix, 2026-05-07) — scoped, not 2-column:

Tenant uploads a CSV with FOUR columns: (archetype, table_key, old_source_id, new_source_id). The ledger refresh command:

  1. Validates every row has all 4 columns populated (no partial coverage).
  2. Looks up each (archetype, source_key, table_key, old_source_id) tuple in the ledger; rejects unknown old IDs explicitly.
  3. Rejects rows where the new (archetype, source_key, table_key, new_source_id) would collide with an existing ledger row (would create duplicate identity).
  4. Rejects duplicate old_source_id entries within the CSV (ambiguous remap).
  5. Applies updates only after ALL validation passes (fail-closed; transactional).

The source_key is NOT a CSV column — it's specified via a CLI flag (--source-key <key>) so the operator must explicitly narrow the operation to one source. This mirrors the H1/F1 pattern: scope-narrowing is mandatory; cross-source CSV imports are refused.

Write paths to source (varies by source capability — but does NOT vary the identity layer):

  • Coda: API write-back of platform_uuid as a sidecar column (when API permits + tenant authorizes). Optional optimization; ledger remains authoritative even if write-back never happens.
  • MySQL: DBA cooperation (write platform_uuid into a sidecar column via DBA-side migration) when feasible.
  • XLSX: out of scope for write-back; tenant uses CSV refresh upload to update ledger after source restructure.

The CRITICAL framing-shift: write-back to source is OPTIONAL platform-side; the ledger is authoritative. Per partner_model 2026-05-07 calibration, identity primitive is uniform; write/refresh paths can vary by source capability.
