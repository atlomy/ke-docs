ADR-002: Hybrid Ontology (Relational + JSON)

Date: 2025-12-28
Status: Approved
Deciders: Architecture Team, External Consultant

Context​

Epistemic data in Atlomy is inherently schema-fluid:

  • Tenants have custom fields ("lemma_ar", "dialect_notes", etc.)
  • AI proposes new field structures
  • Multi-tenant ontologies diverge ("Lemma" vs "Term" vs "Concept")

Pure relational schemas require migrations for every tenant customization.
Pure JSON schemas lose queryability, governance, and explainability.

Decision​

We will use a Hybrid Ontology approach:

Principle​

Tables define what can exist. JSON defines how it is expressed.

Schema Design​

CREATE TYPE epistemic_status AS ENUM (
  'DRAFT',
  'AI_PROPOSED',
  'HUMAN_REVIEW',
  'APPROVED',
  'APPLYING',
  'APPLIED_TO_CANONICAL',
  'DEPRECATED',
  'REJECTED'
);

CREATE TABLE epistemic_entities (
  id UUID PRIMARY KEY,
  tenant_id UUID NOT NULL,
  
  -- STABLE: Epistemic primitives (relational)
  archetype VARCHAR(50) NOT NULL,        -- One of the canonical 7: DOCUMENT, TERM, ENTITY, EVENT, MEDIA, RELATIONSHIP, ANNOTATION
  canonical_type VARCHAR(50),            -- Stable classification (frozen by archetype contracts, ADR-006)
  status epistemic_status NOT NULL,      -- Governance state
  confidence_score DECIMAL(3,2),         -- AI confidence
  
  -- GOVERNANCE (relational = auditable)
  created_by VARCHAR(100) NOT NULL,
  approved_by VARCHAR(100),
  created_at TIMESTAMPTZ NOT NULL,
  modified_at TIMESTAMPTZ NOT NULL,
  
  -- FLEXIBLE: Tenant-specific expression (JSON)
  data JSONB NOT NULL,                   -- "title", "lemma_ar", custom fields
  provenance JSONB,                      -- AI reasoning, evidence, sources
  
  -- SEARCH (see Multilingual Search note below)
  search_vector tsvector GENERATED ALWAYS AS (
    to_tsvector('simple', data::text)
  ) STORED
);

-- Indexes
CREATE INDEX idx_entities_tenant_archetype ON epistemic_entities (tenant_id, archetype);
CREATE INDEX idx_entities_status ON epistemic_entities (status);
CREATE INDEX idx_entities_confidence ON epistemic_entities (confidence_score DESC);
CREATE INDEX idx_entities_data_gin ON epistemic_entities USING GIN (data);
CREATE INDEX idx_entities_search ON epistemic_entities USING GIN (search_vector);

Rationale​

What Goes in Relational Columns​

  • Governance fields: Status, confidence, approver (must be queryable for audits)
  • Classification: Archetype, type (needed for AI reasoning)
  • Metadata: Timestamps, creator (required for compliance)

What Goes in JSON Columns​

  • Tenant-specific fields: Custom attributes that vary by ontology
  • AI provenance: Reasoning, evidence, model version (read-mostly, complex structure)
  • Flexible data: Fields added by tenants or AI without migrations

Concrete Example: Same Archetype, Different Tenant JSONB​

The TERM archetype has one universal relational field — canonical_form — validated by the archetype contract (ADR-006). Everything else lives in the data JSONB column, varying freely per tenant:

ATLOMY — a TERM (anatomical lemma):

{
  "short_description": "The abdomen or belly cavity",
  "long_description": "<p>Detailed anatomical description with references...</p>",
  "ancient_words": [
    {"word": "κοιλία", "language": "Greek"},
    {"word": "venter", "language": "Latin"}
  ],
  "body_region": "thorax",
  "transliteration": "koilia"
}

VISIONIS — a TERM (Arabic lexical root for seeing/perception):

{
  "definition": "To look, observe; intentional observation",
  "root_letters": "n-ẓ-r",
  "transcription": "naẓara",
  "sense_category": "Verb of Seeing"
}

Both share canonical_form (relational floor — the one field every term must have). Everything else is tenant-specific JSONB: ATLOMY has two description fields, ancient word arrays, and body region; VISIONIS has a single definition, root letters, and sense category. No migrations needed when either tenant adds fields. The field_mappings in TenantOntology (ADR-004) describe which JSONB keys are user-visible and how they're labeled.

Important Terminology​

When we say "AI can propose schema changes," we mean:

Epistemic Structure (what AI modifies):

  • Adding a field to a tenant's view of a table (in data JSONB column)
  • Proposing a relationship between epistemic entities
  • Suggesting an archetype classification
  • Recommending a data type for tenant flexibility

NOT Physical Schema (what AI never touches):

  • SQL ALTER TABLE statements
  • Database migrations
  • Index creation/deletion
  • Constraint modifications (foreign keys, checks, etc.)

The System Does Physical Schema Changes:

  • After human approval (APPROVED → APPLYING transition)
  • Via Django migrations (versioned, auditable, reversible)
  • With rollback capability
  • Logged in audit trail

This distinction is critical for governance: AI proposes epistemic structures, humans approve canonical schema changes.

Consequences​

Positive​

  • ✅ Governance preserved: Can query "show all APPROVED entities"
  • ✅ Flexibility gained: Tenants add fields without migrations
  • ✅ Explainability maintained: Relational status/confidence tell you what's governed
  • ✅ AI-friendly: Can propose data structures without ALTER TABLE
  • ✅ Searchable: GIN index on JSONB enables flexible queries
  • ✅ Type safety where it matters: Status, archetype are enums (validated)

Negative​

  • ⚠️ Partial type safety loss: JSON fields not validated by database
  • ⚠️ Query complexity: JSON queries harder than relational
  • ⚠️ Performance: GIN indexes larger than B-tree

Mitigations​

  • Application-level validation for JSON schemas (Zod, Pydantic)
  • PostgreSQL CHECK constraints for critical JSON fields
  • Elasticsearch for complex JSON queries (optional acceleration)

Multilingual Search Consideration​

The generated search_vector uses the simple text search configuration (language-agnostic tokenization) rather than english, because tenants work in different languages:

  • ATLOMY: Greek, Latin, English
  • VISIONIS: Arabic, English (+ French, German for secondary scholarship)

A single to_tsvector('english', ...) would stem Arabic and Greek incorrectly. The simple config provides baseline tokenization. Tenant-specific search optimization (Arabic root-based search, Greek morphological search) should be handled at the application layer or via per-tenant search configuration, not in the generated column. Elasticsearch remains the intended path for advanced multilingual search.

Alternatives Considered​

  1. Full Relational (EAV pattern): Rejected. Too many joins, poor performance.
  2. Full JSON (document DB): Rejected. Loses governance, breaks AI explainability.
  3. Separate Tables Per Tenant: Rejected. Creates migration hell, prevents cross-tenant queries.

Implementation​

Phase 1 (Sprint 11-12)​

  • Define epistemic_status enum
  • Create hybrid schema for SchemaSuggestion
  • Add provenance JSON fields

Phase 2 (Sprint 13-14)​

  • Migrate existing entities to hybrid schema
  • Build JSON schema validation layer
  • Add GIN indexes for performance

Compliance​

This decision supports:

  • AI Governance: Status/confidence are relational (auditable)
  • Epistemic Rigor: Structure preserved, expression flexible
  • Multi-Ontology: Tenants express differently, structure remains

Anti-Patterns to Avoid​

❌ Don't: Put governance fields in JSON
✅ Do: Keep status, confidence, approver relational

❌ Don't: Use JSON as "lazy schema design"
✅ Do: Use JSON only for genuinely fluid data

❌ Don't: Query JSON without indexes
✅ Do: Add GIN indexes for frequently queried JSON paths
