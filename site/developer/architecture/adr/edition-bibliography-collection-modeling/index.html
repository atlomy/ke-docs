ADR 058: Edition-Bibliography Collection Modeling — Two canonical_type Collections vs One DOCUMENT Collection with frbr_level

  • Status: Accepted (2026-06-09, ratified under explicit owner delegation — "I give consent for you to decide"; rulings below)
  • Date: 2026-06-09
  • Deciders: owner (pending); drafted by Claude session 2026-06-09
  • Context source: 2026-06-09 escorted-retest deferral handoff (edition-bibliography modeling, point 2b); 2026-06-09 adversarial review (3 independent critics); docs/research/standards/CROSSWALK.md WORK-vs-EDITION verdict
  • Related: ADR-015 (canonical_type discriminator), ADR-017 (Row-ID identity), ADR-029 (published Entry layer), ADR-030 (CIDOC/Linked Art export profile — Proposed stub), Spec 0008 (Citation Framework CSL), PR #511, PR #512, in-flight corrections branch fix/post-521-collection-corrections

Context​

Classics-domain pilots carry edition bibliographies in two strata — early editions and modern editions of the same ancient works. These bibliographies power reference-presentation logic (sigla, bracket conventions, "= editor" equivalences such as "p. 83 Balme", passage refs such as "Joannou 3,15") and must comply with the academic-standards layer the platform has been building. The owner's 2026-06-09 trigger: "collapsing into pickers is a way but we need valid ways to create presentation / bibliography / data aggregation correctly while complying with standards." This is the layer ABOVE the #512 materializer fix — a modeling/config decision, not a re-materialization.

What the standards layer already says​

docs/research/standards/CROSSWALK.md (L61, L74) evaluated WORK-vs-EDITION (FRBR WEMI) as a new-archetype candidate. Verdict: Clause 1 passes (FRBR, BIBFRAME, CIDOC-CRM-LRMoo; metadata + lod families) — but the consensus of the surveyed standards is "DOCUMENT-with-frbr_level floor-field, NOT archetype split": the DOCUMENT contract carries frbr_level in a required floor field or conventional JSONB, with a derives_from self-edge (a literal in docs/research/standards/metadata/cidoc-crm.md, per ADR-004) relating edition strata to the work. spa/src/lib/slot-taxonomy/types.ts:137 already declares a multikey_kind="edition" modifier.

What the citation layer already builds (verified against source 2026-06-09)​

  • CSL projection + render (Spec 0008 / ADR-020 amendment): epistemic/services/csl_projector.py (DOCUMENT/PASSAGE → CSL JSON; schema-validated against vendored epistemic/static/csl_schema/csl-data.json), epistemic/services/citation_renderer.py (citeproc-py → RenderedCitation with provenance), epistemic/services/citation_validation.py (ValidationReport + risk class), TenantCSLStyle (epistemic/models.py:1461), 77 vendored standard styles + tenant styles (classics_v1.csl, media_v1.csl).
  • Display-time citation synthesis (NOT stored strings): spa/src/apps/anchor_explorer/components/SlotField.tsx — formatCitation() (L358), LiteratureList() (L380), AttestationList() (L318) build classical citations from structured PASSAGE fields: reference_abbreviated, chapter/section/page/line_number, editor_abbreviated, jones_chapter_number, early_page. The early-vs- modern reference fields are READ separately at display time — which is why un-collapsing the edition fields (#512's fix) is a prerequisite for correct early-vs-modern rendering regardless of which option below is chosen.
  • Collection identity is the triple (archetype, canonical_type, provenance.table) (ADR-015 discriminator + PR #511 source_table label + PR #512 default).

The empirical question (handoff Q1): what does the current pipeline do by default?​

Answer: the import-wizard path arrives with an EMPTY canonical_type and lands in Option A (two provenance-keyed collections) by #512 default. Evidence chain, all verified at the listed lines on this branch:

  1. The wizard's Coda parser emits archetype candidates via the shared shape scorer: epistemic/services/parser/coda_parser.py:116 → _archetype_from_shape (epistemic/services/parser/xlsx_parser.py:208).
  2. An edition-bibliography table (title + editor/translator/publisher/year signature) matches the DOCUMENT shape branch, which hardcodes canonical_type="" (epistemic/services/parser/xlsx_parser.py:241-251, confidence 0.8). No parser branch ever declares a DOCUMENT subtype.
  3. The heuristic-enrichment lane CAN derive a name-based subtype ("Modern Editions Bibliography" → "Modern Editions") via _derive_canonical_type (epistemic/services/proposals/heuristic_enrichment.py:157, data_import/services/_tenant_discovery_common.py:195) — but it only fires when the table has no meaningful non-heuristic candidate (heuristic_enrichment.py:85-91 guard). Edition tables DO have one (step 2), so the name-derived subtype is never appended on the wizard path.
  4. The proposal builder persists the preferred candidate verbatim (epistemic/services/proposals/builder.py:142-153 parser payload; epistemic/services/materialization/slot_shaping.py:35-39 payload selector), so the ARCHETYPE proposal's canonical_type stays "".
  5. Materialization reads it back (epistemic/services/materialization/field_plan.py:234) and applies the #512 default: canonical_type = table_info.get("canonical_type") or table_name (epistemic/services/materialization/service.py:687) — i.e. the raw source-table name (e.g. "Early Editions Bibliography" / "Modern Editions Bibliography") becomes the collection discriminator.
  6. The CLI config path is different: the anchor tenant's Coda import config DECLARES distinct subtypes — "canonical_type": "Modern Edition" (atlomyapp/import_configs/atlomy_atlas_coda.json:70) and "canonical_type": "Early Edition" (...:78). That path also lands Option A, but with curated labels rather than raw table names. These entries do NOT flow through the wizard.

So both current ingestion paths produce Option A; the wizard variant additionally exposes raw table-name canonical_types. Option B exists nowhere by default — it requires either a declared shared canonical_type + stratum field, or an Entry-Surface read-time aggregation.

What the 2026-06-09 adversarial review showed​

Three independent critics reviewed the collection triple against the FRBR verdict. Findings (cite as "2026-06-09 adversarial review"):

  1. The triple makes the FRBR-WRONG shape frictionless and the FRBR-CORRECT shape lossy. Two provenance-keyed pseudo-collections (Option A) work out of the box. The CROSSWALK-correct shape — one DOCUMENT bibliography + per-stratum filtered tabs — loses authoring: any workspace table with a truthy extra_filter is barred from record creation (atlomyapp/graphql/schema.py:659) and from draft relationship mutations (atlomyapp/graphql/schema.py:730). A parallel corrections PR (branch fix/post-521-collection-corrections, in flight 2026-06-09) narrows that guard and stamps membership at create — this ADR depends on that work landing; it does not solve it.
  2. "One bibliography, two edition strata" has NO aggregation home. The CSL layer projects per-entity — project_to_csl maps "an attestation-style structural projection to ONE CSL JSON item" (epistemic/services/csl_projector.py:36-43) and the module is collection-blind (no canonical_type or collection reference anywhere in it). The collection triple can only say "two unrelated tabs"; nothing can currently state "these two collections are strata of one bibliography."
  3. DECLARED vs TABLE-DEFAULTED canonical_type is unrecorded. PR #512 defaults entity canonical_type to the raw source-table name, and nothing records which stored values were declared by a human/config vs defaulted from the table — so a later scholarly re-typing pass cannot tell them apart. The corrections PR adds provenance.canonical_type_source="table_default" going forward (not retroactively).
  4. Raw table-name canonical_types leak to PUBLIC surfaces — an ADR-029 strain: the anchor-projection noun fallback (atlomyapp/services/anchor_projection.py:127), the Entry-Surface facet noun (atlomyapp/services/entry_surface.py:1213), publication payloads, and per-archetype view names (epistemic/services/per_archetype_views.py:72). The corrections PR addresses this at the display boundary.
  5. Collection identity keyed on source-table NAME is rename-fragile. Row-level identity already uses stable source IDs (ADR-017 Row ID / provenance.coda_intrinsic_id); collection-level identity does not. The asymmetry argues for stable source-table IDs in provenance later.

Decision​

The reconciliation candidate is ratified (2026-06-09, owner-delegated). In substance: collection identity and citation unity are separated concerns.

  • Workspace default = Option A. One workspace collection per source collection stays the platform-canonical default. It matches how research teams already organize their material (their own source tables), it is what BOTH import paths produce today, and the empirical Q1 chain shows it is the de-facto state. No migration.
  • Option B stays tenant-reachable, not platform-imposed. A tenant that wants one merged bibliography declares a shared subtype on the source tables — already supported with zero code (PR #512 preserves declared values) — and uses per-stratum filtered tabs (authorable once the fix/post-521-collection-corrections guard fix lands).
  • Bibliography unity moves to the citation layer where it belongs: the scholarly requirement was never "one tab", it was "one correctly aggregated bibliography with edition strata" — a rendering/aggregation concern, not a storage-identity concern.

Rulings on the six requested items:

  1. Reconciliation ratified (above). A = collection default; B = per-tenant declaration; unity = citation layer.
  2. frbr_level is NOT a required DOCUMENT floor field. When a tenant adopts the merged shape, the edition stratum is a conventional data field plus the derives_from edge vocabulary, shipping independently of ADR-030 (which gates only the public CIDOC conformance claim, not internal vocabulary).
  3. Divergent-collection label home = the seeded collection-registry row (PR #521): its label is admin-editable and — once the corrections branch lands — durable across re-imports. Resolved; no new mechanism.
  4. Collection-level citation aggregation enters Spec 0008 Phase 2 scope: the CSL projection gains a collection-grouping input so "one bibliography, two edition strata" renders as ONE aggregated bibliography across two collections. (Scope commitment; implementation with Phase 2.)
  5. Stable source-table IDs: adopted. Provenance carries the source system's stable table ID alongside the display name (the collection-level analog of ADR-017's Row-ID discipline); collection seeding keys on the ID when present, making collection identity survive source-table renames. Implementation queued (sequenced after the corrections branch — same files).
  6. Re-typing policy: TABLE-DEFAULTED canonical_types are freely re-typeable by tenant admins as non-breaking curation. No bulk migration; the canonical_type_source marker distinguishes defaulted from declared.

Originally filed as Proposed; do not re-litigate the A-vs-B framing without the rulings listed under "Decision requested."

Alternatives considered​

Option A — two canonical_type collections (the current default)​

"Early Editions" and "Modern Editions" are distinct DOCUMENT collections (distinct canonical_types). Cross-edition relationship is implicit, via the PASSAGE early/modern reference fields that point at each.

  • For: already live on both ingestion paths; zero migration; workspace tabs, authoring, and per-collection form configs all work today; matches how the pilot's researchers see their data (two source tables, two tabs); the divergent-collection label has a natural home (source_table, per PR #511).
  • Against: contradicts the CROSSWALK verdict (edition strata are FRBR Work/Expression levels of ONE bibliography, not unrelated sets); "same work, two editions" is representable only implicitly through PASSAGE fields — no derives_from edge, no queryable work identity; standards exports (future ADR-030 profile) would have to reconstruct the FRBR structure from heuristics; wizard-path collections carry raw table-name identity (rename-fragile, leak-prone — adversarial findings 4–5).
  • Chosen? Left open.

Option B — one DOCUMENT collection + frbr_level + derives_from (the CROSSWALK verdict)​

One bibliography collection; editions distinguished by an frbr_level (or edition-variant) field; derives_from self-edges relate expression→work / edition→edition.

  • For: standards-correct per CROSSWALK L61/L74 (FRBR, BIBFRAME, LRMoo consensus); gives "one bibliography, two strata" a real data home; derives_from is already an ADR-004 relationship literal; reachable WITHOUT re-materialization (a declared shared canonical_type defeats the #512 default with zero code change).
  • Against: per-stratum tabs become extra_filter views, which TODAY are barred from record creation and draft relationships (atlomyapp/graphql/schema.py:659, :730) — authoring loss until the corrections PR lands and is verified; the CSL layer has no collection-level aggregation contract either way (adversarial finding 2 — Option B alone does not produce a combined bibliography rendering); the divergent-collection label for the 0-config wizard path loses its source_table home (handoff Q3); open standards-gating question whether frbr_level + derives_from counts as CIDOC-mirroring (gated by ADR-030, still a Proposed stub whose Current Guidance forbids changing internal authoring models to mirror CIDOC classes) or as an ADR-004 vocabulary variant that ships independently (handoff Q2). Reading: FRBR/LRMoo is not CIDOC; CROSSWALK frames frbr_level as floor-field guidance independent of any export profile — but the owner should rule, since LRMoo is CIDOC-family.
  • Chosen? Left open.

Reconciliation candidate — A for tabs + a collection-level aggregation contract for citations​

Keep Option A's two collections as the authoring/tab surface (they are the operational truth of how the source arrives), and add a collection-level aggregation contract above them for the citation/standards layer: a declared grouping ("these N collections are strata of one bibliography", carrying per-stratum frbr_level and the derives_from intent) that Entry-Surface read-time aggregation and a future collection-aware CSL path can consume, and that an ADR-030 export profile can later map to Work/Expression without reshaping authoring.

  • For: preserves working authoring + researcher mental model; honors ADR-030's "export adapts the published layer; it is not the operational truth" guidance; fixes adversarial finding 2 (gives aggregation a home) without the Option-B authoring regression; incremental — the grouping declaration can ship before any per-entity frbr_level backfill.
  • Against: a new contract surface to design, version, and validate (tenant config? TenantOntology? a collection-group table?); risks duplicating what frbr_level-on-entities would express more simply; defers rather than resolves the FRBR-correctness question for the entity data itself; Spec 0008 Phase 2 scope grows.
  • Chosen? Left open — flagged as the drafting session's candidate, not a recommendation with authority.

Trade-offs common to all options​

  • PASSAGE early/modern reference fields: formatCitation() reads reference_abbreviated/editor_abbreviated (modern) and jones_chapter_number/early_page (early) as separate structured fields (SlotField.tsx:358-378). This display-time synthesis works under A, B, or the reconciliation — but under B the per-stratum distinction in pickers and tabs must come from frbr_level filtering rather than collection membership, and under A the "same work" identity that early/modern refs jointly imply has no queryable home.
  • Gates: ADR-030 must be promoted from stub (with its SHACL/fixture validation strategy) before any choice here is sold as standards conformance; Spec 0008 Phase 2 (researcher UX, ENTITY/EVENT/ClaimCluster CSL) is where a collection-aware citation contract would land — backend endpoints exist, frontend surfaces do not (see tasks.md reconciliation 2026-06-09).
  • Migration cost: A→B later = declare shared canonical_type for new imports + a re-type pass over existing entities (needs finding 3's canonical_type_source provenance to distinguish defaulted rows) + tab re-derivation as filtered views. B→A later = split by frbr_level back into collections (cheap if frbr_level was populated; impossible to do faithfully if it was not). Reconciliation→either = drop or promote the grouping contract. None require re-materialization today — both A and B remain reachable from current data.

Decision requested (owner must rule on each)​

  1. A vs B vs reconciliation candidate as the platform-canonical modeling for edition bibliographies (platform-general; the anchor tenant is the motivating case, not the scope).
  2. If B or reconciliation: where frbr_level lives — required DOCUMENT floor field vs conventional JSONB — and whether frbr_level + derives_from is gated by ADR-030 ratification or ships independently as ADR-004 vocabulary (handoff Q2).
  3. Divergent-collection label home for the 0-config wizard path if collections merge (today PR #511's source_table supplies it; handoff Q3).
  4. Whether a collection-level citation-aggregation contract enters Spec 0008 Phase 2 scope (adversarial finding 2).
  5. Whether collection identity moves to stable source-table IDs in provenance, matching ADR-017's row-level discipline (adversarial finding 5).
  6. Re-typing policy for existing TABLE-DEFAULTED canonical_types once provenance.canonical_type_source lands (adversarial finding 3): bulk curate, leave as-is until Option ruling, or fold into the chosen option's migration.

Consequences​

Positive​

  • The A-vs-B fork is now recorded with file:line evidence instead of living in a gitignored handoff; the default the pipeline silently picks (Option A with raw table names on the wizard path) is named and owner-visible.

Negative​

  • Until ratified, new wizard imports keep minting table-name-keyed pseudo-collections, deepening the eventual re-type pass (mitigated going forward by the corrections PR's canonical_type_source stamp).

Neutral​

  • No code change ships with this ADR. Both options stay reachable; the corrections PR proceeds independently at the display/authoring boundary.

Implementation notes​

First step after ratification: if A — document the curated-canonical_type convention for CLI configs and the wizard's review-step subtype field; if B — land the corrections-PR guard relaxation first, then declare the shared canonical_type + frbr_level slot in tenant config and verify authoring on filtered tabs; if reconciliation — spec the grouping contract inside Spec 0008 Phase 2 before touching entity data. In all cases, do NOT re-materialize to force a choice.
