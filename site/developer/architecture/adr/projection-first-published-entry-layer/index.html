ADR-029: Projection-First Published Entry Layer

Date: 2026-05-11 Status: Proposed Deciders: Atlomy Account, assistant Context source: Spec 0009 V2 KE Entry Surface recalibration; minimal-computing review; CQRS / islands / institutional-integration discussion; Spec 0009 deep-review absorption rounds 1-5 Related: ADR-001, ADR-002, ADR-003, ADR-005, ADR-017, ADR-019, ADR-020, ADR-022, ADR-023, ADR-024, ADR-026, ADR-031, Spec 0009, docs/architecture/federated_discovery_spec.md

Context​

KE has two different runtime needs that should not be collapsed:

  • the live authoring/governance environment where researchers add, delete, revise, review, and publish tenant data and media;
  • the public scholarly environment where entries need stable URLs, citation continuity, low hosting cost, archiveability, search discoverability, and institutional integration.

The current V2 migration discussion began around replacing the V1 public reader/SPA. The phrase "public reader" is now too small: the public surface is a Knowledge Environment that may grow profiles, teaching collections, research tools, personalization, 3D/media interaction, and federation. At the same time, minimal-computing sources argue against making dynamic infrastructure the only durable form of public scholarship.

The platform already has the right authoring substrate: Django, django-tenants, tenant schemas, EpistemicEntity, slot config, media artifact/version models, GraphQL, and indexer adapters. The missing decision is where the public and institutional contract lives.

Decision​

KE SHALL publish public Entry surfaces through versioned EntryProjection read models and published/export snapshots. Django + django-tenants remain the live authoring/governance substrate. Public Entry pages, search cards, federation resources, citation/export payloads, media manifests, and institutional integrations consume the published Entry layer, not internal tenant schemas or V1 search documents.

Implications​

Authoring vs publishing​

  • Authoring writes remain in live tenant schemas.
  • Public reads consume rebuilt projections, indexes, and export snapshots.
  • Search engines return IDs/evidence; detail/card rendering hydrates from projection/canonical data, not from search-engine document JSON.
  • Public traffic should not require every anonymous request to walk live tenant schemas when an exported or cached projection can answer it.

Projection and invalidation​

The first implementation uses a publication invalidation ledger, not full event sourcing and not an edit-invalidation system for every research-workspace save.

Normal research edits remain mutable draft/authoring activity inside the tenant workspace. Projection work is triggered only by publication intent or by a public-visible change to an already-published Entry:

  • a researcher publishes one Entry or a batch of Entries;
  • a public-visible field changes on an already-published Entry;
  • a public media item is added, removed, replaced, or re-captioned;
  • a public slot/config/mapping change affects the published surface;
  • a public relationship change affects visible related material;
  • a tenant changes the public Entry Surface template.

Private notes, unpublished draft edits, admin-only metadata, internal review comments, import staging rows, personal teaching overlays, private annotations, and failed/experimental enrichments do not dirty the public projection.

Each projection rebuild records enough input evidence to reproduce and debug the read model:

  • source entity record_version / record_content_hash (ADR-031)
  • relationship record_version / record_content_hash (ADR-031)
  • slot/config version
  • media artifact/version references
  • citation and attestation inputs
  • route aliases and legacy provenance
  • output projection version/hash

Publishing a new Entry uses a synchronous first-publish path: the publish action does not report success until the route resolves to a complete projection or a clear failure has been returned. A failed publish does not replace the last good public projection. Spec 0009 Task -1 must choose and record a concrete latency budget for this path. If a complete projection cannot be built inside that budget, the acceptable fallback is a minimal citable "publishing" projection that resolves the route and is atomically replaced by the full projection when ready; a successful publish must never create a transient public 404.

Async rebuilds are a phase-2 optimization for batch publishes, global public config changes, media batches, full-tenant rebuilds, and replay/repair jobs. When async work exists, the canonical state is a Postgres-backed PublicationWorkItem ledger claimed with SELECT ... FOR UPDATE SKIP LOCKED. Celery or Django Tasks may enqueue or wake workers, but Redis/Celery metadata is not the source of truth for publication state.

No async publication behavior is considered implemented until a runnable worker baseline exists. That baseline can be a Django management command, a Django Tasks backend, Celery, or another executor, but CI/local development must prove that a PublicationWorkItem can be inserted, claimed, executed, marked complete/failed, and left visible for operator audit. A dormant ledger table is not a publication system.

Recommended work-item fields: tenant identifier, work kind, Entry ref, status, priority, run_after, attempt count, locked_by, locked_at, projection_input_hash, projection_output_hash, last_error, and coalesce_key.

Projection version semantics:

  • projection_input_hash hashes the public-visible inputs used for a rebuild.
  • projection_output_hash hashes the serialized public projection output.
  • projection_version is monotonic per Entry and bumps only when the input hash change produces a new public projection.
  • no-op rebuilds do not bump projection_version.
  • overlays store the projection version/hash they target so drift can be detected after later publishes.

Projection hashes are not the optimistic-concurrency mechanism for source models. ADR-031 owns source-row record_version and record_content_hash semantics for stale baseVersion rejection. ADR-029 consumes those values as projection dependency evidence.

Projection dependency coverage is part of the contract, not an implementation detail. Spec 0009 must define the initial allowlist of publication-dependency emitters and keep it auditable: entity publishes, public-visible entity fields, public relationships, media artifacts/versions, citation/attestation inputs, public slot/config/template changes, route aliases, and legacy redirect provenance. New writers that can affect the public surface must either register a dependency emitter or explicitly mark themselves as non-public. A periodic audit should detect already-published Entries whose current input hash differs from the last recorded projection input hash but no rebuild work exists.

The ledger is intentionally narrower than full event sourcing. If replay/audit needs grow beyond projection invalidation, the next step is a Tier 1.5 append-only source-change log: source model, object ref, version/hash, public-visibility classification, actor, timestamp, and optional projection work-item reference. That log is a later ratchet, not a Task 0 prerequisite.

Published Entry state includes tombstones. Unpublishing or deleting a public Entry does not silently erase citation history: it creates an unpublished / tombstoned projection state, preserves route/legacy provenance, removes the Entry from public search and indexes, and returns a clear gone/unpublished response or redirect according to the tenant's publication policy. Tombstone responses must not leak private/draft content; legacy aliases should resolve to the same tombstone rather than a generic 404.

Rich text that appears in public Entry cards, detail pages, exports, and GraphQL payloads is sanitized server-side in EntryProjectionService before it enters the published projection. Clients may still apply defense-in-depth sanitization, but they do not receive unsanitized public rich-text fields as the contract.

Runtime baseline​

Spec 0009 starts with a runtime modernization mini-sprint before projection contracts are frozen: Python 3.12 + Django 6.0. This lets V2 Entry Surface tests and models land on the runtime the platform intends to ship.

Django 6.0 is intentionally chosen over Django 5.2 LTS for this work because its Tasks framework, Model.NotUpdated, built-in CSP middleware, template partials, AsyncPaginator, and cross-backend ORM improvements are relevant to the publication-ledger and public-surface architecture. The Tasks framework is not a worker engine; it is a standard API that can sit on top of the Postgres-backed PublicationWorkItem ledger. Python 3.12 is the target runtime; Python 3.13/3.14 are deferred until their extra audit surface is justified.

The non-LTS choice is explicit: schedule a Django 6.2 LTS follow-up in 2027. Task -2 must verify dependency compatibility (django-tenants, Strawberry, Unfold, pandas, retired data-wizard, ES bridge packages), migrations, admin, GraphQL, import, and the transition reader before Task -1 or Task 0 begin.

Public delivery​

React remains appropriate for interactive KE modules, but a pure SPA is not the final foundation for public scholarship. Public Entry surfaces must be HTML/export-capable even if the migration path first runs through the existing React client and GraphQL.

Acceptable future delivery targets include:

  • Django-rendered/exported HTML with React islands/modules;
  • static HTML/JSON generated from EntryProjection;
  • Astro-style islands over Entry snapshots;
  • Next.js ISR over Entry APIs/exports if a separate Node delivery layer becomes worth its operational cost.

The platform does not commit to Astro or Next.js in this ADR.

Framework migration is evidence-triggered. Revisit public delivery only when measured needs exceed the React/GraphQL migration path: first-load p95 or detail hydration p95 misses agreed targets, public SEO/archiveability needs cannot be met with exported snapshots and metadata, JavaScript payload or low-connectivity access becomes a partner blocker, institutional export consumers require HTML/static packaging beyond the current pipeline, or a paying/funding partner explicitly requires SSR/ISR/static delivery.

Those triggers must become numeric gates before the public delivery layer expands: at minimum, record first-load/detail p95 targets, maximum public JS payload budget, crawler/archive smoke criteria, and low-connectivity acceptance criteria. "Evaluate later" is acceptable only with tripwires that prevent SPA inertia from becoming the default architecture by accumulation.

Personalization and teaching overlays​

Profiles, saved entries, teaching collections, private notes, and annotations are overlays. They reference stable Entry/entity IDs plus projection version/hash. They do not become canonical public Entry fields.

Textual anchors must expect drift. Store more than one anchoring signal where possible:

  • Entry/entity ID;
  • projection version/hash;
  • section or slot key;
  • quote/context selector;
  • position selector where useful;
  • re-anchor status such as anchored, anchored_with_drift, needs_review, or orphaned.

Publication visibility vs scholarly authority​

The sibling atlomy_chat lexical-value workflow separated is_public from is_canonical: making a lexical value visible to the community did not make it the authoritative scholarly version. KE should preserve the same distinction in tenant-neutral vocabulary. In ADR-029 terms, a published Entry is publicly visible and citable according to its publication policy; that does not by itself mean the Entry is verified, canonical, preferred, peer-reviewed, or the tenant's authority record. Authority/canonical/preferred status remains an explicit governance field or release policy, separate from publish/unpublish.

Review/proposal actions that modify a public Entry should target the source record_version from ADR-031 and, when relevant, the projection version/hash from this ADR. A proposal prepared against an older source/projection version must either rebase or return a reviewable conflict; it must not silently merge into a changed public Entry.

Institutional integrations​

Libraries, archives, aggregators, and future federation consume the published layer:

  • stable Entry URLs and route maps;
  • versioned JSON exports;
  • JSON-LD export views where needed;
  • citation/CSL metadata;
  • media manifest references, including IIIF where relevant;
  • CIDOC CRM or other standards-shaped exports as views over projection data.

Standards outputs are export views, not the internal authoring model.

Machine-readable outputs need a minimum profile floor before institutional claims ship:

  • versioned profile and JSON-LD context URLs;
  • conformsTo declarations on export payloads;
  • small fixtures for each supported profile;
  • shape checks with JSON Schema, SHACL, ShEx, or another profile-appropriate validator;
  • explicit coverage labels for each Entry type: full, partial, or unavailable.

The first floor is JSON/JSON-LD Entry export, route maps, citation metadata / CSL where covered, IIIF manifest references for media-bearing Entries, and WADM-compatible annotation targets. Textual-corpus tenants should reserve CTS URN and TEI P5 export hooks even if the first implementation only ships shape fixtures. CIDOC CRM / Linked Art / SPARQL needs a separate profile decision before federation or library-facing claims depend on it.

Tenancy​

This ADR does not move KE away from django-tenants. Schema-per-tenant remains the operational isolation strategy for live authoring. ADR-026 still owns the long-term thousand-tenant strategy, but its evaluation must account for this ADR: reducing public-read pressure through projections/exports may delay or change the business case for a tenancy migration.

Projection service interfaces should accept an opaque tenant identifier/context, not raw schema names as the public service contract. Implementations may resolve that context to schema_context(...) today, but the interface stays tenancy-strategy-agnostic for ADR-026.

Alternatives considered​

AlternativeWhy not chosen
Pure React SPA for the public KEStrong interactivity, but weaker baseline for SEO, archiving, low-JS access, static preservation, and institutional harvesting.
Traditional dynamic Django pages onlySimple stack, but every public request pays live database/schema-switching cost and the public artifact remains tied to live infrastructure.
Full static site onlyExcellent durability and cost profile, but does not fit weekly researcher/media changes, personalization, teaching tools, or dynamic search/research workflows.
Full event sourcing nowStrong replay/audit story, but too much ceremony for Spec 0009. A projection dependency ledger gives the needed invalidation and reproducibility first.
Tier 1.5 append-only source-change log nowUseful audit/replay ratchet, but still more ceremony than the publication-only MVP. Kept as a next step if dirty-audit gaps appear.
Edit-invalidation for every research saveStrong freshness, but overbuilds the problem. Public projections only need publication intent and public-visible changes.
Celery as the publication source of truthMature executor, but Redis/Celery result metadata cannot express KE publication state, last-good preservation, coalescing, and operator audit as reliably as Postgres domain rows.
Django 5.2 LTS as the V2 baselineSafer support window, but gives up Django 6 Tasks, Model.NotUpdated, built-in CSP, template partials, and other features that align with Spec 0009. Kept as the fallback if Task -2 compatibility fails.
Direct institutional access to tenant schemasExposes unstable authoring internals, weakens tenant isolation, and makes backend refactors externally breaking.
Migrate away from django-tenants nowHigh rewrite/leakage risk. The current isolation substrate is load-bearing and appropriate for authoring.
Datasette/SQLite/DuckDB published packagesStrong minimal-computing and local-research story. Defer until the EntryProjection/export profile is stable enough to package.
RO-Crate/Frictionless packages per Entry or releaseGood preservation/packaging complement. Defer to the standards/export sprint after PID/profile floors are ratified.
LakeFS/Dolt-style versioned data storeStrong diff/version story, but too much infrastructure for a local-first V2 migration.
Native SPARQL endpoint as the primary public APIValuable for linked-data partners, but should be generated from published profiles rather than replacing GraphQL/projection as the application contract.

Consequences​

Positive​

  • Public scholarship can become durable, cacheable, exportable, and cheaper to host without abandoning live research workflows.
  • V2 Entry Surface, federation, citations, media, and library integrations share one projection source.
  • Legacy V1 URLs can remain route aliases/provenance while new public identity stays non-semantic and stable.
  • Future delivery-framework choices remain open because the projection contract is serializable.

Negative​

  • Publication invalidation becomes a first-class engineering problem.
  • Public data is immediately consistent with successful first publishes but may be eventually consistent after batch/global published-surface changes.
  • Overlay drift needs explicit UX and review workflows.
  • Export standards work still requires careful mapping; this ADR only fixes the boundary, not every mapping.
  • Django 6.0 is not an LTS release; KE must plan the Django 6.2 LTS follow-up.
  • Publication dependency coverage can rot if new public-visible writers do not register emitters. CI and dirty-audit checks are required to keep the ledger honest.

Neutral​

  • GraphQL remains the application contract for live reads, but it is no longer the only possible public publication format.
  • django-tenants remains central to authoring while becoming less central to anonymous public delivery.

Implementation notes​

  • Spec 0009 owns Task -2 (Python 3.12 + Django 6.0), Task -1 (publication readiness contracts), the first EntryProjection, EntryPublishService, PublicationWorkItem/Django-Tasks backend decision, and overlay-anchor contracts.
  • ADR-023 should define persistent identifiers, publication packages, route maps, and archival exports over the published Entry layer before public PID claims ship.
  • ADR-024 should define the minimum WADM-compatible projection-versioned anchor contract before user overlays/annotations ship.
  • ADR-030 should choose the CIDOC CRM / Linked Art / SPARQL export profile before federation or institutional consumers rely on that standards family.
  • ADR-031 should define source-model version/hash fields before Task 0 writes stale-baseVersion red tests or Task 4.5 records source dependency hashes.
  • Federation should harvest published resources from the Entry/export layer, not tenant schemas.
  • Tests must prove that V1 REST/ES payloads are transition-oracle inputs only, not the runtime public contract.
  • Entry Surface role selection must move away from the single TenantOntology.is_anchor boolean. Multi-anchor public surfaces need a per-role TenantEntrySurfaceConfig contract.
  • Snapshot retention should keep at least the latest good projection, named releases, and a rolling recent history such as 90 days, with tenant quotas and an explicit rollback path.
