ADR 052: Per-Tenant User Identity is Load-Bearing; Global Identity Only as an SSO Add-On

  • Status: Accepted (2026-05-31)
  • Date: 2026-05-31
  • Deciders: Platform owner/architect + Claude (design + 3 Codex rounds + NotebookLM R1 + 4-lens compliance/federation review)
  • Context source: tenant↔platform isolation security program (docs/superpowers/specs/2026-05-31-tenant-platform-isolation-security-program.md); related ADR-051, ADR-035, ADR-016 (telemetry/GDPR), ADR-029/ADR-038 (federation/published projections), ADR-001 (epistemic/operational separation), ADR-042 (search_path is the isolation primitive).

Context​

django.contrib.auth is in BOTH SHARED_APPS and TENANT_APPS, so each tenant (KE) schema has its own auth_user table — per-tenant user identity. Investigation (2025-12-29 RBAC devlog) found this was emergent, not designed: it arose from a tactical foreign-key-integrity need (tenant-schema FKs such as ClaimCluster.author must resolve against the tenant's auth_user) and was then rationalised as "excellent for strict isolation." No prior ADR examined it as a deliberate decision.

During the isolation program an identity fork opened (ADR-051): keep per-tenant identity (Approach A) vs adopt the maintained django-tenant-users library (one global user in public + per-tenant UserTenantPermissions). Engineering-only reviews (Codex, a NotebookLM critique) leaned toward the global library on maintenance grounds and framed a migration spike as the tie-breaker. A four-lens review (GDPR/privacy, standards, zero-trust, federation) reframed it as a compliance decision, not an engineering trade-off.

Decision​

Per-tenant user identity is ratified as load-bearing platform architecture. The platform will NOT move to a global/shared user identity. django-tenant-users (or any global-identity model) is rejected as a replacement for the per-tenant model. This elevates the previously-emergent state to a deliberate, documented commitment.

If a future requirement needs a unified cross-KE login experience (e.g. SSO across the KEs of one institution), it is implemented as an add-on: an external Identity Provider (institutional IdP / OIDC / SAML) federating into per-tenant TenantMembership records — never by collapsing accounts into one global user.

Rationale (four lenses)​

  1. GDPR / privacy. Per-tenant identity gives cross-tenant unlinkability: the same human in two KEs holds two unlinked accounts, so the platform operator cannot correlate their activity across KEs. Right-to-erasure has a clean, schema-scoped boundary. A global user reverses both (erasure must span every schema; operator can correlate cross-KE presence) — see ADR-016.
  2. Standards (LOD). Per-tenant identity keeps CIDOC/IIIF/TEI exports tenant-scoped. A global user would create unintended cross-tenant LOD linkage (one shared person entity across KE exports) with attribution/licensing ambiguity.
  3. Zero-trust. Consistent with "tenant context is platform-derived, not client-supplied" and "identity and authority are orthogonal." (The often-cited "global identity forces a client-supplied tenant_id" is weaker — tenant stays host-derived — so this lens is supporting, not decisive.)
  4. Federation (decisive that it does NOT force global identity). Federated discovery operates entirely at the published-data layer (ADR-029/ADR-038): published EntryProjection resources, persistent identifiers (DOI / ORCID / VIAF / Wikidata / ke://entity/...), and service-to-service HMAC webhooks. Internal DB PKs never leave the source tenant. Cross-KE person-linkage is via ORCID (a scholar-controlled persistent ID on published entities), not a platform login — so a person's scholarship federates across KEs while their login activity stays unlinked. Federation needs no shared user identity.

Consequences​

  • ADR-051 Approach A (relocate TenantMembership to a tenant-local app keyed to the tenant-schema user) is the ratified path; the migration spike is now only relevant if a product requirement explicitly asks for federated SSO, and even then as an add-on, not a replacement.
  • Future contributors must not "modernise" to global users / django-tenant-users without superseding this ADR — doing so would silently break cross-tenant unlinkability (GDPR) and create cross-tenant LOD linkage (standards).
  • The institutional-admin / cross-KE-SSO tier (deferred per decision log 2026-05-23) is the home for any future unified-login work, as an external-IdP add-on.
  • ADR-035 capability bundles (incl. external-collaborator for cross-institution contributors) compose unchanged on top of per-tenant identity.
