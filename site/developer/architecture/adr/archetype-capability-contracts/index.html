ADR-006: Archetype Capability Contracts

Date: 2026-04-29 (Rev 2.1) Status: Proposed (Rev 2.1) — supersedes Rev 2 (same file, prior version). Six schema-implementation fixes (F1–F6) applied 2026-04-29 in response to peer review. Decisions below are not final pending architecture-team evaluation. Deciders: Architecture Team Evidence base: docs/research/archetypes/RECOMMENDATION.md (commit 2a4d75b) — standards crosswalk (12 standards, 5 families), per-archetype evaluations, tenant data overlay (ATLOMY + VISIONIS), PROMOTION_RULES.md applied mechanically. Cross-references for Rev 2 / Rev 2.1: docs/research/2026-04-27-prior-art-survey/independent-architecture-review-2026-04-29.md (§4.3, §4.5), docs/research/2026-04-27-prior-art-survey/comments-and-suggestions-2026-04-29.md (ADR-006 evaluation section), peer review feedback (chat, 2026-04-29) addressed in Rev 2.1.

Revision history (decision trail)​

This ADR has had three iterations. All decision sets are documented here so the trail survives.

Rev 1 — 2026-04-29 (reconstructed draft, never committed)​

Lifted from RECOMMENDATION.md. Key positions:

  • 8 archetypes: DOCUMENT, TERM, ENTITY, EVENT, MEDIA, RELATIONSHIP, ANNOTATION, PASSAGE.
  • RELATIONSHIP modeled as one of the 8 archetypes inside epistemic_entities, with from_id / to_id / rule_name as required relational fields on the same JSONB-bearing row.
  • Two parallel discriminators per archetype: relational kind (ENTITY, MEDIA) and JSONB-level type / event_kind (DOCUMENT, EVENT).
  • ~35 hardcoded RELATIONSHIP_RULES in a Python tuple; new rules require ADR amendment.
  • ANNOTATION carried its own polymorphic FK (target_archetype + target_id) and an ANNOTATION_ABOUT_ANY rule with target=*.
  • conventional_jsonb_keys for several archetypes included array-of-refs to other entities (e.g. DOCUMENT.author, MEDIA.partOf, ENTITY.affiliations) and matching RELATIONSHIP rules existed for the same relations.

Rev 2 — 2026-04-29 (structural rewrite)​

Triggered by the principal's three positions of 2026-04-29. Five structural inconsistencies in Rev 1 surfaced:

  1. Same relation expressed two ways — JSONB array-of-refs and RELATIONSHIP rules for identical edges.
  2. Inconsistent discriminator naming — kind (ENTITY, MEDIA, relational), event_kind (EVENT, JSONB), type (DOCUMENT, JSONB), canonical_type (ADR-002, relational, unused).
  3. ANNOTATION duplication — polymorphic FK target and a relationship rule covering the same targeting.
  4. Tenant onboarding requires ADR amendment for every new relationship type.
  5. RELATIONSHIP-as-archetype masks that relationships are inter-row references whose query patterns want indexed FK joins, not GIN containment.

Context​

ADR-001 through ADR-005 all presuppose an archetype layer. ADR-002 freezes the relational archetype and canonical_type columns but defers their valid values. ADR-003's GraphQL schema is archetype-polymorphic. ADR-004's TenantOntology maps tenant-specific labels onto archetypes. ADR-005's frontend renders per-archetype slot sets.

Sprint 13's two-phase research prelude (commit 010500c and following) surveyed 12 data standards across 5 families and mapped every column of both pilot tenants' sample data before applying two mechanical decision rules:

  • INCLUSION rule — must have ≥ 3 supporting standards from ≥ 2 standard families AND ≥ 1 tenant embodying it, OR pass a JSONB-rescue test.
  • FIELD_FLOOR rule — every archetype contract includes the thinnest possible relational floor plus a conventional_jsonb_keys recommendation.

The consultant's 2025-12-29 guidance (6–8 archetypes) and the Sprint 13 brainstorm hypothesis (7 archetypes) are both within the range this evidence base supports.

ADR-004 prerequisite correction (carried from Rev 1)​

ADR-004 §Context refers to "VISIONIS Reader Text" as a DOCUMENT variant. The research data (DATABASE_READER.xlsx MAIN sheet) shows this is incorrect: the MAIN sheet is a TERM table with denormalized attestation context. Correction is a follow-up wording fix; does not affect contracts here.

Decision​

The canonical Atlomy entity-archetype inventory is 7 archetypes plus 1 typed-edge layer:

Entity archetypes (7):     DOCUMENT, TERM, ENTITY, EVENT, MEDIA, ANNOTATION, PASSAGE
Typed-edge layer (1):      entity_relationships  (relational table; not an archetype)

This supersedes Rev 1's 8-archetype inventory by removing RELATIONSHIP from the archetype list and promoting it to its own typed relational table. All 7 entity archetypes are KEPT. AGENT remains dropped. PLACE, TIME_PERIOD, and SAMPLE remain DEFERRED with documented promotion conditions.

Why RELATIONSHIP leaves the archetype list (C1, unchanged in Rev 2.1)​

Relationships are inter-row references. Their semantic content is the connection, not an interpretive body that varies by tenant. They want hard FKs to entity UUIDs, indexed joins, and referential-integrity guarantees the database enforces.

Putting them inside epistemic_entities as JSONB-bearing rows costs:

  • Query plans — JSONB-containment + GIN index over data.from_ref / data.to_ref does not match the planner's preferred shape for "all PASSAGEs attesting this TERM." A typed entity_relationships table with (tenant_id, from_entity, rule_name) and (tenant_id, to_entity, rule_name) indexes solves the same query at indexed-join speed. JPP scale (~240K edges) is where the difference becomes load-bearing.
  • Referential integrity — from_ref / to_ref as JSONB strings cannot be FK-validated. A row pointing at a non-existent or cross-tenant entity is silently allowed.
  • Source semantic loss at import — the experiment's _raw workaround exists because junction-table source columns had nowhere typed to land when force-fit into RELATIONSHIP's from_ref / to_ref. Typed edges with row-level resolution remove the need for _raw.

canonical_type discriminator (C2, hardened in Rev 2.1 F6)​

Every archetype uses one relational column — canonical_type VARCHAR(50) per ADR-002 — for subtype discrimination. JSONB-level type / event_kind / kind are removed.

Per-archetype enum and validation level are declared explicitly in each contract:

ArchetypeEnumcanonical_type_validationRationale
ENTITY{person, organization, family, place, object, other}HARDDrives query behavior (place uses geo JSONB; person uses biographical JSONB); arbitrary values break the platform
MEDIA{image, video, audio, 3d_model, iiif_manifest, dataset, software, interactive, map, diagram, other}HARDDrives streaming/IIIF/3D-rendering plumbing
ANNOTATIONW3C Web Annotation motivations (bookmarking, classifying, commenting, describing, editing, highlighting, identifying, linking, moderating, questioning, replying, tagging)HARDStandards mandate the vocabulary
DOCUMENTCSL 1.0.2 types (45 values; expanded at validator runtime from schema/csl-types.json)SOFT_ENUMKnown finite set; tenants may add edge cases. Unseen values warn, observed values promoted to enum after threshold review
EVENT{point, period, activity, affiliation} (initial)SOFTTenant-specific event types are common (JPP "dynasty" period, Atlas "edition" period)
TERM{lemma, concept, root, headword, technical_term} (initial)SOFTTenant-extensible per Position 1
PASSAGE{chapter_section, page_line, manifest_canvas, locator_specific} (initial)SOFTLocator-specific types are tenant-driven

Validator semantics (Rev 2.1 F6):

  • HARD: writes with canonical_type outside the enum fail at any lifecycle stage.
  • SOFT_ENUM: writes warn during staging, fail at canonical write unless the value is in the enum or the on-stack promotion list. Observed values can be promoted into the enum via a periodic ADR-amendment pass; until promoted, they remain warnings at staging.
  • SOFT: writes warn at staging if the value is unseen; canonical writes never fail on canonical_type value alone. CI lists per-archetype values seen in fixtures and surfaces drift.

Archetype Contracts​

Each contract defines: required relational floor, conventional JSONB keys (intrinsic-attributes only — C3), canonical_type_enum and canonical_type_validation (Rev 2.1 F6), semantic capabilities, platform capabilities, permission flags, and governance invariants.

Principle (ADR-002): Tables define what can exist; JSON defines how it is expressed. The relational floor is intentionally thin. Rev 2 corollary: anything whose semantic content is an inter-row reference (relationship endpoints, workspace scope, source-row provenance) lives in a typed relational table, not in JSONB data.

DOCUMENT​

Required relational floor: title VARCHAR(500) NOT NULL, canonical_type VARCHAR(50) (CSL-aligned).

DOCUMENT_CONTRACT = ArchetypeContract(
    name="DOCUMENT",
    description=(
        "Texts, sources, manuscripts, editions, treatises, articles, letters, "
        "legal records, bibliographic resources at any FRBR/LRMoo tier."
    ),
    semantic_capabilities=frozenset({
        "can_be_cited", "has_content_structure", "supports_authorship",
        "has_temporal_context", "supports_versioning", "is_citable_passage_source",
    }),
    platform_capabilities=frozenset({
        "full_text_search", "citation_graph", "versioning",
        "oai_pmh_expose", "csl_json_export", "doi_mint",
    }),
    permission_flags=frozenset({
        "allow_public_citation", "allow_versioning",
        "allow_federation", "allow_doi_registration",
    }),
    required_fields={
        "title": FieldSpec(type="CharField", required=True, max_length=500),
        "canonical_type": FieldSpec(type="CharField", required=False, max_length=50),
    },
    canonical_type_enum=("article", "article-journal", "book", "chapter",
                         "manuscript", "thesis", "report", "webpage",
                         # ... CSL 1.0.2 — 45 values; expanded from schema/csl-types.json
                         ),
    canonical_type_validation="SOFT_ENUM",        # Rev 2.1 F6
    conventional_jsonb_keys=(
        # INTRINSIC ATTRIBUTES ONLY — no array-of-refs (C3)
        "frbr_level",         # work|expression|manifestation|item|unspecified
        "publication_date",   # ISO 8601 or historical-calendar-compatible
        "language",           # BCP-47
        "place_of_publication",
        "series",
        "abstract",
        "url",
        "identifiers",        # object<scheme, value>: DOI, ISBN, ISSN, etc.
        # REMOVED in Rev 2 (now typed edges):
        #   author/editor/translator/publisher → DOCUMENT_AUTHORED_BY_ENTITY (role-qualified)
    ),
    invariants=(
        "title must not be empty",
        "frbr_level (when present) must be in {work, expression, manifestation, item, unspecified}",
        "new DOCUMENTs default frbr_level to 'unspecified'",
        "identifiers.doi (when present) must match 10.\\d{4,}/\\S+",
    ),
    confidence_threshold=0.85,
)

Note on the embedded document_id FK on PASSAGE​

PASSAGE keeps a direct relational FK to its DOCUMENT (via document_id on the PASSAGE row), not an entity_relationships row of type PASSAGE_PART_OF_DOCUMENT. Reasoning: every PASSAGE has exactly one parent DOCUMENT with cardinality 1:N enforced at the schema level; there is no semantic reason to model this as a typed edge. This is the one explicit exception to C3 (no inter-row references in entity rows): a same-archetype-pair, mandatory, cardinality-1 parent reference is expressed as a relational FK on the row, not a row in entity_relationships. Rationale: query patterns ("all PASSAGEs of DOCUMENT X") want a single indexed FK lookup; the typed-edge layer is for many-to-many and qualified relationships.

entity_relationships table​

CREATE TABLE entity_relationships (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id   UUID NOT NULL,
    rule_name   VARCHAR(100) NOT NULL,
    from_entity UUID NOT NULL,
    to_entity   UUID NOT NULL,
    qualifiers  JSONB NOT NULL DEFAULT '{}',                 -- validated against rule.metadata_schema at canonical write
    confidence  DECIMAL(3,2),                                 -- universal provenance metric (Rev 2.1 F5: not in required_metadata)
    dedupe_key  VARCHAR(200) NOT NULL DEFAULT '',             -- Rev 2.1 F3: per-rule qualifier-derived hash; '' = no qualifier-aware dedup
    status      epistemic_status NOT NULL DEFAULT 'DRAFT',    -- Rev 2.1 F4: lifecycle starts at DRAFT
    provenance  JSONB,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),

    -- Tenant consistency (Rev 2.1 F2): from/to must be in same tenant as edge
    FOREIGN KEY (from_entity, tenant_id)
        REFERENCES epistemic_entities (id, tenant_id) ON DELETE CASCADE,
    FOREIGN KEY (to_entity, tenant_id)
        REFERENCES epistemic_entities (id, tenant_id) ON DELETE CASCADE,

    -- Rev 2.1 F3: qualifier-aware uniqueness via dedupe_key
    UNIQUE (tenant_id, rule_name, from_entity, to_entity, dedupe_key)
);
CREATE INDEX idx_rel_from        ON entity_relationships(tenant_id, from_entity, rule_name);
CREATE INDEX idx_rel_to          ON entity_relationships(tenant_id, to_entity, rule_name);
CREATE INDEX idx_rel_qualifiers  ON entity_relationships USING GIN (qualifiers);
CREATE INDEX idx_rel_status      ON entity_relationships(tenant_id, status);

dedupe_key formula (Rev 2.1 F3)​

dedupe_key is populated at insert/update by a deterministic formula over qualifier values declared in the rule's dedupe_qualifiers. The default rule (no dedupe_qualifiers) yields '', preserving the simple-uniqueness behavior.

Concrete formula: sha1(jsonb_strip_nulls(qualifiers - all_keys + dedupe_qualifier_keys))::varchar(200) — i.e. extract only the qualifier values listed in dedupe_qualifiers, normalize, hash. Implementation lives in a Postgres trigger or in the Action runtime (preferable for testability).

Examples:

  • DOCUMENT_AUTHORED_BY_ENTITY with dedupe_qualifiers=("role",): two edges between the same DOCUMENT and ENTITY with role="author" collide; role="author" and role="editor" are distinct.
  • PASSAGE_PARALLEL_TO_PASSAGE with dedupe_qualifiers=("edition_relation",): two parallel-passage edges with different edition_relations coexist.
  • ENTITY_LOCATED_IN_ENTITY with dedupe_qualifiers=("start_date",): a person located in different cities at different times has multiple edges.

Bidirectionality (C6, unchanged in Rev 2.1)​

Single-row storage. Query-time UNION resolves the inverse. A bidirectional=True rule does not duplicate rows; the GraphQL resolver issues a UNION over (from_entity, to_entity) and (to_entity, from_entity). Cost is one UNION per bidirectional read; acceptable at JPP scale and below.

Lifecycle-aware validation (Rev 2.1 F4)​

Validator strictness depends on entity_relationships.status:

Statusrule_name resolutionqualifiers schema checkfrom/to FK existence
DRAFT, AI_PROPOSED, HUMAN_REVIEWwarning if unknownwarning on schema mismatchrequired (DB constraint)
APPROVED, APPLYING, APPLIED_TO_CANONICALfail if unknownfail on schema mismatchrequired (DB constraint)

The LLM's proposed edges land in DRAFT or AI_PROPOSED with permissive validation, surfacing warnings to the reviewer. Only when the reviewer approves an Action that transitions an edge to APPROVED does strict validation gate the write. This resolves the contradiction in Rev 2 between "warning if rule unknown" (implementation tasks) and "match required" (write-time text).

The validator ships in two callable forms:

  • validate_for_staging(edge_row) -> list[Warning] — non-blocking; populates a reviewer-visible warning list.
  • validate_for_canonical(edge_row) -> Result[None, ValidationError] — blocking; called at the lifecycle transition into APPROVED.

The materialization pipeline calls validate_for_staging. The Action runtime that flips status to APPROVED calls validate_for_canonical.

Resolution order at write time:

  1. Look up rule_name in PLATFORM_CANONICAL_RULES.
  2. If not found, look up (tenant_id, rule_name) in tenant_relationship_rules.
  3. Apply lifecycle-aware validation (Rev 2.1 F4): warn at staging, fail at canonical.

❌ Don't: Add a new archetype without going through PROMOTION_RULES + 3-tenant evidence + ADR amendment. ✅ Do: Add a new canonical_type value (warns/promotes per archetype's validation level) or a tenant-defined relationship rule first; escalate to archetype only if JSONB-rescue fails.

❌ Don't: Store cross-row references in JSONB arrays. ✅ Do: Express them as entity_relationships rows with the appropriate rule_name.

❌ Don't: Use parallel discriminators (kind, event_kind, JSONB type). ✅ Do: Use the single canonical_type relational column with the per-archetype canonical_type_validation declared (Rev 2.1 F6).

❌ Don't: Hardcode tenant-specific labels as archetype names or rule names in PLATFORM_CANONICAL_RULES. ✅ Do: Use TenantOntology.local_name for tenant labels; use tenant_relationship_rules for tenant-specific edge types.

❌ Don't: Put governance fields (status, confidence, approver) in JSONB. ✅ Do: Keep them relational (ADR-002).

❌ Don't (Rev 2.1): Re-add confidence to required_metadata on a relationship rule. It's the relational column. ✅ Do: Use the column. Reserve required_metadata for semantic per-rule fields (role, target_language, attested_form, edition_relation).

❌ Don't (Rev 2.1): Use single-column FKs on entity_relationships. Cross-tenant edges will pass silently. ✅ Do: Use the composite FKs (from_entity, tenant_id) and (to_entity, tenant_id).

❌ Don't (Rev 2.1): Block legitimate qualified repeats with the bare (tenant_id, rule_name, from_entity, to_entity) UNIQUE. ✅ Do: Declare dedupe_qualifiers on the rule; dedupe_key widens uniqueness automatically.
