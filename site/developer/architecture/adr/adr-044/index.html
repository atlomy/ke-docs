ADR-044: Voice and vocabulary substrate — composable per-tenant sources on tenant ontology, consumed by display and reasoning surfaces under the ADR-014-α bounded-agency contract

  • Status: Proposed
  • Date: 2026-05-24
  • Deciders: User; architecture team
  • Context source: Schema-driven terminology research arc (gitignored, local-only at docs/internal/research/2026-05-24_schema-driven-terminology/); Spec 0017 voice feature; ADR-035 §4.1 layered safety floor dependency; partner_model calibration entries 2026-05-19 and 2026-05-22 and 2026-05-24; ADR-014-α single-call assist contract (α-activated 2026-05-21)
  • Related: ADR-014-α (In-Product AI Runtime — load-bearing parent contract; this ADR is the first to extend α to a substrate-context-enrichment pattern), ADR-016 (Telemetry Substrate — inherited for redact-before-log, classifier integration, retention), ADR-035 (Tenant Contributor Permission Model — §4.1 phrase matrix gets its first implementation here), ADR-037 (Slot-Type Taxonomy + Tier-2 TenantSlotPreset — distinct axis, lives adjacently), ADR-042 (Layered substrate naming — Phase-1 migration coordinates with the rename), Spec 0017 (Import Wizard UX Overhaul — §3.3 and US-D.3 superseded by this ADR), Spec 0020 v1.2 §10.2 Wave 2 (sibling AI-assist consumer under ADR-014-α), Spec 0026 (vocabulary grounding admin workflow — Tier-2 slot-value vocabulary, distinct axis)

TL;DR​

KE's user-facing text is data on the tenant ontology, not strings hard-coded against internal class names. The substrate is a typed per-tenant table (TenantVocabularyEntry), populated from five composable sources (admin-override, AI-reviewed, derivation seed, data-derived, standards-mapped, platform-canonical), compiled into per-request per-tenant vocabulary packs, consumed by both display surfaces (template tags, React hooks) and reasoning surfaces (matching engine LLM gate, ambient chat, future tip engine) under the ADR-014-α bounded-agency contract. Sprint D ships one collapsed substrate phase (typed table + compiled packs + namespace expansion + template tag + four-surface wiring), preceded by enabling DjangoOptimizerExtension globally on the GraphQL schema. The Spec 0017 §3.3 / US-D.3 "JSONB blob + admin editor" framing is superseded: derivation is canonical, override is by tenant-admin tooling not UI, and the substrate is typed-from-day-one with no transitional JSONB.

Context​

The original five-point question​

The architectural intent surfaced in conversation (2026-05-24, captured in the research arc's fresh-session handoff and partner_model entry 2026-05-24:722-748):

How does a multi-tenant scholarly platform compose three vocabulary sources — platform-canonical (deliberately neutral chrome), data-derived (the researcher's own column and table headers harvested during import), and AI-assistive (suggestions, standards mappings, onboarding-time vocabulary proposals) — into a unified import-AND-workspace experience where:

  1. Researchers see their own terms preserved, not replaced by platform vocabulary or canonical-standards vocabulary
  2. The wizard's matching surface bridges across the three vocabularies legibly, surfacing all three at once rather than collapsing two into the third
  3. The workspace also feels native to each project's research domain, not just the wizard
  4. Standards alignment is offered as small nudges, not as renames — the platform helps researchers move toward standards-aligned vocabulary without taking their own vocabulary away
  5. The architecture is robust: a rename of an internal model class doesn't silently break the user-facing vocabulary because the templates never reference internal class names directly

These five commitments are the substrate's acceptance criteria.

What exists today and what is missing​

customers/services/vocabulary_derivation.py ships a prototype of the substrate scoped to permission/bundle/telemetry copy on tenant-admin surfaces. derive(tenant, template_key, archetype_context) resolves a key through: (1) tenant.voice_overrides mapping, (2) an "honest fallback" check that short-circuits to canonical when ontology data is too small/large/junky to derive cleanly, (3) the canonical template in VOCABULARY_TEMPLATES, (4) placeholder substitution against TenantOntology rows. Quality guardrails (_label_issue, _looks_backend_generated, _looks_code_like) detect bad display labels.

Substrate consumer discipline (added 2026-05-26): the substrate adapts even without an explicit override row. derive() substitutes placeholders from TenantOntology (tenant's own archetype + slot labels) into the canonical template, and _fallback_bundle_voice provides smart pluralization. The "no override" state is not raw platform English — it is ontology-adapted substrate output. The admin-override path is the last-resort fallback a tenant may never need to reach. Consequence for any code that consumes the substrate:

  • NEVER hardcode a render only if has_tenant_specific branch. Render via the substrate's default chain.
  • has_tenant_specific / canonical_available / derivation_layer are observational telemetry signals only — they record what the substrate did; they must not gate user-facing rendering.
  • Gates that block on override absence (B9-style "must have admin_override / ai_reviewed / derivation_seed row") are almost certainly miscalibrated; they force friction on tenants whose substrate is already adapting via the data-derived lane and ontology placeholders. R3 absorption (commit f05f8b53) softened B9 to observational-only specifically because the override-required posture asked tenants to commit to vocabulary they hadn't formed yet.

What is missing:

  • The voice_overrides storage. The reader at line 239 is wired (getattr(tenant, "voice_overrides", None)); the Client model has no such field. Reader always returns "" today.
  • Namespace coverage beyond permission.*, decision_event.*, telemetry.panel.*. Wizard, workspace, layered safety floor, and ambient chat use hard-coded English.
  • Reasoning-surface consumption. derive returns a single string; reasoning surfaces (matching engine LLM gate at epistemic/services/proposals/prompt.py, ambient chat system prompt at data_import/services/ambient_chat.py) need structured per-tenant context, not rendered strings.
  • Multi-lane composition. derive answers "single best string"; the Stage 3 matching review card needs "researcher's authored header AND platform-neutral label AND standards-mapped label rendered alongside."

The brittleness pattern and the partner_model corrections​

Spec 0017 §3 specifies a ban-list dictionary (MappingProposal, JSONB, archetype, etc.) and tone rules. The ban-list is spec-only — no sanitizer or lint enforces it. The brittleness: a rename of MappingProposal to MatchSuggestion invalidates the ban-list entry; strings referencing the class name leak the new name. The dictionary discipline is post-hoc.

US-D.3 specified voice_overrides JSONB on TenantArchetypeFormConfig plus an admin editor. Two calibration entries supersede parts of that plan:

  • partner_model.md:349-354 (2026-05-19): derivation from TenantOntology + canonical templates is canonical; no admin editor; voice_overrides field stays as escape hatch for the rare tenant who needs it.
  • partner_model.md:584-586 (2026-05-22): engineering-internal vocabulary and user-facing vocabulary evolve on separate tracks; hard-renaming engineering substrate as part of UI vocabulary evolution is an anti-pattern.

The bounded-agency parent contract (ADR-014-α)​

ADR-014-α (α-activated 2026-05-21) ratified the single-call LLM assist contract for in-product AI. §1 (Bounded Agency, the floor — never relaxed without a new ADR):

The AI surface MAY explain, suggest, summarize, retrieve, score, classify, propose for review. The AI surface MUST NOT, without an explicit user action gated by ADR-035 capability checks: approve, apply, publish, index, delete, mutate any tenant data; mutate platform-canonical state; enqueue background work that would later mutate state; emit signals into telemetry that downstream systems consume as user-equivalent input; bypass any reviewer-gate that exists for the non-AI path.

The platform's primary defense against LLM misbehavior is sandboxing at the action surface, not at the input surface. This ADR's vocabulary substrate is the first ADR to extend α to a substrate-context-enrichment pattern: it enriches LLM input with per-tenant vocabulary, knowing the LLM cannot act outside α's bounded scope regardless of input.

The cross-tenant priming rule, structurally answered​

epistemic/services/proposals/blacklist.py ships KNOWN_BAD_TOKENS — a hand-maintained denylist of current pilot tenant codenames, plus tenant-specific archetype slang from those tenants' domains, plus per-tenant column names added after a 2026-04-26 incident on the ai-mapping branch (see epistemic/services/proposals/blacklist.py for the canonical list — that file is exempt from the prompt-source audit; this ADR avoids restating the contents to keep documentation aligned with the tenant-naming discipline). tests/unit/test_proposal_prompt.py asserts these tokens never appear in prompt source. The rule's intent is cross-tenant priming prevention — preventing the prompt from biasing the LLM toward one tenant's mental model when serving another.

The denylist is reactive by construction: it covers the three current tenant DBs only and requires manual extension per incident. The substrate is the structural answer: tenant-specific terms NEVER appear in source code (only platform-canonical archetype names + structural strings); per-tenant data is compiled per-request via connection.schema_name-forced scoping; cross-tenant priming becomes structurally impossible.

Adjacent ratified work that constrains this ADR​

  • ADR-014-α — load-bearing parent. This ADR is the first to extend α to substrate-context-enrichment.
  • ADR-016 — Telemetry Substrate; load-bearing for redact-before-log discipline (§2), injection_classifier_verdict enum (§2), retention defaults (§2 — 30 days for verbatim free-text; hashed/aggregate beyond), pseudonymisation via per-tenant HMAC key (§3), Art. 17 erasure pattern (§8).
  • ADR-035 §4.1 — Layered safety floor cites a 4×3 matrix of researcher-natural confirmation phrases (Builder ratification 2026-05-17 Amendment 3.a). The matrix is currently spec-only; vocabulary_templates.py:82-86 has only one of the four templates. This ADR's substrate is what the matrix runs on.
  • ADR-037 + Spec 0026 Tier-2 TenantSlotPreset substrate exists for slot-VALUE vocabulary (controlled vocabulary populating a slot — e.g., text_type choices). This ADR is about display-label vocabulary — a different axis. They sit adjacently on tenant-config models and must not collide.
  • ADR-042 in-flight rename of TenantArchetypeFormConfig (likely to ArchetypeFormConfig or SlotPreset) affects naming for any field that lands on that model. The Phase-1 migration coordinates with the rename.
  • Spec 0017 design.md:94 withdrew discipline-declaration at import start before Sprint A on three grounds: friction; fixed-enum mis-categorization; within-domain heterogeneity. The chat-based version proposed here addresses these via design constraints (skippable, open-text/soft-schema, additive-only).

Research-for-publication arc​

Internal SOTA notebook (Special — Comfort-Dial & Beyond — SOTA / Cross-Disciplinary Research, 263 sources organized into three labels) was assembled to inform both this architecture decision and two paper drafts: Paper 1 — Asymmetric Within-Language Localization and Paper 2 — Source Headers as Preserved Domain Signal. The chosen architecture (this ADR) is the case study both papers cite. Industry analogue is Mozilla Project Fluent (closest design-rationale match; presentation-only; doesn't formalize composition or generalize to reasoning surfaces).

Decision​

The platform commits to a vocabulary substrate with the following architectural properties.

1. Typed table, not JSONB​

Vocabulary lives in a per-tenant typed table:

TenantVocabularyEntry (per-tenant schema via django-tenants):
  - id (PK)
  - namespace (varchar, indexed)          # 'wizard', 'workspace', 'safety_floor', 'ambient_chat', 'permission', 'decision_event', 'telemetry'
  - key (varchar, indexed)                # 'stage3.match_card.header', 'row_drawer.title', 'high_tier.confirmation_template', ...
  - source_kind (enum)                    # 'canonical' | 'derivation_seed' | 'admin_override' | 'ai_reviewed' | 'data_derived' | 'standards_mapped'
  - rendered_value (text)                 # display string (post-substitution where applicable; placeholders allowed for derive-time substitution)
  - structured_payload (jsonb, nullable)  # reasoning-surface payload — typed token, relationships, standards URIs
  - archetype_scope (varchar, nullable)   # narrow entry to one archetype (TERM / DOCUMENT / ...) when applicable
  - slot_scope (varchar, nullable)        # narrow entry to one slot when applicable
  - source_provenance (jsonb, nullable)   # CLOSED-SCHEMA: {import_template_id?, harvested_at_day?, harvest_round?, ai_suggestion_id?} only
  - created_at, updated_at

  UNIQUE INDEX (namespace, key, source_kind, archetype_scope, slot_scope)
  INDEX (namespace, key)  -- single-lookup read path

Resolution for single-string consumers becomes one indexed query ordered by source_kind priority. For multi-lane consumers (Stage 3 card, exports), drop the LIMIT and render every row. Same table.

Phase 1 + the originally-planned Phase 4 ("promote to ontology data") collapse: there is no JSONB blob first, no migration second. Typed from day one. The Spec 0017 §3.3 voice_overrides JSONB field is superseded; Client does not gain a voice_overrides column.

2. Semantic-role token naming, never internal class names​

Template keys are dotted-namespace semantic role tokens: wizard.stage3.match_card.header, workspace.row_drawer.title, safety_floor.high_tier.confirmation_template, ambient_chat.system_prompt.voice_block. A rename of MappingProposal → MatchSuggestion MUST NOT require any vocabulary change.

3. Five composable sources, two composition modes​

The five source_kind values, with single-string consumer priority order:

source_kindPriority (single-string)Authority
admin_overrideHighestWhat this tenant explicitly chose to display (populated via tenant-admin tooling, NOT a UI editor)
ai_reviewedSecondAI-suggested at onboarding / first-use and accepted by admin
derivation_seedThirdSeed values for the derivation layer (canonical templates + placeholder substitution against TenantOntology)
data_derivedRender alongside (not in priority chain)Researcher's authored column header or table label, surfaced as parallel lane in matching review
standards_mappedRender alongside (not in priority chain)URI-bound standards label, surfaced in publish/export/standards-bridging surfaces
canonicalFallback baselinePlatform-neutral default; what the substrate renders when nothing tenant-specific is available

For single-string consumers (button labels, headers, safety-floor phrases): priority chain. For multi-lane consumers (matching review cards, export annotations, Stage 3 three-lane display): parallel rendering — data_derived and standards_mapped rows show alongside the priority-resolved canonical/derivation_seed/admin_override/ai_reviewed choice.

4. Two consumer classes under ADR-014-α​

Display surfaces (wizard chrome, workspace headers, safety-floor phrases, receipts, ambient-chat copy) consume via a Django template tag {% voice 'wizard.stage3.match_card.header' tenant=tenant context=ctx %} and a React useVocabulary(key, context) hook backed by a server-rendered JSON payload of resolved tokens for the current view.

Reasoning surfaces (matching engine LLM gate at epistemic/services/proposals/prompt.py, ambient chat system prompt at data_import/services/ambient_chat.py, future tip / recommendation engine, future table-to-table connection inference) consume the substrate as a compiled per-tenant vocabulary pack: a denormalized dict (token → {rendered, structured_payload, source_kind}) compiled at request boundary from TenantVocabularyEntry, cached per-tenant with invalidation tied to vocabulary fingerprint change (reusing the existing _ontology_label_fingerprint SHA-256 pattern). Injected into LLM prompts as ~150-300 tokens of terse YAML-like context.

LLM injection of compiled packs falls under ADR-014-α §1 bounded-agency. The LLM cannot act on injection-shaped input regardless of payload content. Safety guarantees inherit from the parent contract; this ADR does not re-derive them.

5. Override is by tenant-admin tooling, not by UI editor​

Per partner_model.md:349-354, derivation is canonical; the admin_override source_kind is populated by tenant-admin scripts or platform-staff tooling for the rare tenant who needs an override. There is no admin-editor UI. The Spec 0017 US-D.3 admin editor scope is removed.

6. The audit rule converts from denylist to structural allowlist​

KNOWN_BAD_TOKENS is a reactive denylist that covers the three current tenant DBs and requires manual extension per incident. Once Phase 1 ships, no source file in epistemic/services/proposals/ or any LLM-prompt construction code contains string literals from any tenant — only platform-canonical archetype names + structural strings. tests/unit/test_proposal_prompt.py Layer 1 converts from "no token from this list appears in source" to "no string literal in source exists outside the canonical template registry / _ARCHETYPE_DESCRIPTIONS / fixed structural delimiters." The audit rule's intent (cross-tenant priming prevention) is satisfied structurally; the token list becomes legacy and can be retired or kept as belt-and-suspenders during transition.

7. Discipline-priors chat at import start is in MVP under ADR-014-α single-call assist​

The Spec 0017 design.md:94 withdrawal of discipline declaration is reopened with new rationale grounded in the ADR-014-α bounded-agency contract and four design constraints derived from stress-testing against two adversarial scenarios (Counter-example A: same anatomy table shape, different source corpus — manuscript decorations; Counter-example B: out-of-distribution input — internal corporate wiki):

  • Skippable, never blocking: the chat is an optional pre-Stage-1 conversational shim; downstream stages tolerate empty ImportContext and behave as today.
  • Soft schema: ImportContext is open-shape JSON; AI chooses what fields are useful; downstream consumers consume what's present and ignore what's absent. NO fixed enum like {discipline, corpus, granularity, standards}.
  • Additive only, never gate: parser-first matching (epistemic/services/parser/) remains the floor. ImportContext may bias the LLM gate's confidence scoring but never short-circuits it.
  • AI-self-flagged confidence + measurable-or-yanked: if classification confidence is low, AI offers to skip ("I'm not sure I have useful context here; want to proceed without?"). Skip-rate + match-quality delta (with-context vs without-context) instrumented from day one against the human-import-test baseline. If skip-rate > 70% or quality delta < 5% sustained, feature is yanked.

The chat composes with the existing Spec 0017 C.3 ambient chat infrastructure. Both inherit ADR-014-α §1 bounded-agency.

8. Empirical validation floor​

A human import test scheduled this week through all wizard stages establishes the baseline: per-stage durations, override counts, match acceptance/correction/rejection rates, vocabulary-confusion incidents, AI-helper accuracy, hard-coded-string counts per surface, and tenant-vocabulary leakage events. Every ADR-044 phase ships measured against this baseline. Phases that don't improve the relevant metric versus the floor are re-evaluated. The human-test checklist gains explicit metric capture for these data points.

Alternatives considered​

(a) Spec 0017 status quo: JSONB blob on Client + TenantArchetypeFormConfig + admin editor UI​

Rejected per partner_model.md:349-354 (manual editor produces half-empty configurations; derivation is canonical). The "JSONB blob" half is also rejected on architectural grounds: read amplification (partially mitigated by strawberry-django field selection + GinIndex(jsonb_path_ops) but still inferior to typed columns for queryability + multi-lane composition + provenance discipline); opaque to reasoning surfaces (JSONB-of-JSONB is awkward for graph fragments); resolution-order tax (multi-place precedence is application-layer logic instead of typed enum).

(b) Phased JSONB → typed migration (the prior draft of this ADR)​

Rejected. Greenfield pre-production environment means migration friction is not a binding constraint. The Phase 1 → Phase 4 collapse stands on architectural grounds: one shape from day one is simpler than transitional shape + migration.

(c) Translation-file approach (django-i18n style)​

Rejected. Wrong axis: per-tenant variation is not language translation; tenants are not languages; ontology shape changes with imports. Doesn't address reasoning surfaces (translation catalogues are display-only by design).

(d) Per-tenant template forks at build time​

Rejected. Linear maintenance burden in N tenants. Defeats multi-tenant SaaS posture.

(e) Defer entirely; keep voice as spec-only ban-list discipline​

Rejected. The KNOWN_BAD_TOKENS denylist is reactive by construction; covers only the three current tenant DBs; requires manual extension per incident. ADR-035 §4.1's 4×3 matrix has no implementation substrate. Reasoning surfaces gain nothing from spec-level discipline.

(f) Defer discipline-priors chat past MVP​

Rejected. Chat is platform intent under ADR-014-α; agentic practices were never optional. Spec 0017 C.3 ambient chat is in production; Spec 0020 v1.2 §10.2 Wave 2 ships next under α. The stress-test design constraints in Decision §7 are sufficient safety scaffolding to ship within MVP.

Consequences​

Positive​

  • Internal model renames stop propagating to UI. ADR-042's in-flight TenantArchetypeFormConfig rename and all future engineering-internal renames land without UI breakage.
  • Cross-tenant priming becomes structurally impossible. KNOWN_BAD_TOKENS denylist's scaling problem (one entry per leak per tenant per incident) is replaced by structural guarantee (no tenant terms in source code, ever).
  • Multi-tenant native vocabulary becomes structural, not editorial. Pilot and future tenants get native-feeling chrome without per-tenant spec branching.
  • One substrate serves both display and reasoning. AI helper speaks per-tenant vocabulary; matching engine consumes priors as semantic signal; tip engine reads the same source as chrome.
  • ADR-035 §4.1's 4×3 layered safety floor phrase matrix gets its first implementation. Canonical English baseline in Phase 1; per-tenant specialization via admin_override or derivation_seed rows.
  • Aligns with ADR-014-α single-call assist contract. This ADR is the first to extend α to substrate-context-enrichment, codifying a reusable pattern future AI-assist features pick up by reference.
  • Greenfield migration cost is moot. Typed substrate from day one; no transitional shape; no deferred migration.
  • Research-for-publication positioning is concrete. Paper 1 and Paper 2 cite this ADR's architecture as the worked example.

Negative​

  • Sprint D scope expands from "migration + admin editor + template tag" to "enable DjangoOptimizerExtension platform-wide + benchmark re-run gate + DataLoader audit per @strawberry.field custom-resolver + create typed table + populate canonical English baseline + namespace expansion + template tag + four-surface wiring (workspace + ambient-chat + wizard chrome + safety-floor per R2 ratification) + audit-rule conversion + Phase 3 chat shim + B9 runtime live-for-new-tenants gate inside safety-floor wiring." Per-task hour estimates in docs/superpowers/specs/0017-import-wizard-ux-overhaul/tasks.md US-D.3 sum to ~22.25 human-hours for the full 4-surface MVP including D.3.0's benchmark re-run + DataLoader audit sub-tasks. Applying empirical agent-time ratios from docs/calibration/agent-time-estimates.md (N=377; mixed category mean 0.70, median 0.67), expected agent-time is ~15 hours core implementation + 2-3 hours verification overhead = ~17-18 hours agent wall-clock — about 2.5 focused agent session-days. Doable in a single overnight autonomous session. Biggest blast radius of any Sprint D scope considered; wall-clock still bounded.
  • Coordination required with two in-flight architectural threads. ADR-042 rename + Spec 0026 / ADR-037 Tier-2 TenantSlotPreset substrate.
  • Reopening Spec 0017 design.md:94 withdrawal of discipline declaration depends on the four design constraints in Decision §7 holding under real use. If skip-rate or quality-delta metrics undercut the constraints, Phase 3 yanks.
  • Mechanical replacement of hard-coded English in wizard / workspace / safety-floor / ambient-chat surfaces is large-surface-area, error-prone work. Risk of partial migration leaving the substrate split-brain.
  • Admin-override population requires tenant-admin scripts or platform-staff tooling rather than self-service UI. Rare overrides incur real friction.
  • Chat-transcript retention policy is a new platform-wide question this ADR surfaces but does not resolve (see Open Question Q1).

Neutral​

  • The five-source priority + dual-consumer model is novel relative to industry tools. Mozilla Project Fluent is the closest analogue but is presentation-only.
  • Implementation is sequenced by phase, not delivered as one drop. Sprint D ships Phase 1 (the substrate + four-surface wiring + Phase 3 chat shim). Phases 2 (data-derived lane) and 5+6 (AI-assisted onboarding + tip engine) follow as their own specs.
  • Substrate is opt-in per consumption site. Existing hard-coded English in surfaces not yet wired remains valid platform code until migrated.

Limitations​

Empty-tenant behavior (TenantOntology = 0): When a tenant has no TenantOntology rows, the substrate cannot perform vocabulary substitution and falls back to platform-canonical English labels ("Record kind", "Column match", etc.). The substrate-adapts feature requires at least one TenantOntology row to be configured. Seeding a default vocabulary is tracked as a future enhancement (ER-15 "seed default" path, deferred). Validated by ADR-037 Phase A.1 live-test finding F31 (2026-05-27).

This scopes the "Substrate consumer discipline" claim in §Context ("the substrate adapts even without an explicit override row"): that claim holds when TenantOntology is non-empty (placeholder substitution runs from ontology rows); it does not hold for a genuinely empty tenant (zero rows, no placeholders to substitute). The "NEVER hardcode a render only if has_tenant_specific branch" rule and the B9 softening (observational-only) remain correct for tenants with ontology data. For empty tenants, the substrate renders platform-canonical English and Stage 3 surfaces a non-blocking notice to the admin (see Stage 3 template _wizard_stage3_body.html).

Implementation notes​

Sprint D pre-requisite — enable DjangoOptimizerExtension​

Currently atlomyapp/graphql/schema.py:5612 registers schema = strawberry.Schema(query=Query, mutation=Mutation) with no extensions. The optimizer enable is a platform-wide change, not a vocabulary-substrate-specific one — it benefits every GraphQL read path in schema.py (which already does 8+ manual select_related calls that would compose with optimizer-inferred prefetches). The vocabulary substrate's read path happens to be the most N+1-prone surface we're adding, but the optimizer enable lands once and pays back across the schema.

from strawberry_django.optimizer import DjangoOptimizerExtension

schema = strawberry.Schema(
    query=Query,
    mutation=Mutation,
    extensions=[
        DjangoOptimizerExtension(
            enable_only_optimization=True,            # .only() column pruning
            enable_select_related_optimization=True,  # FK joins
            enable_prefetch_related_optimization=True,  # M2M / reverse joins
            enable_annotate_optimization=True,          # annotate() pruning
            enable_nested_relations_prefetch=True,      # nested relation prefetch through filters/pagination
            prefetch_custom_queryset=True,              # use _default_manager (custom) instead of _base_manager for prefetch — KE-specific safety; see "prefetch_custom_queryset for KE" below
        ),
    ],
)

All five enable_* flags default to True per the actually-installed strawberry_django.optimizer source (verified 2026-05-25 via inspect.getsource(DjangoOptimizerExtension) against strawberry-graphql-django==0.84.0). The sixth flag prefetch_custom_queryset defaults to False and is opt-in. Listing all six explicitly is preferred for clarity + future-proofing — if a future release flips a default, the explicit form continues to behave as Sprint D designed.

prefetch_custom_queryset=True for KE specifically: when enabled, the optimizer uses Django's _default_manager (custom, when one is set on the model) instead of _base_manager (always-vanilla) for building prefetch_related() querysets. KE has at least one custom manager with security-critical semantics — telemetry/models.py:88 _TenantScopedTelemetryManager overrides get_queryset() to raise RuntimeError when called from the public schema. With _base_manager (False), nested prefetch silently bypasses this cross-schema guard; with _default_manager (True), the guard fires and the prefetch fails loud rather than leaking tenant data. Django's general recommendation of _base_manager for prefetch (to avoid unintended filtering) does not apply to KE because our custom managers do not filter on read; they guard. Spec 0017 US-D.3 D.3.0 documents this drift discovery + rationale.

enable_nested_relations_prefetch=True value to KE specifically: this flag handles nested relation chains (A → B → C) through filters/pagination as a single optimized query rather than per-step cascades. KE has multiple chains where this pays directly — attestation → claims → citations/references is the canonical case; relationship-edge traversal (EntityRelationship ↔ EpistemicEntity neighborhoods) is another; mapping-proposal audit trails are a third. The optimizer enable is therefore not just preventing vocabulary-substrate N+1 — it's structurally accelerating chain traversal for the platform's most-used read patterns.

Plus per-field strawberry_django.field(prefetch_related=[...]) annotations on substrate-derived resolvers. Without the optimizer, the substrate ships 50 roundtrips per page; with it + compiled per-tenant packs, page-level cost is one DB hit + dictionary lookups.

DataLoaders — REAL use case in KE, audit required (corrected 2026-05-25): a prior version of this section claimed DataLoaders were "explicitly not in scope" because KE has zero current usage. That was too strong. The actually relevant criterion is: DataLoaders matter when a Strawberry field's resolver is a custom Python method (not a direct queryset return) that issues its own DB queries the optimizer can't trace. A 2026-05-25 grep of atlomyapp/graphql/schema.py surfaced multiple such resolvers — @strawberry.field def mapping_proposal_audit_trail, def tenant_permissions_panel, def dpia_refresh_triggers, def decision_event_capture_failures, plus the attestation/relationship chain mutations near lines 4215+5017+5086. These are the candidates for DataLoader. D.3.0 includes an audit subtask: for each @strawberry.field decorator on a method body in schema.py, classify as (a) direct ORM return (optimizer covers it), (b) custom Python with DB queries (DataLoader candidate), or (c) custom Python without DB queries (no action). For (b) candidates, evaluate per-resolver whether DataLoader is the right fix or whether converting to a queryset-returning resolver is cleaner. Don't speculatively add DataLoader scope — audit first, decide per-resolver, document the decisions.

Benchmark re-run as part of D.3.0: enabling the optimizer changes query patterns platform-wide. The existing benchmark touchstones MUST be re-run post-enable to confirm no regressions and capture perf deltas:

  • tests/integration/test_adr017_phase2a_benchmarks.py
  • tests/integration/test_adr017_phase2a_z_47k_benchmark.py (47K-row index benchmark — the "early tests for the four DB indexes" baseline)
  • tests/integration/test_adr017_phase2b_ledger_benchmark.py
  • tests/unit/test_benchmark_v1_baseline.py
  • Broad regression sweep: tests/integration/test_phase2k* series (10+ files) and tests/unit/test_*phase2k* series

If any benchmark regresses by more than 10%, scope out of Sprint D as a separate investigation — don't paper over by reverting the optimizer enable; the optimizer is the right architectural direction and a regression is a signal of a specific resolver pattern that needs explicit prefetch_related to compose correctly with the existing manual select_related calls.

DataLoaders: audit-first, not blanket-deferred (corrected 2026-05-25 from prior draft). The original ADR draft said DataLoaders were "NOT needed, not in scope" because of zero current DataLoader usage. That was too strong and contradicted the audit guidance above. The reconciled stance:

  • DataLoaders MATTER in KE when a Strawberry field resolver is a custom Python method that issues its own DB queries the optimizer cannot trace. The D.3.0 audit identifies these candidates per-resolver (see "DataLoaders — REAL use case in KE, audit required" above for the grep-surfaced candidates: mapping_proposal_audit_trail, tenant_permissions_panel, dpia_refresh_triggers, decision_event_capture_failures, plus attestation/relationship chain code).
  • For each (b) candidate, evaluate whether a DataLoader is the cleanest fix OR whether refactoring to return a queryset directly is simpler (lets the optimizer cover it without a new abstraction).
  • The D.3.0 audit findings are documented in the D.3.0 commit message — per-resolver decisions ("a", "b → DataLoader", "b → convert to queryset", "c"). Speculative DataLoader scope without an audit is what the prior draft was rightly trying to avoid; the audit makes the call empirical.

The audit found the Query-level @strawberry.field decorators in schema.py are all single-shot per-request entry points (not N+1 generators) — DataLoader is not applicable at that layer. The optimizer's real value attaches at the strawberry_django.type decorator layer where nested field resolution happens; the optimizer activates automatically for those. Two resolvers (dpia_refresh_triggers, decision_event_capture_failures) have bounded 200-row list comprehensions with select_related already applied — worth a post-Phase-1 perf-data-driven optimization pass but not blocking.

Sprint D — Phase 1 (target: ~17-18 hours agent wall-clock; ~22.25 human-hours per-task; full 4-surface MVP per R2 + D.3.0 benchmark re-run + DataLoader audit)​

Per-task estimates below carry the human-hour convention from the existing Spec 0017 task format. Empirical agent-time per docs/calibration/agent-time-estimates.md (N=377; mixed-category mean 0.70 / median 0.67 against the per-task hours) is approximately 15 hours core implementation + 2-3 hours verification overhead for the full 4-surface MVP (D.3.0-D.3.15; D.3.0 includes platform-wide optimizer enable + benchmark re-run gate + DataLoader audit + per-resolver fixes). About 2.5 focused agent session-days. Doable in a single overnight autonomous session per the user's planned execution path. The estimate likely overstates net agent-active time (calibration log tracks total wall-clock-including-user-turn-time, which inflates ratios vs pure agent-active time); treat 17-18 hr as the upper bound.

  • Migration creating TenantVocabularyEntry per tenant schema. Seed with canonical English baseline rows for permission.*, decision_event.*, telemetry.panel.* (migrating existing in-Python VOCABULARY_TEMPLATES registry into seed-data rows), plus new wizard.*, workspace.*, safety_floor.*, ambient_chat.* namespace baselines. Migration test asserts table is created in tenant schemas only, never in public.
  • vocabulary_derivation.derive() rewrite to query the typed table (or the preloaded request-local pack) with the same public API; existing callers in customers/ keep working unchanged.
  • Compiled per-tenant vocabulary pack built at tenant-load middleware, cached per-tenant in-process LRU (or Redis when multi-process), keyed by (connection.schema_name, vocabulary_fingerprint) derived from server-side state, never from user input.
  • Cache invalidation correctness (R1 absorption A1, HIGH severity, verified): the existing _ontology_label_fingerprint SHA-256 pattern at customers/services/vocabulary_derivation.py:203-210 ONLY processes TenantOntology rows (archetype + display_label). It would structurally miss updates to four of the five new source_kind values in TenantVocabularyEntry. Sprint D MUST extend the fingerprint to ALSO include max(updated_at) from TenantVocabularyEntry per tenant — OR use a per-tenant DB trigger that increments a cache-version integer on any TenantVocabularyEntry write. Implementation detail at Sprint D's discretion; the architectural requirement is that the fingerprint cannot silently ignore four of five sources.
  • Cache memory footprint (R1 absorption B11): monitor LRU per-tenant pack size; cap at a fixed kilobyte budget (suggested 64 KB initial); spill to Redis with eviction logging when exceeded. Tenants with massive custom dictionaries must not OOM the in-process cache.
  • Cache scoping discipline: substrate functions accept no schema_name parameter; always derive from connection.schema_name. Stricter than the dbvisualizer/services/introspector.py:41-46 pattern (which accepts the parameter for legacy API compatibility but silently overrides). New code starts strict.
  • Django template tag {% voice 'wizard.stage3.match_card.header' tenant=tenant context=ctx %} and React useVocabulary(key, context) hook backed by a server-rendered JSON payload.
  • Mechanical replacement of hard-coded English in wizard / workspace / safety-floor / ambient-chat surfaces with the template tag. Largest single chunk of work.
  • HIGH_TIER_CONFIRMATION_TEMPLATES extended from one entry (reorganize_structure) to the full ADR-035 §4.1 4×3 canonical English templates; per-tenant specializations land later via admin_override or derivation_seed rows. (R1 absorption B9): shipping generic English ({records} → "records") as the canonical baseline VIOLATES ADR-035 §4.1's "use researcher domain vocabulary" rule and risks approval fatigue if researchers see generic phrasing before Phase 5 populates domain-specific terms. Sprint D therefore SHIPS the canonical English baseline, but Phase 5 (AI-assisted vocabulary proposal at tenant bootstrap) is named here as an explicit prerequisite to the high-tier safety floor going live for any new tenant. Until Phase 5 ships, the high-tier safety floor surface gates on the tenant having admin_override or derivation_seed rows populated for the four confirmation templates — render falls back to canonical only as fail-safe, with telemetry marking each fallback for ADR-014-α auditability.
  • tests/unit/test_proposal_prompt.py Layer 1 conversion from denylist (_assert_no_bad_tokens) to structural allowlist (_assert_no_string_literals_outside_canonical_registry). Layer 2 runtime tests still verify rendered prompts don't carry tenant slang.
  • Phase 3 chat shim: optional pre-Stage-1 conversational surface backed by data_import/services/ambient_chat.py bounded-context envelope + _guarded_action_intent mutation-blocking. Output is open-shape JSON persisted on MappingProject.wizard_answers. Skippable with one click. AI-self-flagged-low-confidence offers to skip. Telemetry instruments skip-rate and downstream match-quality delta from day one.
  • Phase 3 atomic ImportContext write (R1 absorption B2): ImportContext is persisted atomically — only committed on user-confirmed conversation conclusion. AI token budget exhaustion mid-conversation discards the partial JSON entirely; a half-populated ImportContext must NEVER reach downstream matching priors. Wrap the write in a transaction; budget exhaustion path rolls back and surfaces a UI retry.
  • Phase 3 control-cohort isolation (R1 absorption A4): Phase 3 measurement requires fresh researcher cohorts. Researchers who completed the baseline human import test (per docs/runbooks/adr037-phase-a1-import-test.md empirical floor) are EXCLUDED from the Phase 3 measurement cohort — they already know platform-canonical terminology and their confusion rates would be artificially suppressed, contaminating the with-chat vs without-chat quality delta. Cohort assignment is enforced at telemetry-tag time, not at researcher self-selection.
  • LLM injection telemetry: every LLM call that consumes the compiled vocabulary pack is logged via the existing ADR-016 §2 telemetry surface; injection_classifier_verdict is captured. Entries flagged confirmed_injection are quarantined per ADR-016 §6.3.
  • Synchronous classifier at write time (R1 absorption B7): the structural-allowlist conversion of KNOWN_BAD_TOKENS closes the cross-tenant priming gap, but admin-uploaded derivation_seed rows containing adversarial strings would be waved through (they're in the tenant's own registry by definition). Sprint D therefore runs injection_classifier_verdict SYNCHRONOUSLY at derivation_seed and admin_override write time — not only at downstream LLM consumption. Catch adversarial uploads at ingestion. Flagged entries are quarantined and the writing user gets a UI rejection rather than a silent acceptance that pollutes downstream prompts.
  • source_provenance closed-schema enforcement: model-level validation rejects payload keys outside {import_template_id, harvested_at_day, harvest_round, ai_suggestion_id}. Day-granularity timestamps only (HIPAA Safe Harbor / Common Rule convention). No raw user identifiers; if needed, pseudonymised via ADR-016 §3 HMAC-with-per-tenant-key. (R1 absorption B8): ai_suggestion_id is itself stored as the HMAC-with-per-tenant-key hash of the underlying suggestion-row ID, not the raw ID. Without this, a quarantine-bucket inspector could chain ai_suggestion_id → raw telemetry row → PII-bearing prompt and bridge over the privacy moat. Hashing the ID severs that chain cryptographically while preserving provenance traceability internally (platform staff with the per-tenant key can reverse-resolve for audit per ADR-016 §8).

Phase 2 — Data-derived lane at Stage 3 (own sprint)​

Stage 3 matching review card extended to render researcher's authored column header (already available on ColumnCandidate.column_name per epistemic/services/parser/types.py:148-188) alongside platform-neutral label. Standards-mapped lane added where applicable. New TenantVocabularyEntry rows with source_kind='data_derived' written at import-apply time, scoped by archetype_scope / slot_scope to the matched destination.

Deduplication threshold (R1 absorption B4): a data_derived row is NOT written for every matched column. Two write conditions are required: (a) the same header (case- and whitespace-normalised) appears across N distinct import sessions for this tenant (default N=2), OR (b) the researcher explicitly corrects the AI-suggested mapping during matching review (signal that they have an intentional preferred term). Without this, header typo variation (date_one / date_final / date_v3 / dat_one) explodes the per-tenant pack and clutters the multi-lane UI with low-signal noise. Threshold N is per-tenant-configurable for future tuning; default 2 keeps the bar low without admitting one-off typos.

Phase 5 — AI-assisted vocabulary proposal at tenant bootstrap (own spec)​

Per-tenant ai_reviewed vocabulary rows are populated through an AI-assisted proposal mechanism. The AI proposes; the admin accepts, rejects, or edits-then-accepts. Accepted proposals land as source_kind='ai_reviewed' rows on TenantVocabularyEntry; rejected proposals leave no substrate residue. Composes on Phase 1 substrate. Inherits ADR-014-α §1 bounded-agency.

Amendment 2026-05-26 — The original spec (Spec 0029) framed this as "extending the Phase 3 chat mechanism" into a first-admin-login chat surface with a 30-50 proposal review batch. Two architectural changes after the original Phase 5 design — R3 absorption softening B9 to observational-only (commit f05f8b53), and substrate-adapts-without-override via _fallback_bundle_voice (partner_model 2026-05-25) — dissolved the pressure for upfront-batch ceremony. The surface mechanism is superseded by a JIT redesign at docs/superpowers/plans/2026-05-26_phase5-vocabulary-jit-redesign.md: vocabulary proposals ride the Spec 0030 Phase 6.B {% tips_for %} tip-family machinery (PR #424) as a new tip family vocabulary_proposal, triggered during the import wizard when noun-signal mismatch is strong, at most 1-3 proposals per session. The bounded-agency commitment, the substrate-priority-chain composition, and the ai_reviewed / rejected provenance shape are unchanged.

Phase 6 — Tip / recommendation engine (own spec)​

Surface efficiency / standardization / improvement tips during import and during workspace work. Consumes vocabulary substrate for native phrasing AND data shape for actual recommendations. Telemetry substrate (DecisionEvent, recommendation_reason_code, PlatformRecommenderMetrics) already exists for measuring tip quality.

Open questions (soft spots — pending resolution before or alongside Phase 1)​

Q1 — Chat-transcript retention policy — RESOLVED by sibling ADR-045 (drafted 2026-05-24)​

Phase 3 (and ambient chat in general) capture free-form researcher text. ADR-016 explicitly scoped to three signal classes (LLM-call / search-query / ingestion-run) and excluded chat. ADR-044 surfaced this gap; ADR-045 (Chat-transcript retention regime) fills it with a four-tier regime under ADR-014-α bounded-agency. Phase 3 ships under ADR-045's extract_only tier: raw transcript bytes discarded at session end; ImportContext extracted to MappingProject.wizard_answers under that JSONField's own retention; no DPIA delta needed (extract_only is at the floor for raw-byte retention). Future chat surfaces (Spec 0020 v1.2 §10.2 Wave 2, future agent-resolver-epic) pick their tier per ADR-045 §1.

Q2 — ImportContext storage shape​

Phase 1 stores on MappingProject.wizard_answers (existing JSONField). If Phase 5's tenant-bootstrap-level priors prove distinct in shape, promote to first-class model later. Soft spot: wizard_answers has no retention policy today either — its conservative interim policy in Phase 1 inherits from Q1.

Q3 — data_derived row write timing in Phase 2 — RESOLVED by R1 absorption B4​

A data_derived row is written only when: (a) the same researcher header appears across N distinct import sessions for this tenant (default N=2), OR (b) the researcher explicitly corrects an AI-suggested mapping during matching review. Headers matching the canonical slot name (name → name) are skipped entirely; same-as-canonical contributes no signal. Threshold N is per-tenant-configurable. See Phase 2 implementation notes above for full deduplication design.

Q4 — Standards-mapped vocabulary's physical home​

Phase 1 schema accommodates standards_mapped rows on TenantVocabularyEntry with structured_payload carrying standards URI + version. Soft spot: standards mappings have own structure (URI, source standard, version, mapping quality) that may want first-class columns in Phase 4 or a follow-up. Phases 1-3 do not depend on the answer.

Q5 — Workspace surfaces post-import: header preservation — RESOLVED by R1 absorption A2​

The original Q5 resolution proposed a new source_alias field on TenantArchetypeFormConfig. R1 absorption A2 caught the collision: that model is mid-rename by ADR-042 (in flight). The corrected resolution uses the substrate that ADR-044 already ships — data_derived rows in TenantVocabularyEntry scoped by archetype_scope + slot_scope. At import-apply time, the matched ColumnCandidate.column_name becomes a data_derived row keyed at workspace.row_drawer.title (or the relevant workspace surface), scoped to the destination archetype + slot. The workspace useVocabulary('workspace.row_drawer.title', {slot: <slot_name>}) then resolves to the header at render time. No TenantArchetypeFormConfig field needed; no ADR-042 collision. Same surface area as Phase 2's deduplication-threshold work.

Q6 — Sprint D de-scope tolerance — RESOLVED twice (R1 A3 descope, then R2 ratification re-undoing the descope after calibration recompute)​

R1 absorption A3 caught the scope/timeline mismatch under the believed 7-12 day Sprint D scope: tasks multiplied 4×, blast radius expanded across the GraphQL layer + 4 UI surface families + audit rules + telemetry, timeline only tripled. R1 promoted descope to MVP-default-of-done: ship workspace + ambient-chat, defer wizard chrome + safety-floor to Sprint E.

R2 ratification (2026-05-25, same day): same-day calibration recompute showed Sprint D MVP is actually ~12-13 agent-hours core + 2-3 verification = ~14-16 hours total = ~2 session-days, NOT multiple weeks. The split-brain risk that motivated R1's descope evaporates at that scope. R2 reverts the descope: all four surfaces ship in Sprint D MVP. The B9 Phase 5 gate (originally a scope-deferral mechanism in R1) moves to its more correct architectural shape: a runtime gate inside D.3.10 — the safety-floor surface checks for derivation_seed or admin_override rows in TenantVocabularyEntry for the tenant before going live, suppressing or warning rather than rendering generic English. This honors B9's intent (no generic-English approval fatigue per ADR-035 §4.1) without requiring Phase 5 to ship before Sprint D.
