Atlomy Tenant Restore Specification

Purpose​

This document defines what is required to fully restore the atlomy_atlas tenant tables into the current multi-tenant Django structure, using existing import tooling where possible and identifying the missing pieces that must be implemented.

This document is intentionally written from two viewpoints that must be kept separate:

  • the intended platform architecture
  • the implementation maturity currently present in this repository

The goal is to answer two questions:

  1. What is needed to restore Atlomy tenant content into the current schema?
  2. Can this be done with the current import stack: retired external no-code surface import wizard, AI-assisted field mapping, Data Wizard, and legacy CSV/Coda commands?

Executive Summary​

The intended architecture is generic, archetype-driven, and tenant-flexible.

The core product premise is not "write bespoke import code for every research domain." The core premise is:

  • ingest heterogeneous source data such as CSV and Excel
  • stage and normalize it through a generic import layer
  • use AI-assisted field mapping and archetype detection to fit data into standard platform objects
  • allow different tenants to instantiate different knowledge environments from a shared architectural core

That premise is visible in the retired external no-code surface-first import design, AI schema adaptation services, import jobs, and generic sync model.

However, full Atlomy restoration is still not currently achievable end-to-end without implementation work.

The right interpretation is not that the generic architecture is wrong. The right interpretation is that the generic architecture is only partially realized in the codebase today.

Partial restoration is possible with the tooling that exists now, but full Atlomy tenant restoration is not currently achievable end-to-end without additional implementation.

What works today:

  • The legacy add_data command can still read from Coda or from the legacy CSV bundle.
  • The legacy add_lemmas command can still sync Elasticsearch lemma documents into atlomyapp.Lemma.
  • Direct bibliography import into atlomyapp.Reference exists.
  • retired external no-code surface supports CSV upload, AI-assisted field mapping, and generic retired external no-code surface-to-Django synchronization.
  • Data Wizard is installed and usable for registered serializers.

What does not work today:

  • The current tenant tables are empty.
  • The current external noco_atlomy_atlas source views are also empty.
  • Elasticsearch is currently red, so the old add_data -> add_lemmas flow is not operational.
  • Data Wizard currently only supports Lemma and Reference.
  • The generic retired external no-code surface sync path assumes retired external no-code surface_id exists on Django models, but core atlomyapp models do not have that field.
  • There is no implemented importer for Page, Model, ModelMapping, ModelLemma, TenantOntology, or most of the current relational structures.

Conclusion:

  • The current tooling is suitable as a foundation and staging layer.
  • The missing work is not a rejection of the generic architecture. It is the work required to complete it.
  • A full restore requires a generic restore workflow that is archetype-aware and mapping-driven, with only limited model-specific adapters where the current domain truly cannot be expressed through the generic layer.

Architectural Premise​

The intended newer import stack is based on the following architectural principles.

Principle 1: retired external no-code surface-first staging​

Source data should enter the platform through a generic import surface and become visible in retired external no-code surface first.

Conceptual flow:

  • CSV/Excel or future database sources
  • retired external no-code surface import and field mapping
  • retired external no-code surface as source of truth for imported rows
  • sync pipeline into tenant Django models

Principle 2: Archetype-driven structure​

The system should not require domain-specific code for every research project.

Instead it should rely on:

  • archetype detection
  • AI-assisted field mapping
  • schema suggestions
  • reusable import jobs
  • tenant-specific configuration

This is the mechanism by which a platform can support multiple knowledge environments while remaining standardized.

Principle 3: Flexible tenant realization over a shared core​

Tenants may differ in:

  • which archetypal objects they emphasize
  • which labels they use
  • which subsets of the model they populate
  • which external sources they ingest

But they should still fit a shared platform core rather than requiring one-off import code for each research domain.

Principle 4: Bespoke code should be exceptional, not normal​

If tenant restoration requires hard-coded per-field logic for every project, then the platform premise has failed.

Where specialized logic is needed, it should ideally appear only as:

  • source-specific adapters
  • archetype-specific transformers
  • configuration-driven mapping rules

and not as a new import pipeline per tenant.

Scope​

This spec covers restoration of tenant content for the atlomy_atlas schema in PostgreSQL.

In scope:

  • Lemma
  • Reference
  • Page
  • Model
  • ModelMapping
  • ModelLemma
  • TenantOntology
  • Configuration
  • Event
  • import-job and restore orchestration

Out of scope:

  • frontend rendering work
  • search relevance tuning
  • tenant branding work
  • production deployment migration planning

Current State​

Tenant data status​

Current observed state:

  • atlomy_atlas tenant content tables are empty.
  • visionis tenant content tables are empty.
  • noco_atlomy_atlas content views are empty.
  • retired external no-code surface metadata tables and bases exist, but source content is not present.

Existing import mechanisms​

1. Legacy lemma-centric pipeline​

Files:

  • atlomyapp/management/commands/add_data.py
  • atlomyapp/management/commands/add_lemmas.py
  • config_data.json
  • atlomy_csv/*.csv

Behavior:

  • add_data reads Coda or CSV flat files.
  • It builds one nested Elasticsearch document per lemma in lemma_index.
  • add_lemmas reads from Elasticsearch and populates atlomyapp.Lemma.

Important limitation:

  • This is not a full relational restore pipeline.
  • It is a lemma/search pipeline with a narrow DB sync step.

2. Direct bibliography import​

File:

  • atlomyapp/management/commands/import_atlomy_bibliography.py

Behavior:

  • Imports bibliography rows from modern_editions_bibliography.csv into atlomyapp.Reference for the atlomy_atlas tenant.

Important limitation:

  • This only covers bibliographic Reference records.

3. Data Wizard​

Files:

  • data_import/wizard.py
  • data_import/admin.py

Behavior:

  • Data Wizard serializers are currently registered only for Lemma and Reference.
  • The admin flow describes upload -> Data Wizard mapping -> run execution.

Important limitation:

  • No serializers currently exist for Page, Model, ModelMapping, ModelLemma, TenantOntology, or Event.

4. retired external no-code surface import + sync​

Files:

  • retired external no-code surface/admin.py
  • retired external no-code surface/models.py
  • retired external no-code surface/services/sync.py
  • data_import/services/retired external no-code surface_importer.py

Behavior:

  • Upload CSV/Excel into retired external no-code surface tables.
  • AI suggests column mappings.
  • Imports rows into retired external no-code surface.
  • Generic sync can push retired external no-code surface rows into Django models.

Important limitation:

  • Generic sync uses update_or_create(retired external no-code surface_id=...).
  • Core atlomyapp models do not have retired external no-code surface_id fields.
  • Therefore the generic sync path is not currently usable for Atlomy core models without schema or adapter changes.

Important interpretation:

  • This is an implementation gap in the generic architecture.
  • It does not mean the architecture is conceptually tenant-specific or bespoke-by-design.

Legacy Source Model​

The old Atlomy data model is flat-file and lemma-centric.

Primary source files​

  • atlomy_csv/lemma.csv
  • atlomy_csv/ancient_words.csv
  • atlomy_csv/ancient_words_early_edition_full_reference.csv
  • atlomy_csv/ancient_words_modern_edition_full_reference.csv
  • atlomy_csv/modern_terms.csv
  • atlomy_csv/modern_editions_bibliography.csv
  • atlomy_csv/early_editions_bibliography.csv
  • atlomy_csv/abbreviated_references.csv

Join logic used in v1​

The key joins encoded in add_data.py are:

  • lemma.csv["Lemma Word"] is the primary lemma key.
  • lemma.csv["Modern Terms"] links to modern_terms.csv["Term"].
  • ancient_words.csv["Lemma"] links usage rows back to lemmas.
  • ancient_words*.csv join by Modern Reference Summary / Early Reference Summary.
  • bibliography tables join by Row ID.
  • abbreviated references join by Reference - Abbreviated Row ID.

Practical meaning​

The old files are strong enough to reconstruct lemma-centric content and bibliographic context.

They are not by themselves a complete representation of the current relational domain for:

  • page CMS content
  • 3D model catalog
  • model hierarchies
  • lemma-to-model links
  • tenant ontology configuration

Current Target Model Coverage​

This section describes current restoration feasibility for Atlomy specifically.

It should not be read as a claim that the platform must permanently rely on per-model bespoke import logic. In the intended design, many of these mappings should eventually be resolved through generic import layers plus archetype-aware configuration.

Models that can be restored with modest work​

Lemma​

Target model fields of primary importance:

  • lemma
  • morph_1
  • morph_2
  • morph_3
  • lemma_full
  • author
  • long_description
  • short_description
  • treatise
  • translation
  • transliteration
  • slug
  • is_active

Source readiness:

  • Strong. Legacy CSV and Coda structure clearly support this.

Reference​

Target model fields:

  • reference
  • title
  • author
  • year
  • optional model_mapping

Source readiness:

  • Strong for bibliography.
  • Weak for full relational linkage to current app semantics.

Event​

Target model fields:

  • title
  • description
  • start_date
  • end_date
  • temporal_sort_key
  • temporal_metadata
  • hijri_date
  • event_type
  • date_display
  • coordinates

Source readiness:

  • Weak. No legacy flat-file import path currently exists.
  • Existing repo only includes hardcoded seeding for Visionis.

Models that require new import design​

Page​

Current model:

  • name
  • description
  • ancient_author
  • author_name
  • treatise_name
  • page_type

Gap:

  • No direct legacy source file currently mapped to this structure.
  • These may need to be derived from authors/treatises in the legacy data or restored from a separate source not yet identified.

Model​

Current model:

  • 3D metadata fields such as name, url, home_image_url, detail_image_url, search_image_url, description, ancient_author, authors, show_in_home

Gap:

  • No known CSV/Coda mapping in the current repo.
  • Likely admin-curated or asset-driven.

ModelMapping​

Current model:

  • parent_model
  • sub_model
  • type

Gap:

  • No legacy structured source currently identified.

ModelLemma​

Current model:

  • model
  • lemma
  • accuracy
  • author_observation

Gap:

  • No legacy structured source currently identified.

TenantOntology​

Current model:

  • archetype
  • display_label

Gap:

  • Tenant-specific configuration, not part of old CSV bundle.

Configuration​

Current model:

  • operational configuration only, especially run_script behavior for legacy commands

Gap:

  • Not a content restore source.

Can This Be Done With Current Tooling?​

Answer​

Partially.

More precisely:

  • the current tooling expresses the intended generic architecture
  • but the current implementation does not yet complete that architecture for all Atlomy target models

What current tooling can do now​

Option A: Legacy CSV/Coda -> Elasticsearch -> Lemma​

Use when:

  • Elasticsearch is healthy.
  • Goal is to restore lemma records fast using the historical logic.

Current blockers:

  • Elasticsearch is red.
  • This path only reliably restores Lemma.

Option B: Data Wizard​

Use when:

  • Target model has a serializer registered.
  • Data is already shaped close to target rows.

Current blockers:

  • Only Lemma and Reference serializers exist.
  • No registered import targets for the rest of the Atlomy relational tables.

Option C: retired external no-code surface Import Wizard + AI field mapping​

Use when:

  • CSV needs staging, inspection, or collaborative cleanup.
  • AI-assisted column mapping is useful.

Current blockers:

  • Generic retired external no-code surface sync does not fit current core models because they lack retired external no-code surface_id.
  • retired external no-code surface is useful as a staging area, not a full restore solution yet.

Practical conclusion​

You cannot fully restore Atlomy tenant content today using only the currently shipped admin tooling.

You can use the current tooling as building blocks for the intended generic restore workflow, but the Atlomy restore itself still needs completion work.

Recommended Restore Strategy​

Strategy choice​

Preferred approach:

  • complete the generic source -> retired external no-code surface -> sync/adaptation -> tenant Django architecture where possible
  • add a direct restore fallback path only where the current generic layer is not yet expressive enough

Do not make Elasticsearch the primary restore dependency.

Why:

  • The current goal is relational database restoration, not search indexing.
  • Search can be rebuilt after DB content is restored.
  • The old ES-first design only covers part of the domain.

Recommended architecture​

Phase 1: Staging and source normalization​

Inputs:

  • Coda direct export or API pull
  • existing atlomy_csv/*.csv

Output:

  • normalized in-memory or staged data objects

Requirements:

  • preserve old join semantics from add_data.py
  • centralize source parsing in reusable services
  • support CSV and Coda as interchangeable sources
  • treat Atlomy as one tenant realization of a broader import architecture, not as a one-off importer

Implementation target:

  • new service layer under atlomyapp/services/restore/ or similar

Phase 2: Direct model restore adapters​

Implement archetype-aware restore adapters with model bindings for:

  • Lemma
  • Reference
  • Page
  • Event
  • optional placeholders for Model, ModelMapping, ModelLemma, TenantOntology

Each adapter should:

  • validate required source fields
  • support dry-run mode
  • upsert by stable business key
  • record restore statistics
  • produce row-level warnings

Guidance:

  • these adapters should be generic by archetype or import pattern where possible
  • avoid encoding Atlomy-only field logic unless the source semantics are truly unique

Phase 3: Orchestrator command​

Add a new management command, for example:

python manage.py restore_atlomy_tenant --schema atlomy_atlas --source csv --config config_data.json --dry-run

Suggested capabilities:

  • --schema
  • --source csv|coda
  • --dry-run
  • --reset-target for destructive reloads
  • --only lemma,reference,page,...
  • --report-path

Phase 4: Admin tooling integration​

Integrate with existing tooling as follows:

  • Data Wizard remains useful for direct Lemma and Reference imports.
  • retired external no-code surface import wizard remains useful for source staging, column inspection, and AI mapping.
  • The long-term target should be a mostly generic retired external no-code surface-first restore path.
  • The immediate Atlomy restore may still require a dedicated orchestration command while the generic sync layer is completed.

Phase 5: Search rebuild​

After database restoration:

  • rebuild Elasticsearch from restored DB data, or
  • temporarily keep the legacy add_data path only as a search bootstrap if required

Required Implementation Changes​

Required for minimum viable full restore​

These items should be understood as work needed to complete the generic architecture, not as a proposal to abandon it in favor of tenant-specific code.

1. Create a new restore service layer​

Needed because:

  • current logic is trapped inside add_data.py
  • current logic outputs Elasticsearch documents instead of relational objects

Deliverables:

  • source readers
  • join assembler
  • archetype-aware upsert adapters
  • restore report generator

2. Add direct Lemma restore without Elasticsearch dependency​

Needed because:

  • current lemma restoration depends on Elasticsearch health
  • DB restore should not depend on a search cluster

Deliverables:

  • direct Lemma upsert adapter from normalized source objects

Long-term alignment:

  • this should ultimately also be expressible through the generic import architecture, not only through a dedicated Atlomy command

3. Add Reference restore expansion​

Needed because:

  • current reference importer only covers bibliography CSV
  • full reference semantics may need richer source fusion

Deliverables:

  • reference loader that handles bibliography plus derived reference strings when needed

4. Design and implement Page derivation rules​

Needed because:

  • no page import currently exists

Deliverables:

  • explicit rule set for generating author and treatise pages from legacy source data, or
  • discovery of a better source of truth if one exists outside the current CSV bundle

5. Decide strategy for 3D model tables​

Needed because:

  • Model, ModelMapping, and ModelLemma have no verified legacy source in the current repo

Options:

  • locate old DB dump or Coda tables not currently included
  • maintain manual restore/admin seeding for these models
  • create separate import sheets for model metadata and relationships

6. Extend Data Wizard if desired​

Needed if the team wants admin-native restore paths.

Deliverables:

  • serializers for Page, Event, possibly Model
  • import validation rules
  • documented import templates

Better target state:

  • Data Wizard and retired external no-code surface import should converge on a shared mapping and transformation model rather than remaining separate import worlds

7. Upgrade retired external no-code surface sync if desired​

Needed only if the team wants retired external no-code surface to become the central restore/staging hub.

Two viable paths:

  • add retired external no-code surface_id to target models where appropriate
  • or change sync mapping logic to use configurable business keys rather than hardcoded retired external no-code surface_id

Recommendation:

  • this is strategically important because it is the main path that makes the architecture truly generic
  • if delayed, Atlomy restore can still proceed through a dedicated orchestration layer, but that should be treated as transitional rather than the final architecture

Proposed Delivery Plan​

Milestone 1: Recover lemma and reference content​

Deliver:

  • direct Lemma restore command from CSV/Coda
  • direct Reference restore command from CSV/Coda
  • dry-run + reporting

Success criteria:

  • atlomy_atlas.Lemma populated
  • atlomy_atlas.Reference populated
  • no Elasticsearch dependency required

Milestone 2: Restore page-like editorial content​

Deliver:

  • Page generation or import strategy
  • explicit rules for author/treatise pages

Success criteria:

  • Atlomy tenant admin contains usable editorial pages

Milestone 3: Resolve model/relationship domain​

Deliver:

  • source-of-truth decision for Model, ModelMapping, ModelLemma
  • either importer implementation or documented manual seeding flow

Success criteria:

  • 3D/admin features have a reproducible restore path

Milestone 4: Optional admin-native workflow​

Deliver:

  • extended Data Wizard serializers
  • restore templates
  • optional retired external no-code surface business-key sync

Success criteria:

  • non-developer operators can perform standard restore/import tasks through admin tooling

Acceptance Criteria​

The restore solution is considered complete when:

  • Atlomy tenant content can be restored from CSV or Coda into the current tenant schema.
  • Lemmas no longer require Elasticsearch as an intermediate storage layer.
  • Restore can run in dry-run and execution modes.
  • Restore emits a machine-readable and human-readable report.
  • Restore is idempotent for repeated runs.
  • Restore supports partial model scopes.
  • All implemented model import rules are documented.
  • Search rebuild is separated from DB restoration.

Recommendation​

Best path for this repository:

  • Use the old add_data.py logic as the canonical reference for field semantics and CSV joins.
  • Do not use the old add_data -> add_lemmas flow as the long-term restore mechanism.
  • Treat the retired external no-code surface-first, AI-assisted architecture as the correct long-term direction.
  • Complete the missing generic pieces in that architecture.
  • Build a transitional restore command for Atlomy only where needed to bridge current implementation gaps.
  • Use existing tooling selectively:
    • Data Wizard for narrow model imports
    • retired external no-code surface import wizard for staging and AI field mapping
    • and evolve them toward becoming the primary full-restore engine

This gives the team a restore workflow that matches the current relational architecture while remaining faithful to the product premise: generic knowledge-environment creation with standardized but flexible import mechanics rather than tenant-by-tenant bespoke coding.
