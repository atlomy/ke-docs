helpKey contract — engineering spec

Audience: Developer Last aligned with platform state: 2026-05-25 Platform version: V2 (pre-1.0)

Purpose​

This is the engineering spec for the in-product help linkage between platform documentation and the running KE application. It implements the architectural amendment from R1 absorption (2026-05-25) — see ../../devlogs/2026_w22/2026-05-25_1900_R1-docs-strategy-absorption.md §A3 — by routing every help-link request through the existing voice substrate (ADR-044), so tenants who have substituted vocabulary (e.g. "K-anonymity" → "public-disclosure threshold") see their own term in the help drawer rather than the platform default.

Read this when you're about to add a ? help icon to a SPA component or Django admin template, when you need to add a new help destination to the docs, or when reviewing the build's help-link integrity report.

Features​

The contract has five pieces:

  • Stable helpKey IDs in docs frontmatter · Source: this spec · Maturity: Validated · Limit: must be platform-canonical, never tenant-specific. The full ID is a dotted namespace path: <surface>.<sub-surface>.<concept>.
  • help-manifest.json built at docs-site build · Source: docs build pipeline · Maturity: Validated · Limit: regenerated on every doc deploy; consumers cache at most one minor version.
  • React <HelpRef helpKey="..." /> component · Source: spa/src/components/HelpRef/ (new; ~80 LOC) · Maturity: Validated · Limit: only consumable inside a tenant context (uses useTenantContext and useVocabulary).
  • Django {% help_ref "..." %} templatetag · Source: atlomyapp/templatetags/help_ref.py (new; ~40 LOC) · Maturity: Validated · Limit: tenant context required.
  • CI gate on missing keys · Source: GitHub Action workflow (new) · Maturity: Validated · Limit: fails the build when SPA / admin templates reference a helpKey not present in the latest published help-manifest.json.

Usability — how you wire it​

Adding a helpKey to a docs page​

In any audience-facing doc (docs/users/, docs/tenant_admin/, docs/superadmin/, docs/standards/), add a help_keys: array to frontmatter naming every concept on that page that the in-product help drawer can deep-link to. Anchor IDs follow the same dotted namespace as the helpKey.

---
title: "Voice and vocabulary"
audience: tenant_admin
diataxis_mode: how-to
help_keys:
  - tenant_admin.voice.entry_create   # → #tenant_admin.voice.entry_create
  - tenant_admin.voice.derivation
  - tenant_admin.voice.safety_floor_gate
---

## What this is for

The Voice & Vocabulary surface lets you control...

## Creating a vocabulary entry \{#tenant_admin.voice.entry_create}

...

Building the manifest​

At docs-site build, walk every page; for each help_keys[] entry, emit one row to help-manifest.json:

{
  "version": "2026.05.25",
  "tenant_admin.voice.entry_create": {
    "url": "https://docs.ke.example/tenant-admin/features/voice-and-vocabulary#tenant_admin.voice.entry_create",
    "title_key": "help_titles.tenant_admin.voice.entry_create",
    "summary_key": "help_summaries.tenant_admin.voice.entry_create"
  },
  ...
}

Note: title_key and summary_key are NOT inline strings — they are vocabulary keys for the next step.

Resolving against the voice substrate​

The React <HelpRef /> component calls useVocabulary(title_key, context) from ADR-044's hook to render the title in the tenant's voice. Same for the summary preview. The destination URL is unchanged (platform-canonical), but everything displayed to the user is voice-substituted.

// spa/src/components/HelpRef/HelpRef.tsx
import { useVocabulary } from '@/hooks/useVocabulary';
import helpManifest from '@/generated/help-manifest.json';

export function HelpRef({ helpKey, surface }: { helpKey: string; surface?: string }) {
  const entry = helpManifest[helpKey];
  if (!entry) {
    // CI gate would have caught this; this is the runtime safety net
    console.warn(`HelpRef: missing helpKey ${helpKey}`);
    return null;
  }
  const title = useVocabulary(entry.title_key, { surface });
  const summary = useVocabulary(entry.summary_key, { surface });
  return (
    <a
      className="ke-help-ref"
      href={entry.url}
      target="_blank"
      rel="noopener noreferrer"
      aria-label={title}
    >
      <HelpIcon />
      <span className="ke-help-ref__tooltip">{title} — {summary}</span>
    </a>
  );
}

Django side​

# atlomyapp/templatetags/help_ref.py
from django import template
from atlomyapp.help_manifest import HELP_MANIFEST  # generated at deploy time
from customers.services.vocabulary_derivation import derive

register = template.Library()

@register.simple_tag(takes_context=True)
def help_ref(context, help_key: str, surface: str = "admin"):
    tenant = context["request"].tenant
    entry = HELP_MANIFEST.get(help_key)
    if not entry:
        return ""  # CI gate catches; runtime safety
    title = derive(tenant, entry["title_key"], {"surface": surface})
    summary = derive(tenant, entry["summary_key"], {"surface": surface})
    return template.utils.format_html(
        '<a class="ke-help-ref" href="{}" target="_blank" rel="noopener noreferrer" aria-label="{}"><span class="ke-help-icon">?</span><span class="ke-help-ref__tooltip">{} — {}</span></a>',
        entry["url"], title, title, summary
    )

CI gate​

A new GitHub Action workflow (.github/workflows/help-key-integrity.yml) runs on every PR:

name: helpKey integrity
on: pull_request
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: python scripts/check_help_keys.py

The script:

  1. Fetches the latest published help-manifest.json (from the docs-site deploy).
  2. Greps the SPA + Django for <HelpRef helpKey="..." /> and {% help_ref "..." %}.
  3. For each referenced key, confirms presence in the manifest.
  4. Fails the PR if any key is missing.

Estimated: ~80 lines Python.

<HelpRef /> renders nothing in the SPA.The helpKey isn't in help-manifest.json (either docs didn't deploy after the key was added, or the key has a typo).Verify the key exists in spa/src/generated/help-manifest.json. If not, check that the docs page declaring it deployed successfully.Docs deploy lane; CI gate check_help_keys.py should have flagged this before merge.
Tooltip shows English platform terms instead of the tenant's vocabulary.useVocabulary(title_key, context) isn't being called — either the component is rendering outside a tenant context, or the title_key isn't declared in TenantVocabularyEntry.Check the tenant context wraps the component; check TenantVocabularyEntry has rows for the title/summary keys.ADR-044 voice substrate, customers/services/vocabulary_derivation.py.
CI gate fails with "manifest version mismatch".The SPA/admin code references a key from a newer docs deploy than the manifest the CI fetched.Pin the SPA's manifest fetch to a specific version OR retry the CI gate after docs deploy completes.Docs deploy lane; help-manifest versioning policy.

Implementation order (when the work begins)​

  1. Decide on the docs-site SSG (currently in 2-week empirical evaluation against Mintlify per 2026-05-25 user decision).
  2. Add help_keys frontmatter to ~10 representative docs across the four audience trees as a smoke test (no SPA wiring yet).
  3. Build help-manifest.json emitter into the chosen SSG's build pipeline.
  4. Land scripts/check_help_keys.py + GitHub Action workflow against a deliberately empty SPA/admin grep result (passes trivially; ready to catch the first real reference).
  5. Land spa/src/components/HelpRef/ + atlomyapp/templatetags/help_ref.py.
  6. Wire the first real <HelpRef /> into TipsPanel.tsx (small, contained, exercises the full path).
  7. Wire the first {% help_ref %} into the Django permissions admin page.
  8. Roll out across other surfaces as the docs grow help_keys coverage.

Total estimated work: ~3-5 focused days once the SSG decision lands.

Out of scope for this spec​

  • The docs-site SSG choice (separate decision; see strategy plan).
  • AI-generated help content from code diffs (Tier-3; would integrate with Code-to-Docs or Mintlify Agent).
  • Embedded AI assistant (Kapa.ai / Inkeep — separate evaluation; the helpKey contract works alongside or without one).
  • Per-tenant doc-content forking (out of scope; tenants get vocabulary substitution, not docs-content substitution).
