Multilingual Data Import - Design Principles

Core Principle: Never Modify User Data​

Users intentionally input Greek, Arabic, Latin text because that's the correct scholarly form.
Automatic transliteration would corrupt their data.

What We Do​

✅ Language Detection (Metadata)​

  • Detect: Modern Greek, Ancient Greek, Latin, Arabic, English, German
  • Store language code as metadata: lemma_lang: 'grc'
  • Purpose: Filtering, categorization, UI hints

✅ UTF-8 Encoding​

  • Ensure all text is properly UTF-8 encoded
  • Handle different CSV encodings (UTF-8-BOM, Latin-1, etc.)
  • Purpose: Prevent encoding corruption

✅ Transliteration for Search (Elasticsearch ONLY)​

  • Provide utility: transliterate_for_search()
  • Called ONLY when indexing to Elasticsearch
  • Never modifies source data in retired external no-code surface/Django
  • Example: Makes "Φιλοσοφία" searchable via "philosophia"

What We DON'T Do​

❌ Automatic Transliteration​

  • Never auto-transliterate Greek → Latin
  • Never auto-transliterate Arabic → Latin
  • User's original text is sacred

❌ Data Transformation Without Consent​

  • No automatic field population
  • No silent data changes
  • User must explicitly request transliteration

Architecture​

CSV/Excel with Greek/Arabic
    ↓
Parse (UTF-8 ensure)
    ↓
Detect Language (metadata only)
    ↓
Store ORIGINAL in retired external no-code surface ← User data unchanged!
    ↓
Sync to Django (original preserved)
    ↓
If Elasticsearch indexing:
    ├─ Original text → main field
    └─ Transliteration → search field (separate)

Example​

Input CSV:

lemma,translation
Φιλοσοφία,Philosophy
فلسفة,Philosophy

Stored in retired external no-code surface:

{
  "lemma": "Φιλοσοφία",  // Original UNCHANGED
  "lemma_lang": "el",    // Metadata
  "translation": "Philosophy"
}

Elasticsearch Index:

{
  "lemma": "Φιλοσοφία",           // PRIMARY: Original for display & exact search
  "lemma_search": "philosophia",   // SECONDARY: Transliteration for fuzzy search
  "lemma_lang": "el"
}

Search Behavior:

  • Query "Φιλοσοφία" → Exact match on lemma field ✅
  • Query "philosophia" → Fuzzy match on lemma_search field ✅
  • Both return the same record with original Greek displayed

Critical Rules for Elasticsearch​

✅ Always Index Original Data​

  1. Primary field = Original language (Greek, Arabic, etc.)
  2. Purpose: Exact search, display, preservation
  3. Never replaced by transliteration

✅ Add Transliteration as Secondary​

  1. Secondary field = Latin transliteration (_search suffix)
  2. Purpose: Help users without Greek/Arabic keyboards
  3. Never replaces the primary field

❌ Never Do This​

// WRONG - Original data lost!
{
  "lemma": "philosophia"  // ❌ Transliteration replaced original
}

Elasticsearch Mapping Example​

{
  "mappings": {
    "properties": {
      "lemma": {
        "type": "text",
        "analyzer": "greek_analyzer",  // Preserves Greek text
        "fields": {
          "exact": {
            "type": "keyword"  // Exact Greek matching
          }
        }
      },
      "lemma_search": {
        "type": "text",
        "analyzer": "standard"  // Latin transliteration for accessibility
      },
      "lemma_lang": {
        "type": "keyword"  // Language code
      }
    }
  }
}

User Control​

If user wants transliteration in retired external no-code surface:

  1. They provide it in CSV: lemma,lemma_transliterated
  2. OR they use UI to manually add it
  3. OR they use admin action to bulk generate (with preview/approval)

Never automatic, always controlled!
