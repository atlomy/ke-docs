KE (Knowledge Environments) Canonical Architecture Vision

Separating Operational Truth from Epistemic Interpretation​

Note on naming: The platform is KE — Knowledge Environments. Atlomy Atlas is the original software the platform grew out of, now one tenant among others. The filename atlomy_canonical_architecture_vision.md is preserved for link stability; "Atlomy" persists as brand. Older prose below may still say "Atlomy" when referring to the platform — read in that historical context.

1. Executive Summary​

KE (Knowledge Environments) is evolving from a monolithic, admin-driven application (originally Atlomy Atlas) into a multi-tenant knowledge platform with explicit epistemic governance. This document defines the canonical architecture that underpins this evolution.

The core insight is simple but foundational:

Operational truth and epistemic interpretation are different concerns and must be embodied in different system layers.

Historically, Django Admin served as a temporary shell for both. As KE grows—introducing AI-in-the-loop workflows, multi-tenant ontologies, and researcher-facing experiences—this conflation has become a limiting factor.

This architecture formalizes the separation.

2. The Foundational Reframe​

The Problem We Were Solving (Incorrectly)​

"How do we add a better UI on top of Django and retired external no-code surface?"

The Problem We Are Actually Solving​

"How do we govern how knowledge is proposed, reviewed, approved, and explored—by humans and AI—without compromising system integrity?"

This is not a frontend migration. It is a conceptual unbundling.

3. The Two Worlds Model​

3.1 Operational Truth (System of Record)​

Purpose: Keep the platform safe, consistent, and auditable.

Characteristics:

  • Deterministic
  • Strongly governed
  • Low-frequency change
  • Infrastructure-facing

Responsibilities:

  • Tenant provisioning
  • User and permission management
  • Canonical schema
  • Data integrity
  • AI guardrails enforcement

Technology:

  • Django ORM
  • Django Admin (internal-only)
  • PostgreSQL (canonical schemas)

Audience: Platform operators, engineers

3.2 Epistemic Interpretation (System of Meaning)​

Purpose: Allow humans and AI to reason about, curate, and explore knowledge.

Characteristics:

  • Fluid
  • Contextual
  • Multi-ontology
  • High iteration

Responsibilities:

  • Knowledge curation
  • AI schema suggestions
  • Ontology navigation
  • Researcher workflows
  • Draft → Review → Approval lifecycle

Technology:

  • React SPA
  • GraphQL (reads)
  • REST (mutations & governance)
  • retired external no-code surface (authoring surface, optional)

Audience: Researchers, analysts, domain experts

4. Data Architecture: Hybrid Ontology (Canonical Decision)​

The Principle​

Tables define what can exist. JSON defines how it is expressed.

Why This Matters​

Pure relational models are too rigid for epistemic work. Pure JSON models collapse governance and meaning.

Atlomy adopts a hybrid ontology.

Canonical Schema Pattern​

epistemic_entities (
  id UUID PRIMARY KEY,
  tenant_id UUID NOT NULL,

  -- Stable epistemic primitives
  archetype VARCHAR(50) NOT NULL,
  canonical_type VARCHAR(50),

  -- Governance (queryable, auditable)
  status epistemic_status NOT NULL,
  confidence_score DECIMAL(3,2),
  created_by VARCHAR(100),
  approved_by VARCHAR(100),

  -- Flexible expression
  data JSONB NOT NULL,
  provenance JSONB,

  created_at TIMESTAMPTZ,
  modified_at TIMESTAMPTZ
);

Benefits​

  • Strong governance without migration paralysis
  • AI can propose structure safely
  • Tenant-specific expression without schema drift
  • Explainability preserved as a first-class concept

4.1 Tenant Realization Over Domain Uniformity​

This architecture does not assume that every tenant has the same scholarly primitives.

What stays shared:

  • governed entities
  • review and approval lifecycle
  • authoring and editing workflows
  • search and navigation patterns
  • frontend composition model
  • auditability and provenance

What may differ per tenant:

  • terminology
  • primary document types
  • object/media types
  • ontological emphasis
  • presentation modules and interaction patterns

Examples:

  • Atlomy may center its knowledge environment on lemmas, 3D anatomical models, corpus-edition references, author pages, and treatise pages.
  • Visionis may center its knowledge environment on terms, Qur'anic pages, 2D images, senses, commentarial material, and timeline-oriented or image-oriented exploration.

These are not contradictions in the platform model. They are different tenant realizations of the same governed epistemic architecture.

The canonical requirement is therefore not "make every tenant look like Atlomy." The canonical requirement is:

Give each tenant a structurally similar research environment for proposing, reviewing, editing, linking, and publishing knowledge, while allowing the domain objects and labels to differ.

That means Atlomy's Lemma, Model, ModelLemma, and Reference should be understood as one tenant-specific realization of broader platform capabilities, not as the permanent universal vocabulary of the platform.

5. API Architecture​

5.1 GraphQL as the Epistemic Contract​

GraphQL is the source of truth for epistemic reads.

Why:

  • Graph-shaped knowledge
  • Client-driven queries
  • Type-safe contracts
  • Self-documenting

The GraphQL schema is the interface. Django models are implementation details.

5.2 REST for Mutations and Governance​

REST endpoints remain authoritative for:

  • Approvals
  • Rejections
  • Status transitions
  • Audited writes

This cleanly separates:

  • Exploration (GraphQL)
  • Authority (REST)

6. Frontend Architecture​

Clean Separation of Interfaces​

  • admin.atlomy.org → Django Admin (internal ops)
  • app.atlomy.org → React SPA (epistemic platform)

No embedding. No hybrid shells. No CSS collisions.

Why This Is Canonical​

Epistemic workflows require:

  • Rich interaction
  • AI explainability
  • Side-by-side diffs
  • Visual graphs
  • Tenant-specific semantics

Django Admin is intentionally not designed for this.

The important nuance is that frontend similarity does not require frontend sameness.

Two tenants may share a recognizable interaction shape:

  • search or browse
  • entity detail view
  • linked evidence or occurrences
  • media/object viewer
  • configurable navigation

while differing in the specific modules they expose:

  • Atlomy: lemma page, 3D model page, corpus-reference occurrence list
  • Visionis: term page, image/page viewer, sense-oriented relations, timeline or manuscript-context modules

So the frontend architecture should be treated as a configurable epistemic shell with tenant-specific components and labels, not as a single hard-coded Atlomy experience copied everywhere.

7. AI Governance Principle (Non-Negotiable)​

AI may propose epistemic structure; humans approve; the system enforces.

This principle is enforced by architecture, not policy:

  • AI operates only in epistemic layers
  • Canonical schema cannot be mutated directly
  • All transitions are auditable

8. What This Architecture Explicitly Does NOT Do​

  • retired external no-code surface is not a governance layer
  • React is not allowed to bypass backend authority
  • Tenants cannot mutate canonical schema directly
  • Epistemic databases are not sources for analytics or ES

9. Strategic Outcomes​

This architecture enables:

  • AI-assisted ontology design
  • Epistemic pluralism across tenants
  • Strong auditability and explainability
  • Future mobile clients
  • Vendor independence (retired external no-code surface optional)
  • Shared platform shape without forcing domain sameness

Most importantly, it gives Atlomy a coherent epistemic identity.

10. Canonical Statement​

Atlomy is not a CRUD system with AI features.

Atlomy is a governed epistemic platform.

This architecture is the foundation that makes that statement true.
