ADR-037 Ratification Brief

Date: 2026-05-19 (overnight session) ADR: 037-slot-type-taxonomy.md — Slot-Type Taxonomy and Tenant Vocabulary Layer Current status: Accepted (2026-05-20 — ratified per Option D.2; user ratified after the R2 absorption + comparative-paths brainstorm + Path B chosen for the post-ratification federation-contract layer) Decision requested: Promote ADR-037 from Proposed → Accepted in one of three forms — full ratification (D.1), binding-shape ratification with decision-log deferrals (D.2 — chosen), or hold + R3 round (D.3).

This brief is independent of the architectural arc that authored ADR-037. It was assembled by a fresh-session agent reading the corrected ADR + the R1 absorption + the integrative-tenant evidence + the standards / SOTA notebook lanes (Options A + A.2) + the R2 NotebookLM round (Option B) cold. It exists because the same agent ratifying its own architecture inherits an advocate-for-my-own-work bias (calibration note 2026-05-19, partner_model.md).

1. What ratifying commits to (the decision in one paragraph)​

Ratification binds KE to a three-layer slot-type model as the durable architectural shape:

  • Layer 1 — SlotKind (canonical, currently 10 primitives, open set): TEXT, RICHTEXT, NUMBER, DATE, BOOLEAN, SELECT, MULTISELECT, RELATION, LOOKUP, MEDIA. Promotion to a new SlotKind is the rarest move (Threshold C — ADR-037 §Evolution; ~annually if at all; requires ADR-037 amendment).
  • Layer 2 — SlotModifiers (parametric vocabulary; ~21 fields total — 13 already on TenantArchetypeFormConfig + 9 added by Phase A.1 including complies_with): per-slot configuration knobs. Schema is canonical; values are tenant-supplied. New modifier fields land via Threshold B (~quarterly; additive nullable migration).
  • Layer 3 — TenantSlotPreset (tenant-curated catalog of named (SlotKind, Modifiers) recipes): the 22-icon picker becomes a preset library, with a 16-preset platform-shipped starter library + tenant-authored presets. Promotion of a tenant preset to platform-default fires Threshold A (~quarterly; decision-log entry; requires ≥2 tenants independently authoring the same shape).

Layered on top is the three-surface publication contract (Post-R1 Addendum): every canonical claim renders coherently on three audience surfaces simultaneously — public reader (citation following), research workspace (tenant editing), compliance export (RO-Crate / BagIt / CIDOC / TEI / IIIF / CSL). The complies_with: list[str] modifier is the load-bearing hook tying the three surfaces together: a slot declared complies_with: [TEI, CIDOC-CRM] renders with a compliance chip in research, emits dcterms:conformsTo triples in public-reader JSON-LD, and projects into TEI / CIDOC export views in compliance.

Phase A.1 backend migration follows (Django Widget → SlotKind inner-class rename keeping the widget column name; drop ARRAY enum value collapsed into MULTISELECT; 10 nullable modifier columns added; TenantSlotPreset model + 16-preset starter library fixture; GraphQL tenantSlotPresets(archetype) query added). Phase A.2 frontend rewrite consumes the registry. Phase B (multikey generalisation + preset CRUD) and Phase C (per-key provenance, deferred until JPP onboards a register-level use case) sequence behind A.1/A.2.

A new tenant onboarding pattern emerged that R1 Focus 5 had not anticipated: integrative tenants spanning humanities + prosopography + settlement archaeology + environmental science + GIS + bioarchaeology + geophysics + AI/ML simultaneously.   • TEXT + RICHTEXT + multikey → multilingual historical chronicles
  • NUMBER + numeric_format (year, BP-range, isotope-ratio) → measurements + dates
  • RELATION + relation_cardinality + target_archetypes → person-to-place, find-to-stratum, sample-to-lab-result chains

The three-layer model accommodates this without modification. 2.7 SOTA notebook evidence (Option A.2 — completed)​

The SOTA notebook (id bb0f0210-…) was queried with five ratification-targeted questions. Full evidence at docs/internal/research/2026-05-19_slot-type-taxonomy-round1/10-sota-notebook-evidence.md. Net signal: strongly supportive of the three-layer model + complies_with modifier + three-surface contract, with one residual tension (ontology-first vs hybrid relational+JSONB) that does not invalidate ratification.

Load-bearing external SOTA citations (none are KE-internal restatements):

  • Croissant Baker (NeurIPS-track 2026) — the closest functional twin of ADR-037's complies_with. Slot-level standards binding to HL7/FHIR/DICOM/Schema.org drives validation, federated cross-site schema verification, packaging-contract drift detection, and metadata-only sharing for restricted data — exactly the four downstream consumption modes Correction 3 plans for. Also independently demonstrates the structural/semantic split: "clean separation of file-derived structural metadata from CLI-supplied semantic metadata. The structural layer covers file locations, content sizes, checksums, RecordSet schemas, and field data types; the semantic layer covers description, citation, license, creator, and publisher."

  • ORKG (Open Research Knowledge Graph) — uses RDF/OWL/SHACL templates as the parametric layer with domain-specific instantiations at the community level: "Templates based on SHACL restrict and document expected schema patterns for recurring comparison types"; "Established ontologies (e.g., BioAssay Ontology, schema.org/Dataset, QUDT) are imported or aligned as needed for domain coverage." ORKG is the strongest counter-architecture voice — fully ontology-first; pure peer to KE's hybrid relational+JSONB choice. ORKG nevertheless re-implements Layers 2 and 3 (templates + predicate clustering), so the three-layer pattern is corroborated even by the architectural alternative.

  • CacheRAG (KGQA 2026) — logical/physical decoupling pattern: User Layer expresses intent naturally; System Layer grounds intent against actual schema. Maps to ADR-037 Layer 3 (preset) → Layer 1+2 (canonical) resolution.

  • Dataverse (Harvard FAIR repository) — public-reader surface with three-level metadata projection: "data citation metadata, which maps to DataCite schema or Dublin Core Terms ... domain-specific metadata, which when possible maps to metadata standards used within a scientific domain ... file-level metadata" — three-tier surface analogous to the three-surface contract.

  • Scholix (RDA/WDS federation framework) — compliance-export hub-exchange contract: "the hubs do not affect existing community-specific practices ... In contrast to the uniformity among the hubs, heterogeneity is a natural part of the outer layer." Directly anti-discipline-labeling.

  • KonsortSWD white paper (German national-research-data-infrastructure consortium) — directly endorses ADR-037 Correction 2's withdrawal of the discipline tier: "research data infrastructures should cooperate with research communities to develop domain-specific versions of generally accepted standards. Communities should specify how they make use of a certain standard by creating a profile of that standard." This is essentially identical to ADR-037's complies_with strategy.

  • Counter-evidence absorbed: heterogeneity-erasure critique ("It is like trying to tailor a highly specialized suit using the average measurements of an entire city.") and historical-fidelity critique ("When the system forces an opinionated structure, it actively destroys the historical fidelity of the data.") both target bad defaults — ADR-037's BP-date silent-truncation example absorbs the same critique via the 22→15 starter-library prune.

  • Residual tension (worth surfacing for review): ORKG is fully ontology-first (RDF + OWL reasoning + SHACL); KE chose hybrid relational+JSONB (ADR-002). ADR-037 does not need to resolve this — it's downstream of ADR-002 — but the three-layer model must map cleanly to RDF/JSON-LD for public-reader interop with ORKG-style platforms. The Post-R1 Addendum's dcterms:conformsTo triples in JSON-LD output is the right hook; the implementation has to actually emit it. Open question item below (§5).

2.7b Standards-notebook evidence (Option A — completed)​

Five Atlomy-Standards-* notebooks (Metadata / Identifiers / Harvesting / STEM / LOD, ~41 sources total) queried via six ratification-targeted questions. Full evidence at docs/internal/research/2026-05-19_slot-type-taxonomy-round1/09-standards-notebook-evidence.md. Net signal: strongly ratify.

Key load-bearing citations (all external, from the published standards' own documentation surfaced through the notebooks):

  • Three-layer model is standards-canonical, not novel — four independent precedents:

    • CIDOC-CRM: Layer 1 = E59 Primitive Value (E60 Number / E61 Time / E62 String / E94 Space / E95 Spacetime); Layer 2 = Properties-of-Properties (.1 properties like P14.1 in the role of); Layer 3 = E55 Type hierarchy. "the high-level base classes ... implemented via Properties of Properties ... natively handled by the E55 Type hierarchy ... institutions (tenants) can plug in their own controlled vocabularies, authority files, or domain-specific thesauri without altering the global schema."
    • CSL: variable="title" (canonical) / form="short", plural="true" (parametric) / APA Style or Locale File (preset).
    • BIBFRAME: Work-Instance-Item (canonical) / Classes-for-Types (modifier) / RDA + community extensions (preset).
    • Dataverse: data-citation metadata (DataCite/DC) / domain-specific metadata / file-level metadata.

  • complies_with has four independent precedents at slot/field granularity:

    • DCMI dcterms:conformsTo with dcterms:Standard range.
    • CIDOC E13 Attribute Assignment + P177 assigned property of type — "the CRM documentation explicitly provides examples where P177 refers to a 'property, external to the CIDOC CRM,' such as mapping a field to a specific scholarly binding structure type".
    • IIIF profile property + scoped JSON-LD context for slot-level standard mapping.
    • BIBFRAME bf:descriptionConventions on bf:AdminMetadata — "This property is used within the administrative layer to identify the 'Rules used for the descriptive content of the resource description.'"

  • The three-surface contract is the OAI-PMH / IIIF / UniProt pattern:

    • OAI-PMH item + metadataPrefix: "defines an item not as a single file, but as a 'container that stores or dynamically generates metadata about a single resource in multiple formats.' The item acts as the single canonical dataset. The metadataPrefix acts as the projection mechanism."
    • CIDOC shortcut-vs-fully-articulated-path: "a 'fully articulated' canonical dataset from audience-specific 'shortcuts' or projections ... A projection is a 'functional equivalent' designed for a specific application or user task."
    • UniProt + HTTP Content Negotiation: single stable URL + Accept-header drives HTML / TSV / RDF projections.

  • The integrative-tenant case decisively favors per-slot compliance over discipline bundles (5-for-5 finding):

    • CIDOC E4-Period-as-cultural-phenomenon-AND-spacetime-volume: "It is simultaneously treated as a coherent cultural phenomenon (humanities) and an E92 Spacetime Volume (a 4-dimensional point set in physical spacetime). This allows an archaeologist to query the exact GIS polygons (E94 Space Primitive) of a settlement, while a historian queries the cultural activities that took place there, all within the exact same canonical entity." This is the integrative-tenant pattern's exact use case.
    • BIBFRAME 40+-year vocabulary-drift warning against coordinating dozens of independent discipline ontologies.
    • FAIR R1.3 + I3 qualified-reference pattern — per-slot compliance, not discipline bundles.
    • Bespoke-parser sustainability warning — generalized interoperability over discipline-specific code.

  • ClaimCluster substrate is supported by the literature (validates ADR-022 composition):

    • W3C Web Annotation body→[targets]: one Body (claim) + multiple Targets (attestations).
    • CIDOC E13 + P16 used specific object + CRMinf I2 Belief / I4 Proposition Set (formal argumentation chain).
    • CRMtex TX14 Reading: "As shown in the Antikythera mechanism example, a single 'Reading' activity can synthesize a physical fragment (TX1), a computer x-ray tomography image (E36), and an auxiliary information object to recognize a specific grapheme sequence (TX12)." This is the exact integrative-tenant attestation pattern.

  • No standards-research finding contradicts the model. Where the literature pushes back, it does so against more aggressive shapes: against polymorphic-class explosion (LRMoo deprecated F14/F15/F19 in favor of generic F1 Work), against shapes-first validation that flattens provenance, against rigid domain/range enforcement (BIBFRAME), against property proliferation, against discipline-named bundles. These critiques reinforce ADR-037 by warning against the alternatives.

  • One absorbable nuance worth surfacing for ratification reviewers: CIDOC's "all properties are the opinion of someone" framing. Slot-level assertions are reified arguments. ADR-022 + ADR-037 substrate already handles this via DecisionEvent + ClaimCluster + the planned complies_with provenance — but the framing could be strengthened in the Acceptance discussion to make the reification explicit. Recommend a one-paragraph addition to ADR-037 §Acceptance acknowledging reified-arguments framing.

3. Falsifying conditions​

What would have to be true for ADR-037 to be the wrong architecture? For each, what evidence rules it out OR what residual risk it carries.

F1 — "The three-layer model is wrong for some tenant's data shape."​

Rule-out evidence: ADR-022's Anchor primitive already routes every source-type the platform supports (GLTF / IIIF / TEI / AV / GIS / TABULAR / PASSAGE_SPAN). The integrative-tenant pattern exercises all 10 SlotKinds + the proposed Phase-A-promoted GEOMETRY/TIME_RANGE additions without re-architecture. Independently, the standards literature (FRBRoo W-E-M-I tiers; CIDOC E-class separations; TEI's class/element separation) arrives at canonical-vs-interpretive separations of the same shape.

Residual risk: a tenant whose data shape needs cell-level dynamic per-row schema variance (Coda-style formula expressions, cell-references-in-formulas, conditional logic). ADR-037 §A6 hostile-tenant case (R1 absorption) names this and refuses architecturally — the tenant onboards with their data shape but without the formula feature, OR uses a downstream tool for derived values.

F2 — "complies_with is the wrong shape for slot-level standards interop."​

Rule-out evidence: ADR-030 is a Proposed stub that explicitly defers the profile-choice decision until ratified; Spec 0008 ships CSL operationally but doesn't carry a slot-level declaration mechanism; CROSSWALK.md is a 12×9 matrix, not a per-slot binding. The complies_with modifier fills exactly the gap downstream export tooling will need to know which slots project into which standards-aligned output.

Residual risk: ADR-030 ratification (when it lands) could land on a profile shape that supersedes slot-level complies_with — e.g., a per-archetype declaration with derived slot inheritance, or a SHACL-shape-driven approach with slot inference. Mitigation: complies_with is declaration-only in Phase A; no Phase A code validates it. If ADR-030 supersedes it, the column drops in a future migration with no downstream code rework.

F3 — "The integrative-tenant pattern would be better served by a 4th tier (discipline / community layer)."​

Rule-out evidence: Spec 0017 design.md (2026-05-17 ratification walk) explicitly withdrew the domain-archetype dropdown for three reasons that scale to a discipline-library proposal: (1) onboarding friction conflicts with the make-or-break first-import design constraint; (2) any fixed enum mis-categorises researchers from non-registered fields; (3) within-domain heterogeneity is severe — within "humanities" alone, Classics is epistemically more distant from music theory or media studies than from some humanities/STEM pairings. Integrative tenants would either enroll in multiple labels (re-creates ADR-004's tenant ontology problem at discipline granularity) or pick a dominant discipline (falsifies their methodology).

Residual risk: if cross-tenant convention sharing fails to emerge organically via ADR-037 promotion thresholds + standards declarations + future tenant-preset import/export, the discipline-library option becomes attractive again. The architectural defense is: promotion thresholds are programmatic; standards declarations are already in flight; preset import/export is Phase B's scope. The mechanism exists at the ratification point; absence of usage at year T is signal to amplify promotion-detection, not to add a tier.

F4 — "Phase A migration footprint is too large even after the A.1/A.2 split."​

Rule-out evidence: R1 absorption A4 already split Phase A into A.1 backend + A.2 frontend. A.1 = enum rename + 10 nullable columns + TenantSlotPreset model + GraphQL extension.
