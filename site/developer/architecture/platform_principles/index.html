KE (Knowledge Environments) Platform Principles

Date: 2025-12-28
Status: Canonical
Purpose: Core architectural principles that govern all design decisions

Note on naming: The platform is KE — Knowledge Environments. Atlomy Atlas is the original software the platform grew out of, now one tenant among others. "Atlomy" persists as brand; "KE" is the platform name. Older prose below may still use "Atlomy" for the platform — read in that historical context.

The Foundational Principle​

Canonical Structure Is Shared; Interpretation Is Tenant-Specific

This single principle connects KE's entire architecture:

  • FDW Layer: Canonical structure in PostgreSQL, epistemic interpretation in tenant schemas
  • Hybrid Ontology: Tables define what can exist (shared), JSON defines expression (tenant-specific)
  • Tenant Ontology Mapping: Archetype structure is shared, labels are tenant-specific
  • Interface Separation: Operational truth is shared, epistemic interpretation is tenant-facing

Why This Matters:

  • AI can reason across tenants (shared structure)
  • Tenants retain autonomy (custom interpretation)
  • Governance is enforceable (structure is legible)
  • Ontology drift is explicit and controlled

The Four Pillars​

These ADRs form a closed, self-reinforcing system:

1. Who The System Serves​

ADR-001: Epistemic vs Operational Separation

  • Operational users (admins): Shared truth, stable interface (Django Admin)
  • Epistemic users (researchers): Interpreted knowledge, evolving interface (React)

Consequence: Two interfaces, one platform

2. What Can Exist​

ADR-002: Hybrid Ontology (Relational + JSON)

Tables define what can exist. JSON defines how it is expressed.

  • Relational: Governance fields (status, confidence, approver)
  • JSON: Tenant-specific expression (custom fields, fluid data)

Consequence: Structure is legible, expression is flexible

3. How Knowledge Is Queried​

ADR-003: GraphQL as Epistemic Contract

  • GraphQL schema represents the epistemic surface, not backend implementation
  • Clients (React, AI, mobile) query the same contract
  • REST remains for mutations and governance

Consequence: Frontend independence, type safety, AI-native APIs

4. How Meaning Drifts Safely​

ADR-004: Tenant Ontology Mapping

Ontology drift should be explicit.

  • Structure: TERM archetype (shared, canonical)
  • Label: "Lemma" vs "Term" vs "Concept" (tenant-specific, mapped)
  • Mapping lives in tenant_ontologies table (relational, queryable)

Consequence: Multi-ontology support without structure collapse

The Epistemic-Canonical Lifecycle​

Understanding when epistemic knowledge becomes canonical truth:

┌─────────────────────────────────────────────────────────┐
│                  EPISTEMIC LAYER                        │
│  (Fluid, AI-assisted, tenant-specific interpretation)   │
└──────────────────────┬──────────────────────────────────┘
                       │
                       │ State: DRAFT
                       │ ↓
                       │ State: AI_PROPOSED
                       │ ↓
                       │ State: HUMAN_REVIEW
                       │ ↓
                       │ State: APPROVED
                       │     (Human decision point)
                       │ ↓
                       │ State: APPLYING
                       │     (System enforcement begins)
                       │ ↓
                       │ State: APPLIED_TO_CANONICAL
                       │
┌──────────────────────▼──────────────────────────────────┐
│                  CANONICAL LAYER                        │
│    (Rigid, governed, shared structure)                  │
│                                                          │
│  - Epistemic structure is materialized                  │
│  - Becomes queryable via canonical SQL/FDW              │
│  - Immutable (changes require new epistemic proposal)   │
│  - Auditable (provenance preserved)                     │
└─────────────────────────────────────────────────────────┘

Lifecycle Rules​

Manual Transition (Always):

  • APPROVED → APPLYING: Superuser clicks "Apply to Canonical"
  • Requires explicit confirmation (blast radius shown)
  • Cannot be reversed (structural change persistence)

Automated Transition (Conditional):

  • APPLYING → APPLIED_TO_CANONICAL: System confirms completion
  • Only after:
    • Database migration succeeds (if schema change)
    • retired external no-code surface sync completes (if field addition)
    • Elasticsearch re-index finishes (if searchable)

Never Automated:

  • AI cannot approve (structural limitation)
  • No "auto-apply" for breaking changes
  • Human in the loop for governance

What Crosses the Boundary​

Epistemic → Canonical:

  • ✅ New tables/fields (schema additions)
  • ✅ Relationship definitions (foreign keys)
  • ✅ Data type changes (with migration)
  • ✅ Archetype classifications

Stays Epistemic Forever:

  • ❌ Tenant-specific labels ("Lemma" vs "Term")
  • ❌ Custom field names (in JSON, not relational)
  • ❌ AI reasoning/provenance (metadata only)
  • ❌ Workflow state (DRAFT, REVIEW, etc.)

Terminology Clarifications​

"Schema Changes"​

When we say "AI can propose schema changes," we mean:

Epistemic Structure (what AI modifies):

  • Adding a field to a tenant's view of a table
  • Proposing a relationship between entities
  • Suggesting an archetype classification
  • Recommending a data type for flexibility

NOT Physical Schema (what AI never touches):

  • SQL ALTER TABLE statements
  • Database migrations
  • Index creation
  • Constraint modifications

The System Does Physical Schema Changes:

  • After human approval
  • Via Django migrations (versioned, auditable)
  • With rollback capability
  • Logged in audit trail

"Canonical" vs "Epistemic"​

Canonical:

  • Nature: Rigid, governed, shared
  • Location: PostgreSQL tables (Django ORM)
  • Authority: Single source of truth
  • Changes: Migrations, manual, versioned
  • Examples: User accounts, tenant records, billing

Epistemic:

  • Nature: Fluid, AI-assisted, interpreted
  • Location: Tenant schemas (retired external no-code surface + FDW)
  • Authority: Derived from canonical, enriched by tenants
  • Changes: Proposals, reviews, state machine
  • Examples: Knowledge entities, schema suggestions, relationships

Canonical Models and Multi-Tenancy​

Atlomy maintains a single canonical model layer.

Django models represent shared canonical structure. Tenancy is enforced via:

  • Database schema isolation (per-tenant PostgreSQL schemas)
  • Row-level constraints (tenant_id foreign keys)
  • Tenant ontology mappings (TenantOntology table)
  • Epistemic views and projections (GraphQL schema)

Models are never tenant-specific:

  • A Book model serves all tenants
  • Configuration lives in db_table Meta (points to tenant schema)
  • Semantic differences handled via TenantOntology (e.g., "Book" vs "Source" vs "Reference")

AI never generates or mutates Django models directly:

  • AI may propose epistemic structures
  • AI may suggest schema evolution
  • AI may generate migration drafts (as artifacts for review)

But:

  • Only human-approved migrations modify canonical models
  • Canonical models remain globally shared
  • If a change requires tenant-specific divergence, it belongs in the epistemic layer — not in Django models

Implementation Consequence: This is why models_epistemic.py (or equivalent) contains shared structures, not tenant-duplicated code. Tenant isolation happens at the database level, not the model-definition level.

Anti-Patterns (What These Principles Prevent)​

The ADRs form an institutional immune system against:

❌ Flattening governance into JSON
→ Prevented by ADR-002: Status, confidence, approver must be relational

❌ Hardcoding tenant labels in React
→ Prevented by ADR-004: Labels live in tenant_ontologies table

❌ Skipping epistemic lifecycle for speed
→ Prevented by ADR-002: State machine enforced by database enum

❌ Using REST where GraphQL fits better
→ Prevented by ADR-003: Epistemic queries use GraphQL contract

❌ Mixing operational and epistemic UI
→ Prevented by ADR-001: Separate interfaces for separate users

❌ AI auto-approving structural changes
→ Prevented by Lifecycle: Manual transition at APPROVED → APPLYING

❌ Creating tenant-specific Django models
→ Prevented by Multi-Tenancy Clarification: Models are shared, tenancy is data-level

❌ AI directly generating Django model files
→ Prevented by Multi-Tenancy Clarification: AI outputs are inputs to governance, not code artifacts

❌ Per-tenant migrations or apps
→ Prevented by Multi-Tenancy Clarification: Single canonical migration stream, tenant schemas diverge via data

Design Decision Framework​

When faced with an architectural choice, ask:

1. Who is this for?​

  • Operational users → Django Admin (ADR-001)
  • Epistemic users → React (ADR-001)

2. What needs governance?​

  • Governed → Relational columns (ADR-002)
  • Flexible → JSON fields (ADR-002)

3. How will it be queried?​

  • Complex reads → GraphQL (ADR-003)
  • Mutations → REST (ADR-003)

4. Does meaning vary by tenant?​

  • Yes → tenant_ontologies mapping (ADR-004)
  • No → Canonical archetype (ADR-004)

5. Is this epistemic or canonical?​

  • Fluid, AI-assisted → Epistemic layer (goes through lifecycle)
  • Rigid, governed → Canonical layer (direct mutation)

Compliance​

Every architectural decision in Atlomy must:

  1. Align with the Foundational Principle: Shared structure, tenant-specific interpretation
  2. Reference at least one ADR: Show which pillar supports this
  3. Respect the Lifecycle: Don't bypass epistemic → canonical governance
  4. Use Correct Terminology: Epistemic structure ≠ physical schema

Enforcement:

  • Code reviews check ADR alignment
  • PRs reference ADR numbers
  • Architecture reviews audit compliance

How This Architecture Evolves​

Understanding when and how to change this architecture is as important as understanding its current state.

When Do We Add a New Archetype?​

New archetypes are rare and significant. Add a new archetype when:

✅ Do add when:

  • A fundamentally new epistemic pattern emerges across multiple tenants
  • Example: TERM, BLOG_POST, PRODUCT, EVENT
  • Has distinct governance needs (different lifecycle, permissions, relationships)
  • Cannot be expressed as a variant of existing archetypes

❌ Don't add when:

  • Just a label variation ("Lemma" vs "Term" → use tenant_ontologies)
  • Tenant-specific customization (use JSON fields in data)
  • Cosmetic difference (same structure, different presentation)

Process:

  1. Document pattern across ≥3 tenants
  2. Propose via ADR (e.g., "ADR-005: LEGAL_DOCUMENT Archetype")
  3. Architecture review + consultant sign-off
  4. Implementation: Add to enum, update GraphQL schema, migrate existing data

Frequency: ~1-2 per year (archetypes are structural, not tactical)

When Does Epistemic Structure Become Canonical?​

The lifecycle determines this, but here are the decision criteria:

Becomes Canonical When:

  • ✅ Human approves (APPROVED state)
  • ✅ Blast radius is acceptable (reviewed and documented)
  • ✅ Migration path is clear (reversible or acknowledged as breaking)
  • ✅ Provenance is complete (AI reasoning + confidence captured)
  • ✅ Superuser explicitly triggers "Apply to Canonical"

Stays Epistemic When:

  • ❌ Still in DRAFT or AI_PROPOSED state
  • ❌ HUMAN_REVIEW but not yet approved
  • ❌ Breaking change with unclear migration path
  • ❌ Experimental feature (use feature flag instead)

Gray Area (requires judgment):

  • Tenant-specific fields: Always epistemic (JSON), never canonical
  • Shared relationships: Start epistemic, promote to canonical if used by >50% of tenants
  • Archetype refinements: Epistemic until pattern is proven stable

Guideline: When in doubt, keep it epistemic. Canonical changes are expensive to reverse.

When Do We Add a New ADR vs Extend an Existing One?​

Add a New ADR When:

  • ✅ Introducing a new architectural pattern (e.g., caching strategy, event sourcing)
  • ✅ Making a technology choice with long-term consequences (e.g., "ADR-005: Redis as Cache Layer")
  • ✅ Establishing a governance rule across the platform (e.g., "ADR-006: API Versioning Policy")
  • ✅ The decision affects multiple teams or multiple sprints

Extend an Existing ADR When:

  • ✅ Refining an existing principle (e.g., adding examples to ADR-002)
  • ✅ Clarifying terminology (e.g., "schema changes" clarification added to ADR-002)
  • ✅ Documenting a consequence discovered in production
  • ✅ Adding an anti-pattern to prevent regression

Update (Not New ADR) When:

  • Fixing typos or formatting
  • Adding references to related docs
  • Updating implementation status

Supersede (Mark Old ADR Deprecated) When:

  • Fundamentally changing direction (e.g., "ADR-007: Replacing GraphQL with gRPC")
  • Old ADR becomes obsolete (link to new ADR)

Frequency: Expect ~2-4 ADRs per year. Too many = decision fatigue. Too few = under-documented.

What Decisions Are Explicitly Out of Scope?​

Current Architecture Does NOT Specify:

  1. Deployment Infrastructure (intentionally deferred)

    • Cloud provider choice (AWS vs GCP vs Azure)
    • Container orchestration (K8s vs ECS vs bare Docker)
    • Why: Platform can run anywhere Django + Postgres run
    • When to decide: When traffic justifies complexity (>100K req/day)

  2. Frontend Framework Alternatives (React is chosen, but...)

    • Not prescriptive about state management beyond "start simple"
    • Not mandating specific UI component libraries
    • Why: Frontend evolves faster than backend
    • When to revisit: If React ecosystem fundamentally shifts (unlikely in 5 years)

  3. AI Model Selection (infrastructure, not architecture)

    • Which LLM (GPT-4 vs Claude vs Gemini)
    • Hosting (OpenAI API vs self-hosted)
    • Why: Model choice is operational, not structural
    • When to decide: Per-feature basis, based on cost/performance

  4. Search Engine Alternatives (Elasticsearch is current, but...)

    • Could be swapped for Typesense, Meilisearch, etc.
    • Why: ES is implementation, not contract (GraphQL hides it)
    • When to revisit: If cost becomes prohibitive or performance insufficient

  5. Multi-Region Strategy (not needed yet)

    • Data residency requirements
    • Global replication
    • Why: Single-region sufficient for current scale
    • When to decide: When serving >3 continents or GDPR requires it

Rate of Change (Expected Evolution Timeline)​

Stable (Rarely Changes):

  • Foundational Principle: "Canonical structure shared, interpretation tenant-specific"
  • ADR-001 (Interface Separation): Operational vs Epistemic split
  • ADR-002 (Hybrid Ontology): Relational + JSON approach
  • Expected Change Frequency: Once every 3-5 years, if at all

Semi-Stable (Evolves Gradually):

  • ADR-003 (GraphQL Contract): May add mutations over time
  • ADR-004 (Tenant Ontology): May add field-level mappings (currently label-only)
  • Archetype definitions: New archetypes added ~1-2/year
  • Expected Change Frequency: Extend ADRs 2-4 times/year

Dynamic (Frequent Evolution):

  • GraphQL schema fields: New queries/types per sprint
  • React components: Continuous iteration
  • API endpoints: New features = new endpoints
  • Expected Change Frequency: Weekly (managed via feature flags + versioning)

Governance for Evolution​

Who Can Propose Changes?

  • Any engineer can propose ADR
  • Frontend changes: Frontend lead + architecture review
  • Backend changes: Backend lead + architecture review
  • Cross-cutting: Requires architecture team + consultant sign-off

Approval Process:

  1. Propose: Draft ADR or RFC
  2. Review: Architecture team + affected teams
  3. Feedback: Minimum 3 business days for comment
  4. Decide: Consensus (not unanimous, but no strong objections)
  5. Document: Update ADRs, platform principles, migration plan
  6. Communicate: All-hands summary, update docs

Emergency Overrides (rare):

  • Security vulnerability requiring architectural change
  • Production incident revealing design flaw
  • Process: CTO can approve, but must be documented retroactively within 1 week

Evolution Anti-Patterns​

❌ Don't: Add ADRs for every technology choice (Redis, Celery, etc.)
✅ Do: Add ADRs for architectural patterns (caching strategy, async processing)

❌ Don't: Change foundational principles without consultant review
✅ Do: Extend ADRs with clarifications and examples freely

❌ Don't: Bypass lifecycle "just this once"
✅ Do: Fix the lifecycle if it's blocking progress, then use it correctly

❌ Don't: Create "temporary" workarounds that violate principles
✅ Do: Acknowledge technical debt explicitly, create plan to resolve

Principle Evolution vs Code Evolution​

These principles evolve slowly. Code evolves fast.

  • Principles: Change when system forces you to (like FDW → hybrid ontology)
  • Code: Change when features require it (new GraphQL types, React components)

The Test: If you're changing a principle to fit code, you're doing it backward. Change code to fit principles, or propose a new principle with strong justification.

Compliance​

Every architectural decision in Atlomy must:

  1. Align with the Foundational Principle: Shared structure, tenant-specific interpretation
  2. Reference at least one ADR: Show which pillar supports this
  3. Respect the Lifecycle: Don't bypass epistemic → canonical governance
  4. Use Correct Terminology: Epistemic structure ≠ physical schema

Enforcement:

  • Code reviews check ADR alignment
  • PRs reference ADR numbers
  • Architecture reviews audit compliance
