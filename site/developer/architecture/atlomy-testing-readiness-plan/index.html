Atlomy Data Testing Readiness Plan

Purpose​

This document answers a practical question:

Is the current import and sync stack ready for meaningful testing against Atlomy data as represented by the legacy CSV bundle and the intended Atlomy production-style knowledge environment?

It uses commit 589128398ba0ca4f361d78cb9a9e2088bb7512cf as an architectural anchor because that commit introduced the major retired external no-code surface-first import wizard, AI-assisted schema adaptation, monitoring, and sync-oriented design.

It should be read together with the canonical architecture direction in docs/developer/architecture/atlomy_canonical_architecture_vision.md.

This matters because the actual goal is not to reproduce v1 internals. The goal is to recover and extend the final user-visible and editor-visible outcome:

  • a tenant database that exposes structured knowledge in admin
  • an authoring surface that allows additional content and objects to be added safely
  • a public-facing knowledge environment where lemma pages, index views, occurrences, references, pages, and 3D models resolve coherently

Short Answer​

Not yet for full-fidelity Atlomy testing.

The repository has enough infrastructure to stage, inspect, and partially import Atlomy-shaped data, but it is not yet ready for reliable end-to-end testing of a full Atlomy restore into the current tenant knowledge environment.

Current reality:

  • good foundation exists for generic import and staging
  • partial testing is possible now for Lemma and Reference
  • the real target is broader than Lemma materialization and includes the connected knowledge experience around lemmas
  • full relational Atlomy restoration is blocked by model coverage, relationship coverage, and sync identity gaps
  • legacy Elasticsearch-based restore is also blocked because Elasticsearch is currently unhealthy

2026-04-20 Addendum: What The Latest Local Audit Changed​

The local picture is now more precise than the original readiness snapshot above.

  • Elasticsearch is no longer the immediate blocker in local development. The local stack was repaired enough to restore the legacy Atlomy public experience for demo purposes.
  • A local working-layer restore path now exists:
    • atlomy_csv/ sample bundle
    • into noco_atlomy_atlas working tables
    • into the shared raw lemma_index
    • into tenant-local Lemma rows in atlomy_atlas
    • back out through the legacy public pages
  • That means the branch is now usable for a narrow demo path, but the original architectural warning still stands: this is a compatibility bridge, not the intended generic retired external no-code surface/archetype runtime.

Three guardrails became explicit during the audit and should be treated as architecture-level constraints until replaced deliberately:

Guardrail 1. The Public Atlomy Experience Still Depends On The Legacy ES Read Contract​

Today’s public Atlomy pages are still driven by the rich historical document shape in the shared raw Elasticsearch lemma_index.

  • /results/...
  • /all-lemmas
  • /lemma/<slug>/

They do not currently read from:

  • tenant-local GraphQL/archetype renderers
  • TenantOntology
  • the generic retired external no-code surface sync output
  • the thin tenant-local ES projection

Implication for future sprints:

  • Do not treat “tenant data imported” as equivalent to “public Atlomy pages will work”.
  • Any sprint that touches import, sync, search projection, or frontend data-fetching must validate the public Atlomy pages explicitly.

Guardrail 2. Shared Shell Or Header Refactors Can Break Atlomy Even When Data Is Present​

The recent blank/black-page failure was not only a data issue. The branch had drifted from master in the shared shell/header and route-bootstrap contracts.

Concrete examples from the audit:

  • missing HeaderProps.threeDModelPage
  • legacy result/index pages not bootstrapping route-local params correctly
  • shared client/query path failing while direct endpoint fetches still worked

Implication for future sprints:

  • any shared SPA shell, header, route-bootstrap, or cache/query abstraction change must be checked against Atlomy’s legacy routes, not only the new import/explorer surfaces

Guardrail 3. Admin / WYSIWYG Work Must Track Master Explicitly​

master has moved materially on the scholarly editing/admin experience while this branch is still largely on the older stack.

master additions now include:

  • django-prose-editor / TipTap instead of Summernote
  • footnotes
  • resizable tables
  • unified image upload + caption workflow
  • TextAlign / Typographic support
  • embed_url support on Page
  • improved Job admin report visibility

Implication for future sprints:

  • when continuing the tenant/archetype work here, treat master’s admin/editor contract as a parallel source of truth
  • otherwise the branch can “advance” architecturally while silently regressing editor-visible capabilities already shipped on master

Correct Target Outcome​

The target is to restore the outcome that users and editors actually experience:

  • index and search views that expose lemma-oriented knowledge
  • lemma detail pages that combine summary, parallel terms, descriptions, occurrences, and linked models
  • reference displays that depend on structured reference data, abbreviation logic, and page cross-links
  • model views where 3D objects are related back to lemmas and navigable from the public frontend
  • admin-side content that can be extended with new records after restore rather than being a frozen historical import

In other words, v1 is useful mainly as a source-system reference and transformation reference. It is not the product target.

This aligns with the canonical architecture vision:

  • Django and PostgreSQL preserve operational truth
  • the public frontend and APIs expose the epistemic knowledge environment
  • import and restore work should be judged by whether they reconstruct that governed knowledge environment

What Commit 5891283 Established​

The December 2025 import-wizard commit established the intended direction of the platform:

  • retired external no-code surface-first import flow
  • AI-assisted field mapping and schema adaptation
  • import job orchestration and monitoring
  • webhook and sync-driven movement from retired external no-code surface into Django
  • tenant-aware administrative tooling

That commit was substantial and real. It was not just documentation. It added or expanded:

  • data_import/services/retired external no-code surface_importer.py
  • retired external no-code surface/services/sync.py
  • retired external no-code surface/services/schema_adapter.py
  • retired external no-code surface/services/archetypes.py
  • retired external no-code surface/models.py
  • data_import/views.py
  • import UI assets under data_import/static/data_import/
  • integration and unit tests around import, schema adaptation, webhook flow, idempotency, and validation

Architecturally, that commit supports the user's premise that the system is meant to be generic and reusable across tenants and knowledge environments.

Current Validated State​

Based on the current repository and runtime checks already completed in this workspace:

  • retired external no-code surface local external database connectivity is fixed.
  • Atlomy and Visionis bases can be registered and synced into retired external no-code surface metadata.
  • public and tenant admin routing is functioning again.
  • tenant branding and sidebar separation are corrected.
  • the tenant content tables for atlomy_atlas are empty.
  • the external noco_atlomy_atlas content views are empty.
  • Elasticsearch is currently red, so the old lemma pipeline is not reliable.

Code-level state that matters most:

  • Data Wizard registration currently covers only Lemma and Reference.
  • retired external no-code surface sync still assumes a retired external no-code surface_id field on the target Django model.
  • core Atlomy models such as Model, Page, ModelMapping, ModelLemma, TenantOntology, Event, and Configuration do not currently expose a generic sync identity field compatible with that assumption.
  • frontend and API code already expect richer lemma-centered behavior, including:
    • model cards and model-detail navigation from lemma pages
    • occurrence rendering from structured reference data
    • author and treatise page linking
    • index-style views that depend on coherent lemma and translation data

What "Good For Testing" Actually Means​

For Atlomy, testing readiness should not be defined as "can we import lemmas?"

It should be defined as whether the restored tenant can support the core knowledge environment behaviors:

  • admins can inspect and extend the restored content in Django admin or the intended authoring layer
  • public lemma pages render non-trivial content, not only titles
  • occurrences render from structured reference data
  • references can resolve author and treatise navigation where applicable
  • 3D models appear on lemma pages where relationships exist
  • model pages can navigate back to lemmas through ModelLemma and ModelMapping
  • index views and search results can expose the same knowledge graph coherently

This is the correct acceptance frame for Atlomy-data testing.

Readiness Verdict By Capability​

Ready Now​

  • CSV and Excel staging into retired external no-code surface
  • admin-driven inspection of imported data in retired external no-code surface
  • AI-assisted mapping experiments
  • partial import testing for Lemma and Reference
  • architecture and implementation review against the December 2025 design

Partially Ready​

  • generic retired external no-code surface-first testing for simple flat records
  • restore of bibliography-oriented data
  • proof-of-concept tenant ingestion for a subset of Atlomy data

Not Ready Yet​

  • full Atlomy tenant reconstruction as a working knowledge environment
  • reliable sync of relational structures across current Atlomy models
  • production-like restore testing for pages, models, model relationships, page cross-links, ontology, and events
  • legacy Elasticsearch restore path as a fallback

What Is Missing​

1. Source Data That Matches The Current Target Model​

Available legacy source files are strong for lemma-centric content and bibliography, but they do not obviously cover the entire relational surface needed for the current knowledge environment.

What this means:

  • atlomy_csv/*.csv can reconstruct a large part of term-oriented content
  • they do not, by themselves, clearly reconstruct the current Page, Model, ModelMapping, ModelLemma, and TenantOntology state expected by today's UI, API, and admin model
  • if Atlomy production data includes richer CMS, 3D model catalog, or tenant ontology content, those source exports must be identified and included

2. Sync Identity Strategy For Generic Restore​

The current retired external no-code surface sync implementation uses retired external no-code surface_id as the unique identifier when creating or updating Django rows.

This is the single clearest implementation gap between the generic architecture and the current Atlomy models.

What is needed:

  • either add retired external no-code surface_id to sync-enabled Atlomy models
  • or make sync pluggable so a mapping can specify a business key or composite key per model

Preferred direction:

  • make identity configurable per mapping, not hard-coded per platform

This keeps the architecture generic and reduces pressure to modify every tenant model in the same way.

3. Model Coverage Beyond Lemma And Reference​

Current import tooling does not yet cover the full target set needed for realistic Atlomy testing.

Missing or incomplete restore path is most important for:

  • Page
  • Model
  • ModelMapping
  • ModelLemma
  • TenantOntology
  • Event
  • possibly Configuration, depending on whether restore should also recreate import/runtime settings

What is needed:

  • serializers or sync adapters where needed
  • explicit field mappings for each target model
  • relationship ordering so parent objects are created before dependent objects
  • restore logic that aims at public/frontend completeness, not only table population

4. Relationship And Ordering Logic​

Atlomy data is not only flat data. It includes linked records.

Testing against real Atlomy data will require:

  • deterministic import order
  • foreign-key resolution strategy
  • idempotent upsert behavior
  • conflict behavior for re-imports
  • reconstruction of the relationships that make lemma pages and model pages useful

At minimum, the pipeline needs a dependency order like:

  1. TenantOntology and reference tables
  2. Lemma, Reference, Model, Page, Event
  3. ModelMapping
  4. ModelLemma

At a product level, these relationships are not optional implementation detail. They are the mechanism by which the public knowledge environment works.

5. Elasticsearch Fallback Is Unavailable​

The legacy pipeline still matters as a reference and partial fallback, but it is currently blocked by cluster health.

Consequences:

  • add_data can still transform source material conceptually
  • add_lemmas cannot be treated as a dependable verification path while Elasticsearch remains unhealthy
  • search-oriented regression testing should not be used as the main restore validation path until Elasticsearch is repaired

6. Test Harness For Atlomy Restore Acceptance​

The repository contains tests for generic import behavior, but not yet a clear end-to-end acceptance harness for Atlomy restore completeness.

What is needed:

  • a fixture set representing real Atlomy source data
  • a defined expected outcome per target model
  • schema-specific validation checks after import
  • repeatable commands that can be run in Docker against atlomy_atlas
  • acceptance checks tied to public behavior, not just row counts

What Is Already Available​

Source Assets​

  • legacy Atlomy CSV bundle in atlomy_csv/
  • config_data.json
  • legacy import commands in atlomyapp/management/commands/

Generic Import Stack​

  • retired external no-code surface importer
  • schema adapter
  • archetype detection
  • sync logging and conflict tracking
  • import job model and admin UI
  • webhook-driven sync flow

Existing Django Models​

  • atlomyapp/models.py already defines the current target model set for core Atlomy content
  • this is enough to plan the restore target even when source coverage is incomplete

Existing Public Knowledge-Environment Code​

The current codebase already shows the desired end state clearly.

Important examples include:

  • lemma-detail flows that render models, parallel terms, descriptions, and occurrences
  • selectors that derive displayed references and linked model data
  • backend mixins that connect Lemma, Page, ModelLemma, ModelMapping, and reference payloads for the public API

This is useful because it means the missing work is not mainly "invent the product behavior." The missing work is restoring and synchronizing the data structures that this behavior depends on.

Existing Tests And Reference Coverage​

  • import API tests
  • schema adaptation tests
  • webhook flow tests
  • idempotency and conflict tests
  • importer validation tests

These do not yet prove Atlomy restore readiness, but they are useful scaffolding.

Operational Access Already Recovered​

  • local retired external no-code surface is working
  • tenant and public admin are reachable
  • Atlomy and Visionis bases are present for experimentation

Needed Inputs And Resources​

To make this genuinely ready for Atlomy-data testing, the following inputs are still required.

Data Inputs​

  • authoritative Atlomy source exports for any content not represented in atlomy_csv/
  • confirmation whether the intended test dataset is CSV-only, Coda-derived, retired external no-code surface-derived, or a mixed restore source
  • if available, a representative production snapshot or sanitized export from www.atlomy.com
  • explicit source exports for page content, 3D model catalog data, and any reference-normalization rules that power occurrences and citation display

Mapping Inputs​

  • per-model identity decision:
    • retired external no-code surface_id
    • business key
    • composite business key
  • field-level mapping rules for each target model
  • relationship rules for linking Model to Lemma, Model to Model, and Reference to ModelMapping
  • mapping rules for page-link resolution such as author pages and treatise pages where the public frontend expects those navigational joins

Runtime Resources​

  • healthy Elasticsearch if the legacy route is to remain part of verification
  • working tenant schema with migrations applied
  • retired external no-code surface base with clean import tables or a repeatable reset process

Human/Decision Resources​

  • one owner to define restore acceptance criteria
  • one owner to define which target models are required for the first successful Atlomy test
  • one decision on whether phase 1 testing should prioritize:
    • generic retired external no-code surface-first restore, or
    • transitional Atlomy-specific restore command that later gets generalized

Recommended Plan​

Phase 1. Define The Testing Target​

Decide what counts as "good enough for testing on Atlomy data".

Recommended definition for the first milestone:

  • import representative Atlomy data into the atlomy_atlas tenant
  • produce non-empty Lemma, Reference, Model, ModelLemma, and Page tables if source exists
  • keep the process repeatable and idempotent
  • validate that tenant admin can browse and inspect the imported records
  • validate that the public lemma experience can show models, occurrences, and linked page navigation for at least a representative sample set

This milestone is more realistic than requiring the entire platform to be perfect before any testing begins.

Phase 2. Close The Sync Identity Gap​

Implement one of these two options:

Option A:

  • add retired external no-code surface_id to sync-enabled Atlomy models

Option B:

  • extend retired external no-code surfaceTableMapping and sync services so mappings can define the lookup strategy per target model

Recommended option:

  • Option B for long-term architecture
  • Option A only as a tactical bridge if faster testing is needed immediately

Phase 3. Build A Model Coverage Matrix​

For each target model, document:

  • source dataset
  • key fields
  • identity strategy
  • import order
  • required transforms
  • verification query

Priority order:

  1. Lemma
  2. Reference
  3. Model
  4. ModelLemma
  5. Page
  6. Event
  7. ModelMapping
  8. TenantOntology
  9. Configuration

Phase 4. Implement The Minimum Restore Path​

Build the smallest path that supports useful Atlomy testing.

Recommended minimum:

  • retired external no-code surface-first import for Lemma and Reference
  • configurable sync identity
  • adapter or serializer support for Model and ModelLemma
  • optional Page import if source content exists
  • support for the joins needed to render occurrences and page navigation in the public experience

This gets the tenant out of the current empty state and creates a meaningful test surface.

Phase 5. Add Restore Verification​

Create Docker-executable verification steps that check:

  • row counts per target model
  • required foreign keys resolve
  • duplicate re-import does not create drift
  • admin pages load for imported entities
  • representative lemma pages render models and occurrences correctly
  • author/treatise navigation resolves where source data supports it
  • optional search validation if Elasticsearch is healthy

Phase 6. Repair Or Explicitly Retire The Legacy Fallback​

Make a clear decision:

  • either repair Elasticsearch and keep legacy lemma restore as a comparative reference
  • or stop treating it as a viable restore fallback and move entirely to the retired external no-code surface-first path

Right now the repo sits awkwardly between both worlds.

Suggested Deliverables​

Deliverable 1. Atlomy Restore Gap Matrix​

A model-by-model table showing source, mapping, lookup key, dependencies, status, and owner.

Deliverable 2. Configurable Sync Identity​

Either:

  • new mapping configuration on retired external no-code surfaceTableMapping, or
  • a minimal sync adapter abstraction

Deliverable 3. First Atlomy Test Dataset​

A curated, repeatable dataset and import recipe that can be run locally without guessing.

That dataset should include at least one representative lemma with:

  • occurrences
  • author and treatise references
  • model relationships
  • enough supporting page content to prove public navigation works

Deliverable 4. Restore Verification Command Or Checklist​

One command or short command set that validates import completeness inside Docker.

Recommended Immediate Next Steps​

  1. Create the model-by-model gap matrix for atlomyapp core models.
  2. Decide whether sync identity will be retired external no-code surface_id-based or configurable by business key.
  3. Identify which Atlomy production-style data sources exist beyond atlomy_csv/.
  4. Choose the first milestone scope for testing: minimal viable tenant content or full relational restore.
  5. Only after those decisions, start implementation.
