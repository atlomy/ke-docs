KE Admin Overlay — architecture

Status: Active (Phase 0–12, May 2026). Built on top of Django Admin + Unfold theme; complementary to ADR-015's eventual Native React shell.

What this is​

The "KE Admin Overlay" is the layered set of templates, CSS, JS, and ModelAdmin extensions that turns Django's stock Unfold-themed admin into a slot-driven curator workspace for KE — Knowledge Environments tenants. It is NOT a fork of Unfold; it composes ON TOP of it.

Why it exists​

Atlomy Atlas's V2 architecture stores every tenant entity in epistemic_entities.data (JSONB) keyed by per-tenant TenantArchetypeFormConfig.slot_name. Editing a TERM's Lemma Word field directly in a JSON textarea is a poor UX for researchers. ADR-015 prescribes a Native React shell as the long-term destination; the KE Admin Overlay is the working surface in the meantime, leveraging Django Admin's free machinery (auth, audit log, save-and-continue, list_filter, change history) without re-implementing them.

The slot-driven editing model​

Data flow (read)​

EpistemicEntity (Django model, UUID PK)
  └ .data (JSONField, JSONB blob with Coda-cased keys)
  └ .archetype, .canonical_type, .status, …

TenantArchetypeFormConfig
  └ .archetype, .slot_name, .display_order
  └ .source_field         (dotted-path: "data.Lemma Word" or "lemma_full")
  └ .composition_template (optional: "{data.Lemma Word}, {data.Morph 1}")
  └ .widget               (text | richtext | multilingual | linkable | lookup | …)
  └ .label, .help_text, .required

Resolution path (in epistemic/admin.py:_build_slot_rows):

for cfg in TenantArchetypeFormConfig.objects.filter(archetype=entity.archetype).order_by("display_order"):
    if cfg.composition_template:
        value = compose_slot_value(entity, cfg.composition_template, cfg.composition_skip_empty)
    elif cfg.linkable:
        value = entity_relationships_projected_via_display_field(...)
    elif cfg.lookup_for:
        value = walk_linked_slot_and_project_target_field(...)
    else:
        value = resolve_source_field(entity, cfg.source_field)  # IMPORTANT: pass entity, not entity.data

Resolver direction is load-bearing: resolve_source_field (in epistemic/services/composition.py) walks dotted paths via getattr then dict.get. So data.Lemma Word walks getattr(entity, "data")["Lemma Word"]. Passing entity.data here would walk entity.data["data"]["Lemma Word"] and silently return None.

Data flow (write — the JSONB-mirror pattern)​

The standard Django ModelForm renders EpistemicEntity.data as <textarea name="data"> (JSONField widget). It already handles save/audit/save-and-continue. Rather than reinventing this with a custom view, the KE term-form overlay LAYERS slot-driven inputs ABOVE the same form, with JS that mirrors slot values into the hidden textarea on every keystroke:

// templates/admin/ke/_term_form_overlay.html
document.addEventListener("input", function (e) {
  var input = e.target;
  if (!input.classList.contains("ke-slot-row__input")) return;
  var row = input.closest(".ke-slot-row");
  var path = pathFromSource(row.dataset.source);  // strip "data." prefix
  if (!path) return;  // slot points at a model attribute, not JSONB
  var ta = document.querySelector('textarea[name="data"]');
  var data = JSON.parse(ta.value || "{}");
  data[path] = input.value;
  ta.value = JSON.stringify(data, null, 2);
});

On Submit, Django's standard ModelForm validates + saves the JSONField; reload re-evaluates composition templates server-side. The slot rows are now READ from the saved data, completing the cycle.

Limitation: shallow paths only. Multilingual / list-of-dict slots (translations, descriptions) read correctly but the JS sync writes a flat string to the JSONB if you type into them. A proper writer for nested kinds is a follow-up.

Slot-config invariants (per tenant)​

For atlomy_atlas TERM (post 2026-05-07 cleanup, 31 slots):

  1. First slot by display_order IS the primary identifier. No other declaration is needed — the changelist Preview column, the public reader's <title>, and the term form's headline all resolve from this slot.
  2. composition_template slots compose from data.X placeholders. Empty placeholders are skipped if composition_skip_empty=True.
  3. Plain slots' source_field MUST start with data. for atlomy_atlas (Coda-imported data lives in JSONB). A bare slot name (e.g., lemma_full) walks entity.lemma_full, which is a model attribute / property — useful only for derived/computed surfaces.
  4. Slot configs are tenant-scoped. Cleaning atlomy_atlas's slots doesn't affect jpp / visionis. Each tenant maintains its own.

CSS variable cascade — Unfold + KE coexistence​

Unfold's Tailwind classes use var(--color-base-{50,100,...,900}) etc. The KE skeleton injects an inline <style id="ke-color-overrides"> AFTER Unfold's <style id="unfold-theme-colors"> that:

  • Maps --color-base-50…950 to KE's surface ramp (canvas → ink-1)
  • Maps --color-font-default-light/dark, --color-font-important-light/dark, etc. to KE ink shades
  • Maps --color-primary-50…700 to the active --tenant-accent family

Critical: the ramp does NOT flip in dark mode. Tailwind's dark: prefix on classes already does the swap (e.g., bg-white dark:bg-base-900 → in dark mode, dark:bg-base-900 wins → reads var(--color-base-900)). If you flip --color-base-900 to a LIGHT value in dark mode, you'll cause dark:bg-base-900 to render LIGHT — opposite of intent.

Floating Tweaks widget — placement choice​

The widget lives at the END of <body> in skeleton.html (NOT in nav-global-side block) because Unfold's change_form.html and change_list.html both define {% block nav-global-side %} themselves to host their own "Add" button. Any child override of nav-global-side (e.g., in base_site.html) gets clobbered by the leaf templates on those pages.

The position: fixed widget is universal; it appears on login, dashboard, changelists, change forms — wherever the skeleton renders.

Per-archetype filter sidebar entries with live counts​

atlomy/settings.py:_ke_archetype_counts() runs ONE GROUP BY query against EpistemicEntity.archetype per page load (~5ms). The result feeds the sidebar lambda in UNFOLD['SIDEBAR']['navigation'], producing entries like Terms 1.2K, Documents 79, Passages 5.9K. Failure modes (e.g., partially-migrated tenant) degrade silently; the sidebar still renders without counts.

How this co-exists with ADR-015 (Native React shell)​

ADR-015 prescribes a Native React tenant admin shell at /app/admin/ as the long-term destination. The KE Admin Overlay is the working surface UNTIL that lands. They are not mutually exclusive:

  • The KE Admin Overlay extends Django Admin via templates + small JS — leverages auth, audit log, save-and-continue, list_filter for free.
  • ADR-015's Native React shell would replace the entire /admin/ for tenant-data work with React + GraphQL.
  • Both share the same data substrate (EpistemicEntity + TenantArchetypeFormConfig) and the same public reader preview at /term/<uuid>/preview/.

When ADR-015 ships, the KE Admin Overlay is deprecated for tenant-data work; the Django Admin stays available for platform-admin / debugging.
