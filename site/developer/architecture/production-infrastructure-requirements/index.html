Production Infrastructure Requirements (provider-neutral)

Date: 2026-06-10. Status: canonical requirements statement for cloud provider conversations (drafted for the Google / Microsoft infrastructure consultations; provider-neutral by design — requirements here, provider mappings in the meeting). Cost baselines: the dated us-east-1 worksheet (docs/research/2026-05-01_search-engine-comparison/2026-05-14_search-engine-tco-us-east-1-worksheet.md) under its own "dated planning numbers, not a quote" discipline. Ops detail: docs/runbooks/worker-tier-deployment.md. Operational home / index for all deploy material: deploy/README.md (IaC, provider comparison, costs).

R1 — Compute: web tier + REQUIRED worker tier​

The platform ships as containers (web app, async worker, scheduler, edge proxy). The worker tier is a production REQUIREMENT, not an option (decision 2026-06-10, supersedes the "Option 1/Option 2" framing of the 2026-06-10 cost brief as to whether a worker runs at all): long-running imports/materializations MUST NOT run inside web-serving processes. What remains flexible is placement — co-located on the web host (PoC floor) vs a separate machine/instance group (trigger-gated by telemetry). The dispatch substrate (DB-ledger claims via SELECT … FOR UPDATE SKIP LOCKED, beat sweeper recovery, retryable resume on incomplete runs) and the artifact storage abstraction (ADR-054 increment-B, shipped 2026-06-10) make placement a config decision: a worker with no shared filesystem replays imports via object storage — proven by an automated falsification test.

  • PoC floor: 1 small VM (2 vCPU / 4 GB class) running all containers.
  • Growth shape: web + worker split; worker scales horizontally (ledger-claimed jobs are safe under N workers).

R2 — PostgreSQL (the system of record) + the extension question​

Schema-per-tenant multi-tenancy (django-tenants): one PostgreSQL database, one schema per tenant + a shared public schema. Today Postgres 14; JSONB-heavy (hybrid relational+JSON ontology per the platform principles).

The managed-Postgres extension question — RESEARCHED (2026-05-26), now a confirm-or-roadmap ask: no hyperscaler's managed-Postgres allowlist carries PGroonga or ParadeDB (RDS / Cloud SQL / Flexible Server ship the pg_fts + pgvector class only). DECIDED policy (WOL-R2 A3): the supplier-managed default is OpenSearch-class + in-Postgres FTS; the extension engines are explicit per-tenant opt-in on self-managed Postgres-on-compute (the system of record stays managed). Vendor ask: confirm the allowlist status or give a roadmap. Detail: deploy/cloud/providers.md.

R3 — Search: a MULTI-ENGINE substrate with per-tenant automated assignment​

This is not a pick-one-engine decision. The platform registers four engines (PostgreSQL FTS, PGroonga, ParadeDB, OpenSearch-class) behind one indexer protocol, and each tenant is assigned its engine by automated criteria: per-tenant corpus evidence (Gate-1 empirical runs over the tenant's own script/language/field shape) produces a structural recommendation + a curated passing-engines list, with per-record-kind overrides inside a tenant (engine_by_archetype) and a documented safe retreat path (e.g. pgroonga → pg_fts). A ratification gate (UnratifiedSearchEngineError) blocks unvetted selections in production (Spec 0009 Task 8; epistemic/services/indexers/registry.py).

Infra consequence: production hosts the substrate concurrently with per-tenant routing — by DECIDED deployment policy (WOL-R2 A3): managed default = OpenSearch-class + in-Postgres FTS everywhere; PGroonga/ParadeDB as explicit per-tenant opt-in on self-managed Postgres-on-compute (see R2). Note GCP and Azure offer no managed OpenSearch (self-host there; AWS/OCI do). The v1 legacy stack additionally runs Elasticsearch 7.10 until cutover.

R4 — Object storage​

Already assumed by the platform: media (S3-class is the configured default backend) + import artifacts (named storage alias, env-swappable backend — shipped 2026-06-10). Modest volumes (research corpora, not media streaming); tenant-prefixed keys; lifecycle/retention managed by the application.

R5 — Cache / queue: Redis-class​

One Redis (or compatible managed equivalent) with three logical roles: task broker (/0), task results (/1), short-TTL ephemeral credential + cache (/2 — deliberately separated; credentials never enter queues or the DB).

R6 — Tenancy, domains, TLS​

  • Subdomain per tenant (tenant.platform-domain) → wildcard DNS + wildcard TLS.
  • Optional custom domain per tenant (a research project presenting under its own university domain) → per-domain TLS issuance (ACME/managed certs) and host-header routing. The tenant→domain mapping is application-managed (django-tenants Domain model); the provider needs to make cert issuance and routing for N custom domains cheap and automatable.

R7 — AI services​

LLM calls are provider-pluggable (LLM_PROVIDER seam; AWS Bedrock today). For Google/Microsoft: Vertex AI / Azure OpenAI map onto the same seam. Usage shape: bursty, import-time enrichment + proposal generation; no training; no tenant data retention by the model provider (contractual requirement).

R8 — Transition reality: v1 runs alongside​

The v1 operational substrate (Django + MySQL + Elasticsearch 7.10 + React SPA) serves current users while v2 is built. Production hosting must carry both during the migration window: add MySQL-class + the v1 containers to the footprint until cutover.

R9 — Observability, backups, residency​

Container logs + metrics (the deferral-trigger metrics of ADR-055 must land on the provider's telemetry surface); automated DB backups with point-in-time recovery; EU/academic data-residency flexibility is a question to put to each provider (tenants are university research projects; residency expectations vary per institution).

R10 — Forward requirement: always-on compute for the realtime/event layer​

The ratified event-substrate + collaboration direction (design spec 2026-05-26; research 2026-05-29) imposes a compute-service constraint TODAY: the collab server is an always-on, long-lived WebSocket process behind an L7 WS-capable load balancer with sticky sessions. Rule: no timeout-capped serverless for platform compute (e.g. a 60-minute connection cap is disqualifying for that tier — on GCP this means GKE-class, not Cloud Run). Choosing compute services that satisfy R10 now avoids a forced migration when the collab layer ships.

What we ask a provider (meeting checklist)​

  1. Managed Postgres: extension support matrix (PGroonga / pg_search), HA + upgrade story for extension-bearing instances.
  2. The multi-engine concurrency shape: managed-search tier + extension engines running side-by-side, platform-routed per tenant — cheapest sound topology at ~100k-entry scale per the worksheet's scope.
  3. Container hosting for a small always-on footprint (web + worker + scheduler
    • edge) with a cheap PoC floor and a clean path to splitting the worker.
  4. Object storage + lifecycle, Redis-class managed service.
  5. Wildcard TLS + automated per-custom-domain certs at N≈tens of domains.
  6. LLM service mapping onto our pluggable seam; no-retention terms.
  7. Academic/research program pricing or credits; data-residency options.
  8. Both stacks during transition (v2 above + v1 MySQL/ES).
