Archetype Strategic Planning

Date: 2025-12-29
Status: PLANNING
Context: Emerged from Sprint 12 AI Schema Adaptation work

Background​

During Sprint 12, we implemented an AI-powered schema adaptation workflow. Initial implementation created new Django models dynamically (models_epistemic.py), which was later identified as an anti-pattern that violates core architectural principles.

This led to a deeper investigation into the correct archetype-based architecture.

Critical Questions & Answers​

Q1: Should researchers create new canonical models?​

Initial Implementation (Anti-pattern A):

  • Researchers create "Book" table in retired external no-code surface
  • AI approves → New Book model created in models_epistemic.py
  • Migration runs → New PostgreSQL table
  • Problem: Canonical namespace explosion, cross-tenant collisions

Correct Architecture (Pattern B):

  • Researchers create "Book" table in retired external no-code surface
  • AI maps to existing DocumentArchetype
  • Data syncs to archetype model
  • TenantOntology records: "This tenant calls DOCUMENT 'Book'"
  • Benefit: Shared canonical structure, tenant-specific interpretation

Decision: Pattern B is correct and aligns with foundational principle: "Canonical structure is shared; interpretation is tenant-specific"

Q2: Should archetype capability contracts be programmatic or LLM-native?​

Answer from Consultant:

Both - but with strict hierarchy:

  1. Programmatic contract = source of truth

    • Deterministic, diffable, reviewable, enforceable
    • Lives in code, versioned, tested
    • Independent of LLM behavior

  2. LLM artifacts = adapters, not authorities

    • agents.md - how AI reasons about archetypes
    • Tool schemas - how AI proposes mappings
    • Skill definitions - how AI interacts with system
    • These reference the contract, never define it

Litmus test: "Can we run this system with LLMs turned off?" If answer isn't yes → contract is in wrong place.

Recommended Structure:

class ArchetypeContract(TypedDict):
    name: Literal["DOCUMENT", "TERM", "ENTITY", "EVENT", "MEDIA", "RELATIONSHIP"]
    description: str
    
    required_fields: dict[str, FieldSpec]
    optional_fields: dict[str, FieldSpec]
    
    allowed_operations: list[Operation]
    forbidden_operations: list[Operation]
    
    relationship_capabilities: list[RelationshipRule]
    
    promotion_rules: PromotionPolicy
    validation_rules: list[Invariant]

Q3: Should we pause for an archetype definition sprint?​

Answer: YES - Non-negotiable

Why now is the correct moment:

  • ✅ Dynamic model creation removed → archetypes ARE the extension point
  • ✅ AI is schema-aware → needs stable targets
  • ✅ Frontend is archetype-driven → assumptions will harden fast
  • ✅ Governance is formalized → archetypes are platform law

If we don't pause now:

  • Archetypes will be defined implicitly, inconsistently, under deadline pressure
  • Encoded across migrations, UI hacks, prompt logic
  • Exactly the failure mode we're trying to avoid

Proposed Archetype Definition Sprint​

Scope: 1-2 weeks max​

Output 1: Archetype Inventory (Hard Limit: 6-8 total)​

Strong Candidates:

  • DOCUMENT - Books, Sources, References, Texts
  • TERM - Lemmas, Concepts, Vocabulary
  • ENTITY - People, Places, Objects
  • EVENT - Timeline entries, Historical events
  • MEDIA - Images, Videos, 3D Models
  • RELATIONSHIP - Connections between entities

Possible:

  • COLLECTION - Grouped entities (optional)
  • ANNOTATION - Comments, notes, glosses (optional)

Test: If it feels easy to add → it's probably epistemic, not canonical

Output 2: Archetype Capability Matrix​

For each archetype, define:

AspectExample (DOCUMENT)
Core fieldstitle, content, author (non-negotiable)
Allowed relationshipscan reference other DOCUMENTS, ENTITIES
Forbidden patternscannot have temporal ordering (that's EVENT)
Expected lifecycledraft → review → published → archived
Typical tenant labels"Book", "Source", "Reference", "Text"
Promotion boundariesretired external no-code surface table → DOCUMENT if has title + content

Capability Contract Example (REFINED):

DOCUMENT_CONTRACT = {
    'name': 'DOCUMENT',
    
    # What is meaningfully possible
    'semantic_capabilities': {
        'can_be_cited',
        'has_content_structure',
        'supports_authorship',
    },
    
    # What the platform offers
    'platform_capabilities': {
        'full_text_search',
        'citation_graph',
        'versioning',
        'embedding_pipeline',
    },
    
    # What tenants can control
    'permission_flags': {
        'allow_embedding',
        'allow_versioning',
        'allow_public_citation',
    },
    
    'required_fields': {
        'title': CharField(max_length=500),
        'content': TextField(),
    },
    'optional_fields': {
        'author': CharField(max_length=255),
        'publication_date': DateField(),
    },
    
    # CRITICAL: Relationship types must be declared
    'allowed_relationships': [
        RelationshipRule(
            from_archetype='DOCUMENT',
            to_archetype='ENTITY',
            relationship_type='MENTIONS',
            bidirectional=False,
        ),
        RelationshipRule(
            from_archetype='DOCUMENT',
            to_archetype='DOCUMENT',
            relationship_type='CITES',
            bidirectional=False,
        ),
    ],
    
    'forbidden_operations': {
        'temporal_ordering',  # That's EVENT
        'media_streaming',    # That's MEDIA
    },
    'promotion_rules': {
        'required': ['title', 'content'],
        'confidence_threshold': 0.85,
    },
    
    'invariants': [
        'title must not be empty',
        'content length > 10 characters',
    ]
}

Why Three Capability Layers:

  • Prevents conflating "DOCUMENT supports embeddings" (semantic) with "Embedding pipeline exists" (platform) with "This tenant uses embeddings" (permission)
  • Keeps AI honest about what's possible vs what's enabled
  • Makes system composable

Output 3: Explicit Non-Archetype List (CRITICAL - HARDENED)​

Things that must NEVER become archetypes:

❌ "Book" - this is a tenant label for DOCUMENT
❌ "Source" - this is a tenant label for DOCUMENT
❌ "Manuscript" - this is a tenant label for DOCUMENT
❌ "PersonRole" - this is archetype_data on ENTITY
❌ "Gloss" - this is a tenant label for ANNOTATION
❌ "Edition" - this is archetype_data on DOCUMENT

Why this matters: Prevents slow schema inflation via well-meaning approvals.

Rule: If multiple tenants would call it different things for the same semantic concept → it's a label, not an archetype.

GOVERNANCE LOCK (New): If a term appears in the Non-Archetype List, it may never be promoted without:

  1. A formal ADR documenting why the earlier exclusion was wrong
  2. Written refutation of original reasoning
  3. Architecture team + consultant sign-off

This creates architectural memory.

Output 3.5: RELATIONSHIP Archetype Governance (CRITICAL)​

RELATIONSHIP is the most dangerous archetype - it can silently undo all discipline.

Problem: Free-form relationships lead to graph collapse:

  • RELATED_TO
  • ASSOCIATED_WITH
  • MENTIONS
  • IS_KIND_OF
  • ...and the graph becomes useless

Solution: Relationship types must be declared in archetype contracts

Workflow:

  1. AI suggests a relationship type
  2. Humans approve it
  3. Once approved, it becomes part of the contract
  4. Future instances of this relationship type are validated against the contract

Contract Structure:

RELATIONSHIP_RULES = {
    'DOCUMENT_MENTIONS_ENTITY': RelationshipRule(
        from_archetype='DOCUMENT',
        to_archetype='ENTITY',
        relationship_type='MENTIONS',
        bidirectional=False,
        cardinality='many_to_many',
        required_metadata=['confidence', 'context'],
    ),
    'DOCUMENT_CITES_DOCUMENT': RelationshipRule(
        from_archetype='DOCUMENT',
        to_archetype='DOCUMENT',
        relationship_type='CITES',
        bidirectional=False,
        cardinality='many_to_many',
    ),
}

Enforcement:

  • RELATIONSHIP model validates against declared rules
  • AI cannot propose relationships not in contracts
  • New relationship types require archetype contract amendment

This turns relationships into first-class ontology, not loose edges.

Output 4: ADR or Canonical Doc​

Deliverable: Either:

  • New ADR: "ADR-005: Archetype Capability Contracts"
  • Extension to Platform Principles

Must include:

  • Programmatic contract structure
  • Archetype inventory (the 6-8)
  • Non-archetype list
  • Evolution rules (when to add new archetype: ≥3 tenants, pattern proven)

Strategic Insight: The Moat​

What most "AI-native" systems do:

  • Let the model invent structure
  • Try to clean up later
  • Result: chaos

What we're doing:

  • Fix the structure (archetypes)
  • Let AI operate freely within it
  • Result: speed + correctness, adaptability without chaos

This is the defensible moat:

  • Competitors: "We support X data types"
  • Us: "We support X capabilities across any data shape"
  • Ontology becomes product, not infrastructure

Why: Archetypes are law, not implementation detail. Once code exists, contracts get retrofitted instead of designed.

Key Architectural Principles (Reinforced)​

  1. Canonical structure is shared; interpretation is tenant-specific

    • Archetypes = shared
    • Labels + JSON = tenant-specific

  2. Tables define what can exist; JSON defines how it's expressed

    • Archetype models = what exists
    • archetype_data JSONB = how tenants express it

  3. Archetypes are rare, platform-level events

    • ~1-2 per year
    • Requires ADR
    • Needs ≥3 tenants showing pattern

  4. AI proposes; humans approve; system enforces

    • AI suggests archetype mappings
    • Humans approve
    • Programmatic contracts enforce

  5. Programmatic contracts are source of truth

    • LLM artifacts reference, never replace
    • System works with LLMs off

Consultant Refinements (2025-12-29)​

Architectural Verdict​

✅ Plan is correct, mature, and unusually disciplined
✅ Demonstrates second-order thinking and resistance to AI-induced schema drift
✅ This is a defensible moat

Critical Refinements Applied​

  1. Three-Layer Capability Structure

    • Semantic capabilities (what is meaningfully possible)
    • Platform capabilities (what the system offers)
    • Permission flags (what tenants control)
    • Prevents conflation of "supports" vs "exists" vs "enabled"

  2. RELATIONSHIP Archetype Governance

    • Relationship types must be declared in contracts
    • Free-form relationships forbidden
    • Turns relationships into first-class ontology

  3. Hardened Non-Archetype List

    • Promotion requires formal ADR
    • Must refute original exclusion reasoning
    • Creates architectural memory

  4. Sprint 13 Kill Switch

    • No persistence/GraphQL code without finalized contracts
    • Prevents contract retrofitting
    • Archetypes are law, not implementation detail

Additional Tests​

"LLMs Off" Test: Can the system run without LLMs? If not → contract is in wrong place.

"Junior Engineer" Test: Can a junior engineer enforce this contract without understanding AI? If yes → contract is correctly placed.

"Boring" Test: After Sprint 13, archetypes should feel boring. That's how you know they're right.
