KE Security Principles

Status: Draft, active guard rail Date: 2026-05-12 Related: TENANT_ISOLATION.md, Spec 0009, ADR-001, ADR-017, ADR-023, ADR-029

Purpose​

This document records the security posture KE development should preserve while the V2 platform line evolves. It is intentionally high level: implementation details live in API_SECURITY_IMPLEMENTATION.md; tenant database mechanics live in TENANT_ISOLATION.md.

Security work should not become a parallel architecture. It is a constraint on the platform architecture:

  • canonical structure is shared;
  • interpretation is tenant-specific;
  • operational truth and public projections stay separate;
  • tenant context is derived by the platform, not supplied by the browser.

Principle 1 - Tenant Context Is Platform-Derived​

The tenant for a request is selected by trusted routing and middleware, not by a client parameter.

In the current Django stack, that means:

  • Host/domain resolves to request.tenant;
  • django-tenants sets connection.schema_name;
  • ORM and raw SQL must operate inside that active schema context;
  • public or API contracts must not accept raw schema_name as an authority.

A raw schema name may exist inside django-tenants implementation code, maintenance scripts, or trusted operator tooling. It is not a browser or public API contract.

Principle 2 - Identity And Authority Are Different​

Authentication answers "who is this actor?" Authorization answers "what may this actor do in this tenant?"

Every mutating surface must check both:

  • user identity from Django auth/session/JWT or a trusted service principal;
  • tenant role or platform role for the requested action.

is_authenticated alone is not enough for tenant-admin, import, publication, mapping, attestation, source-sync, or artifact mutation flows.

Principle 3 - Public Read Models Are Not Authoring Tables​

Spec 0009 public Entry Surface reads should use published projections, route maps, search indexes, and export snapshots. Public readers must not receive live draft authoring rows by default.

This protects:

  • private research notes and drafts;
  • partially imported rows;
  • failed or experimental enrichments;
  • unpublished tenant configuration changes;
  • citable public routes during rebuilds.

The publish path is the authorization boundary where private authoring state becomes public scholarly output.

Principle 4 - No Client-Supplied Authority Fields​

The browser may send intent, payload, and references. It must not send fields that decide authority.

Do not trust client-supplied values for:

  • schema_name;
  • tenant_id;
  • user_id;
  • actor;
  • role names;
  • publication state transitions;
  • filesystem paths;
  • internal object storage paths;
  • command names or management-command flags.

When such fields appear in legacy or transitional APIs, treat them as migration debt and either remove them from the contract or validate them against server-owned state before use.

Principle 5 - Mutations Are Explicitly Guarded​

Every mutation has a named policy before it writes:

  • public anonymous read-only;
  • authenticated tenant viewer;
  • authenticated tenant editor;
  • authenticated tenant admin;
  • platform staff;
  • platform superuser;
  • trusted internal worker/service principal.

The policy belongs near the entry point and should be visible in code review. Mutation resolvers and DRF actions should fail closed.

Principle 6 - Browser API Calls Stay Same-Origin And Mediated​

The SPA should use a small shared API layer rather than ad hoc fetch, axios, and GraphQL clients scattered across features.

The shared layer should enforce:

  • relative same-origin URLs for browser requests;
  • CSRF discipline for session-authenticated writes;
  • Authorization headers for JWT-authenticated calls;
  • consistent credentials mode;
  • typed error handling;
  • no absolute backend URLs from components.

This is the KE equivalent of the "frontend must route through the trusted proxy" Zero Trust pattern in Next.js/FastAPI projects.

Principle 7 - Sensitive Infrastructure Is Never Returned To The Browser​

The application must not return raw infrastructure credentials or unrestricted connection strings to normal users.

Examples:

  • database passwords;
  • database superuser names;
  • cloud access keys;
  • object-storage private paths when signed URLs or public manifests are the intended contract;
  • internal service secrets;
  • network topology beyond what a user needs to complete the workflow.

Developer tools that need infrastructure access should run server-side, through scoped service code, not by handing credentials to the browser.

Principle 8 - Public Assets Have An Explicit Access Model​

Every media and object-storage surface must be classified as one of:

  • public citable asset;
  • authenticated tenant asset;
  • temporary signed URL;
  • private/operator-only artifact.

Unsigned public URLs are acceptable only for content deliberately published as public. Draft uploads, imports, private annotations, and tenant source files need authenticated access or signed URLs.

Principle 9 - Auditable Work Beats Hidden Side Effects​

Security-relevant changes should leave records:

  • publication transitions;
  • source/import actions;
  • attestation overrides;
  • manual relationships;
  • role and membership changes;
  • source-sync and bulk update jobs;
  • public projection rebuild work;
  • failed authorization attempts when useful for operations.

For long-running or high-impact work, a ledger row such as PublicationWorkItem is preferred over a synchronous browser-triggered command.

Principle 10 - Security Gates Should Accelerate Spec 0009, Not Stall It​

The security posture should be applied as gates:

  • Immediate critical gate: remove credential disclosure and unauthenticated write paths before broader dogfood or tenant exposure.
  • Entry Surface gate: new Spec 0009 GraphQL/SPA surfaces must follow the shared API, auth, tenant-context, and projection-read rules from the start.
  • Public launch gate: CSP, media access, rate limits, audit coverage, and security regression tests must be green before public launch.

This keeps the V2 path moving while preventing insecure contracts from becoming the foundation of the Entry Surface.
