Security Architecture

Status: Index Date: 2026-05-25 Audience: Platform engineers

Why this index exists​

KE's security posture spans many code paths: schema-level tenant isolation, GraphQL resolver-level authorization, secrets brokering, CSP and content sanitization, payload-free telemetry with HMAC redaction and hash-chained integrity, bounded-agency AI assist contracts, per-tenant search isolation, and pre-commit lint gates. This index is the single entry point so engineers can find which document, ADR, or substrate file owns each guarantee, without first having to grep the repo. Read this before touching any cross-tenant, telemetry, AI-assist, secrets, or auth surface.

Core security tenets​

  • Tenant isolation is structural, not application-checked. Tenant context is set by django-tenants middleware as a Postgres search_path; resolvers never re-check it from a client field.
  • Every cross-tenant statistic obeys K-anonymity. Default floor K=5, configurable per environment via TIP_ROLLUP_MIN_K, clamped at the platform tier so a misconfigured env can never publish unredacted small-cohort signal.
  • Telemetry is payload-free at the platform tier. Per ADR-016, platform-tier events carry redacted identifiers and shape signals only; raw content stays in tenant-tier substrate.
  • HMAC redaction happens at the boundary, before any cross-tenant aggregator sees a row.
  • AI proposes, never applies. Per ADR-014-α, the in-product runtime is a single-call assist contract; mutations route through normal resolver authorization, never through the LLM.

Tenant Isolation​

KE deploys a shared-database, schema-per-tenant model on PostgreSQL via django-tenants. TenantMainMiddleware resolves the tenant from the request host and sets connection.schema_name; the ORM and any raw SQL operate inside that schema's search_path. Cross-tenant read or write that bypasses search_path is a runtime error path, not an application-level permission check — there is no equivalent of "ask if the row belongs to this tenant" because the row is not addressable from outside the tenant's schema. This is the load-bearing property: tenant isolation is structural, so an authorization bug in a resolver cannot leak data across tenants without first defeating Postgres search_path.

Tenant context propagates through GraphQL resolvers via info.context / request.tenant / connection.schema_name. Resolvers must never accept schema_name, tenant_id, or actor as authoritative client input — see SECURITY_PRINCIPLES.md Principles 1 and 4. A legacy endpoint that still accepts those fields treats them as validation input against server-owned state, not as authority.

The database schema visualizer (/dbvisualizer/schema/) is the only surface that explicitly reflects on schema metadata. Its introspector at dbvisualizer/services/introspector.py ignores any client-supplied schema_name and forces the active tenant schema; information_schema queries filter explicitly by table_schema. Schema metadata is acceptable to return; raw database passwords or unrestricted connection strings are not.

AuthN / AuthZ / RBAC​

Authentication uses Django auth/session/JWT plus a tenant-aware overlay. Authorization is layered: a TenantMembership per (user, tenant), a role bundle library (researcher-contributor, external-collaborator, reviewer-only, tenant-admin), and per-project rule overlays. Permission flags live on permissions_jsonb with an optional scope dimension that can narrow a grant to a project, archetype, or workspace. Enforcement happens at the GraphQL resolver entry point via a shared helper surface (require_authenticated_actor, require_tenant_role, require_platform_staff, require_platform_superuser) — see atlomyapp/security.py for the helper implementation and API_SECURITY_IMPLEMENTATION.md § "Tenant Role Helper Target" for the target shape.

The mutation policy matrix (API_SECURITY_IMPLEMENTATION.md § "Mutation Policy Matrix") names the minimum role required for each mutation class: publication and unpublication require tenant admin or a configured publisher role; source-import confirmation requires tenant admin/editor plus the import permission; tenant form and config changes require tenant admin; mapping proposal approval requires tenant editor/reviewer; artifact promotion to edition requires tenant admin/publisher; platform tenant provisioning requires platform superuser. is_authenticated is never sufficient on its own for a mutating surface — the role check sits next to the authentication check, not behind it.

The tenant-creating user gets a bootstrap permission grant (ADR-035 §3.1) so a single-contributor tenant — the common starting state for a new tenant — has a layered safety floor (§4.1) from day one. New tenants do not begin in a state where no one has admin authority.

Secrets Management​

External service credentials route through customers/services/external_credentials.py. The ExternalServiceCredential model never stores raw API keys; secrets are stored in AWS Secrets Manager and the model holds a reference (secret_backend, secret_arn, scoping metadata). The platform fetches the live value through boto3.client("secretsmanager").get_secret_value(...) at use time. See customers/migrations/0003_externalservicecredential.py for the schema and customers/services/external_credentials.py for the backend selector logic (SecretBackend.AWS_SECRETS_MANAGER is the live backend).

Rules:

  • New code paths that need a third-party API key must consume it via ExternalServiceCredential; never read a key directly from environment variables or settings except for platform-tier infrastructure secrets (database password, Django SECRET_KEY, etc.).
  • A credential's scope (tenant, service, role) is part of the model; resolvers fetch only credentials whose scope matches the active request.
  • The browser must never receive a raw credential — see API_SECURITY_IMPLEMENTATION.md § "Infrastructure Disclosure Rules".

Operational rotation and incident playbooks belong on the super-admin side; if no operator-facing document exists yet, contact the platform operator.

CSP and XSS Hardening​

Content Security Policy is configured in atlomy/settings.py under SECURE_CSP, using Django's built-in django.middleware.csp.ContentSecurityPolicyMiddleware (Django 6 native CSP). The production hardening checklist (remove unsafe-eval, replace unsafe-inline with nonces or hashes, tighten img-src away from broad https://*, drop localhost connect-src, keep HSTS and secure cookies enabled, define allowed frame-ancestors) is captured in API_SECURITY_IMPLEMENTATION.md § "Runtime And Header Rules" as a public-launch gate. The current development profile is intentionally permissive; tightening is gated on the public Entry Surface cutover.

XSS hardening in the SPA flows through the SafeRichContent component at spa/src/components/SafeRichContent/, which sanitizes user-supplied HTML via DOMPurify before parsing it with html-react-parser. The backend pairs that with nh3-based sanitization on rich-text fields ingested through the prose editor pipeline. The allowlists for both sides must be kept in sync — any new TipTap or ProseMirror extension that emits new tags or attributes needs the corresponding allowlist updates on both backend and frontend before it can survive a round trip. A sanitizer mismatch is a silent data-loss bug as well as a security risk: the backend strips an attribute the frontend would have rendered, or the frontend strips a tag the backend stored, and the user sees their content quietly mutated.

Replacement of the unmaintained react-html-parser (2018) with html-react-parser is in progress across the SPA; SafeRichContent is the migrated reference. New components must use the migrated path and must not introduce a fresh dependency on the legacy parser.

Telemetry and Privacy (ADR-016)​

The telemetry substrate (telemetry/) is a hybrid two-tier store. Tenant-tier events may carry full payloads inside the tenant's schema; platform-tier events are payload-free, with HMAC-redacted identifiers via telemetry/services/_redact.py. The platform-tier audit log is hash-chained, and integrity is verifiable end-to-end via telemetry/management/commands/verify_platform_event_chain.py.

The redact-before-log discipline is non-negotiable. Any new platform-tier event type must route its identifying fields through _redact.py before the row is written; a raw tenant-tier id, user id, or text payload arriving at the platform tier is a defect, not a performance optimization to revisit later.

K-anonymity is enforced at the cross-tenant rollup. recommendations/services/tip_rollups.py reads the platform floor TIP_ROLLUP_MIN_K from atlomy/settings.py (default 5 per Spec 0018; Spec 0030 §6.3 documents the rollup contract; Spec 0030 R4 absorption added the platform-tier clamp so a relaxed env value cannot lower the published floor below the platform minimum). Rollup queries that fall below K return no row rather than a small-cohort signal. The clamp is one-way: env can raise K above the platform minimum but cannot lower it.

DPIA refresh is triggered when telemetry surface area or retention changes; Spec 0018 PR #315 wired the refresh audit so a change to the substrate's privacy footprint cannot ship without a DPIA review entry. See ../../superadmin/dpia-operations.md for the operator-facing schedule.

AI-Runtime Security (ADR-014-α)​

The in-product AI runtime is a single-call assist contract: the LLM emits a proposal, the user reviews it, and the existing mutation pipeline executes the change under normal resolver authorization. The LLM never has a privileged code path to write. Multi-step agent loops (β) are explicitly deferred per ADR-014; any future change that introduces an autonomous apply path must be ratified before it ships.

The α activation establishes the security envelope around the assist contract:

  • Risk classification at apply time — proposed mutations are tagged at the apply boundary; high-risk classes (publication, schema change, contributor permission change) require an explicit confirmation phrase before the mutation runs. See Spec 0018 § C.2.4 and C.2.5. The phrase is a structural friction, not a UX detail.
  • Action-guard on ambient chat — Spec 0017 § C.3.8 blocks direct-mutation phrasing on the ambient chat surface before the LLM call. Users must move to the proposal surface to commit a change. This keeps the chat surface a read/advise channel even when a user types an imperative.
  • Voice and vocabulary substrate (ADR-044) — tenant-declared voice overrides and vocabulary substitutions constrain how the AI surfaces tenant terms, preventing cross-tenant terminology bleed. Universal platform code consumes tenant vocabulary through the substrate; it never hardcodes tenant-specific aliases (enforced by the lint_no_tenant_vocabulary pre-commit gate below).
  • Chat transcript retention regime (ADR-045) — chat transcripts are scoped to the tenant and bounded in retention; transcripts are not a recoverable substitute for the audit log. A user cannot rely on a chat transcript to prove a mutation happened or did not happen — only the hash-chained audit log carries that authority.
  • Bounded-agency tip surfaces — recommender tips and AI-surfaced suggestions follow the same pattern as the assist contract: they propose, the user decides. See Spec 0030 for the tip producer and the K-anonymity floor that governs cross-tenant tip evidence.

Search and Index Security​

Search is per-tenant. ADR-011 sets OpenSearch with ICU and per-language analyzers as the per-tenant search engine, with each tenant indexed in its own namespace. The SPA and GraphQL surfaces require a ratified search profile for a tenant before production search is permitted — calls to the search resolver against a tenant whose profile has not been ratified return an "Unratified search engine error" rather than silently falling back to a misconfigured index. This is enforcement, not a user-facing toggle: misratification is treated as an operational incident.

The ratified-profile gate exists because a misratified profile is a privacy hazard, not only a relevance problem: an index built with the wrong analyzer chain can leak partial tokens of fields the tenant intended to keep out of search. Failing closed is the only acceptable behavior.

Audit Log Integrity​

The audit log is hash-chained per ADR-016 § 3. Each platform-tier event references the hash of its predecessor; tampering with any historical row invalidates every subsequent hash. telemetry/management/commands/verify_platform_event_chain.py walks the chain and reports the first inconsistency. Verification can be run on demand by an operator and is suitable for periodic scheduled execution.

What the audit log is and is not:

  • It is the authoritative record of platform-tier security-relevant events: publication transitions, source/import actions, attestation overrides, role and membership changes, source-sync and bulk update jobs, projection rebuilds, and failed authorization attempts when those are useful for operations.
  • It is not a copy of user content. Identifiers are HMAC-redacted at the boundary; full payloads stay in tenant-tier substrate. A super-admin investigating an incident correlates platform-tier audit events with tenant-tier records through the redaction key, not by reading content from the audit log.
  • It is not reconstructable from chat transcripts, application logs, or browser history. Only the chain itself carries the integrity guarantee.

Super-admin incident query and recovery paths live under the super-admin docs.

Cross-tenant data flow boundaries​

Several KE features look superficially cross-tenant. They are not — they are tenant-scoped surfaces with a payload-free signal channel to the platform tier. Engineers touching these surfaces should keep the asymmetry clear:

  • Tip rollups — the cross-tenant aggregator reads platform-tier event rows (already HMAC-redacted at write time) under a K-anonymity floor. It cannot reach tenant-tier substrate. A tip surfaced in one tenant is derived from shape statistics across ≥K tenants, not from another tenant's content.
  • Federation and marketplace — see ../../superadmin/federation-and-marketplace.md for the federation model. Federation is explicit publish-and-pull, not background sync; a tenant's content does not appear in another tenant's reader without an authored publication step.
  • Search indices — per-tenant. There is no global cross-tenant search index. Operator dashboards that aggregate index health metrics consume metadata only.
  • Recommender metrics — see ../../superadmin/recommender-metrics.md. Metrics are platform-tier signals, not tenant-tier content.

If a new feature seems to require cross-tenant reads of tenant-tier substrate, treat that as an architectural decision and open an ADR; the platform's privacy posture is built on this asymmetry, and a casual exception erodes the rest of the model.

Pre-commit and Pre-push Security Lints​

Pre-commit gates enforce security-relevant structural rules. Install via bash scripts/install_pre_commit_hooks.sh once per clone. The hooks are configured in .pre-commit-config.yaml and run at both pre-commit and pre-push stages. Skipping the hooks (--no-verify) is not permitted on shared branches; if a hook fails, fix the underlying issue rather than bypassing.

  • scripts/lint_no_tenant_vocabulary.py --strict — audio-review-3 critique #5 structural guard rail (2026-05-01). Blocks tenant-specific vocabulary in platform code paths (epistemic/, data_import/, customers/). Tenant vocabulary lives in TenantArchetypeFormConfig, never inline. Suppression markers: # noqa: tenant-vocabulary (line) or # lint-no-tenant-vocabulary: skip in top-of-file docstring (file). Use sparingly and only for documented exceptions pending refactor.
  • scripts/lint_no_new_legacy_fields.py — blocks reintroduction of retired field shapes on epistemic models. Old shapes are a common surface for permission and provenance regressions.
  • scripts/atlas/check_no_tenant_hardcode.py — checks for tenant-slug hardcodes in code paths that should consume tenant config instead.

Adding a new security-sensitive surface​

When you add a resolver, view, importer, or AI-adjacent surface that touches any of: cross-tenant data, mutating writes, secrets, telemetry, search indexing, or AI proposals — walk this checklist before opening the PR:

  1. Tenant context — derive tenant from request.tenant / connection.schema_name; never accept schema_name or tenant_id from the client as authority. Validate any legacy client field against server-owned state.
  2. AuthZ — name the policy explicitly at the entry point. Pick a row from the mutation policy matrix or document why your case needs a new row. is_authenticated alone is not a policy.
  3. Secrets — if you need an external credential, fetch it through ExternalServiceCredential. Do not add a new env var for a per-tenant API key.
  4. Telemetry — if your surface emits platform-tier events, route identifiers through telemetry/services/_redact.py. If it touches a cross-tenant aggregator, confirm K-anonymity is enforced upstream.
  5. AI proposals — if your surface lets the user act on an LLM output, route through the assist contract; do not let the LLM trigger a mutation directly. Tag the proposed mutation's risk class.
  6. Sanitization — if your surface accepts or renders user-supplied HTML, route through SafeRichContent on the frontend and the nh3 sanitizer on the backend. Update both allowlists in lockstep if you introduce a new tag or attribute.
  7. Audit trail — security-relevant writes record an audit row. Long-running or high-impact work goes through a ledger row (e.g., PublicationWorkItem) rather than a synchronous browser-triggered command.
  8. Pre-commit gates — run the lint scripts above locally before pushing. If a gate flags your change, fix the cause rather than adding a suppression.
  9. Regression test — add or update a test from API_SECURITY_IMPLEMENTATION.md § "Security Regression Test Checklist" that covers your specific change.

If the change crosses an architectural line (new cross-tenant aggregator, new AI apply path, new public read surface, new tenant scaling assumption), open an ADR rather than slipping it through as an incremental commit.

Reporting Vulnerabilities​

For now, contact the platform operator directly. KE does not yet publish an external responsible-disclosure policy; that artifact is on the security roadmap.

When in doubt about whether something is a security issue, file it as one and let the operator triage. False positives are cheap; missed reports are expensive. Internal reporters should include the affected tenant, the surface (resolver, view, importer), a minimal reproduction path, and any audit-log references that bracket the suspected incident.
