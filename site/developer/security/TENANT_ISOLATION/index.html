Tenant Isolation Architecture

Status: Active tenant-isolation reference Related: SECURITY_PRINCIPLES.md, API_SECURITY_IMPLEMENTATION.md

Overview​

The Atlomy Platform deploys a Multi-Tenant SaaS Architecture using a "Shared Database, Separate Schemas" approach. This ensures strict data isolation between tenants while allowing for efficient resource usage and centralized updates.

This document covers database tenant isolation. It is necessary but not sufficient for full platform security. API authorization, GraphQL mutation policy, frontend request discipline, media access, and public Entry Surface gates are covered by:

  • docs/developer/security/SECURITY_PRINCIPLES.md
  • docs/developer/security/API_SECURITY_IMPLEMENTATION.md

1. Database Tenant Isolation​

We utilize django-tenants to manage PostgreSQL schemas.

Mechanism​

  • Schema Separation: Each tenant has a dedicated PostgreSQL schema.
  • Request Routing: Middleware (TenantMainMiddleware) intercepts every request, determines the tenant from the request host, and automatically sets the PostgreSQL search_path for that connection.
  • Data Safety: Standard Django ORM queries operate within this search_path. It is technically difficult for a developer to accidentally cross tenant boundaries because the connection context is scoped to the schema.

Active Protections​

LayerProtection Mechanism
MiddlewareTenantMainMiddleware resolves tenant from URL host. 404s if tenant unknown.
ORMAll queries run on a connection with SET search_path = [tenant], public.
Direct SQLAny raw SQL execution must explicitly assume the middleware has set the path.

Boundary Rule​

Client-provided tenant or schema identifiers are not authority. Browser/API contracts should not accept raw schema_name to decide which tenant to read or mutate. Trusted maintenance scripts and django-tenants internals may use raw schema names, but request-handling code should derive tenant context from request.tenant and connection.schema_name.

2. Database Visualizer Security​

The platform ships a single React-based schema visualizer (/dbvisualizer/schema/) that introspects the live PostgreSQL schema for the current tenant. The legacy DrawDB and ChartDB iframe-based designers were retired alongside the retired external no-code surface integration (see adr/018-retire-retired external no-code surface-and-data-wizard.md).

Risk Analysis​

Any schema-introspection tool requires careful scoping; cross-tenant data leakage is the primary risk if a request inspects the wrong schema.

Implementation Defenses​

The custom SchemaIntrospector service enforces isolation:

# dbvisualizer/services/introspector.py

def __init__(self, schema_name=None):
    # SECURITY CRITICAL: Strict Tenant Isolation
    # We ignore any user-provided schema_name and FORCE the current tenant's schema.
    current_schema = connection.schema_name
    self.schema_name = current_schema
  • Forced Scope: The introspector ignores client-side parameters requesting other schemas. It only reflects the schema active on the current database connection.
  • Filtered Views: The information_schema queries used by the introspector explicitly filter by table_schema = %s.
  • API Security: The visualizer endpoints are protected by @login_required and inherit the middleware's tenant context.

Credential Disclosure Rule​

Schema introspection must remain server-side. Visualizer APIs may return schema metadata, but must not return raw database passwords, cloud credentials, or unrestricted connection strings to browser users.

3. API & Data Access​

Django Admin​

  • Authentication: Standard Django Auth.
  • Authorization: Superusers see everything, but typical Staff users should be restricted by admin permissions and tenant role policy. Do not assume staff == trusted for new tenant-admin surfaces.
  • View Isolation: The Admin site only displays models present in the current tenant's schema.

GraphQL And REST​

Tenant isolation only answers "which schema is active?" It does not answer "is this actor allowed to perform this mutation?" New and existing APIs should follow API_SECURITY_IMPLEMENTATION.md:

  • derive tenant from middleware;
  • derive actor from Django auth/JWT;
  • require tenant/platform roles for mutations;
  • avoid AllowAny on write-capable views;
  • avoid CSRF-exempt browser-session mutation paths unless an explicit replacement auth contract is in place.

Future Improvements (Roadmap)​

  1. Row Level Security (RLS): For sensitive shared tables, implement Postgres RLS if shared-table designs re-enter the architecture.
  2. Dedicated DB Users: In high-security environments, evaluate separate PostgreSQL roles per tenant or per service class.
  3. Security regression tests: Add tenant-switch, unauthenticated mutation, credential non-disclosure, and public/private media-access tests alongside the surfaces they protect.
