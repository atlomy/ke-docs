Platform-Principles Enforcement (Code Gates)

Atlas v2 enforces its foundational platform principle — canonical structure is shared; interpretation is tenant-specific (see docs/developer/architecture/platform_principles.md) — through automated code gates. Tenant-specific values live in TenantArchetypeFormConfig and similar runtime config tables, never in platform code.

This page documents the enforcement layer: what's checked, where, how to suppress legitimate exceptions, and the constraints that make these checks honest.

What's enforced (two complementary gates)​

Gate 1: Tenant-slug comparison branches — scripts/atlas/check_no_tenant_hardcode.py​

Forbids: code branches that switch behavior on tenant identity, e.g.

if tenant.schema_name == "atlomy":         # ❌ FAIL
    use_lemma_table = True
elif tenant.schema_name == "visionis":     # ❌ FAIL
    use_term_data = True

Why: tenant-specific behavior must come from per-tenant config rows (TenantOntology, TenantArchetypeFormConfig, archetype registry), not from if/elif chains. Per ADR-012.

Patterns caught: tenant.schema_name == "...", tenant_id == "...", tenant_slug != "...", etc.

Allowlisted paths: tenant-bootstrap scripts (create_<tenant>_tenant.py), tests, migrations, docs, the script itself.

Gate 2: Tenant-vocabulary string literals — scripts/lint_no_tenant_vocabulary.py​

Forbids: tenant codename + tenant-domain field-name string literals anywhere in platform-level packages, e.g.

# In epistemic/services/some_module.py
KNOWN_TENANTS = ["visionis", "jpp"]                  # ❌ FAIL
FIELD_HEURISTICS = {"TERM": ["TRANSCRIPTION"]}       # ❌ FAIL
default_dbname = "atlomy_atlas"                      # ❌ FAIL

Why: even without an if branch, hardcoding tenant codenames or tenant-domain field names means platform code knows what a tenant is supposed to look like. Audio-review-3 (2026-05-01) critique #5 documented the recurrence of this failure pattern across multiple sessions.

Vocabulary catalogues:

  • Tenant codenames: atlomy_atlas, visionis, jpp, roman_law
  • Tenant-domain field names: ATLOMY (lemma_full, morph_1, ancient_words, …), VISIONIS (TRANSCRIPTION, TRANSLATION, LEXICON ID, AUTHOR NAME, SUBJECTS)

Update both lists as new tenants/vocabulary are caught (see "Adding new vocabulary" below).

Scanned paths: epistemic/, data_import/, retired external no-code surface/, customers/ (the platform packages where v2 work happens).

Allowlisted paths:

  • tests/, docs/, migration files matching *_seed_*.py
  • atlomyapp/ (the original tenant app; intrinsically carries Atlomy vocabulary)
  • epistemic/services/proposals/blacklist.py (the audit denylist module — by-design enumerates tenant identifiers so the prompt module can be greppedfor them)
  • The lint script itself

Suppression (escape hatches)​

Use these when the lint flags a legitimate use; do not silently bypass.

Inline # noqa: tenant-vocabulary​

For single-line uses where tenant-name examples are genuinely useful:

# CLI help text genuinely benefits from concrete tenant-name examples.
parser.add_argument(
    "--schema",
    required=True,
    # noqa: tenant-vocabulary -- CLI --help text needs concrete examples
    help="Tenant schema (e.g. atlomy_atlas, visionis, jpp).",
)

The # noqa: tenant-vocabulary token can be on the same line as the offending string or on the line immediately above. When on the line above, it ALSO suppresses subsequent indented lines (multi-line list/dict literals).

File-level # lint-no-tenant-vocabulary: skip​

For known findings pending refactor — places where tenant vocabulary is currently hardcoded but flagged for removal:

"""
Module docstring.

# lint-no-tenant-vocabulary: skip
This module currently hardcodes ATLOMY-specific table names. Pending
platform-principles refactor: migrate to a per-tenant runtime config
row owned by the ATLOMY tenant, per ADR-012.
"""

Use sparingly. Each file-level skip MUST include a TODO trail describing what's blocking the refactor and where it's tracked. The intent: visible technical debt, not silent absorption.

Active file-level skips (as of 2026-05-01):

  • retired external no-code surface/services/working_db.py — ATLOMY_WORKING_TABLES list. Refactor to per-tenant runtime config.

How the gates run​

Pre-commit (developer's machine)​

Install once per local checkout:

bash scripts/install_pre_commit_hooks.sh

The installer is idempotent — it appends to any existing pre-commit hook rather than overwriting. After install, every git commit runs the lint; failures block the commit.

Pre-flight check (skill)​

skills/pre-flight-check/SKILL.md §6a is the manual run. Invoke before any commit touching platform packages:

python scripts/atlas/check_no_tenant_hardcode.py
python scripts/lint_no_tenant_vocabulary.py --strict

CI (GitHub Actions)​

.github/workflows/tests.yml runs both gates as fast-fail steps before the test suite:

- name: Atlas — no tenant hard-codes (Python)
  run: python scripts/atlas/check_no_tenant_hardcode.py

- name: Atlas — no tenant vocabulary in platform code
  run: python scripts/lint_no_tenant_vocabulary.py --strict

A failure on either step fails the workflow before tests run; PRs cannot merge.

Kiro hook (auto-run for Kiro users)​

.kiro/hooks/no-tenant-vocabulary-lint.kiro.hook (gitignored, local-only) prompts an agent to run the lint when files in scanned packages are edited. Equivalent to the pre-commit hook for the agentic-IDE workflow.

Adding new vocabulary​

When the platform onboards a new tenant or a new tenant-domain leak surfaces:

  1. Tenant codenames — update _TENANT_CODENAMES in scripts/lint_no_tenant_vocabulary.py.
  2. Tenant-domain field names — update _TENANT_DOMAIN_VOCABULARY in the same file.
  3. Run the lint to surface any pre-existing leaks the new vocabulary newly catches; either fix them or allowlist them with TODO trails.
  4. Update this doc — add the new tenant + its domain vocabulary to the catalogue lists above.

The lint's strength scales with the catalogue's completeness. Treat the catalogue as the running record of "what tenant vocabulary the platform has been tempted to absorb."

Why two gates, not one​

The audio-review-3 critique (2026-05-01) explicitly noted that the recurrent hardcoding pattern keeps surfacing in different shapes:

  • Round 1 (Session 04b): slotName === "attestations" checks in React components.
  • Round 2 (Session 05): _NAME_FIELD_HEURISTICS map in dict_generator.py.
  • Round 3 (Session 05): name/title "universal" fallback that wasn't actually universal.
  • Round 4 (Session 05): hardcoded Unicode-range script enumeration.
  • Round 5 (Session 05): Engine.OPENSEARCH_PAIRED leaking into the engine-agnostic protocol surface.

check_no_tenant_hardcode.py catches the comparison-based pattern (Round 1 shape). lint_no_tenant_vocabulary.py catches the string-literal pattern (Rounds 2–4 shapes). Round 5 is a different category (protocol leakage) caught by the protocol-test contract (tests/unit/test_indexer_protocol.py). The three layers cover the recurrence space.

If a sixth shape emerges, the principle is to add a sixth structural guard rail rather than relying on human review to catch it.
